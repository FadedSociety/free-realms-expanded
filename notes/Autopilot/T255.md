# T255: Recipe-book rows show the crafted product

## What changed

- `src/recipes.rs`
  - `RecipeCatalog::wire_rows` now takes `name_id`, `icon_id`, `tint_key` from
    the **output** (product) presentation first and falls back to the pattern
    presentation only when the product has no catalogue row. The row's final
    `item_definition_id` is the output id when it is positive and present in the
    loaded item catalogue, else the pattern id. Both converts use
    `u32::try_from(...).unwrap_or(0)`, so a negative/absent id cannot wrap.
  - New `CraftingJob::recipe_filter`: Chef 10, Blacksmith 12, Miner 9, replacing
    the profile id in `filter_type`. Chef/Miner are captured; Blacksmith 12 is
    (R) inferred from candidate rows 155/165 plus T033's 9/10/12 mapping. It is
    a recovered protocol enum, not a compiled gameplay tuning value.
  - Doc comments on `RecipeWireRow` and `wire_rows` state that the display and
    item fields are the product's and that a future row field must decide
    product-vs-pattern explicitly.
- `tests/recipes_wire.rs`: seven new tests plus two helpers
  (`loaded`, `emitted_row`, and a scratch catalogue copy for the captured row 51
  product). `CraftingJob`, `serde_json`, `sha2` and `fs` imports are test-only.

Files changed: `src/recipes.rs` (+43/−8, net +35), `tests/recipes_wire.rs`
(+270/−2); no other module. No hub file touched (net 0 in `gameplay.rs`,
`bin/osfr-gateway.rs`, `encounter.rs`, `gateway.rs`). Nothing deleted.

## Native evidence (IDA, this run)

- `0090a720` is the bounded `RecipeData` row reader. Decompiled field order: id,
  name, an `IconData` pair via `008caaa0`, description, +0x1c word, member byte,
  filter, component count/list via `008fc680`, item definition id, passes byte,
  +0x2c word. This is exactly the encoder order in `encode_recipe_row`.
- `008fc680` (`0090a720+0xf1`) reads the component list and calls `008db930`
  (`008fc680+0x55`), the 32-byte component reader.
- `00c8d170` (0x3f handler) dispatches operations 1, 2, 3 and 5. Op 1 reads the
  row through `sub_C8BE30` -> `00c8be78` -> `0090a720`; op 5 reads count and
  keyed rows through `sub_C8BEB0` -> `00c8bf32` -> `0090a720`.
- The self packet's recipe loop calls `sub_90B930` then `sub_90A720` for every
  row (`00944fe0+0x7b5` = `00945795`), after reading the count. The self packet
  and the 0x3f add/replace operations therefore share the exact same row type
  and reader.

Reconciliation with `notes/Research/Recipe Content.md`: that note says no
recipe row was found in the preserved **application traffic** (no 0x3f frame),
which still holds. The named rows are the preserved self packet's (opcode 12)
recipe section, not a 0x3f frame, but they are the same `RecipeData` structure
read by the same `0090a720` reader that 0x3f operations 1/5 use. They are not
self-data identity fields or reward-bundle entries. The fix stays in the 0x3f
`RecipeWireRow` encoder; the self packet is not retargeted.

## Security threat note (secure-code-guardian)

- A hostile client can send a recipe id in 26/24 or replay minigame result
  messages. This change adds no parser, no opcode and no client-supplied
  display/item value: row name/icon/tint/item ids come from the server-owned
  `recipes.json` and the server's item catalogue, and the learned set is server
  state. Unknown, unlearned, rank-locked or under-stocked ids are still refused
  before any state change by the unchanged `begin_recipe` validation (existing
  cooking/smelting/forging/recipe-book refusal tests, all green here).
- The item field is chosen only from the validated output id or pattern id; a
  negative/absent catalogue value becomes 0 with `try_from`, never a wrapped
  u32, so no out-of-range id is fabricated. The filter mapping is a compiled
  recovered enum table, not attacker-controlled and not a tuning value.
- No save, coin, trade, reward, role or chat path changed; no free grant or
  sell path was added. `wire_rows` takes `&self`/`&Inventory` and is read-only,
  so a missing-presentation path cannot consume a pending offer or item.
