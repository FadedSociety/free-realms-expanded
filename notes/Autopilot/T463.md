# T463: players near a boombox dance its sequence in lockstep (35/63) and stop on leaving, mounting or expiry

Sonnet builder (Opus lane rules), on the autopilot tip `f1965ae5`. T459 (catalogue) and T461 (press spawns the
box) are both on that tip, so the fleet research note's "predecessors unmerged" no longer holds. No earlier
`T463-*.patch` existed.

## What changed

- `src/boombox.rs` (owner of the whole slice, no hub touched):
  - `synchronized_animations(&[(guid, anim)])`: the 35/63 encoder. `u16 35, u16 63, i32 count`, then
    `{u64 guid, i32 anim}` per entry.
  - `Boombox::step_ms(step)`: longest clip over every model in `clip_ms`, `saturating_sub(blend_ms)`, 0 becomes
    1000 ms (R).
  - `Dance` (per synchronized box): sequence, step lengths, the models with clips, range, priority, the clock
    `(step, ends_ms)` and the `dancing` set (who has been sent the current step). `Placed::dance` is `None` for
    `independent` and `transform` rows. `Boomboxes::released` holds dancers of replaced or ended boxes for the next tick.
  - `Boomboxes::dance` runs at the end of `tick`: one owner box per eligible session (priority, then X/Z
    distance, then placement order), clock step, one 35/63 per recipient for everyone when a step begins or for
    newcomers only otherwise, and 35/8 idle for whoever stopped. `audience()` is dancer plus every session near
    them that `knows_character` (the `ride_fanout` rule, plus the dancer's own entry).
- `src/players.rs`: `PlayerRegistry::is_mounted(session)` over the existing `mounts` map. `set_mount` writes
  `MountTail::NONE` (removing the entry) for a summoned but unboarded ride, so only a seated rider counts.
- `src/bin/osfr_gateway/boombox_routing.rs`: one gateway test through the real tick; `viewer_as` gives a test
  viewer a player model. `deliver` and `tick` are unchanged: the library's `Sends` already carry the dance.

## Evidence

- 35/63 layout, IDA (shared broker, this run): dispatcher case 63 at `0x009316a0` builds the packet (`0x008eafc0`)
  and reads it with `0x00919c90`: header `0x008d6830` (two u16), then `0x008fc2d0` (i32 count, a loop that stops at a
  reader error and has no cap), then `0x008db2a0` per entry (u64, then u32). Each guid is looked up with
  `0x00984960` and played through `0x0096c780(anim, -1, 0, 0, 1, 0)`. 12 bytes per entry, matching the encoder.
- Idle: 35/8 animation 1 base is `loc_stand`, `AnimationTypes.xml:101` (`lab/working/OSFR.Client`);
  `piece_052::animation_packet` is the existing encoder. The private copies in `enemies.rs` and
  `encounter.rs` (`fn animation`) were not touched: switching them would not shrink this diff.
- Step lengths: Jingle Bell (878) step 3 is 10667 ms for models 1, 2, 61 and 11000 ms for model 60, so the
  length is 11000 - 600 = 10400 ms with the maximum and 10067 ms for model 1 alone. The clock test pins it.

## (R) choices

- Step length minus `blend_ms`, 1000 ms floor (brief; Sanctuary instead clamps the blend to `duration - 1`).
- Packet cap 64 entries (the client has none).
- Range is X/Z from the box's spawn point (brief). Sanctuary uses 3D from the spawn point; nobody has a native
  capture of either. A box needs `range_m` within the registry's interest radius (100 m now).
- Equal priority: the nearer box wins (brief), where Sanctuary rotates by least served. Only synchronized boxes
  compete: an independent or transform box with a higher priority does not suppress a synchronized one until
  those slices exist.
- A dancer who starts mid-step gets the current step alone (brief; Sanctuary sends idle and waits).
- One 35/8 on mounting (brief). Sanctuary sends two (base flag, then an `Unknown` flag); the native test the brief
  asks for decides it.
- The clock starts on the box's first tick, restarts nothing when nobody is near, and loops the sequence.
- Equal-priority, equal-distance ties go to the earlier box.

## Open gaps

- A viewer who walks into range of an already dancing player sees them idle until the next step (the longest
  Jingle Bell step is 10.4 s). Fixing it needs a per-viewer "told" set; left for the lead's native result.
- No native run (lead): two clients dancing in sync, mounting stopping the dance, `35/8 base 3550` to see whether
  the client picks a new slot per loop (`boombox-random-dances`).

## Structure

- Graph: `search_graph` on the autopilot-int project was not used; the owner is obvious from the brief and
  `boombox_routing.rs` (rg for `boombox`, `ride_fanout`, `knows_character`, `set_mount`, `animation_packet`). The
  callers of `Boomboxes::tick` and `spawn` are only `boombox_routing.rs` (`tick`, `place`).
- Modules touched: `src/boombox.rs` (+ about 220 lines of code and 330 of tests), `src/players.rs` (+6),
  `src/bin/osfr_gateway/boombox_routing.rs` (tests only).
- Hub files (`gameplay.rs`, `bin/osfr-gateway.rs`, `encounter.rs`, `gateway.rs`): net 0 lines. Nothing deleted.
- Cost per tick: with no live box, nothing (the early return is unchanged). With boxes, one extra pass over
  each box's already computed `near` set, one small map of eligible sessions, and `nearby_sessions` per dancer
  only on a step change or a join or stop. Nothing is saved; dance state is session-only.

## Checklist

1. A refusal changes nothing: no new request path or refusal. `dance` reads the registry and mutates only the
   box's own state; the press commit and its refusals are untouched (T461 tests still pass).
2. Rollback: no transaction here. The dance state lives in `Boomboxes`, which the gateway already clones with the
   world it stages (T461); `released` is inside it.
3. Deltas, not snapshots: nothing from inventory, coins or position is written. The tick reads live positions.
4. Busy rules: dancing is not an activity (no `Occupation`); it only reads `is_mounted`. A seated rider stops
   dancing; leaving the ride rejoins at the current step (test).
5. Entry paths: the only entry is the server tick. No client request starts, steers or stops a dance.
6. Reachable in production: `Boomboxes::tick` already runs from `boombox_routing::tick` in `step`; the gateway test
   `t463_two_dancers_get_the_step_through_the_real_tick_and_expiry_stops_them` drives the real press, tick and
   queue.
7. Reconnect: dance state is never saved. A reconnect is a new session: out of range it hears nothing, in range
   it is a mid-step joiner (test `a_disconnect_mid_dance_tells_nobody_and_does_not_stall_the_box`).
8. Every exit path restores the player: leaving range, mounting, expiry and replacement all send idle
   (`released` and the `gone` list); a disconnect or a zone change sends nothing because the client dropped the
   scene (`audience` returns nobody for a session that left the registry or the box's zone).
9. Economy: nothing granted, spent or saved.
10. Wire format: 35/63 and 35/8 checked against the client readers above; golden bytes in
    `the_packet_is_the_clients_layout`, and `steps()` in the tests re-parses count against byte length.
11. Unique ids: no new ids; box guids unchanged. Dancer guids are character guids.
12. Others see changes: every step and stop goes to the dancer and every nearby session that knows them
    (tests: lockstep, viewer filter, leaving, mounting, expiry).
13. Content works end to end: all eleven shipped synchronized rows dance (they share the same code path; Jingle
    Bell and the single-step totem are exercised); independent and transform rows send nothing (test).
14. Values in data: range, priority, blend and every clip length come from `boomboxes.json`. The 1000 ms floor and
    the 64-entry cap are sanity constants (R), not gameplay tuning.
15. Canaries break production code (run, then reverted): step length without the maximum over models failed the
    step-length test and the lockstep test; dropping the release on replacement failed `a_replaced_box_lets_its_dancers_go`;
    removing the mount check failed the mounting and the eligibility tests; skipping `knows_character` failed
    the viewer-filter test.
16. Session plumbing: untouched (`gateway.rs` and `osfr-gateway.rs` have no diff).
17. One player's error never stops the server: no `?`, no unwrap on client data, `saturating_add`/`saturating_sub`
    for times, `step_ms[step]` indexes a vector built with the sequence's own length (validated non-empty at
    load). A recipient whose queue refuses is skipped by `boombox_routing::deliver` (T461 test).
18. Type rules on the type: `Dance` documents each field; `Boombox::step_ms` owns the length rule; "mounted" is
    one method on the registry.
19. Hot path: the early return for no live box is unchanged, and a steady tick sends nothing and allocates only
    the per-tick eligibility map.

Threat note (secure-code-guardian): nothing a client sends reaches this code. A hostile client can influence
only its own pose, model (through its own outfit) and mount state, each already validated elsewhere. A client at
most dances or stops dancing; it cannot make the server list another player or exceed 64 entries per packet.
