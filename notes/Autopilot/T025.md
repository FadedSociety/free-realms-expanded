# T025 Harden load-sensitive bot tests

## What changed

- `tests/mount_bots.rs` now waits for the gateway's `session_ended` log after a
  logout before seeding a character, waits for both bots' `AddPc` views before
  the first state-changing mount request, and waits past the server's one-second
  spawn debounce from the observed first spawn.
- Login retry backoff no longer immediately queues another handshake after an
  unanswered `SessionResponse`; the retry waits for the gateway to drain.
- `tests/bot_acceptance_1016.rs` uses the same logout and peer-join waits. The
  equip refusal checks accept either the stated refusal or an out-of-order
  `38/5`, then assert that a `38/5` never follows. The quest journal test waits
  for the gateway's `rejected` or `unchanged` event instead of fixed pumps, and
  the relog check proves the restored selection by observing an `unchanged`
  selection response.
- Removed fixed pumps from warpstone travel/attunement and quest acceptance
  paths where the following save read or server answer already provides the
  completion condition.
- Negative assertions use bounded quiet windows. Movement pacing and handshake
  retry delays remain because they enforce protocol/debounce timing rather than
  waiting for an assertion to become true.

The saved attempt was present at
`lab/autopilot/patches/T025-a1.patch`, not at the task-relative path. Applying
that archive patch produced no rejected hunks and left no `.rej` or `.orig`
files.

## Reconstructed test rules (R)

- A bot login is complete for a multi-bot scenario only after its peer's
  `AddPc` is visible; a login reply alone does not prove shared-field join.
- A logout is complete only after the gateway logs `session_ended` with
  `client_disconnect`, because that event follows the character save write.
- Quest selection completion is observed through the gateway's structured
  `quest_journal` outcome event, not elapsed wall time.

No gameplay rules or server behavior changed. The edits only synchronize
existing tests with observable gateway state.

## Open gaps

- `a_handshake_is_answered_quickly_even_with_full_content` remains ignored
  because it records the existing W154-F1 server finding: the debug gateway can
  take seconds to load content before answering a handshake.
- The two-second quiet windows are still finite. They bound negative assertions
  after the gateway has answered, but they are not proof of arbitrary later
  activity on a system that is starved for more than that window.
- This is a test-only change; no native client run was required or attempted.
