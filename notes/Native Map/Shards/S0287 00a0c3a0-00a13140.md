## 1. GAQ = the client game-action queue (ui.gaq, 00a0c3a0 .. 00a0ebc0)

The range opens with the queue builders. Each builder

1. allocates a queue-item object (`GaqGenericNoResponse::vftable`, or `GaqItemTradeInvite` /
   `GaqItemGroupAnnounceEncounter` / `GaqItemDuelRequest` / `GaqItemInviteAndStartMiniGame` /
   `GaqItemClaimItem`, 00a0d320, 00a0d550, 00a0d840, 00a0dc20, 00a0e090);
2. takes the next id from the manager's counter `*param_1` and links `(id, item)` into the manager
   (`FUN_00a0ad20` / `FUN_00a0ac80` / `FUN_00a0ae60` / `FUN_00a0af00` / `FUN_00a0afa0` / `FUN_00a0b040`);
3. fills a `ClientLuaParam` array whose element 0 is the action name (`ItemReceived`,
   `FriendBeatHighScore`, `GameTopScore`, `PersonalHighScore`, `TradeInvite`, `GroupAnnounceEncounter`,
   `DuelRequest`, `FriendInviteToGame`, `ClaimNotification`);
4. calls the Lua function **`Gaq:AddGameAction`** through `FUN_009797a0`
   (string `01812058`, referenced by every builder).

The recovered client Lua (`lab/decompiled/client-ui/ScriptsBase.lua:31770`) shows exactly that entry point:
`AddGameAction = function(self, theType, theText, theCookie, param3..param9)` dispatching on `GaqTypes.*` and
creating UI/gaqitem.swf entries. So this whole block is **UI notification/queue code, not wire code** - the
action names are UI item types, and the transmitted accept/decline requests happen further up the Lua side
(outside this shard).

Manager side (ui.gaq): `00a0dae0` removes by id (hash buckets at `this+0x18`, id & 0x3f, chain at node[4]) and
mirrors the removal to Lua `Gaq:RemoveGaqItemById` (`01812040`); removal variants select by virtual vtable
slots 0x14/0x1c/0x20/0x28 (`00a0df40`, `00a0df80`, `00a0e030`, `00a0e740`, `00a0e770`, `00a0e7c0`,
`00a0e7f0`, `00a0eb90`); `00a0e9e0` propagates item status (slot +0xc) back to Lua. The singletons are reached
through thunks of the form `mov ecx,[ecx]; jmp` (`00a0d540`, `00a0d810`, `00a0daa0`, `00a0dfe0`,
`00a0e020`->`00a0bf80` which is itself a GAQ builder, `00a0e670`, `00a0e6c0`, `00a0eb40`, `00a0eb50`,
`00a0ebc0`).

`00a0c3a0` (class name from the caller log string `ClientRewardManager::PlayItemReceivedNotification`,
`00b899f0`) additionally performs an item-definition lookup (hash `id & 0x3ff`, key at +0xb4, chain +0xb0) and
logs `AddItemReceived - Failed to lookup item definition id: %d, receivedType: %s.` on a miss. It is reached
from the coin-store gift handler (`00c764f0` HandleCoinStoreReceiveGiftItem) and the transaction-complete
handler (`00c78220`), which ties the GAQ to the store reward path.

## 4. Console/debug text ring (debug, 00a0f640 .. 00a0f820)

A 500-line ring of wide-string entries (16-byte `IString<unsigned short>` elements at +0x1c), a write index
at +0x10, an oldest index at +0x14 and a dirty flag at +0x18, plus a file name built as `<ctor argument>` +
`.outEdit` (00a0f700). `00a0f7f0` appends text to the current line, `00a0f7a0` advances to the next line
(wrapping at 500 and dropping the oldest) and `00a0f820` flushes the ring into a `GuiEditCtrl` obtained
through `FUN_009f8dc0` (a `dynamic_cast` to `GuiEditCtrl`). Callers are the print handlers
`00901f10` (`OnPrintConsole`) and `009020c0` (`OnPrint`), plus the frame function `0094a970`; the destructor
`00a0f650` is called from `008a6020`.

## 5. Allocators and refcount helpers (engine.mem / engine.refptr / engine.containers)

00a13060/00a130a0), 0xe0/8 (00a12e30/00a12e70), 0x88/8 (00a12f10/00a12f50).

Six identical `RefPtrReleaseIfLive_*` bodies (`00a12ca0`, `00a12d40`, `00a12d70`, `00a12da0`, `00a13020`,
`00a13140`) release a member through virtual slot +0x28 (`FUN_0081ad80`) when `DAT_01be1090` is non-zero, and
twelve identical `RefPtrAssign_*` bodies (`00a112d0` + eleven clones) release the old object, store the new
one, acquire with `FUN_0081ce10` and drop the temporary reference. All twelve are assigned in a row by the
single caller `00a1de60` (outside the shard), so the twelve target members are only known from that caller.
