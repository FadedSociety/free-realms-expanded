# S0392 (00c42400-00c482e0) - client objectives, minigame goals, action-bar containers, minigame data sources

147 functions mapped. The range contains four connected families plus the engine container/allocator
machinery they use. Everything below is client-side evidence; every server statement is a labelled
hypothesis.

## 1. Client objective runtime (opcode 45 family)

The registry is a 100-bucket hash list: bucket array at manager+0x14, chains through node+4, key at
node+8, doubly-linked list head +8 / tail +0xc / count +0x10. Entry flags: byte +0x1c = enabled,
byte +0x1d = completed.

- Construct: `00c43010` (called from the minigame-manager constructor `009bc410`).
- Dispatch: `009be130` is the opcode-45 packet dispatcher. Its cases call, in order,
  `00c43090` (case 8, clear/disable: logs `Clearing objective %d`, clears +0x1c),
  `00c430e0` (case 9, failed: clears +0x1d only while enabled, logs `Server failed objective %d`),
  `00c435c0` / `00c436b0` (case 6, LookAt by guid / by location),
  `00c437a0` (case 10, UIEvent name), `00c43870` (case 11, FirstMovement isMouse),
  `00c43940` (case 12, HousingFixtureMove fixture+action). Each registration allocates a concrete
  ClientObjective subclass (`00cf3890`/`00cf35e0` LookAt, `00cf3920` UIEvent, `00cf3a00`
  FirstMovement, `00cf3aa0` HousingFixtureMove) and links it **unconditionally** - there is no
  duplicate-id check in any add path.
- Fan-out to live objectives: `00c43140` (vtable slot 3, the Lua `Ui.OnObjectiveEvent` path, the
  vault note [Original Opening Microtutorial Recovery] cites this exact address), `00c43180`
  (slot 2) and `00c431c0` (slot 1). Slot 0 is a no-op stub in all four ClientObjective classes, so
  the "poke" in `00c43490` is inert.
- Teardown: `00c43390` unlinks and frees the list head, `00c43440` wraps it with this+4,
  `00c43490` purges every disabled entry (and unlinks+frees them) at minigame start
  (`009bf5e0`).

Server contract (hypothesis, depends on the note's 45/7 completion frame and on `00cffba0`, which
sets +0x1d = 1 after sending): the original server registered one objective per id, accepted a
7-byte 45/7 completion only while the client entry was enabled and not completed, and used 45/8 to
retire an objective and 45/9 to re-arm it for a retry. Because the client never de-duplicates adds
and never validates the sender, duplicate registrations would double-create entries; the client
also frees disabled entries only at the next start/purge point.

## 2. Minigame goal states (45/1..4 HUD path)

Distinct from the client objectives: these are the minigame's own goal rows.

- `00c42a30` constructs the per-minigame object (~0x908 bytes plus the id at +0x918, set by
  `009b8190`); it embeds `SoeUtil::Array<MiniGameGoalState,0,1>` at +0x7c (buffer +0x80, count
  +0x84) with 0x110-byte elements.
- `00c42870` materialises one runtime goal from a data record: status +0x30 = 1 (NotStarted),
  count +0x44 / total +0x48 from the source's +0xd4/+0xd8, and a guaranteed display name (string
  table lookup, else the wide fallback `<OBJECTIVE %d>`).
- `00c42400` finds a goal by key; `00c42740` mirrors source counters and re-runs the formatter;
  `00c42440` is the status-text formatter: 1 NotStarted, 2 InProgress, 3 Completed, 4 Failed,
  5 failure-condition, 6 MembershipRequired, with the `ObjectiveProgressFormat` template for 2/5.
- `00c42bd0` (add, stride 0x110) and `00c42c60` (rebuild from the loaded source, one record per
  source index) maintain the array.
- `009b6700` (dispatcher case 3 / `ObjectiveComplete`) sets status 3 on the found goal and, when
  `goal+0x28 == 0` or `goal+0x2c != 1`, adds the amount argument to the per-category score counters
  at minigame+0x2fc (and bumps +0x2cc), with the category taken from goal+0x24 and limited to
  six values; it then fires the client event `ObjectiveComplete`. Case 4 (`009b6950`) is the
  failure counterpart.

Server contract (hypothesis): 45/1..4 records are keyed by the goal id, carry the per-completion
score amount, and come only while a minigame state exists (`*(handler+0x18) != 0` gates cases 1-4
in `009be130`). The client trusts the server for status and counts.

## 5. Minigame data sources (UI/Lua tables) and the boss packets

Registration names are literal: `00c472d0` BaseClient.MiniGameGoals, `00c473a0`
BaseClient.MiniGameScore, `00c47440` BaseClient.MiniGameGroup, `00c474e0` BaseClient.MiniGame /
BaseClient.LastMiniGame, `00c475e0` BaseClient.MiniGameData, `00c47680` BaseClient.MiniGame.Trophies,
`00c47d00` BaseClient.MiniGamePortal. Each object has the data-source vtable triple (+0/+0x30/+0x34),
slot 1 = column names (`00c45760`, `00c45800`, `00c45860`, `00c45a00`, `00c45af0`, `00c45bb0`,
`00c477c0`), slot 2 = row count (`00c45e20`, `00c45e40`, `00c470b0`, `00c47210`, `00c47910`), slot 4 =
value (`00c460e0`, `00c462a0`, `00c463a0`, `00c468c0`, `00c46c20`, `00c46e40`, `00c47930`), with
destructors and scalar deleting destructors at `00c46f30`..`00c47d90`. Column names are the most
useful new contract surface: the score row exposes Name/Icon ID/Score Type/Score Count/Score Max/
Score Points (stride 0x48, block at minigame+0x2cc+0x6c, count +0x70) and the group schema exposes
32 fields including `Price`, `Must Purchase Item ID`, `ShowStartScreenOnPlayNext` (and the typo
`ParentMiniGamed` preserved from the binary).

Boss packets: `00c47db0` builds `BaseMiniGameBossPacket` through the minigame base constructor
`008a4420` with sub-opcode 0x3e (family opcode 0x27 = 39 is written by that base constructor);
`00c47e80`/`00c47f70` add the discriminator 1 (update) / 2 (delete) at +0x14 and the packet vlables;
the handler `00c48c90` (shard S0393) reads a u32 discriminator from the wire, builds the matching
object, and applies it to the `MiniGameBossDataSource` rows through `00c48bd0` (id, type, float) and
`00c489b0`. `00c481f0` finds a boss row inside that source (entry array at +0x25c, count +0x260,
stride 0x20); `00c48240`/`00c482e0` are the `Array<MiniGameBossDataSource::Entry,0,1>` resize/free
vtable slots (S0393's `00c48a00` provides the entries). Column names: Name, Health (`00c48040`).

Server contract (hypothesis): a received minigame-family 39/62 record carries a 32-bit type marker
1 = boss update, 2 = boss delete, followed by the per-type payload (update: id, type/state, float
health fraction applied by `00c48bd0`; delete: id). Depends on S0393's `00c48620`, `00c489b0`,
`00c48b60`, `00c48bd0`.

## 6. Contradictions / clarifications against existing notes

- The vault's quest-objective work (opcode 49, e.g. `00c7a990`, `00c7aa10`, and
  [Research/Native Journal Live Objective Keys.md]) is a *different* system from both families
  here. Do not reuse its objective-key semantics for the 45/x client objectives or for the 0x110
  goal records; the goal key lives at record+0 and the client-objective key at node+8.
- The community packet catalogue (Sanctuary / FreeRealms-Legacy) has no rows for base opcodes 39
  or 45, so no catalogue class names could be cited for the objective or boss packets; the family
  and sub-opcode values above come from the client constructors and the dispatcher switch only.
  Consequence for this shard's records: the objective handler bodies (`00c43090`, `00c430e0`,
  `00c435c0`, `00c436b0`, `00c437a0`, `00c43870`, `00c43940`) carry no `wire` item, because the
  family/opcode numbers never appear as constants inside them - they are fixed in the packet
  registry consumed by `009be130`, whose case indices (8, 9, 6, 6, 10, 11, 12) are the only
  in-binary link. Adding "45/x" would have been unverifiable; the mapping is recorded here instead.

## 7. Open questions

1. Boss payload byte layout: the u32 discriminator is proven on-wire by the reader in `00c48c90`,
   but the exact field encoding after it lives in S0393 (`00c48620`/`00c48b60`) and was not
   verified here.
2. `00c429d0` calls the array constructor `00c42810` twice; Ghidra dropped both destination
   addresses, so the two score arrays' exact offsets are unresolved.
3. `00c44440` and `00c44470` are byte-identical code-3 broadcast loops; which caller owns which
   copy is unresolved (both are external).
4. `00c45b90` and the other lazy data-source hooks call base slots whose implementations
   (`FUN_010c8f30`, `010cb0e0`) were not mapped here.
5. No in-database caller exists for `00c42e90` (HashList buckets at +0x10); its class could not be
   bound, so it is kept as a mechanical constructor record.
