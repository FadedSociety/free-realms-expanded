## What changed

A 49/14 turn-in can fail to grant its reward: a full bag, a reward item missing from the catalogue,
a bad reward row, or a coin or XP amount past its wire field. Before this change,
`QuestEngine::finish_turnin` returned an `io::Error` for all of these. The combined `[0,25]`
request form re-raised that error and `Server::step` ended the session. Now:

- `rewards::apply_grant` returns a typed `GrantFailure` with the brief's seven variants:
  `BagFull`, `LockedProfile`, `UnknownItem`, `BadItem`, `WireRange`, `InvalidKey` and `Shape`.
  It implements `Display` and `Error`, plus `From<GrantFailure> for io::Error` (kind
  `InvalidData`), so every `?` caller still compiles. `progression_extras::apply_award` returned
  the grant as its tail expression, so it now converts with `Ok(...?)`.
- `finish_turnin` matches the failure in `refuse_turnin`:
  - `BagFull` -> `QuestDenial::NeedSpace`.
  - `WireRange` -> `RewardLimit`.
  - `UnknownItem`, `BadItem`, `Shape` and `InvalidKey` -> `RewardData`, plus one stderr line:
    `quest_turnin_reward_refused quest=<id> reason=<class>`.
  - `LockedProfile` -> the existing F249 `Job` denial, which releases the end screen.

  The three new denials pay nothing. They keep `pending_turnin` and `pending_turnin_actor`, leave
  the quest `Active`, and return the caller's `RewardState` unchanged. The duplicate locked-profile
  pre-check in `finish_turnin` is gone, because `apply_grant` already refuses that case as
  `LockedProfile`.
- `QuestDenial::message()` owns the one `(R)` line for each new denial.
  `append_npc_quest_outcome` sends that line as `chat::system`.
- `QuestEngine::abandon` (26/23) now clears a pending end screen for the quest it abandons. Before,
  it refused. The brief's step 4 assumed abandon "still" cleared the screen. At base it returned
  `Unavailable` whenever `pending_turnin == Some(quest_id)`. That guard dates from the baseline
  commit and has no recorded reason. Without this change, a `RewardData` refusal would trap the
  quest.
- The 49/14 arm still ends with `END_DIALOG_26_4`, and the next Talk reopens the held 49/13.
- **Brief step 5 (speak `QuestOutcome::messages`) is not built. The evidence contradicts it:**
  - On 49/4, the client formats its own localized completion line, `"%s %s"` (quest name +
    completed text), posts it, and fires `CompleteQuest`. IDA `0x00a928b0`, re-checked this run.
  - On 49/9 with the bool at 0 (the server's value), the client posts its own objective-status
    line. IDA `0x00a931b0`, re-checked this run.
  - Split quest titles are `Quest <id>` placeholders. `opening_order`, the only source of `Next:`
    lines, is set only by `QuestEngine::from_opening`.

  Speaking those messages would duplicate the client's text with raw ids. An earlier review called
  this a blocker; that review's canary is canary 4 in the earlier list below.

## (R) choices

- `(R)` Denial lines:
  - `NeedSpace`: "Your bag is full. Make room and turn the quest in again."
  - `RewardData`: "This quest's reward cannot be paid. You can abandon it from your journal."
  - `RewardLimit`: "You cannot receive this reward right now. Turn the quest in again later."
- `(R)` Each `GrantFailure` variant has one message, and most variants reuse an existing wording.
  `WireRange` has new wording: "reward coins or XP exceed the wire field". It merges the old XP
  total, coin and XP wire, coin balance and profile XP overflow texts. `BagFull` and `Shape` also
  merged several old texts.
  - No test or caller matched a dropped string (searched all of `src` and `tests` on this tip).
  - The other `apply_grant` callers now carry the merged wording: `enemies.rs:628` and
    `minigame.rs:582` (`?`), and `gameplay/derby_session.rs:213` (`{error}`).
  - `fishing_service.rs:1016` discards the error.
- `(R)` An `Inventory::grant` refusal after the row checks is `BadItem` (`RewardData` + log),
  because making room cannot fix it. That covers an over-stack row, an exhausted or corrupt
  item-id counter, and an encoding error. The exception: when the bag holds `>= MAX_ITEMS` stacks
  and `accepts_reward` passes the row, the failure is `BagFull`.
- `(R)` On the quest path, `WireRange` is always the player's wallet or XP. Every engine
  constructor runs `validate_definition`, which refuses a content row past `i32::MAX`.
- `(R)` A profile whose XP would pass `u32::MAX` gets "later", but no retry can ever succeed.
  Unrealistic, so not changed.
- `(R)` `apply_grant` checks its applied-key short-circuit before the locked-profile check. The old
  pre-check ran first. On the quest path the two orders differ only if a grant key was applied
  while `pending_turnin` is still set, and no normal path produces that.
- `(R)` Abandon releases a pending end screen for the same quest. Abandon still pays nothing and
  still refuses quests that are not active.

## Threat note (secure-code-guardian)

A hostile client can send 49/14, 26/23, 26/8, 26/10, 26/6 and 49/2 at any time, with any quest id.

- 49/14 settles only the saved `pending_turnin` with its recorded actor. The packet's quest id
  cannot pick another quest, and no part of the reward comes from the client.
- A refusal pays nothing. `apply_grant` stages the grant on a clone, and the denial returns the
  caller's `RewardState`. The tests assert snapshot and serialized-save equality. The grant key
  `quest:<character>:<quest>` limits a retry or replay to one payment.
- Abandoning a pending quest pays nothing and needs the quest to be `Active`. A re-offered quest
  must be completed again, and its grant key does not change, so abandon cannot be used to farm.
- The log line holds a fixed tag, a u32 quest id and the class name: no identity, chat or packet
  bytes. Only a broken content row or save can produce it. Repeated 49/14s are bounded by the
  gateway packet budget.
- No reward error uses `?` on the 49/14 path any more. The only `Err`s left there are the existing
  malformed-body decode and the "pending quest definition disappeared" server-state check.
