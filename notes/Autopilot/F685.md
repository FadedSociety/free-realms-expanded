## Threat note (secure-code-guardian)

- What a hostile client can send: `realm win` is a 15/1 chat string; the server parses only the text and
  gates it with `may_run` (`--dev-tools` or the account-store role) plus `can_run_realm_command`
  (Admin for `win`). A player without that gate gets the existing denial and no state change. An Admin
  in a content set with no engine now gets one system line and an unchanged session (the old code
  panicked; the gateway's `contain` turned that into a disconnect).
- The drop roll is not client-triggerable: it runs only on a server-observed battle win; item id,
  quantity and chance come from `field_battles.json` and are bounded at load.
- A capped wallet refuses the whole reward: one logged line plus one `chat::system`, returning `Ok`, so
  one player's cap cannot fault the shared tick for others. A full bag is **not** a refusal: it skips
  only the chance drop and pays the rest, silently (documented above).
- No client-reported item ids, quantities or results are read. The new code adds no new packet, no new
  persisted field and no `unwrap` on client data.
- Economy: the guard now asks the production `CoinShop::sell_unit_price`, so no store row, free-item
  rule or client-Worth fallback can make the 25% drop farmable without the test failing.

## (R) rules
