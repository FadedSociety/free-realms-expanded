## Lock fixes (third review)

### Moderation busy DoS

- **Before (L042 r3).** `osfr-login` took `AccountStoreLock` around every broker request past the
  cheap checks, reads included (opcode 11), and under it loaded the store, the resource tables and
  the store again. One modified authenticated client spamming opcode 11 (session bucket 200/s) kept
  the lock held, so every staff write answered "busy" after `STAFF_LOCK_WAIT` (50 ms).
- **Now.** Only a save takes the lock, and the lock lives where the save is (`src/login.rs`):
  - create (5) and delete (9) take it immediately before L055's `reload_account_store` and hold it
    through the save;
  - `authenticate_account` reads the file without the lock when it already holds this login's
    account (every broker login: `osfr-login` refuses a principal whose account is missing or
    keyless before the service runs, accounts are never removed, and saves replace the file by
    atomic rename). Only creating or migrating the store, or adding the account, goes through the
    new `add_account`, which takes the lock and re-reads the file under it (loopback mode only in
    practice).
  - `osfr-login`'s `application` is back to the tip's shape: no lock. `run` keeps L042's change:
    startup validates the store and refuses a stale lock, and holds nothing for its life.
- **Why in `login.rs` and not "lock opcodes 5 and 9 in osfr-login".** A lock around the whole
  broker request would still cover the resource-table load and two store loads per request, and a
  create with a taken name or a delete of a guid the client does not own is refused without ending
  the session. Spamming those would hold the lock as tightly as opcode 11 did. In `login.rs` the
  hold is one store load, the in-memory checks and (on success) the save. `osfr-login` is
  single-threaded and runs an unlocked prelude per request (principal load, resource tables, login
  re-check), so the lock is free between requests for longer than it is held, and a staff writer
  polling every 10 ms for 50 ms should find it free. This is reasoned from the code, not measured
  under load (R); the deterministic test is that a held lock no longer stops reads at all.
- **Busy writes.** A create or delete that still finds the lock held after `LOCK_WAIT` (500 ms) is
  refused with an error, which ends that login session as before (L042 r3 did the same for every
  non-login request); nothing is written. A busy key-pair login no longer exists, so L042 r3's
  "token stays unspent on a busy store" path and its test are gone with it.

### Silent lock leak

- `AccountStoreLock::drop` now prints `account store lock <path> could not be removed: <error>` when
  `remove_file` fails, on the request that leaves the lock, not the next one.
- `acquire_within` prints `account store lock <path> is held; request refused` once when it gives
  up. This moved from `osfr-login` (L042 r3), because login's lock is now taken in `login.rs`; it now
  also shows for the gateway's staff writes and `osfr-account`.
- No security log is in reach: the guard holds only a path, `SecurityLog` has one writer per file
  (the gateway's), and its closed schema is account and session ids. A lock leak has neither, so it
  is a host fault on stderr, not an audit row.

## Security

Threat note (secure-code-guardian, security-reviewer). Every boundary touched:

- **Login packets -> store writes (`login.rs`).** A hostile client controls the opcode and payload.
  Create and delete hold the writer lock across re-read, checks and save, so no other writer's
  change is lost; a refused create or delete returns before the save and writes nothing (store and
  identity bytes asserted). The lock is taken only after the payload decodes, so a malformed packet
  never touches it.
- **Login packets -> store reads.** Login, list, name check and select read the atomically replaced
  file without the lock; `replace_bytes` renames, so a reader sees the old or the new document,
  never a torn one. Rust opens files with delete sharing, so readers do not block the rename.
- **First login -> account creation.** Unreachable from broker traffic: the principal's account is
  checked on the file before the service runs, and only an account already in the file reaches the
  lock-free path. In loopback mode the client can only name the configured `--session`. Creating
  the store or the account is under the lock and re-reads the file first, so two first logins
  cannot both create.
- **Staff writes (`moderation::run`, `realm role`).** Unchanged: 50 ms lock wait, "busy" answer,
  nothing written. They can no longer be starved by read spam; see Lock fixes for the write-spam
  bound.
- **No new oracle.** Login replies are unchanged; the ban is still the ordinary failed login after
  key-pair redemption. A busy create or delete ends the session exactly as any other login error,
  and the "is held" line goes to the host's stderr only. The moderator's typed name is never logged.
- **No secrets in logs.** The two stderr lines carry the host's own lock path and the OS error;
  nothing from a packet, no token, key, name or account id.
- **Name resolution.** Typed words and stored names fold by one rule (`name_words`), so a look-alike
  cannot be created on another account and every typeable name reaches at most one account in a
  store built under the rule. Older stores that already hold cross-account look-alikes still refuse
  ("no single character"), never guess.
- **Atomic saves.** Every save is still `AccountStore::save` -> `character_store::replace_bytes`.

## Open gaps

- **Write spam.** A modified authenticated client can still send refused creates or deletes (taken
  name, a guid it does not own) at the session bucket rate. Each holds the lock for one store load
  and the checks, and the unlocked prelude per request is longer, so a staff write still finds the
  lock free; with a very large store (near the 1 MiB cap) and many sessions this margin shrinks. A
  per-session write budget would close it fully; left for the lead.
- **CPU per request.** Every broker request still reloads the resource tables and the store two or
  three times (pre-existing; the `ponytail:` comment in `osfr-login.rs`). Only the lock moved out.
- **Account creation from network input in broker mode.** It is unreachable (see Security), but it
  rests on accounts never being removed; an operator who swaps the store file between the
  principal check and the service's load would let `add_account` add the account (now under the
  lock). Pre-existing; the `(R) Account-store mode never creates/migrates` rule is enforced only at
  startup.
- **Lock identity.** `Drop` removes the lock by path, so if an operator deletes a live lock and
  another writer takes it, the first writer's drop removes the second's. Pre-existing; the new
  "could not be removed" line does not catch that case (removal succeeds).
- `cargo test --bin osfr-gateway l042_` (the brief's filter) matches no test: L042's tests live in
  `moderation::tests`, so the filter `moderation` was run.
- Native gates of L042 (moderator mutes and bans the bot with the real client) remain for the
