# S0022 (0046b77b..0046efeb) - encoded draw records, the D3D9 display, container/iterator helpers, MSVC STL

## 1. Encoded draw records (0046b77b..0046c98c)

The eight implementations and their eight stdcall entries form the append side of the GFC draw
record buffer. Their per-record work is delegated to helpers whose accepted map labels name the
operation exactly:

| record flavour | encode one | encode a batch | copy a record |
|---|---|---|---|
| 0x1c (28 B) | 0046556b EncodeDrawRecord28 | 004655ae EncodeDrawRecords28Batch | 004651ee Copy28Bytes |
| 0x24 (36 B) | 00465656 EncodeDrawRecord36 | 00465699 EncodeDrawRecords36Batch | 00465221 Copy36Bytes |

Each implementation appends records, then maintains the target object's tracked rectangle at
+0x10..+0x1c, and each has three clip flavours:

* 0046b77b / 0046bd72 - batch append; the rectangle may come straight from param_3 or from a clip
  node taken with 00466ce6 (DrawDevicePopNode32) and filled with 004dbd55.
* 0046b89c / 0046be93 - single record with the cached clip node at +0xc, intersected through
  004f7cd4 / 004f749f.
* 0046bad7 / 0046c0ce - single record clipped against the caller region param_3, validated per
  element by 004f7dfd.
* 0046bc5c - single 0x24-byte record, no clip-node creation path.

They return the encoder result (1 on append) and the clip-path variants return 2 when a clip test failed, and they reset the tracked rect to
`0,0,-1,-1` when the clipped area is empty. The eight stdcall entries 0046c8ac..0046c98c match
pointers present at 0x017648d0..0x01764900 and forward to the append implementations. The owning
class of this table is not established: the constructors previously cited do not install this
table as their final vtable. Treat these as public forwarding entries, not confirmed class methods.

The object itself: +4 holds the record-buffer writer (base/cursor/extent at +4/+0xc/+0x10/+0x14/
+0x18, grown by 00461ffa), +0xc the cached clip node, +0x10..+0x1c the tracked rectangle.

## 4. Container and iterator helpers (0046c2bc..0046ca8d, 0046d14c..0046dedf)

The re-derivation separated three easily confused roles, and the accepted callee labels confirm
each one:

* **retain-copy** (`RefPtrCopyIfNonNull` 0045f1ff/0045f220: call virtual slot +0xc, store) versus
  **release-destroy** (`RefPtrScalarDeletingDtor` 0045f26e/0045f292: call slot +0x10).
  Hence 0046c520/0046c632 and their wrappers are *copies*, while 0046c505/0046c617 and the
  pop-back helpers 0046deb7/0046dedf are *releases*.
* **fill/copy into raw storage** (`Copy12IfNonNull` 0045f1e0, `CopyQuadIfPresent` 0046a252,
  `UninitCopy4_*` 0045f019/0045f056/0045f0a1, `UninitCopy45F1E0/46A252/45F1FFA`): these are the
  `_Uninitialized_fill_n` / `_Uninitialized_copy_n` helpers behind the accepted callers
  `std::vector::_Insert_n` and `VectorAppend2..12`; 0046c48f/0046c59e/0046d763/0046da84/
  0046d7fa/0046db28/0046d8e0..0046d968/0046db08..0046dc6c all belong here.
* **backward move / backward copy** (`RefCopyBackward5BAB/5C60` 0046a4a4/0046a52d and the
  `CopyBackward12/16/36` adapters): 0046c6c5/0046c6fc move a pointer range down, releasing the
  overwritten slots.

Other members of the same object family:

* 0046d14c/0046d175/0046d1de/0046d26d - `end()-1` accessors: build end() (00464ec7 / 00464a6c /
  0046484d / 00464943), advance the copy *backwards* (the `IteratorAdvanceCopyPairNeg*` helpers
  pass -n to a 0xc-stride checked step) and dereference. PopBackAndRelease (0046f8cd) reads the
  slot, retains the pointer and then pops; SwapQueuedObjects and DrawSurfaceCommitLists do the
  same in the surface commit path.
* 0046d1a3/0046d296 - guarded back-insertion wrappers (AppendSlotBackGuarded9F85/9F5D).
* 0046d207/0046d2d1 - key lookups: each runs one lower-bound search (`LowerBoundIterator64715` /
  `64991`) and compares its result with an end iterator. 0046d207 constructs that same end
  iterator in both branches; if the lower-bound result is not end and its key is <= the requested
  16-bit key, it stores the result, otherwise it stores end. It does not search a second container.
* 0046ca8d - key-presence test used by DrawQueueAppendObjectRecord (00477ee7); the key arrives as
  a stack argument.
* 0046c9ac - compacts the object's 0xff-entry rectangle array and shifts the node list.
* 0046dd9f/0046de29/0046de45 - shutdown, deleting destructor and outer destroy path of the
  slotted object table (caller RemoveIndexedSlot 0046f7f2); 0046da0e is its erase-one-slot

## 6. Cross-cutting observations

1. **The tracked-rectangle protocol is the output contract of the 2D record buffer.** Every
   append ends by expanding, intersecting and possibly invalidating the rect at +0x10..+0x1c
   (the display's own copy lives at +0x6c..+0x78); the display flush routines 0046cf8c/0046d05e/
   0046d0c1 consume it.
2. **Two record sizes (0x1c and 0x24) exist side by side**, each with its own batch encoder and
   copy helper; the 0x24 flavour carries more fields, so the two are not interchangeable.
3. **The display state machine is fully recoverable** from 0046cac7 + 0046cd73: four outcomes
   (0 ready, 1 no video mode, 2 reset failed / state lost, 3 dependent reset required) and five
   exact messages, with the D3D9 error constants in the code.

## 7. Open questions

* The owning class of the draw-record append block is unproven. Function pointers occur at

* Which of the nine tree instantiations stores which payload is not decidable from this shard -
  the node constructors live in other shards.
* 0046d685 stores an iterator word plus a dword-search result; what the pair denotes is not
  established by the function alone.
* The element sizes behind the four `end()-1` accessors are not all proven (only the 0xc stride
  of 0046d14c is).

## 8. Review corrections and recurring pitfalls

The second independent review narrowed several overclaims. 0046d207 builds the same end
sentinel in both branches, so the fallback is not a second-container lookup. 0046d343, 0046d438,
0046d4b4, 0046db4a and 0046e228 copy tree members after their callers initialize them; only
0046d552 is called from the self-assignment-guarded erase-and-copy path. The owner of the table
containing 0046c8ac..0046c98c remains unknown. The EH caller of 0046d928 does not prove a vector
insert role, and the repeated vector length-error throwers do not identify element types.

The first pass also got these wrong (kept as a warning for future shards):

1. **Callee semantics were assumed from the calling shape.** Two families were inverted:
   `RefPtrCopyIfNonNull` (retain) was read as a release, and the `_Uninitialized_fill_n`-style
   loops were labelled as array destructors. The callee's own accepted label settles it.
2. **A class was inferred from adjacency.** The "font device" name came from the glyph-shaped
   story, not from an anchor; the constructors in the same block are DrawSurfaceCtorA/C.
3. **Wrapper direction was not verified from the bytes.** The 12/16-byte wrappers were named as
   "iterator constructors" although their callee is a range copy returning the destination end;
   the argument reshuffling in 0046dd77 forwards arguments 2/4/5/6 and drops 1 and 3.
4. **A key parameter was missed.** 0046ca8d was described as a "region has content" test; the
   stack argument is the key that the result depends on.
