## What changed

- **New test suite** `prototype/osfr-tools/tests/vendor_buy_sell_gateway.rs`
  (9 tests including the shared `vendor_purchase` reconnect test, LF, no BOM).
  It drives the real request path
  `Gateway::handle_at` -> gameplay -> NPC router -> `NpcInteraction` /
  `CoinShop`, and reads state back with `Gateway::snapshot()` and the real
  `game_store` envelope. The fixture is the shared
  `tests/common/vendor_fixture.rs` representative vendor
  (`9_500_000_045`, stock item `76_427`, `stores.json` purchase 752 / resale
  376); no fixture was copied. It is a **combined regression bundle** over the
  existing coverage, not all-new behaviour: `tests/vendor_sell.rs` already
  proves a gateway sell -> save snapshot -> reconnect (`vendor_sell.rs:739-772`)
  and a gateway buy -> sell round trip (`vendor_sell.rs:849-874`), and
  `tests/common/vendor_purchase.rs` already proves the representative 66/43 buy,
  the relog and the poor/full-bag refusals. The genuinely new pieces here are
  the real `game_store` envelope/save bytes for the purchase, the 66/43 + 165/5
  combination with the save/relog in the middle, the forged price fields, the
  66/42 repricing row, the near-cap sell and the two-character gateway check.
- **Shared test helper move** `tests/common/gateway_vendor.rs`: `connect_with`

- **Shared fixture accessor** `tests/common/vendor_fixture.rs`: the fixture keeps
  the `stores.json` path it was built from, and `sell_price_of(item)` reads the
  authoritative resale price for the bought stock row (the existing
  `sell_price()` still answers for the seeded item).
- **No production change.** `src/`, content JSON, Cargo files and the hubs are

Tests and what each one proves:

1. `request_bodies_match_the_client_writers` - byte-level pins for the requests
   this suite sends: 26/8 is 13 bytes (header, u64 target, one zero bool;
   `0x008b6bc0`), 26/10 is 16 bytes (header, u64 target, i32 choice;
   `0x00a36f80`), and 165/5 is 20 bytes (header, u64 merchant, i32 instance,
   u32 quantity; writer `0x00c75a70`, fill order `0x00c76dd0`). The 66/43 and
   66/44 bodies are pinned by
   `vendor_stock_coverage::vendor_buy_wire_matches_the_client_reader_layout`.
2. `a_player_buys_a_stock_item_and_the_save_holds_the_new_wallet` - 26/8 ->
   26/10 opens the 66/42 window; the window quotes the `stores.json` price; a
   66/43 buy answers 66/44 status 1; coins drop by exactly that price; one new
   instance/count is granted; the seeded stack and character pose survive; every
   bag instance id is unique; the reopened 66/42 window is identical (authored
   stock is not consumed per purchase); `game_store::save`/`load_or_create`
   round-trips the snapshot.
3. `the_purchase_survives_a_real_relog` - save the committed snapshot, load it
   with `game_store`, rebuild a `Gateway` through `connect_with`, assert the
   saved inventory/wallet is unchanged and there is no double grant; a relog has
   no open shop (66/44 status 0, state unchanged); a fresh 26/8 -> 26/10 window
   spends the saved wallet (1000, not the fixture's 1752); a second buy lands
   and the next is refused by the live balance.
4. `the_same_item_can_be_sold_once_through_165_5` - the bought instance sells
   once with merchant 0 = the open shop; the 165/6 result is 1, kind 2, the item
   definition and `stores.json` resale price, quantity 1, `remaining` 1 (the
   buy-back ledger entry the client reads) and a nonzero ledger transaction; the
   stack is gone and coins rise by the resale price; a replay of the same
   instance/quantity returns 165/6 `INVALID_ITEM` and changes neither snapshot
   nor save bytes; a second buy/sell interleaving reads the live wallet and a
   new instance; the vendor stock row is still listed.
5. `buy_and_sell_refusals_change_nothing` - insufficient coins; forged/unknown
   item id; quantity `u32::MAX`; a foreign merchant on 165/5; an unowned sell
   instance; a sell quantity above the owned count; a full bag; a wallet one
   coin below the cap whose sale credit would overflow; and an out-of-range
   interaction. Every buy refusal answers one 66/44 status 0, every sell refusal
   one 165/6 with the production result code; each case asserts the outcome
   requested no save (`!gameplay_changed`, `!state_changed`), and that the whole
   `Gateway::snapshot()` and freshly serialized `game_store` bytes are unchanged.
   Positive controls after the refusals (a real 165/5 sale, then a real 66/43 buy
   on the same open shop; a freed full-bag slot) prove the shop was never
   consumed.
6. `the_round_trip_uses_no_dev_commands` - records the exact request headers:
   `26/8, 26/10, 66/43, 165/5` only; no family 15 chat, no `realm` bytes, no
   admin packet; the session role is `AccountRole::Player` before and after the
   flow (the shared `connect_with` sets no role, so this is the production
   default, not the helper's own setup); the reply stream contains the ordinary
   66/42, 66/44 and 165/6 packets and no chat line; the vendor is in the
   fixture's `NpcVisibility` zone-0 spawn list (the same loader world entry
   uses), so it is drawable from content.
7. `a_client_supplied_price_field_cannot_change_the_server_price` - a 66/43 with
   the same real item/quantity/transaction but every server-unread field
   (`initial_dwords[1]`, the three context dwords, `trailing_dwords[1]`) forged
   to a 1-coin price buys successfully and debits the 752-coin `stores.json`
   price, grants one item, and disturbs nothing else.
8. `two_players_at_the_same_vendor_keep_independent_wallets_and_shops` - two
   gateways for two different character GUIDs at the same content open the same
   window; one purchase leaves the other snapshot and wallet untouched; both
   open shops then serve their own purchase with their own wallet. Instance ids
   are per-character namespaces; each bag's ids stay unique and never reuse the
   seeded instance 1.

## Client evidence (IDA, 2014 client)

All queries used `lab/autopilot/ida_query.py` against the pinned database. No
result contradicted the existing notes.

- `decompile 0x00b3ab20` (66/43 serializer): header, two initial dwords
  (`this+6`, `this+7`), a context record (`sub_8FB810`), one dword, the
  length-prefixed string, then three trailing dwords (`this+15..17`). This is
  the shared `encode_merchant_buy_66_43` shape (40-byte empty-string body).
- `decompile 0x00b32430` (66/44 reader): after the header it reads seven dwords,
  the length-prefixed string, then five dwords; the field stored from the fourth
  trailing dword is object `+0x58`.
- `decompile 0x00b48a10` (66/44 dispatcher, case 44): calls
  `sub_B39A80(v28, ...)` and tests `v29 != 1`, where `v29` is the `int` that
  immediately follows the 88-byte `v28` object - i.e. `+0x58`, wire offset 48.
  The result status is therefore at offset 48, as the shared helper asserts.
- `decompile 0x00b29cd0` (66/42 row reader): six dwords, a bool, three dwords,
  a bool - exactly `MerchantEntryV2`.
- `decompile 0x008b6bc0` (26/8 constructor): two dwords (u64 target) + byte.
- `decompile 0x00a36f80` (26/10 constructor): two dwords (u64 target) + i32.
- `decompile 0x00c75a70` (165/5 serializer): header (`sub_C75580`), merchant
  record (`sub_8FB810` at `this+4`), then `this+6` and `this+7`. The same record
  is filled by `decompile 0x00c76dd0`: merchant pair `a2`/`a3`, item `*a4`,
  quantity `a5`. `decompile 0x00c77030` passes the null merchant globals
  `qword_1BEEA08`, so merchant 0 = the open shop on a native sell.
- `decompile 0x00c74ef0` / `decompile 0x00c71f30` (165/6 reader): header, result,
  leading item, then kind, u64 merchant, transaction, u64 timestamp, item pair,
  quantity, unit price, remaining (56 bytes). `decompile 0x00c78220` compares
  the result dword with 1 before the success dispatch.
- 66/46 hide is an outbound service message; no inbound 66/46 route exists, so
  this suite neither sends nor needs it.

## Reconstructed rules (R)

- The mapping of the opaque 66/42 row dwords to purchase/resale prices, and the
  66/43 request mapping (`initial_dwords[0]` = item, `trailing_dwords[0]` =
  quantity, `trailing_dwords[2]` = transaction id) stay the existing (R)
  convention; the test reads those fields but does not re-implement the T362
  row layout.
- A 165/5 sell with merchant 0 means "the shop this player has open" (recovered
  from `0x00c77030` + existing server policy). Any other merchant must equal the
  open NPC key.
- The authored vendor list is an infinite stock list: the production path never
  decrements a per-row count, so the expected remaining state after a purchase
  or sale is the unchanged 66/42 window. The sale/buy-back ledger lives on the
  session-only `CoinShop` and is not part of `GameplayState`/`Snapshot`.
- Inventory instance ids are per-character namespaces: two independent gateways
  may both allocate the same numeric id in their own bags; each new id is still
  unique within its character and never reuses the seeded instance 1.

## Security threat note (secure-code-guardian)

- **Attack surface.** A hostile client can send 26/8/26/10 with any NPC GUID,
  66/43 with any item id, quantity and transaction id (and arbitrary bytes in
  the fields the server does not read), and 165/5 with any merchant, instance
  and quantity. This change adds no parser, route, reward, content value or
  save field; it proves the existing production refusals.
- **Why a hostile request cannot profit.** 26/8/26/10 require a known NPC in
  range; 66/43 requires the server-side open shop, the item in that vendor's
  authored stock, a valid quantity and the `stores.json` price (client price
  fields are ignored); the bag cap is 100 occupied stacks and coins are checked
  with checked arithmetic. 165/5 requires the open shop and range, merchant 0 or
  the exact open merchant, an owned instance that is not rented/equipped, a
  quantity within `count - consumed - stored`, a store row not `no_sale` and a
  server resale price. A transaction replay finds no owned instance and pays
  nothing. Instance ids are never reused from another character's namespace, and
  every refusal in the suite is asserted to leave the canonical snapshot and
  serialized save byte-identical.
- **Canary evidence.** The deliberate pre-ownership credit makes the replay and
  unowned-instance refusals change coins, and the suite fails on the snapshot
  equality - so the proof is sensitive to exactly the economy defect the gate
  names.
- **Isolation.** Refusals are per-request `Err`/result packets; `app_fuzz` and
  the old refusal suites stay green; the test-only code unwraps only its own
  fixture data, never a server result.

   `Gateway::snapshot()` and a fresh `game_store` save's bytes before/after;

   refusal goes through the production staged `Gateway::handle_at`; the

   No shared `Rc`/`RefCell`/`Arc` or side table was added.
