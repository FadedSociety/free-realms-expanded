# T774: NPC shops never open empty

The owner's native check (2026-10-26 22:07Z, binaries `6a3172b5`) found Mr. Twinkle's shop empty. The
brief asked to fill every NPC shop from client/Legacy store data and the wiki. The survey below
shows that 98 of the 194 vendor-role NPCs have **no recovered item-level stock at all**, and that no
retained source proves stock for them; the only item two of them name (`Bait`) has no purchase
price. Inventing stock is not allowed (F192, lead sign-off 2026-10-19). So the diff fixes
the observable defect instead: the client can no longer be sent an empty merchant window.

Re-applied 2026-10-27 on the `autopilot` tip (`3875a6db`) from the earlier attempt's patch
(`T774-a1.patch`), per the lead's 2026-10-27 decision: accept the diff as is, author no stock
without item-level evidence, and leave Mr. Twinkle Talk only. The patch applied cleanly (hunk
offsets 8/66/77/77); its two tests and their canary are kept and were re-run on this tip. The
numbers below are this run's.

## What changed

- `src/npc_interaction.rs` (the owner of the merchant window; +10/-3):
  - `merchant_window` keeps only rows with a `stores.json` purchase price. A row without a price
    cannot be bought and `coin_merchant_packets` already dropped it, so it was never stock.
  - `build_options` offers the Shop choice only when that window is non-empty. The old comment
    ("A role-bearing NPC without a mapping opens an empty window") documented exactly the bug.
  - `MerchantItem::purchase_price_coins` documents that it is always `Some` in a built window.
- `tests/npc_shop_stock.rs` (new, 413 lines): the content gate + Mr. Twinkle end to end.
- `tests/vendor_stock_coverage.rs`: the two empty-shop exception assertions now assert **no Shop
  choice** instead of selecting a shop and finding an empty window.
- `tests/npc_greetings_sanctuary.rs`: the edited-set merchant (Pucca De'Flor, no priced stock) must
  no longer list Shop; the role assertion is unchanged.
- No content JSON changed. No hub file changed (`gameplay.rs`, `bin/osfr-gateway.rs`,
  `encounter.rs`, `gateway.rs`: 0 lines each). Nothing deleted.

## Threat note (secure-code-guardian)

What a hostile client could send: a 26/10 naming a Shop choice. There is no trust boundary change —
the choice was already validated against the active menu, and the server now does not offer a
choice it cannot fill, so an empty merchant window (and a shop session with no stock) cannot be
opened. A malicious 165/4/165/5/66/43 is still gated by the open-shop + range + `vendor_items` +
`CoinShop` checks, which are unchanged. `merchant_window` is built from server content only (no
client data), prices come from `stores.json` (server-authoritative), and a refusal still changes
nothing: `select` returns `InvalidOption` before touching the clone, which the gateway discards (the
new test asserts the snapshot is unchanged and the still-open menu answers Talk afterwards). The
change adds no persisted state, no client-controlled id, no free grant and no packet field.
