# T712: the placed Rainbow Randomizer shows a random colour, not a plain red box

The placed box's AddNpc (35/2) now carries the look its **actor model** defines: the model's
`.adr` texture alias, one of its tint aliases, and the item's tint id. The Rainbow Randomizer
rolls one of its six model tints per placement, and that same pick selects the colour song, so the
box's colour and tune always agree. The old rows copied the item definition's
`TextureAlias`/`TintAlias` into the NPC; those names are not aliases the actor definitions define,
so the client fell back to the model's default skin (red). The task's item-alias hypothesis and
the real client disagree; IDA and the extracted actor definitions win (see below).

Skills used: **ponytail (full)**, **secure-code-guardian**, plus the lean-structure principles
(reuse the owner module, no hub growth).

## The bug and the client evidence

- The old rows sent item aliases such as `boombox-rainbow-M` and `dyetint`. For item 1913 the
  captured item row is texture `""`, tint `dyetint`, `default_tint` 0 (W84 baseline); Legacy's row
  adds texture `boombox-rainbow-M`. The extracted client
  `mkt_boombox_rainbow_01.adr` defines **no texture alias** and exactly six tint aliases: Red,
  Orange, Yellow, Green, Blue, Purple. Its `.dma` defaults the body material to red
  (0.945/0.114/0.114), so an unresolved texture alias plus `dyetint` leaves the box plain red.
- Every other row's `-M` item alias likewise does not name its model's `.adr` alias (only
  Realmshake's does). The `.adr`-defined aliases are the only ones the model can resolve.

Client facts (IDA, this run):

- 35/2 AddNpc reader **`0x00921a10`** (`PlayerUpdatePacketAddNpc_ReadBody`, confirmed): after
  `sub_8D6830` it reads the actor u64 at `this+16/+20`, name id `+24`, model id `+28`; the two
  counted look strings are assigned at `0x00921c04` (`lea ecx,[edi+24h]` -> texture) and
  `0x00921c46` (`lea ecx,[edi+34h]` -> tint), then the i32 tint id at `this+68` (decimal = `+0x44`)
  just before the `+156` bool. The Hex-Rays decompile is capped at 400 lines; the string stores and
  the `+68` dword are in the decompile/disassembly at those addresses.
- **`0x007e2500` `TextureAliasesRead`** reads alias-name + texture pairs from the actor
  definition; **`0x007e2940` `TintAliasesRead`** reads alias-name + a Vector4 colour. A failed
  override logs `0x017ec698` "Actor definition pending texture alias %s (with override texture %s)
  for actor %s failed to load!"; tint aliases are hash-checked into `BadTintAliasHashes.txt`
  (`0x017eda20`).
- The six colour songs are `ActorCompositeEffectDefinitions.xml` **16448-16453**:
  `PFX_music_boombox_red`, `_blue`, `_green`, `_orange`, `_purple`, `_yellow`. The wiki page says
  the box "appears in one randomly chosen colored tint ... they all play a different tune" (used
  as a reference, not a client fact).
- T483's ride look and the boombox use the same three `NpcSpawn` fields; the shared type is now
  `startup_world::ActorLook` (mounts re-exports it as `RideLook`).

which is what the old unresolved aliases also rendered as.

## Threat note (secure-code-guardian)

A hostile client only names a bar slot in 36/10. The server resolves that slot to its **bound
inventory instance**, then to the server's catalogue row; the texture alias, tint alias, tint id,
model, colour list and song ids never come from the request. The random pick is the server's RNG.
The row is server content, validated by `Catalogue::load` (row count, tint count and alias-length
bounds, duplicate aliases, non-negative song/tint ids, unknown fields refused). The press is still
gated by the existing item-bar/busy/recast checks and spends nothing. No save, coin, item or
player-supplied string is written; the AddNpc uses only server data and the codec's counted
strings. Refused presses are unchanged and the existing tests assert byte-identical state.
