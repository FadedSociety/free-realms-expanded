# T530: Pet clothing — 53/11 equip/clear, saved slots, actor attachments

## What changed

- **53/11 is decoded at an exact length** (`src/pets.rs`): u8 flag (0 fit, 1 clear), the pet
  equipment pane slot, the item instance. `DECODED_SUBTYPES` gains 11, so the gateway's pet label
  (`application_handler` reads that table) and app_fuzz cover it (two new hostile seeds).
- **The rules live on the request path.** `PetService::handle_at_ms` intercepts 53/4 and 53/11
  (the two requests that need the live inventory) and `PetService::wear` validates a fit: the
  target is the summoned pet; the item is owned, type 3, its definition slot is the pane slot, its
  class is in the model's `item_classes`, the model is not vanity, and the definition draws a model.
  A clear empties the pane slot. Every accepted change answers 53/11 (slot state), the 53/5 roster,
  and one 35/6 actor change to the owner and to the viewers; a refusal changes nothing and echoes
  the slot as it stands (a slot outside the five pane rows echoes nothing).
- **Saved slots.** The fitted instance ids were already in `PetEquipment` in the roster save; a
  save/reload test pins chest-id survival, the next spawn and the resummon.
- **Attachments everywhere.** `PetPresence` gains `attachments`; the AddNpc spawn carries them.
  Summon, the zoning resummon and the late-viewer `pet_view` resolve the rows from the live
  inventory (`PetService::worn_attachments`), so all three paths dress the actor. A live change
  uses the one 35/6 encoder (`inventory::equip_change_packet`, next to `write_attachment`), and
  `gameplay::item_change_packet`'s removal shape now calls the same encoder (gameplay.rs −6).
- **Trade.** `Gameplay::trade_inventory` now supplies `PetService::equipped_instances(state)`
  instead of an empty set: an item a pet wears or holds cannot be offered. Ids the bag no longer
  holds are filtered out so a stale save row cannot fail `TradeInventory` validation.
- Slot helpers on `PetEquipment` (`worn`, `fit`, `instances`) and one `WEARABLE_SLOTS` table on
  `PetEquipmentSlot`; `equip_item`/`unequip_item` now write through them. `Inventory::item_facts`
  (renamed from `kit_facts`) is the one `(type, slot, class)` reader for kit and clothing;
  `Inventory::attachment(id, slot)` builds the six attachment fields from `write_attachment`'s
  rules. `startup_world::write_npc_attachment` is the one attachment encoder.
- **New-tip port (previous patch did not apply).** The shared 53/x builders moved from
  `src/bin/osfr_gateway/pet_wire.rs` to `tests/support/pet_wire.rs`, so `pet_wire::wear` was added
  there; `PetService::pet_guid` gained the pet id (T830), so every call in this work uses
  `pet_guid(owner, pet_id)`; the core pet route now lives in `handle_at_ms` (T866 and the care
  routing) and `handle` is the inventory-less sibling, so the no-inventory summon keeps its
  refusal shape while `handle_at_ms` resolves the clothing rows. The zoning resummon signature
  and the reopen tests were updated to the new tip rather than forced through the old hunks.
- Tests: new `tests/pet_clothing.rs` (10 tests), `InventoryFixture::with_pet_items`/`Wearable`,
  53/11 app_fuzz seeds, and call-site updates for the new `summon`/`resummon` attachments
  parameter (`tests/pets.rs`, `pet_follow`, `pet_zoning`). `tests/piece_045.rs` now also compiles
  `startup_world` because the included `inventory.rs` names its attachment row type.

## Client evidence (IDA, re-read 2026-10-28)

- **Live 53/11 Lua callbacks:** `EquipItem` → `00c07990` (`sub_C07990`), `UnequipItem` →
  `00c07ae0` (`sub_C07AE0`), registered by the name table at `0x01829fa8`/`0x01829fb0`. Both build
  the packet with ctor `00b50e00` (family 53, subtype 11; zeroes `+0x0c`, `+0x10`, `+0x14`), fill
  `+0xc`/`+0x10`/`+0x14`, and send through wrapper `00b5c7e0`.
- **Equip (normal UI path):** the first Lua argument is the item guid string. `sub_C07990` tests
  it with `sub_E3A5F0` (a number/`tonumber` test) and, for a string, goes to `0x00c07a77`:
  `sub_E3A820` fetches the string and `sub_101CD50` → `sub_738E70` parses its decimal digits
  (`atoi`), storing the result at `+0x10`; `+0xc` stays 0 and `+0x14` gets the pane slot. The
  numeric-zero fallback (`0x00c07a4e`) sets `+0xc = 1` and looks the item up from the slot, but
  it is not the normal item-selection path. So the live body is **flag 0, slot, item**.
- **Clear:** `sub_C07AE0` sets `+0xc = 1` and `+0x14 = slot`; `+0x10` stays 0. The body is
  **flag 1, slot, 0**.
- **Packet builders:** `00b60220` (flag 0, `+0x10 = *a2`, `+0x14 = a3`) and `00b602c0` (flag 1,
  `+0x14 = a2`) have no direct xrefs (the Lua callbacks build the same object); they are the
  shape witnesses for the two actions. Serializer `00b5a790` writes `+0xc` (byte), then `+0x14`,
  then `+0x10`, matching reader `00b55c30` (byte `+12`, dword `+20`, dword `+16` = flag, slot,
  item). The 53/11 client handler (`00b5ce60` case 11 at `0x00b5eb65`) only refreshes the equip
  panel; it validates nothing, so the server must.
- **Pane slots:** `ScriptsBase.lua` `PetInventorySlotMap` (lines 22296-22308) is
  `HeadData, "", ChestData, "", FeetData, CollarData, ToyData` and `PetSlotMap` starts `1,3,5,6,7`
  → head 1, chest 3, feet 5, collar 6, toy 7. Equip flow `ScriptsBase.lua` 22717-22720 (`mode == 5`
  → `Pet.EquipItem(b, c)`); the `>199` utility handoff is in `sub_C07990`.
- **35/6 actor change:** dispatcher `0092f460` case 6 at `0x009314e3`; reader `sub_919c20` →
  `sub_90a1f0` → `sub_8e86f0`. Wire: target u64, item id, model/texture/tint-alias strings,
  tint, effect, slot, profile (`+0x1e8`), one word the handler reads (`+0x1c`), wield (`+0x1ec`).
  The handler finds the actor by guid (`sub_984960`), and at item > 0 adds the attachment with
  `sub_95d620` → `sub_95a1c0`; at item 0 it removes by slot with `sub_96b970`. Then it applies
  `sub_96a3e0(actor, profile)` and `sub_9582c0(actor, wield, 0)`. `sub_95a1c0` returns without
  adding when the model string is empty.
- **AddNpc attachments:** reader `00921a10` reads the counted list with `sub_9131c0` (count, then
  `sub_8e86f0` rows) and actor creation `sub_968c80` applies each row with `sub_95a1c0`. AddNpc
  `active_profile` is applied with `sub_96a3e0` at `0x0092f9fb`. `has_attachments` is a separate
  captured flag (0 in every captured row); this task leaves it at the template value.
- `EquipPetMannequin`/`EquipPetMannequinBundle` strings (`0x018225b8`, `0x01822148`) are used by
  `sub_b5ce60` and `sub_b58d90`; both log when the proxied pet actor is missing, which matches the
  attachment rows being applied to the actor object.
- IDA correction to the brief/research pack: the two u32 are **slot then item** (not item then
  slot); the live Lua callbacks are decisive. The shipped catalogue's pet rows use the same item
  `Slot` values: 2163 head turban (slot 1, class 31), 1192 dog chest shirt (slot 3, class 31),
  1193 cat chest shirt (slot 3, class 61), 876 toy (slot 7, class 31).

## (R) rules and why

- **Target = the summoned pet.** The 53/11 body names no pet; the client's Pet Inventory pane is
  the active pet's (`Pet.GetActivePetId`, `PetController:PopulatePetController`). The brief's
  "owned (active or not)" is not achievable without a pet id.
- **Fit gates:** type 3, definition slot == pane slot, class in the model's `item_classes`
  (`73`/`144`/`145`/`146` are on 160 of the 165 models — five late-bound models have no classes
  row at all — but no clothing row carries them; dog clothes are class 31, cat clothes class 61),
  not vanity, and the definition has a model. The model string is required because the client's
  attachment add ignores an empty model.
- **35/6 profile = the pet actor's AddNpc `active_profile`** (8 from the captured content
  template), so `sub_96a3e0` sees no change; wield 0 like every other non-weapon row the player
  path sends. A clear sends item 0 and empty strings with the slot, the removal branch above,
  exactly the shape the player's own unequip broadcast uses.
- **Attachment order** is the pane-slot order (head, chest, feet, collar, toy); the client keys
  by slot, and the count is bounded at five by the equipment struct itself.
- **Trade** blocks every instance a pet wears or holds, kit utilities included (they are
  "equipped on a pet" too). Stale ids are filtered because `TradeInventory` refuses a set naming
  an item its inventory lacks, which would block trading for the whole character.
- **Player equip** is already refused for pet clothing by the inventory rule
  `definition.slot == slot && profile.slots.contains(slot) && profile.allowed_classes.contains(class)`:
  the shipped catalogue's 16 player profiles allow none of classes 31/61 (checked in the round70
  catalogue, 2026-10-28), and pet clothing is slot 1/3/5/6/7. The trade gate above is the
  code-enforced half of the same invariant.

## Threat note (secure-code-guardian)

A hostile client can send any 53/11 body. The decoder requires the family byte pair, subtype 11,
the flag 0/1 and **exactly** 9 body bytes; anything else is an `Err` that the gateway drops, and
nothing is sent. The handler trusts only ids: it looks up the **owned** instance in the bag
(count > 0), the definition row the server itself loaded (type/slot/class), the model's class list
and the roster pet. No client word reaches a slot write before all of those pass. The pane slot is
mapped through the five-entry table; 2, 4, 8 and 200 are refused with no reply, so a wild slot
cannot be echoed into client state. A refused fit replies with the slot's unchanged item and never
touches the roster or inventory (the test snapshots both), and cannot consume, equip, sell or
trade the item. There is no path here to grant an item, coins or XP. No new limiter: 53 already
pays the per-session packet/byte buckets like every application, and the handler allocates at most
one small echo plus (on success) one 35/6. `equip_change_packet` and `attachment` only read the
server's own catalogue; no client string is echoed into a packet.

## Checklist (GPT Sol review items)

1. **A refusal changes nothing.** `a_wrong_class_slot_or_type_item_is_refused_and_changes_nothing`
   snapshots the roster and the inventory state before each of six refusals (wrong class, wrong
   slot, wrong type, no model, unowned instance, item in the wrong row) and five invalid pane
   slots, asserts equality and that `changed` is false with the unchanged echo. The gateway test
   also snapshots `gateway.snapshot()` across a wrong-class request through the real dispatch.
   Canary 2 removed the class check and this test failed.
2. **Rollback covers all state.** No new transaction: `wear` validates completely before its one
   roster write; a failed `equip_item`/`unequip_item` still answers the unchanged slot. No
   `Rc`/`RefCell`/side table escapes.
3. **Apply deltas, never snapshots.** No payout or exit path is touched; the equip only sets one
   optional id on the requested pet.
4. **Busy rules are mutual.** Clothing is instantaneous (no timed run, no new activity), so no
   `Occupation` row exists for it and no existing activity changes. The pet's timed care cannot
   conflict: clothes live in different slots from the kit, and a fit does not end or start a feed,
   groom or trick.
5. **Every entry path is gated.** One production route reaches the action: gateway →
   `Gameplay::handle_in_world` → `handle_pets` → `PetService::handle_at_ms` → `wear`. The public
   `PetService::handle` has no inventory and refuses 53/11 (`pet care requires the live
   inventory`); its summon path (tests only) is documented as dressing no actor. The
   `the_gateway_fits_real_catalogue_clothing` test drives the real dispatch.
6. **Reachable in production, tested through it.** The suite includes that gateway test (real
   `Gateway::load_gameplay`/`handle_at`, shipped catalogue, save/reload/reconnect); the other
   tests use real request bytes through `handle_at_ms`. No copy of the validation is tested.
7. **Survives reconnect.** `an_equipped_item_is_saved_and_dresses_every_spawn` saves
   `document_value`, reloads with `from_document`, re-summons and re-runs the resummon; the
   gateway test reconnects through `reload_saved` + the handshake and finds the head row and the
   dressed AddNpc.
8. **Every exit path restores the player.** A dismiss/zone change drops the actor (unchanged
   path); the persisted slots keep the clothes, and the next spawn re-applies them. A refusal
   leaves nothing entered.
9. **Economy safety.** Only owned instances are touched; no grants. The trade set now blocks pet
   equipment (asserted through `Gateway::trade_inventory` in the gateway test), and the player
   equip rule refuses pet clothing because no player profile allows classes 31/61. No
   client-reported outcome or quantity is used.
10. **Wire format matches the client reader exactly.** 53/11 is the sender/reader order (flag,
    slot, item) at the exact 9-byte length; the 35/6 change is byte-built in `equip_change` (test
    helper) and compared exactly, including the profile read from the pet's own AddNpc; the AddNpc
    rows are parsed back with `startup_world::parse_add_npc`.
11. **Unique ids.** No id is allocated; the pet actor guid keeps the existing owner+pet scheme; the
    item word is an owned instance id.
12. **Others see changes.** Every accepted fit/clear puts the identical 35/6 into `wire.shared`
    (the gateway's nearby fanout) and into the owner's private list; the spawn, late-viewer and
    resummon paths carry the rows in the AddNpc. Canary 1 proves the viewer assertion depends on
    the push.
13. **Content works end to end.** The gateway test equips a real catalogue turban (definition
    2163) on a real adopted lab (item 2644) and asserts the echo, the roster, the 35/6, the
    nearby fanout, the trade block, the save and the reconnected AddNpc.
14. **Values live in data.** The five pane slots are the client's own slot map (pinned table, not
    tuning constants); item type/slot/class come from the catalogue rows; the profile comes from
    the content spawn template.
15. **Canaries break production code.** Both canaries removed production code (the viewer push and
    the class gate) and the named test failed; both were reverted and the suite went green.
16. **Hands off session plumbing.** No change to session creation, teardown, transactions or save
    ordering in `src/bin/osfr-gateway.rs` or `gateway.rs` (both net-zero).
17. **One player's error never stops the server.** `wear` returns a `PetWire` (no `?` out of the
    tick, no `unwrap` on client data); the decoder's `Err` is handled by the existing gateway path
    as a per-player refusal. No shared-tick code is touched.
18. **A type's rules live on the type.** `PetEquipment` owns the slot read/write/list
    (`worn`/`fit`/`instances`); `PetEquipmentSlot` owns the pane-slot table; `PetPresence`'s
    `attachments` field documents that the summon fills them and `view` starts empty.
19. **Hot paths stay cheap.** No per-tick work (costs in Structure). `pet_view` is the only
    per-message addition and it is skipped entirely when no pet is out.
