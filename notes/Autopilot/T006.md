## (R) rules

- Guild names 3-32 chars, letters/digits/space/hyphen/apostrophe, trimmed, no repeated spaces,
  byte cap 96, case-insensitive uniqueness.
- Rank order Leader/Officer/Member/Recruit; the permission matrix is as implemented.
- One guild per character; member cap 100; one live pending invite per target; the invite
  window equals the existing bounded `--group-invite-ttl-ms` (1-600 s); the sweep keeps one
  extra window of grace for a late 129/10.
- Creation eligibility: any unlocked job at rank 15; the rank curve is one per 100 XP, capped
  20.
- Rename and paid rename are refused with `GuildCantRenameAtThisTime`; member locations and
  129/15 are silent; 129/24's first pair is the inviter and the invitee `NameData` is empty;
  129/22 repeats the guild guid in both leading pairs; 129/17 codes follow the client switch.
- Ignore enforcement for guild invites is client-side (the client checks the inviter pair);
  no server-side ignore lookup for a forged accept yet.
- Guild file: one server-wide JSON beside the character save, 1 MiB cap, schema 1, atomic
  `character_store::replace_bytes`, saved after the character/social/chat saves and before
  the staged world commits.
- MOTD: at most 1,024 bytes and no control characters (a newline is currently refused; the
  editor's multiline capability was not recovered).

## Security threat note

Applied `secure-code-guardian` (threat model -> design -> validate -> document) to the
family-129 trust boundary.

A hostile client can forge guild/member ids, act as a non-member, send oversized or negative
string lengths, unknown sub-opcodes or trailing bytes, replay accepts, claim another guild in
guild chat, or put control characters in a MOTD. Controls:

- The actor is the authenticated session's character; the body never names it.
- `decode_request` bounds the packet (64 KiB), strings (4,096 bytes), the location array
  (4,096 ids) and requires exact consumption; malformed bodies are silent.
- Permission, membership, forged-guild and stale-invite refusals are silent; only known
  client result codes produce 129/23. A refused accept keeps the pending invitation (canary).
- The `responds_to` gate only skips work for requests `handle_decoded` would answer with
  silence; it cannot turn a refusal into an action. `a_guildless_member_request_is_silent_and_writes_nothing`
  and the service refusal tests pin that.
- 129/14 answers only the actor's own guild, so a forged id cannot enumerate names.
- Guild chat requires `ChatSession.guild_id` derived from the store and the packet's claimed
  guild id to match.
- The shared per-account action budget runs before parsing/staging; family 129 is charged.
- Pending invites are reclaimed after one extra invite window, so invented target guids cannot
  grow the map without limit. The map is runtime-only and is not persisted.
- An invite to an unknown guid only creates a runtime pop-up for that guid; it changes no
  player's items, position or guild.
- Trace bodies: family 129 is redacted by `trace::sensitive_payload`, so guild names, member
  display names, MOTD and invite text never appear as hex in the packet trace or Studio.

   file write; the forced save failure leaves memory and file unchanged.
