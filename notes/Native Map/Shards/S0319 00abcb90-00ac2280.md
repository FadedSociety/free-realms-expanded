# S0319 findings

## Housing client packet path

This range contains housing body writers, send wrappers, parsers and processor state. `00abcb90` writes the 127-family subtype-1 body with three dwords and a byte; `00ac0400` wraps and sends it. Other body writers cover customization (`00abcce0`), preview (`00abcd90`), locking (`00abce00`), house-name change (`00abce90`), name request (`00abcf40`) and save (`00abf620`, nested block `00abd1d0`). Unnamed fields remain raw. Rating writers and senders appear at `00abcfa0`, `00abd070`, `00abf6f0`, `00abfe70` and `00ac1540`-`00ac1ae0`; their packet classes are absent from the catalogue, and most contain no literal family/subtype opcode.

Housing send wrappers from `00ac01e0` through `00ac1e40` serialize a body or header, construct a tunneled ClientGateway packet and enqueue it. `00ac0b90` serves both the direct lock-toggle path and the add-candidate path's follow-up lock-toggle; both callers construct subtype 11. Receive-side paths include invite notification parsing (`00abd510`), instance-list parsing (`00abf210`), fixture-asset parsing (`00ac1f50`), fixture-list loading (`00abf760`) and fixture-update record parsing (`00ac2180`).

## Fixture records and local structures

`00abeb40` reads a variable-length FixtureDefinition tail. Its 50-byte size is the captured case with empty Category/LuaCall strings and no actions; non-empty fields change the total. `00ac2180` composes that reader with a 133-byte fixture record, 28-byte instance-info block, a guid array and three trailing dwords. The nine captured subtype-40 tails decompose as 28 + 50 + 16 bytes, but this client evidence does not establish server policy.

Red-black tree helpers occupy `00abdc40`-`00abe190`; `00abdc40` steps to successors and `00abdc80` to predecessors. `00abdcc0` updates parent+8 only when it equals the removed node and writes parent+0xc otherwise. Insert fixup `00abdea0` clears bit 0 only on the null-parent path; an existing black parent ends the loop without changing the node bit. Erase `00abe190` also repairs a black node with one black child. In the chunk pool (`00abe340`-`00abe530`), block+0x14 stores total chunks and +0x18 stores free/unused chunks. Allocation decrements +0x18; free increments it and releases the block when the values match. The 0x555 threshold limits each block size, not total pool growth.

Fixture ownership links include `00abd600`, `00abf1b0`, `00abf850` and `00ac2280`; `00abd310` owns the FixtureAction hash-list map. `00abd680` parses `%sHouseNames.txt` and its callers place it in housing resource-loading paths. `00abfda0` resets loaded-house state. Its virtual callback is gated by process flag `[this+0x10]+0x64c`, then invoked through the object at `+0x4198`.

## Wire context and note conflicts

Client captures summarized in `Research/Housing Placement Responses.md` show subtype 2 followed by server subtypes 40 and 44, and subtype 3 followed by 41. This supports a **hypothesis** that the original server answered placement with fixture-update and house-info records and answered pickup with fixture removal. The inference depends on sender `00abffb0`, parser `00ac2180`, the other response handlers and the captured flow; original server policy is not recovered.

`Housing Placement Responses.md` still calls subtype-2's first dword unrecovered, based on its overlap with unrelated community item ids. The later `Housing Placement Selection Identity.md` links it to a client placement selection id across subtype 1, subtype 2 and subtype 42 captures, while leaving the owning table unidentified and qualifying one ordering anomaly. This shard's `00abcb90` proves only that three dwords and a byte are serialized; it does not establish the first dword's meaning by itself.

The rating family has no matching packet-catalogue class. Send direction is visible, but those serializers/wrappers lack a catalogue class and literal opcode, so no guessed rating wire class/opcode or server behavior is recorded.
