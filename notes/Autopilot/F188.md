## Behavior

- A racing tick that only re-stamps `WeaponState::last_tick_ms` returns `changed == false` with no
  replies; the clock still advances (asserted via the saved snapshot).
- Start, finish + reward claim, abort, and any real weapon/pickup/schedule change still return
  `changed == true`. The finish leg of the regression test asserts the 40-coin payout lands once
  and the following tick reports no change.
- Reconnect between two clock-only ticks restores `Racing` with the prior job and keeps ticking
  without requesting a save.
- Restore validation is unchanged and strict: a nonzero clock is still bounded to the race window
  by `WeaponState::validate_for`, and the disabled-content guard compares the whole state.

## Evidence and reconstruction

No client opcode, packet field layout, enum value, reader or writer changed. This is a server-side
save-decision change, so no new IDA trace applies; the weapon wire layout documented in
`src/kart_weapons.rs` is untouched and its codec tests were re-run. (R) rules:

- (R) The racing tick clock is session-local progress ordering, not persisted progress. Only
  `WeaponState::tick` (server `now_ms`) writes it while racing, `WeaponState::begin` resets it, and
  `validate_for` bounds it on restore; no award, item, coin or id depends on it. A tick that only
  re-stamps it must not rewrite the character save.
- (R) A save whose weapons state differs from "nothing live" only by a nonzero tick clock is
  corrupt, even when content reports `weapon_effects=false`.

## Threat note (secure-code-guardian)

Attack surface: a hand-edited/replayed character save under `kart_entry.race.weapons`, and the
client's 33/x race frames. The clock is not client-settable: no packet path assigns it; only the
server tick stamps it. A hostile save can set `weapon_effects=false` with an otherwise default
`WeaponState` and a nonzero clock; that shape is **refused** again (`CorruptSnapshot { field:
"weapons" }`) and the refusal is pinned by the new test. `validate_for` still rejects any nonzero
clock outside `[race_started_ms, race_started_ms + max_race_ms]`, and ids/owners/counters are
validated separately, so the clock can mint nothing. The save-decision change only suppresses a
write request; it adopts no client state, skips no eligibility/budget check and changes no reward.
The new test content is synthetic and contains no player names or chat text.
