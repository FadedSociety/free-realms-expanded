## What this range is

One contiguous source region that contains three kinds of code:

1. **Packet classes used by the script layer** - guild (129), broker (130), inventory
   (42), progressive quest (207), command (26), factory (188) - each with constructor,
   destructor body, scalar deleting destructor, and (for the guild family) a dedicated
   serialise-and-send wrapper.
2. **Lua command handlers** registered into the client's script modules: Broker,
   Guild, EquipScreen, DsTree/DsTreeNode, Tree/TreeNode, ImageList, View,
   CharacterCreateUi, plus a long run of rows of the client's global script table.

   (vtable slots 0..3), `GuiDsImageList`, and the Lua userdata wrappers that hand
   nodes of a GUI tree control to scripts.

## Packet / wire findings (send direction)

* **Guild channel 129.** The family ctor `FUN_00a09b70` stores 0x81 at +4 and the
  sub-opcode at +8; the body writer `FUN_00a0de80` emits +4 then +8 as two `u16`s, so a
  guild datagram begins `81 00 <sub:u16>`. Sub-opcodes proven by ctor arguments in this
  shard: Create 1, Delete 2, Invite 3, Promote 4, Demote 5, Remove/Kick 6, Quit 7,
  Rename 13 - matching the catalogue's community channel 129 rows.
* **Contradiction with the catalogue.** `GuildInviteAcceptPacket` (00c0e8f0) and
  `GuildInviteDeclinePacket` (00c0e950) are built through `FUN_00b17220`, which stores
  sub-opcode **0** and nothing in either Lua command (00c10430) or their senders
  (00a0ee70 / 00a0ed50) rewrites +8. So this build sends `81 00 00 00` for both the
  accept and the decline reply, while the community catalogue numbers them 129/8 and
  129/9. Either the catalogue's client-request numbering for this pair is a
  reconstruction artefact, or the original server disambiguated the two replies by
  something outside the guild framing; that question is left open rather than decided.
* **Broker channel 130** (`BaseBrokerPacket`, 0x82 stamped by `FUN_00bee5f0`):
  Search 2 (`00c0c670`), Place 3 (`00c0c730`), Relist 4 (`00c0ca80`), Buy 5
  (`00c0cb70`), Cancel 6 (`00c0cc50`), sale-value request 7 (`00c0cd30`). The pinned
  catalogue has no broker rows, so the records carry no wire packet name; the bodies are
  one/two `u64` ids plus strings (see 00c0d590-style senders outside this shard).
* **Inventory channel 42** (`FUN_00a10400`): 6 = action-bar assign (`00c14720`, also
  cited by `Research/Pieces/048 Ability bar.md` and
  `Research/Original Inventory Food and Potion Use.md`), 10 = UseStyleCard
  (`00c10890`, catalogue row exists), 15 = immediate-activation use (`00c10940`),
  16 = immediate-activation check (`00c109f0`). 15/16 have no catalogue rows.
* **Command family channel 26** (`FUN_008a2820`, 0x1a): sub-opcodes seen here are
  0x15 (`00c149d0`, matches catalogue `CommandPacketFriendsPositionRequest` 26/21),
  0x18 recipe start (`00c14b30`), 0x28 play-intro-encounter (`00c14920`),
  0x2c storage check (`00c14a80`).
* **Progressive quest family channel 207** (`FUN_00bdc8a0`, 0xcf): start 2
  (`00c144f0`), claim slot 3 (`00c145b0`), claim prize 4 (`00c14670`), each carrying two
  payload words at +0xc/+0x10.
* **Factory channel 188** (`FUN_009d90d0`, 0xbc): request-recipe-reward sub-opcode 14
  (`00c14d40`).
* **Opcode 204** (`00c142c0`, `PacketEnterSocialZoneRequest`) is a payload-free request;
  no catalogue row covers it.
* Guild sends go out inside `ClientGateway::PacketTunneledClientWorldPacket` (gateway
  opcode 6, `FUN_0089ae70`); inventory style-card sends use the client variant
  (opcode 5, `FUN_0089adc0`). Every Lua command in this shard gates its send on the
  client's connected field `*(*(FUN_00769710()+4)+0x280)`.

## UI data structures

* `SoeUtil::Array<GuiDsImageList::Image,0,1>` is a small refcount-free array class whose
  vtable slots are visible here: slot 1 resize/reallocate (00c132d0, grow by 5/4,
  shrink by 6/5 below 3/4), slot 2 free buffer (00c13370), slot 3 move/swap (00c13390,
  xor-swap of the three fields, or forward to the source's slot +0xc), slot 0 scalar
  deleting destructor (00c134c0). `00c13400` is the pop-back primitive the destructors
  use (releases elements through their own vtable slot +0x10 then lowers the size).
* `GuiDsImageList` (ctor 00c13500, dtor body 00c13570, scalar deleting dtor 00c137a0)
  embeds that array at +0x30 and is created from Lua by `ImageList.Create` 00c135f0.
* DsTree/DsTreeNode are Lua-visible wrappers around engine tree objects; the userdata
  helpers push (00c11da0 / 00c126a0) and check (00c11e20 / 00c12720 / 00c129d0 /
  00c12120 / 00c13060) 4-byte handles, and methods call the wrapped object's virtual
  slots (+0x10 name lookup, +0x14 value read, +0x14 flag set for EnableScriptEvents).
  `00c12d40` is a helper that dynamic-casts a GUI object to `GuiTreeCtrl` through
  `__RTDynamicCast` with `GObject` / `GuiTreeCtrl` RTTI descriptors.
