# T004: pets roster, summon, dismiss, name and UI mode

Date: 2026-10-17

## What changed

- Ported the W177 pet service from the shared checkout into `ap-T004`.
- Routed family 53 requests through `gameplay.rs` and the gateway:
  summon/recall (`4`), roster-compatible item summon (`32`), name (`6`) and
  UI mode (`24`).
- Kept the roster in the character save's top-level `pets` payload. The active
  actor and UI mode are session state and reset on reconnect.
- Added the pet actor to the shared-world actor map and replay/removal paths,
  including late viewers and disconnect cleanup.
- Added a 50-pet cap at insertion and save validation, strict bounded request
  decoding, all-or-nothing request staging, and changed-state reporting so
  roster decay is saved.
- Added the recovered name flow: subtype 6 carries one length-prefixed string;
  subtype 10 returns the pet actor GUID, string and accept flag.
- Corrected `PetList` to carry the separate per-record `u32` key required before
  the pet record.
- Populated the pet actor's `AddNpc` with the recovered `Models.txt` model id,
  species texture alias and a facing vector; unnamed pets fall back to the
  bundled species display name.
- Routed subtype 32 through the live inventory: an owned adoption item can
  create the roster entry, consume one item and summon its pet; an already
  saved pet is summoned only when its matching item is owned.
- Added an explicit pet-dirty path: the normal character snapshot preserves the
  top-level `pets` field, then the gateway writes the updated roster through
  `game_store::save_pets_state` after a committed pet change.
- Corrected the pet clock boundary: the gateway passes milliseconds, while the
  existing pet service stores need clocks in seconds.
- Added the recovered `Models.txt` ADR-to-model-id bindings for the bundled
  pet models.

## Reconstructed rules (R)

- The actor GUID is derived from the authenticated owner and never from a
  client field; one active actor per owner.
- The 50-pet ceiling, refusal notices, reconnect actor reset, zone dismissal,
  and fallback model id are local policy.
- Name input is restricted to the recovered name lists; custom vanity names and
  name-change purchases are not implemented.
- Pet needs advance in seconds; a restarted server pulls saved clocks back so
  a prior process's monotonic time cannot reject a valid request.

## Open gaps

- The native client has not been used for this change. Actor appearance,
  follow motion, pet panel rendering and the name dialog remain unverified.
- Follow, care, equipment and trick requests are still service APIs, not
  routed gameplay requests. Subtype 32 accepts an owned adoption item by
  instance or definition id, but the exact meaning of its two recovered words
  and the native adoption presentation remain unresolved.
- The shared pet list's unresolved record fields and the exact zero active-pet
  sentinel remain reconstructed. The list's second string (texture alias) and
  icon fields are still emitted empty/zero.
- The character snapshot and top-level pet payload are each atomically written,
  but they are two sequential writes. A process failure between them during
  item adoption could preserve the consumed inventory without the new pet; a
  combined `game_store` transaction remains lead-owned.

## Security decisions

- Every refusal uses a staged service clone and leaves roster, actor and
  inventory unchanged.
- Ownership is checked against the loaded character roster; item summoning also
  checks the player's inventory.
- Request lengths, name byte length, UI mode range, roster count and actor
  position are bounded before mutation.
- No security-owned modules, launcher files, credentials or account/session
  code were changed.
