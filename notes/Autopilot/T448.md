## Evidence (client addresses, IDA broker)

- `008fb360`: reads a count, then per row a u32 map key and `008dacc0`; the row is hashed by key
  (`key % 0x23`). So the key is the row's map key.
- `008dacc0`: reads dwords into +0, +0x18, +0x14, +0x10, `008caaa0` (+4, +8), +0x1c, then one
  byte stored as bool (`!= 0`) at +0x20. 29 bytes; the last is `payload[28]`.
- `00c326c0` CollectionDataSource field getter, default case at `00c32836`: for field >= 9 and
  <= the field count, it fetches entry `field - 8` (`00992b80`) and returns byte `[entry+0x20]`.
  So `payload[28]` is exactly the `EntryCollectedN` column (`ScriptsBase.lua:3057-3064`, columns
  9..16).
- `00c31f00`: field count = `00992cd0()` + 9, and `00992cd0` returns the maximum per-collection
  count over the list. So without an 8-entry collection, column 16 (`EntryCollected8`) is out of
  range. This confirms in code the community finding that every collection, including one with 8
  entries, must be sent: rows are never filtered.
- Capture `lab/references/rust-gateway-reference/0007-login.bin` (sha256 f4b8b4ca...): the oracle
  test confirms 253 collections, 1,815 keyed rows, 841 with collected = 1, key 41 among them.
- Community decode (behaviour only): Lxzxrus `Sanctuary.Packet.Common/ClientCollectionEntry.cs`
  writes `Id` (the key), then DefinitionId, Index, CollectionId, NameId, IconId, IconTintId,
  Unknown, Collected.

## Test design

The synthetic reference is built with the opening content (`lab/references/opening-anvil-
placement-v1/content`, as `brawler_job_chain` and others do) so the real
`Gateway::load_gameplay` path runs. Its template gets two collections, every row flagged 1:
collection 10 with keys 41, 42, 43 and `u32::MAX`, and collection 20 with 8 entries. Payload and
reward bytes are distinct, so the byte diffs catch any stray write. Saves are injected as JSON
into a fresh character's real `GameplayState`, and the reload test round-trips the real
`Gateway::snapshot()` envelope through JSON.

## (R) choices

- The row key is the entry id that the ledger stores (community decode; the client only proves
  it is the map key).
- The ledger alone decides the flag. Item-owned entries (Lxzxrus marks those collected by
  inventory) are not derived here.
- `MAX_LEDGER_ENTRIES` 32,768 is the existing reconstructed bound; `completed` gets the same
  bound.
- `completed` is saved now, though nothing fills it yet (brief).

## Threat note

There is no new client input: the flags come only from the server-held save. A tampered or
corrupt save with an oversized ledger is refused at load (`invalid collection ledger`), like
achievements. The snapshot cap of 1 MiB (`game_store.rs:14`) bounds the bytes parsed. Unknown or
negative ids flag nothing (a u32 key above i32::MAX never matches). Nothing grants items or
currency.
