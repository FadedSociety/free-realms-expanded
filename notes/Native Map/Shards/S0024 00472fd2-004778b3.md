## Module identity

This range is one translation block of the client's **GDraw** 2D drawing
library, the `GFC_Draw` module of the Scaleform-derived "GFC" framework the
client already uses elsewhere (`engine.gfc.core/app/fx` in S0001). Anchors
outside the shard:

- 00463942 registers class info with the strings `GFC_Interface`,
  `GDrawDeviceD3D9`, `GFC_Draw_DrawDevice`, `1.0.0`,
  `Direct3D 9 DrawDevice`, `GDisplayD3D9Impl` and
  `Direct3D 9 Dependent Display` - i.e. the interface is called
  `GFC_Draw_DrawDevice` and `GDrawDeviceD3D9` is a concrete implementation.
- Class-registration entries 0045bac0 (`GDrawDeviceD3D9`), 004800c3
  (`GDrawSurface`), 0048011c (`GDrawDevice`), 0048019a (`GDisplay`),
  00480270-0048104e (`GDrawFx`, `GLineFx`, `GFlashFx`, `GFillFx`, `GBlitFx`,
  `GTextFx`, `GDrawText`) show the class-name family. They all pass a fixed
  `0x18` size argument, so registration size is not the class size.
- The class-name strings sit in the `0x1765xxx` data block together with the
  vtable/data labels used by this shard (`GDrawDeviceD3D9` at 01764880,
  the G*Fx vtables at `0x17fe91c`/`0x17fde0c`/`0x17fea34`/`0x17fa534`).

I used `engine.gfc.draw` for everything belonging to this device module
(new sub-name under the existing `engine.gfc` family; supported by the
`GFC_Draw_DrawDevice` string). The Fx writer classes themselves stay
`engine.gfc.fx` as set by S0001.

No contradiction with existing notes was found: S0001's `engine.gfc.fx` and
`engine.gfc.core` labels (GDrawFx/GFillFx/GBlitFx ctors, GInterface cleanup)
match what the same classes do here; this shard only extends the family with
the `engine.gfc.draw` device layer.

## Draw pipeline (how it connects)

Queued draw records are 0x20 bytes: 16-bit type id at +0, a descriptor value at
+4 (resolved by 0045fc2b = accepted `LookupDescriptorValue`), the state object
at +8, a count at +0xC and a rectangle at +0x10..+0x1C. 004778b3
(`DrawQueueFlushItem`) pops each queued item from +0x54/+0x4C, maps it into the
item's record array (base +0x18, cursor +0x1C, stride 0x20), writes the item's
payload into the queue's chunk pages through 00475352 and triggers the batch
pass 0047735b once the queue passes 0xFA items. 0047735b
(`DrawQueueExecuteBatch`) locks the dynamic vertex/index buffers
(004622fe/004623b5 = accepted `LockVertexBufferRegion`/`LockIndexBufferRegion`),
translates records through the per-type handler table **DAT_01bc45cc** (indexed
by the type id; virtual slots +0x1C translate, +0x20 release) - the link to the
G*Fx writer objects - switches the per-record state object through 00476d2d
(type 6 dispatches through DAT_01bc45f0), culls against viewport rectangles
(00409f40 = `VectorAt16`), emits visible items (0045ac9f/00462463 =
`SubmitDrawCall`) using the per-batch offset table DAT_01bc4708, then releases
consumed records (00476f76) and recycles the record blocks
(+0x1000..+0x100C). This is the last stage behind the accepted
`DrawQueueDrainAndCommit` (00477cd1), `DrawQueueCompile` (0047990d) and
`DrawQueueReplayTable` (00479c56).

State changes produce field/value deltas: 0047559e compares param_1 and param_2
over 14 dwords and two 10-dword blocks, uses DAT_01af61e4/DAT_01af6234 for
field identifiers, allocates a `count*8+8` record and stores it through
00474e90/00474f0a. 00476d2d is its caller and applies the result during a state
switch; the field meanings remain unknown.

## The container template family (52 records in `crt.stl`)

Roughly half the shard is out-of-line instantiation code for the containers
this module uses: vectors with 4-byte, 12-byte and 36-byte elements
(`size`/`capacity` pairs at +4/+8, memmove of `count*12` through 0045f056/
0046da84), and associative trees with an allocated sentinel node (self-linked
left/right/parent, nil byte at +0x11 or +0x15, key dwords at node+0xC,
per-type allocators 0045ebd6/0045e8d5/0045ec39 that throw `std::bad_alloc`).
Because the allocators use `std::bad_alloc`, these are standard C++
container instantiations, so I labelled them `crt.stl` with archetype names
(`VectorAppendN`, `VectorInsertSlowPathN`, `TreeInsertKeyN`,
`LookupInsertKeyN`, `ContainerDestroyFreeN`, `TreeHeaderInitN`) rather than
inventing class names. The pre-insert/pre-teardown helpers in these records are
the accepted checked-iterator constructors (`VectorIterCtorA..J`,
`TreeIteratorCtor*`, `TreeIteratorDeref*`) and the erase step is the accepted
`std::_Tree::erase_range`; they never destroy elements themselves. Call graphs
stitch them into this module: e.g. 004748f2 (12-byte append) -> 00473290
(insert slow path), 004749c9/00474a4f/00474c29/00474d4b/00474e90
(lookup-or-insert) -> the five tree inserts, 004752ce (`AdvanceSegmentCursor`)
-> 004748f2, 00476081 -> 004752ce.

## Uncertainties and open questions

1. The fourth embedded Fx writer (+0x15C, vtables 0175d3b8/0175d3b4) still has
   no matching registration string (`TopLayerBlitFx`/`BottomLayerBlitFx` are
   registered but their emitters are 00418ce1/00436f31, unproven).
2. The exact Fx class for mode-1 helper 004803f7 and role of mode-5 helper
   0049e668 remain unclear. The GFC Fx note identifies helpers 0048063d,
   00480784 and 0048050e as fill/blit/flash copies for modes 2/3/6; 004771b2
   shows which slots it clears, not the semantic type of every slot.
3. The exact element type of the 12-byte segment vectors (the (base, length,
   block) segments appended by 004752ce) and of the 4-byte vectors is not
   proven; only the strides are.
4. DAT_01bc45cc entries are G*Fx-derived per-type handlers (slot +0x1C/+0x20
   match the per-type write/release calls and 0045fc2b resolves each record's
   descriptor value), but the table's construction site is outside this shard.
5. The page object (0xA4) has no RTTI name in this range; if a later shard
   finds one, the `PageObject*` names here should be renamed to match.
6. 00474818's two virtual predicates are unnamed. 004777fc's first-element
   accessor does not remove the vector entry; the count-changing side effect is
   not visible in the destructor body.
