**Wire shape.** Every BattleMages message starts with the shared two-u16 inner
header read by `FUN_00b70e40` (family + sub) and is carried inside a
`ClientGateway::PacketTunneledClientPacket` (catalogue base opcode 5): the
serialisers `FUN_00b72160` (header) and `FUN_00b72450` (header + an eight-byte value + 3 dwords)
write into a bit-stream. `FUN_008fb810` copies two dwords for the `+0x10` value; its semantic type is unknown. `FUN_00b72b60` / `FUN_00b72c80` wrap and send the stream
(`FUN_0089adc0` = tunneled-client-packet ctor per the accepted map label;
send via `FUN_00925640`). The only two located senders are `FUN_00b72dd0`
(`RegisterPlayer` with the entity guid) and `FUN_00b72e80` (guid + local player
`+0x390`/`+0x394`, gated on the gateway pointer `client+0x280`).

**Inbound routing.** Inner Battle Mages readers and handlers consume the payload carried by `PacketTunneledClientPacket`; this shard has no inner family/sub values in their own code, so their wire entries identify the outer catalogue packet and leave opcode null. `FUN_00b728a0` is `BattleMagesProcessor::vftable[4]`
(read from the binary vtable at `0x01822bc4`). Raw jump table at `0x00b72afc`
maps sub 2, 4, 6, 8, 0xb, 0xc, 0xd to read/apply bodies:
`FUN_00b72020` (sub 2), `FUN_00b71bd0` (4), `FUN_00b71af0` (6),
`FUN_00b72200` (8), `FUN_00b72540` (0xb), `FUN_00b71ef0` (0xc),
`FUN_00b72700` (0xd). Subs 3, 5, 7, 9, 0xa fall to the fail path even though
a sub-5 reader/apply path exists (`FUN_00b71d90` plus unreferenced fragment `FUN_00b71e80`; neither has a recorded caller) -
that asymmetry is the shard's biggest open question.

**Gameplay anchors.** The read/apply bodies walk the entity list at
`processor+0x40` (next `+0x80`, id `+0x10`) and update entities through
`FUN_00cd5250/00cd5260/00cd5270` (projectile vectors) and `FUN_00cd5710`
(create-projectile apply). `FUN_00b72f60` is the activity switch: it is cited by
`notes/Research/Kart Entry Register Prerequisites.md` as a per-state controller

camera block through `FUN_00af9230`, and its enter path calls `FUN_00cd5b30`,
which references the strings `bm_camera` and `bm_reloaddata`.

**Server inference (hypothesis).** A battle-mages server received the tunneled
family-0x85 bodies, kept per-sub payload layouts identical to the readers above,
and answered with the same classes (subs 2/4/6/8/0xb/0xc/0xd) to drive proxied
players and projectiles. `CreateProxiedPlayer`/`KickProxiedPlayer` carry a guid
plus a version word that the client compares against `DAT_01be9940`/

exists for family 0x85 in this investigation, so all of it stays hypothesis.

  the Battle Mages family has a separate, structurally identical reader
  `FUN_00b70e40` at `00b70e40`. Same pattern, different family - do not conflate.

  index <= 1 returns `*(this+0x220+idx*4)`, anything else returns 0. The note's

* The five `+0x648` slots that look like camera/controller handles are, per
  `FUN_00b77d70`, the MG_Soccer cue-sound set; `FUN_00b73b20` releasing them is
  sound teardown, not a camera teardown. Records were corrected accordingly.
* `FUN_00b75460` builds a runtime handle around a definition passed in (its only
  caller passes the five sound definitions), so it belongs to audio, not to the
  scene/effect path it superficially resembles.

4. `FUN_00b76420` has no recorded caller; which frame hook drives the metric
   pass is unproven.
5. The Battle Mages senders in this shard contain no family/sub constant (both
   live in the S0352 ctors), so their `wire` entries name only the tunnel
