## What changed

- **Role.** `AccountRole::Moderator` (stored `"moderator"`) and `AccountRole::outranks` (R: Admin >
  Moderator > Builder = Player, strictly). In `can_run_realm_command`, a moderator runs only `mute`,
  `unmute`, `kick`, `ban` and `unban` (R). `realm role` can grant the role, admin only as before,
  and `osfr-account set-role` accepts it.
- **State** (`src/account_store.rs`). `StoreData.sanctions: BTreeMap<account id, Sanctions>` holds
  `muted_until` and `banned_until` in unix seconds. `serde(default)` lets older stores load, an
  empty map is not written, and `validate` refuses a sanction row for an unknown account. The map
  holds ids and times only. `account_by_display_name` returns the owner when every character
  whose displayed name has the command's words belongs to that one account (attempt 3; it used to
  need exactly one character).
- **Unique by words (attempt 3).** `name_words` reads a name as its whitespace-split, lowercased
  words, however the spaces fall between and inside the two parts. `character_name_taken` (used
  by check-name, create for both the displayed and the temporary pair, `insert_character` and
  legacy adoption) refuses a pair whose words equal any existing character's displayed or
  temporary words. This covers the old exact-pair rule. Loading (`validate`, `name_keys`) stays
  pair-based, so stores that already hold such pairs keep loading.
- **Rules** (`src/moderation.rs`, new).
  - `Command::parse` reads `<action> <First Last> [minutes]`. Names hold no digits
    (`identity::valid_name`), so an all-ASCII-digit last word is the minutes.
  - `apply` (private) checks, in order: the actor's stored role, one target by display name, not
    the actor's own account, the strict hierarchy, a later expiry kept, and no-op unmute or unban
    refused.
  - `run` takes the store writer lock, loads, applies and saves atomically
    (`AccountStore::save` -> `character_store::replace_bytes`). A kick only reads the store.
- **Bound in data.** `data/content/moderation.json` holds `max_minutes` (525600 shipped, (R)). A
  file that does not parse yields 0, so every timed sanction is refused and nothing panics.
  `bundled_bounds_are_sane` asserts the value is at least 1. No minutes means until lifted
  (`u64::MAX`, (R)).
- **Gateway** (`src/gateway/staff.rs`, new; the hub keeps a 6-line dispatch).
  - `staff_command` holds the old inline `realm role` block plus the moderation words.
  - The role gate (`may_run`, with the account-store role) runs before any parsing.
  - A valid moderation command is staged in `GatewayOutcome::moderation`.
  - `refresh_role`, which already runs on every message, also reads the account's `Sanctions`.
    `chat_muted()` compares them with the wall clock.
- **Host** (`src/bin/osfr_gateway/moderation.rs`, new).
  - After `commit_outcome` succeeds, `run_staged` runs each staged command for the verified
    `session.account_guid`. It answers with a system chat line and writes one audit row. For a
    kick or ban it marks the target's bound sessions `kicked`.
  - `Server::step` ends a kicked session through `end_session`, which saves the character and
    leaves the world, social, guild and membership state. Further messages from a kicked session
    are dropped unread.
  - `muted_chat` refuses 15/1 typed chat on every channel (say, tell, group, guild and the rest),
    67/2 and 67/3 quick chat and (attempt 2) the 129/11 guild MOTD, with one line to the sender.
    It now runs before `route_guild`.
  - `refuse_banned` holds the binding's ban check (attempt 2; the hub keeps one call).
- **Ban enforcement.** `LoginService::handle` opcode 1 answers the ordinary `login_reply(false)`
  for a banned account. The broker path re-runs it on every request, so a ban also ends a
  character-select session. The gateway refuses character binding after the ticket check.
- **Store lock per request (attempt 2).**
  - `osfr-login` takes `AccountStoreLock` around one request's load, checks, character handlers and
    save, not for its life. Startup only validates the store and refuses a stale lock.
  - Order in `Session::application`: the cheap checks first (token syntax and the per-IP budget for
    opcode 1, a principal for anything else), then the lock, then token redemption. Malformed
    traffic never touches the lock file. A well-formed opcode 1 with a bogus token does: within
    the per-IP budget (20 a minute, burst 20) it creates, fsyncs and deletes the lock and loads the
    store before redemption fails (corrected in attempt 3; the cost is bounded by that budget).
  - A busy store answers opcode 1 with the ordinary `login_reply(false)` before the token is
    redeemed, so the token survives for a retry. Any other request on a busy store ends that login
    session, as any other login error does.
  - `AccountStoreLock::acquire` retries every 10 ms for up to 500 ms (`LOCK_WAIT`, (R)) before
    reporting `AlreadyExists`. This covers login per request and `osfr-account`, which no longer
    needs login stopped.
  - (Attempt 3) The gateway's staff writes (`moderation::run` and `realm role`) use
    `acquire_within(path, STAFF_LOCK_WAIT)`, 50 ms (R). They run on the world loop every player
    shares, and with a stale lock the 500 ms wait cost every player about 2.5 s per second at the
    moderator's action budget; now it is at most 0.5 s for a burst, then 0.25 s per second. A
    login request that holds the lock longer than 50 ms makes a staff command answer "busy",
    and the moderator sends it again.
  - (Attempt 3) When login finds the lock still held, it prints
    `osfr-login: account store lock <path>.lock is held; request refused` to stderr, so the host
    can see why logins fail after a writer was killed inside its hold.
- **Audit** (`src/security_log.rs`). `EventKind::ModerationAction` and `record_moderation` write
  one unbatched row per applied action: actor and target account ids, the action name and the
  minutes. `record()` refuses that kind. The four refusal kinds keep their batching unchanged;
  `index` and `action_reason` are folded into one `refusal()` table.

## Security

Threat note (secure-code-guardian, security-reviewer):

- **Who may act.** The actor is the host-verified binding (`session.account_guid`, only when
  `selected_character`), never a packet field. There are two gates:
  - The gateway's `may_run` re-reads the role on this message before the name is parsed. A player
    gets the generic developer denial, counted as `DevCommandDenial`, and learns nothing about
    names or roles.
  - `apply` re-checks the actor's stored role under the writer lock.

  Without an account store the host answers "a verified account binding is required" and nothing
  runs.
- **Hostile input.** The only input is the chat text.
  - Lowercased words are compared with stored display names; there are no paths and no format
    strings.
  - The minutes are parsed as a `u32` and bounded by data. `minutes * 60` and `now + seconds`
    saturate.
  - Replies are fixed strings. The command text is never echoed or logged.
- **Wrong target and immunity (attempt 3).** Names that read alike on two accounts
  (`"Ann Lee" "Moss"` and `"Ann" "Lee Moss"`) are refused rather than resolved to one of them.
  Since attempt 3 such a pair can no longer be created, so only an older store can hold one.
  Look-alikes on one account resolve to that account, since sanctions are per account, so a spare
  slot no longer buys immunity. The creation rule compares exactly what the resolver compares
  (`name_words` on both sides), so any name a moderator can type resolves to at most one account
  in a store built under this rule.
- **Refusals change nothing.**
  - Every `apply` refusal returns before `set_sanctions`, and `run` saves only on success.
  - Staged commands run only after the moderator's own transaction commits, so a refused or failed
    bundle runs none.
  - The tests compare the store bytes, session liveness and the audit log before and after every
    refusal, including the case where the store lock is held.
- **Oracle.** Moderators can tell "no single character" from "equal or above"; that is staff-only.
  - The gateway checks a ban only after the binding ticket verifies.
  - The login server's ban answer is the ordinary failed login, reached only after
    `local_session` or broker key-pair redemption.
- **Persistence.** One atomic `AccountStore::save` (`replace_bytes`) under `AccountStoreLock`. The
  role command's lock and load path are unchanged, except that since attempt 3 it waits 50 ms
  for the lock (`STAFF_LOCK_WAIT`).
- **Lock scope (attempt 2).** Every writer (login per request, the gateway's `realm` writes,
  `osfr-account`) holds the lock across exactly one load-modify-save, so none can overwrite
  another's change. Login reloads the store and its handlers under the lock on every request and
  caches nothing across requests. Readers (`refresh_role`, the broker's AUTH2 answers, binding)
  stay lock-free; `replace_bytes` swaps the file atomically.
  - **Busy.** A busy store refuses a login before the token is redeemed (and, since attempt 3,
    prints one stderr line), and a moderation command gets "busy" after 50 ms and changes nothing. A stale lock is still an operator decision: it is never
    removed on age or PID, and login now refuses to start on one, as before.
  - **Cost.** One lock file create, fsync and delete per login request that passed the cheap
    checks, including a well-formed opcode 1 whose token is bogus. Requests are already
    rate-limited per session and per IP. A blocked writer stalls its own loop for at most 500 ms
    (login, `osfr-account`) or 50 ms (the gateway's staff writes, attempt 3). An authenticated player flooding login requests could keep the
    lock busy often enough to make a staff write answer "busy"; each such request already reloads
    the resource tables, so this adds no new amplification (accepted, (R)).
- **Logs.** Audit rows hold account ids, the closed action name and the minutes only.
  `moderation_audit_has_ids_only` checks the exact key set and that no cast name appears. The
  `session_ended` reason is `moderation`, and the binding refusal reason "account is banned" holds
  no ids.
- **Audit flooding (accepted).** Moderation rows are unthrottled, so a hostile moderator could
  rotate older rows out of the bounded L9 log (1 MiB current plus `.previous`). The rate is capped
  by the per-account action budget (5/s, burst 10) and every row names the actor.
- **Fail closed (R).** An unreadable account store mutes chat for that message, just as it already
  drops the role to player.
- **Isolation.** A kick or ban touches only the target's sessions. The actor's session is outside
  the map during dispatch, and self-targeting is refused.

## (R) choices

- The hierarchy is Admin > Moderator > Builder = Player, strictly higher only, and nobody targets
  their own account. A moderator may lift a sanction an admin set, because the rule is on the
  target's role.
- The moderator command set is mute, unmute, kick, ban and unban only.
- The maximum is one year (`max_minutes` in data); no minutes means until lifted.
- A second sanction keeps the later expiry.
- An expired sanction counts as none. Unmute and unban answer "not muted" and "not banned" and
  change nothing; the stale row stays until replaced.
- An unreadable store refuses chat (fail closed, like the role).
- A name resolves when every character whose display words match belongs to one account
  (attempt 3). Names on two accounts that read alike are refused, never guessed.
- New names, displayed and temporary, are unique by their whitespace-split lowercase words, a
  stricter form of the old case-insensitive pair rule (attempt 3). Loading stays pair-based.
- The gateway's staff writes wait 50 ms for the store lock; other writers wait 500 ms.

## Open gaps

- **Fixed in attempt 3: immunity by look-alike names.** See What changed and Security.
  - **L049 merge (lead).** L049 (`d2a33f2`, on `autopilot`, not in this base) changes
    `character_name_taken` to fold Latin letters with `name_key`. On integration, keep this
    words rule and fold each word: in `name_words`, map `name_key` in place of `str::to_lowercase`.
    `name_key` folds per character, so folding per word equals folding per part. The resolver then
    folds the typed command words too, as the brief asks. `name_keys` and `validate` keep L049's
    lowercase pair rule. L049's separator rule refuses 'Al  Bo', so the new login test accepts
    either 4 (taken) or 7 (invalid) for that one case.
  - **Older stores.** A store written before attempt 3 can still hold names on two accounts that
    read alike. Both names stay unmoderatable by name, and the refusal is safe, since it never
    picks the wrong account. There is no `realm ban #<account-id>` form yet. If one is needed,
    `realm role` already parses an account id.
- **Look-alike scripts (not changed).** `identity::valid_name` accepts any Unicode letter, so
  in this base a Cyrillic look-alike of an honest player's name can still mislead a moderator who
  types ASCII. L022's Latin-only rule (on `autopilot`) closes that for new names, and L049 folds
  accents. The confirmation line does not name the account id.
- **Investigated in attempt 3: the `login_broker` handshake flake.** Once under machine load,
  `ban_and_unban_apply_while_login_runs` waited 30 s for the third client's SessionResponse (the
  first `recv` in `NativeClient::connect`). The cause is not established:
  - Code reading rules out L042's lock. The SessionRequest path (`run`'s `[0, 1]` branch,
    `Session::new`) takes no lock and reads only the resource tables and `identity.json`.
  - The per-IP handshake bucket (20 a second, burst 32) and the 32-session cap are far from
    reached.
  - What remains:
    - a lost or very late datagram;
    - a transient file-read failure in `Session::new`, which the loop drops without a reply;
    - the login process having exited. Its `--seconds 300` limit ends it quietly, and an
      `accept` error in `Broker::poll` would end it with a stderr line.
  - The harness now resends the exact SessionRequest every second within the 30 s budget, as the
    real client does and as the server allows ("only an exact retry may reuse an occupied
    peer"). The check that a different request gets no reply now accepts late copies of the
    first response and refuses anything else.
  - On a failure, `Server::drop` now prints whether the login child had already exited before
    the kill, so the next occurrence names the cause.
- **Fixed in attempt 2: the login lock.** Login held the store lock for its whole life, so every
  `realm` write answered "busy" in the runbook topology. Login now locks per request (see What
  changed), and the gates below run with login and the gateway on one store.
- **Native-client gates 1-3 are not run here.** The machine was on battery (85%, discharging) after
  the shutdown, and a lab gateway and login of the lead's were already running. The same three
  gates pass over real sockets with real processes and bots
  (`moderator_mute_and_ban_land_while_login_runs_and_lapse`). A run with the FreeRealms client
  remains for the lead's native lane.
- **Kick does not keep a player out.** A kicked player can log in again at once, because the
  gateway binding ticket is a static HMAC with no expiry or nonce
  (`login::gateway_binding_ticket`). Use a timed ban to keep someone out; the runbook says so.
- The kicked or banned client gets no SOE disconnect and times out, as with every existing
  `end_session`.
- The mute covers chat and (attempt 2) the guild MOTD. It does not cover guild names on create or
  rename, mail or other text features.
- **Refusals are not audited.** A moderator's refused attempt (for example on an admin) writes no
  row; a player's attempt counts as `DevCommandDenial`. A refusal row would help spot a rogue
  moderator, but it needs a closed reason enum and changes the audit key set; left for the lead.
- **Not live-tunable.** `MAX_MINUTES` is read with `include_str!`, so it is fixed at build time,
  unlike reloadable content. A file that does not parse refuses every timed sanction (safe).
- **Deploy one build.** `deny_unknown_fields` and the new `moderator` role mean an older login,
  gateway or osfr-account refuses a store this build wrote. The runbook now says so.
- A brief store read failure (for example a sharing violation during another process's atomic
  replace) mutes that one message (`refresh_role` fails closed, like the role).
- Expired sanction rows are never pruned; growth is bounded by the account count and the 1 MiB
  store limit.
- `ban_blocks_login_until_expiry` injects the clock into the sanction (a ban that ended in the
  past), not into the login check, which reads the wall clock.
- `realm role` still writes the store during staging (unchanged, pre-existing).
- `apply`'s second role check (under the lock) cannot be reached separately through the production
  path, because the gateway gate runs first in the same dispatch. It is defense in depth and has no
  canary of its own.
- `Action::word` repeats the table in `Action::parse`; kept, because the exhaustive match is
  compiler-checked.
- Hub `src/bin/osfr-gateway.rs` is +17, under the 40-line budget but not net-zero (see Structure).

## Checklist

1. Refusals change nothing. Every refusal path compares the store bytes, liveness and the audit
   log: `moderation_refusals_change_nothing` (including the held lock and the ambiguous name), the
   hierarchy test and the expired-unmute case. Canaries C8, C11, C12, C13 and C16.
2. Rollback covers all state. The only state is the account-store file, written once after the
   commit, and the `kicked` flag, set after a successful save. Nothing is staged outside.
3. Deltas, not snapshots. Sanctions are merged into the freshly loaded store under the lock; no
   inventory, coins or position is touched.
4. Busy rules. Moderation is not an activity. A kick or ban ends the session through
   `end_session`, which already releases trades, groups, guild presence and fields.
5. Every entry path is gated. There is one entry (`realm` chat -> `staff_command`); bundled and
   combat-split messages go through the same per-child dispatch. Login and binding both check the
   ban (C4, C5b). Attempt 3: every path that creates a name (native create for the displayed and
   the temporary pair, check-name, `insert_character`, legacy adoption) goes through
   `character_name_taken`, so all of them use the words rule (CB).
6. Real path. The tests drive `Session::dispatch_message`, `Server::step` and
   `LoginService::handle`. Attempt 2 adds the production topology itself: a running authenticated
   `osfr-login` (`login_broker`) and real gateway, login and bot processes on one store
   (`bot_acceptance_1016`).
7. Survives reconnect and restart. The mute test restarts the server and relogs, and the ban test
   re-binds before and after expiry. The state is in the account store.
8. Exit paths. Kicked and banned sessions end through `end_session`; the ban test checks the save
   (C6).
9. Economy. Not applicable (no coins or items). The minutes are bounded and ids never come from
   packets.
10. Wire format. No new packet; only the existing 15/3 reply and `login_reply(false)`.
11. Unique ids. Not applicable.
12. Others see changes. The target's removal reaches others through `end_session`'s existing
    `leave_player` fan-out.
13. End to end. The commands answer, persist, block chat, refuse login and binding, and end
    sessions.
14. Values in data. `max_minutes` is in `data/content/moderation.json`, with a sanity test.
15. Canaries break production code; every one is listed above, and the sources were restored
    byte-for-byte.
16. Session plumbing. This is a lead-only task. The only lifecycle change is one `kicked` branch in
    `Server::step` that calls the existing `end_session`; save ordering is untouched.
17. One player's error. `run_staged` returns only the moderator's own queue error. Log failures are
    printed and never undo the action, and no arithmetic can panic.
18. Rules on the type. `Sanctions::muted` and `Sanctions::banned`, `AccountRole::outranks`, and
    field docs on `StoreData.sanctions` and `Gateway::sanctions`.
19. Hot paths. No state is cloned per tick; the cost is one bool per session per step.
