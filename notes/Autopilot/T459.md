# T459: boombox catalogue, and boomboxes on the item bar

Attempt 1, Opus lane. No earlier patch existed.

## What changed

- **New data** `prototype/osfr-tools/data/content/boomboxes.json`.
  - 15 rows, sorted by `item_id`. LF line endings, 26,390 bytes, sha256 `ad086dcd…3373a1623`.
  - Shape: `{schema_version: 1, boomboxes: [...]}`.
  - Row fields follow the brief: item_id, model_id, kind, dance_sequence, clip_ms, blend_ms, song_effect_ids,
    standing_animation_id, priority, transform_model_id, transform_reapply_ms, duration_ms, range_m,
    spawn_offset_m, recast_ms, texture_alias, tint_alias, and `source [{kind, evidence}]`.
  - Every row cites the line of its Sanctuary row, the line of its item definition, and the Models.txt line of
    its model. It also carries an (R) entry for the measured clips and the tunables, plus an (R) entry for any
    model conflict.
- **New generator** `scripts/build_boomboxes.py`.
  - Stdlib only; run it with `python -I`. Running it again reproduces the same sha256.
  - It reads `Sanctuary-main-20261019@10f129e src/Resources/Consumables.json` and
    `FreeRealms-Legacy@9e08202 src/Resources/ClientItemDefinitions.json` through `git show`, as data only.
  - It also reads the client's `Models.txt` and W84's captured baseline `inventory.json`.
  - Its asserts make a drifting source fail the run: exactly 15 Class 171 items, and no unexpected Sanctuary
    fields.
  - The kind rule: `transform` when there is a TransformModelId, otherwise `synchronized` when SynchronizedDances
    is set, otherwise `independent`.
  - It leaves out the six Sanctuary-only rows: 76877, 78075, 900059, 900060, 900061 and 900063.
- **New module** `src/boombox.rs`, registered with one line in `lib.rs` (CRLF kept).
  - `Catalogue::load(dir)`: a missing file gives an empty catalogue.
    - Limits: 256 KiB and 64 rows, `deny_unknown_fields`, unique item ids.
    - Bounds: ids > 0, with 0 meaning "none" for standing and transform. Every ms value is in 1..=600000,
      `range_m` in 1..=50, `spawn_offset_m` in 0..=10, `recast_ms` in 3000..=600000.
    - The row shape must also agree:
      - The sequence is not empty.
      - Every clip list has one entry per dance step.
      - `clip_ms` is empty exactly when the kind is `independent`.
      - `transform_model_id` > 0 exactly when the kind is `transform`, and `transform_reapply_ms` is 0 otherwise.
      - At least one source.
  - `Catalogue::get(item_id)`.
- **Item bar** `src/item_bar.rs`.
  - `ItemBar::load(directory, boomboxes: Arc<Catalogue>, saved)`. The Arc sits next to `effects` (`serde(skip)`),
    so a save clone stays cheap and nothing about the catalogue is saved.
  - `View` carries the catalogue. `owned_action` accepts a recovered consumable, as before, or a catalogued boombox
    with no rental.
  - `slot_update` already sends a row without an Effect as disabled. 36/10 on a box reaches `consume`, finds no
    Effect and returns 36/1 (`abilities::unsupported_cast_failure`), changing nothing.
  - 42/15 and 42/16 still match only `use_wire::consumable`, so they are untouched.
- **Hub** `src/gameplay.rs` (net −1 line). The item bar is now loaded after `npc_content` is resolved, so the
  catalogue comes from the same authored-content folder as stores, rides and NPCs: the bundle's content when it
  ships `npcs/`, otherwise `data/content`.
- **content_check** `scripts/content_check.py`.
  - It accepts an AnimationGroup id (from `AnimationGroups.xml`) for `boomboxes.json`, as it already does for
    `job_abilities.json`.
  - The standing dances 3200, 3550 and 3570 are groups only, and the brief's gate 2 allows groups.
- **Tests**
  - `tests/item_bar.rs`: the five `ItemBar::load` calls pass `Default::default()`.
  - New `tests/boombox_catalogue.rs`: 8 tests (see Gates).

## Where the brief or research was wrong

1. **"A rental … the existing Unavailable rejection covers it."** It did not. `OwnedAction::is_available` only
   checks the count, and only `usable` refused rentals. `owned_action` now refuses a rented boombox outright. The
   reply is UnknownItem ("That item can't go on the item bar."), and reconcile drops such a binding.
   - Rental potions are deliberately untouched ("keep the potion path unchanged"). A rented potion can still bind
     and shows enabled, but every use is refused.
   - Open, for the lead: apply the same rule to potions?
2. **Class 171 at runtime.** The item definitions the server loads first are the captured rows. Both W84's
   baseline `inventory.json` and the OSFR server's `Customize/ClientItemDefinitions.json` say:
   - 35759 (Clockwork Boombox) is **class 9**;
   - 9114 (Ghost Tails Campfire) and 67888 (Party Crate) are **class 171**.

   The reference definitions that W84's catalogue is generated from (Legacy, and Sanctuary too) give exactly the
   15 boomboxes as Class 171. Gate 4 therefore checks against those, and the item bar keys on catalogue ids,
   never on class. The client's picker also lists 9114 and 67888 (Type 1, ability > 0); the server refuses them,
   which the test covers.
3. **Aliases.** The 5 captured rows (1180, 1913, 8185, 35759, 48244) carry empty model and texture strings in the
   definitions the server loads. Their `texture_alias` therefore comes from the reference item row, the same row
   that supplies the model file. Each row's evidence says so.
4. The research pack's "realm give at gameplay.rs:2972" and "the brief has the two model ids the wrong way round"
   were checked and are not used here: the brief's model-conflict rule is applied as written.

## (R) choices

- **Clips and kinds.** `clip_ms` and `blend_ms` were measured by Sanctuary (10f129e), not read from client data.
  `kind` is derived from Sanctuary's flags. Independent rows (1913, 48244, 76935) have an empty `clip_ms`; their
  per-dancer random tables are the boombox-random-dances slice.
- **Tunables.** duration_ms 180000, range_m 15 and spawn_offset_m 2 are Sanctuary's BoomboxDefinition defaults
  (`BoomboxDefinition.cs:9-11`). recast_ms 180000 is the duration with the 3000 ms floor from 14914ac
  (`ConsumableAbility.ClampCooldown`). All are per row and tunable within the loader's bounds.
- **Model conflicts**, kept (R) until the lead checks them natively:
  - 69825 Chiller uses **4428** (its item model is mkt_boombox_realmshake_01.adr); Sanctuary has 1062.
  - 76927 Pop-Dance uses **1062** (its item model is bw_boombox_01.adr); Sanctuary has 4076.
  - Counter-evidence: Models.txt describes 4076 as "K-Pop Boombox", which suggests Sanctuary may be right for
    Pop-Dance. Note too that 69825 and 76935 now share 4428.
- **No client model file.** 48244 (XVD-S) keeps Sanctuary's 185 sh_primitive_radio_01.adr, and 76934
  (Xylophone) keeps Sanctuary's 4100.
- A rented box cannot bind (rentals are never usable on the bar; rental expiry is not modelled).

## Threat note (secure-code-guardian)

A hostile client controls 42/6 (slot and instance id), 42/9 and 36/10.

- **42/6 with an instance it does not own.** `owned_action` looks the id up only in the player's own inventory:
  UnknownItem, nothing changes.
- **A class-171 item that is not catalogued, or a rented or used-up box.** UnknownItem or Unavailable. The bar is
  byte-identical (tested), and the answer is the authoritative 38/25.
- **36/10 on a bound box.** It reaches the one spend path, finds no Effect and returns 36/1. No item is consumed,
  no recast is stamped, and nothing is spawned or granted.
- **Server data.** The catalogue is read-only content from a fixed path, bounded in size and rows, with
  `deny_unknown_fields`. Nothing from the client becomes a path or a catalogue key.

## Checklist

1. **A refusal changes nothing.** Refused 42/6 (rental, none left, not a boombox): the item bar is equal and its
   serde bytes are identical. Refused 36/10: inventory and item_bar (including the recast map) are equal. The
   rental and catalogue canaries fail the test.
2. **Rollback covers all state.** There is no new state. The catalogue is an immutable `Arc`, and `assign` keeps
   its existing compare.
3. **Deltas, not snapshots.** Not applicable: nothing is paid out or restored.
4. **Busy rules.** Not applicable: binding is not an activity, and using a box stays refused until the spawn
   slice.
5. **Every entry path.** 42/6 and 42/9 both go through `assign` → `View::owned_action`. 38/25 refresh and
   reconcile use the same `View`. 36/10 goes through `consume`, and 42/15 and 42/16 stay consumable-only.
6. **Production path.** The real `Gameplay::load` resolves the catalogue, and test 6 drives
   `Gameplay::handle_in_world`.
7. **Reconnect.** In test 6 the bound box survives a reload (still disabled at world entry). A binding whose row
   left the content loads without an error and is dropped at the first refresh (test).
8. **Exit paths.** Not applicable: there is no activity.
9. **Economy.** Nothing is granted or consumed. Only owned instances can bind, and rentals are refused.
10. **Wire format.** No encoder changed. The 38/25 slot for a box uses the existing `for_owned_action` with
    `enabled = false`, and the test decodes it with `use_wire::decode_slot_update`.
11. **Unique ids.** Not applicable.
12. **Others see it.** Not applicable: the item bar is private.
13. **Content end to end.** The shipped file loads in production, and binding works with the real row (test 6).
    Use is deliberately disabled until the spawn slice.
14. **Values in data.** Every tunable is a per-row value in `boomboxes.json`, bounded by the loader.
15. **Canaries** break production code (see Gates).
16. **Session plumbing.** Untouched.
17. **Tick safety.** Nothing runs in the tick. A bad file fails `Gameplay::load` with `Err` (a content error, the
    same behaviour as `consumables.json`).
18. **A type's rules on the type.** `Boombox::valid` holds every row rule. Doc comments on `clip_ms`,
    `transform_reapply_ms` and `Kind::Transform` say which fields depend on the kind.
19. **Hot path.** `owned_action` scans at most 64 rows, only when an item is not a recovered consumable (it
    short-circuits), on 42/6 and on refresh (4 slots). Nothing per tick; `state()` clones only an `Arc`.
