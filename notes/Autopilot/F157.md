# F157 - F121 review repair

Repairs the GPT Sol review of `fd48caf` (`lab/autopilot/reviews/fd48caf-F121.md`).
Every BLOCKER is addressed below; finding 5 is a lead-only dispatch/security
decision and is called out for the lead instead of being self-approved.

## What changed

1. **Tick and shared reward paths now settle achievements (review 1).** The
   counter scan moved out of the request handler and is called at every
   authoritative transaction seam:
   - `Gameplay::tick` snapshots the counters at entry and settles changed ones
     before returning, so soccer/kart/derby tick payouts, DoT kills and
     gathering ticks award their titles in the same tick. Regression:
     `tick_reward_crossing_a_rank_awards_its_title_without_reconnect` drives a
     real soccer match through `Gateway::handle_at`/`Gateway::tick_at`; the
     50-XP win crosses level 20, the tick emits `152/1`, and the following
     `152/4` selects the title without a reconnect.
   - `Gameplay::apply_encounter` settles after job XP, a kill or a completed
     run (the shared-field and shared-effects path bypasses the request sync).
     A plain hit or a coin-only reward does no scan.
2. **Duplicate definition ids are authorized and described once (review 2).**
   `ClaimWindow::definitions_response` no longer rejects `[id, id]`. All
   requested ids are authorized against the pending rows or the existing
   tracker first, then deduplicated before the response blob is built.
   Regression `duplicate_definition_ids_are_authorized_and_described_once`
   queues one grant with two entries for definition 8, lists it through `108/1`,
   then sends the native-reader-derived `108/5` with `[8, 8]`: one complete
   `108/6` row, no claim consumed. An unowned id is still refused with no reply
   and no state change (`[8, 25]`: 25 is a catalogue definition, so only the
   ownership check can refuse it).
3. **Hub logic moved to an owner module (review 3).** The counter mapping,
   settlement and the transition call live in the new
   `src/gameplay/progression.rs` child module (same pattern as
   `gameplay/npc.rs` and `gameplay/occupation.rs`); `gameplay.rs` keeps one
   thin call per transaction and is 83 net lines smaller than the F121 tip.
4. **One achievement transition engine (review 4).** `on_event` and `observe`
   now share `AchievementProgression::advance`; only the next-counter
   derivation stays separate (incremental vs absolute). The completed-rule
   behavior is documented on each method and unchanged: an incremental event
   skips a completed rule, an absolute observation keeps its stored counter
   current without emitting.
5. **Lead-only dispatch change kept, not self-approved (review 5).** The
   account budget still runs before `Gateway::handle_at` stages a bundle, and
   the recursive combat dispatch still marks its children budgeted. Added the
   coverage the review asked for:
   `mixed_bundle_is_dropped_whole_when_its_budgeted_child_is_refused` (a free
   `167/1/4` child does not run when its budgeted sibling is refused) and
   `account_budget_is_shared_across_sessions_and_not_across_accounts` (two
   connections of one account share the bucket; another account keeps its own).
   This remains a session/security decision for the lead: see "Open gaps".
6. **Complete `108/6` decoding proof (review 6).** `decode_definitions_response`
   parses the tracker echo, success byte, declared length, count and every
   definition row, comparing each to the catalogue row and asserting exact
   cursor consumption. (F205: item 8 is compared to a pinned reader-derived
   fixture instead, so the encoder and test no longer share ground truth.)
7. **Notes (review 7).** This file has the full checklist (1-19) and the
   `## Structure` section; `notes/Autopilot/F121.md` now carries the missing
   item 17 and its own structural accounting as a F157 addendum. (F205: the
   earlier "items 17-19" wording was wrong; only item 17 is required.)

## Threat note (secure-code-guardian)

- A hostile client can send duplicated or forged definition ids, unknown
  trackers, forged claim ids, title ids, and over-budget bundles. The server
  authorizes every requested definition id against its own pending rows or an
  existing tracker before dedupe/lookup; an unauthorized id still receives no
  reply and changes no state (test asserts the snapshot).
- Duplicate ids are only a wire-shape possibility created by native
  `00a04c10`; they never grant extra definitions, items or claims. The response
  describes each definition once and consumes no claim.
- The account budget remains one bucket per authenticated account, charged
  before staging; a refused bundle changes no gameplay, saved bytes or replies.
  Refusal is silent (no amplification) and recorded as `BudgetRefusal`.
- No reward amount, item id, title field or counter value comes from the wire.

## Reconstructed rules (R)

- Achievement counter values are `job rank - 1` and the completed regional
  quest count; only a counter that moved is observed, so progress-only
  observation emits nothing. (R, unchanged from F121)
- Accepting a repeated definition id and deduplicating the display list is
  server policy; the native client really can ask for `[id, id]`.
- The soccer test's 50-XP job reward and seeded 1850 XP are test fixtures, not
  recovered content values; the shipped achievement thresholds/titles are used
  as content.
- F121 rules stand: pending claims instead of immediate achievement items,
  claim row `+4` = grant count, unnamed `+0x14`/`+0x150` fields zero.

## Checklist

1. **Refusal changes nothing.** New refusals are the unknown-definition id and
   the over-budget bundle. Both are tested with a snapshot taken before the
   refusal, then equality after (and no outbound replies); the duplicate test's
   refusal sits beside an accepted request that also asserts the snapshot, and
   canary 3 proves the ownership check (not a missing catalogue row) is what
   refuses it.
2. **Rollback covers all state.** Achievements, titles, claims and counters
   live in the cloned `ProgressionExtras`/`Gameplay`; this repair adds no side
   table, `Rc` or `Arc` state. A refused staged clone is dropped whole.
3. **Deltas, not snapshots.** Settlement reads the current inventory/profile
   snapshot and applies only titles/claims; the existing live-coins claim test
   (unchanged) still passes. The tick path replaces the staged gameplay clone,
   not an older captured snapshot.
4. **Busy rules mutual.** No activity was added or changed, so the
   `Occupation` table and its gates are untouched; the spine count is unchanged
   at 39.
5. **Every entry path gated.** Levels, jobs, busy and eligibility are unchanged;
   achievement settlement now additionally runs on tick and shared-encounter
   transactions (the two paths that previously lacked it) and still on every
   request and both login paths. No new reward path was created.
6. **Reachable in production, tested through it.** The tick regression drives
   `Gateway::handle_at` login/Play/lifecycle/shot and `Gateway::tick_at`; the
   budget tests drive the binary's `Session::dispatch_message`; the duplicate
   test drives `Gateway::handle_at`. Canaries broke production code.
7. **Survives reconnect.** Achievement counters/titles remain in the existing
   `ProgressionExtrasState`; the pending-claim reconnect/replay test still
   passes. The tick sets `out.changed` when a title is awarded, so the same
   staged character state is saved.
8. **Every exit path restores the player.** No lifecycle was added; the soccer
   match uses its existing finish/close flow, and title selection does not own
   an activity. The dashboard of exits (cancel, disconnect, timeout, win) is
   unchanged.
9. **Economy safety.** Definitions never consume a claim and never grant an
   item; dedupe happens after server-side authorization. Rewards still come
   only from server-owned grants; no client quantity/id is trusted.
10. **Wire format matches readers.** The complete `108/6` body is decoded and
    consumed exactly by an independent test decoder; `150/7`, `150/3`, `152/1`,
    `152/3`, `152/4` layouts are unchanged from the F121/T005 evidence. The
    `00a04c10` no-dedupe fact is cited above.
11. **Unique ids.** Unchanged from F121: achievement claim ids are stable
    hashes with the high bit set; title ids come from owned definition bindings.
12. **Others see changes.** This repair adds no other-player presentation. The
    removed job-switch experiment never shipped; no broadcast path changed.
13. **Content end to end.** The regression asserts the real end state: a
    50-XP server-scored soccer win crosses rank 20, `152/1` carries the
    content-bound title id, `152/4` answers with `152/3` selecting it, and the
    saved snapshot's active title equals that id. Not just an intermediate flag.
14. **Values in data.** Achievement thresholds, counters, title names/ids and
    the claim bindings come from shipped content; no timeout, cap or tuning
    constant was added. The 50 XP/1850 XP values are test fixtures.
15. **Canaries break production code.** All three canaries edited production
    code (`tick` settlement, definition dedupe, definition ownership), failed
    the intended tests, and were reverted before the final green runs.
16. **Hands off session plumbing.** This repair does not touch session
    creation, teardown, transaction ordering or save ordering. The F121
    dispatch/budget relocation remains a lead-only decision (review 5) and is
    flagged NEEDS-LEAD rather than claimed as accepted.
17. **One player's error never stops the server.** (F205 correction: the
    claim that this settlement ran only inside a single session was wrong.)
    `apply_encounter` settles from `Gameplay::tick_shared_effects` and
    `receive_field_damage`, which `Server::tick_shared_instance` calls for every
    player in a field; a settlement `Err` faulted that whole field. F205 makes
    the settlement atomic and deferred: claim/title capacity failures are logged
    and the moved counter is re-observed by a later transaction, so no caller
    receives an `Err`. Regression:
    `tests/titles_claims.rs::settlement_capacity_failure_defers_the_award_without_failing_the_transaction`.
    The counter conversion is bounded with `unwrap_or` and rank math uses
    `saturating_sub`.
18. **A type's rules live on the type.** The counter/value decision is
    `Gameplay::achievement_counters` in the owner module; the transaction
    boundary decision is documented on `settle_achievement_counters`; the
    incremental/absolute difference is documented on `on_event`/`observe` and
    implemented in the shared `advance`.
19. **Hot paths stay cheap.** `handle_in_world` keeps F121's one counter
    snapshot per request; `tick` adds one snapshot per tick, and `tick_at` only
    ticks opening/kart/soccer/derby sessions (not an ordinary loaded player).
    `apply_encounter` scans only when the outcome has job XP, a kill or a
    completed run. When no counter moved, no reward state is cloned and no
    packet is emitted.
