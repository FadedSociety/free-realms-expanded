## Half 1: the review step has no item list to fill

- The review popup is `tradeConfirmation.gfx` (window `wndTradeConfirmation`, Lua `TradeConfirmation`). Its
  movie script has six text fields and buttons only: a warning line, the body line, a status line, ACCEPT,
  CANCEL and exit. `init` fills them from string keys (TradeScamWarning 506, TradeBodyText 504,
  TradeScamWaiting 509, TradeScamReview 511, TradeScamAccept 514, TradeScamCancel 516). There is no list, row,
  data-source or `TRADES` binding. The `masterList` string seen in the file is the bundled TweenLite
  animation library's own array, not trade data.
- String 511 (locale row `Global.Text.511`, key `world_text::locale_hash`) is not a panel title. It is the
  status line: `startTradeTimerMessage` and `enableAcceptButton` swap the status line from 509 (waiting) to
  511 ("review the items") when the client gets the confirm message (59/18, `00c6df10` case 18 raises
  `TradeConfirmation:StartTradeTimer`). It tells the player to look at the items in the trade window.
- That window is still on screen. `TradeConfirmation:OnResize` places the popup 315 px left of centre, and
  `player_trade.gfx` `lockForTrade` only disables the quantity stepper and the add/remove arrows; the
  offer and partner lists stay visible and keep refreshing (`refreshOffers`, `refreshOthers`). The native
  note of the same night already confirms the offered items show in both main windows (owner correction).
- `TradeConfirmation:Populate` is empty in the client Lua (`ScriptsBase.lua` 56714). No native call feeds the
  popup, so there is no packet to add. The original client behaves the same: the final check is the main
  window's two lists. Changing packets would not change the popup.

Recommendation: close the "review lists no items" finding as client behaviour. If the owner wants a list in
the popup, that is a new client-side widget, which a server cannot add.

## Half 2: why a cancel says "left the game" (client text recovered)

Client status handler `00c6df10` case 15 (59/15, one byte) picks the text key per status. The hashed locale
rows resolve with `Global.Text.<id>` (id from `CodeStringMappings.txt`, hash `locale_hash`), which the build
guide had left unresolved:

| status | key (string id) | what the player reads |
|---|---|---|
| 1 | TradeCanceled (2398) | "<partner> canceled the trade" |
| 2 | TradeCanceledPartnerDisconnected (2395) | "<partner> left the game" |
| 7 | TradeCanceledYouEnteredInstancedZone (3096) | "Your trade has been canceled." (no name) |
| 8 | TradeCanceledPartnerEnteredInstancedZone (3097) | "Your trade with <partner> has been canceled." |
| sub 16 | TradeRejected (2399) | "<partner> doesn't want to trade" |

Statuses 2, 7 and 8 also withdraw an unanswered invite toast (`00a0eb90`, only while the session counter is
0); status 1 does not. So 7 and 8 are generic "cancelled" lines whose key names are about instanced zones.

Server today (`src/trade.rs`): `close_pending` always sends status 2, so an invite that times out, whose
inviter walks away, or that is cancelled shows "left the game" to two players who are both online.
`maintain` sends 2 to both when either side fails `online_player`; `refresh_trade_player`
(`src/bin/osfr_gateway/delivery.rs`) calls `unregister_player` (status 2 to both) when a still-connected
character's inventory stops validating; an active client cancel (sub 7) sends status 1 to both, so the
canceller reads "<partner> canceled the trade" about their own click; `settled(false)` and `timeout` also use
1.

Proposed mapping (R, our choice among the client lines; statuses chosen by the client text above):

| end | canceller / mover | other player |
|---|---|---|
| client cancel, active or pending | 7 | 1 for an active session, 8 for a pending invite (toast must go) |
| invite or session timeout, walked out of reach, battle/mini-game start (`cancel_for`, `set_away`), failed commit (`settled(false)`) | 8 | 8 |
| real logout (`disconnect`, `unregister_player` from logout, `maintain` with a side offline) | none (gone) | 2 to the player still present |
| inventory stopped validating while connected | 8 | 8 (needs a distinct call, not `unregister_player`) |
| invite declined | already 59/16 | n/a |
| instanced zone | already 7 / 8 | n/a |

Tests to write with the change (two sessions on one shared gateway, `tests/player_trade.rs` world helper and
`tests/common/gateway_packets.rs`, no new helper): one per row, reading the 59/15 status byte of each
recipient (today's tests only compare the sub-opcode list `[15, 5, 15, 5]`, so none of them pins the byte);
a logout test asserting the surviving side gets 2 and a timeout test asserting nobody gets 2.
