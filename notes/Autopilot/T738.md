# T738: grouped players in one battle run share one arena (rebuild of T441)

A member who accepts the group's encounter prompt (T440) fights the same enemies as the starter:
one summoner health, one minion set, one driver tick for the enemies, one win. Every member keeps
their own health, knockout, results screen, prize wheel and payout. Solo runs build no arena and
answer byte for byte as before.

This run is the lead's rebuild: I applied `lab/autopilot/patches/T441-a3.patch` with
`git apply --reject --whitespace=nowarn`, ported the two rejected hunks by hand, deleted the
`.rej` files, re-ran every gate and hardened one flaky rig wait.

Registered skills: **ponytail (full)** and its review pass (I cut the redundant `kinds` assertion
in `a_solo_run_answers_the_same_with_or_without_a_group_fight_elsewhere`; everything shipped is
used), **secure-code-guardian** (threat note below). IDA: no new client layout; I checked the

## Design decisions (brief step by step)

1. **Registry.** One map by run instance (the arena keeps the battle id; the group id was dropped
   as dead state). Not `(group, battle) -> instance`: the run instance is already the key T440
   hands out, and a client never names it. **Deviation:** the arena is created at the first
   Accept, copied from the inviter's live run, not at the first Go. A grouped player nobody joined
   has no arena, so a lone run stays byte for byte the old path (gate 9) and costs nothing per
   tick.
2. **Join.** Accept stages the member's join exactly as T440 does. Before it, `prepare` finds the
   live arena (it must `admits()`: not won, not lost, not faulted, under `MAX_MEMBERS` 4 (R)) or
   copies a new one from the inviter's live run. After the commit, `attach` adds the member. The
   joiner's own scene load (`on_zone_ready`) runs inside the loan, so the late-join burst is the
   arena's actors and current health. An arena that will not admit (full, won, lost, faulted)
   takes nobody: the Accept still joins T440's run and the joiner plays their own solo copy. A Won
   run cannot be accepted at all (`run_live` needs a live run), and an ex-member's own Go starts a
   solo run in a new instance. Instance ids never come from the client.
3. **Driver tick.** `group_arena::tick` runs once per server tick before the sessions' own ticks.
   Per arena: prune members who left the instance, mark lost, fan out a win, else (`due`: 100 ms,
   the solo step) one driver engine runs `tick_arena_enemies` for every standing member; each
   enemy moves and swings once, at its target. **Deviation:** a one-member arena still ticks (the
   brief's "at least two members" is read as "one driver for the whole run", not a minimum):
   after the other member leaves or disconnects, the remaining member's enemies must still move
   and turn (gate 7). Each hit is applied through that member's own staged gateway
   (`receive_arena_damage`: health, knockout, results), saved first, then packets. A tick that
   faults freezes that arena only (`faulted`, logged once).
4. **Outcome.** The win is the goal enemy's death in any member's action (`leave_arena` records
   `won`). The next driver tick runs `finish_shared_win` for every member still in Loading or
   Fighting: results, prize wheel (a pick of its own), the member's own reward and the
   `CompleteDungeon` quest credit through the normal `apply_encounter`, XP to that member's active
   job, once (the phase moves to Won, so a repeat finds nothing). A knockout is personal (R): only
   that member's results; the arena is lost only when no member is Loading or Fighting (re-derived
   every tick, so a Retry makes it live again). Close returns only that member (T440's exit); the
   arena lives until its members have left the instance, then goes. **Deviation:** not removed at
   the win itself. A disconnect drops the member at the next tick (location no longer the run's);
   the saved run goes through the existing login abandon path to the safe pose.
5. **Packets.** What one member's hit made, the others also need: enemy health, spawn, removal,
   effects, motion, animation, boss bar, objective count, and never anything naming the arena's
   own player actor (guid 1 is a different character on each client). Only hits and ticks fan out
   (a scene load answers its sender alone). Damage popups (32/7) go to the member hit.
6. **Limits.** Hubs against the tip's ceilings: `encounter.rs` 2890 (-82, 2997),
   `osfr-gateway.rs` 4640 (+13, 4643), `gateway.rs` 2106 (+1, 2142), `gameplay.rs` 5129 (+1,
   5168); `world.rs` +31 (not a hub).

## Recovered vs reconstructed

- (R) `MAX_MEMBERS` 4 (a sanity bound; the party's own size limit applies first).
- (R) Enemy targeting: the last attacker while that member is standing in the fight, else the
  nearest standing member.
- (R) A knockout is personal; the run is lost only when every member is knocked out or gone.
- (R) After every member is lost, a Retry rejoins the arena where it stands (enemies are not
  reset).
- (R) Kill-credit quests (`defeated` ids) stay with the member whose hit killed; every member gets
  the `CompleteDungeon` credit and the win payout.
- (R) Stuns and target buffs on enemies belong to the arena, not to the caster; a member's own
  DoTs and caster buffs stay theirs.
- (R) Battle 96 is the only `summon_below_percent` battle: summoner 900 HP, six minions, two per
  75/50/25 % tier (`data/content/field_battles.json`).

## Threat note (secure-code-guardian)

A hostile client cannot name an arena, an instance or a member: the Accept comes from the
server-held invite row (T440), and the run is rechecked against the inviter's live run, the party
and the responder's Go gates; the arena is found from the session's own character and its current
location, so a forged or replayed 41/103 answers nothing. Instance ids never come from the client.
A forged 36/10 still goes through the unchanged hit path (range, swing gate, shield,
server-computed damage); hostile slots/targets are refused or ignored there. A member's hit cannot
pay another member: every payout runs on that member's own gateway, once per run (phase guard). An
enemy hit lands only on the member it targets, and a member cannot be hit by another member's
packet. Over-cap, won, lost and faulted arenas take no member (the joiner plays their own solo
run). One member's failed step (their reward, save) rolls back that member and the arena step and
is logged; a faulted arena freezes alone and nothing propagates out of the tick. No client
quantity or id reaches a payout, and a replay of Close or Go pays nothing.

## Checklist

1. Refusal changes nothing: the loan is a copy; a dispatched action that errors drops it, and a
   refused hit (`Ok(default)`) is copied back unchanged. Tested: a refused hit before the fight
   (`a_refused_hit_changes_nothing_in_the_shared_run`, with canary b breaking production code),
   T440's refused Accept (`a_refused_accept_leaves_the_invite_answerable`: location, membership,
   party and save bytes equal, invite still answerable), and the `admits` latch
   (`only_a_live_arena_with_room_admits`).
2. Rollback covers all state: all arena state lives in `SharedArena` (cloned per action and per
   driver tick); members' own state rides their gateway clone; no `Rc`/`RefCell`/`Arc` side
   tables. A driver member step that errors restores that member's gateway and the arena and logs
   `arena_member_refused`; a save error aborts the tick before any install.
3. Apply deltas: payouts run on the member's live gateway at the finishing step
   (`apply_encounter`); no old snapshot is restored over live state. Tested by the once-only win
   and the Close/Go replay payout equality (`a_win_pays_every_member_once...`, unit
   `a_win_pays_each_member_once...`).
4. Busy rules: no new activity; a run is an encounter, already an `Occupation`. The join uses
   T440's Go gates (`Gameplay::join_group_battle`, the `activity_busy` table); no hand-written busy
   check was added.
5. Every entry path gated: the only way in is T440's Accept (group, live run, Go gates) and then
   `admits()`; `tick_arena` acts only on members placed, ready and scene-loaded; a client cannot
   name a run, an arena or a member. Tested by the recheck suite and a refused Accept.
6. Reachable in production, tested through it: `tests/shared_group_arena.rs` drives real sockets,
   `Server::step`, the application dispatch, `commit_outcome` and the driver (no internal calls).
7. Survives reconnect: the shared run is runtime only and never saved, so a save cannot seed one;
   the member's own save carries their canonical run and the existing login abandon returns them
   to the safe pose. Tested (`a_disconnecting_member...`: B reconnects outside the run at the
   battle marker, no arena).
8. Every exit path restores the player: Close (only that member, tested), knockout
   (`a_knockout_is_personal...`), disconnect (prune + abandon, tested), win (results + Close,
   tested); Retry after a shared loss is re-derived per tick (unit-covered, see gaps).
9. Economy safety: rewards come only from the server's own win (`win_run` reached from a
   server-computed hit or the fan-out), once per run (phase guard, unit and socket tests); a
   replayed Close or Go pays nothing (socket test); quantities and ids are never client-supplied.
10. Wire format: no packet written or changed, only recipients; the offsets the fan-out reads are
    byte-tested (`public_reply_tests`, including 35/12's count-first layout) and the writers are
    pre-existing; the client 35/2 deserializer was checked (`FUN_00921a10`).
11. Unique ids: the run instance comes from World's allocator (T440); an arena never mints one;
    enemy GUIDs come from content and are disjoint from field GUIDs (existing pin test).
12. Others see changes: enemy health, spawn, removal, effects, motion, animation, boss bar and the
    objective count fan out after the actor's commit (`Held::publish`) and from the driver; tested
    by the shared-health test (the partner sees the one health) and the two-parties test (the
    other party sees nothing).
13. Content works end to end: the shipped battle 96 over real sockets; the tests assert the final
    outcome (one summoner, one minion set, results once for both, prize wheel, payout through
    `assert_payout`), not an intermediate flag.
14. Values in data: enemy behaviours, HP, thresholds, rewards and prizes stay in
    `field_battles.json`/`behaviours.json`; the 100 ms arena step matches the solo tick;
    `MAX_MEMBERS` is the one compiled bound (R).
15. Canaries break production code: both canaries edit production code (`group_arena.rs`,
    `encounter.rs`), not the test, and both fail; both reverted (see Gates).
16. Session plumbing: not changed. `dispatch_message_inner` and `Session::tick_at` gain a loan
    around the existing `handle_at`/`tick_at` and a `publish` after the existing commit (13 lines,
    the brief's step 3 wiring and T440/T461's accepted post-commit precedent). Session creation,
    teardown and transactions are untouched; `commit_outcome` still saves before anything is
    published. The driver tick saves outside it, one member at a time (F839: `group_arena::step`).
17. One player's error never stops the server: the driver runs under `contain`; each member step
    rolls back and is logged; a failed save rolls back that member only (F839, fault-injected);
    no `unwrap` on client data; saturating/checked arithmetic throughout.
18. A type's rules live on the type: `SharedArena` documents what it owns (all runtime) and what
    stays personal, and owns `admits`/`due`/`set_lost`; `ArenaSim.acting` and `last_hit` are
    documented on their fields (and `reset_session` detaches a member).
19. Hot paths: see Structure for the per-tick and per-packet cost; nothing is cloned when no
    shared arena exists, and solo play never builds one.

## Open gaps

- A member's damage popup (32/7) on an enemy is shown to the hitter only; the other member sees
  the enemy's health bar fall (35/5) but not the number.
- Stuns and buffs a member applied to enemy actors stay in the arena until they expire (they are
  keyed by enemy, not by caster) — intended (R).
- `finish_shared_win` does not run `sync_tracked_target`; a fan-out win does not grant the
  achievement settle beyond what `apply_encounter` already does for rewards.
- Gate 5's "quest credit": battle 96 has no quest with a `complete_dungeon` goal (only battle
  12400 in brawler and 12350 in adventurer are authored), so the socket test observes the
  once-only phase, results, wheel and payout and the `CompleteDungeon` event path, not a visible
  quest count.
- The 5th member's Accept (over the four-member cap) has no socket test (the rig seats four; the
  `admits` latch is unit-tested).
- Closed by F839 (lead): `tick_arena` commits each member's step alone (`group_arena::step`: copy,
  step, save when changed, then install). A failed save drops that member's copy and steps the
  arena back, never faults the arena, and a pending win retries on the next tick, paying once
  (`a_member_whose_win_save_fails_is_paid_once_on_a_later_tick`). Only a panic faults an arena.
- Retry after a shared loss makes the run live again (the lost flag is re-derived every tick):
  unit-covered by `a_knockout_is_personal_and_keeps_the_arena_effects`, but there is no socket
  test that presses Retry in a shared run.
