## Threat note (secure-code-guardian)

Attack surface: family 53 subtype 32, an 8-byte client body (definition u32, tint u32), plus
the save envelope it can trigger. A hostile client could send:
- a zero/truncated subtype or a zero definition: `PetRequest::decode` returns an error
  (`wrong length`, `zero item definition`); an unknown subtype decodes to `None` and the
  gateway ignores it, so neither reaches gameplay state;
- a definition/tint pair that does not match an owned instance:
  `owned_item_for_record`/`adopt_with_replies` refuse; `tests/pet_routing.rs`'s wrong-tint and
  no-certificate tests assert inventory, roster, actor and save bytes unchanged;
- a pair for an item that is not a configured pet certificate: `definition_for_item` refuses;
- a replay after the certificate is spent: no owned instance, refused without mutation;
- an adoption while a minigame is active: `PetBusy` from `Gameplay::blocks(gates.pets)`
  refuses in `PetService::summon`;
- a save-failure race (the server's own disk/reader): the commit returns Err before installing
  staged state, so the certificate is not spent and no pet or roster entry exists (tested).
  In production that Err ends only the sender's session (`contain` -> `end_session`), never
  another player's; the test also proves the session state is unchanged, so the error is not a
  half-applied transaction.
The server never trusts a client pet id from this subtype (the two words are an item record),
never allocates an instance id from client bytes, and the save path is host-owned. No secrets,
no logging of payload text, no new filesystem path is derived from client input. This diff is
test-only, so it adds no attack surface; it pins the refusal and rollback behaviour above.
