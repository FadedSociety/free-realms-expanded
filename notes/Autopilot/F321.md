## Semantics chosen (finding 2)

A reward remains one server-authoritative outcome. `items` (bag-limited, atomic
through `grant_bundle`), `coins` (wire `i32`) and `job_xp` (wire `u32`) are
refused together when any component cannot be represented; nothing is
half-applied. The review's preferred per-component remedy was attempted in
attempt 2 and renamed the three tests the integrator protects by name; the
review also accepts naming the un-granted prize. The item is therefore still
withheld on a capped reward, but it is no longer silently destroyed: the
refusal line says so. A per-component payout remains an optional lead
follow-up (it needs the protected test names updated and is an economy
decision).

## Security threat note (secure-code-guardian)

A hostile client cannot name a reward amount, item, definition or result: the
payout still comes only from the server's own actor HP transition / won-battle
state and the loader-validated content table. This diff adds no input field or
request. The client combat surface is unchanged (a replayed lethal or corpse hit
is refused before credit; a target must be known/alive/in range; the participant
set is server-owned). On a cap the whole reward is refused before any mutation,
so the player cannot mint a withheld component; the item prize is the
server-verified battle prize and this change touches no price or sale path. The
content read is local trusted data, not client input, and is now bounded;
malformed/oversized content still refuses the load instead of partially
applying. The refusal string is fixed `(R)` text and contains no client text.
No save, trade, session or role surface changed; the two test robustness edits
are test-only. The 1 MiB cap and the `(R)` string are the only constants
involved; neither is client-controlled.
