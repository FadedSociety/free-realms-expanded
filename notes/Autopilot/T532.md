# T532 - a happy pet speeds its owner up

Rebuilt on the newest tip: `T532-a2.patch` was applied with `git apply --reject`, every rejected hunk was ported by hand, the `.rej` files were deleted, and the gates were re-run. The rejects were all tip drift: T533's hand-kept `treasure` field and treasure branch in
`pet_tick`/`settle_pets`, and the T533 test file's three `settle_pets` calls that the older
patch could not know. Two claims in the earlier attempt's note were wrong and are corrected here
(icon 3851 and composite 15216 both resolve; 57918 is an item row, not an effect definition).

## What changed

- `data/content/pets.json` (LF; `deny_unknown_fields` kept): a top-level `happy_buff` block -
  `happy_mood` 25, `speed_bonus` 3, `duration_ms` 10000, `refresh_ms` 4000, `tag_id` 1800000000,
  `icon_id` 3851, `name_id` 116881, plus a `source`. Every number is (R) except the three client
  ids, whose evidence is below.
- `src/pets.rs` (the owner of the rule):
  - `PetContent.happy_buff: Option<HappyBuff>`, `HappyBuff::valid()` bounds: mood 0..=100 finite,
    bonus 0.1..=10 finite, duration 1 000..=600 000 ms, refresh 100..duration, tag id above
    1.5e9 (past the consumable and world-tag ranges), icon and name non-zero. A content set
    without the block behaves exactly as before.
  - `PetService.happy: Option<HappyBuffLive>` = one live row (`refresh_at_ms`), cleared by
    `reset_session` (reconnect) and whenever the rule stops.
  - `happy_buff_tick(now_ms) -> Option<Vec<Vec<u8>>>`: the only place the rule is evaluated.
    Holds = summoned pet, not vanity, decayed mood >= `happy_mood`; while it holds one 38/16 row
    (`abilities::build_effect_tag`, reader `008d8870`) starts and refreshes every `refresh_ms`;
    when it stops the row is removed (38/17, `encode_remove_effect_tag`). `None` when nothing is
    due, so an ordinary tick returns after two `Option` checks. Session-only: it never marks a
    save.
  - `happy_speed_bonus() -> Option<f32>`: the live bonus read by both the validator and the stat,
    so the two cannot disagree.
- `src/movement.rs`: `SpeedModifiers::with_speed_bonus(bonus)` folds the flat bonus into the
  existing `buff_multiplier` as `(base + bonus) / base`, clamped to the 1.0..=10.0 range
  `effective_speed` already enforces. A non-finite/negative bonus is ignored (narrows, never widens).
- `src/mounts.rs`: `MountService::speed_stat(guid, bonus)` builds the unframed 38/7 with stat id 2
  `MaxMovementSpeed` = `mounts.json on_foot.max_movement_speed + bonus`, reusing
  `startup_catalogues::build_stat_update` + `world::unframe_tunnel` exactly as the ride stat path
  does. A non-finite or non-positive sum returns `None` (the builder asserts on NaN).
- `src/gameplay/rides.rs` (the pet/ride glue): `Gameplay::speed_modifiers(Option<&Gameplay>)` is
  the whole policy the gateway needs; `sync_happy_buff` turns one buff step into the row plus the
  speed stat and skips the stat while seated (a ride's own 38/7 owns the speed then). Hooked into
  `handle_pets` (summon/dismiss request), `pet_tick` (mood drop, refresh, expiry) and
  `settle_pets` (zoning); `settle_pets` now takes the character so it can address the stat.
- `src/gateway/companions.rs`: one line, `settle_pets` passes `&self.state`.
- `src/gateway.rs`: one line plus the unused `SpeedModifiers` import. The validator now takes
  `Gameplay::speed_modifiers(gameplay.as_ref())`. Hub is one line shorter than before.
- `src/bin/osfr_gateway/pet_wire.rs`: `dismiss(pet_id)`, the client `Pet.Dismiss` (`00c07420`)
  shape the suite used to inline; the shared test-body module already owned `summon`.
- Tests: new `tests/pet_speed_buff.rs` (11 tests); `tests/pet_wired.rs`, `tests/pet_zoning.rs`,
  `tests/pet_tricks.rs` and `tests/pet_treasure.rs` each get the new `settle_pets` arity
  (the first three from the patch, `pet_treasure.rs` ported here).

## (R) rules

- Mood 25, +3 world units/s, 10 s duration, refresh every 4 s (the described `PlayerPet` values).
  The locale has rank strings for "Pet Happiness Speed Boost" 1-5 but no rank-to-number mapping,
  so the flat bonus ships.
- The client's captured on-foot stat is 8.0 (`mounts.json on_foot`), so the buffed stat sent is
  11.0. The validator keeps its own (R) base 10 and adds the same +3 units/s: allowance 13 for a
  client that moves 11, the same ~25% slack it has on foot.
- The buff ends as soon as the rule stops (dismiss, mood drop, zoning, reconnect) instead of
  letting a stale row run its countdown, which is inside the brief's one-duration window.
- `tag_id` is server-assigned, one constant per player session, above `consumable_effects`
  (1.0e9..1.5e9) and world tags (1.5e9..): one buff row that can never alias another feature.
- While seated the ride's 38/7 owns the speed: the row still refreshes, the stat is skipped, and
  the next refresh on foot restores it (at most `refresh_ms` late).
- No mood-rank scaling (no recovered mapping) and no composite foot beam (no 35/41 path).

## Threat note (secure-code-guardian)

A hostile client can send only the pet requests the router already decodes (53/4 summon/dismiss,
53/6 name, 53/16 utility, 53/18 groom, 53/19 feed, 53/22 tactile, 53/24 UI mode, 53/28 water,
53/32 adopt, plus the T489 trick verbs). None of them can name the buff, its tag id, duration,
icon, stat id, bonus or the vanity flag: the rule is computed from the saved roster, the server
clock and validated content. A refused request (unknown/foreign pet, malformed body, unknown
action) leaves the roster and live state unchanged - the refusal test snapshots
`Gameplay::state()` and the pet document and asserts both equal after an unowned summon, with no
38/16/17/7 reply. The only externally visible effect is the owner's own speed: the allowance
widens by the content's 3 units/s inside the validator's bounded multiplier (max 1.3 here), never
by client bytes. `speed_stat` refuses a non-finite or non-positive sum before the builder (which
asserts on NaN), every content value is bounds-checked at load, and a backwards pet clock makes
`decayed` return `None` (buff ends) instead of panicking. No save format changed and the buff is
session-only.

## Checklist

1. **Refusal changes nothing.** `a_refused_pet_request_leaves_the_buff_and_the_pet_alone`
   snapshots `Gameplay::state()` and `pets_document()`, sends an unowned summon, asserts both are
   equal, `!changed`, no 38/16/17/7 and the pet still out. The canary (vanity check removed) fails
   two production-behaviour tests, not a manufactured test failure.
2. **Rollback covers all state.** The buff lives in `PetService`, inside the `Gameplay` value the
   gateway clones per message (`gateway.rs:1440`) and commits only on `Ok`; no `Rc`/`RefCell`/`Arc`
   state or side table escapes a refused transaction. The sync after a refusal only re-evaluates
   the rule and cannot set the buff.
3. **Apply deltas, never restore snapshots.** The stat is recomputed from live `mounts.json` and
   the live bonus at send time; nothing is captured to restore later.
   `a_refresh_replaces_the_one_row_and_never_stacks` asserts the live value.
4. **Busy rules are mutual.** No new activity and no `Occupation` row: the buff is a passive
   consequence of a summoned pet. The pet router's existing minigame gate is unchanged.
5. **Every entry path gated.** One evaluation point (`happy_buff_tick`) is reached from the
   request path, the world tick and the zone path, and `reset_session` clears it; no packet path
   can start a buff or name it. The suite drives the summon request, tick and zone path.
6. **Reachable in production, tested through it.** Tests drive `Gameplay::handle_in_world`
   (gateway -> gameplay -> `PetService::handle_at_ms`) and `Gateway::handle_at` with real 125
   movement for the allowance; no copy of the rule is tested.
7. **Survives reconnect.** The buff must *not* survive: `a_reconnect_starts_without_the_buff`
   asserts `reset_session` clears it and the next step sends nothing. Nothing new is saved.
8. **Every exit path restores the player.** Dismiss, mood drop, zoning and reconnect each end the
   buff and send the on-foot stat (`dismissal_...`, `a_mood_drop_...`, `zoning_...`); a zone
   resummon starts a fresh row only after the old one was removed.
9. **Economy safety.** No items, coins or grants are touched; nothing is client-reported. N/A.
10. **Wire format.** 38/16 reuses `build_effect_tag` (reader `008d8870`, blob `008bfc00`, 85
    bytes) and 38/17 `encode_remove_effect_tag` (ctor `0089e540`); the tests decode both with the
    pinned decoders. 38/7 reuses `build_stat_update` (reader `0090a540`/`008e7640`, applier
    `0091e1a0`); the test parses it with that layout and asserts payload length.
11. **Unique ids.** The tag id is one server constant (1.8e9), never the public-world/actor id;
    the pet actor GUID is unchanged (`pet_guid`). One row per tag id, so a refresh cannot stack.
12. **Others see changes.** The buff row and the stat are addressed to the owner only; no other
    player's view changes, so no fanout is added (`nearby` stays empty for these packets). The
    visible foot beam is deliberately not sent (see gaps).
13. **Content works end to end.** `pets.json happy_buff` is bundled and validated; the suite
    asserts the final row (name 116881, icon 3851, 10 s) and the final stat (8 + 3), plus a real
    movement acceptance, not an intermediate flag.
14. **Values live in data.** Mood, bonus, duration, refresh, tag, icon and name are in
    `pets.json` with `valid()` bounds; only the client stat id 2 and the existing (R) base 10
    stay in code next to the ride stats that already use them.
15. **Canaries break production code.** The canary edited `happy_rule_holds` in `src/pets.rs`,
    not the test, and was reverted to the identical hash.
16. **Hands off session plumbing.** Session creation, teardown, transactions and save ordering in
    `src/bin/osfr-gateway.rs` and `gateway.rs` are untouched; the gateway edit is the
    movement-policy argument and the import removal.
17. **One player's error never stops the server.** `happy_buff_tick` returns `Option`, never
    `?`/`Err`; a backwards pet clock makes `decayed` return `None` (rule false, buff ends);
    `speed_stat` filters a bad sum; no `unwrap` touches client data on this path.
18. **A type's rules live on the type.** `HappyBuff` carries `valid()` and a doc comment per
    field; `HappyBuffLive` documents that it is session-only; `SpeedModifiers::with_speed_bonus`
    documents the clamp; `MountService::speed_stat` documents the stat and the `None` rule.
19. **Hot paths stay cheap.** With no pet and no buff the tick is two `Option` checks and no
    allocation; with a pet it is one `Arc` strong-count bump and one `decayed` view. A sent row is
    at most 97 bytes and the stat 28 bytes, at a 4 s cadence; no state clone.
