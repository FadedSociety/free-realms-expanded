  passed to the `"message"`/`"QuestNpcEndTextMessage"` block, and `a6` drives

## (R) rules

- The 3-count to 4-count reset is the existing `repair_counters` policy (R),
  not a new migration. Old in-progress Path counts and a held turn-in are

  documented here because the review's alternative (padding old counts) would
  silently misattribute counts after any objective reorder.

## Security threat note (secure-code-guardian)

A hostile client can still send `26/8`, `26/10`, `26/6`, `49/2` and `49/14`
at any time or replay a completed turn-in. The F232 diff adds no parser,
selector, gate, reward or save path; it only strengthens test assertions over
existing server behavior:

- The 49/13 end text is a server-built content field. The new assertions pin
  its documented reader offset (`0x00c7b990`), so a content edit that drops the
  debrief id fails the suite instead of silently blanking the client screen.
- A duplicate regional row or an extra-spawn binding for the giver could make
  the client's click resolve to a different actor than the one the server
  treats as the turn-in speaker. The content target now refuses both, and
  canaries 1 and 2 prove it.
- The migration test loads a crafted in-memory `QuestState`, not client input;
  it asserts the reset pays no coins/XP and leaves no held screen.
- Existing refusal tests (`assert_no_offer`, `assert_packet_changes_nothing`,
  `wrong_npc_and_replay_do_not_advance_or_pay`) are unchanged and still assert
  no save-byte change on wrong job/NPC, out-of-order talk, duplicate accept and
  replayed turn-in.
