# T658 - Enemy drops from the item-pass evidence

Brief: wire the 142 `quest-lines/wiring/drop.json` rows into the field-kill and battle reward data.
Result: **one** row survives the match (Yeti yarn, battle 12310). The other 141 are skipped with a reason
below. This is far fewer than the brief expects, and the lead should read the skip table before planning more drop work.

## What changed

- New `src/encounter/battle_drops.rs`: a `drops` list per `field_battles.json` battle row
  (`item_id`, `quantity`, `chance` 0..=1, `source` tags; load-time bounds, <= 4 rows, `(R)` rule through
  `field_rewards::validate_source`), and one roll per win. A hit rides out as the new
  `EncounterReward::bonus_items`.
- `src/gameplay/encounter_rewards.rs`: `bonus_items` are granted only if `accepts_reward_bundle` says the
  bag takes them; otherwise the drop is lost and the win's coins, prize and XP are untouched (item 17: a full
  bag must not turn a win into a tick `Err`).
- `data/content/field_battles.json` battle 12310 (Petty Yetis): one drop, item 893 "Yeti yarn", chance 0.25 (R).
- `tests/battle_item_drops.rs` (8 tests), 2 unit tests in `battle_drops.rs`, and the T658 review fixes below.
- T658 review fix: `EncounterEngine::debug_win` (the `realm win` dev route) drops the rolled chance items from
  its outcome before returning, so the dev shortcut pays only the deterministic coins, prize and XP. Before the
  fix the drop was granted through `realm win` too, which made any dev-path bag assertion a 25% coin flip and
  made the old checklist item 5 false. `realm give` remains the way to inspect a drop.

Field kills: **no change.** The only field-kill rows that match a shipped field enemy (Hooligan, Bixie
Soldier) are Wild Eagle / Wild Hawk, which are pet pals, not catalogue items (see skips). So
`field_kill_rewards.json` stays coins and job XP only.

  Client reader `0x008e3760` is the `ClientItemDefinition` reader: the first dword lands in `this + 4` (name id),
  the next in `this + 8` (description id) and the next in `this + 12` (icon), matching `Inventory::presentation`
  (`inventory.rs:620-637`); the same function's ResellValue path is cited at `inventory.rs:1493-1503`. So the
  item layout has a client reader; only the server-side `drops` table has none (the client carries no drop rates).
- (R) 25% per win, quantity 1, per-fight not per-kill, drop only if it fits. No source gives a rate, which yeti,
  or per-kill vs per-fight. Tunable: edit `chance` (0 retires it) in `field_battles.json`; no recompile.

## Checklist

1. Refusal changes nothing: a bonus item that does not fit is skipped (the bag is untouched and the win's
   other payouts are applied, `a_bag_with_no_slot_loses_only_the_drop`); the existing coin/XP-cap refusal
   refuses the whole reward and now names the chance drop too. Its test,
   `a_capped_win_refuses_the_drop_with_the_rest_and_changes_nothing`, snapshots the bag and economy and
   asserts both are unchanged after the refusal. Canaries: replacing the fit guard with `true` fails the
   full-bag test, and restoring the old refusal text fails the capped test.
2. Rollback: no new state outside the bag; `grant_bundle` is already staged on a clone.
3. Deltas, not snapshots: `grant_reward` adds to the live bag.
4. Busy rules: no new activity.
5. Entry paths: the roll sits in the single battle-win site. The developer `realm win` (`debug_win`) reaches
   that site but `debug_win` clears `bonus_items` before returning, so the dev route pays only the
   deterministic coins, prize and XP; `the_dev_win_never_grants_the_chance_drop` forces `chance`
   to 1.0 through the runtime catalogue and proves the dev win still grants no yarn. (This corrects the
   pre-review false claim; before the fix `realm win` granted the drop, making dev-path bag assertions a
   25% coin flip.)
6. Production-reachable: tests run marker click, Go, melee kills, results through the gateway. The dev-route
   test also passes through the real `realm win` dispatch.
7. Reconnect: `a_forced_drop_survives_the_results_close_and_a_reconnect` closes the results, saves through
   `game_store` and reloads through `Fixture`/`reopen` (the production reconnect path), asserting the yarn is
   still in the bag. Nothing pending persists; mid-win disconnect has no new state.
8. Exit paths: unchanged.
9. Economy: yarn is junk meant to be sold to a merchant; 25% per repeatable win is (R) and tunable. The
   runtime sale flags are `(no_sale = false, ResellValue = 0)` for def 893 and `stores.json` has no row for it,
   so `CoinShop::sell_unit_price` returns `None`: today the drop cannot be turned into coins at all. The real
   client resale value is unrecovered; `the_shipped_rows_are_data_driven_and_grantable` pins both facts and
   fails if a future catalogue Worth or store sell price makes the 25% rate a faucet. The roll is
   server-side only; no client value is read.
10. Wire format: no new packet. The drop uses the existing inventory-add replies from `grant_bundle`.
11. Unique ids: no ids minted.
12. Others see changes: inventory is private; unchanged.
13. Content end to end: the drop is non-empty, granted, and asserted in the bag after a real win.
14. Values in data: `chance`, `quantity`, `item_id` in `field_battles.json`, bounds validated at load.
15. Canaries (all four re-verified in the F681 fix run, each `exit 101`): (a) the roll call replaced by
    `Vec::new()` fails the forced-drop test; (b) the fit guard replaced by `true` fails the full-bag test;
    (c) `debug_win` no longer clearing `bonus_items` fails `the_dev_win_never_grants_the_chance_drop`
    ("realm win never mints the drop"); (d) the old refusal text without the chance drop fails
    `a_capped_win_refuses_the_drop_with_the_rest_and_changes_nothing`. All reverted byte-for-byte (sha256
    match); the suite is green again.
16. Session plumbing: untouched.
17. A per-player failure never reaches the tick: a full bag is a silent skip, not an `Err`. Chance is bounded
    to 0..=1 and finite at load.
18. Type rules on the type: `BattleDrop` owns its bounds (`validate`); `EncounterReward::bonus_items` documents that
    it never refuses the rest; `debug_win` owns the dev-route exclusion (comment at the clearing loop).
19. Hot path: no per-tick cost.

Threat note (secure-code-guardian): a hostile client sends nothing that reaches the roll; only a server-observed
battle win does. The roll is server entropy; the item id and quantity come from content, bounded (<= 100, catalogue
checked at roll by the grant). A replayed win cannot pay twice (the existing results-close and replay tests still hold).
Content tampering is the lead's file set.
