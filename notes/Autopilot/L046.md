## What changed

- `houses.json`: 25 lot rows gain a `deed` object: `item_id`, `store_bundle_ids` and a
  per-row `source`. Rows with no recorded deed stay without one. CRLF preserved; no other
  field changed (checked by parsing old and new and comparing every other key).
- `stores.json`: 9 deed rows with the original Station Cash price (`sc_price`, fandom wiki
  regular price) and a new `L046` source tag, written as the six positional tags of
  `source_tag_order` like the ride rows. Existing rows, categories and prices are unchanged
  (byte-identical prefix; checked by parse).
- `station_cash.rs`: `Listing.deed` (item Type 16, `DEED_ITEM_TYPE`). `place_order` takes a
  `LotGrant`: a deed listing calls it instead of granting an item. No lot means a refusal
  (`ORDER_FAILURE`) with nothing charged. The grant is the last step that can fail, and the
  debit after it cannot fail. `preview` (66/1) asks the same `LotGrant` with `commit = false`,
  so a deed the order would refuse previews as that refusal and nothing is staged.
- `coin_shop.rs`: `handle_marketplace` passes the `LotGrant` to both preview and order. The
  direct `handle` path has no housing, so it refuses every deed.
- `housing_service.rs`: `LotDeed`, deed validation (id > 0, source present, no bundle 0, one
  deed per lot across the table), `HousingService::grant_deed`, and the
  `HousingReply::NotifyHouseAdded` variant. A deed with no enabled lot is the lookup refusal
  `HousingError::InvalidProperty`; the doc says the method is atomic only through its staged
  caller.
- `housing_native.rs`: the `NotifyHouseAdded` codec (127/49).
- `gameplay/housing.rs`: `HousingSession::grant_deed` stages the grant on a cloned service
  and commits only after the replies encode and `commit` is set.
- `gameplay/npc.rs`: the 66/x route passes the session's lot grant, keyed to the character
  guid.
- `gameplay.rs` (hub, +5 net): `dormant_housing` keeps a character's saved lots when the
  content has no `houses.json`, and `state()` writes them back, so a dormant login never
  drops paid lots on its next save.
- Tests: new `tests/lot_deeds.rs` (9 tests). The only edits to existing tests are the one
  `handle_marketplace` call in `station_cash.rs`, the listed-count pin (52 to 61), and two
  ride-only loops that now skip deeds (`station_cash.rs`, `ride_sources.rs`). The struct
  literal in `tests/housing_service.rs` gains `deed: None`.

## Security

Replay additions:

- **Starter lot vs deed (economy).** `grant_deed` never grants the starter property. The free
  Condo cannot be sold for Station Cash, and a kitless Condo (which would block its kit forever)
  cannot happen. The refusal is the same `InvalidProperty` -> `ORDER_FAILURE` as any unsold deed,
  so it adds no oracle. Tested; canary C1.
- **127/23 after a purchase (client input, empty body).** The kit still rides only a newly
  granted starter: `granted` compares the character's lot count before and after the staged
  grant. A deed lot owned first changes neither that decision nor the ids, which are floored
  above every id any of the character's lots holds. Tested; canary C2.
- **Merged content validation.** Deed uniqueness (L046) and the kit's id, count and build-area
  checks (L040) both still run at load. Canaries C3 and C4.
- **Merged session glue.** `kit_items` (zero resale, L040) and the staged `grant_deed` (L046) are
  both live. Canaries C5 and C6.
- **Wire.** 127/49 was rechecked in IDA for the replay. `sub_AB2F50` (`0x00ab2f50`) reads the
  header (`sub_AB2BC0`), then one u32 into `this+0xc` and two u64s into `this+0x10` and
  `this+0x18`. This matches `NotifyHouseAdded::encode`.
- **Nothing else.** No new logging, file write or `unwrap` on client data, and no session or
  gateway change.

Original L046 security notes:

- **Trust boundary: 66/3 order (client input).**
  - Fields that are parsed and validated: bundle id, store id, quantity, tint, gift and
    coupon. Only a server-built listing resolves to a deed.
  - The client never names a deed or a lot. The item id passed to `grant_lot` comes from
    the catalogue listing.
  - Quantity must be 1, and gift and coupon orders are refused. Both rules are unchanged.
- **Refusals change nothing.** These cases all refuse with no change to wallet, inventory,
  lots or order history:
  - the deed has no enabled lot;
  - the player already owns the lot;
  - the order arrives with no housing session (`handle` path);
  - an encode fails;
  - the wallet is short.

  Tests snapshot the whole `GameplayState` as JSON bytes before and after.
- **Atomic commit.** The lot is granted on a cloned `HousingService` and committed only when
  its replies encode. The debit follows and cannot fail. Wallet and lot are both in
  `GameplayState`, so they land in one `game_store` save (`replace_bytes`). A restart round
  trip through `game_store::save`/`load_or_create` is tested.
- **Replay.** The existing whole-order replay key returns success with no second grant. A
  new tracking id for an owned lot is refused before any debit.
- **Economy.** The deed never enters the inventory, whether or not a lot exists. The
  `Listing.deed` flag comes from item data, not from `houses.json`. This means it cannot be
  sold, traded or regranted as an item. The free starter lot is not listed. No currency is
  minted.
- **No oracle or enumeration.**
  - Every refusal is the same `ORDER_FAILURE`, apart from the existing insufficient-SC code.
  - A player learns only about their own lots.
  - Deed ids are public catalogue ids.
  - 127/39 lists only the buyer's own lots.
- **Logs.** No new logging and no secrets. `npc_merchant_66` logs nothing.
- **Isolation.** The deed path has no `unwrap`/`expect` on client data. `grant_lot` returns
  `None` on any error instead of propagating it.
