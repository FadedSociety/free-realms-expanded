# T329: push the Station Cash ride catalogue at world entry

## Summary

T230's Station Cash wallet worked in the 2026-10-20 native run (`lab/runs/client-baseline-20261020T213321Z`:
the splash and the Marketplace both showed **500 SC**), but the Marketplace was empty. `src/coin_shop.rs`
only pushed the catalogue in reply to 66/12, and the native store screen never sends 66/12; the
66/24/66/33 handshake had no caller at all (`marketplace_initial_packets` was dead).

T329 sends the handshake and catalogue with the world-entry reply stream:

- `CoinShop::world_entry_packets` (new, replaces the dead `marketplace_initial_packets`) returns the
  66/24 enable handshake, the 66/33 payment-source flags and the store rows (66/7, 66/6, 66/9, 66/5)
  when `station_cash.enabled` and `marketplace.enabled_on_handshake` are both on; otherwise nothing.
- `Gameplay::world_entry_marketplace_packets` exposes it from the shop owner (`src/gameplay/npc.rs`).
- `Gateway::startup_for(Kind::Ready)` appends those packets once to the world-entry reply stream.
  The 66/12 reply is kept unchanged.
- 66/29 (the store's close-of-screen statistics report) and 117/41 (a one-time commerce session
  request) are now understood and silently accepted, each with a test: they no longer trace as
  "unknown application message" and change nothing.
- No order path, price, grant, coin or save change. `place_order` is untouched.

**IDA contradicts `notes/Design/Station Cash.md`.** That note says the store screen sends 66/12 via
`RequestServerStatus`. The binding exists, but the native screen opened by SHOP! does not call it;
the trace has no 66/12. IDA plus the trace win: the catalogue must be pushed. This also matches the
community reference (`lab/references/FreeRealms-Legacy/src/Sanctuary.Game/Zones/StartingZone.cs`,
`SendInGamePurchase`: 66/24, 66/33, 66/6, 66/7, 66/5, 66/9 during zone initial data, i.e. before
`PacketZoneDoneSendingInitialData`). Behaviour reference only; no code was copied.

66/29 is a client report (there is no statistics response class), so silently accepting it is the
minimal correct behaviour. 117/41 is a request for a commerce session ticket; this restoration has
no payment backend, and the native screen worked without the reply, so it is silently accepted too.

## Wire format

Only the delivery time moved; every byte layout is T230/F324's:

- 66/24: one byte, `00b3bf30`.
- 66/33: two bytes, `00b3c000`.
- 66/7/66/6/66/9/66/5: the reader-derived layouts walked by `tests/station_cash.rs`. The shipped
  catalogue is 52 bundles: the 66/5 packet is `36 + 185 * 52 = 9,656` bytes.
- World-entry order is 24, 33, 7, 6, 9, 5, appended after the startup snapshot's Ready messages.

## Reconstructed rules (R)

- Pushing the store data with the Ready world-entry stream is (R): the recovered readers accept the
  data whenever it arrives, and the community server pushes the same packets during zone initial
  data. Native acceptance is the lead's next step; the fallback is the Loaded stage.
- The gate `station_cash.enabled && marketplace.enabled_on_handshake` is T230 policy (R). A package
  with `station_cash.enabled: false` sends exactly the pre-T329 packet set (nothing extra).
- The 66/29 payload is telemetry and is not parsed; its field meanings are unrecovered (R).
- 117/41's subtype semantics are unrecovered (R); it is treated as a no-reply session request.
- The catalogue is pushed once per world/zone entry and bounded by the catalogue size.

## Checklist

1. **A refusal changes nothing.** The disabled package test (`world_entry_sends_no_...`) enters the
   world with `station_cash` off and `enabled_on_handshake` on, asserts no 66 packet and an
   unchanged 66/12 reply. `store_statistics_and_one_time_session_requests_are_accepted_silently`
   snapshots the gateway before and after both packets. Canaries (see Gates) break the production
   push and the 66/29 label and fail their tests.
2. **Rollback covers all state.** The change adds no transaction and no shared mutable state; the
   packets are derived from the immutable `Arc<Catalogue>` and `Arc<StoreCatalogue>`; nothing is
   stored per session.
3. **Apply deltas.** No inventory, coin, wallet or position value is captured or restored.
4. **Busy rules are mutual.** No activity is added; `occupation.rs` is untouched and `place_order`
   still takes the hub's `activity_busy` answer.
5. **Every entry path is gated.** The only push is `startup_for(Kind::Ready)` via
   `world_entry_marketplace_packets`, and the 66/12 reply uses the same station-cash gate. The kart
   loading stream replaces the Ready stream for a race entry, where the store is not reachable; the
   66/12 request path still pushes when the client asks.
6. **Reachable in production, tested through it.** `tests/coin_store_siblings.rs` drives the real
   `Gateway::handle_at` login -> Ready -> Loaded sequence with a full content package and inspects
   the Ready replies; `tests/station_cash.rs` decodes the shipped catalogue the same method returns.
   The gateway test proves the dispatch; the station-cash test proves the shipped rows and prices.
7. **Survives reconnect.** Nothing new is persisted; the catalogue is rebuilt from content on every
   entry, so a reconnect cannot lose or duplicate it.
8. **Every exit restores the player.** No activity, no busy state and no player-owned state is
   involved; the 66/29 and 117/41 refusals/accepts change nothing.
9. **Economy safety.** No free grant, no client-supplied price or quantity, no order change. The
   pushed rows come from `stores.json` and the server inventory catalogue; the accept-silently
   packets grant nothing. `earn_only` rows stay unlisted.
10. **Wire format.** Readers cited above: 66/24 `00b3bf30`, 66/33 `00b3c000`, 66/7 `00b48040`,
    66/6 `00b44d70`, 66/9 `00b45560`, 66/5 `00b48700`/`00b41860`. The byte layouts are unchanged
    from T230/F324 and still covered by their reader-derived byte tests; the new world-entry test
    checks the 66/24 value, the store size and the shipped price position.
11. **Unique ids.** Unchanged; the bundle id is the positive item id and the catalogue alias guard
    still rejects an earn-only collision.
12. **Others see changes.** The catalogue is player-private; no world broadcast is needed or sent.
13. **Content works end to end.** The shipped content test decodes all 52 listed rides and their
    scaled SC prices; the gateway test shows those packets reach the client-facing reply stream.
    Native purchase acceptance is the lead's step.
14. **Values live in data.** The store, category, scale and price data stay in `stores.json`; the
    gate and the enable flag are existing configuration. No new constant.
15. **Canaries break production code.** Canary 1 disables the production world-entry push and the
    enabled world-entry test fails; canary 2 removes 66/29 from the production label list and the
    accept-silently test fails with a rejected trace. Both reverted with identical hashes.
16. **Hands off session plumbing.** No session creation, teardown, transaction or save ordering was
    changed; gateway.rs only appends to the already-staged startup reply and labels two packets.
17. **One player's error never stops the server.** The new server packets are built from static
    content; the two accepted client packets are not parsed and return `Ok` with no reply; no tick
    path can fail on them. `app_fuzz` seeds cover both.
18. **A type's rules live on the type.** `CoinShop::world_entry_packets` owns the gate and documents
    it; `Gameplay` exposes it by name; the dispatch labels are comments on the router.
19. **Hot paths stay cheap.** The push runs once per entry, not per tick: six packet builds and
    ~9.6 KiB for the shipped catalogue. The 66/29/117/41 route is the existing dispatch with no
    state clone and no reply.

## Security threat note (secure-code-guardian)

A hostile client can send 66/29 and 117/41 with any bounded body (the native trace's 69-byte and
6-byte shapes, plus garbage). Both are now understood traffic and are silently discarded: no reply,
no parse of counts/strings, no allocation from client data and no state change (asserted). The
catalogue is server-built from `stores.json` and the item catalogue; no client field selects a row,
price or quantity, and `station_cash.enabled: false` sends nothing at entry. The order path and its
validation are untouched, so a hostile order is still refused exactly as F324 left it. Malformed
application messages still return `Err` and drop only that message for that session; the app_fuzz
corpus (with both new selectors) exercises the routing with trace on and off. No secret, file or
network I/O is added.
