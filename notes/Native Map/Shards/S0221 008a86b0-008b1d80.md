## What this range is

The shard falls into five blocks.

1. **Client capture / upload / housekeeping methods, 008a86b0-008a9200.** These are methods of the big client object whose capture state lives at +0x8c0..+0x910 (the same fields the accepted S0220 labels `BaseClient::StartImageCapture` 008a80d0 and `ImageCaptureStep` 008a8500 use). ## Contradictions and open questions

1. **Object identity of the tutorial flag.** The trial notes describe 008a89a0/008a9200 as operating on "player", and the field review shows the BaseClient constructor 00941ba0 zeroing the same +0x780 flag inline. The capture methods in this shard touch +0x8c0..+0x910 on the same receiver. Either the tutorial flag lives on the BaseClient object itself, or the note's "player" naming is loose; the flag semantics from the notes stay authoritative, and the identity should be settled by reading the zone-reader call sites 009472e9/00947cbe.
2. **Uploader lifecycle vs capture flow.** 008a8750-008a8990 construct and pump a YouTube uploader handle, and gated calls prepare capture metadata. The exact transfer trigger and relation to capture start remain unknown; the +0x28 virtual probe at the start of 008a8750 is unmapped.
3. **Packet contract details.** Only 0x69/105 has a catalogue twin. Client code shows 0x60 send/receive paths, 0xac and 0xba receive paths, and 0xb4 send/receive plus subcommand-3 response; server-side meanings, timer fields, and membership fields still need capture or emulator corroboration.
4. **Unmapped helper groups** that several labels lean on: 010003e0/010003f0 -> 010065xx; 0101c8a0/0101cd40/0101cd70; 00ad6750/00ad6760; 00ada830/00ada8b0; 0081ce10; 00d2e150/00d2e350; and the 0x0108c*** uploader library. Each is one hop from a confirmed label, but none is proven in this shard.
5. **What +0x8e8 and +0x900 are.** The early wrappers prove only that +0x8e8 is a captured state object and +0x900 a string/list-holding sub-object; no RTTI or note names either one.
