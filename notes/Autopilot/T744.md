# T744: Station Cash Marketplace: member price, the stray "profile" line, "Sort By: undefined"

## Summary

Three native findings from the 2026-10-26 run (`lab/runs/client-baseline-20261026T135758Z`) are
addressed:

1. **Member price.** `bundle_record` wrote 0 at bundle +268, which `009a56d0` case 32 reads as
   `MembersOnlyPrice`; the client's `getMOItemPrice` uses that field for a member, so every tile
   showed `SC 0` and the detail pane showed a 100% discount. It now writes the regular (scaled
   `sc_price`) price there: no discount, never 0.
2. **"profile" line / missing price on three Boombox tiles.** The 66/5 record shape was already
   identical for every row; the difference was on the client, not the wire. Jingle Bell (878),
   Pop-Dance (76927) and Tiki (76928) are exactly the Boombox rows whose item definitions are
   absent from the startup definition capture, so the client left those tiles on their loading
   path (`hasLoaded` false, `onDataLoaded` never called). The native server trace shows the client
   sending exactly three 66/27 requests for those three items (and no others); the server did not
   answer. `CoinShop::handle_marketplace` now answers 66/27 with the requested bundles' 35/37 item
   definitions **first** and the 66/28 pending-content pairs second.
3. **"Sort By: undefined".** The five sort options are client-local, loaded from
   `Resources/ItemSortTypes.txt`; no 66/x packet in the client dispatcher feeds them, so there is
   no server field to send. The labels are `Default`, `Alphabetical A - Z`,
   `Alphabetical Z - A`, `Price Low to High`, `Price High to Low`. The "undefined" is the
   marketplace SWF's combo label field (`SortManager` sets `labelField` on itself, not on
   `cbSorts`, whose rows are `Id`/`Name`), i.e. a client-side UI defect. Evidence and the exact
   cites are below; this item is an open client gap, not a server change.

### "profile" line and missing tile price

- AS3 `marketplace/../buttons/MarketplaceItemButtonExpanded.as` `onDataLoaded` sets
  `txtProfile.text` from the bundle's `ItemDef` ("Profile Name") and the price fields; the
  authored `txtProfile` placeholder is the literal `profile` seen on the three tiles.
- `buttons/MarketplaceItem.as` `_setLoading` calls `onDataLoaded` only when
  `base.DataSource.hasLoaded(dsItem)` is true. `base/DataSource.as` `hasLoaded` is
  `item.HasContentDefinitions == "1"`.
- `009a56d0` case 20 computes `HasContentDefinitions` with `sub_B282A0` → `sub_B246A0` over the
  client's pending-content set (`[[ds+0x274]+0x1C8]+0x2C8`); a bundle the client has asked for
  but not yet had cleared returns 0. The client tracks the missing bundles and requests them with
  66/27 (`00b47b20`, batcher `00b48120`; request serializer `00b41a30` → `00b3dd80` →
  `00b37140`, i.e. count, then per entry store id, bundle id, item-id count and item ids).
- The 66/28 reader `00b2e2d0` (dispatched by `00b48a10` case 28 to `00b40050`) reads a count and
  eight-byte `(store id, bundle id)` records. For each pair `sub_B39340` → `sub_C3B720` finds the
  bundle and `sub_C36F80` checks that **every** content item resolves in the client definition
  map; only then does the handler remove the pending entry (`sub_C36FE0`/`sub_B288A0`) and fire

  bundle pending.
- Why only those three rows: the startup 35/37 capture
  (`lab/references/rust-gameplay/inventory.json`, 1,383 records / 1,329 unique ids) contains
  1180 Realms Roll, 1913 Rainbow and 48244 XVD-S, but not 878 Jingle Bell, 76927 Pop-Dance or

  `27 | 38 => no reply`. The receipt of 878/76927/76928 in the request is also why their

- Captured proof: the native run's `server-trace.jsonl` has **exactly three** inbound 66/27
  packets, each 24 bytes, one per missing Boombox:
  `42001b00 01000000 01000000 6e030000 01000000 6e030000` (878),

  `42001b00 01000000 01000000 802c0100 01000000 802c0100` (76928) at `ts_ms` 539171/539184.

  the pending 66/27 set, not the definition map. That is why the fix must send 66/28, and why the
  definitions-first order matters.
- Fix: `CoinShop::handle_marketplace` now parses 66/27 strictly, selects the definition from the

## Security note (secure-code-guardian)

66/27 is new inbound client input. A hostile client can send any count, store id, bundle id and
item-id list. Controls:

- The existing `marketplace_request_is_well_formed` cap (64 bytes for a Marketplace request)
  still applies before parsing; `decode_content_request` also bounds the body and requires the
  exact 66/27 header and full consumption (no trailing bytes). Count ≤ 8; each entry's item-id
  list is skipped against the body (an item count that runs past the body is refused) and is
  never stored.
- The reply never trusts a client id: the bundle must be a listed bundle of the configured store
  (`Catalogue::listing`), and the definition is that listing's item record. A hostile client
  cannot request an unlisted item's definition, cannot alias another bundle, and cannot amplify
  the reply beyond the request's ≤4 bundles in one 64-byte packet.
- The request reads content only: no coins, items, wallet, save or session state changes
  (`changed: false`); refusals are per-request `Err` (the existing 66/1, 66/3 convention).
- The 35/37 batch is `encode_definition_batch_v2`, which refuses a record shorter than four
  bytes and returns an error instead of panicking; the records come from `Inventory::load`, and
  no client value selects or builds one.
- 66/5 values are still server content; no new client field selects a price, category or item.
