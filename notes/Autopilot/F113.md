`lab/autopilot/reviews/6cd3ffe-T019.md` was valid. The bundle contained bare
application packets, so `Gateway::parse_message` rejected the first 66/43 child
before the purchase ran. The test therefore passed the unchanged-snapshot and

they are addressed under "F151 post-review remediation" below.

  the 66/43 purchase and the malformed 26/8 child. Parsing reaches gameplay for

  snapshot unchanged, and retrying the 66/43 request debits exactly 15 coins

## Threat note (secure-code-guardian)

A hostile client can send a `[0,25]` bundle with any child order, a bare child,
a nested child, an over-long length, more than 128 children, and any 66/43
item, quantity or transaction id. The refusal is safe at every layer:

- Every child is decoded before handling (`Gateway::application_messages` and
  `parse_message`, `src/gateway.rs:1478-1483`). Empty, nested, oversized and
  over-count bundles are refused before gameplay; a bare child fails
  `parse_message`; a bundle whose replies exceed 8 MiB is refused before commit
  (`src/gateway.rs:1502-1508`, `:1866-1871`).
- `handle_at` clones character, `Gameplay`, movement and flags and assigns only
  after the whole bundle succeeds (`src/gateway.rs:1494-1500`,
  `:1872-1881`). Any child error in a bundle returns `Err` and drops the staged
  purchase (`src/gateway.rs:1741-1744`). Production additionally clones the
  whole `Gateway` before calling it (`src/bin/osfr-gateway.rs:1622-1654`), so a
  later child failure cannot commit the first child.
- The purchase's mutable state — inventory, coins, `next_instance_id` and
  `vendor_transactions` — is inline in the cloned `Gameplay`/`CoinShop`
  (`src/gameplay.rs:203-204`, `src/coin_shop.rs:171-181`), not a shared `Arc`
  or side table; T019 removed the old shared shop. The
  `Arc<Mutex<NpcInteraction>>` is still shared by clones, but the 66/43 path
  only calls the `&self` validator (`src/npc_interaction.rs:637-658`) and never
  writes it.
- The item id must be in the open shop's stock and the character in range
  (`src/npc_interaction.rs:643-657`). Quantity must be non-zero and at most
  `i32::MAX`; the price is `checked_mul` from `stores.json` (never the client
  price); coins must cover it; the bag must have room
  (`src/coin_shop.rs:365-486`). The transaction id is only a bounded `u32` map
  key (`MAX_CLIENT_TRANSACTIONS`). No id, item or coin is shared with another
  session.
- A refusal does not insert the transaction id into the cache;
  `vendor_sell.rs:1087-1095` retries the same id and is charged exactly 15,
  which would fail if the cache or inventory leaked.

## Checklist

1. **A refusal changes nothing.** `gateway_bundle_failure_does_not_commit_a_vendor_buy`
   asserts the failed bundle returns the second child's gameplay error
   (`tests/vendor_sell.rs:1080-1084`), the gateway snapshot is unchanged
   (`:1085`), and the same transaction id then succeeds and debits exactly 15
   (`:1087-1095`). The production canary commit made the snapshot assertion fail
   with coins 85 vs 100, proving the test sees a committed purchase. No NPC
   menu, offer, counter, item or cooldown is consumed on this path.
2. **Rollback covers all state.** `handle_at` stages `state`, `gameplay`,
   movement and flags and assigns only after the loop
   (`src/gateway.rs:1494-1500`, `:1872-1881`); a combined child error returns
   before the assignment (`:1741-1744`). The purchase state is inline
   (`src/gameplay.rs:203-204`, `src/coin_shop.rs:171-181`). The retry with the
   same transaction id proves the idempotency cache did not leak. The shared
   `Arc<Mutex<NpcInteraction>>` is read-only on 66/43; a pre-existing seam for
   NPC-menu children is noted under Open gaps.
3. **Apply deltas, never restore old snapshots.** The shop is synced from the
   live inventory immediately before the transaction
   (`src/gameplay/npc.rs:855`), and `buy_once` stages from the current state
   (`src/coin_shop.rs:437-439`). The retry debits 15 from the current coins, not
