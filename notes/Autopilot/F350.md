## Threat note (secure-code-guardian)

What a hostile client could send, and why it is refused:

- an unpublished **167/1/2 Play id**: the catalogue lookup (`Catalogue::admit`)
  returns `Refusal::Unknown` before any encounter/inventory change; the reply
  is one chat line and test 4 asserts snapshot + save bytes are unchanged.
- a forged **167/1/2 Play for a real battle** while another activity runs: the
  shared busy/occupancy gate (`warp_blocker`/`active`) refuses before the prize
  preflight (test 2 asserts the live run is untouched).
- a forged **26/8 marker GUID** or a **41/108 Go** with no/consumed pending
  screen: an unknown actor opens nothing and Go is inert (test 4).
- an arbitrary **36/10 target GUID**: `strike_damage` returns the default
  outcome when the GUID is not an active arena/field actor; test 4 asserts the
  typed snapshot and save payload are byte-identical.
- a replayed **26/42 Close** or a first-run Go: only a Won/Lost active run
  exits and the pending screen is consumed (tests 2, 3, 5).
- a **full bag**: the four-row prize preflight refuses before the encounter
  changes (test 4).
- **quest credit** comes only from `EncounterOutcome::defeated`, which the
  server writes from the server's actor definition on a server-verified kill;
  no client payload, win flag, quantity or item id is trusted. The battle
  reward is the existing `EncounterReward` applied on the win.
- **ids**: arena GUIDs are unique (loader refuses duplicates, test 6); the five
  enemies intentionally share two recovered kind ids because definition ids
  name a kind, not an instance.

No new parsing, save field, role check or reward rule was added.
