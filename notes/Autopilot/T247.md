## Security threat note (secure-code-guardian)

- **Attack surface:** a hostile client can send 26/8, 26/10, 26/6, 49/2 and
  49/14 at any time, and can report movement through the normal movement path.
  This slice adds no parser, selector, packet family, reward amount or
  client-supplied quantity. It is data only; the server derives every objective
  counter from authoritative NPC/movement events.
- **Why a hostile claim is refused:** 26/8/26/10 must name an NPC content key,
  pass the 12 m range and (regional-label) zone check, and select an option from
  the open server menu. 49/2 must match the single `pending_offer` set by the
  server's own 26/6 choice; the offer runs the existing prerequisite, level,
  job, membership and limit checks. 49/14 must match `pending_turnin`, which is
  set only by a server Talk that completed every objective and then the 49/13
  release; the reward transaction uses the existing grant key
  `quest:<character>:<quest>`. Out-of-range, wrong-zone, wrong-NPC, forged or
  replayed packets leave `GameplayState` and its save bytes equal (tested).
- **Economy:** 50 coins/25 Adventurer XP come only from the content row on a
  server-verified completion, once. No items and no free grants; no client
  quantity or item id is read; a second turn-in or accept pays nothing.
- **Fail-closed content:** the existing loader rejects a malformed objective
  (0.0 radius) with `InvalidData` before any player state exists; no `unwrap`
  on client data was added.
- **Visibility:** quest state is per character; no actor, spawn, outfit or
  broadcast path changed. The admin broadcast remains the existing T199 path
  with its own role/validation policy.

## Skill review

- **Ponytail (full).** The smallest implementation is content plus the tests
  the brief requires. It reuses the split loader, `RuntimeGoal::VisitPosition`,
  the NPC Offer/Talk router, the 49/x builders and the existing reward
  transaction; no new objective kind, helper, command or spawn. The one
  non-obvious addition (`jobs.json`) is the loader's existing structural
  invariant, not a second offer path. The test file reuses the established
  packet-driven harness style of `quest_job_xp.rs`; it copies only the fixture
  files the gameplay loader needs so the opening story cannot contaminate the
  event wallet.
- **ponytail-review on this diff.** Cut the first attempt's full-opening
  fixture (its story coins made the reconnect assertion meaningless) to a
  minimal copied fixture; removed a duplicated reward-equality JSON block and a
  redundant `std::slice::from_ref`; the remaining helpers are each used by at
  least two tests or encode one packet layout with its client citation. No
  unused helper or speculative config remains (rustfmt and the compiler are
  clean).
- **secure-code-guardian.** Threat note above; every refusal has a whole-state
  and save-byte equality assertion; the reward is server-verified and paid once
  by the existing grant key.
- **Principles applied:** model-the-domain (content record + existing typed
  `RuntimeGoal`/`ContentGoal`, zone 0 on the type’s existing rule),
  subtract-before-you-add (no production code, no parallel path),
  test-behavior-not-implementation (real 26/8/26/10/26/6/49/2/49/14 and
  `on_location`), make-operations-idempotent (duplicate accept/turn-in and
  reconnect), minimize-reader-load (the quest is one file; the test cites the
  readers next to the packet builders), keep hot paths cheap (no tick code).
