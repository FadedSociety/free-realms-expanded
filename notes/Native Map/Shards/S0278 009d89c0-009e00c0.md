## The wire: base opcode 188 (0xbc) with a sub-opcode

Three independent anchors establish the factory packet contract:

1. `BaseFactoryPacket::BaseFactoryPacket` (009d9070) writes base id **0xbc (188)** at +4 and
   zero at +8; shared initializer 009d90d0 writes the caller-supplied sub-opcode.
2. The same field layout is used by the command family: `BaseCommandPacket`'s constructor
   (`FUN_008a2820`, outside this shard) writes **0x1a (26)**, which matches the community
   catalogue row `FreeRealms-Legacy 26 BaseCommandPacket`.
3. The receive dispatcher `FUN_009e9d40` (outside this shard) constructs a `BaseFactoryPacket`,
   reads a sub-opcode from the message body and switches on it.

## The data model the packets carry

The containers instantiated here name the plot model directly (RTTI, all in the same .rdata):
`HashListMap<__int64,FactoryPlot::PlacementNode,1024,-1>` (value 48 bytes; 009d9f10/009dfc40,
find 009db200, clear 009df380, insert 009e00c0), `HashListMap` over `FactoryFoundation`,
`FactoryMisfortune`, `BlueprintDataSourceInfo`, `SoeUtil::StrongType<__int64,SecondsStamp>`,
`List<FactoryNpcTooltipInfo::FactoryNpcTooltipEffectInfo>`, `List<ItemRequestEntry>`,
`List<ClientItem const*>`, `List<EffectTag>`, `Array<FactoryPlot::PlacementNode>` and
`SoeUtil::IString<char>`.

Two structural facts fall out of the address arithmetic and are worth carrying forward:

* `FactoryPacketUpdatePlot` initializes one composite plot-data member through 01059590
  (009d98a0). Its destructor path through 010596b0 (009d9900) tears down foundation and
  misfortune maps, a placement-node array, and the 1024-bucket placement map. Wrappers 009da840
  and 009dc3c0 call that aggregate cleanup body but do not identify one map member or owner.
* +0x22c0 is not a plot record but the active NPC tooltip info record (its effect list hangs
  off record+0x1c): 009db8d0 returns it only when the key pair at +0x22b8/+0x22bc differs from
  the sentinel DAT_01be6010/DAT_01be6014 and the flag +0x23a0 is 1; caller 00a79250 builds the
  tooltip UI from it and 009e8760 fires the Lua event FactoryHandler:HaveNpcTooltip.
* 009d9b70 derives a grid scale from a definition (the reciprocal of definition+0x18) and
  writes it to +0x4188 of the guarded sub-object FUN_008a67a0 returns - the same field
  FUN_00c0ba80 (House.SetGridSpacingInCentimeters) uses for 100.0/cm - so the factory plot
  grid and the housing grid spacing share one value field.
* The per-instantiation container hooks in the shard's tail are pinned to their vtables:
  009db9a0/009db9e0 (dwords 0x01810544/0x01810548, timestamp-keyed 10-bucket map),
  009dba00/009dba40 (0x01810554/0x01810558, int/int 10-bucket map), 009dbad0/009dbb10
  (0x018104ec/0x018104f0, NPC tooltip effect list), 009dbbc0/009dbc00 (0x01810500/0x01810504,
  item-request list), 009dbc30/009dbc70 (0x01810510/0x01810514, 256-bucket tool-definition map),
  009dbc90/009dbcd0 (0x01810520/0x01810524, 32-bucket blueprint data-source map),
  009dbcf0/009dbd30 (0x01810534/0x01810538, client-item-const list) and 009dba60
  (0x01810588, placement-node array buffer).
* The `List<EffectTag>` members belong to the factory placement/data records (placement
  record +0x44, factory data records +0x50 on the blueprint path), NOT to the NPC tooltip;
  the tooltip's effect chain is the distinct `List<FactoryNpcTooltipInfo::FactoryNpcTooltipEffectInfo>`,
  whose fixed-capacity form has a 10-node, 16-byte-stride, null-terminated embedded free list
  initialised by 009dbb30.
* The packets that carry strings (`OpenToolshed` 009de150, `OpenBlueprintGenerator` 009de250,
  `UpdateExperience` 009de350) embed a reference-counted `SoeUtil::IString` member at +0x0c;
  their destructor bodies release the buffer with the atomic count at buffer-4
  (009de1c0/009de2c0/009de3d0).

## Plot grid generation

009de470 and 009dea70 walk every plot in the +0x20 list, take the definition's 8-float grid
rectangle (cell size at +0x18), and per cell query the world through FUN_00fd4290 with flags
0x80000103 and stamp a textured quad through FUN_007f99e0. The texture is looked up by id
0x39b97eb4 in the asset hash chain and falls back to the literal **`white_noise.dds`**
(FUN_007fa530). 009dea70 adds a per-cell query `FUN_01059b80(row,col,1)` that flips the low
bytes of the colour/flags word, i.e. it distinguishes cells the plot considers set. This is
consistent with the 1360x728-cell farm grids the vault already recorded from
`Resources/FactoryPlots.txt` (notes/Research/Pieces/039 Gathering job progression.md).

## Relationship to existing notes

The vault's housing module (notes/Research/Housing Restoration.md) documents a **separate**
family, `BaseHousingPacket` base opcode **127**, for placing and moving fixtures. Nothing in
this shard belongs to that family: the 188 family is the plot/farm side (foundations,
blueprints, build tools, ranks, misfortunes), which the same note already touches through
`FactoryPlots.txt` and `FactoryRanks.txt`. So "Factory" is not a synonym for housing; when
writing server handlers, keep 127 and 188 apart.
