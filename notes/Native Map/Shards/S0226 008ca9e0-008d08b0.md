# S0226 findings (008ca9e0 .. 008d08b0)

Scope: 165 functions, all mapped in `out.jsonl` (36 confirmed / 121 likely / 8 speculative).
Read-only pass over the pinned Ghidra export; no game or lab input was modified. This revision
incorporates the independent review in `review-history/1`: the four hash+list erase callbacks,
the tree-node destruction path, the time-source gloss and every vtable-slot binding were
re-checked against the code and the raw bytes.

## What this range is

The shard is a cross-section of five different source areas that happen to sit in one
address window:

1. **Container template helpers** (008ca9e0..008cb620, plus repeats later; 44 records in
   `engine.containers`). They are per-type emissions of the same shapes: recursive
   binary-tree free over children at +8/+0xc (fourteen copies, 008cac90..008cb620),
   intrusive-list erase with a virtual removal callback, hash-list erase with bucket
   counts 8/16/100/128/256/1024, one 100-bucket and three 10-bucket "remove head and
   _free" helpers (008cc3d0, 008cc480, 008cc530, 008cc5f0), two red-black-tree node
   inserts (008cafd0, 008cce20, fixups 008bfff0 / 008c2120) and array grow/copy paths
   (008caeb0, 008ce430). The erase callbacks are a **two-structure** design: they first
   hash-unlink the node through a per-type helper over the bucket array at container+0x14
   (008ae420: bucket = node+0x1c mod 0x47; 008ae8f0: node+0xd8 & 0xff; 008aec50:
   node+0xc8 & 0xff; 008aefe0: node+0xb8 & 0xff; chain link stored in the node's last
   field), then unlink it from the doubly linked list (head this+8, tail this+0xc, count
   this+0x10 for the 0x47/256-bucket containers; head this+4 / tail this+8 / count
   this+0xc for the 8/16/100-bucket shapes) and finally dispatch the container's removal
   callback virtual. A related helper, FUN_008c1f70, is the red-black **tree erase**
   (successor search FUN_008af680, rotations FUN_008aff30/FUN_008b00c0, tree count at
   this+4); the node destruction path 008ccdc0 deletes a node's payload range from the
   chain at this+8 and then calls it. Only offsets distinguish element types; no class
   name is recoverable inside these bodies, so their names stay mechanical.
2. **SoeUtil::IString machinery** (008cb680..008ce0a0, `lib.soeutil.string`).
   Constructor bodies that install `SoeUtil::IString<char>::vftable` with the shared
   empty buffer `DAT_01be48fc`, and ~15 destructor bodies that rewrite the vtable and
   release the shared buffer via a locked refcount and virtual slot +8. They run from
   EH unwind funclets, which is the strongest single signal that they are destructors.
   One array destructor (008cb9a0) names `SoeUtil::Array<RailDefinition::PointData,0,1>`
   in its own RTTI - the only appearance of `RailDefinition` in this shard.
3. **Typed row readers for table parsers** (008cd0f0..008ce7d0, `engine.util`).
   All share one reader structure: cursor +8, end +0xc, error byte +0x10. Each reader
   loads N u32 values (plus occasional bool/8-byte pairs) into a caller record and on a
   short read zeroes the field, sets the error byte and clamps the cursor. The four
   readers the vault note cites - 008cd0f0 (games, 20 B), 008cd1d0 (options, 16 B),
   008cd280 (values, 16 B), 008cd360 (settings, 24 B) - are the kart-lobby 102/2 row
   parsers and are `confirmed` through `Research/Kart Lobby Definition Framing.md`,
   which cites these exact addresses. The note also fixes the 008e5450/008e5580/
   008e56c0/008e5800 parser chain above them. Note the settings reader deliberately
   loads its fourth value into slot 4 before slot 3, matching the note's field order.
4. **net.packet classes** (008cebc0..008cf7a0). Packet constructors, destructors and
   scalar deleting destructors for: `PacketSendZoneDetails` (opcode 0x2b = 43,
   catalogue row), `PacketTargetClientNotOnline`, `PacketClientKickedFromServer`
   (0x51 = 81), `PacketClientPendingKickFromServer` (99), `ClientUpdatePacketNotifyPlayer`
   (client-update subtype 0x17 = 23) and `GameUtil::Logging`. Three of these
   constructors have exactly one caller, the unlabelled dispatcher 009471a0, which
   also builds many other packet classes; the receive direction recorded in `wire`
   rests on that factory role. The packet destructors compose the confirmed fixed-string
   destructor bodies (IStringFixed<char,8/32/64/128/256/2048> at 00792630, 00703350,
   004022b0, 0070a900... ) and the player-update packets release an IString member at +0x28.
5. **Effect-definition asset loaders** (008cf920..008cfec0, `engine.asset`; 23 of the
   165 targets are vtable entries). `SensoryEffectDefinitionLoader` implements
   `SensoryEffectDefinitionManagerInterface` and
   `AssetManagement::AssetDeliveryHandlerInterface` (008cf920/008cf9d0); its +4
   interface vtable uses the adjusting thunk 008cf9c0 (sub ecx,4; jmp 008cfa70). Four
   `Actor*Definition` classes carry an
   `AssetManagement::AssetRequestInterface::AssetRequester` sub-object at +0x90 with
   the usual ctor/dtor/delete trio plus two extra virtuals: a float-equals-sentinel
   predicate at slot [4] (008cfb40 has +0xbc, 008cfc50 has +0xa8, 008cfd60 has +0xac,
   all compared against DAT_01762a30) and a byte getter at slot [5] (008cfb60 +0xc8,
   008cfc70 +0xb4). Each class's second vtable holds a +0x90 adjusting thunk at slot
   [0] (008cfb70, 008cfc80, 008cfd80, 008cfeb0 -> the class's scalar deleting
   destructor). The shared base destructor is FUN_007e0b10 (ActorEffectDefinition).
6. **Player state and projectile records** (008cff40..008d0310).
   Six flag-bit getters (008cff40..008cffc0) read bits of the state block at
   +0x142/+0x143/+0x147/+0x148; their only caller 00973200 carries the string
   `ProxiedCharacter::Process`, so the block belongs to ProxiedCharacter - recorded as
   caller-derived, not as this function's own evidence. 008cfff0 is the predicate whose
   only caller 008ded4f carries the Lua property name `Player IsMoving`.
   `ProjectileParameters` (008d00e0 ctor, 008d0240 dtor, 008d0310 delete) matches
   `Research/Pieces/055 Ranged enemy attacks.md`, which cites 008d00e0 by address.
7. **PlayerUpdate packet family** (008d0330..008d08b0). Constructors call the family
   constructor `FUN_0089fbb0(subtype)`, which stores opcode 0x23 (35 - accepted label
   `BasePlayerUpdatePacket::BasePlayerUpdatePacket`) and the subtype, then install the
   concrete vtable.

## Vtable families seen through the slot map

The shard's slot data adds one class family that no single body names:
`GameUtil::Logging`, `RewardBundleBase`, `ClientRewardManager` and `ClientRewardBundle`
share three vtable entries - a slot [0] getter returning the counted pointer at +0xc
(008cf790, 13 bytes) and two 6-byte forwarding thunks at slots [1] and [2] (008cf770,
008cf780) that jump to the object's slot 0. GameUtil::Logging's own vtables also carry
the class's scalar deleting destructor at slot [5] (008cf880). This is the one place in
the shard where several classes provably share the same method bodies.

## Packet and server-contract inferences that span functions

* **PlayerUpdate subtypes recovered here.** 10 = `PlayerUpdatePacketAddNotifications`
  (008d06d0, catalogue row 35/10), 11 = `PlayerUpdatePacketRemoveNotifications`
  (008d07c0; no catalogue row), 12 = `PlayerUpdatePacketNpcRelevance` (008d08b0,
  catalogue row 35/12), 52 (0x34) = `PlayerUpdatePacketUpdateTintAlias` (008d04d0).
  Two more subtypes are only visible in raw bytes: 008d0330 pushes 0x2e (46) for
  `PlayerUpdatePacketCustomizeNpc` and 008d0400 pushes 0x30 (48) for
  `PlayerUpdatePacketRemoveNpcCustomization`. The decompiler drops those immediates
  from the pseudocode, so they are recorded in `open_questions` rather than in `wire`
  (the validator requires opcode constants to appear in the pseudocode text). A lead
  running `bytes 008d0330` sees `6a 2e` / `6a 30` immediately before the call.
  Hypothesis for the server: it drove NPC appearance with 35/46 and reverted it with
  35/48, and removed notifications with 35/11 - neither 46, 48 nor 11 has a row in the
  pinned Sanctuary/FreeRealms-Legacy catalogue, so the emulator catalogue is incomplete
  here rather than contradicted.
* **Notify/kick opcodes.** 0x2b (43) is `PacketSendZoneDetails` (catalogue); 0x51 (81)
  and 99 have client constructors and destructors but no catalogue rows. Hypothesis:
  the original server sent 81 to eject a client and 99 as a pending-kick notice, each
  with a reason string (the constructors embed exactly one IString). The receive
  direction is inferred from the dispatcher 009471a0 being the only caller of those
  constructors plus the semantic of the names carried in RTTI.
* **ClientUpdatePacketNotifyPlayer** (008cf5e0) calls `FUN_0089d180(0x17)`, a second
  family constructor (client-update family, 009392c0 dispatcher). Subtype 23 carried one
  string member at +0xc. This links the 0x17 family to the same dispatcher family as the
  PlayerUpdate packets.
* **Kart lobby 102/2**: the row readers are only the leaf half of the chain; the
  producer side is gone and the note's byte-exact framing remains the contract. Rows 2
  and 3 (options/values) still have no recovered semantics.

## Contradictions and catalogue gaps

No contradictions with the vault notes were found; the four kart-lobby reader addresses
match the note exactly. Two gaps are worth flagging to the lead:

* The pinned packet catalogue has no rows for subtypes 11, 46, 48 (PlayerUpdate) and no
  rows for `PacketClientKickedFromServer` / `PacketClientPendingKickFromServer`, even
  though the client has RTTI-named classes and opcodes for them. Any Rust packet table
  built only from the catalogue would silently omit these.
* The `RailDefinition::PointData` array (008cb9a0) is the only RTTI sighting of a rail
  type in this range; nothing else here parses rails, so the type appears incidental to
  the object being destroyed.

## Most important open questions

1. Who owns the container instantiations? The bodies prove the layouts (links, bucket
   masks, element strides) but never a class. If any shard labels a caller such as
   008fa0d0, 008d46f0..008d4e40 or 01029690, the per-type names can be upgraded.
2. What do the ProxiedCharacter flag bits at +0x142/+0x143/+0x147/+0x148 mean, and what
   does the predicate 008cfff0 guard (`+0x1c4 < 1` plus bit 2 of +0x143)? The Lua name
   `Player IsMoving` on its caller is the only semantic hint.
3. `ProjectileParameters` field semantics beyond the note (what the +0x20/+0x24 globals
   are, and the two `Target` sub-objects) - the ctor only proves the layout.
4. The reader helper block (008caaa0, 008cb4c0, 008cb500, 008cb540, 008cb5a0, 008cc760,
   008cd0f0..008ce7d0) is used by parsers whose own shards (008e3c30, 008e5450, 008e6190,
   008e7210, 008e9d70, 008fa4b0, 008fcdb0, 0091b530, ...) are outside this shard; tying
   each row reader to a named packet needs those parsers labelled.
5. What are the three extra virtuals shared by GameUtil::Logging / RewardBundleBase /
   ClientRewardManager / ClientRewardBundle for (008cf790 getter, 008cf770/008cf780
   forwarding thunks), and what do the four classes' payloads look like? The vtable
   relationship is proven here; the semantics are not.
