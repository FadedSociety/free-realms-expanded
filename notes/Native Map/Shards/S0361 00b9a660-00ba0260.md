## What this shard is

One coherent client-side feature: the **kart-racing minigame** (vehicle race).
Four layers appear in address order:

1. `VehicleRaceProcessor` gameplay state and its 24 race **sound events**
   (00b9a660..00b9bab0, plus e2b0/e490/e4c0/e500/e530/e560..e7d0/f110..f190/
   f360/f690..f930 in the second half).
2. The complete **`BaseVehicleRacePacket` class family** (inner opcode 33):
   constructors and scalar deleting destructors for 30 of the 34 subtypes
   (00b9bc10..00b9df60), plus the two "fat" constructors 00b9c910 (33/11) and
   00b9d040 (33/33), the 33/27 destructor pair (00b9ee60/00b9eed0/00b9f320),
   the ClientData copy constructor (00b9dfd0) and its store helper 00b9ef60.
3. **SoeUtil containers** used by the processor: typed `List<T>` node
   allocators/frees/removes/adds for `ProxiedVehicleRace`, `RacerInfo`,
   `ProxiedVehicleRacePickup`, `ProxiedVehicleRaceMissile`,
   `ProxiedVehicleRaceMine`, `ProxiedVehicleRaceExplosion`,
   `ProxiedVehicleProximityArrow` (00b9d3d0..00b9d700, 00b9d720..00ba50-level
   adds, 00b9e560..e7d0 removes, 00b9ec50, 00b9fa20), an IString ctor/dtor pair
   (00b9ead0/00b9eb30 and a second ctor at 00b9f1b0), a 48-byte-element array
   append/grow/trim set (00b9bab0, 00b9eba0, 00b9f0d0, 00b9f9e0), and the
   `GameProcessor` base ctor/dtor (00b9efd0, 00b9f050, 00b9f340).
4. The 33-family **payload parsers** (00b9fb10, 00b9fc80, 00b9ff10, 00b9ffb0,
   00ba0070, 00ba0260) and the shared **header reader** 00b9fab0.

## Mechanical facts worth keeping

* **List layout (all seven typed lists):** embedded object at +0 = vtable,
  +4 = head, +8 = tail, +0xc = count; slot 2 = node allocator, slot 3 = node
  free; slot 0 = scalar deleting destructor that drains first. Node link fields
  differ per type: ProxiedVehicleRace +0x1bb0(next)/+0x1bb4(prev) inside a
  **0x1bc0-byte** node; RacerInfo +0x20/+0x24 in 0x28 bytes; Pickup +0x24/+0x28
  in 0x2c; Missile +0x90/+0x94 in 0xa0; Mine +0xc0/+0xc4 in 0xd0; Explosion
  +0x50/+0x54 in 0x60; ProximityArrow +0x70/+0x74 in 0x80. Head is at **+4**,
  tail at **+8** (proved by the end-branch writes in 00b9e560 and 00b9b9e0);
  `00b9b9e0` inserts *before* a node (or appends when the node argument is 0)
  and is the relinker used by the racer-list sort `00b9e860`.
* **The processor holds two proximity-arrow lists** (+0x310 and +0x320), not
  one: 00ba2f80 sets both `List<ProxiedVehicleProximityArrow>` vtables and both
  heads (+0x314, +0x324) are drained. Their distinction is not recovered.
* **Every proxied racer embeds a 33/5 `UpdateVehicleRaceClientData` packet** at
  +0x1b40: 00cdf9b0 (out of shard) constructs it via 00b9be30, and 00b9ef60
  copies a fresh one in via the copy constructor 00b9dfd0. That makes the 33/5
  packet the racer's state record, not just a wire message.
* **Race sound events:** 00b9f360 looks up 24 `Vehicle_*` events and builds one
  sound emitter each (00b9d2d0, 0x58-byte object from the SoundEmitter factory
  0078fea0); 00b9a660 destroys them (virtual slot 0 delete + event refcount-1),
  00b9ac50 sets a float on all but the countdown pair, 00b9ae90 stops the three
  looping emitters (Shield_Active, CowCatcher_Active, Wrong_Way) via virtual
  slot 3 with argument 0 plus byte +0x4d.
* **Dispatcher case -> helper (from 00ba74d0, context):** 0x5 -> 00ba1070 ->
  00b9fb10; 0x8 -> 00ba1310 -> 00b9ffb0; 0xe -> 00ba11c0 -> 00b9fc80; 0xf ->
  00ba1380 -> 00ba0070; 0x21 -> 00ba1620 -> 00ba0260; the ctors 00b9c200,
  00b9c910, 00b9cae0.., 00b9cf70, 00b9cc20, 00b9ccf0, 00b9ce30 etc. are
  constructed inside their cases. Parsers are always `header (00b9fab0) + fields
  with per-field bounds checks`; truncation zeroes the field, sets the reader's
  error byte at +0x10 and clamps the cursor, and NaN floats set a second flag at
  +0x11.

## Server-contract inferences (hypotheses, each depends on the listed pieces)

* **Registration/spawn hypothesis:** the client sends 33/9 with its guid pair
  (00b9c2d0 and sender 00ba5eb0, described by the register note). Client receive
  paths cover 33/11 (00b9c910/00ba7370) and configuration 33/34 is described in
  adjacent research. This suggests the service associated a registration with
  race state and supplied spawn/configuration data; server matching, ordering
  and acceptance rules are unknown.
* **Progress hypothesis:** 33/14 (parser 00b9fc80) carries a guid plus
  lap/placement/flag fields, then the dispatcher applies them to racer state
  (00b9d210 and dispatcher context 00ba74d0). This is consistent with server
  supplied progress, but update cadence and authority rules are not recovered.
* **Client-request hypothesis:** 33/6, 33/9, 33/19 and 33/22 have client send
  paths in 00ba48a0/00ba5eb0 (out of shard; packet constructors here). The
  available evidence establishes requests/state sent by the client, not what
  the original server validated or changed. Server validation rules remain
  unknown; the research notes caution that client positions are untrusted.
* **Object-state hypothesis:** client receive cases and parsers cover 33/11,
  33/12, 33/13, 33/15, 33/24, 33/27 and 33/29 (dispatcher 00ba74d0 and packet
  construction paths in this shard). This is consistent with the service
  supplying proxied-object state. Local arrow markers (00b9da50) also exist;
  server authority and client prediction boundaries are not fully recovered.

## Contradictions and corrections

* `Research/Kart Vehicle Configuration and Input.md` lists subtype 8
  (VehicleHit) as "sent only", but the dispatcher has case `0x8` which both
  constructs 00b9c200 **and** parses through 00ba1310 -> 00b9ffb0 (guid, guid,
  float). The client therefore *does* read incoming 33/8; only 7 and 9 have no
  dispatcher case in the export (consistent with "sent only" for those).
* Early hypothesis in this pass (superseded): the ProxiedVehicleRace list was
  first read as "head at +8, insert-after". The end-branch writes prove the
  opposite (head +4, tail +8, `00b9b9e0` links *before*); the records use the
  corrected reading.
* `00b9e490`/`00b9aee0` + `00b9e500`/`00b9e530` + `00b9e4c0` + 00b9e240/e2b0
  are the results/exit predicates used by 00ba6530: they read racer byte +0xf00,
  live pointer +0x10b0, expected counts +0x1c4/+0x1c8 and reset byte +0x18c /
  float +0x190. No note records these fields yet; they are candidates for the
  results-screen model in the successor notes.
