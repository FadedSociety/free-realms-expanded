# T259: a finished soccer match advances FinishMinigame quest objectives once

## Result

`Gameplay::tick_world`'s soccer branch settled the match on full time and adopted
the payout, but never reported the terminal result to the quest engine, so a
soccer win could not advance any `ObjectiveKind::FinishMinigame` goal (kart,
chess and the type-8 paths already did). The fix is one call into the existing
hook, in the existing order:

1. the server-built terminal sequence (`39/14` `OnGameWonMsg`, `39/18`, `39/47`,
   `39/19`) is queued;
2. the settled reward state is adopted on the live inventory/profiles (the
   existing `adopt_reward_state`, plus `out.replies.extend(settled.replies
   .iter().cloned())` so the packets stay readable for the hook);
3. `npc_minigame_win(&settled.replies, &mut out)` runs once, appending the
   ordinary `49/9` objective row (and `49/10` when that step completes).

No new marker was added: `TickResult::settlement_due` (set by
`Session::tick` only for `MatchPhase::Finished` while `!settled`) is the
once-only guard, and `Session::settle` is itself idempotent. The event is
derived only from the result packets the server generated from its own score
and clock; the client's family-76 input never reaches it. Losses (a tie counts
as a loss for the per-player result), cancels, early closes, duplicate settles
and reconnects produce no event.

`npc_minigame_win` is unchanged in behaviour; only its doc comment grew to name
the soccer source and the client readers. Kart, chess, fishing and the type-8
passes keep their own producers and packets.

### Integration repair (attempt 2)

The first integration failed the full suite in test 9 at
`tests/soccer_quest_credit.rs`: after a refused catalogue bind the test asserted
`state().npc_quests.is_none()`. That assertion contradicts the documented
contract on `bind_npc_quest_catalogue` ("a refused rebind keeps the bound
catalogue and the saved progress") and worker rule 1 (a refusal changes
nothing): a refused bind must not consume the saved state. The sibling fixture
`tests/shared_field_kill_quest_credit.rs:641` already asserts the kept state
after the same refusal. The test now asserts the kept save's `character_id`
(the state is untouched, no engine is bound) and still proves A's match settles
and pays without a quest credit while B's session credits its own goal. The
production call is unchanged from attempt 1; only the test expectation moved.

## Client evidence (IDA available)

The slice adds no opcode or field. It consumes the server's own terminal
packets, which are already built by `src/minigame.rs`, and the tests pin the
layout of what it emits.

- `39/18` (`MiniGameGameOverPacket`): shared header — `u16` family 39, `u8`
  subtype 18, then three `i32` (instance, group `-1`, game id) — then `u8 won`
  and three `i32` (stars, elapsed seconds, score). Reader `0x009b7ec0`
  (`ReadNineFieldRecord`) → `0x009b48b0`; shared header `0x009b2340`
  (`ReadMiniGamePacketHeader`); client handler `0x009ad480`
  (`ApplyMiniGameGameOverResult`) stores the won byte at state `+0x63` and the
  three words at `+0x70/+0x74/+0x78`. The third header word is the game id
  (Minigame Framework guide: native Cooking info was `(46000001, -1, 46)`).
  `npc_minigame_win` reads `p[15]` as the win flag and `p[11..15]` as the game
  id — the same offsets the writer uses.
- `39/14` (`OnGameWonMsg`): shared header + `i32` length-prefixed string
  including its NUL, read by `0x009b89e0` (`MiniGameFlash:OnMessage`). The
  hook's shape check `p[19..] == b"OnGameWonMsg\0"` matches that body.
- `49/9`/`49/10` objective rows: six-byte header (`u16` 49 + `i32` subtype),
  then quest, objective key, current, `f32` progress, notification byte, one
  `i32` (49/9, 27 bytes) or quest, key, `f32` progress, one `i32`, notification
  byte (49/10, 23 bytes). Readers `0x00c7b5e0`/`0x00c7b650` →
  `0x00c7af60`/`0x00c7b070`, applied by `0x00c7a990`/`0x00c7aa10`.
- The brief calls `0x00c7bd10` the "49/3 objective packet" reader. IDA shows it
  is `ApplyQuestAddPacket` (49/3 `QuestAdd`, the quest record) and the Build
  Guide agrees; objective progress is 49/9/49/10 above. IDA wins. This changes
  no server output: accept/login still send 49/3 `QuestAdd` unchanged.
- The soccer state path (`76/13`, `76/14`, `76/16`) is client-to-server input
  only. A client `GoalMade` is refused by the soccer service; a client `39/14`
  or `39/18` is not an accepted lifecycle sub-opcode, so it is ignored. Test 6
  proves a claim settles nothing.
- Re-checked this run with `ida_query.py decompile`: `0x009b7ec0` calls
  `0x009b48b0`, which runs the header reader `0x009b2340` (`i16` family + `u8`
  subtype + three `i32` = 15 bytes), then reads one byte (`won`) and three
  `i32`. `0x00c7af60` reads four `i32`, one `i8` and one `i32` after the
  six-byte `0x00c7acd0` header (the 27-byte `49/9`), and `0x00c7b070` reads
  four `i32` and one `i8` (the 23-byte `49/10`). The offsets the hook and tests
  use are the reader's.

## Security note (secure-code-guardian)

Hostile client surface: family-76 impulses/states/controls, family-39
`5/6/7/46` lifecycle messages, forged `39/14`/`39/18` result claims, and a
pre-result `26/42` close.

- The quest event is derived only from `settled.replies`, the packets the
  server itself built from its own score and clock in `MinigameRuns::finish`.
  No client body is parsed for a win, score or game id.
- `MinigameRuns::handle_client` accepts only `39/5`, `39/6`, `39/7` and `39/46`
  from a client; any other subtype (including 14 and 18) returns an empty
  outcome. The client's `76/8` `GoalMade` is refused before the score changes
  (`soccer_service`), so a client cannot fabricate a goal or a terminal result.
- The game id is the settled session's own content id (`42`/`43`/`44` from
  `data/content/soccer.json`); a `43`/`44` match does not credit a `42` goal
  (test 4). The event's `minigame_id` is validated positive by the quest
  engine, and the counter uses `saturating_add(1).min(required)`.
- The only trigger is `settlement_due`; a loss, cancel, early close, duplicate
  settle/close and reconnect emit no event. The reward is the existing
  `apply_grant` run-keyed payout; this slice grants nothing.
- A per-player failure inside the settlement returns `Err` from that staged
  tick, so nothing from the settlement commits (no partial reward or quest
  credit) and the gateway's per-session `contain` disconnects only that player.
  Test 9 covers a stale quest save refused for A while B's match still settles
  and credits.
- No secret, identity, save-path or session-plumbing code was touched.

## Checklist

(Numbered 1-19 against `lab/autopilot/worker-rules.md`.)

1. **A refusal changes nothing.** The settlement runs on the staged `Gameplay`
   clone and commits only at `*self = staged`; a loss/cancel/early-close/dup
   never enters the block. Tests 3 and 5 snapshot counts and coins before the
   refused paths and assert them unchanged; canary 1/2 are the production
   breaks for "exactly once". Test 9 also asserts a refused catalogue bind
   leaves the saved quest state in place (the integration failure was an
   assertion that the refusal consumed it).
2. **Rollback covers all state.** The soccer session, reward state and npc
   quest state all live in the cloned `Gameplay`; there is no new shared
   `Rc`/`RefCell`/`Arc` or side table. An `Err` from the hook drops the clone,
   so neither reward nor quest progress commits.
3. **Apply deltas, never restore snapshots.** The payout is still applied on
   the live `reward_snapshot()` and adopted; the quest counter is the engine's
   `saturating_add(1).min(required)`. Nothing restores a captured inventory,
   coin balance or position.
4. **Busy rules are mutual.** No new activity, station or minigame; soccer's
   `Occupation` row and the busy table/pin test are untouched.
5. **Every entry path is gated.** The credit is inside the one settlement seam
   reached by `Gameplay::tick`; there is no new request, NPC, automatic or
   reconnect path. The Play path and its admission checks are unchanged.
6. **Reachable in production, tested through it.** Tests drive
   `Gameplay::handle_in_world` (`167/1/2`, family-76, `39` lifecycle, `26/42`),
   `Gameplay::tick` (the gateway's session tick), and `Gameplay::load` +
   `bind_npc_quest_catalogue` (the gateway load call). No test calls
   `npc_minigame_win` or a copy of it.
7. **Survives reconnect.** The counter lives in
   `GameplayState.npc_quests`; the reward in the inventory save. Test 7
   serializes `GameplayState`, reloads it through `Gameplay::load`, rebinds the
   catalogue and asserts the counter stays 1, the login sync carries that
   counter, no `39/18` replays, and the coins do not move on later ticks.
8. **Every exit path restores the player.** Unchanged: the result Close
   (`26/42`) returns the pre-match pose via `exit_soccer`; cancel, early close
   and reconnect keep the existing behaviour. This slice adds no stuck state.
9. **Economy safety.** This slice grants no item or coin. The 10-coin soccer
   reward is the shipped content value paid by the existing run-keyed
   `apply_grant` once per settled match; the test asserts one payout and the
   coin packet's balance. The quest credit comes only from the server-verified
   terminal result, and the shipped reward grants no job XP (asserted).
10. **Wire format matches the client.** No new bytes. The `49/9`/`49/10`
    assertions use the reader-derived 27/23-byte layouts and offsets; the
    `39/18` win flag and game id offsets are the writer's and the client
    reader's. Readers cited above.
11. **Unique ids.** No new instance/GUID/lifecycle id; the quest and match ids
    are the shipped/synthetic content ids and the run instance stays the
    process-wide `NEXT_INSTANCE_ID` value that `MinigameRuns` already owns.
12. **Others see changes.** The quest row is private to the settling player's
    session; no visible actor/outfit/state is changed. No new fanout.
13. **Content works end to end.** A real Play → start → server goal → full time
    → settle produces the reward and the objective row; the near-cap fixture
    asserts the step completes (`49/10`) and the counter lands on the required
    count.
14. **Values live in data.** No tuning constant was added. The goal count, game
    ids, match clock and reward are content (`data/content/soccer.json`, the
    split quest file, the test fixture's short clock for bounded tests).
15. **Canaries break production code.** Both canaries edited
    `src/gameplay.rs` (removed / duplicated the call) and failed the intended
    tests; each was restored to the SHA-256-identical file, the rebuild was
    forced, and the suite went green again (the restore mtime trap is written
    up under Canaries).
16. **Hands off session plumbing.** `src/gateway.rs`,
    `src/bin/osfr-gateway.rs`, sessions, teardown, transactions and save
    ordering are untouched.
17. **One player's error never stops the server.** The hook's `Err` aborts only
    that player's staged tick; the gateway runs each session tick inside
    `contain` and calls `end_session` for that key on error
    (`bin/osfr-gateway.rs:3809-3822`), so neither a panic nor an `Err` can leave
    `Server::step`. Test 9 gives A a stale quest save: A's catalogue bind is
    refused with `InvalidData` (the per-session load path the gateway uses,
    `gateway.rs:816`), the refused bind keeps the saved state, A's match still
    settles and pays without a credit, B's match in the same fixture settles
    and credits its own goal, and the test process keeps running.
18. **A type's rules live on the type.** The soccer session's
    `TickResult::settlement_due`/`settled` remain the once-only rule (documented
    in `soccer_entry.rs`); this slice adds no field or flag. The quest cap rule
    stays on `QuestEngine`.
19. **Hot paths stay cheap.** The hook runs only on `settlement_due`, once per
    match, not on the 20 Hz tick and not per packet. It allocates no match
    state. The one added cost is cloning the handful of small terminal/reward
    packets into `out.replies` on that single tick so the hook can scan them;
    a normal tick allocates nothing new.

## Open gaps

- **Synthetic goal count.** The brief asked for a `count: 1` goal, but a
  one-match goal is capped by the engine, so a duplicated credit is
  indistinguishable from a correct one and the brief's second canary (which
  must fail) cannot fail. The test content uses `count: 2` (two finished
  matches) and adds the brief's near-cap fixture (saved count 1 → one match
  completes it). The production rule is unchanged: one settled match = one
  event; the engine caps the counter.
- **No native run.** The slice adds no packet and the soccer result burst was
  already native-proven for the shared lifecycle (kart/crafting), but no soccer
  match was played on the original client in this run. The 39/18/39/14/49/9
  layouts are pinned to the readers above and the existing suites.
- **A tie is a loss.** The soccer service's per-player mapping
  (`winner == Some(team)`) makes 0-0 a loss, so a tie credits nothing; that is
  existing `(R)` policy and was not changed.
- **Quest status after completion.** The quest stays Active until turn-in; the
  test asserts the counter and completion row, not a turn-in (out of scope).
- The test fixture copies the private opening content and the shipped split
  content per test, like the existing `shared_field_kill_quest_credit`
  fixtures; it removes `harvesting.json` because the opening inventory lacks one
  optional farming reward (same rule as those fixtures).
