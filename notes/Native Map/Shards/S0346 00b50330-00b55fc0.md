## Server-contract inferences (hypotheses)

No decoded pet datagram exists (note 091 reports the same gap), so every
`server_inference` below is a hypothesis tied to a client writer, not an observed
server behaviour. The pieces that must be inferred together: the subtype table
above, the request bodies pinned in note 091 (4: pet_id+action, 26: 4 floats +
flag, 28: flag, 32: pet_id+item_id), the reader signatures in this shard, and
the pet profile record from the preserved dump.

* Summon/recall (subtype 4, client origin 00b50890): the server must have
  validated ownership, spawned/despawned the pet actor and answered with subtype
  9 (PetActivePacket) so the client could cache the active guid.
* Buy (subtype 25) -> response (subtype 31); the response's two flag bytes and
  two dwords are the accept/refuse result plus the new pet id, unverified.
* Utility requests (16/18/19/35) -> notification (20/21): the server must have
  mutated the food/groom/utility fields of the pet record and echoed the result;
  the client gates utilities on the pet-busy flag +0x143 (note 091) and on
  `PetsHandlerOnSummonFailed`-style checks (00b549f0).
* Pet UI refresh after every pet action is client-side only (00b53450 through
  the Lua handler names carried by the strings in 00b53450/00b53530).

## Uncertainties and open questions

* Three functions are pure `BasePacket`/`TargetProcessorEventHandler` vtable
  resets whose owner cannot be recovered: 00b51a20 and 00b51c30 (each called only
  from MSVC unwind funclets, byte-identical to each other) and 00b547e0 (no
  callers at all, so it cannot even be classified as ctor vs dtor). They are left
  at `unknown` on purpose; adjacency to neighbours is not evidence.
* 00b52010 and 00b52030 are 8-byte tail-call thunks (`mov ecx,[ecx+8]; jmp ...`)
  into the pet state machine at 00cc8ff0/00cca410. Their owning class is unknown;
  the names stay mechanical (`Wrapper00cc8ff0`, `Wrapper00cca410`).
* Direction of the subtype-0xc, 0xd, 0x15 and 0x18 packets is inferred from the
  class semantics (server -> client state messages), not witnessed.
* All field readers were left with an empty `wire` list: they parse payload
  fields, not a named packet, and no opcode constant appears in their bodies.
  The opcode lives in their callers (0xb57xxx-0xb58xxx), outside this shard.
* The item-group key -0x50c03a16 consulted by 00b549f0 and the predicate
  00bf7c20 are unlabelled; the "reason string" path through 0097c1e0/008edba0 is
  likewise reconstructed only from shape.
* The constant 3 at +0x20 of every 36-byte name-pair record (00b54330) has no
  recovered meaning; the second IString of the pair is presumably the localized
  name but no anchor proves it.

passes. The 27 unlabelled tail functions (00b549f0..00b55fc0) were named here
for the first time.

`reverse-engineering` methodology with the shard's Ghidra export (`nmq show`,
`nmq bytes`, `nmq callers`, `nmq notes`) provided all anchors; RTTI vtable-slot
records were used as strong evidence for the scalar deleting destructors and the
`PetTileTargetHandler` predicate. `game-research-websearch` was not needed: the
family is already pinned by vault note 091 and the community readers, and every
label in this shard stands on an in-binary anchor. Helper scripts used:
`scratch/digest.py`, `scratch/pcdiff.py`, `scratch/table.py` (read-only
analysis; no record or evidence was generated by script).
