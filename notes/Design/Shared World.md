# Shared World

Build Plan **3.1**, supporting **M4: about ten friends playing together**. This is a design, not an implementation or native acceptance claim. W108 changes no code, content, saves, Plan or Ledger.

**Decision proposed for review (R):** one gateway process, one simulation writer, one enemy state per `(zone, instance, authored GUID)`. Reuse the existing coordinator, combat calculations, packet writers and interest machinery. Keep personal progression in each player's Gameplay. Do not add threads, an actor framework, ECS, database, distributed ownership or a replacement combat engine for this milestone.

Evidence notation: **C** = current Rust source; **N** = recovered client evidence; **R** = reconstructed server policy or proposed implementation. Every proposal below is **(R)** unless explicitly identified as C or N. Client packet support does not recover the original server's recipient selection, aggro, credit or loot policy.

### State placement (R)

`Server::step` is the only writer. Add the existing `world::World` coordinator beside the cloneable SharedWorld, owned directly by Server. World owns each instance's mutable NPC combat state. Keep coordinator/combat state **outside** `SharedWorld::clone`; do not put it in an Arc<Mutex> shared by staged Gameplay clones. The loop already provides serialization [C2]. World's PlayerId means authenticated **character GUID** here; never mix account IDs or transport SessionIds into that namespace.

Refactor the field storage and field branches **inside encounter.rs first**, retaining its private Actor, ground helpers, damage calculation and packet writers [C5, C6]. Split actor-world mutation from the player's combat resources; do not share an entire EncounterEngine, which also contains player health/cooldowns/readiness [C5, C11]. Later move arena enemy/phase state through the same seam. World owns runtime entries; Gameplay requests actions and consumes player-specific effects. Proposed names/types are implementation choices, not existing APIs.

The route must be explicit: teach Gateway's application dispatch to recognize shared field interaction/attack requests and return a small typed shared-action intent instead of running the local EncounterEngine. Keep immutable GUID/definition metadata available for menu/target classification. Add an explicit intent field to the staged outcome and treat that as a handled request; the current empty-outcome/unknown-message check otherwise drops it [C12]. Session dispatch resolves that intent against World and stages the resulting personal effects before commit. Reuse the existing parser's ordered event sequence: split combined messages into ordered event commits so an attack cannot use a later movement event's position. Do not forward raw unvalidated packets to a second combat parser or infer routing from trace output. Player-local cave/opening requests retain their existing route.

Quest-gated fields: hold one canonical actor even when inactive. Presence is the union of ready players in the instance with any matching active quest. Once enabled, **all** nearby players see the same actor and may help; only eligible personal quests gain progress. Removing a quest does not heal or respawn the actor [the current reset behavior is C7]. When the last eligible player leaves, stop new engagements and let an existing engagement resolve or evade home; then hide it. Dead actors keep their original respawn deadline even while hidden. Quest reacceptance cannot reset that deadline. Always-on rows are unaffected. These visibility changes are R and require the old four Hooligans' regression gate.

Retain current native zone meanings. Regional labels are not extra continents (`world.rs::OPEN_WORLD_ZONE`, lines 22-25); World must receive validated runtime zone descriptors for **0, 411 and 9600** as applicable, using existing scene transitions. Do not blindly use every ContentDb regional zone row as a new playable scene. Reuse coordinator membership/allocation [C10] without also emitting its static NPC batch over the live NpcVisibility startup. Exactly one route emits each actor.

Shared field HP, positions and respawn clocks are process lifetime state for M4; a server restart starts a fresh world epoch/population after pending credit recovery. Reconnect to the same running server does not reset them. Player saves keep personal tutorial state and a shared-run reference/safe return pose, not authoritative shared enemy copies. Loaders must accept existing solo saves under their existing validation; old per-player field/arena enemy snapshots never seed or overwrite a shared runtime. A stale shared-run reference returns the player safely to public space. This is a compatibility rule for future builders, not permission to rewrite current campaign saves.

## 2. Combat with several players

All rules in this section are R. Shared enemy mutation runs once per simulation step, not once per player tick. Preserve existing 100 ms simulation cadence and bounded movement integration (`encounter.rs::EncounterEngine::tick`, lines 2736-2740; `tick_field`, lines 3099-3100). Player resource updates can remain session-local. No spectators, idle sessions or extra bots accelerate an enemy's attack, DoT, movement or respawn clock.

**Targets and aggro.** Candidates are authenticated, zone-ready, alive combat-job players in the same ZoneInstance, within authored aggro/leash bounds, outside personal knockout grace. On idle acquisition choose nearest by squared distance, then character GUID. Keep the current valid target until invalid, out of chase range or beyond home leash; another hit records contribution but does not force target switching. On invalid target reacquire among valid candidates, otherwise evade home. Preserve the existing home-heal/Returning immunity [C6], and clear all contribution and NPC effects when an engagement resets. One enemy attack damages one chosen target; nearby observers do not take duplicate damage. Do not add a threat table or taunt mechanic until required by an authored ability.

**Attacks.** Authenticate the attacker from Session, never from packet actor IDs. Resolve target within server-owned `(zone, instance)`, validate ready/alive/job/ability/level, server-accepted position, range, energy and per-player cooldown. Retain native request parsers and current combat calculations [C11, C12]. Explicit target and basic self-centred target selection must both resolve against the shared runtime. Unknown, returning, hidden, dead or other-instance targets are no-ops/refusals without side effects. AoE enumeration comes from the server's instance actors and range, not a client target list. All damage paths, including job DoT and AoE, use the one shared HP transition. Clamp effective damage to remaining HP. A second lethal request sees dead state; it cannot defeat or reward again.

**Contribution and credit.** Track effective damage by character and contribution-time job; a healer/buffer helps when a validated beneficial effect changes an already contributing party member's health/status during that encounter. Zero damage against shields, overheal and a party membership alone do not qualify. Eligibility persists until enemy death or engagement reset; there is no arbitrary last-hit timeout. Bound contributors to admitted sessions. At death freeze the set of helpers still connected/ready in the same instance and within 100 m of the enemy. A connected knocked-out helper still qualifies. A helper who has left/logged out before death does not; a reward already frozen survives later logout through the transaction below. These are explicit playtest policies for the owner to review.

Each frozen helper gets **one** kill event for that enemy incarnation, even without a party; applicable active quests receive count 1 through the existing defeat mapping [C8]. No progress for inactive/finished quests, distant spectators or unrelated party members. Do not send opening progression for a regional field kill unless that definition is explicitly bound to the player's opening objective. Credit identity is `(world run epoch, instance, actor GUID, spawn generation, character GUID)`, never GUID alone. Quest accept/drop/relog cannot replay a completed death event.

**Loot and XP.** Personal entitlements, not a contested corpse: each eligible helper gets the configured full per-kill coin/item/XP bundle once. This intentionally avoids last-hit theft, rolls and a new loot UI for ten friends. No multiplier by party size. Credit XP to the combat job captured at the last qualifying contribution, so a later job switch cannot redirect it. Current field kills have no positive field reward path [C8]; absent authored per-kill values mean **zero coins, zero items, zero XP**, not an invented drop table or the battle's 50-XP reward. The builder must add/use explicit optional reward data only when the lead supplies reviewed content; synthetic tests supply a bounded reward fixture. Existing arena prize choice is selected by the server once per eligible recipient and frozen before the wheel. Client acknowledgements do not roll or grant again [N4, N6 do not establish any retail loot policy].

**Observers and wire delivery.** Reuse W96's ZoneInstance cell candidate query and W106's directed set/diff approach [C9]. Expose a narrow read-only nearby-session query; do not build another player spatial grid. Player-to-player visible sets are capped and directed: neither the attacker's PC view nor its inverse is an NPC recipient list. Keep a separate per-session known-NPC set, covering passive and hostile actors under the existing 100 m / 64 NPC budget (`world.rs::NpcVisibility::update`, lines 413-457). At M4's cap, ranking at most 64 field actors is sufficient; no new NPC spatial index is needed. Order by distance then actor GUID, keep relevant engaged actors selected within the budget, and reject attacks on actors outside the final known-NPC set.

Reconcile NPC sets after player pose/readiness/eligibility changes, NPC motion/death/respawn, instance transfer and reload. For new members queue AddNpc, current HP, current status/motion, then relevance. For retained members send only applicable deltas. For leaving members queue removal once and clear known state. Death removes the actor from all current observers; repeat lethal requests produce no second removal. A late join while dead gets no spawn, and the single due respawn adds the same GUID at full HP with a new server generation. These are server delivery choices R, using recovered creation/removal/HP paths [N1 `00921a10` / `0092f460`, N2 `008b3840`, N3 `008b3d00`].

For each observer that knows the necessary actors, send actual attacker swing, 32/7 hit feedback, 35/5 authoritative enemy HP, applicable status/animation, then 35/3 death removal. If an observer lacks the attacker actor, omit two-actor feedback but still send the known enemy's HP/death; never synthesize a false GUID-1 attacker. The target player's private HUD HP/energy, quests, inventory/XP and results remain recipient-only. Enemy attacks broadcast their animation/known-actor feedback to observers but send personal HUD damage only to the victim. Recovered handler `00a2ba40` looks up both actor pairs [N3]; recipient selection and ordering are R. Remove the local-GUID-1 assumption in this new path before multiplayer acceptance [C11].

## 3. Group instances

Policy in this section is R, including the owner's explicit request: **accept enters; decline stays where the member is, still in the party** ([[../Research/Owner Field Notes]], party-consent section). Existing client invitation entry points support reuse [N5 `00a9a0b0` / `00aa36c0` / `00a7d830`, N6 `00a97720` / `008b6da0`]; popup layout and full round trip remain unverified.

1. A valid solo Go creates one private child under the public instance. Any valid member of a party may initiate; starting does not require silently promoting them to leader. Allocate one run per group at a time; repeated starts return that run's state rather than allocating copies. Freeze battle, difficulty, initiating group/roster and each member's return pose. Check combat job/level and entry eligibility independently per member. No automatic teleport of other members.
2. The initiator enters. Send each other connected eligible roster member one native encounter invitation, with a 30-second server deadline. An ineligible/busy member stays put and gets a refusal reason; no hidden job switch. One outstanding instance invitation per member. A second start while one is pending does not replace it silently.
3. On Accept, derive the responder from Session, match the outstanding group/run/encounter and exact response identifiers, recheck membership/job/level/current activity, then consume the invite and stage transfer into that same private instance. Raw instance IDs from clients never confer access. Response replay, stale roster, expired run and replies without an invite do nothing. Decline/expiry clears the invitation only; it never calls group leave or moves the player.
4. Preserve existing scene begin/ready/loaded ordering [C10, C12]. `players::ZoneInstance.instance_id` is a checked nonnegative conversion of World's allocated i32 id, not a second allocator. For private arenas the existing family-41 instance uses the same positive ID; `CharacterState.zone_id` remains the scene/zone ID. Two groups in zone 9600 have different instances and cannot see, chat locally with, hit or loot each other. Public zone 0 may legitimately retain id 0. Check instance changes even if the zone number does not change.
5. The first accepted/ready member can start fighting; pending invitees are not members and cannot hold readiness forever. Already accepted/loading members have a 15-second load deadline. Retain `World::mark_zone_ready`'s all-current-members result [C10] for initial activation, but remove timed-out loaders before evaluating it. Once started, late accepted members enter the same live enemy snapshot; they gain no retroactive kill credit. Do not reset the shared phase or enemy HP when another client finishes loading. No new acceptance after terminal results.
6. A group arena has one shared enemy/wave/phase runtime. Personal combat resources and results stay separate. Reuse the existing solo battle-96 transitions, summon/shield rules, loss/result/Close and prize presentation [C11; native review run `184205`]. The last enemy triggers one shared win transition and eligible per-player entitlements. Close returns **that member**; it does not eject the rest. A member leaving the social group while already inside may finish but gets no new invitations; grouping is entry authority, not a persistent lock on the fight.
7. On disconnect remove that member from World, readiness, aggro targets and interest. Cancel their unaccepted invite. Other accepted members continue. Keep today's explicit social behavior: disconnect removes party membership [C13]; no automatic party restoration. Reconnect returns to the stored safe public pose, following the existing solo reconnect policy, rather than resuming an arbitrary stale instance. Rejoining a still-live run requires a fresh valid invitation and current party membership. Declining is distinct from disconnecting.
8. Retain empty private instances for **60 seconds**, using existing `collect_empty_instances` [C10], then drop combat/effects/contributions/observer caches and run bindings. Clear outstanding invites on terminal/empty retirement; keep durable unpaid entitlements until applied. Public instances remain. Never reuse private IDs within a process; checked exhaustion refuses allocation. Cap private instances at 16 and pending member invitations at admitted session count for M4. Bound any instance left nonempty by a stuck loader through the load deadline and existing disconnect timeouts.

Current coordinator entry emits a full static NPC batch [C10]. Route either the existing scene sequence plus one visibility burst or a filtered coordinator sequence, never both. The adapter must preserve existing scene geometry/tutorial data, rather than replacing it with World defaults. Cave 411 remains solo personal tutorial until separately approved; this design does not turn the opening into a group dungeon accidentally.

Apply instance filtering to local say/quick-chat recipients in the gateway as part of membership integration. Tells and party chat remain intentionally usable across instances. Do not accidentally restrict party communication to the members who accepted the encounter.

## 4. Transactions, Security and cost

### Threat model and invariants (R)

Attack surface: hostile targeted/area attacks, movement, invite/start/answer/exit/revive messages, reconnects and reward acknowledgements. Assets: canonical NPC health, other players' health, party membership, personal progression and save files. Threats: impersonation, other-instance attacks, doubled kills/rewards, fake invite joins, cooldown reset by reconnect, packet/instance exhaustion and rollback-refunded budgets. Host-selected content and journal paths must not become packet-selected paths. Follow [[Security Model]]; this design does not authorize wider binding or Studio privileges.

Validate exact request shapes/lengths and finite server poses before indexing or allocating. Use checked conversion/arithmetic, known IDs and bounded content/candidate counts. Combat entry and actions use account-level budgets in the existing shared Security sidecar **before** staged dispatch, independent of authoritative cooldowns. Proposed extra limits: starts/invite replies 2/s burst 4; combat requests 10/s burst 20 per account, bounded by admitted accounts. These are R, to be measured; do not treat today's social-only route budget as combat protection [C3]. Never refund consumed budgets on save/parse/validation rejection. Do not hold Security's mutex through simulation, encoding or file I/O. Security audit records numeric IDs/reason categories only, no names, chat, tickets or packet bodies.

### Commit sequence (R)

Keep session/Gateway staging [C2, C12] and cloneable social/registry metadata [C1]. World and enemy state are not fields of that clone. Use one concrete staged change per shared action/tick: copied touched enemy row(s), touched instance membership/run state, and only affected player Gateway snapshots. Immutable content stays shared. No generic transaction framework or full World clone.

1. Parse and charge budgets, bind sender identity, read canonical server pose/readiness and instance, then validate action against current enemy state. Process every child of a combined application sequentially in the same scratch transaction, or split it into ordered action commits; later children must observe earlier accepted changes. Never independently stage two attacks against the same old HP.
2. Calculate the touched actor/player changes and build **recipient-specific** packet lists before publishing anything. A nonlethal player attack stages one enemy and attacker resources; an enemy hit also stages its victim. A tick stages only due/moving actors and affected players. No I/O/packets occur from simulation helpers.
3. For a single personal save, persist its staged snapshot through the existing save path before installing the actor/resource change. Pure NPC motion/respawn does not rewrite every character save. Staging failure before persistence discards all combat/quest/reward changes and queued packets, but not Security consumption.
4. A kill can change several characters' quests/XP/inventory. Sequential `save(A); save(B)` is **not atomic** [C3, C14]. Add one narrowly scoped **pending reward/credit batch** file under the host-selected save root. Freeze one bounded post-image per affected character (using canonical save serialization, including the credit receipt), previous-image digest, numeric batch ID and terminal enemy event. Persist this batch atomically before overwriting any recipient save. This durable batch is the commit decision; after it exists the death is never rolled back or re-rolled.
5. Replace affected character documents, then install the corresponding live Gateway states, shared death/generation/deadline and observer changes, and only then queue replies. If any replacement fails after the batch decision, retain the batch and freeze mutations/saves for its affected characters and enemy; retry from those frozen post-images. Uninvolved sessions can continue. Disconnect/shutdown cannot write their old snapshots over a decided batch. If sends fail after state commit, disconnect the affected recipient; never replay the grant to repair a socket error.
6. Before admitting logins on restart, replay the single pending batch idempotently, accepting a save only at its expected previous digest or exact decided post-image; a different image is a fail-closed recovery error. Preserve unknown envelope sections. Finish all replacements before deleting the batch. A crash midway cannot leave a recipient permanently unpaid or paid twice. The journal is bounded to at most 16 canonical documents plus metadata; enforce the existing per-save bound [C14] and a total byte limit. Recovery uses validated numeric character IDs beneath the server save root, never paths supplied by packets or by unvalidated journal strings.
7. Use a persisted numeric next-batch/run-epoch counter so receipt IDs cannot collide across restarts. Reserve/increment it durably before writing a batch; gaps are harmless, reuse is forbidden. Instance/generation IDs remain process-local. Only one unresolved batch exists at a time; refuse further reward-producing shared actions while it is unresolved. This is a deliberate M4 ceiling: reuse the existing JSON/atomic-replace machinery, add a database only after measured save cost or recovery needs justify it. Process-crash replay is required; power-loss durability requires verification of the replacement helper and filesystem flush behavior, not a claim based on rename alone.

Do not use `Arc<Mutex<World>>` or shared NPC state inside Gameplay clones to evade this commit boundary. The NPC menu and coin shop are inline `Gameplay` fields since T019 removed the shared shop and F155 removed the shared NPC menu, so a cloned `Gameplay` is the staging unit; see [[Security Model]] S12. Instance entry/exit stages membership and the character transition together; save failure before commit must leave both old membership and location intact. A batch decision is a distinct irreversible persistence boundary, not an error path that simply restores a clone.

### Clone measurement

W96's lead-reviewed baseline is **about 12 microseconds for SharedWorld clone at 16 sessions**, about 1% of a 1.17 ms median gateway step ([[Build Plan]], 2026-10-16 W96 update). That measured world had no shared field actors [C1]. W106 changed cached registry views [C9]; its faster movement timings are not a new clone benchmark.

The 12-microsecond claim **does not establish the cost after adding shared enemies**. ## 6. Risks, review questions and W108 verification

Questions for the owner (proposed defaults above let implementation proceed after lead review):

- **R fairness:** approve full personal rewards for each effective helper, 100 m death eligibility, effective healing/buffs as help, and no reward for a helper already disconnected at death? Existing authored field reward defaults remain zero.

Main risks: the original invitation popup/response layout still needs native proof; shared DoT/AoE/status paths can retain hidden per-player writes; GUID-1 assumptions corrupt feedback; coordinator startup can duplicate NPCs; content region IDs can be confused with scenes; queue failures after commit cannot be rolled back; multi-file recovery must block stale disconnect saves. The design therefore gates each explicitly. Ten-player performance and power-loss durability remain unmeasured. None of the original server's aggro/loot/XP-sharing rules were recovered by reading client receive handlers.
