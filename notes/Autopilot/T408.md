## Client evidence (IDA, read-only broker, re-decompiled in attempt 2)

- `0x00c0a500` Lua `Quest_AbandonQuest`: `sub_C09F60(&v5, sub_D83C90())` then `sub_C0A3D0(v2, 1)`.
- `0x00c09f60` ctor: `sub_8A2820(23, 0)`, then `*(this+4)` (dword index 4, byte `+0x10`) = id.
- `0x008a2820`: `this[1]=26`, `this[2]=subtype`, `this[3]=a3`.
- `0x00c0a350` writer: `sub_90AC70(a2)`, then writes `min(remaining, 4)` bytes from `*(this+4)`.
- `0x0090ac70` preamble: two 2-byte writes, `this[1]` (26) and `this[2]` (23); `this[3]` is never
  written.
- `0x00c0a3d0` sender: serializes with `0x00c0a350` and sends; no extra body fields.
- Body = `1a 00 17 00 <u32 id>` = 8 bytes. The brief's premise holds ("this+4" in the brief is the
  dword index; the byte offset is `+0x10`).

### 49/6 reply (found while confirming the reply path)

- `0x00c7cd40` case 6 calls `0x00c7b500(&v44, a2, a3, 0)`: a4 = 0, so no trailing allowance.
- `0x00c7b500` `QuestAbandonedPacket::Unserialize` runs `0x00c7ae40` and returns true only when
  the reader error flag is clear.
- `0x00c7ae40` reads the 6-byte prefix (`0x00c7acd0`: u16 family + u32 subtype), u32 id at
  `+0xc`, then **one bool byte** at `+0x10`; a missing byte sets the error flag.
- Case 6 on success: looks the quest up (`0x00c7a610`), removes it (`0x00c7c1f0`), and when the
  bool is 0 prints the chat line (`0x00a92cd0`). `notes/Native Map/Classes/QuestAbandonedPacket.md`
  agrees (ctor `0x00c79730` stores the id at `+0xc` and a byte at `+0x10`).
- So the server's old 10-byte 49/6 was dropped by the client: even a correctly decoded request
  would never have removed the quest from the journal. The brief's stated goal ("the 49/6 removal
  and the journal update") needs the 11-byte reply, so this slice adds the byte although the
  brief's out-of-scope list says "no new wire field" (IDA wins; flagged for the lead).

## Threat note (secure-code-guardian)

A hostile client controls only the 26/23 length and the u32 id. Any length other than 8 is
refused before any state is read (`Err`, nothing staged). The id only selects from the sender's
own `QuestEngine` state: unknown, 0, `u32::MAX`, completed, not-yet-offered and other characters'
ids are all `Unavailable` denials with no reply and no change. No arithmetic on the id, no
`unwrap` on client length (slice is length-checked first). No reward, item or coin path.
