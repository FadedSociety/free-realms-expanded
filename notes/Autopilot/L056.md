# L056: login reply carries the account's IsMember byte; the client caps MaxCharacters (lead)

Brief: `lab/autopilot/opus/lead-briefs/login-account-info-max-characters.md`. Native run
`client-baseline-20261022T123645Z` logged "can have a maximum of 1 character" although the account store says
`slots.max_characters: 6`, so "Add a Character" showed the Become-a-Member message.

## Finding: the client ignores the payload's MaxCharacters

The brief's goal (the client shows the account's `slots.max_characters`) cannot be met by any wire format.
The client computes MaxCharacters from the membership byte and drops the payload value:

| Step | Address | What it does |
|---|---|---|
| UDP login switch | `0x00fa9220` (case 2) | Builds the reply struct, calls the reader, then the handler `0x00fa0920` |
| LoginReply reader | `0x00fa40e0` (via `0x00fa57c0`) | `[opcode u8][LoggedIn u8][Status u32][IsMember u8]`, then the ApplicationPayload as a u32-length array (`0x009538e0`) |
| Handler | `0x00fa0920` | Calls handler vtable slot 4 with (LoggedIn, Status, IsMember, payload) |
| `ClientLoginManager::OnLoginAuthReply` | `0x009542d0` (vftable `0x01809ef4` slot 4; only xref `0x01809f04`) | Defaults `{member 0, max 1, admin 0}`. If LoggedIn and the payload is non-empty, decodes it with `0x00954170` → `0x00953790` as `[member u8][max u32][admin u8]` (matches ours). **Then, unconditionally:** `0x00954375-0x00954383` overwrite the member flag with the outer IsMember byte (also cached at `this+0x14`), and `0x0095437d`/`0x00954394`/`0x00954398` set MaxCharacters = `1 + 2 * (IsMember != 0)`. Only the payload's admin byte survives. Calls `(this+8)` slot 0 |
| `ClientAccountManager::OnAccountInfo` | `0x00719330` (vtable `0x017e7ccc` slot 0) | Status 1: copies the three dwords to `+0x22280/+0x22284/+0x22288` and logs them |
| `GetMaxCharacters` | `ScriptsBase.lua:16204-16222` | "Add a Character" opens the creator only when MaxCharacters `> 1` (it does not compare with the current count) |

The XML/TCP path (`0x00fa97d0`, "LoginReply" → `0x00fa0920`) reaches the same `0x009542d0`, so it is capped too.
The character-list callback `0x00719550` does not touch `+0x22284`. So the client shows **1 for a non-member and
3 for a member, whatever the server sends**; 6 is unreachable with the stock client. (IDA wins over the
`Research/Game Rules and Membership.md` row, which reads the callback values as server-supplied.)

The server bug: `login_reply_fields` wrote the outer IsMember byte as a constant `0` and put membership only in
the payload, which the client overwrites. So even an account flagged `membership: true` reached the client as a
non-member with a 1-character cap and no member UI.

## What changed

- `src/login.rs` `login_reply_fields`: the outer IsMember byte (offset 6) is now `u8::from(membership)`, the
  same value as the payload's member byte (`MembershipState::new(membership, None)` is active iff `membership`).
  Comment cites `0x00fa40e0` and `0x009542d0`. The payload (member, max, admin) is unchanged. `login_reply(false)`
  still passes `false`, so failed logins are byte-identical to before.
- `tests/login.rs`: `login_reply_with_max_characters` takes the member flag; new
  `login_reply_carries_account_membership_in_the_byte_the_client_reads`, which drives `LoginService::handle`
  (opcode 1) for a member and a non-member account, pins the exact reply bytes, and models what the client
  stores (`client_account_info`, reader-derived from the addresses above): member → (member, 3, not admin),
  non-member → (not member, 1, not admin). It also checks a refused login and that the store file is unchanged.

Effect today: none for existing accounts, because every account is created with `AccountFlags::default()`
(`osfr-account create`, `LoginService::authenticate_account`), so `membership` is false and the client keeps
showing 1. A member account now shows 3 and can open the creator; the server still enforces
`slots.max_characters` (6) at create (`account_store.rs:328`, status 6 TooManyCharacters).

## Question for the owner (decision needed for the playtest flow)

A second character per account in the real client needs the account to be a **member** (client then shows 3, not
6). Options: (a) make new accounts members by default (the 2014 final era, when membership was free for everyone;
also the Legacy reference's `MemberByDefault ?? true`). In-game member gates (member items, quest limit) read
game-state `+0x464`, which the membership activation message (opcode 100) sets, not this login flag, so (a) for
the login reply alone changes the creator's slot count and the account-info member column; (b) an operator command to set membership per account; (c) keep everyone
a non-member (one character each). The brief forbids flipping membership without a lead decision, so this change
does not. Also decide whether `slots.max_characters` should drop to 3 so the client's number and the server's
cap agree (today the client says 3 but the server allows 6; Lua only checks `> 1`). The native check in the
brief ("maximum of 6") cannot pass with any server change.

## Security

Threat note (secure-code-guardian, security-reviewer):

- **Trust boundary: login reply (server → client).** The only new datum is the authenticated account's own
  membership flag, already present in the payload since before this change. It is written only on the success
  path (`login_reply_for_account(true, account.flags.membership, ...)` after `authenticate_account`).
- **No membership oracle.** A wrong login name (direct path) or a failed broker token redeem
  (`bin/osfr-login.rs` → `login::login_reply(false)`) gets `login_reply_fields(false, false, 1)`: no account is
  looked up and byte 6 stays 0. The test asserts a refused login against a store holding a member account gives
  (not member, 1, not admin) and LoggedIn 0; canary 2 (failure path passes `true`) makes it fail.
- **Hostile client input.** No client-controlled value is read or stored by this change; the login request
  parse (`r.string`, `r.end`) is untouched. The client cannot set its own membership: the flag comes from the
  server-side account store only.
- **Saves.** Nothing is written: login of an existing account does not save the store (test compares the
  store file bytes before and after). No new log lines; nothing secret logged.
- **Not a privilege grant.** The client's member flag gates client UI only; server-side checks
  (`GameRuleSet::may`, slot cap) still use the account store.
