## Corrections to the first pass (rounds 1-3 review items)

- 00407283: the loop repeats **while** slot +8 returns 0 and returns 1 on the first
  non-zero result; the earlier text had the direction inverted.
- 00409999: returns 0x4011 when +0x78 == 0 and **0x411** (0xFFFFC400 + 0x4011
  truncated) otherwise - not 0x11.
- 004098b1 and 00407c19: both failure branches end with `xor al,al`; the functions
  return false (AL=0) when the candidate is null or its slot +0x20 reports a zero low
  byte. Ghidra's `in_EAX & 0xffffff00` is stale upper EAX.
- 00409165: compares the 16-bit key at **+0x0C** (not the low word of +0x10); its
  tail-jump target is slot +4.
- 00407b11: sentinel-valued buckets are restamped to 0xffffffb0 and chains hanging from
  real (<0xffffff88) links are freed; the loop shapes are partly lost behind the
  noreturn _free, so the record is deliberately speculative.
- 00406ff2: the manager slot +0xD0 call is *possibly* a release; caller 0041e189 tears
  this handle family down through +0xA0, so the record is speculative.
- 00406fc6: the block it zeroes is the 0x18-byte handle cache of 0041e189
  (provider-handle refresh), not hit-test state.
- 00408311: the +0xEC getter is not tied to the +0xEC flag that 0040817d tests on its
  +0x24 target; that linkage was removed.
- 0040af80 / 0040afca: the object code passes **ECX = param_1+4** to FUN_004c920b /
  FUN_004fed0f (invisible in the pseudocode).
- S0001 wording: FUN_004d9207 is a size-taking allocator, not an object lookup -
  verified directly here via FUN_004dbcb6 (S0046), which calls
  `FUN_004d9207(count << 4)` and then `_memcpy`s count*16 bytes into the result.
- 004074c6 / 00407527 / 00407588: the "reset/clear" reading was wrong - the object code
  switches the receiver by the first stack argument (0 selects this, 1 selects this+0x1C,
  2 selects this+0x38) and hands the second stack argument (the source record) to the
  selected record plus the other two. Raw bytes confirm this for all three functions; the
  previously recorded 0/1 mapping was inverted and is corrected here.
- FUN_004e4e15 is a string clone-assign (destination in ECX, source as argument,
  length -1 = whole source; an empty source stores the sentinel 0x01BC7E28), and
  FUN_004d83ba destroys such a string. Records that had read FUN_004e4e15 as a release
  were corrected: 00407dde (copies temporaries, destroys through FUN_004d83ba), 00407faa
  (clone of this+0x10 into a stack temp, temp destroyed afterwards) and 00408045 (clones
  the selected source INTO *param_2; param_2 is the destination and is written through).
- 00407faa also had the +0x30 gate on the wrong object: the object code reads it from the
  receiver itself (`local_6 = (**(code **)(*param_1 + 0x30))();`), not from the slot +8
  target (repair 3).
- 00409b56: polarity inverted - it returns 0 when all six dwords of the record pairs match
  and both AdjustEntryCounters runs return 0, and 1 when the pairs mismatch or either run
  returns non-zero (repair 3).
- 00409025: release order corrected - slot +0x90 dispatch, then the stack record's
  container release (FUN_004c9f6e), then the GInterface::vftable rewrite, then the
  materialized caller record's release (repair 3).
- 004090b4: 004093c3 is not a variant of the 0x175d240 pair; it builds 0x175c44c ->
  0x175d358 and belongs with 0040a66d.
- 0040982b: its two callers feed the returned static into +0x48/+0x4C property writes
  paired with the LayoutSpacing literal (00609f1c gates on ReadBaseControlProperties,
  00609f66 on StoreControlProperties) - no compare site exists in the map; downgraded to

- 0040ab41: the released container is at +4 (`lea ecx,[esi+4]`), not at +0.
- 00407308: the FUN_00405193 receiver is the caller's record (destination); this+0x78 is
