# T104 Group invite expiry

## What changed

- `src/social_lists.rs`: pending group invites now retain their monotonic
  `created_ms`. `expire_group_invites(now_ms)` removes a row at 60,000 ms and
  above. It emits no packet because the recovered family-40 wire has no group
  invite-timeout notice.
- `invite_to_group` and `respond_group_invite` take the caller's `now_ms`, run
  expiry first, and therefore cannot use a stale row for capacity or acceptance.
  A late accept follows the existing 40/5 result 3 "not invited" path.
- `src/bin/osfr-gateway.rs`: the existing `Session::tick -> tick_at ->
  commit_outcome` maintenance path calls expiry with the same monotonic clock
  already passed to `TradeService::maintain`. Invite and accept routing also
  pass that clock into the social service.
- `tests/group_invite_expiry.rs`: adds the 59,999 ms boundary, expired capacity
  release/refusal/re-invite, and membership/social-save preservation tests.
- `src/bin/osfr-gateway.rs` tests: `gateway_tick_expires_an_idle_invite` drives
  the real session tick past the deadline without sending an accept.

No application selector was added, so no new `app_fuzz` seed is required.

## Reconstructed rules

- (R) An unanswered group invite reserves group capacity for at most 60,000 ms
  of server monotonic time. The 59,999 ms boundary remains valid; 60,000 ms
  expires it.
- (R) Expiry only removes the pending row. It does not disband the group,
  change membership, move either character, write social persistence, or spend
  action budget. Pending invites remain volatile and are never saved.
- (R) Expiry is silent. A later accept receives the existing 40/5 code 3
  refusal; no group timeout opcode or extra wire field is invented.

The client guide records group pop-ups in the 300 s GAQ class and a 60 s
visible window. The 60,000 ms server reservation deadline is our reconstructed
server policy.
