## Security Note

A hostile client can send 26/24 with any i32 recipe id, a truncated or longer
body, repeated requests, or a completed movie sequence after a placement reload
moves or removes the station. Each one is refused before state changes:

- `decode` accepts exactly eight bytes; any other length is a rejected packet.
- The client supplies only the recipe id. Learned state, active job, rank,
  exact owned ingredients, station proximity and idle services are server
  facts in `recipe_book::start`; a missing service is `Unavailable`, not a
  panic.
- The start handler checks `Gameplay::activity_busy()` (the shared occupation
  `start` gate) first, and `recipe_book::start` re-checks `in_activity` and all
  three services. Replaying the start while a run is live returns `Busy` before
  any service, inventory or station mutation; a session handles one request at
  a time, so the checks cannot interleave.
- `GameWon` derives the transaction from the server recipe table after four
  validated rounds; the reported quantity is bounded but never used for the
  grant. A duplicate `GameWon` returns no transaction.
- Completion re-checks the active job and a station resolved from the current
  opening actors and placement models. If a reload moved or removed the
  station, `apply_smelting` returns `Err` before consuming or granting; the
  gateway discards its staged clone, so the snapshot is unchanged and neither
  save flag is set (new test and canary below).
- Refusals carry only the existing chat feedback; they do not touch inventory,
  coins, attempts, completions, cooldowns or placements.
