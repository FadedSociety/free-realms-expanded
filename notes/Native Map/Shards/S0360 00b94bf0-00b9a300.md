# Shard S0360 findings (00b94bf0..00b9a300, 148 functions)

Read-only pass over the native-map Ghidra export with `nmq`. Every record in
`out.jsonl` carries its own anchors; this note is the narrative that spans
functions. Byte-level claims were checked with a capstone decode of `nmq bytes`

## Cross-function findings

**Chat channel numbering is corroborated for 0, 4 and 9.** The subtype-3
switch in `00b966e0` dispatches the channel word to handlers whose own string
literals name the channels: case 0 -> `00b0fad0` (WorldSay), 4 -> `00b10070`
(GroupSay), 6 -> `00b0fcb0` (WorldTrade), 7 -> `00b0fda0` (WorldLfg), 8 ->
`00b0ff80` (WorldArea), 9 -> `00b10160` (GuildSay) and 10 -> `00b0fe90`
(WorldMembersOnly). Combined with the community enum that
`Research/Pieces/088 Chat channels.md` records, this pins group 4 and guild 9
as well, not only the four toggle numbers (`00b978b0` maps WorldArea 8,
WorldTrade 6, WorldLfg 7, WorldMembersOnly 10).

**Two quick-chat send paths, each with its own serializer.**
`00b97100` serializes through `00b96f80` (base fields `00b96d40` plus the u16
at `+0xa0`, the dword at `+0xa4` and `+0xa8`) and is used by the channel
setters `00b97380` (channel 0), `00b97480` (4) and `00b97580` (9 with two
extra dwords) and by the toggle `00b978b0`; all four construct a
`QuickChatSendChatToChannelPacket` through `00b90a10`. `00b97210` serializes

and then fires the script event `ChatLog:EchoWhisperFromQuickChat`. Both
helpers end in the shared gateway send `FUN_00925640`; `FUN_00894560` is only
the 8KB buffer destructor, not a send.

**Point-of-interest reply framing.** `00b98b70` (the op-57 handler, called from

## Contradiction with an existing note

`Research/Kart Entry Register Prerequisites.md` shows the 33/9 register block
with `FUN_00b997a0(); // send`. The body of `00b997a0` is a destructor (it only
rewinds `BaseVehicleRacePacket::vftable` and `BasePacket::vftable`); the actual
send in that block is `FUN_00ba4420` (its callee list carries
`ClientGateway::BasePacket::vftable`, and it is guarded by
`[client+0x280] != 0`). The note's block then destroys the temporary with
`00b997a0` after `local_4 = 0xffffffff`, which is the normal scope exit. The
note's conclusion (register is a processor-start action) is unaffected; only
the "send" label on `FUN_00b997a0` is wrong.

## Open questions

* Six destructor emissions in the family (`00b996b0`, `00b99700`,
  `00b99940`, `00b99a40`, `00b99bf0`, `00b9a300`) are reached only from EH
  cleanup funclets, so the derived class each cleans up cannot be proven from
  the body. They are named for the base class with suffix letters.
* The two extra dwords `00b97580` (channel 9) stores into its packet are not
  recovered.
* Whether the op-57 body carries a length prefix in front of the record stream
  is still unproven (no 56/57 frame exists in the preserved captures); this
  shard only proves the i32 length field the handler reads.
* The header writer `00b950a0`, the base serializer `00b96d40` and the send
  helpers `00b97100`/`00b97210`/`00b98ec0`/`00b99000` take the opcode from the
  packet object header, so no opcode constant exists in those bodies; wire
  claims there rest on the callers that build the packet classes.
