## 1. MiniGameBossDataSource and its Entry array (00c48300..00c48f40)

source name **"MiniGame.Bosses"**, keeps an id-to-name lookup service pointer at +0x254 and an

00c48ea0 reads +0x230; the value accessor 00c488d0, vtable slot 4 of 01831ff8, reads
row*0x20 + [this+0x22c] + 0x18 and returns the name for column 0, the float for column 1). In the
insert branch of 00c48bd0, the new entry gets key/id/name, then writes the key (`param_2`) at +0x18;
`param_4` is unused on insert. The update branch writes `param_4` to +0x18. This code-level
discrepancy is verified; its intended meaning is unknown.

The receive path is `HandleMiniGameBossMessage` 00c48c90: it builds a local base packet through
00c47db0 and branches on the inner type word - 1 reads fields through 00c48620 and applies
00c48bd0; 2 reads a key through 00c48b60 and applies 00c489b0. Its caller 009bfea0 is the

semantics are client-side parsing evidence, not original server implementation evidence.

those earlier labels were over-specific. The accessor field mapping in 00c48f60 remains supporting

Note the layout collision worth review: for ActionBarDataSource +0x254 is an **embedded

## Cross-shard / server-contract hypotheses (all labelled as such in the records)

- Client code sends invite (175/20), invite response (175/17), ready/quit (175/18/19), owner launch
  or matchmaking requests (175/22/23), and a kick-member request (175/21). It parses the other
  listed subtypes through receive handlers. This direction split is consistent with server-authored
  group state, but the original server is unavailable, so server ownership remains a hypothesis.
  Parsed subtypes are 175/1,2,3,4,5,7,8,9,13,14,15,16. The body of sent requests is a 16-bit value
  plus three 32-bit values (writer 00c4cd20); field meanings remain unknown, and the pinned corpus
  has no 175 capture.
- The dispatcher handles sub-opcode 4 (PlayerHasBeenAccepted), and 00c4c240 also constructs that
  class while parsing an input buffer. Whether it relays or responds to that input is unresolved.
- Sub-opcode 6 (ActivityCanceled per note 020) has no constructor and no dispatcher branch in this
  range, so the shard cannot confirm that row of the vocabulary.

## Unresolved / risks

- The eleven base-vtable cleanup functions 00c49680..00c49d90 only store `BasePacket::vftable`
  and return. EH callers establish cleanup use, but no derived packet class is provable from these
  bodies or caller list. They use neutral address-suffixed names and `net.packet`; do not bind them
  to adjacent constructors without funclet ownership evidence.
- MiniGameBossDataSource carries **two** 0x20-byte-element arrays (+0x22c rows consumed by the UI
  accessors, +0x258 entries maintained by the message path). Which one the ageing pass 00c48930 and
  the clear 00c48700 operate on was resolved by offsets (they use +0x25c/+0x260), but why the UI
  copy exists is unknown.
- The ring buffer at 00c49440/00c49460/00c494b0/00c49500 (0x10-byte elements, overflow counter at
  +0x24, callers in the 009c0xxx region) has no identified owner class.
- `SetField278AndNotify` 00c49000 is placed in `ui.actionbar` because the field it writes is
  initialised by the ActionBar data source constructor, but its two callers are generic client UI
  code, so the class binding stays unproven (class null in the record). The 00c4bd60 wrapper parses
  a header and counted 64-bit-pair list, but has no recorded caller or opcode; its ActivityLaunched
  identity is only a structural hypothesis, not a mapped packet identity.
