## Client evidence

- Native toolbar populate `0x008ee3d0`: loops every toolbar row. For a filled row it takes
  `v4[3]` (the name id) through the string table and calls `sub_9CF920(row, name, icon, ...)`;
  an empty row calls `sub_9CF920(row, "[empty]", 0, 0, 0)`. `sub_9CF920` is
  `HandlerActionBar:setButtonData`.
- Toolbar slot reader `0x008e6760`: kind dword first; kinds 1/3 read definition id and energy
  then icon (field 2), name (field 3), fields 5/6; kind 0 consumes only its dword. The
  `ability_entry` layout is unchanged: 36/5 basic entry name is the 5th dword (packet offset
  +16 from the entry start, toolbar offset 28).
- Item definition reader `0x008e3760`: class at definition +32 / slot at +40, i.e. +44/+52
  in a 35/34 reply row. Both the cast gate and the label use those offsets through
  `Inventory::equipped_weapon_for_class`.
- `ScriptsBase.lua:5211-5244` (`setButtonData`): the displayed name comes from the ActionBar
  data source; only the icon is replaced, and only when the icon id is 3938. `5168-5196`
  (`PopulateActionBar`) draws rows whose `Assigned` is 1. `52170-52178`
  (`RequestWeaponAbilities`) reads the currently equipped item id and serializes
  `BaseClient.ItemAbilities`; it does not grey out or hide an ability whose weapon is
  missing. So the server must send the empty bar while unarmed (OSFR #124 reference).
- `piece_014.rs:427-429` lists recovered row 75030 as class 25, but the shipped reference
  content's serialized bytes put class 71 at the gate offsets and `tests/job_basic_attacks`
  casts with 75030 as class 71. The code follows the live definition bytes (the same bytes
  the cast gate reads), not the recovered list.

## Sell / consume / trade check

Only the 42/2, 42/3 and 42/8 requests can change the active profile's slot 7. 42/8 resolves
its definition/tint to an owned instance and goes through the same `Inventory::equip`, so the
same branch and resend cover it; `unarmed_bar_is_empty_and_rearm_restores_it` re-arms the
starter through 42/8.

- Vendor sell refuses any item instance that is equipped (`coin_shop.rs:791-808`,
  `RESULT_SERVICE_UNAVAILABLE`), and only calls `Inventory::consume` after that check.
- Trade refuses an equipped item (`trade.rs:1227-1232`), so a trade commit cannot remove
  the equipped weapon.
- No production item-use path targets a weapon (`item_bar` items, crafting materials, pet
  items, style cards); `Inventory::consume` would unequip, but nothing reachable consumes a
  slot-7 weapon.

Therefore no sell/consume hook or test is needed: the sell path refuses an equipped instance
before it reaches `consume`, and trade refuses equipped items, so neither can unequip the
active weapon.

## Security threat note (secure-code-guardian)

- A hostile client can send 42/2, 42/3 and 42/8 with arbitrary slot, profile and item ids,
  then look for a 36/5. Before any bytes are added, the existing inventory router validates
  message length, the family/opcode, item ownership and count, the content profile and slot,
  the definition slot/class, the unlocked profile, rank, gender and membership. A refused
  equip returns the existing chat refusal and commits nothing (the test snapshots
  `GameState` and asserts equality). The resend only reads the committed state and
  server-owned content tables; the client never supplies a name id or a definition id for
  the label. Replies are bounded by the loaded roster (one basic, at most three job rows and
  one power-up; 160-byte definitions plus one 36/5), and the account action budget gates the
  request rate. No snapshot is restored, no item or coin is touched, and a request for
  another job's outfit does not relabel the active bar.
