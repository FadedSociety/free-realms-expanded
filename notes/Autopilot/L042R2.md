## Security

Threat note (secure-code-guardian, security-reviewer). Every boundary the resolution touches:

- **Staff chat -> post-commit actions (hub).** A hostile client controls the chat text. `realm move` is
  admin-only in the role table (`can_run_realm_command`: unknown words are admin-only; the moderator arm
  lists the five moderation words only), and the moderation words are role-gated in `staff_command` before
  the name is parsed. Both are staged on the transaction's outcome and taken before `commit_outcome`; they
  run only when the commit succeeded, so a refused or failed transaction changes nothing. Neither reads an
  id from the packet: the actor is the session's verified `account_guid` (moderation) or the session itself
  (move).
- **Audit rows (security log).** One `append` with the size cap and rotation for all three row kinds, so no
  row kind can grow the log past its cap or skip rotation. Rows carry ids, closed action names, minutes,
  zone and position only; no name, chat or command text (key sets asserted for both unbatched kinds). A
  `moderation_action` kind arriving through the deserialisable `SecurityEvent` is refused by `record` and
  writes nothing, so it cannot be batched under another actor.
- **Store lock (osfr-account footer).** "Login may keep running" stays true: every writer, `member`
  included, takes `AccountStoreLock` for one load-modify-save, and login holds it only for its own saves.
  A busy store refuses with nothing written.
- **No new oracle.** Replies are unchanged from L042 and L043; the merge adds no message.
- **Saves stay atomic.** No new write path: the account store saves through `AccountStore::save`
  (`replace_bytes`), L043's offline move through `game_store::replace_pose`.
