- Constructor `008b3b70` (decompiled): `[this+4] = 0xA4` (164), GUID
  `+8/+0xc`, constant 4-float blocks at `+0x10`/`+0x20`, `+0x30/+0x31 = 0`,
  `+0x34 = 0`.
- Writer `009127f0` (decompiled): 2 bytes, `sub_8fb810(&this+8)` (u64), f32
  `+0x10/0x14/0x18`, f32 `+0x20/0x24/0x28`, bytes `+0x30/+0x31`, 4 bytes
  `+0x34`; `+0x1c` and `+0x2c` are never written - exactly 40 bytes.
- Reader `008e5ba0` (decompiled): int16, 8 bytes, three floats into
  `+0x10/0x14/0x18`, three floats into `+0x20/0x24/0x28`, two bytes into
  `+0x30/+0x31`, dword into `+0x34`; `+0x1c` and `+0x2c` are wire-absent
  constants (1.0 and 0.0).
- Handler `0090e470` (disassembly; IDA does not define this body as a
  function): constructs, reads, refuses a short body or trailing bytes, looks
  the actor up by the 8-byte id (`sub_984960`), refuses a missing actor or the
  local player (`[edi+0xc8]`), then applies the motion.
- Sender `0092e670` (decompiled): stamps the local actor id at `+8`, the local
  position `+0x10..+0x1c`, direction `+0x20..+0x2c`, state/unknown
  `+0x30/+0x31`, velocity `+0x34` from the local character (`+0x674`).
- Legacy reference (behavior only, no code copied):
  `PlayerUpdatePacketJump.cs`/handler rebind the GUID to the authenticated
  player and send to visible players.

The 125-vs-164 split is D09's finding and was not re-verified by T008; this
implementation depends only on the 164 evidence above.

## Security threat note (secure-code-guardian)

A hostile client can send: a body with another actor's GUID (refused: `decode`
compares it with the session's character GUID; the relay body always uses the
server-loaded GUID); 39/41-byte or truncated bodies (refused: exact length and
the outer reader's end check); NaN/Inf or >1,000,000 positions/directions
(refused); NaN/Inf or >10,000 velocity (refused); a valid jump faster than the
client would send (the pose still passes the 125 speed envelope, and the
observer broadcast is capped at one per 100 ms per session); or a jump to make
observers see motion (the recipient set comes from the server registry's
directed views plus `knows_character`, not from the packet; the sender never
receives its own relay). Refusals are returned before any staging, so no
menu, offer, counter, item or cooldown changes, and a refused jump does not
consume the relay window (tested). The window is in-memory session state,
dropped on leave. Per request the cost is an `Option` check; only an accepted
164 allocates one 40-byte body and does one bounded nearby/visibility query,
and the throttle is checked before the fanout. No secrets, names or chat text
are involved. The app-fuzz seed uses a foreign GUID so every mutation
exercises an atomic refusal; matching-GUID bounds are pinned by the unit tests
and the real-dispatch refusal loop.

## Open gaps

- No native two-client acceptance: whether observers animate the relayed jump,
  and collision/gravity, is client behavior and was not run here.
- The 100 ms window and the 10,000 velocity guard are reconstructed (R);
  there is no movement-policy content table (the 125 speed envelope is also
  compiled and documented (R)), so they are flagged rather than inventing one.
- The strict body-GUID equality assumes the client's actor id equals the
  server-loaded character GUID (what self data and AddPc send). The body GUID
  is never trusted for routing; a future client with different actor ids would
  have its jumps refused by design.
- Two valid jumps in one bundle keep only the last body; both poses are
  validated and the final pose reaches observers through the 125 fanout.
- The 164 state/unknown bytes are relayed opaque; their meanings are only
  partly recovered.

## Checklist

1. **Refusal changes nothing.** Invalid 164s fail in `parse_message`/`decode`
   before staging. The real-dispatch test snapshots the gateway state and the
   relay window for foreign GUID, excess velocity, NaN position, Inf
   direction, out-of-bounds position, 39/41-byte bodies and a pre-Ready jump;
   each refusal returns `Err`, leaves the pose unchanged and sends no 164; an
   accepted jump 100 ms after the last relay still reaches the viewer, so the
   refused jumps consumed no window. The clamp is a correction, not a refusal. A
   refused jump never reaches `allow_jump`. Canaries 1-5 and 7 prove the
   refusal assertions can fail.
2. **Rollback covers all state.** The only new state is
   `PlayerRegistry::jump_ms`; `jump_fanout` mutates the existing
   `staged_world` clone inside the transaction and the clone is committed only
   on success. No `Rc`/`Arc`/side table escapes.
3. **Apply deltas.** The relay body is built from the freshly validated pose
   (`validated.state`), never from a captured snapshot; the registry applies
   the existing pose delta. A later committed child clears the pending body,
   so an older jump is never relayed over a newer pose (canary 8).
4. **Busy rules are mutual.** Jump is not an activity, adds no
   `Occupation` row, and is movement with the same gates as opcode 125, which
   is allowed during other activities. No busy table or caller changed.
5. **Every entry path is gated.** The only path is the tunneled client 164; it
   shares the 125 Ready/world-entry gate and `movement::validate`. Tests cover
   accepted (Ready), pre-Ready refusal, invalid bodies and clamp. There is no
   NPC/automatic/reconnect entry for a jump.
6. **Reachable in production, tested through it.** The binary test drives
   login -> Ready -> Loaded -> `dispatch_message` (164) through the real
   transaction, then decodes the bytes queued on the recipient's real SOE
   sender (`drain_replies`), including a real `[0,25]` bundle. The gateway
   refusals are exercised on the same session after accepted jumps.
7. **Survives reconnect.** The relay window is deliberately session state, not
   saved state; `leave` drops it and a rejoin starts fresh (test in
   `tests/players.rs`). No jump state needs to outlive the session.
8. **Every exit path restores the player.** No activity lifecycle, location
   change or stuck flag is added; a refused/clamped/throttled jump leaves the
   character free and the existing position rules in force.
9. **Economy safety.** No item, coin, reward, grant or client-reported outcome
   is involved. The only client quantities are validated pose floats and a
   bounded velocity.
10. **Wire format matches the reader exactly.** Reader `008e5ba0`, writer
    `009127f0` and constructor `008b3b70` are cited at the code; the unit test
    rebuilds the reader-derived 40-byte body byte-for-byte, and the
    real-dispatch test decodes the queued 164 body (opcode/GUID/position/
    velocity/state).
11. **Unique ids.** No instance/GUID allocator was added; the existing
    session-bound character GUID is used and a body naming another actor is
    refused.
12. **Others see changes.** The jump is broadcast only through the existing
    directed-visibility rule (`nearby_sessions` + `knows_character`) on the
    real fanout path; the three-session test asserts the directed viewer gets
    it, a near non-viewer and the sender do not, and the recipient decodes the
    wire body.
13. **Content works end to end.** This is a protocol feature with no content,
    NPC, quest or reward. The endpoint - an observer receives a decodable
    relay - is asserted.
14. **Values live in data.** The only new values are the (R) 100 ms relay
    window and the 10,000 velocity guard; no movement-policy content table
    exists (the 125 speed envelope is likewise compiled and documented (R)),
    so they are kept with that policy and flagged as an open gap instead of
    inventing a one-value content file.
15. **Canaries break production code.** Eight canaries edited production code
    (decode GUID, velocity, finite/bounds, exact length, throttle, directed
    filter, pending-body clear) and each failed its test with the real failure
    lines above; all were reverted and re-ran green.
16. **Hands off session plumbing.** The bin diff is one import and one fanout
    call in the existing commit stage; session creation, teardown,
    transactions and save ordering are untouched.
17. **One player's error never stops the server.** Decode/relay return `Err`
    for bad input; only that session's packet is refused. The fixed-size
    unwraps follow the exact-length check, arithmetic uses `saturating_sub`,
    and the fuzz corpus cuts/mutates the 164 seed and asserts no panic and no
    mutation.
18. **A type's rules live on the type.** `PlayerRegistry::jump_ms` is
    documented with its rule and cleanup; every `JumpUpdate` field documents
    whether it is untrusted, validated or opaque; `GatewayOutcome::jump` says
    a later child clears it; `allow_jump` documents that the caller checks
    registration and that the pose is committed regardless.
19. **Hot paths stay cheap.** Non-jump messages pay one `Option` check in
    `jump_fanout`; only an accepted 164 allocates a 40-byte body and does one
    bounded nearby/visibility query; the throttle runs before the fanout and
    the window is one map entry per jumping session, removed on leave. No new
    whole-state clone.
