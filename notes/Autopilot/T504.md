## Result

Every client card button ends in the 167/1/2 join of an activity id (`StartTutorial` `00c04970` joins `Tcg.ActivityId`,
default 1049.0; `StartTreasureWar` `00c049f0` joins `Scg.ActivityId`, default 1078.0, both confirmed in the decompile;
the sender `00be7d80` drops an id it was not given in the 167/1/1 list). The portal published only battles, chess and
soccer, so those buttons did nothing. Now:

- `data/content/card_game.json` carries the 17 rows (lobby 7, 14 decks, tutorial 1049, Treasure War 1078) with
  per-row `legacy-data` / `client` / `reconstructed` provenance.
- `src/card_game.rs` loads and validates it (size bound, `deny_unknown_fields`, unique nonzero ids, category 11 or 26,
  non-empty image names, tutorial id must be a row of the file). The file is optional, like `chess.json`.
- `Kind::CardGame { minigame_id }` rows go through the one row writer in `activity_portal.rs`; card rows read their
  wire values (app system id, category, image set, position, display ids, tutorial id, art, join flag) from their data
  row. Entry type is 1 for every row (R).
- Play on a card row is refused by `admit` after the Unknown and Busy checks: category 11 answers the client's own
  Global.Text 140987 line, Treasure War answers "Treasure War is not open yet." (R). No state change, no zone change.
- The catalogue is built in one function, `Catalogue::assemble` (battles, chess, soccer, cards; one validated
  `append`: unique nonzero ids, at most 64). Startup and `realm reload battles` both call it, so a reload no longer drops
  the soccer rows. The card content rides inside the catalogue (`Catalogue::cards()`), so a reload republishes it.

### ImageSetId 7591 (R, shipped)

`GetCell` col 6 hands `+0x14` raw to Lua (`addHorzItem_lua`, `ScriptsBase.lua:36914`) and the Flash consumer is not
reachable from the exe. Evidence for the table it indexes: across the Legacy rows (original server data) the value
names an `Images.txt` icon every time, and often has no `ImageSets.txt` row at all (combat 1345, fishing 21061,
soccer 1317 is a pine cone in `ImageSets.txt` but the soccer category icon in `Images.txt`, chess 7543, checkers
7540). 7591 is `icon_category_minigames_tradingcardgame_64.dds` in `Images.txt:5049`; `ImageSets.txt:6847` reuses the
number for a housing wall icon, which cannot be the intent. The brief said to ship 0 if the column indexed
`ImageSets.txt`; the evidence says it does not, so 7591 ships, tagged `reconstructed` on each row, and Treasure War
(no image set in Legacy) ships 0.

### Can Games > Trading Card Game show at all? (answer, not built)

`ActivityCategories.txt` rows 11 and 26 have CONTENT_ID 36. The loader `00be58f0` lists a row when
`flag == 0 || IsContentUnlocked(CONTENT_ID)` (`flag` = byte `+0xac` of an object at client `+0x18cbc`, setter not
traced; `010463c0` returns 1 for id 0 and otherwise reads an unlocked byte from a hash, logging "ContentPacks.log"
when the pack is unknown and returning locked). `ContentPacks.txt` row 36 "All TCG" is unlocked in the
LOCAL/MAIN/DEV/QA/TEST/STAGE/LIVE/INTL columns and locked in BBE/PS3QA/SCEQA/SCEMGMT/SCELIVE. Which column this client
reads is not traced, so whether the category shows on a stock client is (R); on the columns that unlock it, it shows.
No content-enable packet is invented. This is the one open question for a native check: if the Games window has no
Trading Card Game entry, look at `ClientConfig.ini` environment and `flag` first.

## Threat note

A hostile client can send 167/1/2 with any id, including a deck id, a forged id or a repeat storm. An unlisted id gets
the generic "not available" line, a listed card id gets the "unavailable" line, and in both cases nothing is read or
written beyond building one chat reply. The 12-byte length check in `parse` is unchanged. A malformed or oversized
`card_game.json` stops startup with an error (size cap 1 MiB, 32 rows, ASCII image names up to 64 bytes) instead of
publishing a bad list.
