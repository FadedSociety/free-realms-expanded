# T545 — admin-only `realm duel <minigame_id>` credit for the Card Duelist chain

Developer tool: one chat command credits a TYPE 16 card-duel result to the issuing character so
the Card Duelist quests can be proved end to end before the card service produces a result. The
command pays nothing; the quest's own 49/14 turn-in pays the cap and the job XP. The shipped
content keeps both quests disabled and the reachability producer pin is untouched.

This is attempt 2: the attempt-1 review (`lab/autopilot/reviews/pre-T545-a1.md`) is addressed
below, then the final shape, evidence and gates.

## Security threat note (secure-code-guardian)

Attack surface: one chat request, `realm duel <text>`, plus the existing quest packets.

- A Player or Builder sending it is refused by the existing `command_refusal` /
  `developer_command_denied` before dispatch (unknown `duel` key; `account_store.rs` unchanged):
  one chat line, `dev_command_denied`, byte-equal production save, no quest packet. Tested.
- An admin can send any u32. Missing, zero, non-decimal and extra arguments are usage refusals;
  a non-TYPE-16 id is refused against the **content** whitelist, so a hostile or mistaken client
  cannot credit kart 18, derby 39 or Treasure War 727, and cannot credit another player (there
  is no target argument). Tested.
- The command cannot fabricate rewards: it emits only `FinishMinigame`; coins, 51187 and XP are
  paid by the existing 49/14 path from quest data through the checked `rewards::apply_grant`.
  A replayed 49/14 pays nothing and the second `duel 507` changes nothing. Tested.
- Ordered quests still gate the event: `duel 668` before meeting Esther advances nothing
  (the engine credits only the open step). Tested.
- No client quantity is trusted; the id is parsed as `u32` and bounded by the 1024-row list,
  so there is no overflow or allocation from the input. No secret, key, account data or
  absolute path is in the diff.

## Checklist

1. **Refusal changes nothing.** `only_an_admin_can_credit_a_duel` (Player, Builder) and
   `non_duel_ids_are_refused_and_change_nothing` (0, abc, 18, 39, 727, u32::MAX, missing/extra
   argument) snapshot the production save bytes (`Fixture::saved_bytes`) first, then assert
   byte equality, no `changed`, no 49/x packet and no objective move. Canaries 1/2 break
   production and fail. The command emits no event on any refusal.
2. **Rollback covers all state.** No new transaction or shared state; the whitelist refusal
   returns before any mutation, and the gateway's existing staged-clone commit covers the
   success path. No `Rc`/`RefCell`/`Arc` side table.
3. **Apply deltas, never restore snapshots.** Pay-out stays in `quest_engine::finish_turnin` ->
   `rewards::apply_grant`; the Poe test asserts the cap, `+300` profile-120 XP and unchanged
   coins, and a replayed 49/14 pays nothing.
4. **Busy rules are mutual.** The command starts no activity and opens/closes no activity
   state; no `Occupation` variant is added or bypassed. `spine_rules` and the occupation pin
   test pass.
5. **Every entry path is gated.** Admin-only on both `handle_in_world_inner` and
   `handle_opening_inner` (the `may_run` check precedes `developer_cheat`); the test drives the
   production `handle_in_world` dispatch. No NPC menu or automatic path was added.
6. **Reachable in production, tested through it.** The suite walks the real 26/8 -> 26/10 ->
   26/6 offer, 49/2 accept, 49/13/49/14 turn-in and the real chat request; the shipped-content
   test binds the shipped split catalogue to the real realm dispatch. No internals are called
   to fake the credit.
7. **Survives reconnect.** `Fixture::save_and_reload` (the production `game_store` envelope and
   `load_or_create` then the split-catalogue bind) between the credit and the turn-in keeps the
   completed objective; a second round trip after the turn-in keeps Completed, the cap and the
   XP.
8. **Every exit path restores the player.** The command has no lock, timer or location change;
   refusals leave the open menu and state untouched, and the turn-in completes through the
   existing path that clears `pending_turnin` (the replay is refused).
9. **Economy safety.** The command grants no coins, XP or items; the only reward is the quest's
   existing 49/14 grant from server-side data. The test asserts exactly one cap, unchanged coins
   on the Poe reward, `+3` coins on Esther, and nothing on replays. No client quantity is used.
10. **Wire format.** No wire change; TYPE 16 is content data and the event is server-internal.
    The test uses the existing reader-derived packet helpers (`tests/support/npc_quest_chain.rs`),
    and the client table header is cited above.
11. **Unique ids.** No instance or lifecycle id is created; the cap grant uses the existing
    inventory allocator. Public-world instances are untouched. N/A.
12. **Others see changes.** Quest state is per-character; nothing visible to other players
    changes. `a_credit_touches_only_the_issuing_character` proves the second player's saved
    character is byte-equal. N/A.
13. **Content works end to end.** Both chain tests assert the final `Completed` status, the
    objective completion, the cap and the exact coin/XP outcome; the Esther test asserts no
    item.
14. **Values live in data.** The TYPE 16 whitelist is in `card_game.json` and its bound/source
    are validated there; no compiled id list. The quest XP/coins/item ids remain quest data.
15. **Canaries break production code.** The three canaries edited `credit_card_duel` and
    `card_game.json`; real tests failed (see the test section) and each edit was restored and
    rerun green.
16. **Hands off session plumbing.** No change to `bin/osfr-gateway.rs`, `gateway.rs`, session
    creation/teardown, transactions or save ordering.
17. **One player's error never stops the server.** No shared-tick or other-player code changed;
    parse failures are usage refusals and the `?` on the event path is a per-request error the
    gateway rejects for that application, not a tick exit. The two-player test keeps the other
    session unchanged.
18. **A type's rules live on the type.** `Content::validate` owns the list/source pairing,
    empty-file compatibility, sorted/unique/zero/oversized and client-provenance rules, and
    `Content::is_duel_row` owns the lookup, with the field docs stating the list is sorted and

19. **Hot paths stay cheap.** Admin chat only: no tick, movement or per-packet path added.
