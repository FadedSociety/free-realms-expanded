# S0005 (00414a48-00419846) - findings

179 functions mapped; `validate.py` reports `valid_records=179 errors=0`.
This is the **GFC client-framework mid-block** (data-access wrappers, box-layout
state, a dense MSVC template/STL emission block, control-base routines). No
packet code exists in this range: no opcode constants, no `net.*` callees, so
every record has empty `wire` and no server inference.

## 1. GDataAccessWrapper virtual family (00414a48-00414f29, 00415038-004150b3)

Eleven adjacent functions are the first 14 slots of **one unnamed vtable at
0x175dc60**: 00414e1d(0), 00414f29(1), 0xd83a6d(2), 0x41b3b3(3), 00414b4f(4),
00414ad7(5), 00414a48(6), 00414952 `GetOwner`(7), 0x41b41f(8), 00414bcb(9),
00414cbf(10), 00414d77(11), 00414dd0(12), 00414f07(13). Slot 7 is a
Ghidra-named `GDataAccessWrapper::GetOwner` (S0004, mangled comment), and the
identical 14 slots head the RTTI-named `GStringAccessWrapper` (0x17f29b4) and
`GBitmapAccessWrapper` (0x17f2a0c) vtables - so the 0x175dc60 class is the
GDataAccessWrapper base.

Layout recovered from the bodies: `+0 = vptr`, `+8 = GDataAccess*`,
`+0xC = 16-bit GPropertyId`, `+0x10 = owner GObject*`, `+0x14..+0x24 = typed
value descriptor` (kind 0 = empty, kind 1 = owner + four words, kind 2 = owner
+ one word). The load/save pair writes the binding into a data node named
`GDataAccessWrapper` with either `Access` (owner object) or `Id` (numeric id)
- both literals are quoted in 00414cbf/00414bcb - and 00414d77 copies bindings
between wrappers. 00414e1d re-pushes the recorded descriptor to a data access
through its slots +0x58/+0x5C when the access is (re)attached, i.e. the
descriptor is the wrapper's cached value, not packet data.

`GStringAccessWrapper` concrete members: ctor 004184f4 (writes the
`GStringAccessWrapper::vftable`, runs the GDataAccessWrapper ctor 0041493a),
dtor body 00418581, and the slot 18/19 forwarders 00415038/0041505a (forward to
access slots +0x6C/+0x68). `GBitmapAccessWrapper` overrides the same slots with
0041507f/0041508e (slots +0x78/+0x90). A second data-access class (vtable
0x175ec58, unnamed) has the value fetch/store pair 004150b3/0041512f at slots
37/38, using the same context guard helpers 004c88d5/004cd10a as the wrapper.

## 2. Value-class dispatch and layout state (00414fa0-004165ef)

00414fa0 is a six-mode message switch (in-place init / copy-init / allocate+init
/ allocate+copy / destroy / deleting destroy) for the 0x18-byte two-vtable value
class used by the data-access family (vtables 0x175d240/0x175d23c; copy-init
00409180 is also called by GStringAccess code at 00435394).

The layout objects expose their state through named attributes read/written with
paired loaders/storers: `Flags` (+0x10), `HStretch`/`VStretch` (+0x16/+0x17)
(004154e7 / 004155a8), `ControlName`/`FixedSize` (+0x48/+0x4C) (004159a4 /
00415a37), `SpacerSizeId`/`SpacerSize`/`SpacerType` (+0x48/+0x4C/+0x44, default
`Horizontal` block PTR_s_Horizontal_01af4ddc) (00415b66 / 00415c22),
`UseSeparator`/`Separator`/`SeparatorId`/`UseOuterMargin`/`OuterMargin`/
`OuterMarginId`/`Direction` (00416099), `StackType`/`ItemIndex` (004165ef), and
`Items` + per-item `ItemClass`/`ItemData` bindings (00415e55 -> 004153b9, with
004152c2 as the instantiate-and-bind counterpart). `GSize` values are resolved
by 0041588c/0041593b through a global object's slot +0x18 with a type check
against the `c GSize` type-name string. The glue: 0041588c's resolved pair feeds
00415b23; 004154e7's flags feed every loader.

Stretch/layout maths: 00415cfe and 004161ea compute the 0x80000/0x800000
stretch mask from the object's own flags plus its children (004161ea honours the
StackType==2 start index); 00416315 computes the minimum size pair; 00416463
arranges children (calls 004156b2 per child); 00415f75 translates the subtree
rect by (dx,dy); 004155fe serves cached min/max pairs (lazy-refresh bit 0x200)
through the static byte map PTR_FUN_01af522c; 004156b2 aligns a child rect using
own slot +0x2C alignment bits (low nibble 2..6, high nibble 0x20..0x60);
0041836e intersects rectangles with the (0,0,-1,-1) empty convention.

External RTTI in FreeRealms.exe names `GVBoxLayout` (0x17f2f04) and `GHBoxLayout`
(0x17fce64), whose vtables carry 00415280/0041528b/0041529e and share the
layout slots used above; the neighbouring vtables 0x175ee28/0x175ee80/
0x175eed8/0x175ef60/0x175efe8 (vbox/hbox/stack variants) are unnamed in the
export. 00415280/0041528b are linker-folded adjustor thunks (call through the
interface pointer at +0xC with this+4). 0041529e and 00418c05 are different
folded thunks, proved at byte level in review: 0041529e (83 C1 04 E9 ..) adds 4
to ecx and tail-jumps to 004c9e83, and 00418c05 (81 C1 A8 01 00 00 E9 ..) adds
0x1A8 before tail-jumping to 00412c48 - neither is a call-and-return wrapper,
and the receiver adjustment is the state they pass on.

## 3. Template/STL emission block (00416893-00418250)

A dense block of MSVC template code for the client's own containers plus
std::basic_string: `_Rb_tree` lower_bound/upper_bound in 16- and 32-bit-key
variants and at least six node layouts (the byte the walks stop on is the
nil/sentinel flag, at +0x11, +0x19, +0x1D, +0x31 and +0xF; the colour byte
sits at the preceding offset), tree rotations (00416bda/00416c1c/00416d3e/
00416d80/0041704f/004170fe/004171ad/004171ef), header-node allocation
(00417091/00417140), node construction with key copy (0041760b/0041763e/
00417671 store _Left/_Parent/_Right at +0/+4/+8, copy the key to +0xC and set
colour + nil at +0x18/+0x19, +0x1C/+0x1D and +0x30/+0x31), iterator
construction/dereference/increment/decrement (00416893/004169f1, 00416ccc/
00416cd8, the predecessor walk 004172bd and the successor walks 00417334/
0041738f at their +0xF/+0x31 nil bytes), a family of checked {container, position}
pointer iterators with inclusive [first, last] bounds (0041691d, 00416e06,
00416e51, 00416edb, 00416f0b, 00416f56, 00416fad, 00416fdd, 0041747c, 004174be,
00417500, 004175db, 004178d9) and vector/array range operations for
element strides 4, 8, 0x10, 0x1C, 0x28 and 0x30 (0041791e/0041796d/004179b5,
00417b51, 00417d11..00417e4c, 0041810c, 00418191, 004181e3, 00418250). The
container element type is a small interface holder; its copy/fill helpers
retain the SOURCE holder's object through vtable slot +0xC (the AddRef side) and
release the destination's through slot +0x10(0) (004179f8/00417a30/00417a90/
00417cd7/00417ff1/00418171/00418437/00418662) - the same interface convention as
the GFC interfaces (accepted records 004114d5/00413e5f read slot +0xC as AddRef),
so these
instantiations belong to the GFC side, not to the CRT proper. 00416aaf is `std::basic_string<char>::_Eos` (Ghidra-matched
VS2003-2008 library function; the only non-Global namespace in the shard).

## 4. FX constructors and the bitmap control theme (004186c9-004187fa)

004186c9/00418700/0041873b are the constructor of `GLineFx`, `GFillFx` and
`GBlitFx` (each runs the GDrawFx base ctor 00405a32 and stores its RTTI vtable
pair; effect kind 1/2/3 at +0x18; GBlitFx defaults a 0xFFFFFF field). 004187fa
is the bitmap control-theme loader: it asks the application manager (+0x264) for
theme kind 2, accepts the stored theme name `GFC_Drivers_CtrlTheme_Bitmap`,
loads `BitmapTheme.thm` and instantiates `GBitmapCtrlThemeLoader` from
`GCtrlTheme_Bitmap.dll` through the class loader 0041454a, reporting the
"GFC Warning: GApplication::Initialize ..." diagnostic on incomplete themes.
The DLL itself is an external artifact not present in this export.

## 5. Control base block (00418c10-00419846)

00418ce1 is the control base-class **property writer**: it serialises
`CtrlFlags` (with the `GFC_CF_NOTVISIBLE` default), `StyleId` (+0xB0),
`ClientOrigin` (+0xA4), `Placement` (+0x78), `MinMaxInfo` (+0xC4),
`NoninheritedMap` (+0x3C) / `InheritedMap` (+0x38, resolved through the access
context pair 004c6dcb/004cd10a), plus `ToolTipInfo`, `TopLayerBlitFx`,
`BottomLayerBlitFx`, `Layout`, `ActiveChildPath`; it is called from ~20 control
implementations in the 0x6060xxx-0x660xxxx region (buttons, labels, panels,
tables), which anchors it as the base control method. 00418f4d writes the same
+0xB0 field with the default block DAT_01bc3570 and emits the 0xE notification
kind (SetStyleId - the confirmed writer 00418ce1 stores the same +0xB0 field
under that literal with the same DAT_01BC3570 default);
00418ffa maintains bit 0x4000000 with manager bookkeeping at +0xD4 and the
0x24924 notification mask (SetBit4000000AndNotify; the visibility reading is a
cross-function inference); 0041951c fills the caller's context (returning 1
after the related-object query or the 0x10101 fallback block) - its earlier
hit-test role is not verified and it has no callers; 0041964d measures a size
pair; 00419846 maps a position onto the target rectangle in floating point.

The control tree is walked recursively through stack `GObjectIterator`s
(children via the object at +0x24, slot +0x50(&iter, kind)): 00419123 (notify
walk), 004191af (subtree search whose return value is the child under which the
match was found, 0 for a direct child - never the match itself), 0041925b
(directional neighbour search - nine anchor points per child, 0x5A/0xB4 offsets
for the horizontal/vertical directions, nearest child by Manhattan distance),
004195ff (clear child +0x48), 004196d8 (recursive attach of the +0xC0 object),
00419790/004197f3 (set/clear +0x40 recursively). 00418fc6 resolves a linked
object (manager +0x44, mode +0x11C) and is reused by 00419846. 00418c10
dispatches on the short id at +0x1C of its argument record (DAT_01BC2A60 /
DAT_01BC7344, payload forwarded to slot +0xC4) and is called from 00823840;
reading it as a window/lobby message handler is an inference from that caller.

## Review corrections (independent pass 2)

The following were corrected after review and byte-level re-checks; the record
file reflects all of them:

- Adjustor thunks mistaken for call wrappers: 0041529e (add ecx,4; jmp
  004c9e83) and 00418c05 (add ecx,0x1A8; jmp 00412c48); 00418541 turned out to
  be byte-identical to 0041528b (+0xC interface, corrected again in pass 3).
- "Index" iterators renamed to pointer/position iterators with the inclusive
  [first, last] adopt check (0041691d ... 004178d9), and 004168d2/004168fa/
  00416963 renamed to positional step wrappers (steps 1 and 4).
- The tree walks stop on the nil/sentinel byte, not a colour; the node colour
  byte is the one written from the constructor argument and the header init
  stores 1 there (00417091: +0x18 = 1, +0x19 = 0).
- Node construction field order: +0/+4/+8 are _Left/_Parent/_Right
  (0041760b/0041763e/00417671), key copy to +0xC, colour then nil at the
  trailing pair.
- Deleting destructors 004176a4/004176c3 run their destructor bodies on the
  member at +0x10 (lea ecx,[esi+0x10]), not on the whole object.
- 00418662 copy-assign writes +4/+8 (not +8/+0x10); the holder helpers invoke
  slot +0xC on the source before slot +0x10(0) on the destination.
- Contract fixes: 004191af returns the child under which the match sits;
  0041951c's branch logic is the inverted form documented in the record;
  00415b23 clears result components per kind 0/1/else; 004156b2's fast path is
  gated on bit 0x100 of +0x14; 00415cfe's 0x880000 shortcut needs a null
  out-parameter.
- 00417e4c copies 0x1C-byte elements (renamed CopyBackward0x1C); 00417dcb is
  the 0x28-byte variant.
- Class attribution removed where it rested only on adjacency: 00418581 is now
  ReleaseTwoHoldersAndBases (field +0x40/+0x44 evidence only, class null).
- Domain words without an own anchor were moved out of names: 00418ffa,
  00418c10, 0041964d, 00418fc6, 004154e7, 004155a8, 00415f75, 00416025,
  00416315, 00416463, 00415b23 (00418f4d was given back the semantic name

## Cross-shard links and notes

- The value/node interface used throughout (slots +0x18/+0x1C/+0x50/+0x54/
  +0x58/+0x5C/+0x64/+0x68/+0x6C/+0x70/+0x110) belongs to the GDataAccess object
  implemented at 0x428xxx-0x433xxx (S0009/S0011, `GDataAccessImpl`,
  `GStringAccess`), so those shards should define the node contract this shard
  only consumes.
- `GetOwner`/`GetDataId`/`GetDataAccess` (00414952/56/64, S0004) are the
  accessor side of the same vtable family mapped here.
- The 0x175dc60 vtable has no RTTI in the export (COL slot is 0), so the
  GDataAccessWrapper attribution rests on the shared 14-slot inheritance into
  the two RTTI-named wrapper vtables, the S0004 `GetOwner` mangling and the
  `GDataAccessWrapper` literal in 00414cbf. Reviewers should treat the class
  name as strong but the *individual* method names as inferred behaviour names.
- Process note for reviewers: `nmq.py` follows `lab/native-map/ACTIVE` (the
  pilot DB), whose S0005 pseudocode and shard boundaries differ from
  `run/map.sqlite`, the DB `validate.py` checks. All evidence in this shard's
  output was checked against `run/map.sqlite` with `NM_DB` pinned.

## Most important open questions

1. What do value-descriptor kinds 1 and 2 encode (which control properties map
   to a four-word vs one-word payload), and what happens inside data-access
   slots +0x58/+0x5C?
2. The data-node interface behind the wrapper load/save (`+0x64` element lookup,
   `+0x6C` create, `+0x70` Items child with defaults DAT_01bc7e28/20) is not
   identified; it determines whether the load/save pair targets saved page data
   or a live store.
3. What is the object at control +0x44 (manager) and its states +0x11C = 1/2
   used by 00418fc6/00418ffa/00419846? This gates visibility handling and the
   coordinate mapping.
4. The bitmap control theme module `GCtrlTheme_Bitmap.dll` and its
   `GBitmapCtrlThemeLoader` class are external; the theme file format
   (`BitmapTheme.thm`) is a client asset, not recovered here.
5. The notification masks 0x24924 (and the 0xE / DAT_01BC28C8 block kinds) route
   into FUN_004d93a3; identifying that dispatcher would connect this shard to
   the message/notification system, but it lives outside the shard.
