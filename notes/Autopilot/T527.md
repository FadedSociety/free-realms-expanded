## Client evidence (IDA, this run)

- 168/14 ctor `00bff390` sets the family sub-opcode 14 and initialises two i32 fields to -1.
- 168/14 writer `00bff500`: decompiled this run. It writes `this+0xc` (first `sub_7CC400` call,
  length 4), then `this+0x10` (second call). `Mount.Upgrade` `00bffbc0` reads Lua argument 1 into
  `v4[3]` and argument 2 into `v4[4]` and logs
  "Upgrading Mount mountId = %d, upgradeItemDefinitionId = %d". So the request body is
  `i32 row id`, then `i32 upgrade item definition id`.
- 168/15 reader `00b05590` -> `00b05220`: decompiled this run. `sub_B05220` reads one i32 into the
  reply object's `+0xc` (or 0 and an error byte on underrun); no other field is read.
  `00b06100` case 15 calls `sub_B05590`, shows the green "UpgradeSuccessful" message, sends the
  dismount request and then builds 168/6 from that id, logging
  "Automount after upgrade: id %d". So 168/15's i32 is the roster row the client re-summons.
- T482 (already merged) established that the 168/6 id is the inventory instance id, so 168/15
  sends the same row id. The row ids used here come from `MountCatalog::owned_rides` /
  `owned_instance`; `trained` existed at `mounts.rs:1374` before this task, and the prerequisites
  named in the brief are present in this worktree.

## (R) reconstructed rules

- The upgrade-item allowlist, consuming exactly one saddle per successful upgrade, per-instance
  permanence and the refusal notices are server policy (R); the original server code/state was not
  recovered.
- A traded or sold ride loses its flag: `saved_upgrades` keeps only ids that are still owned ride
  rows. A receiver never inherits a sender's training (the flag set is per character).
- Sanity bounds on the data: at most 16 entries, each id > 0, non-empty source evidence, no
  duplicates. An empty list is valid and turns upgrades off.
- `is_upgradable` stays a ride-definition flag (no training state changes it).

## Security note (secure-code-guardian)

Hostile client: any 168/14 body can name arbitrary row and item ids, and can replay a valid
request or send two in one bundle.

- The row must resolve through `owned_instance`: a positive, owned, positive-count inventory row
  whose item definition maps to a ride in the catalogue. A ride id, a negative id, an unowned row
  or a non-ride item is refused.
- The item must be in the content allowlist and the player must own a positive-count instance of
  it. The instance id that is consumed is chosen by the server from that inventory scan (lowest
  id), never taken from the request, so the client can only spend its own saddle.
- The saddle is consumed with the existing transactional `Inventory::consume` (its normal 38/4 /
  38/2 reply), and the training flag is inserted only after it succeeds. Two upgrades in one bundle
  see the first result (flag set and saddle gone) and the second is refused; no double consume.
- Refusals are staged: the saved state and the inventory are asserted byte-equal before/after
  (`refusals_change_nothing`, `a_repeat_upgrade_is_refused_and_consumes_nothing`). The only writes
  on a refusal are the in-memory roster cache (`last_sent`, session-only) and the notice/roster
  replies.
- No grant, no client-reported result, no path from client bytes to the filesystem.

## Checklist

1. **A refusal changes nothing.** `refusals_change_nothing` snapshots `GameplayState` and
   `InventoryState` before each of the six refusals and asserts equality afterwards; the repeat
   test does the same, and the canary above breaks the guard and fails on the missing refusal.
2. **Rollback covers all state.** The plan is pure; `Inventory::consume` clones internally; the
   `MountService` flag is inserted only after it returns. No `Rc`/`RefCell`/side table escapes.
3. **Apply deltas, never restore snapshots.** The consume changes the live inventory and the flag
   is added; no saved inventory/position is restored. The roster is rebuilt from live state.
4. **Busy rules are mutual.** The upgrade is a one-shot request, not a persistent activity, so it
   adds no `Occupation`. It is gated by `ride_restrictions()` -> `blocks(Gates::ride)`, whose
   existing rows already refuse during gathering, crafting, chess, encounters, minigames, kart,
   derby and fishing; no other activity can start while the request runs because it finishes
   inside one message.
5. **Every entry path is gated.** The only path is gameplay's 168 dispatch -> `handle_mounts` ->
   `upgrade_ride`; there is no NPC/menu/parallel path in this task. Restrictions, ownership and
   the allowlist are re-read on every request. Reconnect restores the flags but not any ability to
   upgrade without a saddle.
6. **Reachable in production, tested through it.** `tests/mount_upgrade.rs` drives
   `Gameplay::handle_in_world` (the same route the gateway uses for family 168), not a mocked or
   copied rule. The gateway labels 168 as `mounts` already, so no selector change was needed.
7. **Survives reconnect.** `the_upgrade_survives_save_and_reload` saves `GameplayState`, loads a
   new `Gameplay` from it and boards the ride; the glide block is still trained.
8. **Every exit path restores the player.** The upgrade changes no mount/pose/ability state; a
   refusal leaves the player free, a success leaves it free until the client's own 168/6. A failed
   consume aborts the staged game rather than half-updating.
9. **Economy safety.** One server-selected owned saddle instance is consumed through the normal
   inventory API; no free grant, no client quantity, no client-reported result; the training is
   permanent and refused once per instance.
10. **Wire format matches the client reader.** 168/14 layout is from writer `00bff500` and
    `Mount.Upgrade` `00bffbc0`; 168/15 is one i32 from `00b05590`/`00b05220`. Tests decode the
    roster and 38/7 independently and pin the 168/15 bytes.
11. **Unique ids.** No ids are allocated; the roster row is the inventory instance id, which the
    existing allocator makes unique per inventory.
12. **Others see changes.** The upgrade is owner-only (roster and 38/7); no other-player visible
    state changes until the rider boards, which already goes through the directed-visibility
    fanout.
13. **Content works end to end.** The test owns the actual items 76856 and 79150 from the runtime
    catalogue, upgrades, consumes, and boards with `GlideEnabled` 1 and the trained values.
14. **Values live in data.** The allowlist is in `mounts.json`; the trained glide values were
    already `trained_glide` data. The only constants are the existing sanity ceiling pattern
    (`MAX_UPGRADE_ITEMS = 16`).
15. **Canaries break production code.** See the canary section: the guard in
    `MountService::upgrade_plan` was removed and the test failed; restored, it passes.
16. **Hands off session plumbing.** No change to `gateway.rs`, `src/bin/osfr-gateway.rs`, session
    creation/teardown or save ordering.
17. **One player's error never stops the server.** The handler returns `Err` for malformed bodies
    (the gateway's per-message staged path handles it) and for an internal consume failure the plan
    just validated; every rule refusal is an `Ok` outcome. No arithmetic on client values beyond
    `i32` reads and no `?` inside the shared tick.
18. **A type's rules live on the type.** `GameplayState.upgraded_rides` documents what counts,
    that it is per instance, pruned on save and skipped when empty; `MountService.upgraded` and
    `RideUpgrade` document the same decisions. `MountCatalog::is_upgrade_item` owns the allowlist
    rule; `trained` owns "definition flag or per-instance training".
19. **Hot paths stay cheap.** Per tick nothing was added. Per 168/5 row the change adds one
    `BTreeSet::contains` (O(log n)); per board one `contains`; `saved_upgrades` runs only when
    `Gameplay::state()` is built (saves/snapshots) and scans the inventory once per trained id,
    which is empty for almost every session. No allocation in `settle`/`roster_sync`.

## Open gaps

- The saddle's sale/trainer and the Glide Training quest chain are separate briefs; item 79150 is
  not authored in the repo's own content (there is no item catalogue in the repo), so the gameplay
  test uses the private round70 runtime package that defines it. Production login with an item
  catalogue that lacks 79150 cannot obtain the saddle, which is the next brief's job.
- `upgrade_items` is now a required field of `mounts.json` (absent field = load error). Only the
  bundled content ships a mounts.json in this repo; an external overlay without the field would
  fail closed until updated. An empty array is accepted (no upgrades).
- The client's `is_upgradable` filter is untouched, per the brief.
- The live `MountService.upgraded` set is pruned on save, not on every ownership change; a stale
  live id could only matter if a different ride instance reused that exact instance id before the
  next save. The receiver of a traded ride never inherits the sender's flag.
- 168/15's trailing-byte policy was not probed (the packet is exactly one i32; the client's reader
  reads one i32 and a flag).
