## Fix for the attempt-2 integration failure (this run)

Attempt 2 failed `sheep_watch_dungeon::refusals_change_nothing`: the forged 41/108 Go got a reply, a 35/11
clearing two NPCs. Cause (traced with temporary prints, reverted): a 26/13 job switch swaps the active job but
never refreshed the quest engine's eligibility; the next packet that reached `handle_npc_packet` did (its first
line), which moved the quest revision, so the end-of-packet marker pass refreshed markers on an unrelated refused
packet. The delayed refresh was also a real lag: the markers for a new job's quests arrived one packet late.
Root-cause fix: the 26/13 branch of `handle_in_world_inner` calls `refresh_npc_quest_eligibility` once after the
selection commits (one line plus a comment, `gameplay.rs`), so the switch's own packet carries the refresh and the
next request moves nothing. New test `job_switch_settles_markers_in_its_own_packet` (canary: removing the line
fails it). The rest of the attempt-2 patch applied cleanly (no `.rej`/`.orig`).

## Per-pass cost

- Per-player, nothing new and revision equal: one `starts_with` scan of the batch's packets and one u64 compare. No
  allocation (empty `BTreeSet`s do not allocate). `update_npc_visibility` is unchanged apart from that scan.
- Per-player with new NPCs or a moved revision: `marker_targets` runs once per non-empty set (the added NPCs, then
  the visible known ones when the revision moved), so both non-empty is two bounded scans of the NPC table (a few
  thousand rows each), and one `marker_for` per returned row (at most 64 rows in total).
- Shared pass: skip condition gained one u64 compare; with nothing moved it still `continue`s before any work. A moved
  revision does one `marker_targets` pass, over `known & wanted`.
- Nothing clones whole state: `MarkerView` holds an `Arc`.

## (R) choices

- Markers are not re-sent per tick; a revision bump triggers one refresh (35/10 for NPCs with a marker, 35/11 for
  quest NPCs without one). A newly added NPC gets only a 35/10 (nothing to clear).
- An offered quest hides the giver's '!' (the engine denies offering while an offer is pending), so the marker is
  cleared when the 49/1 opens and returns on a decline. Expected; flagged for the native run.
- `select_quest` and the auto-switch flag bump the revision too (the brief says every `changed` outcome): one
  harmless refresh with identical markers.
- The refresh re-sends the same marker over an NPC that already has it. Whether the client replaces or stacks a
  repeated 35/10 for one guid is the native question the brief already lists; remove-then-add is the fork's route.

## Open gaps

- The live placement tick (`placement_watch::tick_live_placements`) calls `NpcVisibility::update` directly and is
  not wrapped by `append_quest_markers`. This is no marker gap today: `NpcVisibility::place` does not register a
  `content_keys` entry, so `marker_targets` has no content key to mark; it would need the same wrap if placements
  ever become quest-bound. Developer/World Builder path only; the player-driven per-player and shared paths are
  covered and no required test drives it.
- The AddNpc notification image field stays (R) (IDA `00921a10` decompile is capped before it); the brief's native
  follow-up must decide whether 35/10 alone draws '!' and '?' or the AddNpc field is also needed.
- Whether the client replaces or stacks a repeated 35/10 for one guid is unproven; the refresh can resend an
  unchanged marker, as the (R) choice above says.
- Tick-only live-event flips (`tick_live_events`) refresh markers on the next handled packet or movement, not in the
  tick that flipped them; the brief only requires the refresh on a handled packet.

## Threat note (secure-code-guardian)

A hostile client sends nothing new: no new request selector, so no `app_fuzz` seed. A forged 49/2 for an unoffered
quest is refused by the engine and bumps nothing (`refused_accept_changes_no_marker`). Markers are computed from the
player's own engine and written only to that player's replies and queue; they never enter `nearby` or `broadcast`
(`players_see_their_own_markers`). A marker encode refusal (more than 256 rows, unreachable on the client-driven
paths because the view cap is 64) logs `quest_marker_skipped` and skips the packet for that player, never an error
out of the tick.
