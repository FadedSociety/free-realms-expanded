# T370 - Prove one normal player logs in, enters the world, chats, moves and keeps the save across a real server reconnect

## What changed

One new default-suite file, test-only:

- `prototype/osfr-tools/tests/playtest_gateway_smoke.rs` (+915 LF lines). It
  includes the production gateway binary (`#[path = "../src/bin/osfr-gateway.rs"]
  mod gateway_runner`) and the shared synthetic reference
  (`tests/common/gateway_reference.rs`), then drives three scenarios through the
  real `Server`:

1. `a_normal_player_logs_in_enters_moves_chats_and_relogs` - a `Player`-role
   account with dev tools off sends the real login 1, ready 13 and loaded 10;
   the server reports the session ready (`test_location(...).2`) and the typed
   self-data 12 packet names character 2 with the account store's name. A
   movement 125/1 pose inside zone 0 is accepted (no 38/12 snap-back), saved,
   and the 15/1 say line echoes back. A clean SOE disconnect writes the save;
   the test restarts a second `Server` on the same state directory and relogs
   the same character: the 12 packet carries the saved pose and identity name,
   `test_location` restores guid/zone/pose/rotation, and one session exists. A
   duplicate login of that character is refused before it reads the save, the
   save bytes do not change, and the owner still speaks.
2. `the_smoke_uses_no_dev_commands_or_roles` - the account role is `Player`;
   a `Gameplay` loaded from the existing opening play fixture (the same
   `tests/support/npc_quest_chain.rs` content the first-hour suites use), bound
   to that role with role commands trusted and dev tools off, reports
   `may_run("give")` and `may_run("coins 10")` false - the same predicate the
   account-store session uses. No `realm`/teleport text is sent, and every sent
   message is the ordinary login 1 / ready 13 / loaded 10 / movement 125 /
   chat 15 subtype 1 family. The security log has no `dev_command_denial` or
   `budget_refusal` row and does not echo the character name or login ticket.
3. `a_bad_packet_or_abrupt_disconnect_ends_only_that_session` - a
   parseable-but-gross pose (10,000 units) is refused with the server's 38/12
   location message, changes neither the live pose nor the save bytes, and
   leaves the session alive. A truncated 125 body ends that session with a
   contained error and the save bytes stay unchanged. A fresh session then
   logs in, moves and speaks. Separately, a logged-in session's UDP socket is
   dropped while another session stays live: the server keeps stepping, the
   live session still moves, a new visitor session logs in and speaks, and
   shutdown saves all three characters through the normal path.

No production, content, role, login, session, transport or save-ordering change
is in the diff. `git status --porcelain` shows only the new test file (and this
note).

## Client evidence (IDA, read-only, checked for this slice)

- Movement 125 reader `0x008e5940` decompiled: reads `u16` (object `+4`), the
  `u64` GUID as two dwords (`+8`, `+12`), three `f32` position components
  (`+16`, `+20`, `+24`), three `f32` direction components (`+32`, `+36`, `+40`),
  then two bytes (`+48`, `+49`), and finally writes the position W (`+28`) as
  `1.0` and the direction W (`+44`) as `0.0`. That is exactly
  `u16 opcode, u64 GUID, 3*f32 position, 3*f32 direction, u8 state, u8 unknown`
  on the wire; handler `0x0090de90` is the caller's apply path. The test's
  `position_request` writes 34 body bytes plus the opcode, matching this reader.
- Typed chat 15/1 sender `0x00b15340` and reader `0x00b140c0` are recorded in
  `notes/Research/Unrouted Client Requests.md` R051 ("routed and correct").
  The test does not restate the layout: it uses the production
  `chat::local_request` builder (`src/chat.rs`, "a client local-chat request
  (15/1) carrying `text`, as the client sends it") and wraps it as the outer-5
  application request.
- Login 1, ready 13, loaded 10 are the native sequence in
  `lab/autopilot/native-notes/2026-10-20.md` run `client-baseline-
  20261020T204059Z`: `gateway.login 1/32 -> gateway.ready 13 -> gateway.loaded
  10 -> movement 125/1 accepted`, from `server-trace.jsonl` with zero
  `rejected` rows. The 1/32 label is the trace's runtime packet label; the
  request itself is the existing gateway login body (ticket, GUID, version,
  empty string), which the test copies from `tests/multiplayer.rs` and
  `tests/gateway.rs`.

## (R) rules and open gaps

- **No new (R) gameplay rule.** The test drives existing reconstructed rules;
  the only values it adds are synthetic fixture strings, a synthetic pose and
  the test's own connection ids.
- **(R) In-process harness has no trace sink.** `Server::new(Options)` does not
  accept a trace and `Server.trace` is set only by the binary's `run()`. The
  brief allows the fallback: the test asserts the real server/session flags and
  the absence of a refusal reply instead of `rejected` rows, and uses the
  security log for the developer-command audit.
- **Test 2 loads the existing opening play fixture for one predicate.** A
  no-content gateway session deliberately has no `Gameplay` (movement and chat
  are gateway-level), and `Gameplay::load` needs a content tree with
  `inventory.json`/`profiles.json`. Test 2 therefore includes
  `tests/support/npc_quest_chain.rs` and loads its copy of
  `lab/references/opening-anvil-placement-v1/content` - the same fixture the
  first-hour suites already require - to call the real
  `Gameplay::may_run("give")`/`may_run("coins 10")` with the stored `Player`
  role, role commands trusted and dev tools off. No new content is authored.
  This one predicate costs ~3.9 s of fixture copy/load in a 4.5 s test.
- **Abrupt-drop reaping is the existing 60 s idle timeout.** On Windows the
  server does not see a closed UDP port immediately (the existing
  `a_vanished_client_does_not_stop_the_server` pins this), so this test does
  not wait 60 s. It asserts the server keeps stepping, the live session still
  moves, a new session logs in and speaks, and shutdown saves the abandoned
  character.
- No native client run; the session is lead-controlled. This slice is
  server-side and test-only.

## Security threat note (secure-code-guardian)

- Surface: the test is a hostile-client-shaped driver of the real server (SOE
  handshake, login, movement, chat). It sends only fixed synthetic values:
  no user names, no chat logs, no environment data.
- What a hostile client could send and why it is refused (existing production
  rules, asserted here where applicable): a movement body with a non-finite or
  over-`1_000_000` coordinate is refused by the gateway reader (that refusal
  ends the session with a contained error, as test 3 shows); a parseable but
  gross pose is refused by `movement::validate` and answered with the server's
  own 38/12; a truncated 125 body is refused and contained; a duplicate login
  is refused before the save is read or written and cannot take over the live
  session; a `Player` role with dev tools off cannot run `realm give`/
  `reload battles`. Chat is the ordinary 15/1 budgeted path; the security log
  assertion shows the flow did not produce a developer-command denial, a budget
  refusal, a name or a ticket in the log.
- No new parser, save, coin, item, reward, role, chat, session or gateway code;
  no secret, key or name is written to code/notes. The account fixture uses the
  existing synthetic names from `tests/multiplayer.rs`, not a player's.
- Refusals change nothing (item 1): the test asserts save bytes and live pose.
