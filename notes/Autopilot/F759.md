## Threat note (secure-code-guardian)

A hostile client can send any 53/32 definition and tint. The server resolves the pair to an **owned** inventory
instance (`owned_item_for_record`), refuses a non-pet/unknown item, a wrong tint, an unowned instance and a full
roster, and a refusal changes neither the roster nor the inventory. The item is consumed only after the pet
insert validates, and both halves commit together; no client-reported quantity is trusted and no coin, XP or
reward moves on adoption. The display-name/texture fallback only picks strings from pinned content for an actor
the server already owns. Details and test names are in `notes/Autopilot/T454.md` ("Threat note").

## Checklist

1. **A refusal changes nothing.** Staging clones the roster and inventory and commits both only on success
   (`adopt_with_replies`, `handle_with_inventory`). Tests: `an_owned_item_that_is_not_a_pet_changes_nothing`,
   `a_full_roster_refuses_the_item_and_keeps_it` (50 real 53/32 adopts then the 51st refused, last item kept),
   `pet_routing::unowned_pet_item_and_malformed_refusals_each_change_nothing`, f161
   `the_roster_rides_in_every_document_save_and_a_refusal_writes_nothing` (document bytes). Canary: `MAX_PETS`
   raised to 51 failed the full-roster test; reverted.
2. **Rollback covers all state.** The mutable state is `PetService` (roster + active actor) and `Inventory`;
   both are cloned per transaction. `Arc<PetContent>` is read-only. No side table escapes.
3. **Apply deltas, never restore snapshots.** Adoption consumes one owned instance through `Inventory::consume`
   on the live-derived clone; no coins/position/inventory snapshot is restored. f161 asserts the saved
   inventory equals the live inventory after the commit.
4. **Busy rules are mutual.** `Gameplay::handle_pets` passes `blocks(|gates| gates.pets)` from
   `gameplay/occupation.rs`; I added no activity and did not touch the table.
   `tests/pets.rs::minigame_busy_rule_rejects_summon_without_mutation` still passes.
5. **Every entry path is gated.** One path: `application_handler` → `Gameplay::handle_pets` →
   `handle_with_inventory`. No NPC/automatic adoption path; vendor grants use `adopt_vendor_grant`. The coin
   store uses the same `definition_for_item` gate; `a_pet_item_bound_by_pets_content_is_sold` and the shipped
   vendor gate pass. No level/job requirement exists in recovered pet data; owning the certificate is the gate.
6. **Reachable in production, tested through it.** f161 drives `Session::dispatch_message` for an item-only
   pet; `tests/pet_catalogue.rs` drives the same `handle_with_inventory` the gateway calls (no copied logic).
   The reviewer's 7885-literal request was not possible in the gateway fixture (7885 is not defined there); the
   Wolf 15493 case exercises the identical path end to end.
7. **Survives reconnect.** f161's item-only test drops the session, reconnects and asserts species 15493, name
   "Wolf", texture "base" and tricks `[2057, 2058, 2059]` from the save. No save-format change; older rosters
   load unchanged (`tests/pet_routing.rs::roster_reload_preserves_ownership_and_the_client_list_reports_no_active_actor`).
8. **Every exit path restores the player.** A refused adoption creates no actor; dismiss/zone/timeout ride the
   existing W177 paths; `pet_wired::zoning_dismisses_without_persisting_the_actor_and_reload_keeps_roster`
   passes. No new exit was added.
9. **Economy safety.** The item is consumed only after a successful insert+validate; an unowned item, a
   non-pet item, a wrong tint and a full roster all refuse without spending it; no coins/free grants; no client
   quantity is trusted. Duplicate species adoption still spends one certificate each (lead decision, pinned by
   `each_adoption_item_adopts_a_new_pet_even_when_the_species_is_owned`). Binding the two items changes no
   shipped vendor row (`REVIEWED_UNSELLABLE` empty, shipped gate green).
10. **Wire format matches the client reader.** No layout change. 53/32 is built by the reader-derived
    `pet_wire` (`00b60110`, `00a1ec00`), and the tests read the resulting 35/2 AddNpc with the production parser
    of reader `00921a10` (texture alias + name).
11. **Unique ids.** `next_pet_id` with checked overflow; actor id from `pet_guid`. Unchanged.
12. **Others see changes.** The new name/texture ride the existing `PetPresence::spawn_packet` → shared → nearby
    path; `pet_wired` and `pet_bots` cover other players seeing the pet.
13. **Content works end to end.** Both dead items resolve, adopt end to end, spawn client models 483/1530 and are
    consumed; all 528 client Type-2 items are bound (pinned against the source file).
14. **Values live in data.** New values are `pets.json` rows with `src`; the tint override is now a pinned
    client-catalogue import; no tuning constant was added.
15. **Canaries break production code.** All five canaries edited production files (`pets.json`, `src/pets.rs`,
    `src/coin_shop.rs`), each failed the intended test, and each was reverted (verified with git).
16. **Hands off session plumbing.** No session creation/teardown/transaction/ordering change; the only

17. **One player's error never stops the server.** Refusals return `Ok(Some(PetWire))` with a notice; no `?` on

18. **A type's rules live on the type.** `PetItem::name`/`texture_alias`, `Pet::learned_tricks`,
    `PetContent::model_id` and the two fallback methods carry doc comments stating their rules.
19. **Hot paths stay cheap.** No per-tick/per-packet clone added; display name/texture are computed on
    adopt/summon and AddNpc replay, with linear scans over 113 species and 528 items only on that path.
