## (R) rules

- Per-character relay budget: 10 relays/second, burst 4. A normal jump cadence
  (~0.5 s) is well below it. Over budget drops only the extra 164; the pose
  still fans out through 125.
- Vertical velocity: finite values are clamped to +/-100.0 (10x the 10 u/s 125
  base); a finite out-of-range value is not refused (a refused body would end
  the session). Non-finite position/direction/velocity, bad length, wrong
  opcode and a foreign GUID are refused before staging.
- The relay body uses the server-bound GUID, the final committed pose and the
  accepted 164's state/unknown/velocity. A later 125 supplies pose only; a
  later application child drops the impulse.
- The 50 ms native send gate is not a server boundary; the budget is.

## Security threat note (secure-code-guardian / Security Model S3)

A hostile client can send a 164 for another character GUID (refused: the
session character is the only accepted id), a short/trailing/wrong-opcode body
(refused before staging), NaN/Inf/out-of-range position or direction (refused
by `jump_relay::decode` + `movement::validate`), a huge finite velocity
(clamped, never a disconnect), a state byte without bit 2 (relayed as-is; the
observer applies no velocity, so the sender only loses its own animation; the
pose still moves), or a 164 flood. The flood is capped at 10 relays/s burst 4
per character; over budget only the extra 164 is dropped, and the accepted
poses still fan out through the existing 125 path (which is the same directed
viewer set). The key set is bounded by `MAX_SESSIONS`; `end_session` removes
the character's key, so a reconnect starts a fresh burst (a deliberate leak
limited by the session/packet/byte budgets, and the lead's cleanup rule). The
relay body's GUID is server-bound, its pose is server-validated, and it goes
only to sessions whose directed view contains the sender; the sender is
excluded. The limiter lives in `Security`, outside the staged world clone, and
is charged only after a successful commit, so a refused or failed transaction
neither spends nor refunds a relay. No items, coins, rewards, roles or other
player-triggerable economy state are involved; no secrets or names are logged.

## Checklist

1. **A refusal changes nothing.** Invalid/foreign/pre-Ready 164s fail before
   `handle_at` assigns the staged clone; the real-dispatch test snapshots the
   state and the recipient for each refusal. The budget is charged only in the
   post-commit fanout, so a refusal cannot consume it. Covered by the existing
   refusal assertions and canaries 1-4.
2. **Rollback covers all state.** The relay body is a field on the staged
   `Gateway`; the limiter lives in `Security` (shared `Arc`, like the account
   budget) and is spent only after `commit_outcome` succeeds. No `Rc`/`RefCell`
   or side table escapes. A refused transaction assigns nothing.
3. **Apply deltas, never restore snapshots.** The body is built from this
   request's final committed pose and the accepted 164 bytes; no earlier pose is
   written back. The `[164, 125]` bundle test asserts the final pose and the
   jump's state.
4. **Busy rules are mutual.** A jump is movement and shares the opcode-125
   gate/validation/save path; no new activity or `Occupation` row. No busy
   table change.
5. **Every entry path is gated.** The only entry is the tunneled client 164;
   world-ready is checked in `handle_at`, movement goes through
   `movement::validate`, and the body is server-bound. Tests cover the pre-Ready
   refusal and `reset_session`; there is no NPC/automatic/reconnect path.
6. **Reachable in production, tested through it.** The bin test drives
   `Session::dispatch_message` (login -> Ready -> Loaded -> bundles) and decodes
   the recipient's queued 164; `tests/gateway.rs` drives `Gateway::handle`.
   No test calls the limiter or the relay builder as a shortcut.
7. **Survives reconnect.** Nothing new is persisted: the relay body/impulse are
   per request, and a relay budget is intentionally session-scoped (the lead
   requires the key to be dropped on leave, so a reconnect starts fresh). The
   leave cleanup is in `end_session`; `KeyedBuckets::remove` and the unit test
   pin the forget; `reset_session` clears a staged body. No save schema change.
8. **Every exit path restores the player.** No activity, location or stuck
   flag; `reset_session` clears the staged body; a clamped jump leaves the
   character free with the committed pose.
9. **Economy safety.** Not applicable: no item, coin, reward, grant or
   client-reported outcome. Input bounds and owner checks still apply; no
   client quantity reaches an economy path.
10. **Wire format matches the reader.** Reader `008e5ba0`, writer `009127f0`,
    constructor `008b3b70`; the unit test rebuilds the 40-byte body
    byte-for-byte (state at byte 34) and the real-dispatch test decodes the
    queued body. No field added or removed.
11. **Unique ids.** No allocator; the server-bound character GUID is used and a
    body naming another actor is refused.
12. **Others see changes.** Directed viewers only (`nearby_sessions` +
    `knows_character`, sender excluded); the flood test asserts all 10 poses
    reach the viewer while at most 4 relays do. No new visible state without a
    broadcast.
13. **Content works end to end.** Protocol feature, no content. The endpoint
    (a directed observer receives one decodable 164 at the final pose with the
    jump state, and the pose fanout is independent of the budget) is asserted.
14. **Values live in data.** There is no movement-policy content table; the
    relay rate/burst (R) are the lead's accepted compiled values and the
    100.0 velocity clamp is the one remaining (R) value. Flagged as open; not
    invented into data in this task.
15. **Canaries break production code.** Four production edits, each failed the
    named regression, all reverted to matching hashes (details above).
16. **Hands off session plumbing.** The brief's Lead decision explicitly
    requires the leave cleanup, and `lead-signoffs.md:30` accepts the staged
    field/build and the post-commit fanout. This diff changes no creation,
    teardown ordering, transfer branch or save ordering: `end_session` only
    removes the character's limiter key after the existing active-session
    bookkeeping, and `delivery::post_commit` runs broadcast then jump.
    **F266's item-16 answer was false and is corrected here.**
17. **One player's error never stops the server.** The limiter and the leave
    cleanup are infallible; lock poisoning uses `into_inner`; the 164 decode
    checks length before fixed slices. `post_commit` propagates only through
    the existing per-session `queue_delivery` path; nothing new runs in the
    shared tick.
18. **A type's rules live on the type.** `JumpImpulse` documents the jump
    bytes vs the final pose; `Gateway::jump_relay` documents the staged body;
    `Security::jump_relays` documents the per-character budget; `KeyedBuckets`'s
    `remove` is documented; `post_commit` documents the committed-only rule.
19. **Hot paths stay cheap.** A non-164 message pays one `Option<JumpImpulse>`
    copy; an accepted 164 allocates one 40-byte body and does one bounded
    nearby/visibility query plus one short `Security` mutex lock after commit.
    The limiter lives in the shared `Security` `Arc`, so staging a world does
    not clone it; no whole-state clone was added.
