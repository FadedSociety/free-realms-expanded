# T795 - Card game start order: the offer names the card asset list, 39/37 is answered while offered, then 39/5 -> 39/17 (lead brief, native + research 2026-10-27)

Native run 2026-10-27: the Card Duelist start screen stayed on "Loading..." and nothing sent 39/5. Cause and fix, with
every client fact checked against the client again for this task (addresses are `FreeRealms.exe` virtual addresses).

## Root cause

`PlayerStartMiniGame` (`009beb70`, log `MiniGame:PlayerStartMiniGame`) calls Lua `:setNotReady` (the "Loading..." button)
and starts the client's loader state machine (`009bf5e0`, state at manager `+0x2BEA0`) only for a non-empty preload name
(the string length at info offset `+632`) or for types 1, 2, 17, 22. Our 39/16 sent an empty name for type 16, so the loader never ran,
`MiniGame:SetMiniGameReady` (`009b0cc0`) was never reached and the Start button never enabled. The ticket exchange was in
the wrong order too: the card manager asks for the ticket itself (39/37, `009bf590` -> `009bdc60(37,-1,-1)`, called from
`00ad4f50` state 2 once the card assets are loaded) and the 39/0x28 answer (vtable slot 25 `00ad32e0`: stores the two
ticket halves at `+0x2BA98/+0x2BA9C`, then `009aaf30` sets the loader state to 3) is what enables Start. 39/17
(`009b9550`, vtable slot 21 = `Startup` `00ad47f0`) reads that stored ticket, so it must come last.

## Corrected order (what the server now does)

| # | Dir | Message | Server rule |
|---|---|---|---|
| 1 | S>C | 39/16, type 16, preload `TradingCardGameAssets.txt` (R), flags `[1,1,1,1,0]` | `Launches::begin` |
| 2 | - | client loads the list, downloads the card assets (needs `TcgServerAddress`, below) | - |
| 3 | C>S | 39/37 `[instance,-1,-1]` | accepted while `Offered` (and still `Starting`/`Playing`); mints a ticket |
| 4 | S>C | 39/0x28 `[instance,-1,game]` + u32 low + u32 high | a repeat gets a fresh ticket that replaces the character's earlier one; TTL and single use unchanged |
| 5 | C>S | 39/5 (Start click) | ignored until step 3 happened for this run |
| 6 | S>C | 39/17, header only | `Offered -> Starting` |
| 7 | C>S/S>C/C>S | window close: 39/6 -> 39/19 -> 39/7 | unchanged (T782) |

### Flag `+616` (the end-of-game dialog)

`LeaveMiniGame` (`009bf190`, the 39/19 handler): when the game was started (`game+98`, set by 39/17) it runs
`ShowMiniGameEndDialog` (`009b7170`, goal-count based, built for a 39/18 result) if `game+2312` (info byte `+616`,
copied by `00c42c60`) is set, else Lua `:QuitGameWithNoEndGameScreen`. A card run that played (39/17 sent) ends in 39/19
after the card window's 39/6, with no goals and no 39/18, so `+616` = 1 would open an empty end dialog. (R) `Launches::begin`
sends 0. A run cancelled from the start screen never reaches that branch (`game+98` is 0). If a native run shows the
card window closing badly with 0, the revert is `spec.flags[4] = 0` in `Launches::begin` (the validator needs no change).

## TcgServerAddress: what the client needs, what the harness did, what changed

- The client reads `[AssetDelivery] TcgServerAddress` at PlayClient init (`0092da87..0092daaa`) and hands it to both card
  managers (`00ad4500`). The type 16 manager's slot 24 (`00ad3670`, run from loader state 3 in `009bf5e0`) builds the asset
  set "AssetsTcg" ("Free Realms TCG", the same `AssetDeliveryIndirect` class as the main set, constructor `0109d960`) on it.
- That set asks `<TcgServerAddress>/manifest.crc` (HTTP completion `010a1980`). A non-200 answer logs "Http error getting
  manifest.crc" and the callback `0109bd00` reports "Failed to receive the manifest crc file.": the set never finishes.
  A 200 body `crc,length` is compared with the CRC of the local `tcg/AssetsTcg_manifest.txt` (`0109bd00`); equal means the
  local manifest is used (`0109b650`) and no manifest is downloaded, otherwise it fetches `manifest.txt.z`
  (`010a0dd0`, `0109bea0`) and then every file the local TCG pack lacks as `<address>/<n>/<name>?<crc>`.
- `00ad4f50` state 1 waits for that set to finish (its vtable `+36` call), then asks for `TradingCardAssets.txt` (an entry of
  the local TCG pack); state 2 sends the 39/37 once the list loaded and more than 2 time units passed. So a TCG set that
  cannot finish means 39/37 never comes, with or without the preload fix.
- Checked against the local client copy: the TCG pack holds 57 of the 58 manifest entries with equal CRCs (the 58th,
  `README.txt`, has size 0), and `TradingCardGameAssets.txt` (the 39/16 list) is an entry of the main pack. Nothing needs
  downloading once `manifest.crc` matches, and the main asset server is not involved.
- Before: `run-local-baseline.py` rewrote every URL of `ClientConfig.ini` to `http://127.0.0.1:9/` (a refusing sink) and only
  `IndirectServerAddress` to its asset server, so `TcgServerAddress` pointed at the sink: the card set could not finish.
  There is no Rust asset responder: the "asset responder" is the harness's Python `AssetsHandler`.
- Now: `asset_delivery.baseline_ini` (the harness's ini rewrite, moved out of the script so it is testable) points
  `TcgServerAddress` at `<asset server>/tcg`, and the harness answers `/tcg/manifest.crc` (and `/tcg/manifest.txt.z`, for a
  client that cannot find its local manifest) from the run copy's `tcg/AssetsTcg_manifest.txt`. Any other `/tcg/...`
  request is a 404 and shows in the run's `asset_http_counts`. Path shape: the base has no trailing slash, like the stock
  address, so the client's `<base>/manifest.crc` is `/tcg/manifest.crc` whichever way it joins (a trailing slash would
  risk `/tcg//manifest.crc`; the main set's trailing-slash base is served as `/manifest.crc`, probably because Python's
  HTTP server collapses a leading `//`). (R) that the card set joins like the main set; the next run's `asset_http_counts`
  show the real path.
- Not done (not small or not ours): the players' launcher (its own repository) rewrites every URL to the sink as well and
  has no responder, so players would hit the same stall. Either the launcher serves `/tcg/manifest.crc` on loopback the way
  the harness does, or the gateway grows a tiny HTTP responder (new network surface, lead decision). Treasure War (type 23)
  uses the same address but stays refused.

## Threat note

A hostile client can send 39/5, 39/37 and 39/6 in any order, repeatedly, for any instance. Only packets naming the
session's own card instance reach the run (T782); a 39/5 before a ticket is ignored without changing anything; a 39/37 can
only mint tickets for its own character, each replacing the last (at most one outstanding per character, bounded table),
and a ticket works once, for that character, before its TTL. Nothing changes a save, an item or a coin. The harness
responder serves only `/tcg/manifest.crc` and `/tcg/manifest.txt.z`, built from the run's own manifest bytes; no path from
the request reaches the file system.
