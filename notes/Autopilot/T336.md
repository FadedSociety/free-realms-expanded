## Security note (secure-code-guardian)

A hostile client can still send a 26/10 naming any opening actor GUID with any
selection, 26/8, 39/x frames, the blocked 26/13/36/10/42 families, or chat.

- The handler resolves the GUID in the server-owned opening actor list and
  checks `actor.kind != "enemy"`, the zone and the 12 m interaction radius
  before any dispatch; a bad selection is silently ignored, and a lead/actor
  menu request only opens the server menu.
- For a craft actor the new helper checks, in order, the active profile, the
  pending opening objective, the exact requirement counts from the server
  inventory, and then the service's learned/rank/inputs check; a refusal is one
  fixed server sentence, or the service's existing `Err`, before any mutation.
  The whole handler runs on the staged `Gameplay` clone, which the gateway drops
  on `Err` or refusal-commit, so no item, material, clock, run or save changes.
- For a gather actor the local drop requires a strictly increased opening count
  (server-quantified event), the matching loaded service and the active job.
  It grants fixed server rows through `grant_reward`; no client quantity or
  drop id is read. Duplicate/completed, out-of-range, wrong-job and refused
  interactions pay nothing (tests assert inventory, opening counts and the
  serialized save).
- No new `unwrap` on client data. The service `Option` is content state and the
  call site checks `is_some` before the helper; the guarded `unwrap`s are the
  same ones the old arms used after the same check.
