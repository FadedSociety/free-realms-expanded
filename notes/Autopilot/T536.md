# T536: permanent dance spots at two world radios

Sanctuary-main turns two world radios (Npcs.json 33617 and 33838, model 185, BoomboxItemId 48244)
into permanent dance spots. This task draws both radios and makes them permanent XVD-S boxes: a
player in range dances the row's clips and stops on leaving; the box never expires and never sends
an AddNpc, poof, song or removal (the prop is an ordinary NPC).

The fleet research pack (`lab/fleet/out/brief-research/T536.md`) was stale: it said no boombox code
existed. The boombox catalogue (T459), pressed boxes (T461), synchronized dance (T463) and
independent clips (T494) all exist at the workspace tip `c7f08e92`, so this builds on them. This
attempt applied the review patch onto that tip; it applied cleanly (no `.rej`/`.orig`).

## Threat note (secure-code-guardian)

Nothing a client sends reaches this code: radios come from authored content read at startup, and
the dance tick reads only server-side positions and models. A hostile client can walk into range,
which only plays an animation it could already get from any pressed box; it cannot name a box, a
catalogue item, a model or a packet field. A content row with a bad item id cannot load, so a typo
cannot silently create a dead dance spot. The set is small (two boxes), nothing is saved, and the
per-tick cost is bounded by the live-box count. No auth, session, transport, economy or role code
is touched.

## Checklist

1. A refusal changes nothing: the only refusal is the startup load error; `permanent` fills a local
   value and returns `Err`, so the world is never replaced (`Server::new` fails). Tested by both
   canary 2 and `boombox_radios::a_row_naming...`; no menu, offer, attempt, item or cooldown exists
   on this path.
2. Rollback covers all state: `Boomboxes` lives inside the cloned `SharedWorld`; permanent boxes add
   no side table (`fixed` is a `Boomboxes` field).
3. Deltas, not snapshots: nothing captured earlier is restored; a restart rebuilds boxes only, and
   the existing fault path already clears temporary models.
4. Busy rules: a radio is scenery, not an activity; it adds no `Occupation` row. Dancers are
   refused by the existing owner map when mounted or out of range; tested.
5. Every entry path is gated: one startup load (`Server::new`) and one tick; both are tested through
   the real functions. There is no NPC-menu, event or reconnect path to the boxes.
6. Reachable in production: `Server::new` calls `boombox_routing::load`; the gateway test drives
   the real `tick` with arrived sessions and a real `Scene`, and the startup test drives `load`
   with real `Options`.
7. Survives reconnect: nothing is saved; a session that arrives later simply finds the prop in the
   NPC list and dances on the next tick. The gateway test walks the dancer out and back in; the
   restart test rebuilds the boxes with no dancer state.
8. Every exit path restores the player: leaving range, mounting, disconnect and zoning release
   through the existing `release_unowned` path (walk-out and walk-back test); a permanent box itself
   has no exit.
9. Economy: no items, coins or rewards; no client quantity or id is read.
10. Wire format: unchanged. The only new use is the existing 35/63 encoder, re-verified against
    `0x00919c90` -> `0x008fc2d0` -> `0x008db2a0` this run; the prop uses the existing extras AddNpc
    (`0x00921a10`).
11. Unique ids: the prop guids are Sanctuary's actor guids, and `content_check --strict`'s
    cross-actor guid duplicate rule reports nothing for them; they also differ from the `BOOM` box
    tag.
12. Others see changes: dancers are sent to the dancer and every session that knows them via the
    existing `audience` rule; a dedicated viewer test covers it.
13. Content works end to end: both rows load, bind to catalogue row 48244, draw as a box, and dance
    a player; the assertions are on the animation packets and the idle on leaving.
14. Values live in data: range, priority, clips and standing group come from the catalogue row;
    permanent ignores its duration. The zone reuses `world::OPEN_WORLD_ZONE`.
15. Canaries break production code: both canaries above broke production code and failed the
    tests; each was reverted byte-identically.
16. Session plumbing untouched: one startup line; no session creation, teardown, transaction or
    save ordering change.
17. One player's error never stops the server: no new `?` in the tick; the existing `contain`
    wrapper turns a fault into a restart that keeps the permanent boxes. The load `?` is startup.
18. A type's rules live on the type: `Placed.ends_ms` documents that `None` is permanent and
    `Placed::permanent` is its single reader; `ExtraNpc::drawn` is the one drawn rule;
    `BoomboxProp` documents what it carries.
19. Hot paths stay cheap: with no box the tick returns at once; with the two radios it does two
    `nearby_sessions` calls and the existing owner pass per tick, with no new per-message
    allocation beyond the two small `Placed` values cloned with the world (empty `add`, shared
    `Arc` catalogue row, no dance state until a player is near).
