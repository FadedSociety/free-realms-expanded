## What was wrong, and the patterns behind it

The original pass knew more than it used: `nmq show` already printed the vtable-slot binding of
every virtual method, and the two inbound dispatchers outside the shard (`00aa36c0` for family 41,
`00aa2560` for family 26, `00aa2980` for the matchmaking family) call the constructors and
destructors of one packet class per sub-opcode case. Three mistake patterns were fixed:

1. **Generic destructor labels for class-specific copies.** `BaseEncounterPacket::BaseDtorChain`
   / `ScalarDeletingDtorBody` names were replaced by the class each copy actually serves, taken
   from the vtable slot binding (`00a99f60`, `00a9a190`, `00a9a280`, `00a9a2f0`, `00a9a3d0`,
   `00a9a440`, `00a9a510`, `00a9a5e0`, `00a99cb0`, `00a99d30`, `00a9ad90`, ...) or from the
   dispatcher case pairing (`00a98a20`, `00a98a70`, `00a98ac0`, `00a98b40`, `00a98bf0`,
   `00a98ca0`, `00a98cf0`, `00a98da0`, `00a98df0`, `00a98ea0`, `00a98f50`, `00a986f0`,
   `00a98750`, `00a9b7e0`, `00a99070`, `00a99120`, `00a99170`, `00a991c0`). The shared base
   destructor really is `008a3040`/`008a3100` (accepted elsewhere), so copies in this shard must
   not be labelled with the base class.
2. **Wire direction.** A packet object constructed in an inbound parse path is not a send. The
   family-41 constructors (`00a989c0`, `00a98b90`, `00a98c40`, `00a98d40`, `00a98e40`,
   `00a98ef0`, `00a9a0b0`, `00a9a200`, `00a9b990`, `00a9c300`, `00a99e10`, `00a99ef0`), the
   family-26 constructors (`00a98620`, `00a98680`, `00a987a0`, `00a99b60`, `00a99bd0`,
   `00a99cd0`, `00a9ad20`, `00a9b650`, `00a9b850`, `00a9c1c0`) and the matchmaking constructors
   (`00a98fa0`, `00a99010`, `00a990c0`, `00a9a4b0`, `00a9a580`) are now `recv`. Send remains
   where a builder really sends: the duel-invitation response `00a97c10` (via helper
   `00a96140`), the group-encounter responses `00a97720`/`00a979a0` and the minigame invite
   `00a97cc0` (via `00a96250`).
3. **Decompiler cookie misreads.** "Calls X on a stack local" was wrong wherever the callee
   receives its argument in ECX: `00a994c0` (constructs a `MatchmakingQueueDefinition` in place
   via `0106e850`), `00a986f0` (Target sub-object destructor `0101b370`), `00a98930`
   (reward-bundle destructor `0103d010`), `00a99ab0` (sub-object constructor `01062540`),
   `00a9c110` (list member at +0x20), `00a9c270` (member at +0x18), `00a9c5b0`, `00a9c660`.
   Raw-byte decoding settled each one.

  9, 0xc, 0x16, 0x19, 0x1c, 0x27; `00a9d360` is the PlaySoundIdOnTarget body reader.
* **SoeUtil containers/strings** (`lib.soeutil*`, `engine.containers`, `engine.mem`): the
  `Array<T,N,1>` vtable is [0] scalar deleting dtor, [1] allocate/grow buffer, [2] free buffer,
  [3] swap-with-other (field swap for `N=0`, copy-through-temporary for `N=4`/`16`); `List<...>`

  buffer with heap fallback. The growth policy in `00a9a710`/`00a9a890` is x5/4 when growing,
  keep when capacity <= 4/3 of the request, x6/5 when shrinking (the original record had the
  ratios inverted).
* UI/quest odds and ends: `UIProcessor` ctor/dtor/scalar-deleting-dtor (`00a97450`, `00a98020`,
  `00a98250`), `GroupEncounterRespondToInvite(Matchmaking)` (`00a97720`, `00a979a0`),

## Cross-function packet and server-contract inferences

* The family-41 sub-opcode space is used in both directions: 41/0x69 is built by `00a97c10` for
  send and also parsed by dispatcher case 0x69, which prints the "DuelDeclined" string when the
  accept byte is zero. `00a879f0` is the shared 0x69 constructor; `00a97c10` fills record+0x10
  from entry+0xc10, +0x18/+0x1c from two dwords and +0x20 from the accept byte, and sends only
  while entry+0x280 is nonzero.
* Dispatcher case 0x6b (`00a98c40`/`00a98ca0`) writes entry+0xc10, which is exactly the field
  `00a97c10` reads back - the two paths share the same encounter-entry object.
* Commands 26/3 (`00a99bd0`) and 26/28 (`00a9ad20`) match the base-command dialog family that
  the 071 note recovered from the supplied server enum; the client parses them, so a replacement
  server must emit them, not expect them.
* Server-side hypothesis for 41/2 (labelled as such in the record): the trailing boolean byte
  controls tutorial mode on the client (`player+0x780`), per the captured retail frame; the
  reconstructed cave already exercises this.

## Open questions

* `00a988e0` (two-store base-dtor copy) has no direct call site at all - only EH funclet
  `015c1440` - so its derived class stays unbound.
* Class identities of the plain destructors that rest on dispatcher case pairing
  (`00a98a20` ... `00a98f50`, `00a986f0`, `00a98750`, `00a9b7e0`, `00a99070`/`00a99120`/
  `00a99170`/`00a991c0`) are `likely`, not `confirmed`: the pairing is strong but the bodies
  themselves carry only base vtables.
* `00a9c8a0`/`00a9c6c0` implement the exchange by copying through a scratch
  `Array<...,0,1>`; the template's real method name is unknown, so the names state the observed
  swap semantics.
* Whether `00a9c800`'s deque is the command-history deque (caller `00a9e480` uses it with count
  1 at a 100-element limit) remains unproven.

## Recommendation to other shards

Any shard containing `BaseEncounterPacket::*` / `BaseCommandPacket::*` names for bodies that
only store base vtables should be re-checked against `vslots` and against the three dispatchers
(`00aa36c0` family 41, `00aa2560` family 26, `00aa2980` family 0x8d); the generic names are
almost always a per-class copy the dispatcher pairs with a known constructor.
