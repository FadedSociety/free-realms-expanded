## Threat note (secure-code-guardian)

Attack surface: family 53 subtype 32, an 8-byte client body (definition u32, tint u32), plus the
save envelope it can trigger. A hostile client could send:
- a truncated/zero subtype or zero definition: `PetRequest::decode` refuses (wrong length, zero
  item definition); an unknown subtype decodes to `None` and is ignored;
- a definition/tint pair that does not match an owned instance: `owned_item_for_record` /
  `adopt_with_replies` refuse; `tests/pet_routing.rs`'s wrong-tint and no-certificate tests
  assert inventory, roster, actor and save bytes unchanged;
- a certificate that is not a configured pet item: `definition_for_item` refuses;
- a replay after the certificate is spent: no owned instance, refused without mutation;
- an adoption while another activity runs: `PetBusy` through the existing
  `Gameplay::blocks(gates.pets)` table;
- a save-failure race (server disk/reader): `commit_outcome` returns `Err` before installing the
  staged gateway/world, so the certificate is not spent and no pet or roster entry exists; the
  early-install canary proves the test catches a regression here.
The server never trusts a client pet id from subtype 32 (the two words are an item record),
never allocates an instance id from client bytes, and the save path is host-owned. No secrets,
no player names or chat text, no new filesystem path derived from client input. This diff is
test-only, so it adds no attack surface; it pins the refusal, rollback, restart and reconnect
behaviour above.
