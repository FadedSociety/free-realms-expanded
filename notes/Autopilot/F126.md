# F126: T014 reload atomicity

## Result

The single BLOCKER in
`lab/autopilot/reviews/7ef81f2-T014.md` is valid and fixed. `realm reload all`
previously loaded behaviour presets into the live encounter before the enemy
reload refused because shared fields were enabled. The gateway then committed
the staged gameplay clone and the live encounter kept the earlier partial
change.

`Gameplay::reload_content` now runs the complete request on a clone. It commits
only the four subsystems a reload owns (`abilities`, `encounter`, `activities`
and `npc_visibility`) after every requested loader succeeds, then merges the
staged `Outcome`. A failure publishes neither state nor reload-generated
packets.

## Evidence and rules

- No protocol, opcode, packet field or client reader changed, so no IDA query
  was needed for this fix. The existing chat request path is unchanged.
- (R) Content reload is a developer operation, not a recovered client feature.
  Its atomic admission rule is local reconstruction: one request is all or
  nothing.
- `reload_field_enemies` already refuses while a shared field exists
  (`encounter.rs`); the new boundary preserves that refusal instead of
  partially applying the preceding behaviour load.

## Changes

- `prototype/osfr-tools/src/gameplay.rs:4530`: `reload_content` stages a
  `Gameplay` clone and a fresh `Outcome`. It runs the existing loader body in
  `reload_content_in_place`, commits only the reload-owned fields on success,
  and then merges every staged outcome field.
- `prototype/osfr-tools/src/gameplay.rs:10342`: added
  `refused_reload_all_keeps_behaviour_and_shared_field_state`. It enables
  shared fields, changes the `field_roamer` preset in a scratch content set,
  omits `field_battles.json`, and drives both the direct reload API and the real
  `realm reload all` chat path. It asserts unchanged resolved behaviour,
  shared actor rows/order, queued replies, `changed`, and the exact error-only
  command reply.

## Security decision

Threat: a client can send the chat command without owning the requested state
change, and a malformed or unavailable content file can fail midway. Existing
role checks still require a builder/admin route and remain unchanged. The
server reads only its configured content directory, never a client path. The
new transaction prevents a refused reload from changing live NPC,
behaviour, activity or visibility state. The regression checks a rejection
through the same `handle_in_world` path the gateway calls.

## Checklist

1. Refusal changes nothing: covered by the regression, including direct queued
   replies and the command path. The canary exercises the production partial
   commit.
2. Rollback covers all state: the whole request runs on a clone; only the four
   reload-owned fields are committed after success. No reload path mutates the
   shared `NpcInteraction` mutex or other escaping state.
3. Apply deltas, never restore unrelated snapshots: the old whole-`Gameplay`
   assignment was narrowed to `abilities`, `encounter`, `activities` and
   `npc_visibility`; other live character state is untouched.
4. Busy rules are mutual: no activity start rule changed. Existing enemy reload
   shared-field/active-encounter refusals remain in force.
5. Every entry path is gated: direct and chat-command paths both use the same
   `reload_content` transaction; existing role checks are unchanged.
6. Reachable in production: the regression sends a real `15/1` chat command
   through `handle_in_world`, the path the gateway dispatches to.
7. Survives reconnect: reload staging is session-local content state; no new
   persisted field was introduced.
8. Every exit restores the player: a refusal returns the normal error reply and
   leaves player/activity state untouched.
9. Economy safety: no reward, item, coins or client quantity path is involved.
   The command still requires the existing builder/admin gate.
10. Wire format: no packet or field layout changed.
11. Unique ids: no id allocation or lifecycle id changed.
12. Others see changes: no new player-visible mutation path; successful reloads
    still use the existing visibility and packet publication.
13. Content works end to end: the regression loads the shipped starting field,
    verifies the grouped actor remains resolved, and checks the exact refusal.
14. Values live in data: no limits, timers or tuning constants changed.
15. Canaries break production code: recorded above.
16. Session plumbing: `gateway.rs`, `osfr-gateway.rs`, session creation,
    teardown, transaction ordering and save ordering were not changed.
17. One player's error never stops the server: `realm reload` runs on the
    requesting session's `Gameplay` clone. `reload_content` returns
    `io::Result` to the `["reload", ..]` arm in `developer_cheat`, which turns
    the error into the command's chat reply (`. Nothing changed.`); it never
    uses `?` through `handle_in_world`, and no shared tick, reward, XP or drop
    path calls it. The `developer_cheat` and `handle_in_world_inner` chain is
    the one the gateway dispatches (traced with the code graph; see Structure).
18. A type's rules live on the type: F126 narrowed the commit from the whole
    `Gameplay` clone to the four reload-owned fields. Since F187 the list is
    named in the `gameplay/content_reload.rs` module doc (`abilities`,
    `encounter`, `activities`, `npc_visibility`) and the all-or-nothing rule is
    marked `(R)`. F159's note claimed that doc named the fields; it did not, and
    F187 fixed both the doc and this note. The staged `Outcome` merge is now
    `Outcome::absorb` in `gameplay.rs`, whose destructuring names every field so
    a new `Outcome` field fails to compile until its merge rule is decided.
19. Hot paths stay cheap: reload is a developer chat command, not per-tick or
    per-packet. The `Gameplay` clone is paid only when the command runs; the
    normal tick path is unchanged.
