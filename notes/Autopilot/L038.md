## Client evidence

- `AnimationGroups.xml:874-880`: `<AnimationGroup name="emo_dance" id="3200">` holds `emo_dance_basic`,
  `emo_dance_01`..`04`, each with `weight="1.0"`.
- `AnimationTypes.xml:1156-1160`: those slots are ids 3201 and 3211-3214. All five are `type="4" priority="1"
  hideSlotType="1"`, with no `freezeMovement` and no `disableBoneMasking`. There is no slot row with id 3200,
  so the old note was right that 3200 is not a slot. It is a group.
- `0x007a9db0` (AnimationGroupTableLoad) reads every `AnimationGroup` (name, id, fallback) into a hash table at
  `this[(u8)id + 4180]` (chain at +4, id at +8), with each `AnimationSlot`/`AnimationGroupSlot` weight.
- `0x007829a0` resolves an animation id through that same table (`v4[(u8)a2 + 4180]`, matching on `v6[2] == a2`).
  An id that is not a group is returned unchanged as a slot id. For a group, it picks a member slot by
  `weight * 100`.
- `0x0096c780` (actor play) calls `0x007829a0(a2, 0)`. If no slot comes back, it logs "Couldn't play
  animation=%d". So 3200 plays one of the five dance slots.
- `0x00b966e0` (BaseQuickChatPacket_Unpack), subtypes 2 and 3: it looks up the phrase row by the received phrase
  id and the sender actor by guid. When the row's animation id (`row+12`) is > 0, it calls `0x0096c780`. The wire
  packet carries only the phrase id, and the receiver takes the animation from its own table. This confirms that
  the server only relays.

## Security

Trust boundary touched: the quick-chat route, `osfr-gateway route_quick_chat`, then
`QuickChatCatalog::authorize_emote`, then `piece_093::validate_emote_phrase`. The graph shows it is the only
production caller path.

- **Client-controlled input:** only the phrase id (i32) in 67/2 and 67/3. This change does not touch it.
  `decode_quick_chat_request` still refuses ids absent from the startup table, and `authorize_emote` maps a
  missing id to `UnknownQuickChatId`.
- **The animation id is server data.** It comes from the server-held startup row and never from the sender. A
  hostile client cannot pick 3200 or any other animation. It can only pick phrase 184, which the real client UI
  already offers.
- **Refusals change nothing.** `authorize_emote` is a pure check on `&self` plus a `Copy` context. A refusal is
  still a silent `Vec::new()` drop in the gateway, with no reply bytes and no state change. No refusal path was
  added; one was removed.
- **No new oracle or enumeration.** Dance now behaves like every other emote: delivered when standing, silently
  dropped when mounted. The sender still cannot tell a mounted drop from any other drop. An unknown phrase id is
  still dropped with no reply (`ChatError::client_reply` returns `None` for everything except
  `PlayerNotOnline`).
- **Mount and freeze rules are unchanged.** Dance is mount-gated like every other emote (tested). None of the
  emo_dance slots has `freezeMovement`, so moving does not block it. That matches every non-outfit emote.
- **No fallback opened.** Naming the group adds one exact `(3200, "emo_dance")` row. An id with neither a slot
  nor a group has no name. It cannot ride the Dance phrase (`AnimationMismatch`) and is refused outside the block
  (`ForeignAnimation`).
- No saves, no persisted state, no logs, no secrets, no coins or items, no roles.

Threat note: a hostile client can send phrase 184 at any rate. The result is the same relay as any emote phrase:
the same recipient resolution, ignore lists, channel settings and the existing chat throttling. Nothing new is
amplified, because the packet a receiver gets has the same layout and size as any other quick-chat echo.
