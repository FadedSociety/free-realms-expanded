# T537: a dancer's summoned pet dances beside them

A boombox that has a player dancing also puts their summoned pet into the dance: while the owner
dances, the pet is sent 35/8 `play` (base flag clear) of animation 3201 on its own actor guid, to
the owner and everyone near them, repeating every 4 s plus a random 0.5-2 s gap. The values live in
a new top-level `pets` block in `boomboxes.json`; without the block nothing is ever sent.

The fleet research pack (`lab/fleet/out/brief-research/T537.md`) was stale: it said the T459 -> T461
-> T463 chain was unmerged. The pack checked tip `1e2def7`; this workspace is cut from `f5dc6abd`,
where the catalogue, pressed boxes, synchronized/independent dances, the transform row and the T536
permanent radios all exist, and `notes/Autopilot/T536.md` documents the last of them. This builds on
all of it.

## Reference behaviour (Sanctuary, R)

`src/Sanctuary.Game/Entities/PlayerPet.cs`: `:182-186` group 3201, duration 4000 ms, gap 500-2000 ms,
join delay up to 3000 ms; `:280` the dance list is that one pair; `:572-592` the next play is
`now + duration + Random.Next(gapMin, gapMax)` while the owner is in dance range, and the pet idles
while the owner moves, it does not face the owner, or it is in water. The first play here is
immediate (R), and the three idle gates are not ported (see Open).

## Decisions and (R) markers

- (R) Timing is Sanctuary's measurement (4000 ms + 500-2000 ms), not a client constant; the client
  animation is 3201. All three are data.
- (R) The first play is immediate. Sanctuary schedules a joining pet up to 3 s later
  (`PetDanceJoinMaxDelayMs 3000`); the brief asks for "on schedule", and an immediate first play is
  the smaller rule.
- (R) Owner movement, pet facing and pet water are not gated. `SharedWorld.pets` carries a position
  but the tick has no pet heading or water flag; Sanctuary's gates would need new state. Documented
  as an open gap, not half-built.
- (R) A transform box's dancer also has their pet dance, because they are dancing (35/8 base); a
  mounted transformed rider is not dancing and gets nothing.
- `pet_gap_ms` is drawn uniformly in `min_ms..=max_ms` (inclusive). Sanctuary's `Random.Next(min,
  max)` excludes the top; the difference is 1 ms of a 500-2000 ms window.
- The block is `Arc`-shared and stored in `Boomboxes`, which is cloned with `SharedWorld` on every
  application message: the clone bumps one refcount instead of duplicating the provenance strings.

## Threat note (secure-code-guardian)

- Attack surface: no new packet, handler, selector or application family. The only client-triggered
  inputs are the existing box press (36/10) and the pet summon/dismiss (53/4, 53/32), both already
  gated (owned/bound/ready item, alive, not mounted, `can_place_box`; owned pet or adoption
  certificate, not busy). The tick then reads server-side state only.
- A hostile client cannot name the animated actor: the guid is `PetPresence.actor_guid`, produced by
  the server (`owner ^ PET_GUID_TAG`, one active pet per owner) and never taken from a request. It
  cannot pick the animation, the interval or the gap (content + server RNG), cannot fan the packet
  to a stranger (the `audience` rule: the owner plus sessions near them that know the character),
  and cannot make a pet that is not summoned dance (the entry is removed when the world's pet table
  loses the owner). It cannot amplify: at most one 21-byte packet per dancing owner per 4500 ms per
  recipient, and only while it is already dancing at a box it legitimately pressed.
- Refusals stay silent and change nothing: a dismissed/absent pet or a session that left is dropped
  from the clock map without a packet. Malformed content fails the startup load (fail closed).
- No economy, auth, session, role or save code is touched.

## Checklist

1. A refusal changes nothing. There is no new refusal: the pet dance runs after the commit, inside
   the tick, and mutates only its own in-memory clock. It consumes no menu, offer, attempt, item or
   cooldown, so the refusal invariant is vacuous here; the existing box-press refusals still pass
   (`t461_*` in the bin target). The one refusal-like case, a dismissing recipient queue, is a
   delivery failure, not a state change, and is asserted to skip only that recipient.
2. Rollback covers all state: `pet_dancers` and `pet_dance` are fields of `Boomboxes` inside the
   cloned `SharedWorld`; a rolled-back message leaves no clock. No `Rc`/`RefCell`/`Arc<Mutex>` side
   table was added (`Arc<PetDance>` is read-only shared data).
3. Deltas, not snapshots: the pass writes `next_ms` in place and never restores inventory, coins or
   position. The gateway test snapshots the saved gameplay state before the dance and asserts it is
   byte-identical after the pet has played twice and been dismissed.
4. Busy rules are mutual: this is not an activity, it has no start/stop, warp, ride, pet or location
   gate and adds no `Occupation` variant. It can only run while the player is already dancing at a
   box, whose press is gated by the existing busy check. No `occupation.rs` change is needed.
5. Every entry path is gated: the only entry is the shared tick; a dancer must win a box through the
   existing owner map (range, not mounted, model allowed), and the pet must be in `world.pets`,
   which only the pet service writes after its own gates. No client request starts a pet dance.
6. Reachable in production, tested through it: the gateway test builds a real `Scene`, loads the
   boxes with the production `load(&options)`, presses through 36/10 `dispatch_message`, summons the
   pet through 53/32 (adopting the certificate's pet), ticks `boombox_routing::tick`, and dismisses
   through 53/4. No internals are called and no logic is copied.
7. Survives reconnect: nothing is saved, which is right for an animation. The pet actor is session
   state (F161: "the active actor is session state, not save state"), so a reconnecting player
   re-summons and the next tick schedules the dance from scratch. Tested twice: the unit test's
   disconnect-then-rejoin mid-dance (no packet to the leaver, an immediate play after the rejoin),
   and `saved_state()` byte-equality across the whole gateway dance (nothing written).
8. Every exit path restores the player: the pet dance changes nothing on the player (no transform,
   no location, no busy flag). Box end, walking out, dismissal and disconnect all drop the clock and
   send nothing more (all four are tested); mounting only removes the dancer from the tick's winner
   map, so the clock is dropped on the next tick by the same path.
9. Economy safety: no items, coins, rewards or client-quantity/id reads. The pet dance touches no
   inventory; the certificate is spent by the pre-existing adoption path, unchanged, and the
   saved-state assertion above pins that the dance itself writes nothing.
10. Wire format matches the client reader exactly: 21 bytes, `35 00 08 00`, u64 guid, i32 3201,
    i32 0, u8 0, asserted byte for byte against the reader-derived layout (not against the encoder);
    reader `0x00908a50`, dispatch `0x009315e7`, play path `0x0096c780`.
11. Unique ids: the animation names the pet's own `PetPresence.actor_guid`, the guid its AddNpc
    spawned (owner ^ tag, one active pet per owner; never `1`, never a world instance). The unit
    test uses an actor id that is not owner-derived, so a recomputation would fail it.
12. Others see changes: the play goes to the owner and every nearby session that knows the owner
    through the existing `audience` rule, tested with a near viewer that hears it and a far session
    that does not.
13. Content works end to end: the shipped block loads and its 3201 is a client slot and a group; the
    gateway test asserts the pet, the owner and the viewer actually receive the packet, and that the
    dismissal stops it. The per-model clip list is in the note above.
14. Values live in data: animation, dance length and gap bounds are in `boomboxes.json`, with loader
    bounds (`> 0`, `1..=600000`, `min <= max`, provenance present) and a refusal case for each.
15. Canaries break production code: both canaries above changed `boombox.rs` itself and failed the
    tests; each was reverted and the suite re-run green.
16. Session plumbing untouched: no session creation, teardown, transaction or save ordering change
    in `bin/osfr-gateway.rs` or `gateway.rs`; the hub lines are 0.
17. One player's error never stops the server: no new `?` in the tick; the arithmetic saturates; the
    existing `contain` wrapper still turns a boombox-tick fault into a logged restart. A refusing
    recipient is isolated by `deliver` (logged, that recipient skipped) and tested.
18. A type's rules live on the type: `PetDance::valid` is the one bounds rule and `PetDance::gap_ms`
    the one draw; `PetGap` documents its inclusive range; `Boomboxes.pet_dance` documents that
    `None` means off and `Boomboxes.pet_dancers` that it holds a due time per session; `Catalogue`
    documents why both fields are shared.
19. Hot paths stay cheap: with the block absent the tick costs one `Option::is_some` check. With it
    present, the pass reuses the tick's winner map (no set, no vector) and takes/retains an empty
    `BTreeMap` until a dancer actually has a pet, so it allocates nothing when no pet is out; an
    entry allocates once per dancing pet. Each play clones one 21-byte packet per recipient, once
    per 4.5-6 s. The per-message `SharedWorld` clone bumps one `Arc` instead of copying the block.
