### Not ported, and why

- a2's `checked_add` counter: F189's wrapping increment cannot alias a live
  pending row (the longest pending window is 600 s; 2^32 invites cannot fit in
  it at any server load), and the checked-add path would silently drop invites
  because `route_application` maps `Err` to an empty reply. Keeping the
  integrated code avoids a new refusal path for no reachable benefit. The
  separate restart-reset gap is recorded below.
- a2's 40/4 notice carrying the generation: the client's case-4 handler never
  reads the record dword (evidence below), and the group id is the correct
  value in a group notice. The F189 review reached the same conclusion.
- a2's test hunks: F189 already contains equivalent or stronger regressions,
  through the same real paths:
  - `t020_group_routing::same_group_reinvitation_binds_responses_to_the_new_generation`
    drives a stale accept and a stale decline through
    `Session::route_application`, asserts 40/5 code 3, no 40/4, the unchanged
    pending row, membership, `group_of` and profiles, then accepts the
    replacement.
  - `group_invite_expiry::same_group_reinvitation_gets_a_fresh_generation_and_refuses_the_old_one`
    covers the service, including the fresh-generation accept.
  Duplicating these would add test lines with no new coverage.

decompile 0x00a983b0` exited 1 with `no answer from the IDA broker
(lab/autopilot/ida_broker.py) within 10 minutes`. I used the pinned IDA-derived

and raw capstone disassembly of the same addresses; the reviewer's IDA

inference and disassembly, not a live decompile.

- 40/1 reader `00921640` -> `00912090` -> `008fca60`: two i16, two
  guid/NameData records, then one i32 into record +0x120 (dword index 0x48),
  then five i32 into +0x138..+0x148.
- 40/1 dispatcher `0093daf0` case 1, raw disassembly at `0093dc0b`:
  `mov ecx,[esp+0x3f0]` (packet +0x130) then `mov [eax+0x120],ecx` (the new
  pop-up record). This is the only access to the packet dword in the invite
  body (`0093db8d`..`0093e028`).
- 40/4 answer `00a983b0`: constructs `GroupPacketGroupAccept` (`008dcf30`),
  copy-assigns the stored pop-up record with `00a8b640`, sends with
  `00a98280`. `00a8b640` copies `param_1[0x48] = param_2[0x48]` (record
  +0x120).
- 40/4 writer `00a97250` -> `00a95c50`: two u16, the shared record (including
  +0x120), the accept byte from +0x138, then five dwords from +0x13c..+0x148.
  The server's `encode_group_invite` and `encode_group_accept_notice` order
  matches.
- 40/4 dispatcher `0093daf0` case 4 at `0093e52d`: reads the accept byte at
  `[esp+0x3f8]` (packet +0x138). A raw disassembly scan of the case body found
  no `[esp+0x3f0]` access; the packet pointer is passed only to the constructor
  (`0093e52d`), reader (`0093e54b`) and destructor (`0093e6db`). The client
  therefore treats the notice's dword as opaque, so the server-built notice can
  keep the group id.

Conclusion: record +0x120 / wire +0x130 is the identifier that survives the
client's read/copy/write path. A fresh generation there makes a same-leader,
same-group replacement distinguishable from the expired pop-up without
colliding with the live group id (which the client never reads from this
pop-up).

## Reconstructed rules

- `(R)` The 40/1 record dword is the per-invitation generation.
- `(R)` A 40/4 answer is valid only when the echoed dword equals the pending
  generation. After the existing lazy expiry, a mismatch answers 40/5 code 3
  without consuming the pending row or changing membership.
- `(R)` The server-built 40/4 notice keeps the group id in the record dword;
  the recovered client case-4 handler never reads it.
- `(R)` Pending invitations and generations are volatile; no persisted format
  change.

## Security threat note (secure-code-guardian)

A hostile client can replay a 40/4 answer for an expired invitation after the
same leader has re-invited the same target into the same group. Before the fix
every echoed field repeated, so the replay could join the target or delete the
replacement. The server also accepts any client u32 in that field.

The fix refuses every mismatch with 40/5 code 3 before consuming the pending
row or mutating membership; the pending row is keyed by the authenticated
character guid, never by a packet identity. A forged value (zero, a random u32,
another invitation's value) and a truncated or malformed 40/4 are refused by
the existing bounded parser and the generation check. The generation is
volatile and increments with wrapping addition; a wrap to `1` cannot collide
with a pending row because 2^32 invites cannot elapse inside the configured
600 s maximum TTL. No item, coin, reward, role, chat or persisted path is
touched.
