## 2. Packet and server-contract inferences that span functions

* **Envelope.** `FUN_00b66830` reads opcode then sub-opcode as two u16 into +4/+8 - the same two
  fields `FUN_00b60910` writes on the client side. The note `Research/Fishing Restoration.md`
  (and the independent review note) documents the same envelope and the writer `FUN_00b69550`.
* **Direction split.** Sub-types 2/5/6/7/15 are constructed on the request paths
  (RegisterPlayerRequest, CastAnim, Cast, ReelIn, Special), while 1/8/10/12/13/14/16 are constructed
  in the receive dispatcher `FUN_00b6cd80`. The notes agree, and 00b627c0/00b62960 are constructed
  both by a request builder and by the dispatcher because the server echoes casts and reels to the
  other fishermen in range. Server contract: the server accepted a registration from one handle,
  owned the cast outcome (answer = bobber spawn sub 8), owned the landing (answer = result sub 14)
  and broadcast sub 5/7 echoes; none of that logic survives, so these links are the recovered
  client-side half of the contract.
* **Player configuration (sub 3).** `FUN_00b65880` fills 16 scalar fields of the config object from
  the server block, called from the sub-3 handler `FUN_00b6a170`. The values (which rods, holes and
  lures a character may use) came from the original server; the client only mirrored them.
* **Result (sub 14).** `FUN_00b64ec0` builds FishingPacketFishingResult with three SoeUtil::IString
  members at +0x28/+0x54/+0x64 (destroyed by `FUN_00b64f50`), so the result's name/alias strings are
  server-authored; the note's recovered field order stays a candidate and the reader
  (`FUN_00b66be0`) is outside this shard.
* **Proxied fisherman records.** `FUN_00b64300` is lookup-or-create by actor handle pair over the
  list at +0x1e8, and the same list is what the dispatcher, the state machine and the per-frame
  update all consult - so the client's view of every other fisherman is rebuilt purely from
  opcode 138 traffic (sub 1/5/7/8/10 and the school packets).
* **Presentation is local, outcomes are not.** State +0x1c (5 = hook/reel per the notes) selects the
  launch-vector angle in `FUN_00b640e0` and the interpolation branch in `FUN_00b65fb0`; nothing in
  this shard decides a bite or a catch.

## 3. Conflicts, corrections and caveats against existing notes

1. **State-machine owner name.** `Research/Fishing Restoration.md` attributes the +0x1c state
   machine to "ControllerFishing". In this binary the object that owns +0x1c, the proxied-player
   list at +0x1e8 and the nine sound slots is the RTTI class **FishingProcessor** (vtable 01822a44;
   ctor `FUN_00b69860` initialises every list vtable; dtor `FUN_00b69d40` calls this shard's
   `FUN_00b61290`). `ControllerFishing::vftable` (0181c2c4) exists separately and is referenced only
   from `FUN_00af83d0`, `FUN_00af8500` and `FUN_00af8940`. Both classes may carry a state field at
   the same offset; this shard's records bind every function here to FishingProcessor with that
   caveat stated in the record (`00b64580`).
2. **PetInWater and tile targets.** Note 091's association of `FUN_00b5fcf0` with the follow
   ("pet can go location") path is consistent with the in-shard dispatcher `00b60770`, which routes
   message kind 0x1000 to it; the kind-1 callee `FUN_00b5fbc0` is still unlabelled, so only half of
   that dispatch pair is identified.
3. **Sub-10 wording.** The note calls sub 10 "handle + u32 + two flags"; the reader `FUN_00b66a80`
   actually reads handle + u32 + **two single bytes converted to bools**. Same widths, but the note
   should probably say two bools.
4. **Element type of the 64-byte school list.** `FUN_00b63a90` (insert by copy, links at
   +0x40/+0x44) and `FUN_00b65560` (clear that frees nodes *without* an element destructor) have
   exactly the node geometry of SoeUtil::List<ProxiedFishingSchool>, yet the erase helper
   `FUN_00b647e0` for that list does run the ProxiedFishingSchool destructor. So the school spawn
   path almost certainly stores a POD school record of the same size, not ProxiedFishingSchool
   itself. Flagged in the record for `00b63a90`.
5. **`wire` cannot always be filled mechanically.** The pet family (base 0x35) and the fleet of
   fishing readers carry no opcode constant in their own bytes - the constant lives in the
   constructor or the caller - and the community packet catalogue
   (`lab/native-map/context/packets.tsv`, 494 rows) contains no pet or fishing class at all, so
   neither `wire.packet` nor a verifiable `wire.opcode` exists for: 00b5ffe0, 00b60080, 00b60110,
   00b601a0, 00b60220, 00b602c0, 00b60350, 00b60420, 00b604b0, 00b60610, 00b607e0 (pet senders),
   00b65880, 00b65cc0, 00b66830, 00b66890, 00b668f0, 00b66990, 00b66a00, 00b66a80 (readers).
   Each such record names the packet class and sub-type in `does`/`purpose`, cites the note or
   vtable that pins it, and explains in `open_questions` exactly which callee writes the constant.
   The 14 records that do carry `wire` are the fishing constructors, where the sub-type literal is
   in the function's own code (00b608b0, 00b60910, 00b60c70, 00b60d20, 00b62620, 00b626f0,
   00b627c0, 00b62890, 00b62960, 00b62a30, 00b62b00, 00b62cb0, 00b62d80, 00b64ec0).

## 4. Most important open questions

1. Sub 3/4/11 entry points: this shard holds the sub-3 config reader (`00b65880`) and the model
   entry reader (`00b65cc0`), but the sub-4 fish info and sub-11 spawn-school readers
   (`FUN_00b6ad20`, `FUN_00b69130`, `FUN_00b691d0`, `FUN_00b673b0`) live outside it. Until they are
   mapped, the client fish table and school spawn content stay candidate-only.
2. Identity of the 64-byte school record (see conflict 4) - a POD copy versus ProxiedFishingSchool.
3. The cast parameters behind `00b640e0`: the 4-float point at +0x240..+0x24c, the factors at
   +0x13c/+0x140 and the angle constants (DAT_018227b0, DAT_018001d0, DAT_017649d4) are unresolved,
   so the vector's unit (velocity versus direction) is still an inference.
4. Object identity of the nine emitter slots (+0x320..+0x364, `00b61290`/`00b65040`) and of the
   effect slots +0x304/+0x308/+0x34c/+0x368 in `00b64360`; only the calls made on them are known.
5. The audio trio `00b61580`/`00b615e0`/`00b61640` and the two 5-byte flag setters
   `00b616c0`/`00b616d0` rest on caller/offset evidence only; the mixer class behind +0x8a0 is
   unnamed.
6. `00b628*`/`00b62680` slot-0 destructors are provably bound to their classes, but the packets'
   payload semantics for PetEquipPacket (sub 11) and PetEquipByItemRecordPacket (sub 0x23) are not
   covered by any note and stay unexplained in this shard.
