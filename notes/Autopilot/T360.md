## Security note (secure-code-guardian)

Threat: a hostile client can send 26/8/26/10/26/6/49/1/49/2/49/14 packets and
41/108/41/109/26/42 battle packets. What it can try, and why it is refused:

- **Accept without an offer / forged accept**: `QuestEngine::accept` requires
  `pending_offer == quest` from the same giver and re-runs eligibility. The
  tests send 49/2 with no offer (before and after acceptance) and observe no
  state change.
- **Finish a different quest**: `finish_turnin` requires the server-owned
  `pending_turnin` to equal the client's quest id. A forged id while a real end
  screen is pending is denied and the pending screen is kept; the test asserts
  the save bytes are equal and the correct id still pays (canary).
- **Premature turn-in / replay**: 49/14 before the win is denied; after payment
  the quest is Completed so a replay is inert (state byte-equal).
- **Out-of-range Talk**: the NPC router's `check_range` (12 m) and the marker's
  screen radius gate interactions; an out-of-range click is an `Err` with no
  state change, and the in-range click is the canary.
- **Busy injection**: the shared occupation table refuses interaction while
  the mining movie runs; the refusal changes no byte and the same Talk works
  after the movie is cancelled.
- **Over-cap reward**: 20 coins is representable, and a near-`i32::MAX` wallet
  makes the existing reward transaction refuse atomically (no coins, same
  bytes, pending screen kept). Control with a normal wallet pays once.
- **Duplicate wins**: `realm win` is the admin-gateway seam; `debug_win` requires
  an active run and pays once at the won transition. A second win is inert.
- **No client-supplied quantity or item**: accept and win grant nothing; only
  the authored 49/14 reward runs through `rewards::apply_grant` with bag/profile
  checks and checked arithmetic.

No secret, auth, role or session code is touched. No new trust boundary.
