## Attempt 1 integration failure and its fix

Attempt 1's diff applied cleanly (`git apply --reject` reported every file "Applied cleanly", no
`.rej`/`.orig`). It failed on the new tip at
`t020_group_routing::f234_a_cross_instance_group_member_is_not_healed_or_saved:988` with
"the same-instance member is healed", in the bin suite and the three harnesses that include the bin
(`bot_smoke`, `multiplayer`, `gateway_npc_offer_runtime`).

Cause: a test bug, not the production rule. The test accepted the party invitation with
`response(0, 1, group, true)`, passing the **group id** as the 40/2 token. Since F203 (`invite_epoch`)
the 40/1 generation is a random per-service start value, and `respond_group_invite` compares the
echoed `invite_id` (`src/social_lists.rs:820`), not the group id. The response was therefore refused
(40/5 result 3), B never joined the party, and the same-instance heal loop found no member. The
cross-instance "not healed" assertion passed vacuously for the same reason.

Fix: take the token from the delivered 40/1 (`invited_id(&invited, 1)`), and assert B's group
membership before the refusal, so the cross-instance assertion cannot pass as a solo no-op. The F182
test in the same file already did this; the F234 test now matches it. No production code changed for
this failure; the review's rules and regressions are unchanged.

## What changed, against the review

1. **BLOCKER (false arithmetic claim / dead public-id refusal) — fixed in the owner.**
   `World::available_public_id` was `(1..).find(..).ok_or(InstanceIdsExhausted)`: a
   `RangeFrom<i32>` never yields `None`, so the refusal was dead and the iterator's successor
   overflowed at `i32::MAX` (debug panic) or wrapped (release loop). The scan now takes its end as a
   parameter and production passes the whole positive space:
   `(1..=max)` with `stage_public` calling `available_public_id(i32::MAX)` (`src/world.rs:1125`,
   call at `:1096`). `RangeInclusive` ends without overflowing, so `InstanceIdsExhausted` is
   reachable. The explicit end also lets the regression drive the scan to exhaustion with `max = 3`
   instead of filling the real id space (`src/world.rs:1529`). The two false claims in
   `notes/Autopilot/F182.md` (security note and checklist 17) are corrected in place.

2. **MINOR [TEST] (cross-instance member was untested) — regression added.**
   `f234_a_cross_instance_group_member_is_not_healed_or_saved`
   (`src/bin/osfr_gateway/t020_group_routing.rs:1046`) drives the real `Session::heal_group` with a
   real group: the picker is in zone 0's public instance, the hurt member is in a child instance of
   the same zone. The refused claim must leave the member's health at 100 **and** its save bytes
   unchanged; then the member moves into the picker's instance, a fresh kill heals once, and the
   duplicate kill does not heal again. The party invitation is accepted with the server-issued 40/1
   token (`invited_id`), not the group id, and the test asserts B is in the group first (attempt 1's
   failure; see above).

3. **MINOR [STRUCTURE] (duplicated id predicate) — one owner per rule.**
   `instance_id_free` (`src/world.rs:1107`) is the single base rule (positive, not owned by a live
   instance, not a public scene id); `instance_id_available` (`:1115`) adds the one extra
   reservation the allocators need (a registered zone's own id). Both allocators
   (`available_public_id` and the private `available_instance_id`) use `instance_id_available`;
   `stage_public`'s scene-derived check uses `instance_id_free` so a zone may still take its own id
   for its public instance (the pinned `tests/world.rs` contract that zone 7's public instance is
   id 7). The review's literal "one predicate including zone ids" is not the invariant that was
   there — `public_id_free` did not test zone ids; the zone test lived in the fallback closure — and
   folding it in would have broken that contract. The two-policy split is on the type's helpers,
   with a regression pinning both halves (`src/world.rs:1544`).
   Net: +3 lines in `world.rs` before the inline tests (not the predicted -8); the three doc comments
   and the explicit `max` end account for the difference, and the predicate duplication is gone.

4. **MINOR [CORRECTNESS] (clear keyed on the instance id, not the scene reload) — fixed at the
   commit fact.** `EncounterEngine::bind_run_instance` now takes `scene_reload`
   (`src/encounter.rs:872`) and clears the ground pickups when `scene_reload` is true **or** the
   instance id changed; the held power-up still stays. `Session::commit_outcome` passes
   `outcome.began_zoning` (`src/bin/osfr-gateway.rs:1779`), the fact the gateway already sets for
   every opcode-31 begin-zoning: a safe-location revive (`revive_at_safe_location` returns `zoning`)
   and a host-authorized transfer (including into the current instance) both set it. New regression
   `a_revive_or_same_instance_transfer_reload_discards_ground_pickups`
   (`tests/power_up_drops.rs:400`) proves an ordinary commit (`scene_reload = false`, same instance)
   keeps the drop and the same-instance reload clears it and pays nothing afterwards. The revive
   route's flag is already pinned by `free_revive`'s gateway test (`revived.began_zoning`), and
   `stage_instance_transfer` sets `began_zoning: true` in its outcome for every target, including
   the current instance.

## Security threat note (secure-code-guardian)

Attack surface: the big-heart group heal, ground power-up pickups, public-instance id allocation,
and the begin-zoning commit hook.

- A hostile client cannot fabricate a scene reload: `scene_reload` comes from
  `GatewayOutcome.began_zoning`, which only server-generated zoning sets (`stage_instance_transfer`
  is host-authorized, not packet-routed; `resume` 41/122 only revives the session's own knocked-out
  state at the server checkpoint). A client cannot name an instance, zone, kill id or percent; the
  claim instance comes from `World.players` membership. The stale-heal path this fix closes was a
  server-side gap (a drop surviving a reload), not a client-supplied value.
- The cross-instance heal filter now has a regression that a same-zone/other-instance member is
  neither healed nor saved. The heal still writes only the member's own session snapshot and only
  when the engine reports `changed`.
- Public-instance entry still accepts no client instance id. The allocator's predicates are the
  single owner of id uniqueness; a scene-derived id may be the zone's own id, while every fallback
  and private id must avoid registered zone ids. Arithmetic: the public scan is `1..=max` (total;
  no `i32` successor overflow) and the private cursor stays `checked_add`.
- No new save field, wire format, role, secret or client parsing was added. No new `fs::write`; the
  touched save write is the existing `game_store::save` call in the heal path.
- Refusals change nothing and are asserted: the refused cross-instance heal leaves health and save
  bytes equal; the opt-in socket transfer test already asserts a refused transfer keeps the pickup
  and membership, and the staged-clone commit is unchanged.
