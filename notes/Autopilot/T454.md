## Threat note (secure-code-guardian)

The only client-triggered input this change affects is the existing 53/32 `SendPetSummonByItemId` body
(`00b60110`: definition u32, tint u32) and the 53/4/6/9/24 variants. A hostile client could:

- **send arbitrary definition ids / tints**: `owned_item_for_record` resolves a definition+tint pair to an
  *owned* inventory instance; a definition it does not own, a wrong tint, or a non-pet item is refused with a
  roster refresh and a notice, and nothing is consumed (`unowned_pet_item_and_malformed_refusals_each_change_nothing`,
  `an_item_record_with_a_wrong_tint_refuses_without_consuming_or_saving`, `an_owned_item_that_is_not_a_pet_changes_nothing`).
- **flood adoption requests to grow the roster**: the 50-pet cap is server-side; the 51st request is refused
  before the item is consumed (`a_full_roster_refuses_the_item_and_keeps_it`).
- **try to duplicate certificates / mint pets**: adoption consumes exactly one owned instance and commits the
  roster and inventory together; a refusal leaves both unchanged (snapshot equality in the tests above, and
  the f161 document-byte refusal test).
- **claim a client-reported outcome**: no reward or coin moves on adoption; only owned items are touched and
  no client quantity is trusted beyond the two words, which select an owned instance.

No new field, parse path, save field or trust boundary is added by the display-name/texture fallback: it only
chooses values from pinned content for an actor the server already owned.

## Checklist

1. **A refusal changes nothing.** `adopt_with_replies` clones `PetRoster` and `Inventory`, inserts/validates
   the pet, consumes on the clone, and only then assigns both; `handle_with_inventory` commits only on `Ok`.
   Tests: `an_owned_item_that_is_not_a_pet_changes_nothing` (roster snapshot + owned item),
   `a_full_roster_refuses_the_item_and_keeps_it` (50 real 53/32 adopts, the 51st refused, last item kept),
   `pet_routing::{unowned_pet_item_and_malformed_refusals_each_change_nothing,
   an_item_record_with_a_wrong_tint_refuses_without_consuming_or_saving}` (save bytes),
   f161 `the_roster_rides_in_every_document_save_and_a_refusal_writes_nothing` (document bytes). Canary:
   raising `MAX_PETS` to 51 made the full-roster test fail; reverted.
2. **Rollback covers all state.** The transaction's mutable state is `PetService` (roster: next id, pets,
   vendor grants, active actor) and `Inventory` (items, coins, next instance id); both are cloned. The only
   shared value is `Arc<PetContent>`, read-only and never mutated. No side table escapes.
3. **Apply deltas, never restore snapshots.** Adoption consumes one instance through `Inventory::consume` on
   the current inventory clone; it never restores a position, coin balance or inventory captured earlier. The
   f161 tests assert the saved inventory equals the live inventory after the commit.
4. **Busy rules are mutual.** The only production entry is `Gameplay::handle_pets` → `blocks(|gates| gates.pets)`
   in `gameplay/occupation.rs`; `PetBusy` is unchanged and `tests/pets.rs::minigame_busy_rule_rejects_summon_without_mutation`
   pins the refusal. No new activity was added, so the table did not change.
5. **Every entry path is gated.** 53/32 has one path: `gateway.rs::application_handler` →
   `Gameplay::handle_pets` → `PetService::handle_with_inventory`. There is no NPC or automatic adoption path
   (vendor grants use `adopt_vendor_grant` with their own stored definition). The new item rows are gated by
   the same `definition_for_item` the coin store uses (`coin_shop::sale_block`), pinned by
   `a_pet_item_bound_by_pets_content_is_sold` and the shipped gate test. Pet adoption has no level/job
   requirement in recovered data; ownership of the certificate is the server-side gate (R).
6. **Reachable in production, tested through it.** f161 drives `Session::dispatch_message` (staging/commit/save)
   for the new item-only case; `tests/pet_catalogue.rs` drives the same `handle_with_inventory` the gateway
   calls, not a copy. Canaries: breaking the display-name fallback, the texture fallback or the coin-store
   Type-2 gate failed the tests that cover them; all reverted.
7. **Survives reconnect.** The saved roster holds species id (= item id for item-only pets), model ADR,
   adoption item definition id, tint and learned tricks. f161's item-only test drops the session, reconnects and
   asserts species 15493, name "Wolf", texture "base" and tricks `[2057, 2058, 2059]` after the restart.
8. **Every exit path restores the player.** A refused adoption creates no actor; dismiss/zone end the actor
   through the existing W177 paths (`settle_pets`, `dismiss`); `pet_wired::{zoning_dismisses_without_persisting_the_actor_and_reload_keeps_roster,
   a_walking_owner_moves_the_summoned_pet_for_viewers_without_a_save}` cover them. The change adds no new exit.
9. **Economy safety.** The item is consumed only after the roster insert and validation succeed; a player
   cannot adopt an item it does not own, a non-pet item, or a wrong tint; no coins or free grants are involved;
   duplicate species adoption is the lead's 2026-10-18 decision and each duplicate still spends one owned
   certificate (`each_adoption_item_adopts_a_new_pet_even_when_the_species_is_owned`). Binding the two items
   makes them sellable only where a vendor stocks them; no shipped vendor rows changed (`REVIEWED_UNSELLABLE`
   is empty and `every_shipped_vendor_item_is_sellable_or_reviewed_unsellable` passes).
10. **Wire format matches the client reader.** No layout changed. The 53/32 body is built by the shared
    reader-derived `pet_wire` builder (`00b60110`, `00a1ec00` at `00a1f2c2`-`00a1f2d2`), and the adopted actor
    is asserted from the production parser of the 35/2 AddNpc reader `00921a10` (texture alias and name are
    fields that reader consumes; `notes/Research/Startup World Content.md`).
11. **Unique ids.** Pet ids come from `next_pet_id` with checked overflow; the actor id is owner-derived
    (`pet_guid`). Unchanged by this fix.
12. **Others see changes.** The new display values ride the same `PetPresence::spawn_packet` → `wire.shared` →
    gateway `nearby` path; f161 asserts the owner view, `pet_wired::the_gateway_exposes_the_saved_pet_roster_and_clears_the_actor_on_zoning`
    and `a_saved_pet_is_summoned_seen_by_two_players_and_dismissed` cover the other-player AddNpc.
13. **Content works end to end.** Both previously dead items resolve to client model rows (483, 1530) and adopt
    end to end; the tests assert the spawned model, the consumed item and the pet's species. Every client
    Type-2 item is now bound (pinned against the source file, count 528).
14. **Values live in data.** Models, items, tricks and names are `pets.json` rows with a `src`; the icon-tint
    correction now comes from the shipped client-catalogue import, not a code constant; no tuning constant was
    added.
15. **Canaries break production code.** The canaries edited `data/content/pets.json` (dropped item row),
    `src/pets.rs` (display fallbacks, `MAX_PETS`) and `src/coin_shop.rs` (Type-2 gate), never test-only code,
    and each failed the intended test before being reverted (verified with git status/diff).
16. **Hands off session plumbing.** No session creation/teardown/transaction/ordering change; the only file in
    `src/bin/osfr_gateway/` is the test module f161.
17. **One player's error never stops the server.** Adoption refusals return `Ok(Some(PetWire))` with a notice;
    no `?` on a client-triggered refusal, nothing runs in another player's tick, and the two-word request is
    bounds-checked by `PetRequest::decode`.
18. **A type's rules live on the type.** `PetItem::name`/`texture_alias` docs state their display role;
    `Pet::learned_tricks` says order lives on the model rows; `PetContent::model_id` documents the duplicate-ADR
    rule; the two fallbacks are documented methods on `PetService`.
19. **Hot paths stay cheap.** No per-tick or per-packet clone was added. `display_name`/`texture_alias` run on
    adopt/summon and on an AddNpc replay (`view`), not in the follow tick; each is a linear scan of 113 species
    and (only when that misses) 528 items, no allocation beyond the returned string. Adoption keeps the
    existing one-clone transaction.
