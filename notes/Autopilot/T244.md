## Verify-first observations

- `quest_engine.rs::definition_from_content` turns `job: 137` into the
  `fisherman` requirement at rank `min_level.unwrap_or(1)`; the split loader
  validates the profile id against `jobs.json`. `CharacterEligibility.job_levels`
  is built by `gameplay/npc_quests.rs::character_eligibility` only for the
  **active, unlocked** profile, so a character on another job is refused even
  when Fisherman is unlocked.
- `offer_denial` checks prerequisites, player level, job then membership; the
  giver check is against `QuestDefinition.giver_npc_id`. `accept` rechecks the
  job (unless the developer `realm offer` override was used).
- `on_event(TalkToNpc)` completes an ordered Talk step and, when every
  objective is now satisfied and the Talk target is the turn-in NPC (or a named
  objective target), opens `pending_turnin` and emits 49/13 in the same request.
  On the very first Talk after accept, the client reaches Reed through the held
  dialogue choice, so the E3 step needs one Talk and one 26/6 release.
- `fishing_service.rs::settle_catch` (line 1011) pushes
  `QuestEvent::FinishMinigame { minigame_id: tracked.game_id }`; `tracked.game_id`
  is set from `spot.game_id` in `FishingService::enter` (line 551), i.e. 599.
  `gameplay.rs::handle_fishing` forwards only the minigame events of a `change.paid`
  catch (lines 2702–2737); the service's own CollectItem is skipped so the catch
  is not counted twice.
- A paid catch leaves the fishing session present (the service cancels the round
  in place); the shared `Occupation::Fishing` gate is `!fishing.is_empty()`, so
  the client must send 39/6 (or 41/109) to leave before NPC interaction. The
  test does exactly that; a 39/6/41/109 closes the round without a grant.
- The catch is deterministic in this content: `fishing.json` has
  `catch_chance: 1.0`, `line_snap_chance: 0.0`; all four sizes of every fish are
  bound to item ids, and the test fixture defines those ids, so one cast one reel
  pays exactly one fish.
- Turn-in does **not** recheck the job (`QuestEngine::finish_turnin`), the same
  engine-wide policy T202 recorded: the gate is on offer/accept, and the reward
  profile is the explicit 137 map. The task's "non-Fisherman turn-in" case is
  therefore tested as the only reachable one: a forged 49/14 with no pending end
  screen, plus a non-Fisherman who is never offered the line. Switching away from
  Fisherman after accepting is not tested as a refusal because the engine permits
  it today; changing that would be a production decision outside this content slice.

## Security threat note (secure-code-guardian)

- Attack surface: a hostile client can send 26/8, 26/10, 26/6, 49/2, 49/14,
  39/5, 39/6, 41/109 and 138/x at any time. No parser, selector, packet family or
  client-supplied quantity was added; the content only names server events.
- The catch count is server-authoritative: it comes from
  `fishing_service::settle_catch` after the server selects the fish, checks the
  optional cap, stages the reward and pays. A client `138/14` (server-to-client)
  frame is refused with `unknown fishing sub-opcode 14` and changes nothing; a
  client 39/18 with type 21 does not reach `npc_minigame_win` (that helper only
  inspects server-generated replies) and changes nothing.
- The quest is never offered to a character whose **active** profile is not
  unlocked Fisherman 137; the eligibility map is built from the saved profile,
  never from the client. 49/2 without a pending offer is refused; 49/14 without
  an open end screen is refused; 49/13 is only reachable by a server Talk that
  completed the ordered step.
- Rewards are the content rows paid once by the existing quest grant key
  `quest:<character>:<quest>`; no item is granted, so there is nothing to sell
  or re-grant. `apply_grant` still refuses a locked profile; profile 137 is
  unlocked by the offer/accept gate.
- Busy rules are the existing table: while a fishing round is live,
  `activity_busy()` refuses NPC interaction (asserted), so the return step cannot
  be completed mid-minigame. The run must be left via 39/6/41/109 first.
- Range/zone, open-menu and prerequisite checks are the existing
  `npc_interaction`/`QuestEngine` path; the tests snapshot the typed save before
  every refusal and assert equality.

## Skill review

  `TalkToNpc`, ordered objectives, 49/1/13/14 transaction), the existing fishing
  guide menu, the existing `FishingService::enter`/`settle_catch` event and the
  existing occupation gate. The smallest change is data only; the test fixture
  copies the reviewed opening bundle and the real spot/trainer files rather than
  inventing a harness. `ponytail-review` found the `send`/`send_at` duplicated

  `fishing_items`) were kept because they are measured in milliseconds and a
  shared fixture would have to leak temp dirs past test lifetime.

- **Principles applied:** model-the-domain (the spot's `game_id` is the only 599
  source; the explicit profile map is the only XP source),
  subtract-before-you-add (no new module/flag/path; content-only),
  test-behavior-not-implementation (packets and saved state, not internal
  helpers), make-operations-idempotent (replays and reconnect),
  minimize-reader-load (two records, no code).
