# T519: Fotomat portraits (156/2 -> 156/3, empty image) and the quiet 115 CRC

## What changed

- New `prototype/osfr-tools/src/fotomat.rs` owns the whole wire: the 156/2 request parser,
  the 156/3 `PlayerImageData` encoder, the 115 CRC parser, and the visibility adapter.
- New `src/gateway/application_preload.rs` holds the W174 quiet list (moved out of
  `gateway.rs`, unchanged behaviour) and the login-time 156/2 answer.
- `Gateway::handle_at` answers a 156/2 for the session's **own** character before `Loaded`
  from the gateway's own presentation, so the request every native login sends is no longer
  dropped as `gameplay_not_loaded`. The in-world `Session::route_application` branch (via
  `delivery::fotomat_reply`) answers self and any character the viewer's directed AddPc
  already shows.
- `PlayerRegistry::presentation_of(viewer, character)` is the one visibility rule: own
  character, or `knows_character`; otherwise `None` (no reply, no state).
- `PlayerPresentation.customization_ids: [i32; 4]` carries the record's four mapping ids
  (head, hair, skin tone, face paint), filled from `style_cards::Look::ids` in
  `Gateway::player_presentation`.
- The gateway labels 156/2 and 115 as `fotomat`; app_fuzz has seeds for both.
- The image is empty (length 0, uncompressed) until the lead's upload ingress exists (R).
  115 is length-checked and dropped; no pending CRC is stored.

## Client evidence (IDA)

### 156/2 request

- Sender `00bd3ff0`: (manager, guid lo, guid hi, provider C string). It returns early when the
  guid equals `dword_1BEAA20/24`; otherwise it looks up the pending map (key `lo ^ hi`) and
  returns when an entry exists, so **the client never re-asks while a request is pending**.
  On a miss it inserts the pending entry (`00bd33d0`), builds the packet (`00bd3230`,
  `008a23f0(2)`), copies the guid and provider (`sub_402CE0`), and sends only when
  `[[*(sub_769710()+4)]+640] != 0` (`00bd36c0`). If that flag is 0, the entry stays pending
  with no send (R, untested here).
- Header reader `00bd31d0` reads two i16 (156/2). The observed login request is 24 bytes:
  `4 + 8 + 4 + 8`. The provider is a length-prefixed string.
- Providers found: `00bd42b0` "Data", `00bd4300` "TcgPortrait", `00bd4350` "Portrait",
  `00bd43a0` "Headshot"; `00bd43f0` (GetHeadshotBuffer) requests "Headshot". Only Headshot
  and Portrait are 8 bytes, so the 24-byte login request is one of those two.
- Sentinel: `xrefs dword_1BEAA20` shows four reads (`00bd4028`, `00bd485c`, `00bd48a4`,
  `00bd48eb`) and no writer. Its meaning is unverified; we do not implement it because the
  client skips sending for it.

### 156/3 reply

- Dispatch: `009499e2` calls `00bd4d30`; it reads the header, checks subtype 3 and calls the
  consumer `00bd4a50`.
- Reader `00bd4180`: header `00bd31d0`; u64 guid; provider string (i32 length, `00894b10`);
  u8 compressed at +40; record `00bd37e0`; image `009538e0(a2, this + 0x2100)`.
- Record `00bd37e0`: i32 Unknown, i32 Unknown2, u64 guid, i32 model, attachment list
  `009131c0`, string head, string hair, i32 hair colour (+0x2020), i32 eye colour (+0x2024),
  string skin tone, string face paint, string model customization, four i32 (+0x2028..
  +0x2034), string provider.
- Attachments `009131c0`: i32 count, then per row three strings (`008fb980`) and three i32
  (`008e86f0`). AddPc's reader `0091aa10` calls the same function, so
  `PlayerPresentation::attachments_wire` is copied unchanged.
- Image `009538e0`: i32 length; negative or longer than the remaining bytes sets the error;
  0 is valid and copies nothing.
- Consumer `00bd4a50`: requires the error flag clear **and the cursor fully consumed**
  (`v19 - v18 <= 0`); inflates with `010ebee0` when compressed; clears the pending entry
  (`00bd20c0`); copies the record (`00bd27d0`); stores the image only when its length is
  nonzero (Portrait at +0x20E0, Headshot at +0x2100). Empty image keeps the record.
- The four ids are the OSFR/Sanctuary `HeadId, HairId, SkinToneId, FacePaintId`; our
  `Look.ids` order is `HEAD, HAIR, MODEL_CUSTOMIZATION, FACE_PAINT, SKIN_TONE`, so the reply
  uses `[HEAD, HAIR, SKIN_TONE, FACE_PAINT]`. Unknown = 0 and Unknown2 = 1 (R; Sanctuary
  `FotomatPortrait`).

### 115

- Ctor `00b4a9c0`: opcode 115 at +4, u32 at +8. Sender `00b4fc30`. PostPortraitToHttp
  `00b4fd60` finds `portrait.png` (`00b4e650`), computes the CRC with `00704a40` (reflected
  CRC-32, init -1, final NOT), builds the 115 and sends it through `00b4fc30` when the
  screenshot manager's send flag is set, then POSTs the multipart image to
  `Portrait/UploadUrl`.
- Wire: u16 115 + u32 CRC, exactly six bytes. Not a family/subtype.

## Reverse-engineering report (no code depends on these answers)

1. **Empty image.** `00bd4a50` keeps the record and clears the pending entry. `00bd4490`
   (render Portrait/Headshot into a texture) only draws when the stored image size at +8 is
   nonzero, so it draws nothing for an empty image. `00bd43f0` (GetHeadshotBuffer) falls
   back to the manager's default headshot bytes (`this+134/135`) when the entry has no image.
   Whether `HeadshotProxy` (`00cc5e60`) uses that default, and `LoadDefaultImages`, were not
   traced; open.
2. **Capture/upload start.** `00b50190` is the per-screenshot portrait job processor: with
   `a4 != 0` it calls `00b4e9f0` (TCG capture) and pushes the result into a UI object via
   `00ad3790`; with `a4 == 0` it builds `PacketGeneratePortraitRequest` (ctor `00ad3190`) and
   sends it through `00ad61f0` when `[manager+4]+640` is set. `00b4fd60` is the HTTP upload
   that sends the 115 first. Direct xrefs to `00b4fd60` are absent (indirect), so the trigger
   that starts the upload was not resolved; open.
3. **Login-time request.** All recent baseline traces have exactly one 24-byte 156/2 while
   `gameplay_not_loaded`, before Ready (e.g. `client-baseline-20261024T213325Z`
   `server-trace.jsonl`, `ts_ms` 138174/138178). The trace records no body hex for this
   request, so the guid is not directly observed. Pre-load the only presentation that
   exists is the player's own, and
   only Headshot/Portrait are 24-byte providers: (R) the request is the self headshot. The
   UI that shows it was not identified; open.
4. **Login ordering.** The brief's "the route must see it as the other session routes do" is
   wrong: `route_application` only sees `outcome.applications`, which `Gateway::handle_at`
   pushes only after the `!loaded` gate. The fix is the pre-load answer in
   `Gateway::handle_at`; the in-world route still handles post-Loaded requests where
   `SharedWorld.players` is reachable. (IDA/code wins over the brief's premise.)

## Threat note (secure-code-guardian)

A hostile client can send any bytes as 156/2 or 115. It cannot choose a target it may not
see: the route answers only the viewer's own character or one its directed AddPc already
contains (`knows_character`), and the pre-load path answers only its own guid. The provider
must be exactly `Headshot` or `Portrait` and no more than 16 bytes; the body must be exactly
24 bytes with a valid UTF-8 provider and no trailing byte. The 115 body must be exactly six
bytes; anything else is dropped. All reads are bounds-checked and lengths use
`checked_add`; no client-controlled field reaches an `unwrap`, allocation before a bound, or
a file. Refusals send nothing and store nothing: the tests snapshot the gateway and the
target registry row before each refusal and assert both unchanged. The reply carries only
what AddPc already broadcasts (guid, model, attachments, appearance strings, mapping ids),
never coins, items, names or chat. Rate: no new limiter; the existing per-session packet
(200/s, burst 400) and byte (256 KB/s, burst 1 MB) buckets in `osfr-gateway.rs` bound
requests, and each reply is a few hundred bytes with an empty image. W173 is chat settings
(26/18, 26/32, 26/33), not an application budget; the brief's premise is stale.

## Checklist

1. **A refusal changes nothing.** `fotomat_route_refuses_without_reply` snapshots the gateway
   and the target registry row before every refusal (unknown/far/other-instance guid, bad or
   17-byte provider, trailing byte, wrong family/subtype, short 156, malformed 115, valid
   115) and asserts no 156/3 and both snapshots equal. `fotomat_refuses_without_reply` checks
   the codec directly.
2. **Rollback covers all state.** No transaction or state is added; the handler only reads
   and builds a reply. The route's deliveries are committed only with the staged world, and a
   refusal returns an empty vector.
3. **Apply deltas.** No coins, items or position are written.
4. **Busy rules are mutual.** No new activity and no busy state.
5. **Every entry path is gated.** Both entry paths (pre-load self; in-world route) call the
   same `fotomat::handle` and the same `presentation_of` visibility rule. There is no level,
   job or budget gate for a public presentation.
6. **Reachable in production, tested through it.** The pre-load test drives
   `Gateway::handle_at` (and the inline Session test drives `dispatch_message`); the in-world
   tests drive `Session::dispatch_message` -> `route_application` -> `delivery::fotomat_reply`
   with a real `SharedWorld`.
7. **Survives reconnect.** Nothing is persisted; the client re-requests after reconnect and
   the reply is rebuilt from the live presentation.
8. **Every exit path restores the player.** No state is entered.
9. **Economy safety.** No coins, items, rewards or client quantities; only the target guid
   and provider are read, and both must match the allowed set.
10. **Wire format matches the client reader exactly.** The decoder follows `00bd4180`,
    `00bd37e0`, `009131c0` and `009538e0` and requires full consumption; the canary (missing
    trailing provider) failed it.
11. **Unique ids.** No ids are allocated.
12. **Others see changes.** No visual state changes; the reply exposes only what AddPc
    already shows.
13. **Content works end to end.** The tests assert the live self and a joined target produce a
    record with their model, strings, four ids, attachments and empty image. Native acceptance
    (Inspect bot, one 156/3 per 156/2, client alive after 60 s) is the lead's after T401.
14. **Values live in data.** None of the new values are tuning: 156/2/3, 115 and the 16-byte
    provider bound are wire bounds. The empty image is a temporary (R) policy until the
    upload ingress.
15. **Canaries break production code.** The canary removed the trailing provider in
    `src/fotomat.rs`; two tests failed on the real decoder. Restored.
16. **Hands off session plumbing.** No change to session creation, teardown, transaction or
    save ordering in `osfr-gateway.rs`/`gateway.rs`. The login-order fix is an application
    pre-check in `Gateway::handle_at`, not a session/save change.
17. **One player's error never stops the server.** The handler returns `Option`; malformed
    client input is dropped, never `?` out of the tick and never `unwrap`ped (the only
    `expect` is on server-built string lengths). The hostile app_fuzz corpus and the refusal
    table exercise malformed bodies.
18. **A type's rules live on the type.** `PlayerPresentation.customization_ids` documents
    that they are the 156/3 record's four ids, AddPc does not carry them, and `fotomat`
    refuses negatives; `presentation_of` documents the visibility rule on the registry.
19. **Hot paths stay cheap.** Two prefix comparisons per application, no allocation or clone
    for a refusal, no per-tick work; the reply allocation happens only for an accepted 156/2.
