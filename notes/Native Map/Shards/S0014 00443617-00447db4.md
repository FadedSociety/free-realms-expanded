# S0014 (00443617..00447db4) - Scaleform GFC clipboard, Win32 input/window layer, STL emissions

220 functions mapped, `validate.py` reports `valid_records=220 errors=0`

range is game logic, Lua glue or network code: it is the Scaleform GFx "GFC"
client frame (engine.gfc.*), its Win32 platform layer (platform.win32.*) and a
large block of MSVC STL/CRT bodies emitted out of line (crt.stl, engine.mem,

## Review repairs (rounds 1 and 2)

The independent reviewers disputed a set of labels; all of them are now fixed
in `out.jsonl`, and the same mistake patterns were re-checked across the whole
shard (small functions were re-decoded from `nmq bytes` before rewriting):

- Fill mis-read as copy. 00444d4e, 00444d6f, 00444d90 and 00444db1 (now
  `UninitFill4_6.._9`) and the byte twin 00444eb3 (`UninitFill1`) never advance
  the source pointer: the loop jumps back to the load of `*param_3`, so param_2
  is a count and the same value is written repeatedly. The wrappers
  00446fd6/00446ff8/0044701a/0044703c (`UninitFill4WrapperA..D`) and 00447126
  (`UninitFill1Wrapper`) forward to those fills with a partly-initialised stack
  dword the callee never reads.
- capacity mis-read as size. The six accessors using the +0xC pointer
  (00443ea2, 00443f90, 00443fab, 00443fc6, 00443ffd, 00444088) are
  `VectorCapacity4C*`: callers 0044c78d (1.5x growth) and 0044df6b (append in
  place at +8 only while size < capacity) prove +0xC is the storage end, while
  the logical count is the +4/+8 pair used by the VectorCount4 helpers
  (0040a99f).
- Direction errors. 00446878 constructs its 01763928 temporary on its own stack
  frame and passes the *caller's* argument to 00443617 (the temporary is not the
  argument). 00447c85 decrements a stack copy of the iterator, so the object is
  never written (renamed `CheckedStepIteratorCopy`). 00446ecc/00446eee guard the
  destination slot (ECX) and copy param_2 into it. 00446f1e takes its receiver
  from the caller's ECX+4. 00444b0c/00444b37/00444cef/00444d16 clone each
  element into the destination slot passed in ECX.
- 00444a6d loads the value once and returns the first matching element pointer
  in EAX (renamed `FindDwordInRange_4`, matching the accepted FindDwordInRange
  family at 0045eccc).
- 00447303 and 00447a12: the recursion was mis-described in the first pass. The
  object at this+0x20 is passed as the *first argument*; the receiver comes from
  a field of another object ([child+0x54] and [this+0x140] respectively), proven
  from the call bytes (push [child]; mov ecx,[eax+0x54]). The 01763CD0 class
  attribution had no support (no data pointer to either function exists in the
  image) and is withdrawn; both records are `speculative`.
- Unreferenced stubs. 0044695f, 00446975, 00446981, 00446ace and 00446bc0 have
  no caller and no reference to their address anywhere in the image; the
  "reached from a table" clauses were withdrawn and the records are
  `speculative` (the forwarding bodies themselves are byte-verified).
- 00443617 was `confirmed` and is now `likely`: its CF_TEXT block is filled from
  a local that Ghidra renders as the empty-string global &DAT_01bc7e2c, so the
  ANSI text source is not established.
- 004467dc is now `CtorEmbeddedGPropertyInterface1763084` with `class: null`:
  GPropertyInterface is the embedded sub-object at +0x14, not the class being
  constructed.
- Allocator records follow the accepted naming convention: `AllocateElements4G`
  .. `AllocateElements4K` (00444632/00444681/004446d0/0044471f/004447d1) and
  `AllocateElements24A` (00444773).

## GClipboardAccess_<format>: clipboard as a family of named classes

The strongest structural result. The GFC clipboard layer keys one access class
per Win32 clipboard format name:

- 0044394f registers the class `GClipboardAccess_GStringObject` (size kind
  0x18) through `FUN_0053da53`/`FUN_004ccf27`/`FUN_00536678`, the same
  registration triplet already labelled for `GClipboardWin32` (00440f13) and
  `GClipboardAccess_Win32_TEXT` (004435e4).
- 004437da constructs the class that wraps a `GStringObject` and interns the
  clipboard format name `Scaleform GFC - GString Unicode Text`; 004466ce is the
  twin for the format `Microsoft Windows - Unicode Text`.
- 00443617 is the write implementation (`likely`, not `confirmed`): it fills a
  `CF_TEXT` block with `_strcpy_s` and a `CF_UNICODETEXT` block with `_wcscpy_s`
  from the UTF-16 payload of the GString at this+0x30 and publishes both with
  `SetClipboardData`. What lands in the CF_TEXT block is uncertain because
  Ghidra renders its source as the empty-string global &DAT_01bc7e2c.
  00446878 is a one-shot wrapper that runs 00443617 (with the caller's own
  argument) inside the lifetime of a 01763928 temporary built on its stack.
- 004475ba and 0044775e are the read and write/clear entry points. Both
  enumerate `EnumClipboardFormats`, map each format to its name with
  `FUN_00440f73` (the already-mapped `ClipboardFormatName`, 00440f73), build
  the class name `"GClipboardAccess_" + <format name>`, resolve and instantiate
  it, and then drive it through virtual slot +0x10C (read) or +0x110 (write).
  0044775e with a null argument calls `EmptyClipboard` instead.

Reading 00447b9a (class ops for the 01763298 class) together with the
access-class slots gives the convention used by this factory: action 0 create,
1 copy-construct, 2/3 allocate then create/copy, 4 destroy (body 00443894,
which is exactly the body the deleting destructor 00446809 calls) and 5 delete
through slot 0. 00447514 repeats the same six-action shape for the 01763570
class (create 004451d2, copy 004458a1, destroy body 00446809's sibling is not in
range). The allocator used by the allocating actions is the stamped engine block
allocator (`engine.mem`), e.g. 004438dd, which stamps 0x56471e89/0x9fe1234a -
the same tag pair used by `SetMagicPairAt18` helpers elsewhere (engine.gds).

## Win32 input: GInputManagerWin32 device layer

- Mouse descriptor: 0044543a completes the record started by 00440428
  (buttons = min(SM_CMOUSEBUTTONS, 8) at +0x10, axes = 2 or 3 by
  SM_MOUSEWHEELPRESENT at +0x14). Keyboard twin is the already-labelled
  004432fd.
- Mouse per-frame poll: 0044547c refreshes the per-button state bytes at +0x48
  with `FUN_004424f8` (async key flags per button), updates cursor deltas
  (+0x58/+0x5c, +0x60/+100), folds the wheel accumulator (+0x70 into
  +0x68/+0x6c) and caches the modifier mask from `FUN_00442659` at +0x50.
- Device activation bytes: 004453c1 (mouse, +0x7C) and 00446181 (keyboard,
  +0x12C) set the flag and, when bit 9 of the owner flag word (+0x80 / +0x130)
  is set, dispatch a 0x1E-byte event record through `FUN_004d9765`; 00445550
  and 00446278 are the mode wrappers (2 = activate, 3 = deactivate then
  activate, 4 = deactivate).
- Key naming/state: 00445695 formats `Button %d` or the axis-name table entry
  (global 01AF5B44), 0044645c formats a name from the keysym table
  (`FUN_004426b5`), 0044650d returns 1.0/0.0 for a key, 00446152 builds the
  modifier mask from the object's own key-state bytes, 0044598d packs the
  button state into a bitmask (0x10000 << index).
- Bring-up: 00446576 registers `GInputManagerWin32` and `GWindowManagerWin32`
  with the GFC registry (`FUN_00544cc0`) using the interface names
  `GFC_Input_Manager` / `GFC_Input_WindowManager` over `GFC_Interface`, version
  1.0.0. 00445f20 builds a device record and returns the human-readable device
  name (`Input Manager`, `System Keyboard`, `Window Manager Mouse`, ...).

## GFC window layer (engine.gfc.win32)

00447303 and 00447a12 (both `speculative`) handle one 0x1E-byte event record for
an object whose listener list sits at +4: the record type is tested against the
globals DAT_01BC7524 (position cache at +0x74/+0x78) and DAT_01BC75CC (wheel
accumulator at +0x70), the record can be offered to a caller-supplied object
through its virtual slot +0x100 (00447303) or dispatched to the listeners with
`FUN_004d9765` after the device-active byte is set, the chain is continued by
recursing with the object at this+0x20 as the *first argument* (the receiver is
`[child+0x54]` for 00447303 and `[this+0x140]` for 00447a12), and the record is
released with `FUN_004d93a3` when its flags carry any 0x24924 bit. `FUN_004d93dc`
copies such records with release/re-reference semantics for the payload dwords.
Neither function has a static caller or any pointer to its address in the image,
so the owning class is unknown.

Smaller window methods: 00445a6d (state-driven `ShowWindow`), 00445af1
(`SetFocus` with a re-entrancy bit), 00445cfe (cache `GetWindowRect` results),
004459d7 (cursor position, optionally `ScreenToClient`), 00445d5b / 00445d80
(lazy factories for the 01763570 / 01763408 helper classes), 00445e99 (create
through slot +0x6C with flag 0x1003120), 004450cf (store an interface with
AddRef/Release), 004458e0 and 0044728a (memberwise copy constructors shared by
the window copy constructors).

## STL and CRT emissions (crt.stl, ~120 functions)

One coherent block of MSVC STL bodies emitted out of line: checked iterator
helpers (equality `ContainerIteratorEq_8..15`, distance `ContainerIteratorDiff4*`,
advance/retreat `CheckedAdvanceByFour*`, `CheckedAdvanceByStride4*`,
`CheckedAdvanceByStride1`, `CheckedRetreatByFour`), tree primitives for the
+0x15 node layout (`TreeRotateLeft15_b` 004468cd, `TreeRotateRight15_b`
00443f29, `TreeInc15_b` 00444271, `TreeDec15_b` 004444a7, `TreeLowerBound`
004469f1, node init 004445d9), vector helpers (the +4/+8 pair is size, the
+4/+0xC pair is capacity - `VectorCapacity4C*`; forward/backward moves via
`_memmove_s`; `UninitFill4_6.._9` plus `UninitFill1` for the uninitialized_fill
shape; 16-byte record copies; allocators `AllocateElements4G..4K` and
`AllocateElements24A`), the range search `FindDwordInRange_4` (00444a6d, value
loaded once, found pointer returned in EAX), and wide/narrow string range
operations
(`FUN_004e8d36` = wide-string assign, `FUN_004e52ed` = narrow-string assign,
`FUN_004e884e`/`FUN_004e4e15` = the corresponding copy constructors; the
sentinels are the globals 01BC7E20 for wide and 01BC7E28 for narrow strings).
Five of these are confirmed as destructors by EH unwind-funclet references:
0044491e, 004449d4, 00447d35, 00447d92, 00447db4.

The `FUN_00d83c2d` abort helper (calls `FUN_00d83c09(0,0,0,0,0)`) is the single
shared failure path behind every checked container access in this shard. 0x24924
is the flag mask that says "this record still owns interface payloads at
+4/+8/+12/... (3-bit tag value 4)"; it appears in 004453c1, 00446181, 00447303
and 00447a12 and is consumed by `FUN_004d93a3`.

## Contradictions and gaps

- No vault note cites any address in this range (`context/note-addresses.tsv`
  has zero hits for 00443617..00447DB4), so nothing here contradicts existing
  notes; these findings are new material and should be folded into the
  Scaleform/GFC research note.
- The CF_TEXT block of 00443617 is filled from the global &DAT_01bc7e2c, i.e.
  the empty narrow string, not from the converted text; the ANSI text source
  should be re-checked on hardware before anyone relies on it (this is why the
  record is `likely`).
- Two different registration mechanisms appear: `FUN_0053da53` (used by the
  per-format classes and the earlier window/clipboard registrations) and
  `FUN_00544cc0` (used only by 00446576 for the two managers). Their exact
  division of labour is unresolved here.
- The interface implemented by virtual slot +0x18 in the script-facing glue
  00444f75 / 00447224 (argument type `p<c GString>`) is not identified; the
  slot is called with the receiver and an in/out parameter pair.
- 00443617's owning class is not proven: it operates on an object whose +0x30
  holds a GString, so the record keeps a mechanical name instead of a class
  binding.
- Which class owns 00447303 / 00447a12 is open: their fields (+0x20 child,
  +0x4 handler list, +0x80/+0x130 flag word, +0x140 device pointer) do not
  match the accepted 01763CD0 key-state layout, and no data reference to either
  address exists in the image.
- The five forwarding stubs 0044695f/00446975/00446981/00446ace/00446bc0 are
  unreferenced in the image; if the lead finds a table that reaches them, their
  purpose can be raised from `speculative`.
