## What this range is

The shard is the client's packet-handler / console block: the three dispatchers of
`ClientCommandProcessor`, the per-message body readers for the command (26), encounter (41) and
matchmaking families, the console command table plumbing, and the GameEvent override used when an
encounter completes. Nothing here is server logic; every finding is client-side parsing and client
state changes.

## `ClientCommandProcessor`: one class, two jobs (00aa06a0, 00aa07b0, 00a9f410, 00aa12c0)

`00aa06a0` is the constructor and reads cleanly: it installs
`CommandProcessor::CommandEventHandler::vftable` then `ClientCommandProcessor::vftable`, stores the
console-context pointer at +4, builds two `SoeUtil::Deque<SoeUtil::IString<unsigned short>,256>`
histories (`00a9bb10`), and registers exactly three console commands through `FUN_00987000`:
the literal `attack` with index 0, the literal at `0181883c` with index 1, and the literal `report`
with index 2. The byte dump at `0181883c` is `68 69 74 00` ("hit"), between "report" (01818834) and
"attack" (01818840). It ends by loading the saved history (`00a9e100`, file `CommandHistory.txt`).
`00aa07b0` is the destructor body and saves that history back (`00a9c420`, same file);
`00aa12c0` is the vtable slot-1 scalar deleting destructor.

The vtable at `0181884c` has five slots in this order: `00a9f410` (slot 0), `00aa12c0` (slot 1 =
scalar deleting destructor), `00aa2560` (slot 2), `00aa36c0` (slot 3), `00aa2980` (slot 4).
The base `CommandProcessor::CommandEventHandler::vftable` at `0180b24c` holds `__purecall` at slot 0
and `009758d0` at slot 1, so slot 0 is the overridable hook (`00a9f410` dispatches kind 0/1/2 to
the attack, hit and report console commands `00a9e790` / `00a9e8f0` / `00a9ea40`) and slots 2-4 are
methods the derived class adds. All three added methods are `(body, length)` dispatchers, so the
same object is also registered as a received-packet handler.

## Wire shapes recovered from the readers

Every body starts with two sign-extended 16-bit words (`00a9cb50`, folded twin `00a9d4f0`), and for
the encounter family the shared 12-byte header (`008d6690`: word, word, dword, dword) feeds
destination +4, +8, +0xc, +0x10, matching the field mapping in
`Reviews/Original Tutorial Mode Exit Field Review.md` for 41/2. Candidate layouts recorded here:

- 41/3 completion: header, flag, three dwords, three reward bundles (`00aa02b0`, rewards through
  `008e7930` whose string names CreateRewardBundleEntry).
- 26/16 confirm friend: header, two ids, a block (`008e7290`) and a trailing flag at +0xa0
  (`00aa0210`); the constructor clears exactly that byte.
- 26/35 positions reply: header, two dwords, two flags, list of entries with two ids, a
  length-prefixed string, booleans and a second string (`00aa1550`, `00aa10b0`, `00a9d840`).
- 26/38 reward preview: header plus one reward bundle (`00aa1420`).
- 26/3 show dialog: header, ids, a count-prefixed list of 0x1c-byte nodes, three strings, three
  floats and a boolean cluster (`00a9ef10`, list builder `00a9d760`).
- 26/2 who reply: count plus 0x3c-byte name entries (`00aa0380`, `00a9de30`, `00a9d960`).
- 26/9 radial menu: 0x250-byte object with ids, a flag, an entry list, a string and a trailing flag
  (`00aa2220`, `00aa1600`, `00aa04d0`, `00a9dca0`), 0x20 bytes shorter list entries than the
  positions reply.
- 41/4 and 41/106: shared header plus one trailing dword; 41/121, 41/133: header plus one boolean;
  the readers are separate functions even where byte-identical in shape, so the cases are distinct
  messages.

## Console subsystem (console not network)

`00a9e030`/`00a9e0a0` navigate a paged ring of 16-byte entries backwards/forwards (cursor +0x7c,
count +0x3c, start +0x40, pages +0x1c); `00a9c990` appends a line; `00a9e100` loads
`CommandHistory.txt` and `00a9c420` (called from the destructor) writes it; `00a9e480` executes a
typed line (splitting, quote handling, command-table lookup `00cb8c50`, dispatch `00986c90`,
`00a9e2d0` prints "Command not supported: %s" on a miss); `00a9f2e0` runs a queue of such lines;
`00aa19e0` prints slash-command candidates ("[No Matches]"). The command table itself lives in the
`0x00cb8xxx` block, outside this shard.

## Encounter-complete event

`00aa1e40` constructs an `EncounterCompleteEvent` on the `GameEvent` base (`007e78e0`), with byte
+0x44, dwords +0x48/+0x4c and two member objects at +0x50 and +0x108 (constructed by `0091c110`
and `0103a1e0`, whose vtable references are `RewardBundleBase` and `SoeUtil` string lists).
`00aa1f90` is the slot-1 override of the base hook that stub-returns 0 (`007db980`); it pulls the
client singleton (`00769710`) and hands those exact fields to `009bf4d0`, which copies them into an
object reached through the singleton. `00aa1f10`/`00aa1fd0` are the destructor body and its scalar
deleting form.

## Contradiction with an existing label

`FUN_00a9ad20` carries an accepted label "BaseCommandPacket::BaseCommandPacket ... installs
BasePacket::vftable, stores 0x1a (26)". The raw bytes (98) decode differently: under an SEH frame it
allocates 0x1c bytes through `FUN_00772a20`, stores `CommandPacketPlayDialogEffect::vftable`
(`0181865c`) at [esi], zeroes +0x10/+0x14/+0x18 and returns; there is no `0x1a` store and no
`BasePacket::vftable` store, and its Ghidra data references list
`CommandPacketPlayDialogEffect::vftable`. That matches note
`Research/Pieces/071 NPC dialogue branching.md` (which says this function builds
`CommandPacketPlayDialogEffect` with opcode 28) and the dispatcher case 0x1c that calls it
(`00aa0ce0`). The label should be re-reviewed; the note and this shard's decode agree with each
other.

   and the 26-family keys have independent confirmation.
2. The matchmaking family has no community catalogue entry, so its parse entries, body readers and
   constructors (`00aa1c20`, `00aa2460`, `00aa24e0`, `00aa0170`, `00a9ffb0`, `00aa0020`,

   `00a9df30`) carry `wire: []` rather than a guessed opcode; none of them contains an opcode
   constant and the catalogue has no class for that family. Whoever finds the family opcode can
   fill all of them in one pass.
3. `FUN_00969590` (the 14-argument sink that 26/28 forwards into) and `FUN_010c08a0`/`FUN_010c09f0`
   (cases 7 and 39) are outside this shard and unread; they decide what those commands do.
4. Case 0x6b (107) is documented by the kart note as "mini-game/39 family" while the dispatcher it
   sits in handles 41 fragments; the true family for that arm is unresolved.
5. `00a9eb90` frees an object whose destructor body is `00703350`; no vtable binds it to a class.

## Method and scratch

All 114 functions were read in address order from the Ghidra export; small functions
(< 48 bytes, all 12 scalar deleting destructors and `00aa1f90`) were decoded from raw bytes with
`nmq bytes`/`mem.py`; ECX-held arguments that Ghidra dropped were recovered by decoding call-site
bytes (`callsites.py`, e.g. the IString destinations at +0x8/+0xc). Helper scripts live in
`scratch/` (`dump.py`, `reader.py`, `callsites.py`, `mem.py`, `switchmap.py`, `bytegroups.py`,
`table.py`, `callers.py`, `notes.py`, `vshard.py`, `subsys.py`, plus the assembly/fix scripts).
Case maps were read from the switch arms of `00aa2560`, `00aa36c0` and `00aa2980`; the paired
constructors were checked for their family-constructor arguments where possible.
