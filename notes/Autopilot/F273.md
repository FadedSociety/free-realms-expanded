## Security threat note (secure-code-guardian)

Threat model: a hostile client sends family-129 bodies and ids.

- The actor is the authenticated session's character; bodies never name it. The guild service
  checks membership, permission and rank in `GuildStore`; `responds_to` only suppresses work
  the handler would silently answer and cannot turn a refusal into an action.
- `NameData::is_valid` bounds each part at 128 bytes and rejects control characters;
  `set_member_name` refuses an invalid snapshot and `GuildStore::validate` re-checks every
  persisted member name on save/load.
- `--guild-invite-ttl-ms` is range-checked at parse time (1..=600000), so a bad host value
  cannot create an unbounded or zero invite window.
- A forged or stale accept changes no persisted state: the timed-out/ignored path does not
  mark the store dirty, the refused request is answered against the rows it found, and the
  runtime sweep is documented cleanup (new test).
- Trace bodies for family 129 are redacted by `trace::sensitive_payload` (names, MOTD, invite
  text never appear as hex).
- No item, coin, position or reward path is touched; guilds grant nothing.
- The `paths.rs` move is not on the trust boundary: same bodies, same inputs.
