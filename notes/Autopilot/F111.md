# F111: T012 review blockers

## Result

Fixed the T012 BLOCKER in `QuestEngine::accept`: requirement and active-limit
refusals no longer call `decline`, so a rejected acceptance leaves the pending
offer and the offered quest untouched and returns `changed = false`. The
developer offer is now consumed only after every gate passes.

Added three regressions:

- `tests/quest_offer_gates.rs::denied_accept_preserves_pending_offer_for_requirement_and_limit`
  covers both the level/job requirement refusal and the active-limit refusal.
- `gameplay::w64_regional_quest_tests::denied_accept_after_a_request_handler_job_switch_changes_nothing_and_requests_no_save`
  switches jobs through `26/13`, offers `3000021` through the NPC interaction,
  switches back to the low-rank job, sends `49/2` Accept, and asserts
  `changed = false`, the exact `QuestState` is unchanged, and no `49/3` is sent.
- `gameplay::w64_regional_quest_tests::npc_request_path_refreshes_eligibility_after_a_request_handler_job_switch`
  uses the non-opening request path, where `26/13` does not itself refresh
  eligibility. It fails if the pre-NPC refresh in `handle_npc_packet` is removed.

The opening-world `26/13` path also refreshes eligibility through
`apply_opening`, so the isolated refresh regression deliberately uses the
non-opening path. The opening path remains covered by the existing offer tests
and the new denial test.

### Threat note

A hostile client can send a forged or stale 49/2 with any u32 quest id and
accept flag. `decode_quest_reply_49_2` rejects a wrong length or prefix, id 0
and flag > 1; `accept` refuses unless the id equals the server's pending offer
and the quest is enabled, then re-checks requirements and the active limit from
server-owned eligibility at accept time. A refusal returns `changed = false`
before any write, preserves the offer and any developer override, and requests
no save. The developer bypass needs `--dev-tools` and cannot outlive its offer.
A limit refusal sends 47/15 carrying only the server-derived member flag.
