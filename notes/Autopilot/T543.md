# T543: multi-line quest talk dialogue with responses and quiz retries

## What changed

- New `src/quest_dialogue.rs`: `DialogueLine` / `DialogueChoice` content types,
  a pure `Conversation` cursor (`start`, `answer`, `Next`/`Finished`/`Abandoned`),
  the 1..=N 26/3 response rows, and load bounds (16 lines per goal, 5 choices per
  line, two `then` levels). A retry re-queues its question after the choice's
  `then` lines; an answer the current question does not offer abandons the cursor
  without changing it.
- `src/content.rs`: `TalkToNpc` gains `lines` (serde default, skipped when empty)
  and `complete_after_dialogue` (default false), with the same bounds checked in
  the unsplit `ContentDb` loader.
- `src/quest_engine.rs`: a talk step's conversation is one `StepConversation`
  (lines plus the complete-after flag, so the two cannot drift). The Talk no longer
  completes a `complete_after_dialogue` step; the new server-built
  `QuestEvent::DialogueFinished` completes only that exact open step. Other talk
  steps still complete on the Talk. `conversation_for_talk` only offers a
  currently open objective.
- `src/gameplay/npc.rs`: a Talk whose outcome is the ordinary dialogue starts the
  step's conversation instead of the single-line 26/3; 26/6 routes to the open
  conversation before the explainer/offer handling; 26/4, a new 26/8/26/10, and a
  real 26/23 abandon end it. Conversation state is session-only on `Gameplay`.
- `data/content/quests/zone_seaside.json`: lines for 3000320 objective 2,
  3000323 objective 1 (`complete_after_dialogue: true`), 3000360 objectives 1 and
  2, with a `legacy-data` tag naming the fork goal index.
- `src/gameplay.rs` gains the one `quest_conversation` field and its init; no other
  hub file changed. `src/lib.rs` registers the module.

## Threat note (secure-code-guardian)

Input parsed from a client: the 26/6 answer id (8-byte packet), 26/8/26/10
interactions, 26/4 close and 26/23 abandon.

- An answer the current question does not offer, including `i32::MIN` or a large
  positive id: `checked_sub(1)` plus a usize conversion and a length filter make
  it `Abandoned`; the cursor is dropped, the handler sends 26/4, and no quest or
  saved state changes. A 16-line conversation with a retry cannot grow its queue
  past 16; an over-bound retry abandons instead of allocating.
- The conversation is only created from the real Talk selection, after the NPC
  interaction gate proved the NPC, range and the offered option; the engine only
  offers a currently open objective (`current_objectives`, which honours the
  ordered-quest first-open-step rule). A later step cannot be talked into early.
- Completion is a server-built `DialogueFinished` event naming the quest,
  objective and NPC; the engine requires that exact step to be active/open and
  marked `complete_after_dialogue`. Only the NPC handler constructs it.
- Replaying a valid row after finish/abandon finds no cursor and follows the
  existing close path; a forged 26/23 clears the cursor only when the engine
  actually abandoned that quest; a wrong/unknown answer closes the dialog and
  drops the cursor, keeping the step open.
- Correction (F810): the first build checked range only when the Talk started
  the conversation, so a player who walked or teleported away could keep
  answering. Each 26/6 answer now needs the same active NPC and reach, and an
  out-of-reach answer drops the cursor and sends only 26/4.
- No economy, item, reward, role or chat surface is touched.

## Open gaps

- A conversation on the final Talk step: for an ordinary Talk step the existing
  held-49/13 dialog-choice path takes precedence, so its lines do not start. A
  `complete_after_dialogue` step does start its conversation (the Talk does not
  ready the quest); F810 makes its finish open the 49/13 end screen at the
  clicked runtime actor with no 26/4 first. The three authored goals are
  non-final steps, so that path is pinned on a fixture edit only.
- A quest offer available at the same Talk as a complete-after step defers the
  conversation until the offer is accepted or declined; the offer path is
  deliberately unchanged.
- Two active quests with open Talk steps at one NPC: the first open step in quest
  id order owns the conversation, while the Talk event still credits every
  matching open step. This is the pre-existing single-line ambiguity.
- The fallback last-line label 103085 and the 1-based row ids are (R) fork
  behavior; the id the client echoes is reader-verified.

## Checklist

1. **A refusal changes nothing.** The wrong-answer and unknown-answer tests
   snapshot `game.state()` before and assert equality after; a busy refusal
   returns before the conversation clear; a rejected menu selection clears only
   inside `selected.is_ok()`. Canary: the retry re-ask was disabled in production
   code and the quiz test failed, then the break was reverted.
2. **Rollback covers all state.** The cursor is an owned field on `Gameplay`, which
   the gateway stages and clones; `OpenConversation` holds no shared pointer, map or
   side table. A refused `io::Result` drops the staged clone.
3. **Apply deltas, never restore snapshots.** No payout path changed; the quest
   completion runs through the existing `on_event` counter increment.
4. **Busy rules are mutual.** No new activity or `Occupation` row; the existing
   `busy_interaction_refusal` still refuses 26/8/26/10 before any conversation
   change. A conversation is not an activity.
5. **Every entry path is gated.** A conversation starts only from an accepted
   `NpcSelection::Talk` (NPC, range, menu) and only for an open
   `current_objectives` step; completion needs the exact server-built
   `DialogueFinished` step. Tests drive 26/8 -> 26/10 -> 26/6, not internals.
6. **Reachable in production, tested through it.** `tests/quest_dialogue_chains.rs`
   walks the real offer/accept/visit/talk/turn-in path and decodes packets with the
   production 26/3 reader.
7. **Survives reconnect.** The cursor is session-only by design (R): reload drops
   it, the saved `QuestState` keeps the step open, and the next Talk starts at line
   1 (`disconnect_mid_quiz_restarts_it`).
8. **Every exit path restores the player.** 26/4, unknown answer, a new
   interaction, an abandon and a disconnect all drop the cursor; finish closes
   with 26/4 and credits the step. No location or lock changes.
9. **Economy safety.** No grant, item, coin, XP amount or client quantity is
   added; rewards only follow the existing 49/14 path after the server-side
   completion.
10. **Wire format matches the client reader.** 26/3 keeps `encode_dialogue_26_3`
    (body reader `0x00a9ef10`); the new rows use the existing five-dword row
    shape; 26/6 stays one i32 (reader `decode_dialogue_response_26_6`). The test
    decodes every 26/3 with the production reader and asserts row ids/labels.
11. **Unique ids.** Choice rows are numbered 1..=5 per 26/3 and never 0, 300 or
    301; no instance or lifecycle ids are involved.
12. **Others see changes.** Nothing in this slice is visible to other players.
13. **Content works end to end.** The quiz completes only after the correct last
    line, then Cole's held 49/13 pays 30 coins and 30 XP; Spritzy's step completes
    on the Talk and her lines finish cleanly. Asserted as final states/packets.
14. **Values live in data.** Text ids, response ids, retry flags, `then` lines and
    `complete_after_dialogue` are in `zone_seaside.json`; the code constants are
    the requested structural bounds and the client-locale fallback label.
15. **Canaries break production code.** See item 1: the break was in
    `Conversation::answer`, not in the test.
16. **Hands off session plumbing.** `bin/osfr-gateway.rs` and `gateway.rs` are
    untouched.
17. **One player's error never stops the server.** No tick work; malformed 26/6
    keeps its existing `io::Result` refusal; no client value is unwrapped
    (`checked_sub`, length filter); `two_players_quiz_independently` runs two
    sessions and proves isolation.
18. **A type's rules live on the type.** `StepConversation` keeps lines and the
    complete-after flag in one map entry (cannot drift); `OpenConversation` is one
    owned cursor with documented fields; `Gameplay.quest_conversation` says it is
    never saved; the new content fields are documented at their variant.
19. **Hot paths stay cheap.** No per-tick or per-packet-scan work: a 26/6 advances
    or clones one small line; a 26/10 scans the active quests' open objectives and
    clones the lines only when a conversation starts. Nothing is saved or cloned
    per tick.
