## Checklist

1. **Refusal changes nothing.** Wrong pending and duplicate confirmation requests snapshot
   the serialized gameplay state before and after. The deliberate pending-clear canary
   failed that snapshot assertion.
2. **Rollback covers all state.** The change adds no shared rollback state. Quest
   settlement remains on the existing staged `RewardState`; recovery only builds packets.
3. **Apply deltas.** Rewards go through the existing quest grant key. The test starts from
   a loaded wallet and asserts three additions of five, never restores an old snapshot.
4. **Busy rules.** No new timed or exclusive activity was added. Quest talk/turn-in is an
   NPC interaction; its new path applies only to an already pending turn-in. Existing
   encounter/crafting/gathering busy gates are untouched.
5. **Every entry path gated.** Offer, accept, Talk completion, same-session reopen,
   reconnect replay, and `49/14` settlement all use the shared NPC/gameplay dispatch.
   Quest eligibility is refreshed at the NPC packet entry, and exact pending state is
   required for settlement.
6. **Reachable in production.** The regression uses the real content loader, NPC
   visibility, `Gameplay::handle_in_world`, field combat tick, and initialization.
7. **Survives reconnect.** The test disconnects before `49/14`, reloads `GameplayState`,
   asserts a replayed `49/13`, then completes exactly once.
8. **Every exit restores the player.** Successful settlement clears pending state and the
   duplicate replay is inert. The dialogue can be reopened without consuming the quest.
   No timeout or separate player-location activity was introduced.
9. **Economy safety.** Coins are granted only by the server quest transaction with
   `quest:<character>:<quest>` idempotency. Forged ids, wrong pending ids, client claims,
   and repeats cannot create a grant.
10. **Wire format.** The test asserts `49/13` actor bytes at 6..14 and quest reply id at
    14..18. The three client readers above were checked directly; offer/reward layouts
    remain unchanged.
11. **Unique ids.** No runtime instance ids were introduced. NPC GUIDs come from content;
    the new spawn uses its existing content key rather than a reused public-world id.
12. **Others see changes.** Quest state is private. The new trainer spawn is verified as a
    directed `35/2` visibility packet. No outfit, job, or mount state was added.
13. **Content works end to end.** The test asserts the trainer spawn, three active offers,
    four real kills, all three `Completed` statuses, and exactly 15 fallback coins.
14. **Values live in data.** Kill count, quest ids, rewards, NPC identity, and spawn
    placement are content fields. The packet offsets are the recovered client layout.
15. **Canaries break production.** Both deliberate production mutations failed the
    production-path chapter test. A third removed the reconnect replay and also failed,
    then was reverted. No canary manufactured its own failure.
16. **Session plumbing untouched.** No gateway transaction, save ordering, teardown, or
    `src/bin/osfr-gateway.rs` change was made. The temporary kill-forwarding canary touched
    `gameplay.rs` only during the test and the file is byte-identical to `HEAD` again.
17. **One player cannot stop the tick.** The change adds no shared-tick arithmetic or new
    `?` path; it only replays a packet and reopens the exact saved pending screen. The
    production regression performs repeated attacks and invalid/replayed confirmations and

18. **A type's rules live on the type.** F135 adds no persisted field. It reads the

    one `Option` check.)
