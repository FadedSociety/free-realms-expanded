### The stale-invite test needed a second fix

The first port still sent the stale 40/4 **after** the real accept had consumed
the invitation. The server therefore refused it through the "no invitation"
branch, not the generation check, and deleting the generation check left the
test green (canary D passed). The test now sends the stale generation **while
the invitation is pending**: A invites B, B answers with
`invite_id ^ 0x8000_0000` (refused, result 3, no 40/4/8/9), then B answers with
the real id and the group forms. This is the regression test for the stale
generation: canary D now fails (`left: None`, `right: Some(3)`) because the
stale body is accepted and no 40/5 refusal is emitted.

## Security threat note (secure-code-guardian)

The diff adds no production parser and no new attack surface; it strengthens
the tests around existing boundaries:

- **Malformed field request (36/10 target mode 2).** A hostile client can send an
  unknown target mode for a known wolf. The gateway must refuse that one
  application message for that player, not damage the shared actor and not pay
  or advance anything. The test snapshots field health, coins and the whole
  saved quest object and asserts equality; canary C proves accepting the body
  fails the field-health assertion. The immediate valid swing proves the refusal
  consumed no attempt state.
- **Duplicate/stale group requests (40/1, 40/4).** A hostile client can replay a
  stale accept or a duplicate invite. The stale generation is answered while the
  invitation is still pending; the test asserts result 3, no 40/4/8/9, and that
  the real generation still forms the group (canary D). The duplicate invite
  asserts result 3 and no 40/1 to the target (canary E). After the refusal both
  members exchange party lines in both directions, so a refusal that removed
  either member fails.
- **Chat.** The server rebuilds sender identity from the session; the test sends
  the client's own name records and only checks routing. Tell recipients are the
  target only; party and say include the sender echo, asserted separately from
  B's delivery.
- **Rewards/economy.** Coins, job XP and quest credit come only from the
  server-owned kill and turn-in. Every payout is counted (no duplicate credit),
  compared with the saved total, and replay/corpse hits pay nothing. A
  duplicated killer credit (canary B) fails the saved-balance assertion.
- **Visibility.** A far session cannot see or be seen across the 100 m interest
  radius; the late joiner's AddPc carries the saved active profile rather than a
  stale pre-switch one.

No off-limits module was touched; no secret, dependency or real player data was
added. The two test literals used as needles are synthetic.
