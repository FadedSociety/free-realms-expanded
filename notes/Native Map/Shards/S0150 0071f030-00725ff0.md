# S0150 findings: character-create definitions and the item-definition framework

Range `0071f030..00725ff0` (151 functions). Everything in this shard is client-side, data-driven
configuration code: the character creator's definition tables, the item-definition store, and the
SoeUtil string/container plumbing they sit on. No packet is built, parsed or dispatched anywhere in
the range, so `wire` is empty for every record; the server-contract questions are stated as open
questions rather than inferences (see the last section).

## What the range contains

**Character-create UI handlers (ui.charactercreate).** `ClientAccountInterface::ChangeItem`
(`0071f030`) is a nine-way switch over the creator slot: 1 skintone, 2 hairstyle, 3 haircolor,
4 eyecolor, 5 facialhair, 6 facepaint, 7 wings, 8 clothes, 9 head/face-type. It stores the chosen
item id at `this+0x9f7c..+0x9f9c`, resolves the mapping/definition through the manager at
`this+0x10` (virtual slots +0x24, +0xc, +0x3c), builds the asset name with `0070ca40`
(`<race>_<gender>_hair_...` templates) and logs category-specific failures into
`ClientAccountManager.log`. It ends by copying the nine ids into the row whose `+0xac`/`+0xb0`
match `this+0x9f50`/`this+0x9f54` (race/gender) and firing the Lua callback
`CharacterCreate:SetCategoryButton`. `0071fd60` builds the nine category buttons and the initial
item grid through the Lua surface (`CharacterCreate:SetUpInitialCategoryButton`, `:ClearItems`,
`:SetOffset`); the race/gender gates in it (facial hair human-male-only, wings pixie-only) agree
with the wiki page "Human".

**Character-create definition tables (game.charactercreate).** Five tab-separated resources are
parsed by near-identical loop functions that open the file through the text reader
(`00fbda90/00fbdaf0/00fbe130/00fbe250/00fbdae0`), skip `#` comments, tokenize with `007065d0`
and link rows into five hash lists that live inside the account data manager object:

| Resource | Loader | Container in manager |
| --- | --- | --- |
| ItemDefinitions.txt | `00724b80` | item-definition manager list |
| CharacterCreateNames.txt | `007236c0` | `+0x9c58` (list head `+0x9c5c`, count `+0x9c64`) |
| CharacterCreateItemMappings.txt | `00723860` | `+0x9c68` (50 buckets `+0x9c78`) |
| CharacterCreateItemTypes.txt | `00723a70` | `+0x9d40` (10 buckets `+0x9d50`) |
| CharacterCreateItemClothingSets.txt | `00723c80` | `+0x9d78` (50 buckets `+0x9d88`) |
| CharacterCreateItemStartingSets.txt | `00723e90` | `+0x9e50` (50 buckets `+0x9e60`) |

`LoadAllDefinitionFiles` (`00724d80`) drives all six loaders and then allocates five
`IdToStringLookup` tables (`00725f40` ctor, `00725ff0` dtor, 100 buckets at `+0xc`) for
FacePaint/Hair/Head/ModelCustomization/SkinTone mapping files, storing them at `+0x9f28..+0x9f38`.
`IdToStringLookup_FindValue` (`00725a70`) is the id-to-string lookup those tables expose; it is what
`ChangeItem` calls to resolve a skin-tone alias id.

**The definition manager and item definitions (game.item).** `ItemDefinitionManager` is constructed
as the base chain of the account data manager (`007218e0` called from the
`ClientAccountDataManager` ctor `00725180`), destroyed at `00725470`/`00725030`, and holds a
10000-bucket id hash plus a doubly-linked list of `ItemDefinition` nodes (id `+0x24c`, hash link
`+0x248`, list links `+0x250/+0x254`, count at `+0xc`). `ItemDefinitions.txt` rows are built by the
factory `00724a80`: type `0xc` produces `ItemDefinitionStyleCard` (`00724820`), type `0x11` produces
`ItemDefinitionCustomization` (`00724960`), anything else a plain `ItemDefinition` (`00724300`), all
in a constant 600-byte block. Each definition embeds a `HashList<ItemStatDefinition,71>` (`00724250`
ctor, `00722b20`/`00723600` removal), an ability-entry `List` and three `IStringNoShare` strings; the
base record `BaseItemDefinition` (`007230f0`, dtor `00723040`) carries an embedded `IconData`
(`00720bf0`: Loggable+IconData vtables, imageSetId `+4`, tintId `+8`).

**Library plumbing.** SoeUtil `IString<char>` (`00722bf0` refcounted destructor, `00722e20`
deleting dtor), `IStringNoShare` (`00722da0`), `IStringFixed<char,256>`/`StringFixed<256>`
(`00725c60`, `00725ee0`), the HashList/HashListMap instantiations, plus the global and per-class
memory-manager allocation operators (`00722660`, `007226b0`, `00721da0/00721e00/00721e60`,
`00721de0/00721e40/00721ea0`).

## Cross-checks against existing notes

- The starting-set row layout from `CCItemStartingSetsDefinition_ParseFields` (`007257d0`) is
  `+0x14` then a skipped token, then twelve integer columns at `+0xac, +0xb0, +0xb4, +0xb8,
  +0xbc, +0xc0, +0xc4, +0xc8, +0xcc, +0xd0, +0xd4, +0xd8`. `ChangeItem` matches on `+0xac`
  (race) and `+0xb0` (gender) and writes its nine slot values into `+0xb8..+0xd8` in the same
  slot order (skintone first, head/face-type last). This is an internal consistency check, not
  proof that the rows `ChangeItem` mutates are the parsed starting sets: the walk is via manager
  virtual slots `+0x4c/+0x50`.
- [[Character Creation Audit]] records that the supplied `CharacterCreateItemStartingSets.txt`
  was empty (zero data rows) and that native creation then failed with `startingSetId=-1` for
  race/gender pairs 1/1, 1/2, 2/1, 2/2. The loader here (`00723e90`) simply parses whatever rows
  the file has into the `+0x9e54` list, so an empty file yields exactly zero starting sets. The
  audit's cross-reference is consistent with this code; the note does not cite these addresses.
- `IconData`'s field names match the harvesting review's normalisation
  (`{Id, TintId}`): dump `00720cd0` prints `ImageSetId=%d` from `+4` and `TintId=%d` from `+8`.

## Contradictions and limits

- Two byte-identical 7-byte bodies each write only `Loggable::vftable` into `this`
  (`00720bc0`, `00720c80`), and both are called exclusively from EH unwind funclets. One is
  presumably the Loggable constructor and the other its destructor, but the direction is not
  proven; they are labelled `Loggable::~Loggable` (likely) and `SetLoggableVtable` (speculative)
  rather than guessing twice.
- The definition-manager list header used by `DefinitionList_Append` (`007233b0`: head `+4`,
  tail `+8`, count `+0xc`, buckets `+0x10`) cannot be the head of the `ClientAccountDataManager`
  object itself, because that object already stores its second vtable at `+4` and its own
  10000-bucket table at `+0x18`. The `this` passed to `AddDefinition` is the pointer stored at
  `ItemDefinition+4` (written by the row parser `0072e050`, outside this shard), so the exact
  embedding of the manager block inside the account data manager remains unproven.
- The sixteen `+0x214..+0x230` accessors (`00724660..007247f0`) are present in the
  `ItemDefinition` vtable read from `017e8e04`, but their function-local evidence carries no
  class anchor, so they are recorded as speculative `GetField_xxx`/`SetField_xxx` with that
  vtable observation in `open_questions`.

## Server contract

No function in this shard touches the wire: the creator's appearance selection is resolved
entirely against local tables, the Lua UI, and the player model. The character-creation request
itself (LoginUdp creation body) is built elsewhere (the audit places the serialization in the
`ClientPcData` patch), so no server_inference is attached to these records. The relevant open
question for the server side is not in this shard: whether the original server validated the
submitted appearance ids against the same definition tables, including the race/gender
starting-set row that supplies defaults. Answering it needs the request-building code, not
these loaders.
