# T400: a crafting station interaction opens the recipe window

## What changed

- **Station interaction opens the recipe window.** Client 26/8 on a crafting station now answers
  server command **26/25 `CommandPacketShowRecipeWindow`** with the station job's recipe filter
  (Chef 10, Miner 9, Blacksmith 12 (R)), which the client turns into `RecipeHandler:Show` listing
  the learned rows of that job. A station is a placed world model that `crafting_stations.json`
  binds (for example the Farnum world Cooking Table `100000002537`), or an opening craft actor
  (stove/furnace/anvil) once its tutorial craft is no longer pending. While the tutorial craft is
  pending the opening actor keeps its 26/9 menu and tutorial start, unchanged. The wrong job and
  no station in reach answer the existing 26/24 refusal lines ("Switch to Chef to make that
  recipe.", "Move closer to a cooking station."). Busy players and every other target fall
  through to the existing NPC, opening and movie paths. The 26/24 start path is untouched.
- **World station spawns carry the station radius as their client prompt reach.** AddNpc
  `unknown_float_51` (byte 237 with an empty name) was 0 for every world spawn, so the client used
  its 7 m session fallback while the server accepts a station within 12 m. `NpcVisibility` now
  sets it from `crafting_stations.json` `interact_range` for station models, including later
  placements, as the opening actors already do (Native Interaction Acquisition Range).
- `activity_busy` moved from the `gameplay.rs` hub into `gameplay/occupation.rs` (the busy-table
  owner) to keep the hub net-negative; no behaviour change.

## What is not settled

- **Why X sent nothing and why the table vanished.** `0093bff0` resolves the same pair the prompt
  name resolves (`00bafb90`), and a resolved actor always produces 26/19 first, so case 45 either
  did not run or saw the sentinel. Static analysis did not find which. Two server-side anomalies
  sit exactly here, neither proven to cause it:
  1. The opening actors were delivered at login while the character was in zone 48000003 at
     (795, 85, 365), about 2,900 m away. The Round 5 review records the same client quirk for a
     battle spawner ("spawned at login 1,500 m away, the client never showed it"). In the two
     runs where the opening table / Bartle worked (013155 click, 203139 X), the character logged
     in 4-5 m from them.
  2. Seven opening actors have a world spawn at the identical position (2537 Cooking Table,
     2540/2546 Collect Bundles, 3156 Hooligan Wolf, 2385/2338/2351 guides); the server sends both.
  I did not change either (no evidence that the server causes the vanish; a fix touches opening
  delivery or content dedupe beyond this brief). After T400 both farm tables are 12 m candidates
  at the same distance and both open the window, so whichever the client targets works if the
  client sends 26/8.
- **Native re-check (lead):** log in at or walk into Farnum (not a far login + teleport), face the
  table within 12 m, press X and also click. Expected: 26/19 + 26/8 in, 26/25 `1a0019000a00000000000000`
  out, the recipe window lists Chef recipes, Stew starts the cooking game. If X still sends
  nothing after a near login, the duplicate (2) is the next suspect.

## Checklist

1. Refusal changes nothing: the handler is read-only (`&self`), the reply carries `changed:
   false`; tests snapshot before/after for both refusals and the window.
2. Rollback: no state is written, nothing to roll back.
3. Deltas: no inventory, coins or position touched.
4. Busy rules: a busy player falls through to the existing paths (movie line etc.); the 26/24
   start keeps its own busy refusal. No new activity.
5. Entry paths: X and mouse both arrive as 26/8 through `handle_npc_packet`; the tutorial 26/10
   path is unchanged; starting still requires 26/24 with all its checks.
6. Production path: wired into the real router; tests drive `Gateway::handle_at`.
7. Reconnect: no new state; the reach is rebuilt at load, placements reapply it.
8. Exit paths: the window opens a client UI only; nothing to restore.
9. Economy: no grants; the GUID is only used to look up server-known actors.
10. Wire: 26/25 cited to `00aa0920`/`00a9d110` (12 bytes, fully consumed); spawn bytes 224/237
    asserted against the AddNpc reader and the captured 334-byte frame.
11. Unique ids: none created.
12. Others see changes: the spawn reach goes through the same 35/2 for every viewer; no
    per-player visible change.
13. End to end: window lists the already-sent learned rows (filter column matches
    `wire_rows`); starting from it is the tested 26/24 path.
14. Values in data: reach from `crafting_stations.json` (bounded 0.1-100 by its loader); filters
    are the existing recovered/(R) constants.
15. Canaries break production code (listed above).
16. Session plumbing untouched.
17. No tick code; per-request errors are only the existing malformed-26/8 error.
18. `unknown_float_51` meaning documented at `set_station_reach`; the type's other fields are
    unchanged.
19. No hot path.

Threat note (secure-code-guardian): a hostile client controls only the 26/8 GUID and flag. Length
and flag are validated as before (malformed → the same error the NPC router already returned).
Any GUID is just looked up; an unknown or non-station GUID falls through. Out-of-reach or
wrong-job requests get a fixed line and no state change; the window itself grants nothing.
