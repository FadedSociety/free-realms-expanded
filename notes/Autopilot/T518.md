  - `FixtureConfigRow` gains `texture_alias`, `tint_alias` (strings) and `default_tint_id` (i32),
    all `#[serde(default)]`, so `capture_defaults` and older documents still parse. Its doc now
    describes the generated table and the (R) fixture-id convention.
  - `FixtureConfig::load(path)` reads at most `MAX_FIXTURE_CONTENT_BYTES` (4 MiB) + 1, refuses a
    larger document, parses with `deny_unknown_fields`, then runs `validate`. `validate` is now
    `pub`; it additionally refuses a negative `default_tint_id`, an alias longer than the codec's
    `MAX_STRING`, and a duplicate **item** definition id (duplicate fixture ids were already
    refused).
  - `HousingService.config` is `Arc<FixtureConfig>`; `new`, `from_state`, `with_content` and
    `from_state_with_content` keep their signatures and `config()` returns `&FixtureConfig`. The
    table is shared by every session clone instead of copied.
  - `fixture_asset` (127/42) sends the row's `texture_alias`, `tint_alias` and `default_tint_id`
    in the slots the client reader exposes; `fixture_update` (127/40) fills
    `Customization.texture_alias`/`tint_alias` from the row. Both cite the reader addresses.
  - `capture_defaults` keeps its nine rows (the seven captured plus the L040 kit pair) and gains
    empty/0 aliases; it is the fallback, not the production table.
- `src/gameplay/housing.rs` `HousingSession::load`: loads `housing_fixtures.json` from the content
  directory when present (validated), else `capture_defaults()`. The ponytail note is gone. Still
  dormant without `houses.json`.
- `tests/housing_service.rs`: `service_with_config` split out of `service_with_lot`; four new
  tests (bundled table contents, duplicate-row refusal + load refusal, old-save reload, 127/42 and
  127/40 aliases).
- `tests/housing_session.rs`: `Content::with_fixtures()` plus two synthetic catalogue rows; two new
  tests (generated table lists an owned Basic Square Block and Standard Outdoor Chair on entry,

## (R) rules

- `fixture_definition_id` = item id for every row except the seven captured rows, which keep their
  captured ids. The capture packet id is an inventory selection, not necessarily a fixture
  definition, so packet and client only need a stable unique key that survives reload; a generated
  id colliding with a captured one is refused by the generator, and duplicate fixture/item ids are
  refused by the loader.
- `default_tint_id` = `Icon.TintId` when it is a positive integer, else 0 (the pinned data uses
  `-1` for "no tint" on items 17750/17751, 250 rows have no tint block, none are 0).
- Alias semantics (`TextureAlias` -> texture, `TintAlias` -> tint) and the 127/40 `Customization`
  slot names are reconstructed from the Legacy field order; the slot *positions* are the client's.
- `category` is the item `CategoryId` as text; `lua_call` stays empty (no client table recovered).
- Type 29 is treated as "placeable" without a category restriction (two independent
  reconstructions agree: this brief's Build rule and Lxzxrus `HousingFixtureRules`); the one
  consequence is the category-308 farming sprinkler.
- `Customization.kind` and `texture_override` and `Customization.tint_id` stay 0/empty: the brief
  fills only the two aliases, and the meaning of the other three is not recovered.

## Security threat note (secure-code-guardian)

- **What a hostile client could send.** Nothing that reaches the new fields. The only inbound
  housing bodies are the existing 127/1 (selection id `u32`), 127/2 (selection + three float
  groups), 127/3 (fixture guid `u64`), 127/4, 127/5, 127/6, 127/19 and 127/20. A client cannot
  name an item definition, a model id, an alias, a tint or a fixture definition: the table is
  server content, and the row is looked up from the *inventory definition* the server already
  owns. 127/1 still binds only an owned single-unit item on the actor's own editable lot, and
  127/2 resolves only a bound selection (unchanged, still exercised by
  `decorate_refusals_answer_127_53_and_change_nothing`).
- **Why bad data is refused.** The content file is bounded at 4 MiB + 1 and validated whole at
  load: schema version, non-empty, `MAX_CONFIG_ROWS`, positive ids, unique item and fixture ids,
  non-negative tint, aliases <= `MAX_STRING`. A row that would make every 127/42 for that item
  fail at encode (negative tint, oversized alias) is refused at startup instead. A refused table
  fails the housing session load (fail closed) rather than falling back silently to a different
  table.
- **Economy.** Placement metadata only: no grants, prices, stock, coins or rewards. The generated
  rows cannot be sold, bought or re-granted; the 127/43 list only describes items the character
  already owns. Conservation, the stacked-instance refusal and every request path are unchanged.
