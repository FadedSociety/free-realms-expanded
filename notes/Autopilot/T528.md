So a bag use of 79150 is **42/16 -> 38/30 -> 42/15**, each request exactly `u16 42, u16 15|16, i32
instance id` (8 bytes).

(b) 36/17 `AbilityPacketExecuteClientLua`:

- ctor `00a2f5e0` (`sub_A2CB70(17)`); reader `00a30060` (`sub_A2FC10` reads the two header int16s,
  then an i32 byte count and the string via `00894b10` into `+0xc`, then three i32 into `+0x1c`,
  `+0x20`, `+0x24`); handler `00a31d40`.
- Dispatcher `00a35cc0`, case 17 at `0x00a367ea`: it loads the three values with
  **`fld dword ptr [esp+30h]`, `[esp+34h]`, `[esp+38h]`** — they are f32 in that order — pushes
  them as Lua arguments 0, 1 and 2, pushes the parsed string pointer (`[esp+24h]`) and calls
  `009797a0` on the Lua manager `dword_1BE1090` with that argument table.
- Encoder shape: `[36,0,17,0]`, i32 name length + bytes, f32, f32, f32. The first argument is the item
  definition id; the other two are (R) 0.

(c) `009797a0` (also called by `ExecuteLuaEvent::Run` `00c4fb60`):

- It copies the name, then scans for `':'` (`0x3a`) -> method mode or `'.'` (`0x2e`) -> field mode.
  With no separator it looks the whole name up as a global.
- It pushes the left part as a global (`sub_E3ACA0(..., -10002, ...)`) and requires LUA_TTABLE (5),
  then indexes the right part and requires LUA_TFUNCTION (6).
- Only in method mode does it push the table (`sub_E3A550(v10, -2)`) before the call.
- Both `BrowserV2:ShowUpgradableMounts` and `BrowserV2.ShowUpgradableMounts` resolve; the colon form
  is the one that passes `self`, which `ShowUpgradableMounts` needs (`self.isUpgrading = 1`,
  `self.upgradeItemDefinitionId = ...`). **Chosen: the colon form.**

## Security note (secure-code-guardian)

Hostile client: it can send `42/15`/`42/16` with any instance id, any count, at any time, replayed or
in a bundle, and it can name an instance it does not own.

- The request carries only an instance id; the *definition* and ownership come from the server-side
  inventory row. An unknown instance is refused (`UpgradeItemNotOwned`) and an instance whose
  definition is not in the `mounts.json` allowlist is not handled here at all (`NotUpgradeItem`), so
  a hostile id can never open a picker for a non-saddle.
- Nothing is consumed, granted, bought or persisted by the use: the packet sent is a static Lua call
  with a server-chosen definition id (never client text), so there is no economy path and no
  injection surface. The Lua name is a compile-time constant; the client cannot supply it.
- Refusals send one system-chat line and no packet; the state snapshot is asserted unchanged in the
  test (state + inventory before/after).
- The picker goes to the owner only (`Outcome.replies`); `Outcome.nearby` stays empty, so nobody
  else's client is asked to run Lua.
- The handler returns `Ok` for every outcome (no `?` on client data, no `unwrap`), so a hostile body
  cannot produce an internal error or a panic; malformed lengths simply fall through to the old
  routes.
- The Marketplace row is server content with `no_sale: true` and `sc_price`; the order path already
  validates the bundle id against the catalogue and the wallet (T230), so a client cannot buy it for
  coins or for free.

## Checklist

1. **A refusal changes nothing.** `a_saddle_use_is_refused_when_not_owned_or_busy` snapshots
   `GameplayState` and `InventoryState` before each of the four refusals (unknown instance for both
   42/16 and 42/15, knocked out, gathering) and asserts equality. Canary 2 breaks the gate and the
   test fails. The accept path is asserted equal too (a use consumes nothing).
2. **Rollback covers all state.** `upgrade_use_plan` is pure; the only state read is the live
   inventory and the existing restrictions. No `Rc`/`RefCell`/side table, no clone, nothing to roll
   back.
3. **Apply deltas, never restore old snapshots.** Nothing is written; no snapshot is restored.
4. **Busy rules are mutual.** The saddle use is a one-shot request, not an activity, so it adds no
   `Occupation` row (the same reasoning as T527's 168/14). It is gated by the shared
   `ride_restrictions()` -> `blocks(Gates::ride)`, which is true for every occupation in the table
   (`Forging`, `Smelting`, `Cooking`, `Mining`, `Harvesting`, `Chess`, `Encounter`, `Derby`,
   `Fishing`, `Soccer`, `Kart`, `FieldEngaged`, `Housing`); a node runs inside one message, so no
   other activity can start while it is in flight. The gathering case in the test is caught earlier
   by the harvesting movie gate, which is also a refusal with no packet and no state change.
5. **Every entry path is gated.** Both `handle_item_bar` call sites reach the route (non-opening
   `handle_in_world_inner`, opening `handle_opening_inner`); the gateway routes 42/15 and 42/16 as
   `item_use` into `handle_in_world` with no parallel path. Owner, allowlist and restrictions are
   re-read on every request, so a relog or reconnect only changes what the inventory holds.
6. **Reachable in production, tested through it.** `tests/mount_upgrade.rs` drives
   `Gameplay::handle_in_world` (the gateway's own entry) with the exact 42/16 and 42/15 bodies, and
   `tests/station_cash.rs` drives the real 66/3 order decoder. No internals are called and no rule is
   copied.
7. **Survives reconnect.** The use introduces no session state (no pending confirmation, nothing
   spent), so there is nothing to persist or restore. The saddle itself is an ordinary inventory item
   and therefore already saved; T527's test covers reloading a save that holds one.
8. **Every exit path restores the player.** A refusal leaves the player free; a success only opens a
   client window, and the picker's Cancel (`BrowserV2:OnUpgradeCancel`) needs no server round trip
   (the brief's rule). No mount, pose or location changes here.
9. **Economy safety.** The use grants nothing and spends nothing; the picker cannot fabricate an
   upgrade (168/14 re-validates ownership, then consumes one server-chosen saddle instance). The
   Marketplace order is the paid path (66/3, wallet debit), the row is not a free grant, and only the
   player's own saddle can be used.
10. **Wire format matches the client reader.** 42/15 and 42/16: writers `00c10940`/`00c109f0` and the
    Lua bindings `00c11bc0`/`00c11cb0` (one i32). 38/30: native `0089ea30`, handler `00a1a7d0`; the
    encoder is the one the consumables path already used and the 25-byte layout is pinned in
    `tests/item_bar.rs`. 36/17: reader `00a30060` + dispatcher `00a367ea` (`fld dword` x3), and the
    test decodes the bytes with a reader-faithful parser (name length, three f32, no trailing bytes).
11. **Unique ids.** None allocated; the instance id is the server's inventory instance id.
12. **Others see changes.** Nothing is visible to others; `out.nearby` is asserted empty and the
    packet goes to the owner only.
13. **Content works end to end.** The saddle is listed and purchasable for Station Cash (station_cash
    test), using it opens the picker with the real item definition id (mount_upgrade test), and T527's
    test consumes it and trains the ride. The content row is real data, not a fixture.
14. **Values live in data.** `sc_price` (and the provenance) is in `stores.json`; the allowlist is in
    `mounts.json`. The only new constants are protocol facts (the Lua name, the 36/17 shape, the
    (R) zero arguments), not tuning values.
15. **Canaries break production code.** See the two canaries above; both changed production code and
    failed the assertion, then were reverted.
16. **Hands off session plumbing.** No change to `gateway.rs`, `bin/osfr-gateway.rs`, session
    creation/teardown or save ordering.
17. **One player's error never stops the server.** The handler never returns `Err` and never
    `unwrap`s a client value; a malformed body is `None` (the old route), a bad instance is a notice.
    No arithmetic on client values.
18. **A type's rules live on the type.** The node allowlist/restriction rule is
    `MountService::upgrade_use_plan`; the 36/17 layout is `MountService::upgrade_picker` with
    `UPGRADE_PICKER_LUA` documented next to it; the 38/30 layout is
    `use_wire::encode_immediate_activation_check`; the 42/15 decode stays in
    `use_wire::decode_immediate_activation`. `Listing.ride` was already the single "is this a ride"
    decision and is untouched.
19. **Hot paths stay cheap.** Per packet, `handle_item_bar` now runs one `decode_immediate_activation`
    (a length check and two `u16` compares) before the existing work: no allocation, no clone. Only a
    42/15/42/16 for an allowlisted saddle allocates (the ~49-byte reply). Nothing was added to any
    tick.
