## Client evidence (IDA, 2026-10-19)

All facts below come from `python -I .../ida_query.py decompile <addr>` against
the shipped `FreeRealms.exe.i64`. They are recovered facts, not reconstructed
rules. Re-verified in this attempt: `008d8e70`, `0090ae60`, `008fca60`,
`00912090`, `009121e0`, `00c235c0`, `00a97250`, `008a35c0`, `008dce80`,
`008dcf30`, `00a95c50`, `008e7290`, `00a0e8f0`; no query contradicted the
layout below.

- `008d8e70` (group header reader) reads exactly two `i16` from the packet
  reader and stores them at object `+4` and `+8`. It reads nothing else.
- `008a35c0` (packet base initializer) sets `+4 = 40` (family) and
  `+8 = the subtype`. `008dce80` (40/1 constructor) calls it with `1`;
  `008dcf30` (40/4 constructor) calls it with `4`.
- `0090ae60` writes exactly those two fields as u16 to the wire. The 40/1
  writer `00c235c0` and the 40/4 writer `00a97250` both call it first.
- `0093daf0` (family-40 dispatcher) reads the same pair with `008d8e70` and
  switches on the second value (cases 1..9). For cases 1 and 4 it re-parses the
  raw packet from the start through `00921640` / `00921700`.
- `00921640` -> `00912090` (40/1 reader): after `008d8e70`, `008fca60` reads
  one u64 guid + NameData, a second u64 guid + NameData, and one u32;
  `00912090` then reads five u32.
- `00921700` -> `009121e0` (40/4 reader): after `008d8e70`, `008fca60`, one u8
  accept flag, then five u32.
- `008fca60` reads exactly two guid/NameData records and one u32. It does not
  read a u16 between the header and the first guid.
- `00c235c0` (40/1 writer) = `0090ae60` (u16 40, u16 1), `00a95c50` (both
  guid/NameData records and the `+72` dword), then five dwords.
- `00a97250` (40/4 writer) = `0090ae60` (u16 40, u16 4), `00a95c50`, then the
  accept byte, then five dwords. `00a95c50` itself writes the two records
  (`008fb810` + `00a0e8f0`) and the `+72` dword; nothing else.

Resulting layout (now implemented and pinned by tests):

```text
40/1: u16 40, u16 1, guid+NameData (inviter), guid+NameData (target),
      u32 (+0x120), u32 x5
40/4: u16 40, u16 4, guid+NameData (inviter), guid+NameData (target),
      u32 (+0x120), u8 accept, u32 x5
NameData (`008e7290`): i32 x3, i32 length + bytes, i32 length + bytes
```

The old note's "two short fields" after the header were the header itself.
`notes/Research/Friends and Groups.md` is corrected with these addresses. The
brief's `notes/Design/Friends and Groups.md` does not exist in this tree; the
existing research note is the file that carried the wrong layout.

## Security threat note (secure-code-guardian)

Attack surface: family-40 invite and accept/decline packets from any
authenticated hostile client.

- **Old padded 40/4** (header + four zero bytes + records): the exact-length
  reader (`r.end()`) drops it; the routed test snapshots the pending row,
  roster and group mappings and asserts they are unchanged, and then proves the
  same session is still served by sending the native packet afterwards. Canary
  1 (pair restored only in the 40/4 arm) makes this test fail, so the refusal is
  live.
- **Truncated or trailing bytes** are already refused by `WireReader::take` and
  `r.end()`; no client-controlled length is indexed.
- **Names** are parsed by the existing bounded `social_name` (128-byte parts)
  and resolved through the authenticated identity directory; the actor guid is
  the session's character, never the packet's sender guid.
- **Token**: the `+0x120` dword is compared with the server-owned pending
  invitation generation (F189); a forged, stale or repeated value returns 40/5
  code 3 with no mutation. This change does not touch that check.
- **Economy**: group invites grant no coins, items or XP and contain no item
  id or quantity.
- **Overflow**: no new arithmetic; the removed reads only shrink the input that
  reaches the existing checks.
