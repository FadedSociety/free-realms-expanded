### Ponytail cut

`wire_rows` had:

```rust
let output_id = u32::try_from(recipe.output.definition_id).unwrap_or(0);
let item_definition_id =
    if output_id > 0 && inventory.has_definition(recipe.output.definition_id) { ... }
```

`validate_recipe` rejects `output.definition_id <= 0` before a catalogue can be
loaded (`src/recipes.rs:482`), so `output_id > 0` is redundant. The guard is
gone; the product-vs-pattern decision is now exactly
`inventory.has_definition(recipe.output.definition_id)`. For a hand-built
catalogue with an invalid output id the fallback is still the pattern id, so
even an unvalidated caller cannot emit a negative id.

  lengths, or minigame result payloads. F289 adds no parser, opcode, field or

- The route-test selector change is fixture setup (`select` sends the ordinary

## F304 correction

The review of this commit (`lab/autopilot/reviews/7a5246c-F289.md`) found that
the checklist's "positive validated pattern id" claim was not enforced:
`RecipeCatalog::load_runtime` builds its item set from the recipe file itself,
so a private `recipes.json` with a zero or negative
`recipe_item_definition_id` loaded and `wire_rows` emitted item 0. F304 adds
the load-time positivity check in `validate_recipe`; the regression test is
`tests/recipes.rs::runtime_catalogue_rejects_a_non_positive_pattern_item_id`
(covers 0 and -1). The security note above and checklist item 9 are true from
F304 on, not at F289.
