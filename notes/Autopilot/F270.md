## Security threat note (secure-code-guardian)

- Attack surface: a hostile client can send 26/8, 26/10, 26/6, 49/2, 49/14,
  39/5, 39/6, 41/109 and 138/2/6/7/14 at any time. F270 added no parser, selector,
  packet family, objective kind or client-supplied quantity. **F287 correction:** the
  net behaviour change is the restored content offer gate; 3070003/3070004 are again
  restricted to the active 137 profile.
- Why that is safe: the offer comes only from Reed's server-side 26/8 -> 26/10 ->
  26/6 -> 49/1 path; 49/2 is accepted only for an offered quest and rechecks the
  remaining requirements (none here); the 49/13 end screen is opened only by the
  server's own Talk objective completion; 49/14 needs that pending screen and the
  per-character grant key. A forged 49/2/49/14, a wrong in-range NPC and replays
  leave the snapshot byte-identical (asserted).
- Reward profile: the content map names profile 137 and `apply_grant` only grants XP
  to an unlocked profile. On the merged tip F249's `rewards::locked_job_profile`
  refuses the turn-in without a grant (and releases the pending screen) when 137 is
  locked. With the gate restored a normal character cannot accept before learning 137,
  so a new offer cannot reach that refusal.
- Client-reported results are still not authority: forged 138/14 is rejected as an
  unknown fishing sub-opcode; forged 39/18 and 39/14 carry the real 599 id and change
  nothing because `npc_minigame_win` only inspects server-generated replies after a
  paid catch. The catch count/items/coins come from `settle_catch`.
- Busy rules are the existing `Occupation::Fishing` table; an active round refuses
  Reed's menu (asserted), and the chapter is only playable after 39/6/41/109.
- No save file is written directly; the tests use the existing typed `GameplayState`
  snapshots, and production writes stay in `character_store::replace_bytes`.
