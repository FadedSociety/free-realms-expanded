# T847: a raised fixture can be lowered again

Native 2026-10-27 ~23:30Z reported that the housing radial's Up control raised a fixture but the
fixture never came down. The trace shows the server refused every `127/5` move, so the fixture's
entity and saved record stayed at ground; the next vertical drag therefore started at ground again.
The server read the `127/5` dword where `127/2` carries the placement scale, and that dword is 0.

## Evidence

### The radial has one Up button that enters a mouse-follow mode

- `ScriptsBase.lua` `MakeHousingRadialMenu` (line 33798) sets four buttons: `Housing_Radial_Up`
  (`INTERACTION_VERTICAL_MOVE`, line 33812), Rotate Left, Remove, Rotate Right. There is no Down
  button. `OnRadialMenuClick` (line 33730) calls `House.MoveFixtureVertically(currentItemGuid)`.
- Binding table `0x0182ae50`: `"MoveFixtureVertically"` -> `sub_C0C140`. It reads the guid with
  `sub_BFEA90` and calls `sub_AB2250`.
- `sub_AB2250` sets `*(this+24)=2` (the vertical edit mode) and sends nothing. It builds the edit
  object (`sub_AAB230`) and captures the current entity pose with `sub_CB93F0` (entity `+752`) and
  `sub_CB9420` (entity `+400`). Horizontal Move uses mode 1 (`sub_AB0D60`).
- `sub_ABB630` is the per-frame update: for `*(this+24)==2` it projects the mouse ray (`sub_7923E0`)
  and moves the fixture locally; it has no server check. Up and down are the same mode, with the
  mouse above or below the start point.
- The commit copies the selected fixture's fields and sends `127/5`: `sub_AC8790` -> `sub_AC7CE0`
  -> writer `sub_ABF620`. The writer emits guid, position float4, rotation float4, a dword, then a
  24-byte tail.

### What the real `127/5` carries

Community-preserved client capture `lab/references/OpenSourceFreeRealms/ofrserver/Packets/p2.pcap`
(sha256 `65ac0801...`), decoded with `lab/reports/piece-022-20261009T025254Z/decode-housing-capture.py`:

- frame 32782 and 33039: 72-byte `127/5`. guid `0x07f54ca17bf5c009` / `...c008`, position
  `(439.5, -0.1107, 427.0, 1.0)`, rotation `(0, 0, 0, 0)`, **dword 0**, tail
  `0,0,0,0,0,1.0`.
- frame 31494: a `127/2` place with the last dword `1.0` (the placement scale). The same offset in
  `127/5` is 0, so it is not a scale.
- frame 32787: the `127/51` reply (guid plus two float4, reader `sub_AB2D10`), carrying the moved
  transform. Handler `sub_AB8DC0` finds the entity with `sub_984960` and applies the transform.

### What the live run did

`lab/runs/client-baseline-20261027T230650Z/server-trace.jsonl` entries 6919-7150:

- The window has 42 `127/5` log rows (the transport and the handler each log a packet) and 21
  37-byte `15/3` system chats: every one of the 21 distinct moves got exactly one refusal and no
  `127/51` was sent. The system packet is 9 bytes of framing plus 28 text characters; the move
  refusal set's 28-character message is "That placement is not valid." So the server did refuse
  every move, as a chat line rather than a `127/53`.
- The moves are the block guid `0x7f3236f9178e23b9` (y -0.87 (ground) -> -0.07 -> back to -0.87
  with rotation 0 -> 2.3774) and then the Chicken `0x7f2892d3de1e9f28`. The -0.87/0 packets are the
  base pose, not a cancel: they are what the client keeps sending because the server never updates
  the fixture. The build box is `y -100..60` (`houses.json` property 25), so no move was refused
  for height or horizontal bounds.
- Reverting the one-line fix reproduces the production error exactly:
  `Housing(TransformOutOfBounds)` from `validate_transform` (scale <= 0), whose denial message is
  "That placement is not valid.".

The `127/51` reply is what moves the actor entity. `sub_AB2250` reads that entity on the next Up,
so without the reply every drag restarted at the ground pose and only upward mouse motion moved the
fixture. The client does not wait for a bounds field or permission from the server to allow a lower
position; it waits for the previous move's `127/51`.

## Reconstructed (R) rules

- (R) The `127/5` dword after the two quads is not a scale. Only its observed 0 is known; no server
  reader exists. The save keeps the fixture's own scale, so a client cannot resize a fixture.
- (R) The 24-byte tail is not decoded. Its last float is 1.0 in both captured moves.
- (R) The vertical drag's ray/clamp geometry is client-local; nothing is reimplemented server-side.
- A move refusal still answers only a chat line (no `127/53`); that is the pre-existing
  `Request::answers_with_denial` policy, unchanged.

## Security note (secure-code-guardian)

- Hostile client input: a `127/5` with any fixture guid, NaN/inf/huge position or rotation lanes, a
  zero/negative dword, a truncated or oversized body, a guid from another lot, or a move without
  entry/edit mode.
- Refused before any write: the codec bounds the body and requires finite floats; the service
  checks the actor entered the lot, is the owner/editor, the fixture exists in that lot, the
  transform is finite/bounded/unit-facing, and the position is in the lot's build area. The lot is
  staged on a clone and only committed after every check.
- The dword is no longer trusted as a scale; the saved scale comes from the fixture's own record,
  so a client cannot resize or alias a fixture. The fixture guid is resolved only inside the acting
  player's lot, the reply goes only to that session, no item is granted or consumed, and no file
  is written by the service (the lead's save envelope owns persistence).
- Threat is unchanged for ownership/economy: a move cannot name another player's fixture, cannot
  create a second fixture, and cannot move an item out of the bag.
