## Threat note (secure-code-guardian)

Attack surface: any client can send 26/8 (arbitrary u64 target + flag), 26/10 (arbitrary
target + i32 choice), 26/6 (arbitrary row), 49/2 (quest id + accept), 49/14 (quest id), forged
49/15 breadcrumbs and position updates at any time. No new parser or wire field was added;
every path below is the existing production one.

- **Forged 26/8 at an unspawned/unknown actor:** `NpcVisibility::content_key` resolves only
  loaded rows; an unknown GUID has no menu and changes nothing. Canary 1 proves the extra row
  is what binds `9000000428` to an interaction.
- **Forged 26/10 choice:** the choice must be an option of the currently open interaction and
  the handler re-checks zone/range; an unoffered choice is an `Err` refusal with the whole
  state unchanged (`unoffered_menu_choice_changes_nothing_and_keeps_the_menu_open`).
- **Forged 49/2 accept:** only an actually offered quest passes `offer_denial`
  (enabled/objectives, giver, pending offer, prerequisite, active+unlocked job, limit) and the
  accept re-checks. The job gate cannot be claimed by the client: `character_eligibility`
  reads the saved active/unlocked profile only. Test 1 and test 4.
- **Forged 49/14:** settles only the saved `pending_turnin`; no end screen, a wrong quest and
  a replay pay nothing and leave every byte equal (test 4). The reward is content-authored
  (5 coins, 25 profile-43 XP, empty items) and paid through the existing
  `quest:<character>:<quest>` grant key, so replay cannot double-pay (tests 2, 4, 5, 6).
- **Near cap:** with the wire coin field at `i32`, a near-cap wallet's checked grant refuses
  at `RewardState`/`apply_grant`: test 4/6 assert `Err`, no coins/XP/item, the pending screen
  still held and both sessions' saves unchanged (the existing quest-row behavior; see gaps).
- **Free items:** the reward grants no item, so nothing is sellable or re-grantable; the
  starter outfit remains trainer-issued only.
- **No client values are trusted:** no amount, item id, quest outcome or score from the client
  reaches the payout; only the server's own Talk/49-14 sequence does.
- **Per-player errors:** the only refusal paths here are per-request results; no `?` was
  added to a shared tick (no production code), and the two-session test keeps both players
  processing.
