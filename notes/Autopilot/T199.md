## Client evidence

- 15/3 is `ChatPacketDebugChat`. F238 re-decompiled the 2014 client: dispatcher `0x00b14350`
  reads the shared two-u16 header with `0x00b0f550` and, for subtype 3, calls constructor
  `0x00b0f9d0` (mode 3) and body reader `0x00b0f5f0` via `0x00b10a20`. The body reader consumes
  two u16 header words, a u32 byte length, that many text bytes (string setter `0x894b10`) and
  one flag byte at `+544`. The server's 15/3 body is `u32 length`, escaped text, one flag byte
  — exactly what `chat::system` writes. `0x00b0f9d0` is the constructor, not the reader.
- 15/1 is `PacketChat`: `0x00b140c0` → `0x00b11600`; its sender/recipient names and GUIDs are
  advisory and never select the actor (`chat::request` returns text only).
- F238 query results: the dispatcher switch, the ctor and the reader were decompiled through
  the live IDA broker; the exact addresses above are the ones in the disassembly. T199's
  original note could only corroborate them through the native-map pseudocode (the broker had
  timed out), so its address label was unchecked until this review.

## (R) reconstructed rules

- Bounds 200 characters / 2 KiB (`MAX_BROADCAST_CHARS`, `MAX_BROADCAST_BYTES`) are local
  defensive limits chosen for this build; no native broadcast command exists to copy.
- ASCII controls `< 0x20` and `0x7f` are refused; other Unicode whitespace inside the text is
  kept. Markup is escaped by the existing `chat::system`, not re-implemented.
- Command matching is on the first word after `realm `, so the message text keeps its case and
  no second realm parser exists.
- The 2 KiB notice bound is unreachable through the client chat route: `chat::request` already
  caps one message field at 2,048 bytes, so an oversized wire line is dropped before gameplay.
  The module bound still guards direct callers (and a future route).

## Threat note (secure-code-guardian)

Attack surface: a client's 15/1 chat body can carry any text, and the command is reachable by
any role that `command_refusal` lets through.

- Player/builder: `broadcast` is not in the ordinary allowlist, so `may_run` (account-store
  role, or `--dev-tools` local admin) refuses it; one system refusal to the sender only, and
  the refusal path changes no state or save (test).
- Control characters: CR/LF/tab/NUL/0x7f are refused before encoding, so a hostile message
  cannot break the length-prefixed packet, forge a second packet, or inject log lines.
- Oversized/UTF-8: the 2 KiB pre-check and 200-character bound refuse before any packet or
  per-recipient allocation; the chat reader's 2,048-byte field cap refuses oversized wire
  messages first (dropped, not answered). No input is echoed in a refusal.
- Markup: `chat::system` escapes `&`, `<`, `>`; the encoder is not duplicated (test asserts
  exact bytes against `chat::system`).
- Identity: client-supplied sender/recipient GUIDs and names in 15/1 are ignored; the session
  supplies the command identity.
- Fanout scope: only `chat_sessions` (sessions that entered the world); a connected handshake
  session is skipped (test), and no offline player or other process is involved.
- Budget/roles/admission: unchanged. The account-wide action budget still runs before staging;
  no new budget, role, security-log event or persistence was added.
- Failure isolation: a refused or failed transaction drops the notice; a recipient that leaves
  between commit and queue is skipped by `queue_delivery` without failing the others.

## Open gaps

- The in-movie refusal is pinned at the gameplay level
  (`an_active_cooking_movie_refuses_the_broadcast_before_staging_it` loads a valid active
  `CookingRun` and asserts the intercept refuses before the command parser). The bin rig still
  cannot reach a movie: the only non-ignored launch path needs the private cooking-station
  fixture (`s6_characterization` is ignored). This is the explicit deviation the review allowed.
- A disconnect between commit and queue is handled by `queue_delivery` (existing path) but no
  new fixture drives that precise window.
- A bundle containing two `realm broadcast` commands keeps the last one (single `Option` per
  staged outcome, as specified); a bundle whose later child is not a broadcast now keeps the
  earlier notice (F238 regression `a_bundle_that_broadcasts_then_helps_keeps_the_notice`).
- The broadcast deliveries are queued by `dispatch_message_inner` after commit, so they are not
  mirrored into the sender's optional `app_out` trace stream (they still go through the normal
  per-session sender and are traced there when that session enables tracing). A trace-only gap,
  not a gameplay one.
- F238 verified the 15/3 reader through IDA (`0x00b14350`, `0x00b0f9d0`, `0x00b0f5f0` via
  `0x00b10a20`); the raw body's text bytes are consumed by a string setter (`0x894b10`), and
  only the length/text/flag shape is needed by this server path.

## Checklist

1. **Refusal changes nothing** — the bin rig snapshots character state and save bytes around
   role refusals (`player_and_builder_broadcasts_are_refused_without_fanout`) and invalid text
   (`invalid_text_is_refused_without_a_save_or_a_witness_notice`, which also asserts the
   witness gets nothing); `empty_overlong_multibyte_or_control_text_is_refused` covers the same
   refusals at the gameplay level and the active-movie refusal asserts unchanged state. No
   menu/offer/counter/cooldown is touched by the path.
2. **Rollback covers all state** — the notice is a field on the staged `Outcome` and
   `GatewayOutcome` only; there is no `Rc`/`RefCell`/`Arc` or side table. F238 captures it into a
   local in `dispatch_message_inner` before `commit_outcome`, so a refused or failed transaction
   drops it and only a successful commit fans it out.
3. **Apply deltas** — nothing here restores a snapshot; the fanout only appends deliveries.
   `announcement_does_not_change_character_state_or_save` compares full gameplay + save bytes.
4. **Busy rules mutual** — no new activity or busy gate; `broadcast` is a command, and while a
   crafting movie is active the existing intercept returns the "Close the … game" refusal
   before the command runs. No `Occupation` entry is needed (no start/stop activity).
5. **Every entry path gated** — the command is added to both realm paths, after
   `command_refusal`/`may_run`; tests cover both content shapes (opening pack and
   opening-less `rust-gameplay`) for admin success and player/builder refusal.
6. **Reachable in production** — `tests/world_notice.rs` drives
   `Gameplay::handle_in_world`; `t199_world_notice` drives the real bin
   `Session::dispatch_message` → `Gateway::handle_at` → `commit_outcome` → `queue_delivery` →
   sender output. No copied logic.
7. **Survives reconnect** — the announcement is deliberately session-only and has no state to
   persist (task invariant); nothing was added to the save schema.
8. **Every exit path restores the player** — the command never moves, equips, or locks the
   character; cancelled/failed/refused paths leave state identical (tests 1/3). A recipient
   leaving between commit and queue is skipped by the existing `queue_delivery`.
9. **Economy safety** — no coins, items, ids or rewards are touched or accepted from the
   client; only server-validated text is relayed. Tests pin that the save is byte-identical.
10. **Wire format** — 15/3 is reused; the exact packet `[15,0,3,0][u32 len][escaped text][1]`
    is asserted byte-for-byte per recipient (`maximum_length_escaped_text_reaches_each_recipient_byte_exactly`,
    a 200-character markup text) and decoded per recipient in every fanout test; client
    dispatcher/ctor/reader addresses are cited above.
11. **Unique ids** — not applicable; no instance/GUID/lifecycle id is created.
12. **Others see changes** — the fanout is the existing directed chat delivery path
    (`chat_sessions` + `queue_delivery`); every online session receives exactly one copy,
    including a replayed reliable datagram (`a_replayed_reliable_packet_announces_once`).
13. **Content works end to end** — each session's received text is asserted, not a flag; the
    sender is included and no session gets a duplicate or the literal command.
14. **Values live in data** — the 200/2 KiB limits are the task's explicit `pub const` spec,
    not tuning knobs; no timeout/window/cap was invented.
15. **Canaries break production** — two canaries above modify production code and fail real
    tests; the bound test initially moved with the const and was fixed to pin literals. F238's
    canary reverted the gateway bundle merge (`.or(...)` → plain assignment) and
    `a_bundle_that_broadcasts_then_helps_keeps_the_notice` failed with the notice missing.
16. **Hands off session plumbing** — F238 removed the first version's `commit_outcome` change
    entirely: no session creation/teardown/transaction/save-ordering changed. The fanout runs in
    `Session::dispatch_message_inner` only after `commit_outcome` returns success
    (`a_failed_save_never_announces` pins that a failed transaction announces nothing).
17. **One player's error never stops the server** — the fanout runs inside the session's
    dispatch after commit; per-recipient queue errors follow the pre-existing `queue_delivery`
    error path for that session. No `?` was added to a shared tick; the command produces no
    shared field work.
18. **Rules on the type** — `Outcome.broadcast` and `GatewayOutcome.broadcast` carry doc
    comments stating the session-only/no-save/after-commit rule; `absorb` is exhaustive so a
    new field fails to compile; `delivery::broadcast_deliveries` documents scope and encoding.
19. **Hot paths stay cheap** — per packet the added work is one `Option::or(..)` merge in the
    gateway (F238 deleted the dead no-reply guard); per tick, nothing. A broadcast encodes once
    and clones the ≤2 KiB packet per online recipient; no state clone was added.
