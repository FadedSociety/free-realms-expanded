# F140 Chess: replay farming and client-pushed computer moves

Status: implementation and focused tests green; `cargo test --no-run` compiled every test target
(exit 0). The graph server was unavailable, so ownership was confirmed with `rg` (see Structure).

## What changed

- `src/chess.rs`: the computer's reply no longer follows from the position alone. Every table gets
  a SplitMix64 stream seeded from OS entropy (`RandomState` keys plus a process counter), mixed with
  the table id and an open counter. `server_move` ranks the legal moves with the existing one-ply
  score and picks uniformly among all moves within an `(R)` near-equal window; `skill` widens the
  window (`margin + margin * (100 - skill) / 100`). The old FEN-parity "easy takes the second-best
  move" rule is gone. The client engine proposal (`OnMoveComputerMsg`) is still ignored.
- `src/chess_service.rs`: `chess.json` gains `daily_reward_coins` (default 1000, bound
  `MAX_DAILY_REWARD_COINS = 100_000`) and `near_equal_margin` (default 25, bound 500).
  `ChessRewardLedger { day, paid_coins }` holds the UTC-day total. `settle` pays only when the row
  award fits the rest of the day's cap and records the paid amount only when the grant actually
  applied; a capped win still settles the run and pays nothing.
- `src/minigame.rs`: `MinigameRuns::finish` now permits a win with no settlement (a capped or
  zero-award win). A loss that carries a grant is still refused.
- `src/gameplay.rs`: `GameplayState::chess` carries the ledger; `load` restores it and `state()`
  returns it. Net +6 lines in this hub.
- `data/content/chess.json`: explicit `daily_reward_coins: 1000` and `near_equal_margin: 25`.

## Security threat note (secure-code-guardian)

- Hostile client sends `OnMoveComputerMsg` with a chosen move: ignored; the server's reply comes
  from its own scoring and RNG (`single_player_server_replies_without_client_move_authority`).
- Hostile client records a winning line and replays it: the per-table OS-seeded stream changes the
  replies, so replayed moves diverge or become illegal; the daily cap bounds the payout even if a
  line still wins.
- Hostile client forges a checkmate, a result message, or a lifecycle packet: only server-validated
  moves reach `accept_move`, `FRServer_GameOver` is inert before a terminal result, and movie
  traffic outside `Playing` is inert. All refusals are staged on a clone.
- Hostile client edits the local save ledger: the file is a local single-player save; the ledger is
  validated against the local bound on restore, and any tampering can only reduce or shift the
  payout window, never mint coins.
- The cap check runs inside `ChessService::settle` (the only grant site), so every route to a chess
  payout passes it.

## (R) reconstructed rules

- UTC day boundary (`now_ms / 86_400_000`); the cap is all-or-nothing per win (no partial payouts).
- Near-equal window semantics and the skill widening formula.
- Per-table seed mixing and SplitMix64 stream.
- Chess reward amounts remain reconstructed content values; the cap default is generous.

## Open gaps

- A capped win shows the normal win screen with no reward bundle; no recovered string exists for a
  dedicated "limit reached" notice.
- Uniform choice among near-equal moves makes every row weaker; hard rows no longer play the single
  best move. Difficulty is now only a window width.
- The 100-halfmove/repetition draw rule is unchanged; the movie still has no draw handler.
- The tests drive a deterministic greedy human against a seeded table (seed 22). A future scoring or
  margin change can make that fixture line stop winning, in which case the cap tests need a new seed.
- No native client playthrough was possible here; the client evidence is the shipped movie source
  and the IDA call graph.

   Tests assert the ledger, `is_active` and reward packets stay unchanged for unknown-row and busy
   refusals and for the capped win. Canary: removing the cap filter made the cap test fail.

   shared cell or side table escapes.

   position snapshot is restored. The cap test starts with 7 coins earned before the game and the
   payout produces 17, so the grant extends live state rather than replaying a snapshot.

   and movie paths all reach it through the same run lifecycle.
