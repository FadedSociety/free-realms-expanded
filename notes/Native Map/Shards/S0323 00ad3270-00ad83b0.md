- **InspectProxy support**: `00ad6730` is an `InspectProxy` virtual flag setter. - **Shared container/runtime code**: `00ad3ba0–00ad45c0` and `00ad5220–00ad5a40` implement tree search, insertion/deletion balancing, rotations, and pooled-node allocation. `00ad5150`, `00ad5aa0–00ad5c70` manage an inline `SoeUtil::List<CharacterAttachmentData,16>`. `00ad6b80–00ad7e10` cover typed arrays, including `ItemRecord`, `CharacterStat`, and `InspectProxy::ProfileEntry`. ## Wire and server hypotheses

The only packet family directly constructed in this shard is the generic `PacketTunneledClientPacket` envelope in `00ad61f0`, used conditionally by the manager path at `00ad6530`. The wire record describes the packet class, while the server inference remains explicitly a hypothesis. The relevant chain is the TCG manager caller (`00ad6530`), nested portrait-data serialization (`00ad6170` and `00ad5c90`), and tunnel construction (`00ad61f0`). No original server implementation or native capture in this range establishes what the server stores or returns.

The binary RTTI identifies inner type `PacketGeneratePortraitRequest` at `00ad35e0`, and its constructor `00ad3190` initializes it from the BaseFotomat family with type 1. The current community catalogue names BaseFotomat opcode 156 and subtypes 2 (`PacketPortraitDataRequest`) and 3 (`PacketPlayerImageData`), but does not list subtype 1. Keep the native subtype-1 name distinct from the community subtype-2 class until serialization or capture proves an equivalence. The existing [engine.screenshot note](../../../../../project/notes/Native%20Map/Systems/engine.screenshot.md) already documents the separate `ScreenshotManager::ProcessPortraitRequest` flow at `00b50190`, its call to `00ad3190`, and local-render fallback; `00ad6530` is another caller, not evidence that the two call sites have identical behavior.
