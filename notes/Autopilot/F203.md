## Threat note (secure-code-guardian)

Attack surface: family-40 invite and 40/4 response packets from any authenticated
hostile client.

- **Forged/replayed dword in 40/4.** The server compares it with the single
  pending invitation for the session-bound target. A mismatch (or no row)
  returns 40/5 code 3 and mutates nothing: no row removal, no roster change, no
  broadcast. The service and T020 route tests cover it; canary 2 shows the
  compare is load-bearing.
- **Restart alias (the new fix).** A client can keep a pre-restart pop-up. The
  new process seeds the counter from an OS-random epoch, so the old dword is
  from a different namespace and is refused; the replacement row survives. The
  regression builds two services, reads both dwords from the delivered 40/1
  bytes, and checks the stale refusal and fresh accept. Residual risk: a 32-bit
  random start can collide with a previous process's value (about `2^-32`); the
  wire field is one dword, so absolute cross-process uniqueness is impossible.
  No client-controlled value seeds the epoch.
- **Nonzero generation.** The seed is clamped with `.max(1)`, preserving the
  pre-F203 invariant that the 40/1 dword is never 0; the increment also
  clamps.
- **Full-group refusal.** F183's ordering (already on this tip) returns 40/5
  result 2 before the removal, so a hostile target cannot destroy a pending
  invitation through a capacity refusal. F183's unit test pins this; F203 does
  not re-add a duplicate.
- **Overflow / ownership.** The generation uses a random start and
  `wrapping_add(1).max(1)`; no client data is used in arithmetic. The target
  guid comes from the session, never the packet. The dword is a bounded `u32`
  read by the existing parser.
- **Economy.** Group invites grant no coins, items or XP and involve no client
  quantity or item id.
- **Refusals change nothing.** Every refusal asserted here leaves the pending
  row, roster, membership and profiles untouched; persistence is unchanged
  (groups are volatile).
