# L045: Housing visits, slice 1: who placed each fixture (brief step 5)

## Summary

The brief (`lab/autopilot/opus/lead-briefs/house-visits-shared-instance.md`) says "split them as
needed". This commit is the self-contained step: **step 5, fixture placed-by and its save
migration**. Steps 1 to 4 and 6 (world lot store, foreign listing, shared instance, live
broadcast, lock ejection, unload) are **not built**. They need lead decisions, listed under
"Open: what visits need next", because the brief's visitor premise does not hold in production.

What changed:

- `SavedFixture` (`src/housing.rs`) gains `placed_by: u64` (`#[serde(default)]`). The server
  sets it from the acting guid: `Housing::place_fixture` records its actor and
  `Housing::save_fixture_placement` overwrites any caller-supplied value with the command's actor
  (the same rule already used for `house_guid`). A move keeps it.
- The migration rule is on the type: `SavedFixture::attributed_to(owner)` turns an unrecorded
  placer (`0`) into the lot owner. Both restore paths apply it: `Housing::rebuild`, which serves
  `restore_lots` (character save) and `load_state` (local snapshot file), and the
  `replace_saved_fixtures` hook. Before this change only the owner could place in production, so
  owner attribution is exact for every existing save.
- `SERVICE_SCHEMA_VERSION` is now 2 (`src/housing_service.rs`). `HousingService::from_state`
  accepts 1 and 2. A schema-1 document loads with owner attribution and is written back as 2 by the
  next character save. 0 and anything newer are still refused whole (`StateError::SchemaVersion`).
- Pick-up returns the unit to the picker (R): this is the existing behaviour (`pickup` returns
  through the actor's `FurnitureStock`) and is now pinned by a co-builder test.

The local snapshot file schema (`housing::SNAPSHOT_SCHEMA_VERSION`, used only by restoration pieces
026/028/030 and tests) stays 1. The field is additive with a default, and that path applies the
same fill.

## Security

Trust boundaries touched:

1. **Client packet to fixture record.** No packet carries a placer. `place_fixture` writes the
   session's own actor guid. `save_fixture_placement` overwrites a caller-supplied `placed_by` with
   the authorized actor, because the field is reachable through `SaveFixtureCommand`. Test:
   `save_fixture_placement_stamps_the_resolved_lot_identity` forges `OTHER` and expects `OWNER`
   (canary C4).
2. **Save document to live state.** A schema-1 document migrates only by filling `0` with the lot
   owner. No lot, fixture, permission, lock or ownership row is dropped or invented. Unknown
   versions are still refused whole before any state is adopted. Inventory conservation checks are
   unchanged. The save stays the one atomic `game_store` document written by the session commit,
   and no new write path is added.
3. **Item movement.** Unchanged. Only a level-3 editor (no production path grants one today) can
   pick up, and the unit goes to the picker's own stock. No coins move.
4. **Logging, oracles.** Nothing new is logged or answered. `placed_by` is never sent to a client,
   so it adds no enumeration surface.

Threat note: a hostile client cannot name a placer, because no wire field carries one. A forged save
is outside the client boundary. A crafted schema-2 save with `placed_by = 0` is treated like
schema 1 (owner). That is benign: in this slice the field gates nothing.

## Open: what visits need next (steps 1-4, 6)

1. **Who may visit (lead decision).** `Housing::can_visit` admits a non-owner only on an
   unlocked lot with a permission of 1 or more. No packet grants a permission, because 127/11, 15
   and 22 are not decoded. So a foreign 127/14 or 127/19 built on `can_visit` would list and admit
   nobody in production, and checklist 6 would fail. The brief's step 6 ("lock ejects visitors not
   on the allow list") implies the opposite rule: unlocked means anyone, locked means the allow
   list. 127/21 VisitRandomNeighbor and the directory's Visit! also suggest strangers can enter
   unlocked houses. That would open every unlocked house by default, so it is the lead's call.
   Alternative: an explicit invite (127/15 grants level 1).
2. **Presence oracle.** A lot store filled from owners' saves at login answers a stranger's
   targeted 127/14 differently for online and offline owners, which leaks online status for any
   guid. The fix is either to answer identically (an empty 127/39 for offline, no lots or no
   permission) or to load offline owners' lots on demand. On-demand loading costs a disk read per
   arbitrary guid and needs a budget.
3. **Hub ceilings and session plumbing.** The store, owner-instance targeting
   (`InstanceKind::House`, unused today) and the 127/40/41 fanout to instance members all sit in
   `Session::commit_outcome` (`bin/osfr-gateway.rs`, net 0 allowed, checklist 16). They need a
   lead-designed seam.
4. **Ejection.** Lock, lot loss and the end of the grace period must move *other* sessions. Only
   the per-session, host-authorized `Gateway::stage_instance_transfer` exists, so ejection needs a
   cross-session primitive.
5. **Unload.** `World` already has `empty_instance_grace_ms` (60 s in `World::runtime`) and
   `empty_since_ms`. Step 6's grace can reuse them once house instances exist.
6. **Co-builder conservation.** `from_state` checks every placed instance id against the
   *owner's* inventory (`PlacedInstanceStillOwned`, `PlacedInstanceDuplicated`), and
   `place_fixture` refuses equal (instance, definition) pairs. Instance ids are per character, so a
   co-builder's fixture can collide with the owner's ids. `placed_by` now makes a per-placer check
   possible in the co-builder slice.
7. **Pushback (economy).** With pick-up going to the picker, a level-3 co-builder's single 127/4
   PickupAll moves *all* of the owner's furniture into the co-builder's backpack. Suggestion:
   PickupAll owner-only, or a co-builder's pick-up of another placer's fixture returns the item to
   `placed_by`. That is harmless today because nothing grants level 3.
