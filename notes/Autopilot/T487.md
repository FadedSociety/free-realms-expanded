## What changed

- `src/pets.rs` (the owner, +62/-1):
  - `PetService.remembered: Option<u32>`: the pet a zone change left behind. Session only, never
    saved and never sent. `Some` implies no pet is active, because `summon` and `dismiss` clear it.
  - `zone_away(now)`: what `settle_pets` now calls. It dismisses as before and then stores the pet.
  - `resummon(actor_guid, owner_guid, owner_position, busy, now) -> io::Result<Option<PetWire>>`:
    `None` with nothing remembered, while a pet is out, or while `busy` closes the pets gate (the
    memory is then kept). A pet the roster no longer holds is forgotten silently. Success is the
    normal summon (`summon`), then the roster a summon sends (53/5) after the 53/9, with
    `changed = false` (the roster does not change, so no save).
  - `dismiss`, `summon` and `reset_session` clear the memory; `remembered_pet_id()` is the
    read-only accessor the glue's cheap guard and the tests use.
- `src/gameplay/rides.rs` (the pet glue, +53/-5):
  - `push_rosters` became `enter_world(character, now_ms, out)`: the same two rosters, then the
    resummon, so the client reads the roster before the pet.
  - private `resummon_pet`: memory guard (nothing remembered costs one branch on a hot path),
    `Gameplay::blocks(pets)` for the gate, then `PetService::resummon`; the packet list goes to
    `replies` (owner) and `nearby` (viewers). A summon the server cannot place is `eprintln!`-ed for
    that player and never an `Err` out of the loaded path or the tick.
  - `follow_pet` attempts the resummon when no pet is out: the first accepted move and the world
    tick both land here.
  - `pet_tick` calls `follow_pet` first (covering the resummon) and then keeps its old rule: `None`
    when there is still no pet, so an idle session sends nothing.
  - `settle_pets` remembers the pet through `zone_away`.
- `src/gameplay.rs` (hub): the two world-entry call sites now pass the character and clock to
  `enter_world`. 2 lines changed, net 0; the file stays 5143 CRLF lines.
- `tests/pet_zoning.rs` (new, 7 tests).

No new `application_handler` selector was added: family 53 is routed already, and `app_fuzz` carries

## (R) rules

- The memory belongs to the connection: `reset_session` drops it and the save never carries it, so a
  relog does not resummon (the brief's requirement 4).
- What counts as "pets blocked" is only the occupation table (`Gameplay::blocks(pets)`), so chess,
  fishing, crafting, gathering, the card run, encounters, derby, soccer and kart keep the pet back,
  and a house lot keeps the gate open (lead housing decision).
- A house lot's loaded stream is its own branch of `initialize_world` (it sends the lot packets and no
  world entry), so the pet a lot's warp remembered returns on the first world tick after it loads,
  where a normal zone's loaded signal returns it at once.
- The pet is placed by the content (`pets.json` `follow`: 2 m behind, 2 m aside) at the owner's
  current pose; its first follow step snaps it to the ground.
- The resummon never marks a save (`wire.changed = false`): only the session remembers the pet.
- A resummon the server cannot place (an unusable owner pose) drops the pending memory so a broken
  pose is not retried every tick; it is logged for that player.
- No values were added to content: the timing is the client's own loaded signal.

## Threat note (secure-code-guardian)

- No new client input is parsed. The resummon is server-driven: the pet id comes from the session's
  own earlier summon, the actor guid is `PetService::pet_guid(owner_guid)` (owner-derived, never from
  a packet), and the position is the authenticated character's current pose.
- A hostile client cannot invent a pet: `resummon` only ever summons the id the server itself
  remembered, after checking it is still in the saved roster. A forged `53/4` summon still goes
  through the existing ownership check.
- The worst a hostile client can do is send messages and ticks, each of which is O(1) while nothing is
  remembered (one `Option` check) and one summon per zone change otherwise.
- A refused resummon (a closed pets gate) changes nothing: the memory is kept, no packet is sent and
  the roster is untouched (`document_value` equality asserted). A resummon the server cannot place
  drops the memory and logs, so a client cannot make the server retry a broken pose forever.
- The pet list refresh (53/5) sent on the resummon is built from the saved roster, not from the
  request.

## Checklist

1. **A refusal changes nothing.** The only refusals are server-internal: a closed pets gate returns
   before any mutation (roster JSON equal before/after, memory kept), and an unusable pose drops the
   pending memory on purpose (documented) with the roster asserted equal. Tests:
   `a_pets_gate_holds_the_memory_and_a_summon_replaces_it` (both) and the canaries C/F.
2. **Rollback covers all state.** The memory is a plain field of `PetService`, inside `Gameplay`, so it
   rides the staged clone the gateway and the pet service use; `zone_away`/`dismiss` run on a clone
   and are committed only on `Ok`. No `Rc`/`RefCell`/`Arc` side table.
3. **Apply deltas, never restore snapshots.** The resummon reads the live character pose and the live
   roster; nothing captured earlier is written back. `wire.changed = false` keeps the save untouched.
4. **Busy rules are mutual.** The pets gate is read only through `Gameplay::blocks(|g| g.pets)` (the
   occupation table); no hand-written busy list was added. `tests/spine_rules` and the occupation pin
   test still pass.
5. **Every entry path is gated.** The resummon runs at the destination's loaded signal
   (`initialize_world` -> `enter_world`, both world-entry branches), the first accepted move
   (`on_location` -> `follow_pet`) and the world tick (`tick_at` -> `pet_tick` -> `follow_pet`).
   `settle_pets` is remembered on every commit (`Session::commit_outcome`). No path skips the gate.
6. **Reachable in production, tested through it.** `tests/pet_zoning.rs` drives `Gateway` messages
   (53/4, `realm race`, 13, 10, 26/42, 125), `Gateway::tick_at`, `gateway.settle_pets` in the
   production commit order, and `Gameplay::initialize_world`/`pet_tick`. No test calls a copy of the
   logic.
7. **Survives reconnect.** The memory is session state by design; `reset_session` clears it and a
   fresh session built from the saved document never resummons (test, canary F). Nothing new is
   saved.
8. **Every exit path restores the player.** The dismissed-into-a-warp, two-warp, kart-race and
   reconnect cases all end with exactly one pet actor or none, at the owner's live pose, with the
   roster unwritten.
9. **Economy safety.** No coins, items or XP are touched. The pet id comes from the saved roster; the
   wire is built from server data.
10. **Wire format matches the client reader.** 53/9 `u32` pet id + 8-byte actor guid (`00b556c0`) and
    the AddNpc-before-53/9 order (`00b54080` binds only an existing actor) are cited above; the
    resummon reuses `PetService::wire` + `list_packet`, whose byte layouts are pinned by the existing
    pet suites, and the new test parses the AddNpc with the production `parse_add_npc`.
11. **Unique ids.** No new ids. The actor guid stays owner-derived (`PetService::pet_guid`, unique per
    owner); the test asserts one actor guid across two warps and no duplicate AddNpc.
12. **Others see changes.** The removal reaches `nearby` at the zone change; the resummon's AddNpc is
    the presence the server replays to viewers through the existing W177 `with_pets` path (the loaded
    commit cannot fan out: the player is not in the interest grid until the join in that same commit).
    The test asserts the removal, the owner's AddNpc, `pet_view`, and the pet's 125 frames in `nearby`
    after the warp; the tick-path resummon's AddNpc is asserted in `nearby` as well, where the session
    is joined and the production fanout delivers it.
13. **Content works end to end.** The final outcome is asserted: exactly one AddNpc for the pet's
    actor, one 53/9 and one 53/5 after the destination's loaded signal, `pet_view` with the same pet
    id, and nothing on later ticks.
14. **Values live in data.** No new tunables: the timing is the client's own loaded signal and the
    spawn offset is `pets.json` `follow`.
15. **Canaries break production code.** Every canary (A-F) edits `src/pets.rs` or
    `src/gameplay/rides.rs`; no canary fakes a failure inside a test.
16. **Hands off session plumbing.** `src/bin/osfr-gateway.rs` and the session/gateway save ordering are
    untouched; `src/gateway.rs` is untouched. The change reuses the existing `settle_pets` and
    `initialize_world` hooks.
17. **One player's error never stops the server.** The resummon catches the only failure (an
    unusable owner pose), logs it with `eprintln!` and returns `false`; `resummon_pet`,
    `follow_pet` and `pet_tick` have no `?` on it. Test: the NaN-pose case returns an error from
    `PetService::resummon` (the service boundary) and the glue never propagates it.
18. **A type's rules live on the type.** `PetService` owns the memory: the field doc states "session
    only, `Some` implies no active pet", and `summon`, `dismiss`, `zone_away`, `reset_session` and
    `resummon` each decide their own clearing rule in one place; the glue only asks
    `remembered_pet_id`.
19. **Hot paths stay cheap.** `pet_tick`/`follow_pet` cost one `Option` check per tick or accepted
    move while nothing is remembered; `blocks(pets)` (14 occupation checks) runs only when a memory
    is pending, and the resummon allocates packets once per zone change. No `Gameplay` clone and no
    packet on the idle path; the resummon does not mark a save.
