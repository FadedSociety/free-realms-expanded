# F113 Fix T019 bundle rollback regression

## Review disposition

The single BLOCKER in
`lab/autopilot/reviews/6cd3ffe-T019.md` was valid. The bundle contained bare
application packets, so `Gateway::parse_message` rejected the first 66/43 child
before the purchase ran. The test therefore passed the unchanged-snapshot and
retry checks without exercising gameplay staging or rollback.

That earlier review had no MINOR findings; the later 01a4640 review does, and
they are addressed under "F151 post-review remediation" below. F185 then found
that the F151 audit had copied a pre-F155 shared-state claim; the correction is
recorded below and in `notes/Autopilot/F185.md`.

## What changed

- `prototype/osfr-tools/tests/vendor_sell.rs` now wraps both bundle children:
  the 66/43 purchase and the malformed 26/8 child. Parsing reaches gameplay for
  the first child, allowing the purchase to execute in the staged Gameplay, and
  the second child then fails there.
- The existing assertions are retained: the failed bundle leaves the gateway
  snapshot unchanged, and retrying the 66/43 request debits exactly 15 coins
  and grants the item. This distinguishes a real rollback from the old shared
  shop's leaked transaction cache.
- No production behavior or security-owned module changed.

## Regression evidence

- Before the fix, the failed bundle was rejected by top-level parsing and never
  reached gameplay.
- After the fix, the targeted test log shows the first 66/43 transaction
  accepted, followed by the retry's second accepted transaction; the gateway
  snapshot remains unchanged between them.
- Canary: temporarily committed `staged_game` in the combined-request error
  branch of `Gateway::handle_at`. The regression test failed with the expected
  coins `100`, observed `85`, at the failed-bundle snapshot assertion. The
  canary was reverted; `gateway.rs` again matches HEAD byte-for-byte.

## Reconstructed rules

No new reconstructed rule `(R)` was introduced. The test verifies the existing
T019 reconstructed transaction policy: a successful buy is staged with the
gateway commit, and a later child failure leaves both inventory and the
idempotency cache uncommitted.

## Threat note (secure-code-guardian)

A hostile client can send a `[0,25]` bundle with any child order, a bare child,
a nested child, an over-long length, more than 128 children, and any 66/43
item, quantity or transaction id. The refusal is safe at every layer:

- Every child is decoded before handling: `Gateway::handle_at` calls
  `application_messages` and `parse_message` on the whole request. Empty,
  nested, oversized and over-count bundles are refused before gameplay; a bare
  child fails `parse_message`; a bundle whose replies exceed
  `MAX_BUNDLE_REPLY_BYTES` (8 MiB) is refused before commit.
- `Gateway::handle_at` clones character, `Gameplay`, movement and flags
  (`let mut gameplay = self.gameplay.clone()`), stages each application child
  on another clone (`let mut staged_game = game.clone()`), keeps that child
  only on success (`gameplay = Some(staged_game)`), returns `Err` from a
  combined bundle before the final assignment, and assigns
  `self.state`/`self.gameplay` only after the whole loop. Production
  additionally clones the whole `Gateway` in `Dispatch::dispatch_message_inner`
  (`src/bin/osfr-gateway.rs`) and later commits it with `commit_outcome`, so a
  later child failure cannot commit the first child.
- The purchase's mutable state — `Inventory` (coins and `next_instance_id`)
  and the `CoinShop` ledgers (`client_transactions`, `vendor_transactions`,
  `sales`, `next_transaction_id`) — is inline in the cloned
  `Gameplay`/`CoinShop`, not a shared `Arc` or side table; T019 removed the old
  shared shop. `NpcInteraction` is inline too (`Gameplay::npc_interaction:
  Option<NpcInteraction>`; split by F155 into immutable `Arc<NpcContent>` plus
  owned `active`), and the 26/10 menu choice is cloned and assigned back into
  the staged `Gameplay`; the 66/43 path only calls the `&self` validator
  `NpcInteraction::validate_merchant_item_66_43` and never writes the menu.
- The item id must be in the open shop's stock and the character in range
  (`NpcInteraction::validate_merchant_item_66_43`). Quantity must be non-zero
  and at most `i32::MAX`; the price is `checked_mul` from `stores.json` (never
  the client price); coins must cover it; the bag must have room
  (`CoinShop::buy_once`). The transaction id is only a bounded `u32` map key
  (`MAX_CLIENT_TRANSACTIONS`). No id, item or coin is shared with another
  session.
- A refusal does not insert the transaction id into the cache;
  `tests/vendor_sell.rs::gateway_bundle_failure_does_not_commit_a_vendor_buy`
  retries the same id and is charged exactly 15, which would fail if the cache
  or inventory leaked.

## Checklist

1. **A refusal changes nothing.** `gateway_bundle_failure_does_not_commit_a_vendor_buy`
   asserts the failed bundle returns the second child's gameplay error
   (`invalid NPC interaction request`), the gateway snapshot is unchanged, and
   the same transaction id then succeeds and debits exactly 15. The production
   canary made the snapshot assertion fail with coins 85 vs 100, proving the
   test sees a committed purchase. No NPC menu, offer, counter, item or
   cooldown is consumed on this path.
2. **Rollback covers all state.** `Gateway::handle_at` clones character,
   `Gameplay`, movement and flags, dispatches each application child on another
   `Gameplay` clone (`let mut staged_game = game.clone()`), keeps a child only
   on success (`gameplay = Some(staged_game)`), returns `Err` from a combined
   bundle before the final assignment, and assigns `self.state`/`self.gameplay`
   only after the loop. The purchase state is inline: `Gameplay` owns
   `Option<CoinShop>`, and `CoinShop` owns its inventory and ledgers. The NPC
   menu is inline too: `Gameplay::npc_interaction: Option<NpcInteraction>`; the
   26/10 branch clones it, assigns it back into the staged `Gameplay`, and the
   clone is dropped if a later child fails. F155 deleted the old
   `Arc<Mutex<NpcInteraction>>` and its eight lock sites
   (`notes/Autopilot/F155.md`).
   `tests/job_trainers.rs::a_failed_bundle_keeps_the_trainer_menu_usable`
   proves the menu survives a failed bundle: the snapshot and unlock are
   unchanged and the original Talk choice still answers. The retry with the
   same transaction id proves the idempotency cache did not leak.
3. **Apply deltas, never restore old snapshots.** The 66/43 branch syncs the
   live inventory into the shop immediately before the transaction
   (`shop.sync_inventory(self.inventory.clone())` in `gameplay::npc::handle`),
   and `CoinShop::buy_once` clones the current inventory state and stages the
   grant before assigning it back. The retry debits 15 from the current coins,
   not from a login snapshot; the existing
   `gateway_vendor_buy_reads_the_live_inventory_after_a_reward` covers a reward
   earned after login.
4. **Busy rules are mutual.** Not applicable: no activity starts and no
   `Occupation` row changes. The 66/43 request is a menu purchase inside the
   already-open vendor session; `gameplay/occupation.rs` has no vendor row.
5. **Every entry path is gated.** 66/43 has one production path: application
   dispatch -> `Gameplay::handle_in_world` -> the 66/43 branch of
   `gameplay::npc::handle` -> open-shop/stock/range validation
   (`NpcInteraction::validate_merchant_item_66_43`) -> server-priced
   `CoinShop::buy_vendor`. `grep` finds no other caller of `buy_vendor` or
   `validate_merchant_item_66_43`. The account action budget runs before the
   gateway stages the bundle (`Dispatch::dispatch_message_inner` in
   `src/bin/osfr-gateway.rs`). There is no client price, level/job shortcut or
   NPC-menu bypass.
6. **Reachable in production, tested through it.** The test calls
   `Gateway::handle_at` with tunneled `[5,0,1]` children in a `[0,25]` bundle,
   the same method `Dispatch::dispatch_message_inner` calls after
   `Gateway::ordered_messages`. The new assertion pins that gameplay, not the
   parser, rejected the bundle. `tests/app_fuzz.rs` already seeds 66/43
   (`words(66, 43, ...)`); no new selector was added.
7. **Survives reconnect.** Not applicable: F113 adds no durable state. A
   successful purchase commits inventory and coins to the character save; the
   idempotency cache is deliberately session-local (T019) and a reconnect
   clears it. Replaying the same id after reconnect buys again and pays again,
   not a free grant.
8. **Every exit path restores the player.** Not applicable to location,
   activity or timeout state: the purchase takes no lock and starts no timer.
   Failure returns before commit; the test's retry proves the gateway still
   serves the character.
9. **Economy safety.** The server price comes from `stores.json`; the client
