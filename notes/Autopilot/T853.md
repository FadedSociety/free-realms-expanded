# T853: publishable gameplay content overlay for the release

## Why

The released gateway runs on `data/content` and had no opening, combat, quests, profiles,
inventory or campaign content: those files only existed in the private native packages
(`lab/reports/native-*/content`). This task adds the publishable overlay
`prototype/osfr-tools/data/release/`; a release's `content/` is `data/content` plus this folder.
`data/content` and every existing test file are unchanged.

## The category capture (evidence)

`categories.json` is rebuilt from a real 44/2 reference-data packet found in the pinned community
packet capture `lab/references/OpenSourceFreeRealms/ofrserver/Packets/p1.pcap` (classic little-
endian pcap; the capture was not modified). The packet is zlib-compressed inside the reliable
stream: UDP source port 20232 -> client port 59128, pcap record 1748 (one-based), reliable
fragments 112..117. The reassembled payload is 2,675 bytes:

- i32 count 71, then per row dictionary key, id, name id, icon id, unknown, bool, display (25 bytes);
- i32 count 74, then per row group id, key, category id (12 bytes); the keys equal their ids.

SHA-256 of the payload `a75f5e2beb3be02c76434145e0cf62b6dc7f98438e48791bd1f569a531f0c21f`,
pinned in `data/release/categories.json` and in `tests/release_content.rs`
(`CATEGORY_PACKET_SHA256`). The rows match the community category table byte for byte, but the
public provenance cites the capture, not the AGPL table.

Client readers checked in IDA (2014 client, `lab/autopilot/ida_query.py`):

| Fact | Address |
|---|---|
| Reference-data dispatcher 44/1, 44/2, 44/3 | `decompile 0x00928d00` (case 2 calls `sub_9215F0`) |
| 44/2 body parser | `decompile 0x009215f0` (initialises a reader, calls `sub_8FCA00`) |
| category + group record parsers | `decompile 0x008fca00` calls `sub_8E98B0` (categories) and `sub_8E9A10` (groups) |
| category row and group row readers | `decompile 0x008e98b0`, `decompile 0x008e9a10` |

No field in the layout contradicts the existing `item_categories.rs` reader/packet builder; the
`tests/item_categories.rs` byte-level test remains the public pin. No wire layout changed in this
task.

## Production changes (why they are small)

The release's two capture-derived templates could not ship as `.bin` files (the publish gate
blocks binaries outside `tests/fixtures`). Following T807's typed-JSON precedent:

- `src/combat.rs`: `template_hex` (serde default) is used when non-empty; `template_file` remains
  for existing content/tests; `template_sha256` still pins either form; 4 KB hex bound.
- `src/opening_world.rs`: the same two-way descriptor for the opening actor spawn template.
- `src/quests.rs`: `journal.hex` replaces the journal file when present; the same length/hash/
  offset/binding proof runs. It calls the now-public `startup_snapshot::decode_hex`, which is
  also available to the file's existing `#[path]` restoration test targets (`piece_069`,
  `piece_071`).
- `src/opening_journal.rs`: `journal.hex` replaces the journal file when present; the same proof
  and `verify_original` run.
- `src/startup_snapshot.rs`: `decode_hex` is public; the four loaders above call it. No behaviour
  change for the startup content that already used it.

No hub file changed: `src/gameplay.rs`, `src/bin/osfr-gateway.rs`, `src/encounter.rs` and
`src/gateway.rs` are untouched. No session, save, transport, economy or dispatch code changed.
The new content path is the same `Gameplay::load` -> `Combat::load` / `Profiles::load` /
`QuestEngine::load` / `OpeningJournal::load` / `OpeningWorld::load` / `ItemCategories::load` chain
the released gateway already calls.

## Threat note (secure-code-guardian)

The release content is trusted operator input loaded at startup; it is not client input. The
security-relevant surface is unchanged: no packet reader, save path, coin/item grant, role or
session code was touched. The new typed fields are bounded at load (`template_hex` 4 KB,
journal hex 2x the loader bound), decoded to bytes, and then subjected to the existing length,
header and SHA-256 checks; a malformed or mismatched value fails the content load closed, before
a session starts. The template hex cannot name a file, and the journal hex cannot name a path,
so a hostile content file is refused rather than causing a read outside the content directory.
The capture-derived bytes contain no account name/number, character state or server text (the
public test pins the template digest and checks the decoded bytes for a text run; the journal is
21 zero/neutral bytes). Nothing another player can trigger is added; no economy value is granted
by this task.

## Checklist

1. **A refusal changes nothing.** `a_broken_overlay_is_refused_without_touching_the_files`
   snapshots the eleven overlay files, breaks the forging marker and then the category proof in
   scratch merges, asserts both loads fail, and asserts every overlay file is byte-identical.
   Canary 2 made the broken-marker case load and the test failed, so the refusal is pinned to the
   production check, not to test code.
2. **Rollback covers all state.** This task adds no transaction and no shared `Rc`/`RefCell`;
   content loading is a read-only fail-closed path. The refusal test proves the on-disk files and
   the source overlay are untouched. N/A for a cloned state.
3. **Apply deltas, never restore snapshots.** No payout, inventory, coins or position code was
   changed. The fresh character is a load-time default (`default_state`), not a later snapshot
   restore.
4. **Busy rules are mutual.** No activity, `Occupation` variant or busy check was added. N/A.
5. **Every entry path is gated.** Only the existing content loaders are reached, by their one
   production chain (`Gameplay::load`); there is no second loader or parallel path. The release
   test drives that chain; the focused test calls each real loader.
6. **Reachable in production, tested through it.** The world-entry test uses
   `Gateway::load_gameplay_from_content` (the binary's no-`--reference` path), the real login and
   world-entry messages. The production loaders are used, not copies.
7. **Survives reconnect.** The overlay is static content; no new persisted state. The fresh
   journal/inventory/profile rules come from the content files. No reconnect-specific state to
   test; the existing save/reconnect suites were not changed.
8. **Every exit path restores the player.** No activity or exit path changed. N/A.
9. **Economy safety.** The fresh character starts with 0 coins and no owned items; the 1,386-item
   capture bag and the Legacy starter kit are removed; `starter_items` is empty so a learned job
   grants no free gear. Every opening reward and recipe consume/product id is asserted to have a
   real definition. No client-reported quantity or result is read.
10. **Wire format matches the client reader exactly.** No wire layout changed. The 44/2 packet is
    the captured 2,675-byte payload, built by the existing `ItemCategories` writer; IDA readers
    `0x00928d00`, `0x009215f0`, `0x008fca00`, `0x008e98b0`, `0x008e9a10` were checked and the
    public packet byte/length pins pass. The AddNpc template is the existing 334-byte 35/2 shape
    checked by `validate_template`; the journal span is the existing 49/x journal shape checked by
    `verify_original`.
11. **Unique ids.** No new instance id/GUID/lifecycle id. Category ids are unique (the loader
    rejects duplicates); profile/equipment rows are the captured unique set. The template's NPC
    GUID is an NPC id, not an instance id.
12. **Others see changes.** No broadcast path changed; content only affects new sessions.
13. **Content works end to end.** The release reaches world entry with opening stages; the
    category packet reaches the client; profiles/inventory/combat/journal load; every reward and
    recipe item is defined. The full opening walk is not replayed here (the existing opening
    suites and the lead's native run cover it).
14. **Values live in data.** All added gameplay content is JSON; the new code only chooses a
    content field. The two constants in the test are pins of captured bytes, not tuning.
15. **Canaries break production code.** Both canaries edited `src/` (combat loader, campaign
    marker check), failed the intended public test, and were reverted with SHA-256 proofs.
16. **Hands off session plumbing.** `src/bin/osfr-gateway.rs` and `src/gateway.rs` are untouched;
    no session creation, teardown, transaction or save ordering changed.
17. **One player's error never stops the server.** The changed code is startup content loading;
    every malformed input returns `Err` and refuses the load instead of panicking; no `unwrap` on
    client data was added. No shared tick code changed.
18. **A type's rules live on the type.** The new fields document their rule on the field:
    `combat::Content` and `opening_world::Template` say a non-empty `template_hex` means the file
    is not read and `template_sha256` pins either form; `quests::Journal` and
    `opening_journal::JournalReference` say the hex replaces the file and the same proof applies.
19. **Hot paths stay cheap.** The hex is decoded once at content load; no per-tick or per-packet
    work is added. The release overlay is read at startup only.
