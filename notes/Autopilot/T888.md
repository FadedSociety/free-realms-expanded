## What the client does (IDA, this pass)

- 53/15 kind 1 (`PetTrickNotify`, handler `00b5ce60` case 15, `0x00b5e7cc`..`0x00b5e82c`) builds the locale line `PetOrderDoTrick`
  (code string 3880, `CodeStringMappings.txt`; locale hash `JenkinsLookup2("Global.Text.3880")` = 2555979520, text
  "[*trickName*], [*pet*]!") from the trick-name text (fourth word) and posts it on the `WorldSay` channel (string `0x0181d6a4`)
  **locally**. It is a client-side line for the owner only: the client sends no chat packet with 53/7 (the sender is `Pet.PerformTrick`
  -> `00b5fb30` -> `00cc7420`, which writes 53/7 and 53/8 only). So our chat routing drops nothing; nobody ever relays the line.
- Case 2 of the brief (client also sends a say line) is false; case 3 (the server must tell viewers) is the build.
- Reader for a server say line by string id: 15/4 `chat::string_say`, `0x00b0f680`; its WorldSay path `0x009012b0` resolves the speaker by
  guid (`sub_984960`, any actor) and shows the bubble, the same path `world_events` uses for event actors.

## Change

`src/pets/tricks.rs` `try_trick`: an accepted 53/7 now adds `chat::string_say(owner_guid, trick name_id)` to `PetWire::shared`
(after the owner animation), so every session the gateway fans `shared` out to (nearby, not the owner: `ride_fanout`) gets the
bubble. The owner's `private` list is unchanged, so the owner's own 53/15 kind 1 still makes the only copy on their screen. A trick
row with no `name_id` sends no line. Refusals still send only the two unlocks (`shared` empty, existing tests pin it).

(R) The viewer line is the trick name only ("Handstand"), not the owner's "Trick, Pet!": a 15/4 line carries only a string id, no
parameters. A literal 15/1 line would need the trick-name text in `pets.json` and would carry the player-chosen pet name past
the chat filter, mute and ignore checks (the server would be authoring a player-text chat line). The lead can decide whether the
pet-name suffix is worth that; the data to do it is the locale rows 3880 and each trick's `name_id`.

## Threat note

A hostile client can send 53/7 only; the server picks the string id from its own `pets.json` row for a trick the pet already
knows, so the client cannot choose the text or the speaker (the speaker is the authenticated owner guid, not request bytes). No
player-authored text is relayed, so the chat filter, mute and length checks do not apply. Spam is bounded by the existing
one-trick-at-a-time lock (a new 53/7 is refused while a trick runs). (R) The viewer's ignore list is not consulted, same as the
owner animation next to it and the event-actor say lines.
