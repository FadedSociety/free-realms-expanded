## What this range is

One translation unit of the client's **Lua binding layer plus the packet classes
it drives**. Two interleaved halves:

1. **Client Lua modules.** Registration functions follow one 29-byte template:
   `mov eax,[module-name-ptr]; mov ecx,[esp+4]; push 0; push <entry-table>; push
   eax; push ecx; call 0x00e39e40; add esp,0x10; xor eax,eax; ret`. FUN_00e39e40
   is the module registrar (creates the module table, stores `_LOADED`, binds each
   `{name, function}` pair with a cfunction closure). All of them are invoked once
   from FUN_00976070 (shard S0260), which walks a fixed list of 56 registrars,
   i.e. the whole client script surface.
2. **Packet classes and their ClientGateway send templates.** Pet, encounter
   matchmaking, inventory, command, group and broker packet constructors, body
   writers and the generic "serialise into a 64 KB stack buffer, wrap in
   `ClientGateway::PacketTunneledClientPacket` / `...ClientWorldPacket`, install
   `ClientGateway::BasePacket::vftable`" senders.

## Packet / server-contract inferences spanning several functions

* **Pet family (base opcode 0x35).** `FUN_00b50670(subtype)` writes `[1]=0x35`,
  `[2]=subtype`; the constructors in this shard select subtype 2
  (PetResponsePacket, 00c06460) and subtype 17 (PetDeletePacket, 00c06b40).
  Handler -> ctor -> body writer -> gateway: Summon/WasGood/WasBad/Dismiss ->
  00c074c0/00c07630/00c07420 -> 00c06e00 (u32 +0xc, byte +0x10) -> 00c07090;
  Equip/UnequipItem/Utility -> 00b50e00/00b514e0 (outside shard) -> 00c06ea0
  (byte +0xc then three u32s) -> 00c071a0; Delete -> 00c06b40 -> 00c06fc0
  (u32 +0xc then a string at +0x10) -> 00c072b0. Note 091's field order is
  reproduced by the body writers, and the "(action 0, ClientGateway template)"
  sender it names is 00c07420.
* **Broker (consignment) family, subtypes 2..7.** 00c0c670 search, 00c0c730
  place, 00c0ca80 relist, 00c0cb70 buy, 00c0cc50 cancel, 00c0cd30
  request-sale-coin; every body starts with the shared two-16-bit header
  00c0cef0 (`[+4]` and `[+8]` low shorts) written by the same helper the send
  templates call. Handler -> packet mapping (via the module table and the
  registered send paths): 00c0dcd0 Place -> 00c0d590, 00c0ddd0 Cancel ->
  00c0d6a0, 00c0de80 (called by Buy 00c0df30) -> 00c0d7c0, 00c0df30 Buy ->
  00c0d8e0, 00c0e000 Relist -> 00c0d9f0, 00c0e110 Search -> 00c0db00. The
  original server owned listing validity, fees and coin/item movement; nothing
  broker-related exists in any recovered server, so all broker
  `server_inference` texts are hypotheses keyed to these send paths.
* **Command family** base = `FUN_008a2820(subopcode, extra)`: quest abandon =
  0x17 (00c09f60 -> body 00c0a350 -> gateway 00c0a3d0), clear merchant
  interaction = 0x2b (00c0a7a0 -> body FUN_0090ac70 -> gateway 00c0ad30, sent
  by the merchant Close handler 00c0ae60).
* **Group family** base = `FUN_008a35c0(subopcode)` with base opcode 0x28:
  changing-job = 0x0e (00c0af40 -> body 00c0b150 (one byte) -> world gateway
  00c0b1d0), gated client-side by the group object at +0x6ec (00c0b300).
* **Inventory family**: item-requirement request = `FUN_00a10400(4)` (00c08fa0
  -> body 00c09b80 -> gateway 00c09c00), sent by 00c09d30. The community
  catalogue documents base 42 subtypes 2/3/6/8/10/11/12 - **not** 4 - so the
  server reply shape is unrecovered.
* **Encounter matchmaking**: add-match request = `FUN_00a7f0d0(3)` (00c08790 ->
  body 00c08910, member list 00c08870 -> world gateway 00c08cf0), driven by
  JoinQueue 00c08e30; PopulateQueues 00c08ae0 and LeaveMatchRequest 00c08b90 use
  sibling ctors (FUN_00a7fb90 / FUN_00a7fc60) and senders (FUN_00a83790 /
  FUN_00a838b0) outside this shard.
* **ClientGateway send templates** (00c07090, 00c071a0, 00c072b0, 00c08cf0,
  00c09c00, 00c0a3d0, 00c0ad30, 00c0b1d0, 00c0d590..00c0db00): all allocate a
  0x10000000-flagged 64 KB stack scratch, call the packet's body writer,
  finalise with FUN_0089adc0 (client/tunneled) or FUN_0089ae70 (world/tunneled)
  and install `ClientGateway::BasePacket::vftable` before FUN_00894560 hands the
  packet on.
* **Wire-fill convention.** `wire` is filled where a class in the packet
  catalogue or a literal opcode constant exists in the function (pet subtype 2 /
  0x11, encounter 3, inventory 4, command 0x17 / 0x2b, group 0x0e, broker 2..7).
  Where the packet class is absent from the catalogue and the function contains
  no opcode constant (body writers, gateway templates, handler send paths), the
  wire array is left empty and the packet identity is stated in `does`/`purpose`
  instead of asserting an unverifiable opcode.

## Contradictions / corrections versus existing notes

* **Chess init entry point (note 008).** The note names `0x00c08010` as the
  ChessInit entry. The MiniGameFlashC table actually binds `ChessInit` to
  **00c080b0**, a one-argument wrapper that calls **00c08010** (destroy +
  allocate 0x1290 + construct + `Chess::start(computer)`). Both addresses are
  real and 008010 is the allocation/start implementation, but a Lua-side caller
  enters at 00c080b0.
* **Merchant module naming.** The module whose name string is `MerchantSell`
  (registered by 00c0a890, table 0x0182a8ac) exposes `Populate`, `SortItems`,
  `BuyFromMerchant`, `BuyFromUi`, `Close`; the module named `MerchantBuy`
  (00c0a9a0, table 0x0182a8dc) exposes `Populate`, `SellToMerchant`,
  `SelectInventoryCategory`. The buy commands live in the *Sell* module and the
  sell command in the *Buy* module; names were kept as registered rather than
  "corrected".
* Note 091 lists subtype 17 -> `FUN_00c06b40` -> PetDeletePacket, which this
  shard confirms, and adds the body shape (id at +0xc, string at +0x10).

## Open questions for the lead

1. Player virtual slots +0x90 (Job.SelectJob) and +0x9c (Job.PopulateJobInfo) are
   unresolved; the player/client object layout is owned by other shards.
2. `FUN_00c064c0` stores only `BasePacket::vftable` although it is reached from
   the PetResponsePacket constructor funclets; which C++ subobject is being
   destroyed is not provable from this TU alone (recorded `likely`, not
   confirmed, with the limitation in `open_questions`).
3. `Inventory.SearchInventoryItems` (00c09a80) is the text-search entry the
   project's own progress notes say crashed once; the failing call is inside
   FUN_0098faf0 or the panel helpers, both outside this shard.
4. The four zeroed housing fields at +0x4130..+0x413c (00c0b3c0, also inlined in
   00c0b710) are a placement/rotation scratch block; their meaning is not
   recovered.
5. The broker body's two leading 16-bit fields (00c0cef0) are most plausibly an
   item id split in halves or two separate shorts; the client alone cannot decide
   which.

## Evidence hygiene

All handler names come from the decoded registration tables (data read with
`nmq bytes`, helper `scratch/ptr.py`; raw dump `scratch/dump.txt`). Names that
rest on a caller/callee's role instead of the function's own anchors are
`likely` and say so in `purpose`. Chess class bindings use the demangled
namespaces (`ChessMove`, `ChessPosition`, `ChessControls`, `Chess`, `ChessMoveData`)
as strong anchors. Packet class bindings use the RTTI vtable stores present in
the function bodies.
