`completion_reward_coins`/`completion_reward_xp` to `DerbyGatewayContent` and changed

## Why no new spawn rows

Every kart portal and derby arena entrance already has a drawable driver NPC spawned from
`data/content/npcs/*.json` (`placement: legacy_data`, positive model id, client locale name). They
are the speedway trainers/rivals the client already draws: Johnny Thunder, Mustang Alli, Chase
Wheeler, Cale Yardbird and Spud Edgins for kart; Mad Jack, Crash Davis, Burt Crewe and Rip Ringa for
the derby. Adding a second actor with the same name at the same turnstile would duplicate a named
NPC and invent placement evidence; T221 reuses the existing actors (Ponytail reuse rung). The
content test proves each gate id is emitted by the production `NpcVisibility` loader with a model and
a `npc_id -> npc_id` click identity, so "a drawable driver at the portal" is asserted, not assumed.

If a future speedway loses its driver, the T201 Warrior-trainer shape applies: add an
`npc_spawns_extra.json` row with `content_key`, a positive model id from `Models.txt`, a `Global.Text`
name id and five provenance entries; no code change.

## Threat note (secure-code-guardian)

Attack surface: any client can send 26/8 (click) and 26/10 (choose) with an arbitrary u64 target and
i32 choice from any position at any time, including while busy or racing.

- **Unknown/forged target.** The 26/8/26/10 path resolves the runtime GUID through the server's
  `NpcVisibility` content-key map and `NpcInteraction` content; a target that is not a spawned
  content NPC yields no menu (tested with Clack, a real NPC that is not a gate) and changes nothing.
- **Range/zone.** Every click and choice re-checks the 12 m reach and the zone (open-world zone 0
  bypasses the regional label by design); a far or wrong-zone target cannot open or select.
- **Forged/stale option.** The choice must be one of the options in the currently open menu for that
  exact NPC (`InvalidOption`/`NoInteraction`); 0, 9, 99, -1 and `i32::MAX` are refused and the menu
  is not consumed (tested with 99; `kart_npc_entry` already covers the wider set). The client can
  never name a race, scene, instance, profile or reward.
- **Gate list authority.** The ids come only from server content (`kart_gates.json`,
  `derby_gates.json`); `admit` checks the gate list, race content, already-active and the shared busy
  table, then the begin path runs on a staged `Gameplay` clone. A refused choice writes no save.
- **Dormant content.** No `derby_entry.json` means no `DerbyGateway`, so no derby option is emitted
  even though the gate list exists; a kart package without `race` publishes no gate. Both tested.
- **Economy.** T221 adds no grant, reward, item id, quantity or client-reported outcome. Entry still
  grants only the server-defined Kart/derby starter outfit via the existing idempotent unlock path;
  the close test asserts coins are unchanged. The synthetic derby package omits both T219 completion
  rewards (serde default 0), so this suite asserts the 39/16 offer only and never triggers a payout.
- **Atomicity/isolation.** No new shared state; the NPC menu is session-local inside the staged
  `Gameplay`, and a malformed packet returns an error that the gateway isolates to that session.

## Checklist

1. **A refusal changes nothing.** `a_busy_player_is_refused_and_nothing_changes` compares the whole
   `Gameplay` state after a busy menu and selection; `an_ineligible_or_forged_choice_changes_nothing`
   compares the full `Gateway` snapshot after a non-gate target and a forged option and then proves
   the offered option still works; `a_derby_driver_offers_nothing_while_the_derby_package_is_absent`
   compares the snapshot after the would-be option. Canary 1 removed a gate id and these failed.
2. **Rollback covers all state.** No transaction code changed. The choice runs on the existing
   staged `Gameplay` clone (`handle_npc_packet` commits only on success); the gate lists are
   immutable `Arc` content, not session side tables. The full snapshot comparison covers menu,
   profiles, inventory and kart/derby state.
3. **Apply deltas, never restore snapshots.** No payout/position restore was added. The close path
   is the existing kart return (previous job, no coins); the test asserts coins and the prior job.
4. **Busy rules are mutual.** No new activity or `Occupation` variant. The drivers use the existing
   `activity_busy()` / `admit(..., busy)` gate; the busy test seeds a real active Mining run and
   proves the driver is not offered and nothing starts. The old busy lists were not duplicated.
5. **Every entry path is gated.** The only path is 26/10 -> `NpcInteraction` -> `kart.admit`/
   `derby.admit` -> staged begin (hub wiring at `src/gameplay.rs` and the NPC dispatch in
   `src/gameplay/npc.rs`; line numbers differ by one argument between the base and the T219 tip and
   are read, not changed). There is no new automatic, reconnect or portal path. The entry path has no
   level check today (documented); the checks that exist are unchanged.
6. **Reachable in production, tested through it.** The tests build a real `Gateway` from the
   reference package plus the shipped gate files, load the shipped NPC content through the
   production fallback, and send the real 26/8/26/10 bytes. They never call a test copy of the
   feature or a service internal for the start. Both dormant cases (kart package without `race`,
   derby package absent) are driven through the same gateway and emit no option.
7. **Survives reconnect.** Gate lists are content and the drivers keep no per-player state, so there
   is nothing new to persist. The existing mid-race save/reconnect path
   (`a_disconnect_mid_race_survives_a_snapshot_with_the_prior_job`) is unchanged and still passes.
8. **Every exit path restores the player.** The close test loads the race scene (13/10) and sends
   the native 39/7: the kart entry is gone, the prior job is restored and coins are unchanged. The
   existing timeout/cancel/abort tests still pass. The derby's existing cancel/close paths are
   untouched and covered by `derby_route`.
9. **Economy safety.** No new grant or reward. The only items on entry are the server-defined starter
   outfit from the existing idempotent unlock; no client id or quantity is read. The close test
   asserts no coins; the synthetic derby package's T219 completion rewards are 0, so entry grants
   nothing. No free item was added.
10. **Wire format matches the client reader exactly.** No packet field changed. The reused 26/8
    constructor `0x008b6bc0`, 26/9 reader chain down to the seven-dword row reader `0x00a9dca0`,
    26/10 constructor `0x00a36f80`/sender `0x00a39090`, AddNpc `0x00921a10` and 33/34 parser
    `0x00ba0680` are cited above; the test parses bytes from the existing reviewed encoder (28-byte
    rows, label at +8), not a guessed layout. Gate ids are content keys (the AddNpc actor id), which
    is the existing click identity.
11. **Unique ids.** No new instance/GUID/lifecycle id. Gate ids are existing NPC content keys; the
    kart instance numbering and the derby instance numbering are untouched. The two-session test
    does not reuse or alias a public-world instance (the race/session instance remains private).
12. **Others see changes.** No outfit/job/mount/actor spawn was added. Entry's job switch keeps using
    the existing `announce_profile_outfit` directed path; the new tests assert the 41/114 entry
    reply and, for the derby, the 39/16 offer.
13. **Content works end to end.** The content test asserts each gate is a drawn actor with a real

14. **Values live in data.** Gate ids, menu labels and the cooldown live in the content JSON; no new

15. **Canaries break production code.** Canary 1 (re-run this attempt on the tip source) removed a

17. **One player's error never stops the server.** No tick or shared-tick code changed. The new

18. **A type's rules live on the type.** No struct changed. `KartGates`/`DerbyGates` keep their
