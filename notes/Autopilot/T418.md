# T418: the scavenger hunt stays closed until an admin opens it

The scavenger hunt (quest 3000200) is now a **live event**. Jacque offers it only
while an admin has it open:

- `realm event open 3000200` opens it, `realm event close 3000200` closes it, and
  `realm event list` shows which live events are open. Each answers with one
  `chat::system` line.
- The open list is world state in `<live_dir>/events.json`, written with
  `{"schema_version":1,"open":[ids]}` through `character_store::replace_bytes`.
  `live_dir` is the `--world` folder, or the content folder when no `--world` is set.
- Every session reads that file when its quest catalogue binds and when its live
  folder is set. After that it polls the file once a second from `Gameplay::tick`,
  so a second player sees an open within about a second without a relog.
- A closed event is not a disabled quest. An accepted hunt still advances, turns
  in and pays once, and the hunt survives a relog while the event is closed.

## Where this differs from the brief

- **An accept after the close withdraws the offer; it is not a no-change
  refusal.** Gate 3 says "refused with no change". The client forgets its offer
  when it sends the accept, so a kept pending offer could never be cleared and
  would block every later offer. Client evidence and the full reasoning are in
  the (R) rules. Every other refusal in this task changes nothing.
- **One map instead of two sets.** `live_events` + `open_events` would be two
  sets that must stay in sync. A single `BTreeMap<u32, bool>` cannot drift.
- **A typed field instead of `object.remove("live_event")`.** `content::Quest`
  already models `enabled` as a field. `tests/content_jobs.rs` loads the split
  quest records through `ContentDb`, which uses `deny_unknown_fields`, so a
  strip-only key would have broken that test. A serde field covers both loaders.
  A non-boolean value is still `InvalidData`.
- **Watch logic reused rather than copied.** The brief allowed a pure move or a
  copy. A generic reader parameter on the existing poll avoided both and needs no
  ponytail note.
- **The T384 sweep opens live events through the shared fixture.** The brief
  says "through `tests/support/scavenger_hunt.rs`". The sweep cannot include that
  file: its `tests/support/quest_records.rs` imports `super::npc_quest_chain`, and
  `scavenger_hunt.rs` nests its own private copy of that module, so the two
  `Fixture` types would differ. The helper is therefore `Fixture::open_live_events`
  in `npc_quest_chain.rs`. `scavenger_hunt.rs` re-exports it and its `fresh()`
  uses it, so both callers share one writer.
- **Runbook lines 177 and 336 were not edited.** Line 177 only says `set-role`
  does not enable dev tools, which is still correct. T445 already states that
  role commands work without `--dev-tools` and cites the native run
  (`client-baseline-20261021T193008Z`) in "Evidence and open gates" and the
  provenance table. Line 336 concerns account-store login, which has not passed
  native acceptance, so it must not be changed. The research pack
  `lab/fleet/out/brief-research/T418.md` reached the same finding.
- **`realm offer` is unchanged.** It still needs `--dev-tools` and is a self-only
  diagnostic. `dev_mark_offered` plus `accept` lets it start a closed event, as
  the brief asks.

## (R) rules

- `(R)` The hunt is offered only while it is open. This replaces T281's
  "always offered" policy and follows the World Builder `realm event` design and
  Build Plan 3.3.
- `(R)` An offer shown before a close cannot be accepted after it. That accept
  **withdraws** the offer the way a 49/2 decline does: the pending offer and the
  Offered row are removed and the change is saved, with no 49/3. This is the
  one accept refusal that changes state, because of client evidence:
  - `0x00a97d70` (Accept) sets the client's offered quest id to -1 after it
    builds the 49/2. `0x00a97e10` (Decline) does the same.
  - So once the client sends the accept it has no offer left and can never send
    the 49/2 decline that would clear the server's copy. The handler also ends
    the dialog (26/4).
  - A kept `pending_offer` would make `offer_denial` refuse every other quest
    from every NPC (including 49/15 breadcrumb starts), and the hunt itself
    (status Offered), even after a reopen. Nothing at bind clears it, so the
    character would be cut off from new quests for good.
  - The withdrawal returns `denial: Unavailable` with `changed: true`. The 49/2
    handler logs it as `withdrawn` and runs the T361 job-level sync only for a
    real accept.
  - Every other accept refusal (requirements, limit, no matching offer) still
    changes nothing. The developer `realm offer` accept still bypasses the
    closed check.
- `(R)` A closed event never touches saved progress. An active hunt advances,
  turns in and pays.
- `(R)` A missing, malformed, oversized, non-regular or wrong-schema
  `events.json` closes every event. Each refusal is logged once per file version
  (`live_events_refused`). Ids that are not live events are dropped and logged
  once per file version (`live_events_ignored`).
- `(R)` An admin `open` or `close` refuses to overwrite a file it could not read,
  matching `load_placements`. The admin fixes or deletes the file by hand.
- `(R)` Sanity bounds: 4 KiB and 64 ids. These are file-format limits, not
  gameplay tuning.
- `(R)` The poll interval is the placement watch's one second (`PLACEMENT_POLL_MS`).
- `(R)` `open` does not broadcast. The operator still sends the two
  `realm broadcast` lines.
- `(R)` `realm event` routes like every builder command, through `developer_cheat`
  on the opening path. A session with no opening content does not route it, the
  same as `realm place`.

## Security threat note (secure-code-guardian)

- **A hostile client sends `realm event open|close|list`.**
  - `developer_command_denied` refuses it before routing: `event` is neither
    ordinary nor in the Builder list, so `can_run_realm_command` allows only Admin.
  - The refusal is the existing role line with `dev_command_denied`. Test 5 shows
    no file is written and no state or save byte changes for Player and Builder.
  - `account_store.rs` and the ordinary-command list are untouched.
- **A hostile client forges 49/2 for a closed hunt.** `accept` refuses it: no
  49/3, no quest started, no reward. With no pending offer of the hunt nothing
  changes. With one, the offer is withdrawn (test 3), which a 49/2 decline can
  already do, so this gives a client nothing new. Forged 49/1 or 26/x Talk
  choices go through `offer_denial`.
- **Admin input.**
  - The id is parsed as `u32` and must be a live event in the bound catalogue. A
    disabled quest stays disabled because `offer_denial` checks `disabled` first.
  - The path is fixed (`live_dir()/events.json`). Nothing in the client message
    names a path.
  - The write is atomic. A refused read or write changes nothing.
- **A malicious or broken file.** Its size is bounded before parsing, it uses
  `deny_unknown_fields`, and every error means "closed". It never panics and is
  logged once per version.
- **Economy.** No reward, item, coin or XP path changed. A closed event cannot
  re-grant or block a payout. The turn-in tests still pay exactly once.
