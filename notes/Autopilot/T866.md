# T866 - The card launch ticket expired while the player read the run panel: the Start click renews it (native 2026-10-28)

Native 2026-10-28 (`client-baseline-20261028T073701Z`, `../lab/autopilot/native-notes/2026-10-27.md`):
the TCG run panel was open and the client asked for its launch ticket (39/37 -> 39/0x28) at
07:39:48; `launch.ticket_ttl_ms` is 60 s, so the ticket expired at 07:40:48. The Start click
(39/5) came at 07:40:56 (68 s after the mint), the card DLL logged in with the ticket the client
had stored, and `card_service` refused it as `expired` (the client's "Your session is not valid").
Every player who reads the panel for more than a minute hits the same refusal.

Attempt 2 (2026-10-28, after review `pre-T866-a1.md`): finding 1 (the ticket-lifetime change
needed lead sign-off) is resolved by the 2026-10-28 T866 row in `lead-signoffs.md`. Finding 2
is a false comment, not a code defect: a repeated 39/37 does not "only report that state", it
re-mints a fresh 39/0x28 and leaves `changed` false. The route comment and this note now say
that, which is why the guard needs both halves; the new
`a_starting_state_ack_and_a_repeat_ticket_request_do_not_renew` pins it. The production code is
otherwise attempt 1 unchanged.

## What changed

- `src/card_service.rs` (`LaunchTickets::renew`, new, 17 lines): moves the expiry of the
  character's outstanding ticket to `now_ms + ttl_ms`, keeping the ticket value. The store is
  per session and holds at most one ticket per character, so the search is over at most one
  row. A spent ticket (removed by `redeem`) or one swept by a later mint is not revived: a
  character without a ticket is left as it was. It renews even when the ticket is already past
  its first expiry, which is the native case (Start arrived 8 s after the 60 s expiry); the
  Start click is what makes the value the client already holds redeemable again.
- `src/card_game.rs` (`Launches::route`: the guard and its eight-line comment, plus three doc
  lines): after `MinigameRuns::handle_client`, an outcome that changed the run and moved it to
  `RunState::Starting` is the accepted Start (`MinigameRuns::start` is the only producer of that
  pair), so the session's ticket is renewed at the same `now_ms` the mint used. Both halves of
  the guard are needed: a repeated 39/37 *re-mints* (a fresh 39/0x28 that replaces the ticket the
  client already holds) and a 39/7 ack reports `Starting`; both leave `changed` false, so
  neither renews. 39/6 leave and 26/42 close set `changed` but move the run to Cancelled/Closed,
  not Starting.
- `tests/card_launch.rs`: one local `ticketed` helper (the T866 tests share one setup) and six
  tests: the brief's long-read gate, the native late-Start case, the no-Start negative (also
  proving a refused Start and a 39/7 ack renew nothing), a spent ticket not being revived, the
  review-2 pin (an ack while Starting and a 39/37 re-mint do not renew), and the whole path
  through the production Gateway dispatch with a 2 s content lifetime.
- No content row changed: `ticket_ttl_ms` was already data (`data/content/card_game.json`,
  bounded to 1 s..10 min by `card_game::Content::validate`) and `renew` uses the store's own copy
  of it.

## (R) rules and open gaps

- (R) the retail server renewed the ticket on Start. No client field or message carries a
  lifetime, and the client never refreshes the value; the only server-side fix consistent with
  the recovered client is moving the expiry. The renewal window (now + the same content TTL) is
  the existing value.
- (R) renewing an already-expired, unspent ticket is deliberate: the reported native run started
  8 s after the first expiry. The ticket is still the session's own, single-use bearer value and
  the Start click still requires the offered, ticketed run in that session, so this adds no
  capability the client did not already have by sending another 39/37 (which mints a fresh
  ticket with a fresh lifetime).
- Open (lead native recheck): open the run panel, wait past 60 s, press Start, and confirm the
  TCG logs in (`card_login` ok in the gateway log) and enters the lobby. Server-side proof is the
  new gateway test.
- Open, unchanged: `Launches::route` recognises the accepted Start through `RunOutcome.changed`
  plus `RunOutcome.state` (`Starting`). A future packet that also changed a run to `Starting`
  would renew too; that only moves the session's own ticket expiry, and the guard is named in a
  comment at the check. The changed-false Starting outcomes (39/37 re-mint, 39/7 ack) renew
  nothing, pinned by `a_starting_state_ack_and_a_repeat_ticket_request_do_not_renew`.

## Threat note (secure-code-guardian)

- What a hostile client could send: its own 39/37 at any time while a run is offered (already
  mints a fresh ticket), 39/5 Start for its own or a stranger's instance, 39/6/39/7, 26/42, and
  malformed 39/x headers. The 411 card login (ticket text, character-id text) comes over the card
  listener.
- Why the change is safe: the ticket store is per session and holds one ticket for the session's
  own character; `renew` is reached only after `MinigameRuns::start` accepts the Start (current
  run, `Offered`, `ticketed`), and it only moves the expiry of a ticket that is already in that
  session's store. A ticket the store no longer holds (redeemed, swept, or never minted) is not
  created or resurrected, so single use and the minting-session-only rule are unchanged. The
  character must also match the minting session's character (`redeem`'s owner check). The ticket
  value never changes, so no new credential is delivered past the one 39/0x28 the client already
  received; a client that could exploit a renewed expiry could equally have sent another 39/37
  and received a fresh ticket. `now_ms` is the same caller clock for mint, renew and redeem, and
  the update uses `saturating_add`. Refusals (`expired`, `character_mismatch`, `unknown_ticket`)
  still spend nothing. No item, coin, save or trace field is touched.

## Checklist

1. A refusal changes nothing: the expired `redeem` before Start is refused and the ticket is
   still redeemable after Start (`a_start_after_the_first_expiry_revives_the_ticket_the_client_
   holds`); a refused Start (another instance), the accepted 39/7 ack and a repeated 39/37
   re-mint renew nothing (`a_ticket_whose_start_never_came_stays_expired`, and the review-2 pin
   `a_starting_state_ack_and_a_repeat_ticket_request_do_not_renew`; canaries 2 and 3 break
   them). `a_start_does_not_revive_a_spent_ticket` shows a refused (unknown) spent ticket is not
   brought back.
2. Rollback covers all state: the expiry lives in `LaunchTickets` inside `Launches` inside the
   `Gameplay` clone the Gateway stages and commits; there is no shared cell or side table.
   `Launches`/`LaunchTickets` are `Clone`, so the staged copy is deep.
3. Apply deltas: no inventory, coins, position or snapshot is captured or restored; only one
   `u64` expiry in the session store moves.
4. Busy rules are mutual: no new activity; `Occupation::CardGame` still reads
   `Launches::is_active` and the card run's lifecycle is unchanged.
5. Every entry path is gated: the renewal is not an action, and it runs only inside `Launches::
   route` after `MinigameRuns::start` accepts (current run, `Offered`, `ticketed`); the graph
   shows that route has one production caller. The redeem path's gates are unchanged.
6. Reachable in production, tested through it: `a_start_after_the_ticket_expired_renews_it_
   through_the_gateway` drives `Gateway::handle_at` -> world dispatch -> `handle_card_game` ->
   `Launches::route`, then the card listener's own `Gameplay::redeem_card_ticket`.
7. Survives reconnect: not applicable by design - the ticket is session-only and never persisted
   (T764/T765); the gateway test asserts the Start marks no save (`gateway.snapshot()` equal
   before/after).
8. Every exit path restores the player: no exit path changed; 39/6 still retires the run and the
   ticket left behind expires (asserted in `a_ticket_whose_start_never_came_stays_expired`).
9. Economy safety: no free grant, reward, item, coin or client-reported result is involved; the
   ticket is not an item and pays nothing.
10. Wire format matches the client reader: no layout change. The Start's answer is exactly one
    39/17 and no second 39/0x28 (asserted), so the stored ticket value the client passes to the
    DLL is unchanged; client readers `009b9550` (39/17 -> Startup) and `00ad32e0`/`00ad47f0`
    (39/0x28 halves -> `--ticket=%llu`) are cited above and in the code comments.
11. Unique ids: unchanged; the card instance range and allocation are untouched.
12. Others see changes: nothing about a card run or its ticket is visible to another player.
13. Content works end to end: the gateway test walks Play -> 39/16 -> 39/37 -> 39/0x28 -> Start
    -> 39/17 -> redeem in the minting session, with the lifetime from content.
14. Values live in data: `ticket_ttl_ms` stays in `data/content/card_game.json` (bounded 1 s to

17. One player's error never stops the server: nothing runs in the shared tick; there is no

18. A type's rules live on the type: `LaunchTickets` owns single use and expiry, and its `renew`
