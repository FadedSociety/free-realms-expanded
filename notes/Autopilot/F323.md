## Findings

1. **BLOCKER - the unsigned relay-budget clock - reverted.** F309 changed the
   per-character relay budget's time base from `Instant::now()` to
   `session.session_start + Duration::from_millis(now_ms)`, a change to a
   lead-owned rate limit with no sign-off. F323 restores the lead-accepted F290
   wall clock: `delivery::jump_fanout` takes no clock argument and reads
   `Instant::now()` at the charge; `post_commit` drops its `now_ms` parameter and
   the session-start derivation; the bin's call loses the argument (same line).
   `Security::jump_relays`' field comment now names the wall clock. The clock
   choice is pinned by a regression (finding 3).
2. **MINOR [SAFETY] - one epoch for the shared `KeyedBuckets` - fixed by the
   revert.** With every `allow` on `Instant::now()` there is one monotonic epoch
   for all sessions, so the capacity path cannot see a later session's clock or
   give a stale key an artificial refill. No new test is needed: the latent
   failure only existed while the clock was per-session, and that code is gone.
3. **MINOR [TESTS] - the flood test no longer depends on the dispatch clock.**
   The ten-jump flood asserts `RELAY_BURST <= relays <= RELAY_BURST + tokens
   refillable during the measured loop`, computed from the production rate: it
   cannot flake with host load and still fails if the limiter is bypassed
   (canary C). The signed wall clock is pinned separately: three jumps with the
   *same* dispatch time, 120 ms apart, must all relay (canary D - the F309
   dispatch clock relays two and drops the third).
4. **MINOR [TESTS] - reconnect/save assertions strengthened.** The leave test now
   reconnects through the real login/13/10 path and asserts the pose the leave
   path saved (the last committed jump, `start[0] + 4.0`), not the guid read
   before login. Canary B (skipped leave save) fails on it. The bucket
   `len() == 1` check carries a comment that it does not identify the key; the
   `is_empty` assertion after the leave is the cleanup guard (canary A mis-keys
   the leave call and fails it). The over-claiming comments and the "dispatch
   clock is deterministic" wording are gone.
5. **MINOR [RULES] - `MAX_VERTICAL_SPEED` - unchanged; lead decision.** No
   movement/relay policy content table exists (the 125 speed envelope is

## Security threat note (secure-code-guardian)

A hostile client can send a 164 naming another character (refused: the body GUID
must equal the session-bound character), a short/trailing/wrong-opcode body
(refused by `jump_relay::decode` before staging), NaN/Inf position, direction or
velocity (refused), an out-of-bounds pose (refused by `movement::validate`), or
a huge finite velocity (clamped to the (R) bound, never a disconnect). A 164
flood is capped per character at 10/s burst 4 through `Security::jump_relays`;
over budget only the extra 164 drops and the accepted poses keep flowing through
125. The bucket set is bounded by `MAX_SESSIONS` and the character key is removed
by `end_session`, so a reconnect cannot inherit a spent budget (tested). Opcode
125/164 movement is not part of the chat/action account budget, so the relay
limiter is the only per-character 164 cap; the transport packet/byte budgets
still bound the raw session rate. F309 moved the budget to a per-session epoch;
that let a later session's clock drive the shared `KeyedBuckets` capacity probe,
so F323 restores the single wall-clock epoch. The limiter is charged only after
a successful commit, so a refused or failed transaction neither spends nor
refunds a relay. No items, coins, rewards, roles or hidden state; no secrets or
player names are logged.
