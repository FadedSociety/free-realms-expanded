# T900: area-enter banner, 104 POIChange then 15/2 EnterArea

The region table (T753/T876: 10 regions, 20 places, 816 shapes) was never used to tell the client where the
player is. Now a player who stays in a new named area for the settle time gets 104 (the banner) and then 15/2
("Now entering ...").

## What changed

- `src/area_banner.rs` (new): `poi_change` (104 builder), `AreaBanner` (one session: announced area, pending area with
  its entry time, last looked-up zone and position), `AreaBanners` (all sessions by id, `poll` and `prune`). Logic
  adapted from Sanctuary `Player.cs` `QueuePointOfInterest` / `UpdatePendingPointOfInterest` / `UpdatePointOfInterest`
  (AGPL-3.0, main 3b3aec3, credited in the file header); the area comes from `RegionTable`, not Sanctuary's tile grid.
- `src/world_regions.rs`: `RegionTable::named_area_at` (region id and name id: the place's, else the region's) and
  `banner_settle_ms()`; `regions.json` gets one new key `banner_settle_ms: 1500` (optional, default 1500, bound 0..=60000).
- `src/chat.rs`: `enter_area` (15/2 builder, next to `string_say`).
- `src/client_areas.rs`: `ClientAreas.banners` (the per-session state already rides in `SharedWorld.client_areas`).
- `src/bin/osfr_gateway/client_area_routing.rs`: `banner_tick`; `src/bin/osfr-gateway.rs`: the one call beside
  `season_tick` in the 20 Hz tick.

## Client evidence

- 104: dispatcher `0x009471a0` case 104 (`0x009489a7`), ctor `0x0089b9f0` (opcode at +4, payload +8/+0xc/+0x10), reader
  `0x008d5dd0` (`i16` opcode, `u32` name id, `u32` POI id, `u32` area id), name id resolved in the locale, then
  `0x00a12a80` -> `0x00c8e440`: stores the three `CurrentPOI` columns and notifies Lua only when the POI id or the area id
  differs from the stored pair. `BaseClient_CurrentPOI_OnDataUpdate` (`ScriptsBase.lua:5049`) calls
  `NotificationHandler:LoadingZone` for `1 < poiId < 11`. So the POI id is the region id; ids 2..10 show the nine banner
  movies, 1 (default region) shows none. IDA beats `notes/Research/Zones and Regions.md` section 4.1, which only
  knew 47/9 and called the 104 path unused; both paths reach `LoadingZone`, and only 104 is sent (never both: a second
  banner would double).
- 15/2: reader `0x00b10580` after header `0x00b0f550` (two `u16`), display `0x00b10250` looks the `u32` up in the locale
  and binds it to `[*area*]` of `EnteringChatArea`. The existing region/place `name_string_id` values are those locale ids.

## Rules and (R) choices

- (R) Settle time 1.5 s: Sanctuary's `AreaSettleMilliseconds`; the client has no delay. In `regions.json`, tunable.
- (R) Area id (third 104 field) is always 0. Its client meaning is unrecovered, and a per-place value would replay the
  banner inside one region (the client notifies on a POI-id or area-id change).
- (R) Region 1 and places inside it (Lakeshore, Wilds, Newbiezone ...) are announced too, with POI id 1: no banner, but the
  client's stored pair changes, so re-entering Snowhill shows its banner again, and the chat line names the place. Sanctuary
  sends nothing for areas without an id 2..12; whether the original announced the default region is unknown.
- (R) A place inside the current region (Briarheart in Briarwood) gets 104 and 15/2 with its own name; the client ignores
  the unchanged 104 pair, and shows the chat line.
- Outside every region the announced area is kept and nothing is sent. A session outside the open world (loading, an
  instance, gone) holds no state, so coming back announces the current area again; the client may ignore an unchanged
  104 pair after an instance (native check for the lead).
- Open: the original's trigger policy is not recovered (Native Map marks it a hypothesis); this is the community policy
  on the client's own readers.

## Structure

- Graph/search: `rg` for `region_table`, `POIChange`, `EnterArea`, `season_tick` (the integration-tip graph was not used:
  the change is one new module plus one call). `client_area_routing.rs` already owns "tell the open-world sessions about
  areas" (opcode 89), so the gateway glue lives there; `SharedWorld.client_areas` already carries per-world area state,
  so no new `SharedWorld` or `Session` field.
- Hub lines: `src/bin/osfr-gateway.rs` +1 (the call). No other hub touched. Nothing deleted. Spine ceiling for the gateway
  is 4643, now 4641.
- Cost per tick: one pass over the sessions; a session that has not moved costs a comparison, a moving one a table lookup
  (20 places and 10 regions, first match wins); an announcement allocates two small packets. `prune` scans only when more
  sessions hold state than exist.

## Threat note

The input is the committed position (already validated by the movement reader); no new inbound packet or selector, so no
`app_fuzz` seed. A hostile client that jitters across a boundary costs one lookup per position update and still gets at
most one announcement per settle time per session; `banner_settle_ms` is bounded at load (0..=60000) and 0 is an owner
choice. Nothing it sends is echoed to other players. State is per session and dropped when the session leaves the open
world or ends.

## Checklist

1. Refusal changes nothing: there is no refusal path; the tick only reads the committed position. A failed queue is logged
   and skips that session (the state already moved; the line is cosmetic).
2. Rollback: state lives outside the staged transaction (ticks run after commit); nothing in a staged gateway changes.
3. Deltas: nothing restores a snapshot.
4. Busy rules: not an activity.
5. Entry paths: one path, the tick, for login, teleport, walking and reconnect (position-driven); `in_open_world` gates it.
6. Reachable in production, tested through it: `walking_into_a_named_area_sends_the_banner_once_after_the_settle_time`
   drives `test_support::enter`, the real 13/10 handshake, the real 125 movement reader and `banner_tick`, the function
   `Server::step` calls.
7. Reconnect: a new session has a new id and no state, so it announces its area once; not persisted by design.
8. Exit paths: leaving the open world or ending the session drops the state.
9. Economy: none.
10. Wire: byte-level tests in `tests/area_banner.rs` against the readers above (104: 14 bytes; 15/2: 8 bytes).
11. Unique ids: keyed by session id.
12. Others see changes: the banner is for the player alone.
13. Content end to end: the shipped `regions.json` drives the tests (Sanctuary, Snowhill, Lakeshore, outside).
14. Values in data: `banner_settle_ms`, bounded.
15. Canaries: `<` to `<=` in the settle test fails six area_banner tests; replacing the gateway poll with no packets fails
    the gateway test (both reverted).
16. No session plumbing touched: only a tick call.
17. One player's error never stops the server: the tick returns nothing fallible; a queue error is logged per session.
18. Type rules: the per-session fields are documented on `AreaBanner`.
19. Hot path: see Structure.
