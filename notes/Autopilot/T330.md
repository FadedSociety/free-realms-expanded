## Threat note (`secure-code-guardian`)

The change adds no client parsing; it enables one data row and drives the
existing parsers. A hostile client could send:

- **A forged 49/2 accept with no open offer** — `QuestEngine::accept` requires
  the quest in `Offered` state; test 4 asserts no 49/3/49/8/49/4 and an equal
  typed state + save.
- **A premature or wrong-quest 49/14** — `finish_turnin` requires
  `pending_turnin == quest`; both are clean no-ops in test 4.
- **A forged 49/13 or a replayed end screen** — only the server holds the
  end-screen packet; the test never sends 49/13 as a request.
- **A wrong-NPC 26/8/26/10 Talk** — the runtime actor maps to its content key
  and `offerable_quest_for_talk` admits only a giver with `can_offer`; test 4
  talks to a different drawable giver and no quest is offered.
- **An out-of-range 26/8 click** — the existing NPC range check refuses before
  any menu or quest mutation; test 4 asserts equality.
- **A replayed 49/14/49/2 after payment** — the grant key
  `quest:<character>:<quest>` and the Completed status make both no-ops; tests
  2, 4, 5 and 6 assert equality.
- **A near-cap coin balance** — `apply_grant` refuses the 13-coin grant with
  `coin balance overflow`; test 4 asserts no 49/4/38/19, no XP, identical save
  bytes and the pending screen left retryable.
- **36/10 melee at a shared-field actor** — the host's `commit_outcome` accepts
  only a target in the session's known-NPC set and the shared field's own
  `handle_shared_field` resolves it; no client quantity is trusted.
- **Two players** — every session owns its quest state, field and reward key;
  test 6 proves one player's battle, win, refusal and turn-in never touch the
  other's snapshot/save.

The `QuestSession` known-NPC set is **test-only**: it mirrors the server's
per-session set so the host's real self/known-target gate still decides whether
an action is dispatched. No production validation was relaxed.
