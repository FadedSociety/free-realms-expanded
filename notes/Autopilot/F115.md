# F115 T020 review repairs

## What changed

- `prototype/osfr-tools/src/social_lists.rs`: an accepted invitation now checks
  `member_group` before consuming the pending invite or mutating either roster.
  A character that joined another party after receiving an invite receives the
  existing 40/5 result 1 and remains in the party it already joined. The invite
  remains pending until acceptance becomes possible, expiry, or teardown. A
  decline still consumes the invite and notifies the original party.
- `prototype/osfr-tools/tests/social_lists.rs`: added the A-invites-B,
  B-invites-C, C-accepts-B, B-accepts-A interleaving. It checks both rosters,
  the one-party mapping, pending-invite preservation, and the unrelated-party
  survivor after B's party dissolves.
- `prototype/osfr-tools/src/bin/osfr-gateway.rs`: added the same interleaving
  through the router with chat-recipient checks, reset the kicked character's
  spam gate before the revocation assertion, and asserted that its chat scope
  is cleared.
- `prototype/osfr-tools/src/bin/osfr-gateway.rs`: added `Server::end_session`
  tests for an owning session and a stale non-owning duplicate. The owner test
  checks group/chat teardown and the survivor refresh; the stale test checks
  that the live owner's active mapping, roster, membership map, chat scope, and
  chat recipients are unchanged.

## Reconstructed policy

- (R) A character in a party cannot accept an older invitation from another
  party. Joining the current party does not disconnect or overwrite the
  membership map. The older invitation stays pending, and its pre-existing TTL
  still bounds how long it can reserve capacity.
- (R) The client exposes no recovered 40/5 result meaning "already grouped".
  F115 reuses result 1, the existing no-group refusal, rather than inventing a
  wire value. The client-side meaning of this refusal remains unverified.

## Threat note (secure-code-guardian)

Line numbers below are in the F183 working tree at run tip `137ed97` (the
F183-a2 patch applied on that base); symbols are authoritative. F183 adds no
production hub line.
Hostile client capabilities on family 40/sub 4 and why they are constrained:

- **Forged body identities.** The 40/4 body carries two GUIDs, two name
  records, the 40/1 pop-up dword, an accept byte and five opaque dwords. The
  parser (`parse_social_request` `(40, 4)` arm,
  `src/bin/osfr-gateway.rs:2906-2919`) consumes and discards the GUID/name
  fields; only that dword and the accept byte reach
  `SocialService::respond_group_invite`. At the reviewed commit `3922af8` the
  dword was the group id; F189 (`4041bc7`) changed it to the per-invitation
  generation the client copies from the 40/1 pop-up. The actor is the
  authenticated `self.character_guid` in `Session::route_application`'s
  `GroupResponse` arm (`src/bin/osfr-gateway.rs:2164-2166`), and the service
  resolves the pending invite by that GUID and compares its generation
  (`src/social_lists.rs:793-811`). A body identity therefore cannot accept for
  another character; a foreign generation is refused. The router test
  `forged_body_identities_do_not_select_another_character_or_invite` sends a
  body naming C while B is authenticated, first with C's generation and then
  with B's; it asserts that only B's pending invite and roster move, while C's
  invite and rosters do not.
- **Stale invitation.** A character that joined another party after the invite
  arrived still has the pending invite keyed by its GUID. The guard in
  `SocialService::respond_group_invite` (`src/social_lists.rs:826-832`) refuses
  with 40/5 result 1 before consuming the invite or touching either roster, so
  the request cannot produce overlapping membership or move the character out
  of the party it joined.
- **Replay.** A repeated 40/4 has no pending invite and gets 40/5 result 3
  without changing state (`src/social_lists.rs:803-805`); a stale or foreign
  generation gets the same result at `:806-811`. A successful first accept or a
  decline removes the invite; a refused stale accept leaves it pending.
- **Forged decline.** Decline only removes the target's own pending invite and
  notifies the existing group (`src/social_lists.rs:841-850`); it cannot remove
  membership or grant anything.
- **Full group.** An accepted invitation for a group already at
  `max_group_members` is refused with the existing 40/5 result 2 before the
  invite is removed (`src/social_lists.rs:833-837`), so the refusal consumes
  nothing; the row still ends at expiry or teardown. Capacity can currently
  free only through member removal, which drops same-group invites, so
  "accept after capacity frees" remains a future-path property.
- **Data and economy.** 40/4 carries no quantity, item, coin or reward. The
  refusal message is a fixed 8-byte 40/5 packet: the 4-byte `40, 5` header plus
  the `u32` result from `encode_group_result` (`src/social_lists.rs:1589-1593`).
  The byte test `group_reader_builders_match_recovered_headers_and_member_order`
  pins `[40, 0, 5, 0, 2, 0, 0, 0]` (`tests/social_lists.rs:449`), and the
  client dispatcher `0093daf0` case 5 constructs the 40/5 reply object and
  reads one result dword (`notes/Native Map/Systems/net.packet.group.md:12,97`).
  No save file, item, coin or cooldown is written.
- **Trust boundary.** The service trusts only the session GUID, the echoed
  generation matched against that GUID's pending invite, and its own maps.
  Client-supplied names/GUIDs are parsed only because the fixed body length
  must be consumed; mismatch is ignored, not merged.
- Existing exposure (not introduced here): `SocialService` has no per-account
  action budget for group requests, so repeated 40/1 or 40/4 packets are limited
  only by the transport/session limits, not by an application budget. The invite
  TTL bounds how long a pending invite reserves capacity, not the request rate.
  Adding a group-specific budget is a security decision for the lead.
