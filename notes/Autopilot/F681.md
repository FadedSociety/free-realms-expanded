## Threat note (secure-code-guardian)

- What a hostile client can send: no packet reaches the drop roll directly. The only trigger is a
  server-observed battle win (the win block in `encounter.rs`); the roll is server entropy and the item id,
  quantity and chance come from `field_battles.json`, bounded at load (item id > 0, quantity 1..=MAX_PRIZE_QUANTITY,
  finite chance 0..=1, <= 4 rows, provenance required).
- `realm win` is not a hostile path: it needs dev tools and the Admin role (the existing gate) and now grants
  no chance drop (`realm give` is the explicit inspection path).
- A full bag or a capped wallet is a refusal, never an `Err`: the whole reward is refused with one system line
  (`apply_encounter_reward` returns `Ok`), so a capped player cannot fault the shared tick for others.
- No client-reported item ids, quantities or results are read; the saved drop is a normal inventory item added
  by the atomic `grant_reward` bundle, so reconnect cannot duplicate or lose it.
- Economy: the yarn is not merchant-sellable in the current data (see MINOR 9); the test fails if that changes.

## Checklist (the review's 19 items)

1. **Refusal changes nothing.** The capped test snapshots the whole `InventoryState` and the `Economy` before
   the win, refuses the reward, and asserts both are equal after; the message assertion is its canary
   (reverting the text fails it).
2. **Rollback covers all state.** No new transaction state: the drop is granted inside the existing
   `grant_reward` atomic bundle on a clone; the refusal happens before any grant. Nothing escapes.
3. **Deltas, not snapshots.** `grant_reward` adds to the live bag; no old inventory is restored over it.
4. **Busy rules are mutual.** No new activity, so the `occupation.rs` table is untouched; battle busy gates
   are unchanged.
5. **Every entry path is gated.** The roll has one site (the battle-win block). The dev `realm win` path is
   explicitly excluded from the drop and tested; the normal melee, reconnect and save paths are unchanged.
6. **Reachable in production, tested through it.** Every test drives marker click -> Go -> melee, or the real
   `realm win` chat dispatch; no internals are called and no test copy of the roll exists.
7. **Survives reconnect.** The new save/close/reload test asserts the yarn is in the bag after
   `game_store` save and `Gateway::load_gameplay`; the drop is an ordinary saved stack.
8. **Every exit path restores the player.** The results Close is exercised with the drop in the bag (drop
   survives, player returns to the open world); a refused/capped win still completes the encounter and leaves
   the player free; there is no new exit path.
9. **Economy safety.** Server-verified win only; item id/quantity/chance are content and bounds-checked; the
   shipped test pins that the current yarn has no sell price, so it cannot be sold for profit; `realm give`
   remains a dev-only tool (Admin + dev tools).
10. **Wire format matches the client reader exactly.** No new packet. The item layout citation is `0x008e3760`
    (name +4, description +8, icon +12); the inventory-add replies are the existing `grant_bundle` ones, and
    the drop adds no field to any packet.
11. **Unique ids.** No ids are minted by this change; the granted stack gets its instance id from the existing
    inventory allocator, and the test reloads the bag rather than fabricating one.
12. **Others see changes.** Inventory is private to the player; nothing here is broadcast.
13. **Content works end to end.** The shipped row is loadable and grantable (existing test), the forced-chance
    test asserts the yarn is actually in the bag after a real win, and the dev/capped tests assert it is not
    granted where it should not be.
14. **Values live in data.** Chance, quantity and item id remain in `field_battles.json`; no new compiled
    tuning value. The dev-route rule is code, but it is a debugging rule, not gameplay tuning.
15. **Canaries break production code.** Two production breaks (dev-win clearing, refusal text) were applied to
    `debug_win`/`encounter_rewards.rs`, each made the intended test fail, then both were reverted byte-for-byte
    (sha256 checked) and pass again.
16. **Hands off session plumbing.** No change to session creation/teardown/transactions/save ordering,
    `gateway.rs` or `osfr-gateway.rs`.
17. **One player's error never stops the server.** A capped wallet is a logged refusal (`eprintln!` + one chat
    line) returning `Ok`; the capped test shows the win completes and the server keeps running. The drop path
    has no `unwrap` on client data.
18. **A type's rules live on the type.** `debug_win` owns the dev-route exclusion (comment at the loop);
    `PrizeStacks` documents both bag modes at the type; `EncounterReward::bonus_items` keeps its doc comment
    (granted only if the bag fits, never refuses the rest).
19. **Hot paths stay cheap.** No per-tick or per-packet cost: the roll runs once per won battle, and the new
    dev clearing runs only inside `realm win`. No state is cloned per tick.
