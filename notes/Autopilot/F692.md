## Review findings -> change

1. **BLOCKER, the pre-Loaded answer cloned the presentation before it read the guid.**
   `fotomat::requested_guid` parses the well-formed 156/2 once and returns its guid, and
   `application_preload::loading_reply` now checks it against `own_guid` **before** calling the
   presentation builder. The builder is injected as `FnOnce`; the `Gateway` method passes
   `current_look` + `player_presentation`, so names, appearance strings and `attachments_wire` are
   cloned only for the session's own, well-formed 156/2. A cost canary
   (`a_foreign_guid_never_builds_the_presentation`) panics if the closure runs for another guid,
   and `an_upload_never_builds_the_presentation` covers 115 and a malformed 115. The T519 notes'
   "no clone on a refusal" claim is now true; it was corrected there (checklist 19 and per-tick
   cost paragraph).
2. **MINOR, a 115 before `Loaded` was dropped by `gameplay_not_loaded` without the shape check.**
   `fotomat::is_upload` is now the exact six-byte shape (`u16 115` + `u32 CRC`), `fotomat::handles`
   is the one ownership predicate, and `Gateway::handle_at` uses `!loaded && fotomat::handles(..)`
   to answer/drop a Fotomat body itself, before the world gate. A valid 115 now reaches the pre-Load
   stage (trace `handled`, no reply, no state); a malformed 115 is not the notice and falls to the
   normal pre-Load path (trace not `handled`). `tests/fotomat.rs` pins both, and the binary login
   test sends valid and malformed 115s through `Session::dispatch_message` before world entry.
3. **MINOR, `parse_upload_crc` parsed a value no production code read.** Deleted. `is_upload` is
   the bool-only six-byte shape the review suggested; the CRC value is documented as reserved for
   the lead's pending-CRC ingress. The test that read the value now asserts the shape directly, so
   no test-only production surface remains.
4. **MINOR, the mapping-id order was encoded twice.** `style_cards::CUSTOMIZATION_ORDER` and
   `Look::customization_ids()`/`Look::portrait_ids()` now own the order once; `Gateway::
   player_presentation` and `Gateway::build_self_message` both call them, and the local import and
   inline order arrays are gone. `tests/style_cards.rs::portrait_ids_are_the_first_four_self_data_
   ids` pins all four fixture models: self-data is head, hair, skin tone, face paint, model
   customization and the portrait ids are its first four.
5. **MINOR [STRUCTURE], duplicate wire helpers.** Deferred; the reviewer marks it "not required
   for this merge". There is no shared `wire` codec in the crate; adding one now, for one module
   pair, would be a new abstraction with no second user. The per-module helpers stay.
6. **MINOR, the rate note named the wrong limiter.** Corrected in `notes/Autopilot/T519.md`: the

## Threat note (secure-code-guardian)

A hostile client can send any bytes as a 156/2 or a 115.

- **Visibility.** In-world, the reply exists only for the viewer's own character or one its
  directed AddPc already contains (`PlayerRegistry::presentation_of` -> `knows_character`).
  Pre-load, only the session's own guid is answered, and the guid check runs before the
  presentation clone, so a client cannot make the server clone a presentation for a guid it does
  not own (the review's concrete cost case).
- **Shape.** A 156/2 must be exactly the parsed body: family/subtype, u64 guid, provider length
  <= 16 and no trailing byte; the provider must be `Headshot` or `Portrait`. A 115 must be exactly
  six bytes; a malformed one is not `handles` and never reaches the Fotomat stage. All reads are
  bounds-checked with `checked_add`; the negative mapping ids are refused by `encode_reply`.
- **Refusals change nothing.** Refusals send no 156/3 and store nothing: the pre-load and route
  tests snapshot the gateway (and, in the route test, the target registry row) before every
  refusal and assert equality. No item, coin, reward, cooldown, menu or offer is consumed.
- **No new allocation before a bound.** `requested_guid` parses the 24-byte request without
  allocating; only an accepted self request builds the presentation and reply. No client field
  reaches `unwrap`, a file, or a shared tick `?`.
- **Rate.** No new limiter; see finding 6: the account application budget and the per-session
  packet/byte buckets bound these requests. Each reply is a few hundred bytes with the empty image.
- **No hex, no fs::write, no busy state** added; the reply carries only what AddPc already
  broadcasts.
