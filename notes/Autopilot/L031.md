4 and 6 handlers are kept; this wires them to the real session: selection ids now resolve, refusals

## What changed

- `src/housing_service.rs`
  - **127/1 resolves the decorate bar's id.** `fixture_asset` (now `&mut self`) binds an unbound
    selection id to itself through the existing `offer`, which accepts only an owned, single-unit
    item with a fixture row, on a lot the actor entered and may edit, in edit mode, with a nonzero
    id. 127/2 is unchanged: it still resolves only a bound id, so a 127/2 alone never places.
    A new binding replaces the actor's others (review fix): at most one live binding per actor,
    so a place/pickup loop cannot grow `selections`.
  - **127/53 rule on the type.** `Request::answers_with_denial` names the decorate requests (127/1,
    2, 3, 4, 6); `Gameplay::handle_housing` is the one denial path. The unused
    `handle_placement_for_client` and its `ServiceOutcome::denied` are deleted (review minor); their
    service tests now assert the exact `ServiceError`, and the 127/53 codec test encodes
    `ServiceError::denial_reply`, which production sends.
  - **Starter fixture (R).** `HousingContent.starter_fixture_item_id` (optional, `> 0`, must have
    a fixture row: checked at load in the new `adopt_content`, which also replaces the two copies
    of the starter/lot-row setup in `with_content` and `from_state_with_content`). `request_grant`
    stages the lot on a clone of the service, grants one unit (tint 0) last, and commits only if
    both succeed.
  - **`end_visit`.** Leave's "forget entered lot, edit mode, selections" is now a public method;
    a refusal (not entered) removes nothing.
  - Module and `fixture_item_list` docs: the selection id is the inventory item guid (evidence
    below); the old "never an inventory identity" note was wrong for 127/1. The same stale line is
    corrected in `src/housing_native.rs` and `notes/Research/Housing Service Integration.md`.
- `src/gameplay/housing.rs`
  - A refused decorate request sends the chat line **and** the 127/53 reason; the staged session
    and inventory are still dropped on every refusal.
  - After a successful request, `Inventory::adopt_state` (the W163 trade diff) turns the staged
    backpack into client updates: 38/4 when an item is placed, 38/2 when one is returned or
    granted. It validates before committing, and runs before the session commits, so a failure
    changes nothing. Skipped when the backpack did not change.
  - `abandon_house_for_reconnect` also calls `end_visit`, so edit mode and selections do not
    outlive a reconnect (before, the service still thought the player was inside and in edit mode).
- `data/content/houses.json` (CRLF kept: 1375 CRLF / 1375 LF): `"starter_fixture_item_id": 7466`
  and one R `client_evidence` line.
- Tests: `tests/housing_session.rs` (9 new tests through `Gameplay`, the `only_list` helper now
  finds the 127/39 among replies, `with_starter` models a pre-condo save with no fixture, the lot-1
  owner test asserts one block), `tests/housing_service.rs` (2 new tests; the content literal gets
  `starter_fixture_item_id: None`; the 127/1 test now expects `UnknownInstance` for an unowned id,

## Stacking check (brief step 3)

`Inventory::grant_with_tint` merges a unit into an existing stack of the same definition and tint
when the stack fits (`max_stack -1` = uncapped). So:
- A new character gets exactly one block (count 1); a repeat 127/23 grants none (tested).
- Pickup returns the unit as a fresh item; with no other block in the backpack it is count 1 and
  places again (tested: `pickup_returns_the_block_and_it_places_again`).
- **Open (lead or the owner decides before native use):** 7466 is buyable in the Coin Shop for 200
  coins (`stores.json`, tint group 1, no_sale). A purchase at tint 0 merges into the starter block
  as count 2, and so does a pickup while another tint-0 block sits in the backpack; place then
  refuses `StackedInstanceUnsupported`, so a paying player loses decorating until stack-aware
  placement is decided. Retail held blocks in stacks (captured 7466 x10, 7462 x34), so retail
  placed from stacks; stack-aware placement is a design follow-up, not done here.

## Security

Trust boundaries touched:

- **127/1 selection id (hostile u32).** It can only bind an item in this character's own live
  inventory: `offer` checks the entered lot, owner or edit permission (`can_enter`), edit mode,
  nonzero id, the instance in this character's backpack, count 1, and a fixture row. Bindings are
  keyed by actor, live only in the session (cleared on enter, leave and now reconnect), and never
  persisted. No other character's data is reachable.
- **Selection growth (review blocker, fixed).** The first version's claim that bindings were
  "bounded by the number of owned items" was false: place never unbinds and pickup returns the
  unit under a fresh monotonic id, so a 127/1 -> 127/2 -> 127/3 loop added one dead binding per
  cycle (about 66/s within the 200 packets/s budget), and `Gameplay` with this map is cloned
  several times per packet on the single-threaded gateway. Now a successful new 127/1 binding
  removes the actor's others, so production holds at most one binding per actor (only test code
  calls `offer` directly). A refused 127/1 leaves the existing binding alone. Tested by
  `a_new_127_1_retires_the_previous_selection` and canary 7.
- **127/2 (hostile).** Unchanged: needs a binding made by 127/1 in this visit; placement is staged
  and the item is consumed last (`Inventory::consume` is atomic).
- **Refusals.** Every refusal drops the staged session and inventory (`handle_housing`), so it
  changes nothing, including session-only state (edit mode, selections); tested byte-equal on the
  serialized `GameplayState` for 18 refusals. The 127/53 text is a fixed literal from
  `denial_message`; it echoes no id, so it is no oracle beyond the player's own backpack, which
  the client already knows.
- **Starter grant (economy).** Server-chosen item from content, never client input; one unit per
  (character, property) because it rides the lot grant, which is idempotent on the saved lots
  (tested: a repeat 127/23 adds none). The block is no_sale and NO_TRADE, so alts cannot sell or
  funnel it. Lot and unit commit together (tested with a refusing stock).
- **Inventory sync.** `adopt_state` sends only the diff between the live and staged backpack of
  this character, validated before commit; no client value flows into it.
- **Reconnect.** `end_visit` closes the stale-visit gap: after a reconnect, decorate requests
  refuse with NotInHouse until the client enters again (tested).
- **Saves.** Unchanged path: lots and backpack are one `GameplayState` snapshot written by the
  existing atomic `character_store::replace_bytes`; reload re-runs the conservation check (placed
  instance not in the backpack). No secrets, player names or chat text in code, logs, tests or
  notes.
