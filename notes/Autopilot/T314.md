## Verify-first observations (confirmed in this worktree)

- **Loader rules.** `QuestEngine::from_split_content` already rejects duplicate
  quest ids, a quest missing from the `jobs.json` `quest_ids` union (or a job
  listing an absent quest), a prerequisite that is unknown or self, duplicate or
  zero NPC ids, a quest bound to two givers, an NPC listing a quest under a
  different giver, and empty runtime provenance. `new_with_disabled`'s
  `validate_definition` bounds coins to `i32::MAX`, item definitions/counts to
  positive `i32`, the job-XP total to `i32::MAX`, and `valid_objective_kind`
  bounds visit geometry (finite `|x| <= 1e6`, radius `0.1..=1000`) and positive
  objective targets. `definition_from_content` rejects an unknown positive
  job-XP profile.
- **What the loader does not reject.** It does *not* reject an enabled record
  with empty objectives (`QuestEngine::is_enabled` hides it instead) and it does
  not inspect standard-goal provenance. `scripts/content_check.py --strict`
  covers both raw-JSON rules (enabled quest must have objectives; objective
  provenance); the new audit asserts `engine.is_enabled` for every enabled
  record and deliberately does not duplicate the raw provenance rule.
- **Drawability.** `NpcVisibility::load` draws only positioned
  `placement: "legacy_data"` regional rows and `npc_spawns_extra.json` rows; it
  maps regional `npc_id -> npc_id` and extra `spawn_guid -> content_key`. A
  `poi_anchor`/`unanchored`/`captured` regional row with no extra spawn is not
  drawable. The audit adds the "positive model/name" requirement (a model-0,
  name-0 AddNpc has no body) and cross-checks every candidate through
  `NpcVisibility::content_key`, so the audit cannot claim an actor the 35/2 path
  never sends.
- **Enabled count.** 41 records are enabled in `data/content/quests/*.json`
  (`enabled` absent or true), not the brief's stale 39: 39 are reachable and 2
  are enabled-by-default behind disabled prerequisites. The brief's "39" matches
  the reachable count; the test prints both and never hard-codes either.
- **Unreachable records (reported, not turned on).** `3020014` (Blacksmith)
  requires disabled `3020013`; `3100020` (Miner) requires disabled `3100019`.
  Both have drawable givers and targets; only their reward rows are empty, and
  the reward gate does not grade them.
- **`3130032` (Postman).** Giver `9000000173` (Postmaster Lane) is a drawable
  `legacy_data` row in `npcs/shrouded_glade.json` with the `quest_giver` role and
  lists the quest in `quests_given`; the one real objective is a Talk to
  `9000000172` (Postchug Runalug), also a drawable `legacy_data` row. The title
  is 141829 (>0), there is no prerequisite, and the reward was empty. The guide
  row 29 reward cell is `unknown`.
- **Giver listing.** Eleven enabled quests are not repeated in their giver NPC's
  own `quest_ids_given`/`quests_given` rows (e.g. `3000009`, `3010003`,
  `3050004`, `3160003`). That is not a break for this gate:
  `npc_interaction::offerable_quest_for_talk` unions the NPC row with
  `QuestEngine::quest_ids_for_giver`, and the split loader checks the reverse
  binding (an NPC may not name a differently bound giver). The audit asserts the
  engine listing, which is the offer path's other half, and the NPC row's
  `quest_giver` role.
- **Pre-existing checker warnings (out of scope).** `content_check.py --strict`
  reports 679 warnings, unchanged before/after: 444 `text_raw_hash`, 208
  `npc_ref_unknown` (out of scope), 19 `guid_shared_actor`, 3
  `text_missing`, 2 `item_default_undefined`, 2 `client_item_undefined`, 1
  `item_loader_limit_near`. This gate does not re-audit those raw-JSON rules.

## (R) reconstructed rules

- `(R)` `3130032` reward: 5 coins use the W110/T202 small-referral fallback and 5
  Postman (profile 4) job XP follows the T202 one-Talk referral rate. The guide's
  reward cell is unknown; a single row is used. No item is granted, so the quest
  creates no free, sellable or re-grantable gear.
- `(R)` reachability is structural: an enabled quest is reachable when every
  prerequisite (transitively) exists and is enabled. Level/job/membership gates
  stay the engine's `requirement_denial` (covered by `quest_offer_gates`); this
  gate does not simulate offers or T281's giver order.
- `(R)` drawability includes a positive model or name id on a `legacy_data` row
  because AddNpc with both zero has no body; the production loader would still
  map its content key, so the audit is deliberately stricter than
  `content_key` alone.
- The client evidence above beats the brief's shorthand; no brief claim was
  contradicted by IDA on the paths this test asserts.

## Tests (`cargo test --test enabled_quest_reachability`, 4 passed)

1. `every_enabled_quest_has_a_drawable_giver` - loads the real split engine and
   NPC visibility; for every enabled record asserts the engine kept it
   (`is_enabled`), the giver has an `npcs/*.json` row with the `quest_giver`
   role, is drawable, and is not a `poi_anchor`-only row. Also asserts every
   enabled id was enumerated (no silent skip) and the count is non-zero.
2. `every_talk_target_and_visit_point_resolves` - every `talk_to_npc` /
   `interact_actor` target exists as a drawable content NPC; every
   `visit_position` (and explicit `reach_poi` geometry) is finite with a radius
   in `0.1..=1000`; every `defeat` `model_id`/`count` and `collect_item`
   `item_id`/`quantity` is positive; every prerequisite id exists. Classifies
   every enabled quest exactly once as reachable or unreachable, prints the
   unreachable reasons, and asserts no unreachable quest is graded and no
   reachable quest has a disabled direct prerequisite.
3. `every_reachable_enabled_quest_has_a_real_reward_and_title` - over the
   reachable enabled set: `title_string_id > 0`; at least one grant has non-zero
   coins/items/job XP; coins and job-XP totals fit the loader's `i32` bound and
   item ids/counts are positive; the quest is in `quest_ids_for_giver(giver)` and
   the `jobs.json` `quest_ids` union; `empty_reward_quest_end_packet` returns
   `None` and `quest_end_packet` encodes the 49/13. Pins `3130032` in the graded
   set, so disabling the fixed record cannot make the gate pass silently.
4. `a_malformed_enabled_row_is_rejected_or_reported` - a clean scratch fixture
   is green, then each planted defect is caught: a missing giver is reported by
   the giver audit; an empty reward on a reachable quest is reported; a disabled
   prerequisite is classified unreachable (recorded, not failed for its
   deliberately empty reward); an absent prerequisite and a non-finite visit
   point are rejected by the production split loader. Fixtures are built under
   `CARGO_TARGET_TMPDIR` and removed on drop; the shipped tree is untouched.

## Threat note (secure-code-guardian)

Attack surface: no new client input path was added. The one reachable effect is
the `3130032` reward any client can earn by completing the server-driven Talk
objective and 49/14 turn-in.

- The reward is server-authored content (5 coins, 5 profile-4 XP, no items). No
  client amount, item id, result or score reaches the payout; the existing
  offer/accept/end-screen gates (`offer_denial`, `pending_offer`, the saved
  `pending_turnin`) are unchanged and already covered by `quest_offer_gates`,
  `quest_engine` and `app_fuzz`.
- The quest has no prerequisite, no job/level gate and no item grant, so it
  cannot be re-granted for profit, cannot be sold, and cannot leave a stuck
  inventory. A 49/14 replay settles only the saved pending turn-in once (the
  existing idempotency tests).
- The audit itself is test-only and read-only over shipped content: no save, no
  session, no shared state; test 4 writes only under `CARGO_TARGET_TMPDIR`.
- `content_check.py --strict` stays at 0 errors, so the reward's provenance and
  profile-4 key pass the authored-JSON audit.

## Checklist

1. **A refusal changes nothing.** Not applicable to production: the slice adds
   no request handler or transaction. The audit is read-only; test 4's loader
   rejection is a construction-time refusal with no state. The reward gate only
   reads the engine and ignores refusals.
2. **Rollback covers all state.** No transaction, `Rc`/`RefCell`/`Arc` or side
   table was added. The audit holds only test-local parsed values; the scratch
   fixtures are private directories. No production rollback path changed.
3. **Apply deltas, never restore snapshots.** No payout code changed. The
   existing turn-in applies the content grant to live inventory/profiles;
   `3130032` grants 5 coins and 5 profile-4 XP as deltas once.
4. **Busy rules are mutual.** No activity, `Occupation` variant or busy check
   was added. The Talk/turn-in path uses the existing NPC router and busy table.
5. **Every entry path is gated.** No new entry path. The audit proves the
   existing reachable set's givers/targets/rewards; the offer path still runs
   `offer_denial` and the accept recheck. Level/job/membership gates are covered
   by `quest_offer_gates` and `quest_save_tolerance`, not changed here.
6. **Reachable in production, tested through it.** The audit calls
   `QuestEngine::from_split_content`, `world::NpcVisibility::load`,
   `NpcVisibility::content_key` and `quest_end_packet`; test 4 drives the
   production loader for the scratch fixtures. It does not call a test copy of
   the loader. The audit does not send packets (the shipped chain suites own the
   packet path).
7. **Survives reconnect.** No persisted state changed; `3130032` has no new
   pending/offer/location state. The reward is part of the content definition
   and the completed quest ledger is the existing save.
8. **Every exit path restores the player.** No occupation/location lock was
   added. The one-Talk quest opens the existing pending end screen and clears it
   on 49/14; the audit is read-only and cannot leave a session mid-activity.
9. **Economy safety.** The only new grant is 5 coins + 5 profile-4 XP (no items),
   server-authored in content. It cannot be sold, re-granted, or driven by a
   client amount/item id; the existing offer/accept/49/14 gates stop replays and
   forged turn-ins. The audit validates every reward grant it reads (positive
   item ids/counts, known profile keys, i32 totals).
10. **Wire format matches the client reader exactly.** No wire bytes changed.
    The audit only calls the existing 49/13 encoder and asserts the non-empty
    bundle; the reader `00c7b990` was decompiled this run and matches the
    encoder's actor u64 / quest / end text / bundle / float order. The 35/2
    AddNpc reader `00921a10` was decompiled and matches the draw fields the
    audit requires (actor u64, name id, model id). No new field, opcode or
    enum.
11. **Unique ids.** No new instance, GUID or lifecycle id was created. `3130032`
    is an existing content id; the reward row adds no new item, instance or
    actor id, and the audit only reads ids. No id is reused or aliased.
12. **Others see changes.** The content fix changes a reward-only row; it does
    not change outfit/job/mount/spawn visibility. No broadcast path is touched.
13. **Content works end to end.** The audit proves the reachable 39 include
    `3130032` with a positive title and a non-empty, encodable 49/13 reward;
    `3130032`'s giver and Talk target are drawable content NPCs with the
    `quest_giver` role. The existing chain/offer suites own the live accept and

14. **Values live in data.** The reward values are in `postman.json`, not

15. **Canaries break production code.** Both canaries edited the shipped

16. **Hands off session plumbing.** `src/bin/osfr-gateway.rs` and

17. **One player's error never stops the server.** No shared tick or fanout code
