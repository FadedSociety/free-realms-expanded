## Security Note

A hostile client can send 26/24 with any i32 recipe id, a wrong-length body,
repeated starts, or a completed movie sequence after an admin placement reload
moved the station. Each is refused before state changes:

- `decode` requires exactly eight bytes; any other length is a rejected packet.
- The client supplies only the recipe id. Learned state, active job, rank,
  exact owned ingredients, station proximity and idle services are server
  facts in `recipe_book::start`; a missing service is `Unavailable`, not a
  panic.
- 26/24 checks `Gameplay::activity_busy()` (the shared occupation `start`
  gate), and `recipe_book::start` re-checks `in_activity` and all three
  services. A replayed or overlapping start returns `Busy` before any service,
  inventory or station mutation; a session handles one request at a time.
- `GameWon` derives the transaction from the server recipe table after four
  validated rounds; the client-reported quantity is bounded but never used for
  the grant. Duplicate `GameWon` returns no transaction.
- Completion re-checks the active job and a station resolved from current
  opening actors and placement models. After a move/remove, `apply_smelting`
  returns `Err` before consuming or granting; the gateway discards its staged
  clone, so the snapshot is unchanged and neither save flag is set.
- Start refusals carry the existing Busy/Move closer chat. The moved/removed
  station completion is refused with `Err`, so the gateway discards the staged
  clone and sends no chat; the client closes the movie or reconnects. No
  refusal touches inventory, coins, attempts, completions, cooldowns or
  placements.
