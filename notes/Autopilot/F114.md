## What changed

- `src/pets.rs`: `PetList` (53/5) writes one list key followed by one record
  whose first field is the pet id. The duplicate key that shifted every later
  field is gone (`00b5aea0`, `00912cf0`).
- `src/pets.rs`: subtype 4 is decoded as the client serializer's fixed 5-byte
  body (`00b5a650`: u32 id plus action byte). Action 0 dismisses the owner's
  active pet and never selects a pet, because `Pet.Dismiss` (`00c07420`) sets
  only the action byte (`00c07454`); the id word is uninitialized stack memory.
  Action 1 still requires a non-zero pet id. The one-byte short form is refused
  as the wrong length.
- `src/pets.rs`: actor packets now precede activation. `wire` emits removal and
  creation before `PetActive` (`00b58bd0` -> `00b54080` resolves the actor
  immediately), and the item-adoption response is ordered inventory replies,
  actor creation, roster (`PetList` with its active pair), then `PetActive`.
- `src/pets.rs`: subtype 32 fields are the client `ItemRecord` definition id
  and tint (`ItemRecord` +0x04/+0x08; `00a1ec00` passes both to `00b60110`).
  The server resolves one owned instance by definition and tint; the old
  cross-field fallback is gone, so a mismatched pair cannot consume a different
  item.
- `src/pets.rs` and `data/content/pets.json`: the actor speed is package
  content (`movement_speed.speed`, validated finite and in 0.1..=20) instead of
  a hardcoded 5.0; `PetPresence.speed` feeds `AddNpc`.
- Tests: `tests/pet_routing.rs` decodes the whole `PetList` independently with
  exact packet consumption, asserts packet order for summon, switch and
  adoption, and adds the wrong-tint refusal (inventory, roster, actor and saved
  bytes), the tunable-speed test and the serializer-shaped dismiss.
  `tests/pet_bots.rs` and `tests/pet_wired.rs` send the serializer-shaped
  dismiss; `tests/app_fuzz.rs` keeps both the valid and truncated forms as
  seeds.

## Recovered facts and provenance

- `00b5a650` writes the dword at object +0xc and the byte at +0x10 for every
  subtype-4 sender (`00b60080`, `00b601a0`, `00c07420`, `00b60610`).
- `00c07420` (`Pet.Dismiss`) executes `mov byte ptr [esp+0x14], 0`
  (`00c07454`) and never writes the id at object +0xc; `00b60610` (forced
  dismiss) sets `local_10 = 0` the same way. Evidence:
  `lab/decompiled/client/FreeRealms/pseudocode.c` and
  `python -I scripts/native_map/nmq.py dis 00c07420 260`.
- Subtype 32: `00b60110` writes its two parameters; its only caller `00a1ec00`
  pushes `ItemRecord+4` then `ItemRecord+8` (`00a1f2c2` to `00a1f2d2`).
  `notes/Build Guides/Gameplay/Items and Inventory.md:50` records the
  `ItemRecord` definition at +4 and tint override at +8.
- `PetList`: `notes/Build Guides/Gameplay/Pets.md:143` (i32 count; a u32 key
  plus record per pet; active id and actor pair after the records); the record
  first field is the i32 id read by `00912cf0`.

## Reconstructed rules (R)

- (R) One active pet per owner; the actor id is derived from the owner.
- (R) Dismissal ignores the id word: any action-0 subtype-4 request dismisses
  the sender's active pet. This follows the uninitialized client field and can
  only affect the sender's own session.
- (R) Actor speed bounds 0.1..=20 and the 5.0 default are local policy.

## Open gaps

- Review blocker 4 (atomic adoption persistence) is not fixed. It needs one
  envelope write that carries both the character snapshot (consumed inventory)
  and the top-level `pets` payload, which requires a new
  `game_store::save_with_pets` (or equivalent) and replacing the two-write
  sequence `save` then `save_pet_roster` in `Session::commit_outcome`
  (`bin/osfr-gateway.rs`). `game_store` and the session commit are lead-owned
  under this task's off-limits list. The diff keeps the existing two writes; a
  crash or second-write failure can still leave the item consumed without its
  pet.
- `src/restoration/piece_091.rs` is a separate, unrouted reference codec that
  still models the short one-byte forced-dismiss body. The live route no longer
  accepts it; correcting that artifact and its recorded round trips is a
  separate task so this diff does not rewrite another piece's evidence.
- The native client was not run for this diff. Actor ordering, dismissal,
  adoption and the list layout are client-reader-derived, not traffic-verified.

## Security-relevant decisions

- Dismiss/action-0 ignores the client id entirely and can only dismiss the
  sender's own active pet.
- Item summoning resolves an owned instance by definition and tint, never by a
  pet id, which removes the cross-field consumption path. Refusals leave
  inventory, roster, actor and the save file unchanged.
- No security-owned module, Cargo manifest or launcher file was touched. No
  player names or chat text were added.

## Lead: atomic adoption persistence (2026-10-18)

Blocker 4 is fixed by the lead (game_store is lead-owned). `game_store::save_with_pets` writes the
character snapshot and the pet roster as ONE document through the existing atomic
`replace_bytes` (temp file, fsync, rename), keeping housing. `PetService::save_with`,
`Gameplay::save_with_pet_roster` and `Gateway::save_with_pet_roster` carry it to
`Session::commit_outcome`, which now uses it whenever `pets_changed` instead of `save` followed
by `save_pets_state`. A crash can no longer keep a consumed adoption item without its pet, or the
pet without spending the item. Test: `tests/game_store.rs::save_with_pets_writes_character_and_roster_in_one_document`
(combined content, housing kept, later plain save keeps the roster, refused write leaves the
file byte-identical). Gates: pet_routing 12, pet_wired 5, pet_bots 2, pets 10, save_schema 5,
app_fuzz 13, game_store 3, `cargo test --no-run` all targets.

## Lead: adoption shortcut regression (2026-10-18)

An adversarial review (3 independent lenses, each confirmed by 2 skeptics) found that the F114
`summon_by_item_owned` change matched an owned pet by adoption-item definition and re-summoned it,
so a second certificate of an owned species was never consumed and could never be redeemed
(Pets.md:20 allows duplicates). Fixed: every owned adoption item adopts a new pet and is consumed;
an owned pet is summoned by id (subtype 3). The read-only `PetService::summon_by_item` (same wrong
rule, no live inventory) is deleted; the read-only `handle` refuses subtype 32, and its now-unused
`inventory` parameter and the dead test helper are removed. Test:
`each_adoption_item_adopts_a_new_pet_even_when_the_species_is_owned` (two certificates -> two
pets, each consumed; none left -> refused, roster and active pet unchanged).
