## Result

The stress harness can now run from a playtest bundle, fights only always-on field
enemies, reports knockouts and purchases honestly, and reads the gateway's new
per-window tick timing. No load was generated and no native client was run.

1. **`run.py --bundle DIR`.** One table, `BUNDLE_LAUNCH`, maps the bundle inputs at the
   paths its README launch lines use (`make_bundle.py` `readme`): `--reference`,
   `--content`, `--terrain`, `--client-locale`, `--resources login-resources`,
   `--server-id-file server/server-id.bin` and `OSFR_GATEWAY_STARTUP_SNAPSHOT`
   (`startup/startup.json`). The identity stays `run_dir/identity.json`, just as the README
   keeps it in `$runtime`. A Python test checks every entry against the README text, so
   if the README changes, the test fails. The bundle content is copied into the run folder, and
   the (R) wallet seed is applied to that scratch copy only. Nothing is written into the
   bundle: the server id is read in place, and the cleanup step deletes only files in the run folder.
   The binaries still come from `git archive HEAD`, so the report prints the bundle's source
   revision (its README "Source Git revision" line) under the build commit and says whether
   they match. `OSFR_GATEWAY_STARTUP_SNAPSHOT` is set process-wide on purpose: the save-load
   verify gateway (`sample_save_load`) needs it as well as the main one.
   Without `--bundle`, the run works as before (HEAD content plus the round70 overlay).
   The scenario refuses content without `item-catalogue.json`, `field_enemies.json` or
   `stores.json` and names the missing files.
   `--scenario-only` (it needs `--bundle`) prints the chosen scenario as JSON and exits
   before it builds anything or creates a run folder.
2. **Enemies.** The 3030007 filter is gone. A row qualifies only with empty `quest_ids` and a
   3-element position. The harness takes the 8 rows nearest `start_position` (non-boss first;
   for stacked rows at one spot, the lower level, then the lower damage). It then orders them
   non-boss, lowest level, then lowest authored damage first. Level comes first because the
   authored `damage` and `max_health` are level-one baselines that `encounter/field.rs`
   (lines 220-225, at load) scales: damage × 1.75^(weapon_tier(level) − 1), health ×
   level_health(level) / PLAYER_MAX. Each bot gets one of them round-robin (`index % n`) and
   uses that target for its opening fight and every later enemy visit. The quest pick, the
   vendor pick and the walking pattern are unchanged. The report line now says "N always-on
   field enemies (no quest gate) nearest the start, round-robin per bot". Each scenario enemy
   carries `level`, `damage` (authored), `boss` and `quest_ids`, so the scenario-only output
   can be checked.
3. **Knockouts.** `knockout_summary` counts knockouts from log lines the bot already prints
   (`<- family/sub len=N`), with no protocol change:
   - 41/125 means knocked out;
   - 41/126 means revived;
   - 36/1 counts as an ability refusal while down if it falls between the two, and as
     another refusal otherwise.

   The save-load logs give the number of knocked-out characters that reloaded. Each one
   counts as reloaded, because `loaded` still comes from the exit code alone. That number is
   a lower bound and the report says "at least": the save-load script is `wait 200` then
   `quit` (unchanged, per the brief), so the bot can leave before the re-sent 41/125
   arrives. The report puts all this on its own "Knockouts (explained, not protocol errors)"
   line, which also warns that the 15 s auto-revive (`encounter/revive.rs`
   `revive_at_safe_location`, `AUTO_REVIVE_MS`) moves the character while its bot walks on,
   so the movement refusals that follow land in `security.jsonl` and
   `refusals-and-errors.log`, not in the knockout count. A downed
   bot's basic attack produces no reply at all (`encounter.rs` `attack` returns an empty
   outcome when `player_health == 0`).
4. **Purchases.** `save_summary` now sets `purchase_persistence` to one of four values:
   `persisted`, `lost`, `unmeasured` (fewer than 2 phase samples) or `not purchased`.
   This replaces the old boolean, which counted a single sample as a failure. The broker
   exit expression moved into `run_failed()` and now also requires every save to be
   `persisted` with non-negative coins, so exit 0 covers every gate. In a short run
   (under 60 s, one phase) the purchase is therefore unmeasured and a broker run exits 1.
   That is deliberate: such a run does not prove the gate.
5. **`tick_stats`.** A new module, `src/bin/osfr_gateway/tick_stats.rs`, is enabled with
   `--tick-stats-seconds N` (0 is off and the default; otherwise 5..=600; anything else is
   refused). `run()` reads the window first, before `Options::parse` and before
   `Server::new` binds the socket, and builds `TickStats` after the server is up, so the
   first window starts with the server.
   - Each window keeps two fixed-capacity sample buffers (steps and ticks). Their capacity
     is window × expected rate, capped at 65,536 samples. Once a buffer is full, a
     reservoir sample replaces entries; the counts and the max stay exact.
   - Each window emits one `tick_stats` event carrying `window_s`, `sessions`, `steps`,
     step p50/p99/max µs, `ticks` and tick p50/p99/max µs.
   - A step is the whole `Server::step`, including its socket wait of up to 10 ms.
   - A tick runs from the `tick_due` decision to the end of that step: the shared-field
     simulation, the session ticks and the flush.

   The hub gets only the flag, the field, its init, two `Instant` captures and one
   `record` call. In `run.py`, the main gateway gets `--tick-stats-seconds` (default
   60). The report adds a "Gateway tick time" table, one row per window, followed by the
   worst p99 and max. The final JSON gains `tick_worst_p99_us`, `knockouts` and
   `purchase_unmeasured`.
6. **`check_bundle.py --bin-dir DIR`** reuses an existing release build. Before it verifies
   anything, it checks that `osfr-login`, `osfr-gateway` and `osfr-bot` are present and
   refuses an incomplete set. Without the flag, it builds as before.

## Checklist

1. Refusal changes nothing: the brief adds no gameplay request path. The CLI refusal of a bad
   window happens at startup, before any other option is parsed and before the socket binds
   (the debug gateway given only `--tick-stats-seconds 4` prints the window error, exit 1). `--bin-dir` refuses before it
   verifies or runs anything (canary E).
2. Rollback: there is no transactional state. `TickStats` lives on `Server` outside
   `SharedWorld`, and nothing about it is staged.
3. Deltas, not snapshots: does not apply.
4. Busy rules: does not apply (no activity).
5. Entry paths: the timing sits in `Server::step` itself, so every step is timed. The flag is
   read in `run()`, the only production entry point.
6. Production path: the gateway test drives the real `Server::step`, and the harness tests
   call the real `run.py` and `check_bundle.py` functions.
7. Reconnect: does not apply. The purchase gate itself is about reconnect persistence; it is
   now scored, not changed.
8. Exit paths: does not apply.
9. Economy: the wallet seed is a scratch-only (R) edit in the run folder, never written back.
   The bundle is only read.
10. Wire format: no wire change. The knockout counting reads the server's 41/125, 41/126 and
    36/1, with client handlers cited above.
11. Unique ids: does not apply.
12. Others see changes: does not apply.
13. End to end: scenario-only against a real bundle lists 8 live (always-on) enemies. A real
    stress run is the lead's acceptance step (broker-login-stress-acceptance).
14. Values in data: the window is an operator flag with bounds 5..=600, as the brief asks.
    The rates only size the buffers.
15. Canaries break production code (A-I above), not the tests.
16. Session plumbing: untouched. `step` gains only the timing captures and the record call
    after the session loop.
17. One player's error: `record` cannot fail or panic. The durations saturate (`u32::MAX`,
    `duration_since` floors at 0) and indexing uses `get_mut`/`get`.
18. Type rules: `Series` owns its capacity, sampling and summary. `TickStats` owns the window,
    and its docs say what step and tick cover.
19. Hot path:
    - Off (the default): two `Instant::now()` per step and an early return.
    - On: one more `Instant::now()` and one store into a preallocated buffer (no allocation).
      Each window sorts at most 65,536 + 1,200 `u32`.
    - Memory: at most 256 KiB + 4.7 KiB per gateway.

## Threat note (secure-code-guardian)

Nothing here parses client input. The new inputs are operator CLI paths:
- `--tick-stats-seconds` is bounded, and a bad value stops startup.
- `run.py --bundle` reads the bundle and copies content into the run folder. It never
  writes into the bundle.
- `check_bundle.py --bin-dir` runs binaries the operator named, with the same trust as
  the build it replaces.
