## Reconstructed rules (R)

- **(R) Close then page.** The original server's NPC scripts did not ship, so no capture of a multi-page
  greeter exists. The client code proves a close is needed for `Show` to rebuild the window; answering
  `[26/4, 26/3]` is this server's reconstruction of the original flow.
- **(R) One echo per page.** The client echoes the close automatically (above), and the reliable channel
  delivers that echo before the re-shown dialog can send its next 26/6, so the first 26/4 after a page
  is the echo and the next one is the player leaving. The flag is a bool for that reason.
- Response ids stay T773's: 310.. for pages, 300 Goodbye, 301 quest row. The row layout and the
  five-button budget are unchanged.

## Threat note (secure-code-guardian)

Attack surface is unchanged: the client-chosen 26/6 row and the 4-byte 26/4 close.

- **Any i32 as the row.** `explainer_page` matches only the pages the open dialogue recorded. An
  unoffered value returns `None`, the ordinary close answers, and no body id, item, coin, quest or
  position changes (`a_refused_row_changes_no_saved_state_and_the_npc_reopens` snapshots the state).
- **A page id with no dialogue open.** `explainer_page` needs an active interaction, so the same
  ordinary close; the test's fresh game case asserts an identical snapshot.
- **Another greeter's page id.** Pages come from the recorded rows of the dialogue whose menu is open,
  so another NPC's page is not reachable through this one.
- **A hostile 26/4.** With no page replay pending it closes the interaction exactly as before. With one
  pending it consumes the bool and the interaction stays open: the attacker can keep their own dialog
  session answerable, which is the intended behavior of the feature they already had (they can Talk
  again anyway). It never clears or grants a quest, item, coin or role, and it cannot touch another
  player's state.
- **Malformed lengths.** 26/4 must be exactly 4 bytes (existing `Err`); 26/6 is the existing 8-byte
  reader; page content is validated at load (`validate_npc`: at most four pages, non-zero ids).
- **Flooding.** Each accepted page costs one 26/3 encode and no save, no coin/item and no tick work;
  per-account packet limits are unchanged.
- No secrets, no client files, no external text: the diff carries only function addresses and stock
  locale ids already cited by T773.

## Checklist

1. **A refusal changes nothing.** `a_refused_row_changes_no_saved_state_and_the_npc_reopens` snapshots
   `Gameplay::state()`, sends an unoffered row (`i32::MAX`), asserts the ordinary 26/4-only reply and an
   identical snapshot, then Talks again and gets the same rows. The close echo also asserts an identical
   snapshot. No new refusal path: the page branch is read-only and runs on the gateway's staged clone.
2. **Rollback covers all state.** The only new state is `OpenDialogue.close_echo_expected`, inside
   `ActiveInteraction` inside the cloned `NpcInteraction`, cloned with `Gameplay`; `gateway.rs` drops the
   staged clone on `Err` (the flag set before a failed encode is not committed). No `Rc`/`RefCell`/side
   table; the content `Arc` is immutable.
3. **Apply deltas, never restore snapshots.** N/A: no payout or exit; the reply only selects locale ids.
4. **Busy rules are mutual.** N/A: no new activity; `busy_interaction_refusal` still gates every 26/8
   and a page click starts nothing.
5. **Every entry path is gated.** Graph: the only player-facing Talk path is `talk_to_npc` ->
   `npc_interaction::dialogue_rows` -> `record_dialogue`; a page click adds no second path. The page id
   must be one the open dialogue sent. Range was checked at 26/10; a page click only re-reads stock
   locale text from the recorded rows (T773's rule, unchanged).
6. **Reachable in production, tested through it.** The suite drives `Gameplay::handle_in_world`

   bundled quest catalogue bound; it does not call builders or `explainer_page` directly.
7. **Survives reconnect.** N/A: nothing persists. Pages are content; the recorded dialogue and the echo
   flag are session state. A reconnect re-reads the same rows.
8. **Every exit path restores the player.** Goodbye (300), an unoffered row and a real player close
   (a 26/4 that is not the expected echo) clear the interaction; each exit reopens with a fresh Talk

9. **Economy safety.** No coins, items, XP or rewards. The server sends only content locale ids; a client
   cannot choose a body id (the page must be recorded) and cannot name another player.
10. **Wire format matches the client reader.** No new shape: the same 4-byte 26/4 (`009f5760`, handler
    `00aa0870`) and the existing 26/3 layout (`00a9ef10`, `00a9b480`, `009f5ae0`). The suite decodes with
    the production `decode_dialogue_26_3` and asserts the close bytes equal
    `encode_dialogue_close_26_4()` and come first.
11. **Unique ids.** No instance/GUID created. Page ids stay 310.. and are disjoint from 300/301.
12. **Others see changes.** N/A: only the clicking player's dialog; nothing is broadcast.
13. **Content works end to end.** Asserted final outcomes: the page body id, the rows after the click,
    another page, the quest row's decoded 49/1 with the greeter's own quest id, and Goodbye's close.
    Native look is the lead's acceptance step.

    the second page row got the ordinary close and 1 test failed. Both were reverted and the diff

16. **Hands off session plumbing.** No edit to `src/bin/osfr-gateway.rs` or `gateway.rs`.
17. **One player's error never stops the server.** No shared-tick or other-player code. The new paths

18. **A type's rules live on the type.** `OpenDialogue.close_echo_expected` carries the rule in its doc
