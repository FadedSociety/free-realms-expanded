# L049: character name parts and folded uniqueness (lead)

New character names now need every part (first and last, displayed and temporary pair) to be letters
joined by single separators. Uniqueness compares a folded key, so an accented or cased look-alike of a
saved name is taken. Loading is unchanged.

## What changed

- `src/account.rs`: `latin_name` became `new_name_part`. It keeps the L022 Latin character set and adds
  the part rule: `name.split([' ', '-', '\''])` must give only non-empty pieces. That refuses a leading,
  trailing or doubled separator ('--', apostrophe-hyphen, '-ab', 'ab-', 'a--b', 'a  b', 'a -b'). The
  brief's "at least 2 letters" follows from this plus the existing 2-character minimum (one piece of 2+
  letters, or 2+ pieces of 1+ letter each). It cannot fail separately, so it has no separate check or
  canary. Both callers (`valid_client_name` for create, `check_name_status` for check-name) use it, so
  the temporary pair follows the same rule. A refusal uses the existing statuses: create 7 (InvalidName),
  check-name -1 (Invalid), which `login.rs` rewrites to 4 as today.
- `src/account_store.rs`:
  - `name_key(part)` folds each character through `LATIN_FOLDS` (38 rows of base and letters covering
    U+00C0..=U+024F); anything else lowercases.
  - Folding comes before lowercasing because 'İ'.to_lowercase() is 'i' plus U+0307.
  - `character_name_taken` compares `name_key` on both sides.
  - `insert_character` and `adopt_legacy_character` now pass the raw name pairs (`name_pairs`). Before,
    they passed pre-lowercased strings, which would have broken the 'İ' fold.
  - `name_keys` (lowercase only) is now used only by `validate`, which runs on load and on save, so
    existing saves whose names fold together still load and save.
- `tests/account.rs`: three new tests, one per brief section (below).

Unchanged: the wire encoding (UTF-8 strings), the length limits (2..=14 per part, 15 combined), the login
flow, `identity::valid_name` and `CharacterIdentity::validate`.

### Fold table provenance (R)

- `LATIN_FOLDS` was generated from Unicode data, then checked against the source. The generator and
  checker are scratch scripts in `%TEMP%\lead-L049\` (`gen_fold.py`, `audit_table.py`).
- The generator applies these rules to every alphabetic code point in U+00C0..=U+024F:
  1. NFKD with combining marks removed, when the result is ASCII letters (é to e, ǆ to dz, ĳ to ij, ſ to s).
  2. Otherwise, a Unicode name of the form `LATIN CAPITAL|SMALL LETTER|LIGATURE <1-2 letters> [WITH ...|DIGRAPH]`
     (ł to l, đ to d, ø to o, æ to ae, œ to oe, ƀ to b).
  3. Manual rows: ð/Ð to d, þ/Þ to th, ß to ss (from the brief); ĸ to k, ı to i, ȷ to j, ŉ to 'n, Ŋ/ŋ to n,
     Ɖ to d, Ɋ to q, Ʉ to u, Ƕ to hv (look-alikes).
- The checker confirms the 38 source rows equal the generator's output, cover 359 letters, each letter
  once, all alphabetic and inside the block.
- Left unfolded (lowercase only): tone letters, open O/E, turned/reversed forms, schwa, gamma, iota,
  upsilon, ezh, yogh, wynn, esh, YR, the clicks ǀ ǁ ǂ ǃ, glottal stops, ƛ, ƻ.

## Security

Threat note (secure-code-guardian, security-reviewer):

- **Hostile client input.** The client can send any UTF-8 up to 128 bytes per name on check-name (opcode
  210, `login.rs` reader) and up to 4096 bytes of creation payload (opcode 5). Each part is length-checked
  (2..=14 chars) before `new_name_part` runs, and the Invalid check comes before the taken check. So
  `name_key` on client input runs on at most 14 characters, and an invalid name never reveals whether it
  is taken.
- **Impersonation.** Accented, cased and ligature look-alikes of a saved display or temporary name now
  count as taken. For example 'Éva' or 'EVA' against 'Eva', 'Weiß' against 'Weiss', 'İlka' or 'ılka'
  against 'Ilka', and 'Zoe Nunez' against 'Zoë Núñez'.
- **No new oracle or enumeration.** Check-name already answers taken or available for the exact name. A
  folded hit tells the client only what checking the base spelling would. There are no new messages,
  codes or timing branches visible on the wire.
- **Refusals change nothing.** `create_character` returns before `insert_character` on every refusal, and
  the login path stages on a clone and saves only on Created (`login.rs` opcode 5). The tests assert
  `store == before` after every refusal: invalid display part, invalid temporary part, folded display
  collision, folded temporary collision.
- **Saves.** Nothing writes differently; `save` still goes through `validate` and then
  `character_store::replace_bytes` (atomic). Typed spellings are stored as entered; the key is never
  persisted.
- **Legacy safety.** `validate` keeps the lowercase-only duplicate rule, so a store with 'Eva' and 'Éva'
  (or a name like '--') loads, lists, selects and re-saves. A canary proves that folding on load would
  break this.
- **Logs.** No logging was added; names never reach logs or traces from this code.
- **Cost.** `name_key` takes the ASCII fast path (no table scan) for ASCII characters. A check costs
  O(characters × pair length), the same order as the old per-character `to_lowercase`. It runs only on
  check-name and create, never per tick.

## Open gaps

- **(R) Every rule here is reconstructed.** The original server's separator and uniqueness rules are not
  recovered.
- **Brief example swapped.** The brief's 'the owner'/'Brýce' example is tested as 'Kyle'/'Kýle'. The content
  rule bars player names in tests.
- **Not folded.** The key does not ignore separators, so 'O'Vale' and 'OVale' are different names. That
  was not in the brief and is a lead call. It also does not fold scripts outside the Latin block, which
  new names cannot use. Legacy names with such letters (for example U+212B Angstrom sign, or lowercase
  hooked letters above U+024F) compare by lowercase only.
- **L022 charset.** It allows Latin Extended-B letters with no base reading, such as the clicks ǀ and ǃ,
  which look like 'l' and '!'. The client font's coverage of them is unknown. Narrowing the charset
  would be a lead decision.
- **Preset first names with a trailing space.** 'Mei ', 'Mia ', 'Max ' and 'Tom ' are refused today
  (before and after this task) if the client sends the space. Whether the client trims them is not
  verified natively.
