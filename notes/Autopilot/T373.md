# T373: prove two players run the same dungeon marker independently

## Result

One new default-suite file, `tests/two_player_dungeons.rs`, proves the current
model is a **session-local** encounter: two in-process `Gateway`s (two
characters) click the same static Sheep Watch marker (battle `12350`, T319),
each owns its pending screen, instance, arena actors, HP/target/cooldown,
results, payout, quest credit and return pose; a third late joiner sees only the
static marker; and one player's malformed packet or mid-fight disconnect leaves
the other fighting and paid.

**No production file changed.** The final diff is the new test plus this note.
The route exercised is the shipped one: 26/8 marker click -> 41/114 start screen
-> 41/108 Go -> zone 9600 -> real 36/10 attacks -> 39/18/47/19 results -> 26/42
Close, through the real `Gateway::handle_at` dispatch. The tests use the shared
`tests/common/field_battle_fixture.rs` session/packet/content helpers; the
per-battle fight/economy/visibility helpers live in the new file.

The six tests (the brief's names):

1. `two_players_start_the_same_marker_with_independent_encounters` - A and B
   each open their own start screen (seeded per-save instance counters 41 and
   108) and Go. A's click/Go changes none of B's snapshot, save payload,
   position, zone or pending screen; B's Go still works after A started; a
   forged 41/108 with no open screen is inert and changes no byte, and an
   out-of-range Go (A walks 50 m away) changes no byte and only drops A's own
   stale screen (the server never saves it), after which A reopens the marker
   and starts; each 41/114 screen and running refresh names its own
   encounter/instance; both arenas load the row's five actors.
2. `a_win_or_loss_in_one_encounter_does_not_affect_the_other` - both sessions
   carry the shipped `Brawler: Delinquent Dilemma` goal. B takes a real hit
   (its enemy HP drops). A wins through the ordinary 36/10 path. A is paid and
   credited 2/4; B's snapshot/save/wallet/quest/active encounter are identical
   to the state captured before A's win, and A's 39/18 results do not appear on
   B. B then attacks again and wins its own fight, credited 2/4; B's win does
   not change A.
3. `both_get_their_own_payout_and_return_to_their_own_pose` - A and B start
   with different saved quest counters (1 and 0) and different pre-entry poses
   (marker and marker+1.41 m), both win. A live `realm coins 7` grant during
   the results screen survives A's Close (no old snapshot restored) and never
   reaches B. A's Close returns A to the marker; B stays in its won arena; B's
   Close returns B to B's own pose. Each save carries only its own
   coins/XP/items/quest counters (3 vs 2). Replaying A's Close and A's Go pays
   nothing and does not start B; reloading both through `game_store` +
   `Gateway::load_gameplay` restores each own state with no live encounter.
4. `a_third_late_joiner_sees_no_arena_actors` - a third session entering the
   field at the marker receives exactly one 35/2 AddNpc for the static marker,
   no arena actor GUID in any 35/2 or raw reply byte, and no 41/114 running
   encounter. Its 26/8 click opens only its own start screen; its own Go starts
   its own instance and leaves A and B untouched.
5. `one_players_disconnect_or_bad_packet_does_not_stop_the_other` - five
   malformed packets (truncated 26/8, 36/10, 26/42, 41/109 and a header-only
   36/10) are refused for A alone with an empty reply and byte-identical
   snapshot/save. A's mid-fight save/reload (the production reconnect path)
   drops A's run without paying and returns A to A's pre-entry pose. B keeps
   moving, attacks, wins through 36/10, is paid once and returns to B's own
   pose. A can start a fresh battle afterwards (no stuck pending state).
6. `the_route_uses_no_dev_commands` - a normal-player session (dev tools off,
   `AccountRole::Player`) is refused `realm win` and `realm battle 12350` with
   zero state change, and the same `realm win` is refused mid-fight while the
   encounter stays `Fighting`. The complete start/fight/return path then runs
   through ordinary client requests only (26/8, 41/108, 36/10, 26/42) and the
   real attacks pay the win; every route outcome reports zero developer-command
   denials.

## (R) reconstructed rules

- The session-local encounter is this build's reconstructed model: `pending_battle`,
  the open start screen and the instance counter are per `Gameplay`/per
  character save, and the arena is the session's own zone-9600 scene. The Build
  Ledger (2026-10-15) records "Arena battles are still per player" and that the
  world `instance_id` is always 0 while `world::World` is unused; the 41/114
  instance id asserted here is `EncounterState::next_instance_id` from the
  character save, not a world instance. Shared World C11 says the same
  ("Arena state and instance counters are per EncounterEngine"). Retail
  group/world instancing is not recovered and is not added here.
- The test instance seeds 41/108 are (R) test values; a production character
  save starts at `next_instance_id = 1` (`EncounterEngine::load`), so two fresh
  characters commonly share instance 1 in their own saves. The suite seeds
  distinct counters to make "each start packet names its own instance"
  observable without claiming a global instance id.
- Both sessions' arena actors carry the row's static GUIDs (a per-session copy
  of the same authored actor ids). That is the existing field-battle model, not
  a new actor-id namespace.
- The saved quest counters (1 and 0 seeded, +2 Alpha Wolf defeats per win) come
  from T319's `enemies.json`/quest mapping; the shipped goal counts kind
  `930050` and the two Alphas advance it (tests 8/9 of T319).
- Coins/prizes are the existing `field_battles.json` row (25 coins, one wheel
  prize, 50 active-job XP); no tuning was added.

## Threat note (secure-code-guardian)

No production parser, save, reward or role rule was changed; the suite drives
the existing attack surface and asserts the refusals. A hostile client could
send:

- a forged 41/108 Go with no open screen: the server ignores the payload ids
  and starts nothing (test 1: empty reply, byte-identical snapshot/save). With
  an open screen, Go starts only that session's own pending battle; a client
  cannot name another session's encounter/instance, and test 3's cross-Go on B
  after B closed is inert.
- malformed 26/8/36/10/26/42/41/109 bodies: each is a single, non-bundled
  application message, so the gateway drops the handler error for that session
  alone. Test 5 asserts an empty reply and byte-identical snapshot/save for
  every packet, and B keeps fighting. A bundled malformed child still follows
  the existing `contain` session-disconnect rule (unchanged; not exercised
  here because it is `bin/osfr-gateway.rs` session plumbing).
- a replayed Close or Go after a finished run: pays nothing, starts nothing
  (test 3). The pending screen is consumed by the first Go (session-local
  `take_pending_battle`).
- a third session joining the field: receives only the static marker, no arena
  actor GUIDs and no other player's running encounter (test 4); it cannot be
  pulled into another fight.
- economy: rewards are applied only from the server-verified 36/10 kills; test
  3 asserts exact coin/XP/prize deltas, one prize from the row's pool, and that
  a live coin delta survives Close instead of restoring a snapshot. B's wallet
  and quest counters never move from A's win or Close.
- ids: instance ids come from each character's own save; the suite seeds
  distinct values and never aliases the public-world instance.

## Open gaps / deviations

- Two in-process `Gateway`s, not two UDP sockets: the brief prefers this when
  the production path is the same, and `Gateway::handle_at` is the same
  packet -> gameplay dispatch the server uses. The UDP session plumbing,
  `Server::step` and `contain` are not exercised; test 5's "disconnect" is the
  production `game_store` save + `Gateway::load_gameplay` reconnect path, not a
  socket teardown.
- The knockout/revive sub-case is documented as not used: the arena knockout is
  the tick's `Lost` path, and the brief allowed "if used". Existing suites cover
  knocked-out Go refusals and the world respawn window.
- The `Lost` results path is not driven by this suite (win and disconnect are);
  the existing `tests/encounter.rs`/opening-cave suites own it.
- No native client run (out of scope); no full-suite run (the integrator does
  it).
- The exact instance values 41/108 are test-seeded per-save counters, not
  recovered production ids; production characters start at 1.
- The Shared World design note proposes a future per-run arena/instance
  coordinator (lead-only). This suite deliberately pins today's per-session
  model, so when that coordinator lands these tests become the migration
  acceptance surface and will need to be revisited; that is a design change,
  not a defect found here.
- The Build Ledger's native two-client check is still pending; no native client
  was run for this slice.

## Checklist

1. **A refusal changes nothing.** Tests 1 (forged and out-of-range Go), 3
   (replay Close/Go and cross-Go), and 5 (five malformed packets) snapshot the
   typed `Snapshot` and the serialized save payload before each refusal and
   assert both are equal afterwards, plus empty replies/no zoning. Canary 3
   shows the out-of-range refusal assertion bites the production range gate;
   canaries 1 and 2 show the instance/return-pose assertions bite.
2. **Rollback covers all state.** No production transaction changed. The tests
   observe the existing staged `Gateway`/`Gameplay` commit; a malformed packet
   is dropped by the gateway for that session only and the snapshot equality
   covers every typed field (including the encounter state).
3. **Apply deltas, never restore old snapshots.** Test 3 grants 7 coins with
   the production `realm coins` command after the win, then asserts Close keeps
   `paid coins + 7` and B's wallet never moves. The win payout itself is
   asserted as deltas over the live balance.
4. **Busy rules are mutual.** No new activity/`Occupation` row. The two
   players each run the existing per-session encounter; the existing
   `sheep_watch_dungeon` refusals still prove a second start in the same
   session is refused by the shared busy gate, and test 1 proves another
   session's live encounter does not block a player's own.
5. **Every entry path is gated.** No new entry path: the marker only opens
   41/114 through the existing 8 m interaction, Go runs the existing
   level/prize/range checks in `gameplay/field_battle.rs`, and the tests send
   no parallel start. The reconnect path is the production `game_store` load;
   the pending screen is not saved, so a reload cannot replay a Go.
6. **Reachable in production, tested through it.** Two real `Gateway`s at the
   production `handle_at` dispatch; every request is a production packet built
   by the shared fixture helpers. No internal engine helper is called to start,
   win, pay or close.
7. **Survives reconnect.** Test 3 reloads both characters and asserts each
   save's own coins/XP/items/quest counters, own pose, and no live encounter.
   Test 5 reloads A mid-fight, asserts no payout and the pre-entry pose, and
   asserts B's live run and save are untouched.
8. **Every exit path restores the player.** Test 3 covers win + Close for both
   players (own poses, no active encounter); test 5 covers disconnect/reload
   (pre-entry pose, no payout, fresh start possible); test 4 covers a late
   joiner (still in the open world). Timeout/failure paths are owned by the
   existing encounter suites and are not changed.
9. **Economy safety.** Rewards come only from server-verified 36/10 kills; the
   test sends no result/win flag and no reward quantity. `assert_payout` checks
   the exact row coin amount, one prize from the row's pool, 50 active-job XP
   and zero for other profiles; B's wallet/quest never move from A's action.
   The one coin quantity in the suite is the authorized `realm coins 7`
   developer grant used as a live delta (test 3), not a client-reported reward.
   No new item or id is added.
10. **Wire format matches the client reader exactly.** No wire shape is added;
    the suite reuses the pinned 26/8 `0x008b6bc0`, 41/108 `0x008b6e70`,
    41/114 reader chain (id bytes 4..8, instance 8..12), 36/10
    `0x00a342e0`/`0x00a35150`, 35/2 `0x00921a10` and 26/42 `0x008a2eb0`
    shapes. The 41/114 field offsets are asserted byte-for-byte, and the 35/2
    actor ids are parsed from the real bytes.
11. **Unique ids.** Each character owns its `next_instance_id`; test 1 seeds
    41/108 and asserts the two start screens and active instances differ and
    each names its own. No new GUID is introduced; the public-world instance is
    not aliased (test 4's late joiner never receives an arena actor).
12. **Others see changes.** No new visible state. Test 4 asserts the late
    joiner's directed 35/2 batch contains exactly one static marker and no
    arena actor, and that another player's running 41/114 is not replayed;
    A/B are unchanged by the third session's entry and start.
13. **Content works end to end.** Battle 12350 loads, the marker spawns, both
    start screens show the row's fields, five actors spawn per arena, the real
    kills complete the shipped `Delinquent Dilemma` goal (1->3 and 0->2), the
    prizes/coins/XP are granted, results open and Close returns each player.
14. **Values live in data.** No compiled tuning is added. Coins are read from
    `field_battles.json`; enemy GUIDs/roster come from the row; the fixed 50
    job XP is the existing engine policy asserted with its comment; quest ids
    and positions are existing game data. The 41/108 instance seeds are test
    values, not content.
15. **Canaries break production code.** All three canaries edit `src`
    production files (`encounter/field.rs` twice, `encounter.rs` once), fail
    the intended new test, and were restored byte-identically (SHA-256 above;
    `git status` empty).
16. **Hands off session plumbing.** No change to session creation, teardown,
    transactions or save ordering in `bin/osfr-gateway.rs`/`gateway.rs`; the
    canary edits were reverted byte-identically. The reconnect in test 3/5 is
    the existing `game_store` path.
17. **One player's error never stops the server.** Test 5's five malformed
    packets are refused for A alone (the gateway swallows the single-message
    handler error), B keeps moving/attacking/wins and the test process does not
    panic. No client-controlled data is `unwrap`ped in this test except

18. **A type's rules live on the type.** No type changed. The suite relies on
    the existing documented rules: `EncounterEngine::pending_battle` is
    session-local and never saved, `EncounterState::next_instance_id` is in the

19. **Hot paths stay cheap.** No production tick or packet code changed; the
