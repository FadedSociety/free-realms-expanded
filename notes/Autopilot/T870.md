# T870 - housing: a creative decorate catalog (every fixture in the tray without owning it)

Sonnet builder, lead-owned housing. Paths are under `prototype/osfr-tools/`. Skills applied: ponytail
(full, with its review pass on the diff) and secure-code-guardian (threat note below).

## What changed

- **Setting.** `data/content/housing_settings.json` (`schema_version`, `creative_catalog`), read by
  `HousingSession::load` through `housing_service::creative::catalog_setting` and handed to the service with
  `HousingService::with_creative_catalog`. The shipped file turns the catalog on; a server turns it off by
  editing it. A content directory **without** the file stays on the owned flow (dormant by default). A
  present but unusable file (bad JSON, schema, unknown field, over 4 KiB) fails the load instead of reading as
  off. Why a file and not a `houses.json` field: every housing test copies the shipped `houses.json` into its
  scratch content, so a field set to true there would flip the owned-flow suites the brief says stay
  untouched. The file also keeps lots (content) apart from a server switch.
- **Tray (127/43).** With the catalog on, the list is one record per `housing_fixtures.json` row (1,198 now,
  bounded by `MAX_CONFIG_ROWS` = the codec's `MAX_COUNT`), each named by its selector. It replaces the
  owned list; owned items are still placed through the bag.
- **Selector and placed ids** (`src/housing_service/creative.rs`, (R), server-side only). Inventory item ids
  are positive `i32`s counted up from a small number, so the upper half (`1<<30 ..= i32::MAX`) is reserved:
  a selector is `1<<30` plus the item id; a placed id (`item_instance_id` of a catalog placement) is
  `(1<<30)+(1<<20)` and up, one per piece, taken above every placed id the lots hold. Bit 30 keeps both
  ids positive `i32`s, as an inventory row's id.
- **Creative is the id.** A saved fixture is creative exactly when its `item_instance_id` is a placed id. No
  second flag exists to drift: a pickup (single and all) returns nothing for such a fixture whatever the
  setting says now, so turning the catalog off later never turns a creative piece into an item, and the
  save format is unchanged (the 127/28 and 127/40 records are identical to an owned piece's).
  `owned_instance` ignores a bag row whose id is reserved, so a hand-edited save cannot alias one.
- **Flow.** `offer` (127/1), `fixture_asset` (127/42) and `place` (127/2) accept a selector while the catalog
  is on: the row comes from the table, the tint is 0, the placed id is fresh, the staged ledger is seeded with
  that one id, and `stock.consume` is skipped. Everything else in `place` is the unchanged owned path and
  the refusal staging is the same (staged clone, bag mutated last). Selectors stay bound after a placement,
  so the same piece places again (unlimited).
- A small subtract: the three copies of the coupling-free `FixtureInstanceInfo` literal are one
  `fixture_info`.

## Threat note

A hostile client can send: a selector while the catalog is off (127/1 -> `UnknownInstance`, 127/2 ->
`UnresolvedSelection`, nothing changes), a selector for an item with no row (`FixtureDefinitionUnknown`), a
placed-band id as a selection (names nothing), a creative id for a pickup (it is the fixture guid that is
looked up, never an item), and unlimited placements (bounded by the lot's `max_fixtures`, build area and edit
mode, as before). A creative piece never enters the bag, so it cannot be sold, traded or stacked into value;
the `Inventory` is not touched by any catalog path. A bag row with a reserved id is ignored as furniture.
Visitors still cannot edit (T872 copies are read-only). Per-request cost: `next_placed_id` scans the lot
snapshots once per catalog placement (at most 4,096 fixtures); the tray is built once per entry.

## Checklist

1. Refusal changes nothing: placement stays staged on a clone, the id is derived (no counter), the bag is
   mutated last; `creative_refusals_change_nothing` snapshots state and bag before and after each refusal.
2. Rollback covers all state: no side table; the ledger is rebuilt per request.
3. Deltas not snapshots: no inventory snapshot is restored; a creative placement applies no inventory change.
4. Busy rules: unchanged (housing session gate in `occupation.rs`); no new activity.
5. Every entry path gated: catalog placement goes through the same `place` (house, can_enter, edit mode, build
   area, fixture limit) as owned placement; there is no second path.
6. Reachable and tested through the real path: `housing_session.rs` drives 127/1, 127/2, 127/3 through
   `Gameplay::handle_in_world` with the shipped-style settings file.
7. Survives reconnect: creative pieces are ordinary saved fixtures; save/load and relog tested at both levels
   (`from_state` accepts them because their ids are never in the bag).
8. Exit paths: unchanged.
9. Economy: free pieces cannot become items (pickup, pickup-all, setting toggled off, reserved bag ids).
10. Wire format: no packet layout changed; 127/43 reuses the existing record (guid, item definition,
    coupling); the guid is a positive `i32` selector.
11. Unique ids: placed ids are unique across every lot the service holds (`from_state` requires that).
12. Others see changes: placements and pickups use the same 127/40, 127/41 and actor packets, so the T872
    broadcast carries them.
13. Content works end to end: shipped file on; session test places, saves, reloads and picks up.
14. Values in data: the on/off switch is data; the id bands are fixed server ids, not tuning.
15. Canaries broke production code (above).
16. Session plumbing: untouched.
17. One player's error: an unusable settings file fails that session's load (as a bad `houses.json` does),
    nothing runs in the shared tick.
18. Type rules on the type: "creative" is decided in `creative.rs` (`is_placed_id`) with the doc comment there;
    `owned_instance` and both pickups call it.
19. Hot paths: nothing per tick; per placement one snapshot scan.
