Brief: `lab/autopilot/opus/lead-briefs/referee-enforcer-jobs.md` (attempt 1). Base: `f06eef0` (L048).

## What changed

- **Two staff job records**, imported with per-row provenance into
  `data/content/staff_jobs.json` (OSFR `src/Resources/Profiles.json` at Sanctuary main `10f129e`,
  rows Id 58 'Referee' and Id 20 'Enforcer', commits 62b44b7, 71e294b, aea3bcd; data facts only, no
  AGPL code). `src/profiles.rs` serializes each as a `ClientPcProfile` record (client reader
  `0x00911d60`) in the exact layout of the 16 captured records, at rank 20, with the tail every
  captured non-combat record carries. A file that does not load leaves no staff jobs (fails
  closed), and content that ever ships 58 or 20 as a player job refuses to load.
- **Granted from the login role, never saved.** `Gateway::bind_account_role` already fixes the
  L048 referee flag (Moderator or Admin); the same decision now calls
  `Gameplay::set_staff_jobs`. The grant lives in `Profiles` as a session-only `StaffSession`
  that `ProfileState` (the saved part) does not contain. A player's session never has it; a
  demoted moderator loses it at the next login.
- **Self data lists them.** `build_self_message` appends the two rows for a granted session
  (`Gameplay::staff_job_rows`); the 16 player rows are untouched.
- **A 26/13 wears a staff job over the real job (display only).** `stage_job_selection` sends
  a granted staff id to `wear_staff_job`: the 38/21 activation names the staff job, neighbours
  get the 35/7 outfit through the existing announce, later viewers get AddPc (`active_profile`
  and attachments) through the existing presentation refresh. `Profiles::active` (what XP,
  quests, trainers, crafting, abilities and saves read) stays the real job; only
  `Profiles::shown` (self 38/21, AddPc, 35/7, world re-init) reports the staff job. Every real
  job change (`Profiles::activate`) takes the staff job off.
- **The outfit is attachments only.** The Referee Shirt (13682) and default items 421 and 429
  are drawn from the item catalogue as an attachment list (`Inventory::outfit_attachments`):
  definition slot, default tint, and refused unless every piece is known and Chest and Legs are
  present (the client's `ProcessProfileSwap` rule). Nothing is granted into the inventory, so
  there is nothing to save, trade, sell, destroy or place, and nothing to take back on demotion.
- **Reward reloads keep the session part.** The three places that rebuild `Profiles` from a
  reward's snapshot (claim XP, minigame XP, quest XP) now use `Profiles::adopt`, which is
  `Profiles::load` plus the current session's staff part.
- `Gameplay::profile_attachments` moved from `gameplay.rs` to `gameplay/jobs.rs` and became
  staff-aware; the two 26/13 sites and `announce_profile_outfit` use it with the shown job.

### What makes a name red (brief "Verify first" 2): not found, nothing built

- **Not the Type.** Captured Miner (14) carries Type 9 in its record (+12), the same as both staff
  rows, and Miners do not have red names.
- **No compare of the AddPc job with 20.** AddPc stores the active job at actor `+0x16c`
  (`0091ae09`). A byte scan of `.text` finds no `cmp [reg+0x16c], 14h`; the only immediate
  compares on `+0x16c` are with -1, 0 and 1, and no `mov reg,[reg+0x16c]` is followed within
  16 bytes by `cmp reg, 14h`. Of the 43 `cmp reg, 14h; jcc` sites, the ones in game code are
  switches (`00a41494`, `00ccacc4`), the name-plate key loop (`009d1d20`, twenty `NamePlate%d`
  keys), name change, soccer and fishing.
- **Not the referee flag.** L048: the AddPc referee byte (actor `+0x140` bit 0x20) is read only
  by `OnReceiveSay`/`OnReceiveWhisper` (chat log `isRef`), and it is the same for both staff jobs.
- No Lua check on profile 20 (`ScriptsBase.lua`: only `GetActiveProfileId` equality checks).
- The overhead name text is built in `ProxiedCharacter::Process` (`sub_973200`, ctor call
  `0097423e` to `OverHeadTextElement` `0096f540`) with a constant default colour
  (`xmmword_1CB53D0`); the colour change path was not recovered (the function exceeds the
  broker's decompile cap).
- OSFR's only difference between the rows is Id and NameId, and its commit says the Enforcer
  "just has a red name". So the server sends job 20 exactly as OSFR does and builds no colour
  mechanism; the native run decides whether the client colours it.

## (R) choices

1. Moderators and admins get both jobs (OSFR policy, the L048 referee decision).
2. The grant is fixed at login; a moderator demoted while online keeps it until the next login
   (a kick forces that), as for the L048 referee flag. Authority is unaffected: the jobs grant
   nothing.
3. A staff job is display only: the real job stays active for XP, quests, trainers, crafting,
   abilities and saves; XP paid while it is worn goes to the real job.
4. The outfit is attachments only, never owned items (stronger than "untradeable staff items":
   nothing exists to trade, sell or save). The staff job's equipment list is empty, so the
   character sheet shows no pieces for it.
5. Record fields not in the captures: the tenth dword 0 and the five unnamed fields 0 (as OSFR);
   rank 20 (OSFR level 20); Type 9, Icon 258, image sets 19/21/4 and the item classes from OSFR.
6. Hint, Trial, Unknown and Unknown2 are not imported: they belong to the 44/3 reference-data
   profile packet (`ClientProfileData`), which this server does not send, and have no field in
   the 38/21 record. Hint 59572 was checked against the locale.
7. The default items use the definition's own slot and default tint.

## Security

Trust boundaries:
- **Client input.** Only the existing 26/13 job id (i32, length-checked by the existing parser).
  A staff id takes the new branch only when the session was granted at login; any other id,
  including 58 and 20 from a player, takes the existing path and gets the existing "not been
  unlocked" refusal with nothing changed. No new packet, parser or field.
- **Authority.** The grant comes only from the account store role read by the host-only
  `bind_account_role` (ticket- and owner-verified account). The staff jobs confer nothing: no
  command, item, coin, XP, quest gate or trainer reads them.
- **Economy.** No item is granted, so trade, vendor sell, destroy, housing placement and saves
  cannot see one. A staff job never earns job XP (every XP path keys on `active`), and no
  Station Cash earning path exists or reads the shown job.
- **Saves.** `ProfileState` has no staff field and `Profiles::load` still refuses unknown job ids,
  so a save can never hold 58 or 20 and a forged one would not load. A wear sets `changed`, which
  runs the existing atomic save of an unchanged state.

Threat note (a hostile client):
- Sends 26/13 for 58 or 20 as a player: refused exactly like any locked job (same chat line, no
  activation, no 35/7, no save, presentation and save unchanged; tested). No oracle: the reply
  does not depend on whether the id is a staff job.
- Sends 26/13 for a staff job as staff with an incomplete catalogue: one chat line, nothing
  changes (tested, both a missing piece and a missing Legs slot).
- Equips or moves an item to profile 58 or 20: the inventory has no rule for those profiles, so
  the existing "unknown profile" refusal applies.
- Learns who is staff: as with the L048 flag, staff are visible by design while they choose to
  wear a staff job. A demoted moderator can still wear one until the next login (R2); kicking
  them ends it.
- Nothing is logged; no new file is written.

## Checklist

1. **Refusals change nothing.** Player select of 58/20 and the undressable outfit are refused
   with a chat line; the tests compare save, shown job and outfit before and after. Profiles
   are only changed after `activation` succeeds.
2. **Rollback covers all state.** The session part lives inside `Profiles`, which lives inside
   the staged `Gameplay` clone; no shared state.
3. **Deltas, not snapshots.** Nothing is restored over live state; `adopt` copies only the
   session part onto the freshly loaded reward state.
4. **Busy rules.** No new activity; wearing is a 26/13 and keeps every existing 26/13 gate
   (race, soccer, movie).
5. **Every entry path gated.** The only way in is `stage_job_selection`, which both 26/13 sites
   call; the grant has one writer (`bind_account_role`).
6. **Real path.** The tests log in through `bind_account_role` then `Gateway::handle` (login,
   13/0, 10/0, 26/13) in production order; the L042/L048 rig tests (real sessions) still pass with
   staff rows in their moderators' self data.
7. **Reconnect.** Nothing is saved; a new login re-derives the grant from the role. Tested: a
   moderator saves through `game_store::save` while wearing Referee, is demoted, and logs in
   from that save with 16 jobs, the real job shown and the same save and outfit as before.
8. **Exit paths.** Any real job change (select, race, kart, cave) clears the staff job; logout
   drops it. No stuck state.
9. **Economy.** No item granted or owned; XP to the real job (tested through `realm level`).
10. **Wire format.** The record is checked field by field against the captured layout, the
    attachment list and the 3001/4005/0 trailer byte for byte, and the self-data row is read
    back by the client-layout parser (`parse_self`). Canary: dropping the tenth dword makes the
    parser reject the self data.
11. **Unique ids.** None created.
12. **Others see changes.** 35/7 to neighbours on wear and on taking it off (tested), AddPc
    presentation for later viewers (tested). Existing gap: viewers already in range get no new
    AddPc, so a name colour keyed on the job id shows only when they next see the player.
13. **End to end.** The moderator's self data lists both jobs, the select returns the 38/21 and
    the presentation carries the job and outfit.
14. **Values in data.** The records and outfit live in `staff_jobs.json`.
15. **Canaries break production code** (see Gates).
16. **Session plumbing untouched** (`bin/osfr-gateway.rs` unchanged).
17. **Tick safety.** No tick code.
18. **Type rules.** `StaffSession` documents that `ProfileState` never holds it; `shown` and
    `active` document which callers read which; the `referee` field documents the grant.
19. **Hot path.** One search of a two-row table per presentation build or 26/13; nothing per
    tick.
