# T623 - A new character's journal lists only its own quests

Base `ebd07a0`. Native run `client-baseline-20261022T163339Z` (`lead-08.png`, `lead-09.png`): a
new character that took only Warrior: Achieve Level 5 saw "Other Quests 25/30".

## Cause (confirmed)

- **The 25 quests are the capture's.** Decoding `lab/references/rust-gateway-reference/0007-login.bin`
  (unchanged since 2026-10-07, sha `f4b8b4ca...`) at body offset 157819: the first quest list holds
  25 records, ids `6, 92, 218, 435, 439, 462, 624, 1019, 1029, 1077, 1304, 1346, 1593, 1617, 1625,
  1648, 1673, 1680, 1875, 2061, 2248, 2270, 2287, 2347, 2513`, then the tail `241, 2513, 1, 10, 30`
  (completed count, selected quest, auto-switch, two limits). 1617's record starts at span offset
  3865; the 1617 binding (4112) is its objective's fourth dword (tail +12). Title 389427 etc. The
  screenshot rows (Stolen Turnips, History Comes Alive!, ...) are these records; 25/30 is this count
  over the captured member limit.
- **Why 2026-10-08 showed 1/30.** Then the self data went through `Gameplay::patch_self`, whose
  opening branch (`OpeningJournal::patch_self`) replaced the span with the opening stages. The typed
  builder (`Gateway::build_self_message`, 2026-10-14) never calls it: `Gameplay::patch_self` has no
  production caller left (only `tests/profiles.rs`). So every login replayed the capture's list.
- The second list (101 records + 4-byte tail) is not the quest journal: `00944fe0` calls
  `00940c60` on player `+0x1add0` (the quest manager) at `0x009456c5` and `00940e60` on player
  `+0x1bee8` at `0x009456d1`. Left as captured (out of scope).

## What changed

  - `parse_quest_journal` split out of `parse_quest_records` (the `00940c60` part: list + 17-byte tail).
  - `QuestFirstRecord::quest_id()` (record dword 0, `0093c840`).
  - `retain_quests(data, own, completed)`: serializes the quest span, writes the bound counters in
    (the existing overlay), drops the bindings (they index the captured span), keeps only the
    records `own` accepts, and sets the tail: `completed`, first kept quest or -1, auto-switch 0.
    The limits stay.
  - `replace_quest_journal(data, span)`: parses a server-built `00940c60` span into the list and
    tail, drops the bindings.
  - Doc on `SelfData::quest_records` says every login replaces the captured list.

  `patch_self` calls it (same bytes, same validation).

## Split quests: kept on 49/3, not in the span (differs from the brief)

The brief asked for active split quests in the span. They already come back at world entry:
`append_npc_quest_login_sync` -> `QuestEngine::active_login_packets` sends 49/3 (with the T403 goal
text ids) plus 49/8/9/10 for every active split quest, pinned by `tests/w74_quest_runtime.rs`. The
client inserts self-data records and 49/3 records the same way: `00940c60` and `00c7bd10` both
call `009225d0` -> `008e9330`, which links a new node into the list and bucket and increments the
count with no lookup of an existing key. Listing split quests in the span as well would show each
twice (and count it twice against 30). So the span holds no split quest, and
`a_saved_split_quest_comes_back_once_by_49_3_not_in_the_self_data` proves the quest arrives exactly
once. Moving split quests into the span means dropping the 49/3 from the login sync and checking
what its select flag does for the helper (`BaseClient_QuestData_OnQuestAdded` /
`QuestHelper:PopulateHelper`, ScriptsBase.lua 13063); that is a lead decision.
