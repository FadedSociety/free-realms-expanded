# T494: Rainbow Randomizer, Realmshake and XVD-S — independent dance clips and a random song

Builder run on an autopilot worktree cut from `autopilot`. T459/T461/T463 are already merged here, so the
fleet pack in `lab/fleet/out/brief-research/T494.md` is stale on its central claim (it says `src/boombox.rs`
does not exist; it does, with the synchronized slice).

## What changed

- `src/boombox.rs` (the owner module; no hub touched):
  - `Boombox.clips: BTreeMap<i32, Vec<Clip>>` (new `Clip { animation_id, ms }`), independent rows only,
    `#[serde(default)]` so the other rows need no field. Loader bounds: independent iff non-empty, model > 0,
    1..=256 clips per model, `animation_id > 0` and unique in the model's table, `ms` in 1..=600000, and an
    independent row needs `standing_animation_id > 0`.
  - `Dance` is now an enum: `Synchronized` (the T463 struct, renamed but behaviour unchanged) or `Independent`
    (new). `Placed` still has one `dance: Option<Dance>`; `transform` rows are `None`. No second flag.
  - `Independent` keeps per dancer `Solo { guid, model, clip: Option<i32>, ends_ms }`. A dancer joins with one
    clip drawn from its model's table; every clip re-rolls when `now_ms >= clip end − blend_ms` (1000 ms floor
    when the clip is not longer than the blend); `choose` excludes the previous id unless it is the only clip.
    A model absent from the table gets the row's `standing_animation_id` (the client dance group 3550/3570/3200)
    as a base 35/8, sent once. Each rolled clip is its own single-entry 35/63 for the dancer and every nearby
    session that knows them. Leaving, mounting, expiry or replacement sends 35/8 animation 1 base, as the
    synchronized slice does.
  - The song is one random `song_effect_ids` entry per spawn (`pick`), drawn from a `Rng` (the
    `power_ups.rs` SplitMix64) owned by `Boomboxes`; the seed is OS entropy, 0 if that read fails.
  - Per tick: winner selection is the T463 priority-then-distance rule with the model gate from `Dance::allows`;
    the independent branch mutates `dancing` in place (remove the gone, keep a playing clip untouched) so an
    idle tick allocates nothing beyond the pre-existing `nearby_sessions` sets. RNG draws happen only on spawn,
    join and re-roll; no clip or song table is cloned per tick.
- `data/content/boomboxes.json`: the three independent rows gain `clips` for player models 1, 2, 60 and 61:
  item 1913 (group 3550) 73 clips/model, item 76935 (group 3570) 53, item 48244 (group 3200) 5. One extra
  `client` source row per item records the rebuild rule.
- `tests/boombox_catalogue.rs`: model check now covers `clips` keys; 12 new loader-refusal cases (missing/empty
  table, clips on a synchronized row, 0/over-cap ms, 0/duplicate animation id, model 0, empty table, standing 0,
  unknown field, 257 clips); new `the_independent_clip_sets_are_rebuilt_from_the_client`.
- `src/bin/osfr_gateway/boombox_routing.rs` (tests only): new
  `t494_a_randomizer_rolls_a_model_clip_and_a_model_without_one_stands`, driving 36/10 through the gateway, the
  real `boombox_routing::place` and the real tick; it checks the 35/41 colour song (16448-16453), a single-entry
  35/63 for the human_f dancer, and the base 35/8 group 3550 for the model with no table (1941).

## (R) rules

- `(R)` clip lengths: Sanctuary's measurements, not client data; all in `boomboxes.json`.
- `(R)` 1000 ms floor when a clip is not longer than `blend_ms` (brief + T463 `MIN_STEP_MS`; Sanctuary instead
  clamps the blend to `duration − 1`, i.e. 1 ms).
- `(R)` one song pick per spawn from the row's six (Sanctuary has the six colour effects; the run found no
  client spawn-time pick, so the pick and the stream are the repo's). F686: the 35/41 source guid is
  the owner, as `Placed::show` passes it; what the client does with that field is unrecovered.
- `(R)` overlapping boxes: highest priority, then nearest (T463); Sanctuary rotates by least served.
- `(R)` models outside 1/2/60/61 (transforms, Realms Roll 1941) have no table and stand.

## Threat note (secure-code-guardian)

- Surface a hostile client has: 42/6 bind, 36/10 cast and 42/16 info with arbitrary item/instance ids, and pose
  movement in/out of a box's range. Nothing new accepts a client id: the spawn uses the server catalogue row
  (loaded from `boomboxes.json` by the definition id already validated in the item-bar path), the clip ids,
  song effects, models and durations are server data, and the box guid is server allocated.
- The `Rng` is not a security boundary (visual variation only): it is not a CSPRNG, it is seeded from OS
  entropy (0 on failure), and a repeat only changes which dance/song is shown.
- Resource bounds: 64 rows, 256 KiB file, ≤256 clips/model, ids positive and unique, ms 1..=600000; a bad row
  is refused at load and leaves an empty catalogue, never a panic. Every packet is built from the server table,
  and each independent 35/63 has exactly one entry, so no client-controlled length/count exists.
- Refusal paths are unchanged (T461 press refusals, tested byte-identical); a refused content row changes
  nothing (the fresh load errors before it is used). No raw `fs::write` or hex formatting was added.
