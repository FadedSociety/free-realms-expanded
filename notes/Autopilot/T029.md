# T029: Fishing payout table and optional cap

## What changed

- `prototype/osfr-tools/data/content/fishing_spots.json`: replaced the single
  `catch_xp` value with a per-grade `payout` table (`grade`, `coins`,
  `fisherman_xp`) plus a top-level `source`, and added `catch_cap` with
  `enabled`, `window` (`session` or `hour`), `max_paid_catches` and `source`.
  The shipped cap is `enabled: false` with `max_paid_catches: null`, so no cap
  value was chosen. `Gameplay` reads this file when it initializes, so a
  running server needs a reconnect or restart to pick up an operator edit.
- `src/fishing_service.rs`: `enter` carries the table and cap into the round;
  `settle_catch` looks up the row for the server-selected grade and uses its
  coins/XP. A capped catch takes the existing no-payout escape path: sub-10
  escape flags, a kind-0 sub-14 result, a notice, and no item, coins, XP or
  quest events.
- `src/fishing_service.rs`: `PaidCatches` accounting is keyed by GUID. A
  session cap counts paid catches across trips in the login session; an hour
  cap keeps a rolling 3600-second timestamp list. `disconnect`, `reset` and
  `reset_all` clear it with the connection.
- `src/fishing_service.rs`: parse validation requires four ordered grades, the
  `R:` provenance marker, and sane limits. Coins are capped at 1,000,000 and
  Fisherman XP at 1,000 per row; a session cap at 10,000 and an hour cap at
  3,600. An enabled cap must have a positive limit. A disabled cap may carry a
  sane pre-set value.
- `src/fishing_service.rs`: `begin` remains the low-level entry with no table
  or cap. Ordinary play uses `enter` from `gameplay.rs`, so the live path is
  covered while existing `begin` behavior stays unchanged.
- `tests/fishing_entry.rs`: the fixture can now restart a round on the same
  service, and new tests cover the cap-off path, the per-grade payout rows, a
  session cap across trips, and the rolling hour window. The malformed-content
  test now covers payout and cap bounds, and the shipped-file test pins the
  disabled/null cap and the 0-coin/10-XP table.

## Reconstructed rules (R)

- Payout: no original fishing payout table was recovered. Client result reader
  `00b66be0` carries name, icon, weight, size grade, time, difficulty, rarity
  and score, and no coin or XP field; the catch reaches the inventory as an
  ordinary item update and the card is built by `00cd0150`. The shipped rows
  reproduce the previous server policy: zero coins and 10 Fisherman XP per
  catch. Every numeric value is tunable R.
- Cap: no original cap was recovered. The client sends no catch outcome and the
  server owns selection and payout, so both windows are R policy. The cap
  counts paid catches only; a bag-full or random escape does not consume a
  slot.
- The refusal notice is R text.

## Open gaps

- The cap ledger is connection-local and is not saved. A relog clears the
  session and hour counters, so the hour cap is a within-login-session control.
  Persisting it needs a save-schema decision (lead).
- The shipped file deliberately has no cap value (`null`) and no coin payout;
  the owner must choose the limit and any payout tuning.
- Old `fishing_spots.json` copies fail strict parsing because `catch_xp` was
  replaced by required `payout` and `catch_cap`. Any playtest bundle must carry
  the new file.
- `begin` (low-level/test entry) does not use the table or cap; ordinary
  gameplay uses `enter`.
- No native client run. The cap and payout are server-side and unit-tested;
  the client's catch-card and notice behavior for a capped escape is not
  natively observed.
- The cap is a count cap, not a rate limiter; the existing ~2.4 s cadence is
  unchanged.
