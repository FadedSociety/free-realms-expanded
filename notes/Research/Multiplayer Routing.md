# Multiplayer Routing

## W35 implementation

The UDP runner now stores sessions in a `BTreeMap` keyed by peer address and SOE connection id. Each session owns its `Codec`, reliable receiver/sender, `Gateway`, character save path, identity, chat permissions, spam gate, and timeout clock. `Server::step` is the single synchronization boundary: it serializes socket input, session ticks, and shared world mutations, so the shared `PlayerRegistry`, `SocialService`, session routing, and chat state need no lock. Cross-session messages are queued through each recipient's `ReliableSender`.

Without `--account-store`, only one session may own the configured `--state` file at a time; the existing state path and startup flow remain the fallback. With `--account-store`, the gateway login's character GUID resolves its owner account and loads/saves `characters/<guid>.json` beside the configured state. Per-character social lists use the adjacent `<guid>.social.json`. The gateway receives only a selected character GUID here; account-ticket validation remains the separate login service's responsibility. A native account-authentication handoff is not established by this integration.

On world-ready, the runner joins `PlayerRegistry` after Gateway has queued the self-data/startup replies, then sends the `SocialService::login` lists. Opcode-125 position changes call `update_pose`; every returned spawn, movement, or despawn tunnel is queued for the recipient session. A zone change leaves the current registry view and the later loaded/world-ready transition rejoins it. Disconnect and timeout leave the registry and call `SocialService::disconnect` before removing the session. `SocialService` is cloned with staged world state; changed friend/ignore profiles are saved beside their character saves before replies are queued.

Typed 15/1 and quick-chat 67/2/3 use `social_chat` and rebuild sender fields from live session state. Enabled `realm` developer commands are processed by `Gateway`/`chat.rs` first and excluded from normal chat delivery. Friend, ignore, and family-40 group requests route through `social_lists`. Client 26/30 ignore requests read the recovered flag (1 add, 0 remove). Families 112/2 and 112/3 are server replies, not client requests.

`SocialService` now derives `Clone, Debug` so the runner can stage it with `SharedWorld`. AddPc still uses the zero/empty reconstructed appearance values already emitted by `players.rs`. The legacy creator identity type retains its GUID-1 sentinel, so account-selected characters beyond GUID 1 are not yet patched into the self-data appearance block. No game content, raw assets, or recovered code were added to the repository.

No new native facts beyond the 26/30 flag callers were recovered in W35. ## Native two-client acceptance plan

Use two distinct authenticated accounts and character saves against one server with `--account-store`. Compare the 46-message startup against the existing single-client private oracle. Confirm independent handshake seeds, SOE sequence/ACK state, and timeout cleanup. Bring both clients to world-ready and verify reciprocal AddPc, movement, range loss/spawn, then say, tell, friend, ignore, and group invite/accept. Transfer one client to another zone and disconnect the other; verify only applicable sessions receive despawn and social-offline updates. Record client version, account/character selection, raw per-session queues, and final save/social-file hashes. This test remains lead-owned and has not been run by W35.
