## Security threat note (secure-code-guardian)

A hostile client can send a recipe id in 26/24 or replay minigame result
messages. The recipe id is looked up against the server-owned catalogue; an
unknown, unlearned, rank-locked or under-stocked id is refused before any
state change (`begin_recipe`, tested with complete-state equality in the
cooking/smelting/forging refusal tests). The client never supplies ingredient
ids, output ids or output counts: those come from `recipes.json`, and a win
commits the fixed transaction once. The new rows only widen the server's own
catalogue; they add no parser, no free grant and no sell path. The new
runtime-catalogue test keeps every loaded recipe's ids inside the item table
the server can actually grant, and the collision test prevents a stale
candidate id from aliasing a live client row (which could otherwise commit the
wrong output).
