## Chat (net.chat, 15 records)

`ClientChatProcessor` is fully covered:

- Constructor `00b15450`: installs `CommandProcessor::CommandEventHandler::vftable` then
  `ClientChatProcessor::vftable`, builds the embedded chat-node map (`00b152a0`) and spam list
  (`00b13500`), registers fifteen command names against nine ids through `00987000` (say 0,
  groupsay 1, tell/whisper 2, yell 3, lfg/3 4, area/1 5, tradechat/2 6, guildsay/gu 7, mo/4 8) and
  reads the four ChatSpeed values 330/1000/2000/30000 into +0x2cb0..+0x2cbc (matching note 088).
- Destructor `00b151d0`, slot-1 deleting destructor `00b156d0`, and the slot-0 command dispatcher
  `00b164b0`: the ChatSpeed spam gate over the `+0x488` entry chain, the `SpamChatBlocked` string sent
  through the chat-window callback, and a nine-way case table into the handlers.
- Ten senders each build a `PacketChat` with `00b0f8f0` and send it through `00b15340`. The channel
  number written into packet+0xc (local_224) per command id: say `00b15710` = 0, tell `00b16220` = 1,
  whisper `00b16350` = 3, groupsay `00b15f50` = 4, yell `00b15870` = 5, tradechat `00b159d0` = 6,
  lfg `00b15b30` = 7, area `00b15df0` = 8, guildsay `00b160b0` = 9 (also writes the guild guid pair
  at +0x1e8/+0x1ec), members-only `00b15c90` = 10 (the dispatcher additionally gates it on
  `(*(*(this+4)+0xc58)) != 1`).
- `00b15340` is the front of the send path: local serialization buffer (`008d4a40`), body writer
  `00b14fa0`, `ClientGateway` tunneled wrapper `0089adc0`, then the shared submit helper `00925640`
  (about 200 callers) and buffer release `00894560`.

The chat-node container is `SoeUtil::HashListMap<int, SoeUtil::List<ChatNode,10>, 256, -1>`:
constructor `00b152a0` (0x400-byte inline bucket array), destructor bodies `00b150e0`/`00b15160`,
slot-0 deleting destructor `00b15110`, and the `SoeUtil::HashList` base delete path `00b15320`.
`ListRemoveNode`-style teardown is `00b142a0` (unlink + count + free through the container vtable).

## Server-contract inferences (hypotheses, tied to wire)

- Chat: the client sends `15/1 PacketChat` itself; the original server must have re-validated the
  channel claim (guild membership for channel 9, subscription for channel 10) and fanned out, since
  the client's own spam gate (`00b164b0`) is bypassable. Depends on note 088 and `00b15340`.
- Guild: the request set (14, 15 and the request classes outside this shard) must have been answered
  by the reply set recovered here (17, 19, 20, 22, 25, 30, 31, 32, 41); the client only fills guids
  and names, so rank rules, name uniqueness, invite timeouts and the paid-rename result codes were
  entirely server-side. Depends on notes 088/090 and the dispatcher `00b1ee10`.
- Guild chat uses the same `15/1` record as every other channel but fills the guild guid at +0x1e8,
  so the original server could route it without a separate opcode (`00b160b0`, `00b14fa0`,
  `00b18380` supplies the guid pair).

## Contradictions, limits and open questions

- Note 090 records that every guild class constructor calls `FUN_00a09b70(<same id>)`. That holds for
  the seventeen classes in the table above, but the three classes in the note's `unverified_numeric_ids`
  set (`GuildErrorPacket`, `GuildInviteAcceptNotificationPacket`, `GuildInviteDeclineNotificationPacket`)
  are constructed through `00b17220` with a zero sub-opcode. The dispatcher case 0x17 (= 23) routes to
  the GuildErrorPacket handler `00b1cd30`, which supports the community number 23 even though the
  constructor leaves the field zero.
- The database renders the chat-node template as `List<ChatNode,10>` while the mangled RTTI descriptor
  at 0x0181d630 reads `...List@UChatNode@@$09...`; the same string's `$0BAA` matches the 256 buckets
  proven by the 0x400-byte memset, so the demangler's rendering of `$09` deserves a second look.
- Six byte-identical memberless destructor bodies (`00b172e0`-`00b17470`) cannot be matched to their
  owning classes from their own evidence; the class only shows in the caller or unwind funclet.
- Four helpers still lack an owning class: `00b16d90` (list sweep that updates live entries and frees
  dead ones), `00b16e80` (deleting destructor whose body is `00caacc0`), `00b16f90`/`00b17090`
  (loading-screen drop and text accessor).
- Six guild body readers parse classes that are absent from the community packet catalogue
  (`GuildMotdUpdatePacket`, `GuildNameAcceptedPacket`, `GuildRoleNameChangedPacket`,
  `GuildInviteCancelPacket`, `GuildDeleteNotificationPacket`, `AdminGuildServerVersionPacket`), and no
  opcode constant appears inside the readers, so their `wire` entries are intentionally empty; the
  sub-opcode is known only from the dispatcher table.
- `00b1b340` fires UI notifications with literal event ids (1, 2, 3, 4, 5, 7, 0xd) through `00cb6b80`;
  the meaning of those ids is not established here.
