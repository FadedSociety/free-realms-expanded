# F129: Fix T025 review blocker

## Finding

`lab/autopilot/reviews/31a917e-T025.md` is correct. `wait_log` polled a log file
and slept without servicing the bot socket. The two quest-selection callers sent
the request first; a lost datagram therefore had no retransmission, so a
healthy server looked unresponsive and the test timed out.

## What changed

- `prototype/osfr-tools/tests/bot_acceptance_1016.rs`: `wait_log` now takes the
  active `bot::Bot` and calls `pump(Duration::from_millis(100))` between log
  reads. Both quest-selection waits pass their active bot.
- `prototype/osfr-tools/src/bin/osfr-bot.rs`: added a `#[cfg(test)]`-only
  one-datagram drop hook and a `dropped_datagram` observation. The production
  bot binary has neither field nor behavior.
- The quest-journal regression drops the first forged `47/12` request before
  waiting for its gateway event. The test asserts that the datagram was dropped,
  that the refusal is observed after retransmission, and that
  `selected_quest_id` remains null.

No gameplay, save, session, transport, or routing behavior changed.

## Client evidence

IDA (read-only) was queried for the existing selection request:

- `decompile 00c7c250` shows `SendSelectQuestRequest` constructing the request.
- `decompile 00c7bc50` shows the request writer serializing the quest id as the
  four-byte field after the base packet fields. This agrees with
  `notes/Build Guides/Gameplay/Quests and Objectives.md`, which records
  `47/12` as `i32` quest id; IDA did not contradict it.

The fix introduces no wire format or application opcode. The test hook drops
the next reliable datagram containing the existing `47/12` request prefix; the
request bytes remain unchanged and no marker is added to server code.

## Security note

The drop hook is compiled only for tests, so a client cannot trigger it and the
production bot has no packet-suppression path. Pumping the socket only services
the existing reliable sender/receiver; it does not add an application route or
trust a client-reported outcome. The forged quest id is still refused by the
real gateway path, and the regression asserts that the persisted selection is
unchanged. No authentication, session, save-ordering, trade, inventory, reward,
or economy code was touched.

This is test synchronization, not a new gameplay rule. The existing `(R)`
journal policy remains: only an owned active quest can be selected, and a
forged id leaves saved state unchanged.
