## Client evidence (checked this task unless marked)

- **35/2 AddNpc reader `0x00921a10`** (`decompile`): `sub_8D6830` consumes the 4-byte
  header, then the u64 actor id is stored at object `+16/+20`; the rest of the reader is the
  field order mirrored by `startup_world::parse_add_npc`. The test parses the real packet
  with that production parser.
- **Warpstone spin.** Every warpstone AddNpc in the startup capture
  (`lab/content/startup-snapshot/startup.json`, 11 rows) carries `animation_id: 1`;
  `AnimationTypes.xml` (`<AnimationSlot name="loc_stand" id="1" .../>`) makes that
  `loc_stand`; `sg_warpstone_01.adr` section 9 is the model's **only** animation slot and
  maps `loc_stand` to `sg_warpstone.gr2` (speed 40), and `sg_warpstone_01.dsk` has the
  `SPIN_BASE` / `SPIN_EYE` bones. Our extra rows are built from
  `world::content_spawn_template`, which sends exactly the captured values
  (`animation_id 1`, `stand/walk/run_animation_id -1`, `movement_type 2`,
  `disposition 1`, `interact_range 100`). There is no server rotation clock in the codebase
  (`grep` for rotation packets: none) and no captured message that rotates a prop, so the
  spin is the client playing the actor's own `loc_stand` clip. `(R)` the visible spin is
  not natively re-verified in this task; the lead's native check confirms it.
- **26/3 dialogue body** (`decompile 0x00a9ef10`): the reader stores the first payload
  dword at `+16`; handler `0x00aa12e0` and display `0x009f5ae0` pass that to
  `Global.Text.<id>`, so the body id is bytes 4..8 — the harness already pins this.
- **26/8** (`decompile 0x008b6bc0`): u64 target + bool, as the server decodes.
- `ida_query find AddNpc` returned no matches; `xrefs 0x00921a10` -> `0x00925eb9` (a thunk
  that only calls the reader) and `0x009296a6`; `xrefs 0x00925eb0` returned none (indirect).
  I could not locate a dedicated "start the spawn animation" function in the time budget,
  hence the `(R)` on the visible spin. Nothing in this diff depends on that function.

## Threat note (secure-code-guardian)

- The only client input this feature touches is the existing 26/8 (u64 actor) / 26/10 (u64
  actor + i32 option) pair. A hostile client can name any actor id, any option id, any
  position, and replay. Refusals: the actor must resolve through `content_npc_key` (the new
  stone rows deliberately have no key -> `unknown_runtime_guid`, no menu, no state change);
  the option must be in the open menu (`InvalidOption`, menu retained); zone/range are
  re-checked on both calls. My new suite drives the refused choice and asserts the menu is
  still usable and no binding changed.
- The dialogue body is a server-side locale id; client text is never echoed and there is no
  string interpolation into packets.
- No saves, coins, items, rewards, roles, chat, sessions or logs changed; the stones are
  static content another player can only see, not trigger.
- No secrets added; no new logging of client-controlled data beyond the existing
  `npc_event` rows (guid/content key/option, already redaction-reviewed).
