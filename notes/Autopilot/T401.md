# T401: Inspect crashed the inspecting client (stats list missing from 149/1)

## Cause (client evidence)

The crash is an empty stats list in our 149/1. The missing 156/2 and 197/6 replies did not cause it.

- Lead's Frida trace: an access violation reading `0x14` at `0x00cc099f`, inside `InspectDataSource::GetValue`
  (`00cc0760`). In the disassembly that address is `mov edx,[eax+8]`, right after `call 00ad7700` in **case 12**
  (`push 1`).
- `00ad7700` is `return [proxy+0x2C4] + 12*index`: a positional lookup into the InspectProxy stats array, with no
  bounds check and no null check. When the array is null, index 1 gives `0xC`, and `+8` gives `0x14`. That matches
  the trace exactly.
- The InspectProxy constructor (`00ad8880`) sets the stats container at `+0x2C0` to `{vtable, data 0, size 0, cap 0}`.
  The only thing that allocates the array is the stats reader `00ad7f40`, which `00ad83b0` (the 149/1 payload
  reader) calls with `this+0x2C0`. `00ad7f40` reads an i32 count. A negative count, or a count larger than the
  remaining bytes, is refused. The array is resized to the count (`00ad7b80`), then `count` entries are read
  with `008e7640`: i32 id, i32 type, then an i32 value only when the type is 0 (int) or 1 (float).
- We sent a count of 0, so `data` stayed null.
- `GetValue` cases 12-16 read entries **1, 5, 7, 17 and 37**. Every xref to `00ad7700` is one of these five
  (`00cc099a`, `00cc09ca`, `00cc09fa`, `00cc0a2a`, `00cc0a5a`). In `ScriptsBase.lua` (lines 3314-3318) they are
  MaxHealth, MaxMana, Defense, StarBoost and CoinBoost.
- How the client reaches the crash: `PlayerInspect:ShowInspectPane` calls `SetInfo`, which calls
  `SerializeData(ds)` (`ScriptsBase.lua` 45240-45330). That walks every column of `BaseClient.Inspect` in
  order. Columns 0-11 read fine, then column 12 crashes. AboutPlayer (`9156`) reads the same five stats.

### Why about 31 s later, and what 156/2 and 197/6 do

- The 149/1 handler (case 0x95 of `009471a0`) runs three steps in order:
  1. It builds the InspectProxy (`009492d5` → `00ad8880`, which parses the payload with `00ad83b0`).
  2. It asks the Fotomat portrait cache for the target's **headshot**: `00949309` → `00bd4810` → `00bd43a0` →
     `00bd3ff0(..., "Headshot")`. On a cache miss this queues a pending entry and sends the request, which is
     the 156/2.
  3. It calls `SnsIntegrationProcessor::StartInspectRequest` (`00949321` → `00bb92c0`). That builds a
     `getUserInfoForFr` XML request for The9's `SnsServer` and sends it through `SendSecureSignatureRequest`
     (`00bb9400` → `00bb84f0`), which is the 197/6.
- The window is **not** opened by either reply. `StateObj_ShowPlayerInspect` (`008c6030`, the `PlayerInspect:Show`
  movie command) is called only from the InspectProxy actor callback at `00ad7460`, at `00ad7550` and `00ad759b`.
  That callback runs when the loaded actor's id `[actor+0x268]` matches `proxy+0x13EC`. It positions the clone
  and pedestal, then shows the window.
- So the ~31 s is most likely the time to load the clone and pedestal actors, followed by the first
  `GetData(0, 12)` (inference; not timed). In the lead's runs the window crashed while it populated, even though
  neither 156 nor 197 had been answered. Neither reply is on the path that opens the window.
- **156/2, no reply needed.** The answer would be a 156/3 `PacketPlayerImageData` (`00bd4180` → `00bd4a50`) carrying
  a portrait image. We have no image service. Without a reply the pending entry stays and no headshot appears.
  The Lua window never asks for one.
- **197/6, no reply on purpose.** A 197/1 signature reply would make the client post to the external The9 SNS
  endpoint (`00bb6ca0`). That is the China social-network feature the brief says not to invent. Without a reply,
  `ExtraDataPopulated` (`+0x178`) stays 0. The About tab is added only when `Ui.IsChinaEnvironment()` is true
  (`PlayerInspect:BuildNavigation`), and the SNS strings at `+0xFC..+0x15C` start as empty strings in `00ad8880`.
  Reading them is therefore safe.
- The gateway already answers neither request. Today they are logged as "unknown application message" and
  dropped, with no reply. I left that unchanged.

## What changed

- `src/player_radial.rs`: `start_inspect_packet` now sends `INSPECT_STATS = 38` stat entries (indices 0..=37), each
  `id = index, type 0, value 0`. Before, it sent an empty list.
- `tests/player_radial.rs`: `parse_inspect` now mirrors the client reader. It decodes the achievement pair, the
  eight scalars, the stats list (with `00ad7f40`'s count bound and `008e7640`'s type rule) and the trailing
  string, then requires the whole payload to be consumed. There is one new test,
  `inspect_carries_every_stat_the_window_reads`, which covers both a full look and an empty one.

## (R) choices

- (R) Each stat entry's id is its position. The client never reads the id (`00cc0760` reads only `+8`).
- (R) Every stat value is 0 (int). This follows W143's policy that strangers see no stats, which is the same as
  coins. To show the target's real max health, energy, defense and boosts, the server first needs a per-player
  stat model, which it does not have yet (`encounter::level_health` is battle-only).
- (R) Count 38, the smallest count that covers index 37 (CoinBoost).

## Threat note

149/1 is built by the server from the target's public look only. The new entries are server constants and take
no client input, so a hostile client has nothing new to send. 156/2 and 197/6 are still dropped without a reply.
Nothing is stored and nothing is relayed. The 26/10 and 26/19 refusals (stale, hidden, far or replayed) are
unchanged. Their existing tests still assert that they send nothing and leave no state behind.
