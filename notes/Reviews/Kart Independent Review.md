# Kart racing independent review

2026-10-08 (Pacific). **The kart racing bounded contract is verified for its own reconstructed checkpoint model, and it is not ready to be wired to live traffic or to the economy layer without the gates below. Ordered checkpoint/lap/replay machinery behaves exactly as documented; the wire decoder rejects more than half of the archived racing frames because it requires tunnel flag 1; `claim_reward` credits caller-built proposals, so arbitrary amounts are payable from an abandoned session; session identity is a bare `u32`; the caller's clock is trusted; `restore` trusts snapshot progress and drops the price schedule; and the opcode 102/2 encoder matches the community subset but not the captured framing. No builder source, builder test, research note or shared file was modified.**

## Repair follow-up (2026-10-09, same reviewer)

Scope: `src/kart_racing.rs`, `tests/kart_racing.rs`, `tests/kart_review.rs`, this note and `notes/Research/Kart Racing Restoration.md`. Repair bundle: `lab/reports/kart-review-repair-20261009T031700Z/` (pre-repair source copies plus hashes, RED and GREEN logs, capture re-check, final hashes).

- **Finding 1 closed: reward authority is derived, not supplied.** `claim_reward` now takes no proposal and derives the award from the session's own state: the session must be `Finished` with every configured lap counted, and the layout must carry an explicitly priced schedule. A `RaceResultProposal` from `finish` is documentation only. Abandoned and mid-race sessions return `NotFinished`; an unpriced finished run returns `Unpriced` and never consumes the one-shot marker; a priced grant is paid once. The forgery path the review demonstrated no longer exists as an API, and the guard tests assert the derived amount rather than trusting caller numbers.
- **Finding 2 closed in-module, gateway binding remains.** `session_id()` is exposed and documented for gateway ownership binding; claims are session-local, so a second session object that merely reuses the id has no claim authority. Which member may send checkpoints for a session is still gateway state and cannot be verified inside this module.
- **Finding 3 recorded, not papered over.** Ordered checkpoint ids remain the only progress source and no geometry is consulted; the module docs now state that unknown gate geometry or physics keeps a track unpriced and not reward-eligible, so this reconstruction cannot be promoted to a spatial authority claim.
- **Finding 4 closed: flags are lossless, direction is not invented.** `decode_racing_frame` accepts tunnel flags 0 and 1, preserves the captured flag on `RacingFrame`, and rejects only flags outside that range. The header, tests and research note no longer describe outer opcode 5/6 or the tunnel flag as direction: all 22,389 archived opcode-33 bodies carry outer 5 in both directions. The two hash-verified flag-0 racer streams and the flag-1 vectors decode losslessly.
- **Finding 5 closed: clock regressions are rejected before mutation.** `on_checkpoint` returns `ClockRegression { now_ms, since_ms }` and changes nothing when the timestamp predates the current lap start; `start` and `finish` return `KartRacingError::ClockRegression`. No zero-length best lap or total can be recorded from a rewound clock.
- **Finding 6 closed: snapshots are validated and the schedule travels with them.** `SessionSnapshot` carries `reward` (`serde(default)` keeps older snapshots unpriced), and `restore` validates bounds before indexing, last-checkpoint/next-index coherence, lap-count/best-lap equivalence, `lap_started_ms >= started_ms`, phase/progress coherence, and that `reward_claimed` only appears on a finished priced run. `TrackLayout::validate` rejects a schedule that prices nothing. The first implementation of these checks indexed `next_index` before validating it and panicked on `next_index = 99`; the new builder test caught it and the bounds check moved first. **Correction to the original finding:** the old "next_index on the last gate with zero gates counted" example was an incoherent snapshot (next gate present without the recorded last checkpoint), not a teleport; with a two-gate track, `next_index = 1` is the normal state after gate 11. The repaired validation rejects the inconsistent combination and accepts the coherent mid-lap state.
- **Finding 7 closed: the encoder is labelled as a community subset.** The module and research note now state that `LobbyGameDefinition::encode` is byte-identical to the pinned community writer but is **not** the native opcode 102/2 framing, and must not be used as a live 102/2 response until the captured framing (u32 remaining length, six rows, further blocks) is recovered.
- **Finding 8 closed with a format correction.** The captured subtype-11 name is length-prefixed, not NUL-terminated: the declared count equals the exact name length in all six frames, and the bytes that follow are the attribute block beginning with the `f32` 400.0 (`00 00 c8 43`). The repaired decoder rejects empty, truncated, embedded-NUL and non-UTF-8 name windows without inventing a terminator requirement. The review's original "unterminated name" phrase described the old lenient window handling; the measured layout is what the repair implements.

## Findings (pre-repair record)

1. **`claim_reward` trusts the proposal it is handed, so the reward seam is open (economy gate).** `claim_reward` (`src/kart_racing.rs:584-603`) checks only `proposal.session_id == self.session_id` and that the phase is `Finished` or `Abandoned`; it never re-derives coins/xp from `layout.reward`, never checks `laps_completed`, and accepts a proposal the module did not build. The review test `forged_and_stale_reward_proposals_are_credited_by_claim_reward` constructs a `Granted { coins: 1_000_000, xp: 1_000_000 }` proposal by hand for an `Abandoned` session whose layout has no schedule and whose lap count is 0, and the module returns `Ok(Granted)`. The same test shows a stale mid-race proposal (one lap of two) remains claimable after the session finishes with a different result; `finish` alone is repeatable and produces a fresh `Granted` proposal on every call (`src/kart_racing.rs:507-527`), so the one-shot guard only exists at `claim_reward`. The builder's test suite never sees this because it only ever claims the object its own `finish` returned. Gate: the lead-owned economy layer must treat `RaceResultProposal` as untrusted input and re-derive the award from server-side session state (phase `Finished`, `laps_completed == layout.laps`, schedule from content), or `claim_reward` must validate the proposal against the stored layout before crediting. The counterexample tests are written to be updated when that happens.
2. **Session identity is one `u32`, and gate hits carry no sender identity (member identity gate).** `RaceSession::open` takes only `session_id` (`src/kart_racing.rs:390-409`), the snapshot stores no member/character id (`SessionSnapshot`), and `claim_reward` accepts a proposal from a *different* session object that merely reuses the same numeric id (test `session_identity_is_only_the_numeric_session_id`). Nothing in the contract binds a checkpoint observation to the racer who owns the session, so the gateway must key sessions by member and reject checkpoints for sessions the sender does not own; the module cannot do that alone.
3. **Client checkpoint ids are the entire proof of progress; there is no spatial corroboration (authority limit, explicit).** `on_checkpoint` (`src/kart_racing.rs:451-493`) accepts the next configured id and nothing else: no position, radius or geometry is consulted, and the module's own battery finishes a two-lap race with `observed_racer_states == 0`. The capture's position-bearing bulk streams (subtypes 5/6/14) are deliberately opaque (module doc `src/kart_racing.rs:28-32`, `observe_racer_state` `:498-505`), so the reconstruction currently has no way to distinguish a racer crossing a gate from a sender that knows the next id. That is an acceptable bounded reconstruction only if the lead records it as such; native gate geometry remains an open mapping task.
4. **The decoder's flag rule contradicts the archive (decoder scope and evidence accuracy).** `decode_racing_frame` requires tunnel flag 1 (`src/kart_racing.rs:177-179`); the module header claims the capture contains no other shape (`:167`) and the research note states the flag is "always 1 in this capture" (`notes/Research/Kart Racing Restoration.md:34`). The independent archive scan counted 22,389 opcode-33 bodies: **12,855 carry flag 0**, including all 4,679 subtype-6 (client racer stream) frames and 8,176 of 8,182 subtype-5 (server racer stream) frames. Test `flag_zero_bulk_racer_frames_exist_and_are_rejected` pins the rejection with two hash-verified archived bodies (`lab` files `racing-01135-flow0-frame27068-op33-sub5.bin`, `racing-00002-flow1-frame21194-op33-sub6.bin`). Either accept 0|1 the way `gateway.rs::tunnel` and `soccer.rs::decode` already do, or narrow the doc and the decoder's scope to priced control frames with that limitation written down. Related correction: all 22,389 opcode-33 bodies carry outer opcode 5, including the client->server ones (subtypes 2/6/7/9/10/17/22 sit on UDP flow 1), so the comment "5 = server to client, 6 = client to server" (`:11`, `:57-60`) is not how this capture distinguishes direction; direction comes from the connection, and accepting both opcodes is harmless.
5. **The caller's clock is trusted; regressions become zero-length best laps (timing gate).** `on_checkpoint` computes `now_ms.saturating_sub(self.lap_started_ms)` (`src/kart_racing.rs:468-474`) and `finish` does the same for `total_ms`. Test `caller_supplied_clock_is_trusted_and_regressions_become_zero_lap_times` starts a race at 5,000 ms, delivers both gates at 4,000/3,000 ms, and the session records `lap_ms: 0`, `best_lap_ms: Some(0)` and `total_ms: 0`. The parameter is documented as a caller-supplied timestamp; the gateway must supply a monotonic server clock, and a non-monotonic observation should be rejected rather than saturated into a record.
6. **`restore` validates two bounds, then trusts the rest, and drops the price schedule (reconnect gate).** `restore` (`src/kart_racing.rs:553-580`) checks `next_index < checkpoints.len()` and `laps_completed <= laps` and rebuilds everything else verbatim. Test `restore_accepts_incoherent_snapshots_and_drops_the_reward_schedule` shows that a snapshot with `next_index` on the last gate and zero gates counted is accepted and then completes a whole lap on one gate; `phase: "finished"` with zero laps is accepted; `best_lap_ms` without any completed lap is accepted. Because `restore` sets `reward: None` (`:558`), a legitimately finished race that reconnects always returns `Unpriced` — safe against double payment, but the lead must re-attach the schedule from content on reconnect (work item 017's territory). Snapshots must remain server-owned; if they can ever be client-influenced, coherence checks are required before this is acceptable.
7. **The lobby encoder matches the community subset but not the captured 102/2 framing (integration gate, not a defect).** The community writer's layout was re-read from the pinned sources: `LobbyGameDefinition.Serialize` writes the entries dictionary then four zero counts, and `PacketWriter.Write(IDictionary<int,TValue>)` (`lab/references/Sanctuary/src/Sanctuary.Core/IO/PacketWriter.cs:164-173`) writes count, then key, then the entry's `Id, Type, Unknown, NameId`. `LobbyGameDefinition::encode` (`src/kart_racing.rs:132-146`) reproduces that byte-for-byte for the three-row vector (oracle 80 bytes, SHA-256 `e088a1f9…`, independently re-derived in `lobby_oracle_re_derives_from_the_community_layout`). The captured opcode 102/2 payload is a different framing: `[u32 remaining length 2378][u32 row count 6][row0 = (1, 1, 1, 37, 3030)]` followed by further blocks (first 48 bytes of `racing-23867-flow0-frame44523-op102-sub2.bin`, SHA-256 `4f6d75c4…`; test `captured_lobby_payload_has_a_length_prefix_and_six_rows`). Row 0 matches the note's "37/3030 pair" claim; the remaining rows carry different trailing values (`(2,2,2,0,0)`), so the row schema beyond row 0 is not established. The module must not be used as the live 102/2 catalogue response until the native framing is recovered; the note already labels this an open gate.
8. **Minor decoder notes.** `vehicle_body_asset` (`src/kart_racing.rs:205-223`) returns `Ok("")` for a declared length of 1 holding a lone NUL, and accepts a name with no NUL at all (test `asset_name_decoder_accepts_empty_and_unterminated_names`); require a non-empty NUL-terminated name or document the tolerance. `LobbyGameEntry` cannot express a `key != id` row even though the community writer's dictionary shape can; the pinned handler and captured row 0 both use equal values, so this is a ponytail-style deferral until a captured row shows otherwise, not a defect.

Per-subtype flow, flag and length counts match the builder's subtype table, with direction re-derived from the capture's UDP four-tuples (flow 0 = server `64.37.170.6:20267` → client `192.168.1.145:61759`; flow 1 the reverse). - **Bounded session behaviour.** The review battery confirms: countdown-phase checkpoints are inert; out-of-order and unknown ids never mutate state (snapshot equality); duplicates are idempotent; stale previous-lap gates are duplicates or out-of-order; the same `Finish`-only-after-last-lap, best-lap tracking and opaque bulk-stream non-interference the builder tests assert on five of six cases now also hold for a three-gate track and for archived flag-0 bodies.

## Verdict

Bounded independent review complete. The checkpoint order, lap accounting, replay/duplicate handling and opaque-stream separation are sound and match the archived evidence they cite. The module is **not** ready for live traffic or economy integration until the lead closes finding 1 (re-derive or validate rewards at the claim boundary), finding 2/3 (member binding and the explicit ID-only authority limit), finding 4 (flag scope, or a corrected claim), finding 5 (monotonic server clock) and finding 6 (snapshot ownership, schedule re-attach) — and it is not a playable minigame until the native gates in the research note are recovered. Lead acceptance and native acceptance remain open.
