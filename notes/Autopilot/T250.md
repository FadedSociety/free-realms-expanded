  already byte-pinned by `vendor_stock_coverage`), so the test adds no second

## Production path and why each assertion proves S12/L8

`Session::commit_outcome` stages the whole purchase on a cloned `Gateway` and a
cloned `SharedWorld`, runs `save(&self.state_path, &staged_gateway.snapshot())?`
inside its `prepared` closure, and only then installs the staged gateway/world
(`self.gateway = staged_gateway`, `*world = staged_world`) and queues replies. A
save error therefore returns `Err` from `commit_outcome`;
`dispatch_message_inner` propagates it with `?`; `Server::step`'s `contain` error
arm calls `end_session` for that session alone. **Production takes both halves:
the transaction errors, and the step ends only that session.** The tests prove
each half:

1. **Transaction error** —
   `a_failed_vendor_save_changes_nothing_and_preserves_buy_back_state` asserts
   `dispatch_message` returns an error whose text contains the filesystem
   `os error`, i.e. it failed in the save, not in packet parsing, and drains the
   session's sender to assert **no client success reply was queued**.
2. **In-memory character unchanged** — the same test takes
   `gateway.snapshot()` immediately before the buy and asserts whole-snapshot
   equality after, then asserts coins and the purchased definition count
   explicitly. `Snapshot` is the canonical `character + gameplay` save payload.
   It does **not** include the session-only `Gameplay::npc_coin_shop` or
   `Gameplay::npc_interaction` fields, so the Coin Shop's state is proven
   behaviourally in the same test: a real 165/5 sale is made before the failed
   buy, and after the failed buy the same sale transaction still buys back at
   the `stores.json` resale price (375 for this item) and restores the item. The
   failed buy's transaction id is then replayed after the save is repaired: it
   must charge and grant, which proves the 66/43 idempotency cache
   (`CoinShop::vendor_transactions`) did not record the failed purchase.
3. **On-disk save unchanged** — the good save bytes are read before the break
   and compared byte-for-byte after the failed buy. Because the broken save
   targets a path under that same good file, no directory entry for it can be
   created either.
4. **Only that session ends / no ghost** —
   `a_failed_vendor_save_ends_only_that_session` builds the t020 server rig
   (`isolation.rs`'s rig), runs the buy as a real reliable datagram through
   `Server::step`, and asserts the victim session key is gone while
   `active_sessions`, `joined`, `players`, `chat_sessions`, `session_keys` and
   `World::player_location` have no victim row, the good save is byte-identical,
   both other sessions remain with their world rows and session keys, and one
   surviving session still answers its next datagram after the victim ends. (F294
   corrected the earlier F285 claim: the F285 test exercised only the first
   survivor; the final test sends the login to both, each on its own socket.)
5. **Control** — `control_a_working_save_commits_the_same_purchase` runs the
   same fixture, handshake, shop open and 66/43 packet with a writable save:
   coins drop by the authoritative `stores.json` price, the item count rises by
   exactly one, and the save file is rewritten. This proves the failing test is
   not passing because the purchase was refused earlier for an unrelated reason.

## Security threat note (secure-code-guardian)

- **Attack surface:** a hostile client can send 66/43 at any moment with an
  arbitrary item id, quantity and transaction id, and can send 165/5/165/12
  around it. This change adds no parser and no route; it proves the existing
  purchase transaction's failure behaviour.
- **Why a hostile request cannot profit:** 66/43 must decode
  (`npc_interaction::decode_merchant_buy_66_43`), must come after a server-opened
  shop (26/8 → 26/10), the item must be in that vendor's authored stock and the
  character must be in range of that NPC
  (`NpcInteraction::validate_merchant_item_66_43`); the client price is ignored
  and `stores.json` supplies the Coin price; quantity and transaction id are
  client values but the buy runs on a staged `Gateway` clone. The test proves
  that when the follow-up save fails, all of that staged state is dropped: no
  coins, no item, no transaction-cache entry, no sale history, no open-shop
  consumption, no save write. The test's poisoned save path is host-side only;
  no client field selects `state_path`.
  The rejection path for malformed/refused 66/43 is already covered by
  `tests/vendor_sell.rs`, `tests/npc_interaction.rs` and `app_fuzz`.
- **Economy:** the control purchase charges exactly the server price once and
  adds one item; the failed purchase charges nothing and adds nothing. The
  buy-back probe proves the pre-existing sale record keeps its id and
  `stores.json` resale price (375) through the failure.
- **Isolation:** the save error is returned as an error, never `unwrap`ped; the
  server test proves the error ends one session through the existing `contain`
  boundary and leaves the other sessions and a second step running.

## Checklist

1. **A refusal changes nothing.** The failed purchase test snapshots the full
   canonical `Snapshot` and the good save bytes around the failure and asserts
   equality; the buy-back probe asserts the Coin Shop state too. The canary
   (ignored save error) makes the same test fail, so it is sensitive to the
   behaviour, not to test-side failure.
2. **Rollback covers all state.** No transaction or shared state was added. The
   production purchase runs on `staged_gateway`/`staged_world` clones and the
   test asserts both the canonical snapshot and the session-only Coin Shop
   (via buy-back) survive the failed save; the server test asserts no world row
   escapes.
3. **Apply deltas, never restore old snapshots.** No payout/exit code changed.
   The control purchase applies the server price to the live-inventory copy
   (`CoinShop::sync_inventory` in the existing 66/43 route) and saves the new
   state; the failing test verifies the old save is not overwritten.
4. **Busy rules are mutual.** Not applicable: no new activity, no
   `Occupation` variant, `gameplay/occupation.rs` untouched.
5. **Every entry path is gated.** The test uses the production 66/43 dispatch
   (`Session::dispatch_message` and `Server::step`); it adds no parallel path.
   The existing open-shop, merchant-item and range checks are exercised before
   the save.
6. **Reachable in production, tested through it.** Gateway → `Session::dispatch_message`
   → `commit_outcome` → `save`, and the server-level case delivers a real SOE
   reliable datagram into `Server::step`. No private transaction helper is
   called by the tests.
7. **Survives reconnect.** Not applicable: this change adds no persisted state.
   The control's committed save is the same canonical envelope; the failure
   test proves the old save is intact for a reconnect.
8. **Every exit path restores the player.** The server test is the exit path
   under test: the failed purchase ends the session through `end_session`; the
   victim has no `active_sessions`, `joined`, `players`, `chat_sessions` or
