## Subsystems and connections

- **Social share (`00adf030–00ae1060`)**: `SocialShareManager` owns three provider states, each with two `IString` fields and a 64-bucket request map (`00ae0850`, `00ae09b0`). Requests are queued as kinds 1–3 and processed by `00ae1060`; `00adfe50`, `00adfef0`, and `00adffe0` represent provider-status, authorization, and payload work. The map helpers insert at head/tail, find by key, unlink, and release tracked nodes (`00adefe0`, `00adf770`, `00adf810`, `00adf8b0`).
- **Social share wire structure (`00adf140`, `00adf280`, `00ae0c40`, `00ae0d50`, `00ae03d0`, `00ae0520`)**: packet constructors inherit `BaseSocialSharePacket`; its base initializer writes base opcode `0xcd` and a supplied sub-opcode (`00ade960`). Constructors in this shard use sub-opcodes 2 and 3. Encoders serialize provider fields and strings; receive handlers parse response fields, match outstanding requests and dispatch callbacks. Community packet catalogue has no SocialShare class, so it does not independently corroborate this family.
- **Client-side HTTP outcomes (`00adfc00`, `00ae0ea0`, `00ae0f60`)**: HTTP completion maps response strings including `success`, `ratelimitexceeded`, and authorization errors to callback states; missing/revoked authorization clears local state. The text proves client mapping only. Hypothesis: the remote social-share service returned these body strings and status codes. This depends on the response mapping at `00adfc00` and request continuations at `00ae0ea0/00ae0f60`; no original server implementation or endpoint is recovered.
- **Steam (`00ae1120–00ae1860`)**: init/shutdown and callback registration/pumping wrap Steam APIs. `00ae1630` compares a microtransaction order ID with SteamUtils, logs authorization and calls a local handler. It does not demonstrate an in-game grant.
- **Items/profile (`00ae19c0–00ae1f70`)**: helpers search 4-bucket item maps, validate equip slots (`00ae1a40`, anchored by `Items.log`), maintain cached item values and insert ProfileItem nodes. The map allocator and cleanup use a four-bucket `SoeUtil::HashListMap`.
- **Player events (`00ae20d0–00ae2470`)**: RTTI identifies PlayerHitpointEvent and PlayerHitpointDeltaEvent; constructors/destructors, virtual apply routines and context lookup connect at `00ae2190`, `00ae2280`, `00ae2350`, and `00ae2470`.

- **Containers/delayed assets (`00ae3940–00ae4e70`)**: pointer-array growth and removal, pending-request arrays/deque, hash map, tree navigation/rotations/rebalance, and queue cleanup support delayed asset operations. Helpers expose storage mechanics; full scheduling semantics remain unresolved.
