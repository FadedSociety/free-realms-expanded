# T219: Derby completion reward

## Result

The demolition derby pays a **flat completion reward** when the server-observed match reaches its
results phase with the character still in it. The payout is recorded per match instance in a
persisted, bounded ledger, so a repeated results record, a reconnect or a replayed match cannot pay
twice. Leaving, cancelling, disconnecting or timing out before results pays nothing. There is no
cooldown and no daily cap (the owner: farming finished matches is allowed).

- `derby_entry.json` gains `completion_reward_coins` and `completion_reward_xp` (R, both default
  0 = payout disabled) with a 10,000 sanity bound. The retired F117 `reward` row and
  `reward_cooldown_s` stay accepted and ignored (F206 migration).
- The ledger lives in `GameplayState::derby` (`DerbyGatewayState::paid_matches`), written through
  the existing atomic character save. It keeps the newest 32 rows; the match instance counter
  resumes above the newest row, so a paid id is never reissued to that character.
- The trigger is `DerbyPhase::Results` only, reached from `Running` after the client-owned
  phase/countdown acknowledgements. The amount never depends on contacts, damage or score.
- The payout reuses the one minigame reward path (D004/S5): `reward_snapshot()` ->
  `rewards::apply_grant` -> `adopt_reward_state`. No second reward applier was added.

## Reconstructed rules (R)

- (R) "Finished" = the server-observed results phase with this session's character still connected.
  The flat coin amount and the Demo Derby Driver XP are reconstructed content values, not recovered
  retail rewards; both are bounded at 10,000 by the loader.
- (R) The 32-row ledger bound is a save-size bound. Dropping the oldest row cannot enable a second
  payout: the instance counter only moves up.
- (R) No cooldown and no daily cap, per the owner 2026-10-20.
- (R) The reward toast is kind 0 / icon 0 / name 0 / no entry rows, matching the existing ordinary
  toast (`kart_rewards::reward_bundle_toast`).

## Security threat note (secure-code-guardian)

Threat: a hostile client owns the whole `34/*` stream. It can send a stationary pose, forge any
bounded contact or impact, replay the record that drove the match to results, replay 39/6, 39/7,
39/5 and 26/42 out of order, cancel and re-enter to farm, keep its wallet at the wire maximum, or
hand-edit a save with a forged ledger.

Why it is refused or harmless:

- The payout is gated on the server-owned phase (`DerbyPhase::Results`), which `finish_match` only
  reaches from `Running`; that requires the full 39/16 -> 39/5 -> 34/6 -> phase 3..8 -> countdown
  4..0 exchange. No client message says "results".
- The amount is content, never a function of a client value: contacts, damage and score cannot
  change it (pinned by `collision_reports_never_change_the_payout`).
- A collision report in `Running` cannot pay by itself: the restored F164 test sends a bounded
  fabricated contact, asserts the server resolves it and the match stays `Running`, then leaves;
  coins and the ledger are unchanged.
- The ledger is the double-pay guard: the same match instance can be claimed once, per character
  save file. Two characters with identical instance ids are paid independently (pinned). A paid id
  is never reissued because `next_instance` resumes above the ledger.
- A forged ledger fails closed: `deny_unknown_fields`, positive ids and a 32-row bound; the load is
  rejected instead of paying.
- A payout that cannot be applied (overflow) returns `Err` before any state commits; the gateway
  rejects that application and the match stays running (`a_refused_derby_completion_payout_changes_nothing`
  asserts the full snapshot is unchanged). A save failure is caught before the staged gateway is
  committed (`commit_outcome` saves first), so the file and the live session state stay unchanged
  and only that session ends through the existing `contain`/`end_session` path.
- Free grants: the Demo Derby Driver starter outfit is still unlock-once at entry (`first_time`)
  and is not touched by the payout.

## Checklist

1. **A refusal changes nothing.** `a_refused_derby_completion_payout_changes_nothing` (real
   `Gateway::handle_at`) snapshots before the results-driving record, refuses the payout (wallet at
   the wire maximum), and asserts the whole persisted snapshot is byte-equal afterwards; the match
   stays `Running` and the session keeps serving (`follow_up`). Canary 1 proves the restored test
   detects a payout in `Running` (the whole application is rolled back to `Running`, not half
   applied). The Gameplay-level staging means every payout error path (`apply_grant`,
   `adopt_reward_state`) discards the staged clone. A save failure is also covered structurally by
   the binary's `commit_outcome`: it saves the staged gateway before assigning `self.gateway` and
   queuing replies (`src/bin/osfr-gateway.rs:1929-1968`), so a failed save leaves the live session
