## Client evidence

- Follow sender `00b5fcf0` (the writer the T455 note calls `SendPetFollowLocation`): the decompiled
  function computes the distance from the picked point (`sub_8A7D50` result) to the vector the
  handler tracks (the `a2` it stores at dword +1204) and only builds the packet inside
  `if (distance >= 8.0 && distance <= 40.0)`. So the client's own target window is 8-40 m; the
  server bound is set to the client's maximum, 40 m, so a real click is never narrowed. The
  server-side rule is still marked (R): the client's tracked point is not proven to be the owner
  rather than the pet, and reachability is unrecovered.
- The 35/8 base packet and the 35/2 AddNpc are the existing writers (`piece_052::animation_packet`
  and the captured AddNpc template); this diff adds no packet field. The T531/F809 client evidence
  for the four bubble ids and the 35/27 reader `008d7880` is unchanged.

## Threat note (secure-code-guardian)

- **Hostile client input:** the follow click is the only new input path touched. Before this
  change a finite target of any magnitude (for example `[1e38, 1e38, 1e38]` or a huge height)
  moved the server pose and was replayed to viewers as 125 frames and a late-viewer AddNpc; the
  pet would warp back only after `warp_far_ms`. Now every target farther than
  `follow.click_max_m` from the owner, in the plane or in height, is refused before any state
  changes: `follow_target`, the pose, `settled` and the rest loop are untouched, so a refused
  click changes nothing (asserted by the whole `PetPresence` plus the next tick).
- The click still grants no item, coin, XP, role, save or collision/reachability authority: the
  pet is a session-only cosmetic actor, and the accepted target only moves that actor. The path
  has **0 production callers** in the graph today; the bound is inside the service method so every
  future route is gated at the one entry.
- The late-viewer packet is built from the server's own rest state (`IdleState`), never from a
  client value, and the AddNpc precedes the 35/8 (asserted in the gateway test). No session,
  login, transport, role, trade, inventory or persisted-file code is touched. No new unwrap or
  panic on client data: the checks are pure `f32` comparisons after the existing finite check.

## Checklist

1. **Refusal changes nothing.** The new out-of-range follow refusal runs before `follow_target`
   and `pose.goto`; the test asserts the whole `PetPresence` is equal before/after for four forged
   targets and that the next tick still finds the pet lying with no animation. Canary 2 proved the
   test catches a missing bound. The NaN refusal and the water/care no-save assertions remain.
2. **Rollback covers all state.** No transaction or side table: the rule is a pure
   `FollowConfig::admits_click`; the only mutation after it is the active pet's target/pose. The
   service's `Arc` content is read-only.
3. **Apply deltas, never restore snapshots.** Nothing restores an old inventory, coin or position
   snapshot. The click moves the live pose to the new target; the follow step advances from the
   live owner pose.
4. **Busy rules are mutual.** No new activity. The idle life still refuses while a feed, groom or
   trick runs or water is current; the follow click remains cosmetic and the `Occupation` table is
   untouched.
5. **Every entry path gated.** The bound is inside `PetService::follow_location`, the one service
   entry (graph: 0 production callers yet), so a future route cannot skip it; it fails closed
   without a follow block. The gateway late-viewer test drives the real join/tick/fanout path.
6. **Reachable in production, tested through it.** The late-viewer replay is tested through
   `SharedWorld::with_pets` with a real viewer join; the rest posture comes from the real world
   tick and the real adoption. The backwards clock is tested through `PetService::care_tick`, the
   same tick `Gameplay::pet_tick` runs. The follow click still has no client route (F809 open gap),
   so its test is service-level like F809's.
7. **Survives reconnect.** No new persisted field: `click_max_m` is content loaded at startup, the
   rest loop and pose are session-only (existing tests cover dismiss/reconnect). Nothing new in
   the save.
8. **Every exit path restores the player.** The refused click leaves the pet lying and settled;
   the accepted click stands it up and the walk/resume behaviour is unchanged. Dismiss, zoning and
   reconnect still drop the actor (existing tests).
9. **Economy safety.** No item, coin, XP or free grant is added or changed. The gateway test's
   adoption uses the test-only `grant_certificate_for` helper on a scratch session; it is not a
   production grant and no quantity or result comes from the client.
10. **Wire format matches the client reader exactly.** No field added. The test rebuilds the 21-byte
    35/8 (guid, i32 slot, i32 0, u8 base 1) and asserts it follows the AddNpc; the AddNpc stays the
    existing 35/2 writer. The click bound's client evidence is the sender `00b5fcf0` (8-40 m), and
    the 35/27/T531 evidence is unchanged.
11. **Unique ids.** No id added; the pet actor guid is the existing owner-derived id.
12. **Others see changes.** The late viewer receives the rest base right after the AddNpc, only on
    its own deliveries (the test filters by recipient); regular ticks already send the visuals to
    the owner and viewers.
13. **Content works end to end.** The gateway test asserts the final delivered packet order, not an
    intermediate flag; `click_max_m` is validated content, and the shipped value is pinned to the
    client's own maximum.
14. **Values live in data.** `follow.click_max_m` is in `pets.json` with load-time bounds
    (1..=100 m, <= `warp_far_m`); the test pins the shipped 40.0 and the boundary. No new compiled
    timing or radius constant.
15. **Canaries break production code.** Three canaries, each a production/data break (hub fanout,

16. **Hands off session plumbing — NOT SATISFIED; needs lead sign-off.** F833's diff changes no

17. **One player's error never stops the server.** The changed code returns `Err` (no panic, no
