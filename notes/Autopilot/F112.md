  `QuestEvent::VisitPosition` after NPC quest login synchronization in both

  launcher, login, account, session, transport, trade, store, studio or
  manifest file was touched.

## Threat note

A hostile client can replay the kart finish `33/7` (or the `41/108` Go), send
`33/9` with forged unrecovered words, forge a `41/108` instance/GUID, spam
`39/14` movie payloads, replay `138/6`/`138/7` fishing frames with a forged
handle, or click arbitrary `26/8`/`26/24` requests. None of these can fabricate
a completion:

- Kart credit is server-owned. `RaceSession::claim_reward` consumes the finish
  marker on a staged copy, the content registry prices the speedway, the active
  job must be Kart Driver, and `claim_reward_with_event` returns the speedway
  only after the payout committed. `handle_kart_entry` and `tick_world` forward
  the quest event only from that return, so a replay (already-claimed finish)
  emits no event. A refused payout leaves the finish retryable and unpaid.
- Quest progress comes only from these server events, never from client text,
  scores or reported results. The cooking/Type8 movie text is accepted only in
  the matching phase/instance, and the replayed win is refused before any
  mutation (test).
- Fishing pays only after the server-owned round and timers; a replayed reel
  after the catch changes no coin, item, XP or quest state (test).
- Every request decoder validates exact widths, ids and ranges; malformed or
  out-of-order frames return an error/refusal before staged state is committed,
  and the tests compare the whole state on refusal.
