## Reconstructed rules (R) and provenance

- The opcode layouts are unchanged from F179/F264 and no production wire byte changed here.
  165/2 request is `family, subtype, i32 count, u32 ids` (`coin_shop::item_definitions` validates
  `inner.len() == 8 + 4 * count`); 165/3 is `flag, i32 count, u32 ids` (`coin_shop.rs`,
  `definition_outcome`). Re-checked with IDA this session: the client writer `0x00c75620`
  writes a dword count (`sub_911420`, 4 bytes) then 4-byte ids (the 165/2 payload, with the
  8-byte family/subtype/count prefix pinned by `coin_shop::item_definitions`); `0x00c74e40`
  reads the 165/3 flag then hands the count to `0x008e8230` for the ids; `0x008e5940` reads the
  125 pose as u16, two actor dwords, six f32, two tail bytes (36 bytes); `0x00a36f80` stores three
  dwords (the 26/10 actor u64 and option i32) after its header call. `0x008e5940` and
  `0x00a36f80` match F264's citations.
- The 8 MiB bundle budget and 4 MiB per-answer cap remain server memory policy, lead-signed
  2026-10-19. This diff changes neither value nor the refusal policy; it removes the unsigned
  refund and documents the deliberate staged-bytes accounting.
- The `realm race` entry and the precommit save-failure path are the production paths F264 used;

## Threat note (secure-code-guardian)

- What a hostile client can send: one `[0, 25]` bundle containing a combat child plus arbitrary
  other children (165/2 reads with up to 4,096 ids each, a `realm race` chat command, NPC
  selections). The session budget bounds the bytes one message stages at 8 MiB; a 165/2 answer
  over 4 MiB is refused before any record is copied; a child that crosses the bundle budget ends
  only that session.
- Why the reverted refund is safe: the budget only refuses. Removing the refund cannot make a
  message stage *more* bytes, and the charge is `saturating_add`, so a hostile bundle cannot
  underflow it. No client input can produce a refund now, so no client can raise the ceiling or
  avoid a refusal.
- Refusals: the over-budget child is refused before commit (the split test asserts the full
  character+gameplay snapshot is unchanged); a refused precommit transfer commits no zone,
  membership or save change (asserted). The only escape on that path is the pre-existing emote
  assignment (finding 4, lead task).
- No economy, item, coin, role, auth or save path is touched; no new `unwrap` on client-controlled
  data; no production file writes (the new test helper writes only inside its `Scratch` temp
  directory); no shared `Rc`/`Arc`/side table.
