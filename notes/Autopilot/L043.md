# L043 - Admin `realm move` for stuck characters (lead-only)

`realm move <character name or GUID> <warpstone name | x z | x y z>` moves another
character, online or offline, into the open world. Admin role only. Retail GMs did this by
hand; the client still ships their quick-chat lines (`en_us_data.dat` physical lines 27386
"Will you please log out, so I can fix your character?" hash 1033945280, 103329 "Are you
stuck?" 3907735121, 78937 "I'll move you." 2989863943).

## What changed

- `src/gameplay/admin_move.rs` (new): parses `realm move` after `command_refusal` and stages
  an `AdminMove { target, position, rotation }` on `Outcome.admin_move`; also the moved
  character's side, `Gameplay::admin_relocation`, which refuses exactly where a 122 rescue
  is refused (`warp_context`: outside zone 0, knocked out, in an encounter, busy by the
  occupation table) and otherwise calls the same `apply_relocation` every warp uses.
- `src/gameplay.rs` (hub, +9): `mod admin_move`, the `Outcome.admin_move` field and its
  `absorb` rule (last staged wins, like `broadcast`), one call after `command_refusal`.
- `src/gateway.rs` (hub, +4) and `src/gateway/admin_move.rs` (new):
  `GatewayOutcome.admin_move` carried like `broadcast`; `Gateway::stage_admin_relocation`
  stages the target's pose, movement baseline, expected jump and the 38/12 packet exactly as
  `handle_at` stages a relocation. It refuses while the world is loading. It sets
  `gameplay_changed`, so the commit saves at once (never the deferred pose save) and a failed
  save commits nothing.
- `src/bin/osfr-gateway.rs` (hub, +14) and `src/bin/osfr_gateway/admin_move.rs` (new): after the
  admin's own transaction commits (the T199 broadcast slot), `admin_move::run` resolves the
  character in the account store, then:
  - a selected session owns it (the login predicate, now the shared `owning_session`):
    loaded and the same character, so stage on a clone of that session's gateway and commit
    through that session's own `commit_outcome` (pose fanout, membership, save). Loading, or
    the account is playing another character: refused.
  - no session owns it: `game_store::replace_pose` rewrites only the saved pose.
  - one `security_log` row per applied move; the admin gets one system line.
- `src/game_store.rs`: `replace_pose` (read, refuse a missing save or another zone, then the
  ordinary atomic `save`, which keeps housing; the pet roster is carried as
  `Snapshot { pets: document.pets }`, see the replay section).
- `src/security_log.rs`: `record_admin_move` / `AdminMoveRow`, written at once, never batched;
  the append-and-rotate code moved into `append`, shared with the refusal rows.
- `src/account_store.rs`: `character_by_display_name` (exactly one match or none).
- `src/restoration/piece_077.rs`: `WarpRegistry::named_arrival`; the terrain lift moved into
  `lifted`, shared with the 90/122 `arrival`.
- Tests: `src/bin/osfr_gateway/l043_admin_move.rs` (4, real `Server` in account-store mode),
  `gameplay::admin_move::tests` (3), `security_log` (1), `tests/game_store.rs` (1),
  `tests/roles.rs` (`move` pinned admin-only), the `absorb` field pin in `content_reload.rs`.

Unchanged: `realm goto`, the save schema, the account store format, session creation and
teardown, transactions and save ordering.

## (R) choices

1. The online target must be where a 122 rescue works: zone 0, not knocked out, not in an
   encounter, not busy. Otherwise refused; the GM asks the player to log out and moves the
   offline character.
2. An offline save must already exist and be in zone 0; nothing is created and other zones
   are refused.
3. Ownership is login's own predicate (account OR character): the move is also refused while
   the account plays a different character.
4. Fail closed: no account store, or no open security log, refuses the move.
5. Warpstones by name ignore attunement. `x z` lands 0.5 m above the server terrain (as
   `realm goto`); `x y z` is taken as given (finite, within the save bounds).
6. Facing: a warpstone's captured spawn facing when known, else the character keeps its own.
7. Moving yourself is refused (`realm goto` does that): the admin's session is out of the
   session map while it dispatches, so it would otherwise look offline.
8. Names match the displayed name ignoring case; two matches refuse (use the GUID).
9. If the audit row fails after a move, the move stands and the admin is told the row was not
   written (stderr too).
10. Two moves in one bundle: the last one runs, like two broadcasts.

## Security

Threat note (secure-code-guardian / security-reviewer):

- **Who may run it.** `command_refusal` runs before `admin_move_request`; `can_run_realm_command`
  lists `move` for no role but admin (pinned in `tests/roles.rs`). A player or builder gets
  the ordinary role refusal, identical for an existing and a missing target, logged as a
  `DevCommandDenial`, and nothing is staged. The host only acts on a staged `AdminMove`, which
  only gameplay creates after `may_run("move")`.
- **Hostile input.** The admin's chat text is the only input: split into words, coordinates
  must be finite and within `MAX_COMPONENT_MAGNITUDE`, a GUID must exist in the account store,
  a name must match exactly one character. The save path comes from that store-verified GUID,
  never from the name.
- **Races.** The server is single-threaded; the check (`owning_session`, login's predicate)
  and the write happen in the same step. A selected but unloaded session (it has already read
  the save and would save over a rewrite) is refused. A logging-in session that selects later
  reads the already-replaced file.
- **Refusals change nothing.** Gameplay stages nothing on refusal; the target is staged on a
  clone and committed only by `commit_outcome`; `replace_pose` writes only after every check,
  through the atomic `save`. Tests assert save bytes, live state and the audit log unchanged.
- **No oracle.** Non-admins learn nothing (same refusal text with or without a target).
- **Audit.** One row per applied move: account and session of the admin, target GUID,
  online flag, zone and position before and after. No names, no chat text (asserted).
- **Saves stay atomic.** Offline: ordinary `game_store::save` (temp + fsync + rename).
  Online: the target's commit saves before installing anything.
- **Pet roster (replay onto L036).** The roster now lives in the same document. The offline
  move passes the roster it read straight back (`pets: document.pets`) into L036's single
  `save`, so the pose and the untouched roster land in one `replace_bytes`; there is no second
  write and no path that drops or reshapes a roster. The admin's input never reaches the
  roster. Pinned byte for byte by `l043_offline_move_keeps_the_pet_roster_byte_for_byte`.

## Checklist

1. Refusal changes nothing: tested for role refusals, loading target, no security log, busy
   or out-of-zone target (gameplay state), other-zone and missing saves (bytes unchanged).
2. Rollback covers all state: the target gateway is a clone; the world clone and save are
   `commit_outcome`'s own; no shared side table.
3. Deltas, not snapshots: only the pose is written; offline everything else (gameplay,
   housing, and since L036 the pet roster) is read and written back in the same step with no
   other writer. The roster is pinned byte for byte by the new pets test.
4. Busy rules: the online target uses the occupation table through `warp_context`.
5. Every entry path gated: chat (opening and fallback paths both pass `handle_in_world_inner`
   after `command_refusal`); Studio's `/api/command` goes through the same dispatch.
6. Reachable and tested through production dispatch: `l043_admin_move.rs` drives
   `Session::dispatch_message` on a real `Server`.
7. Survives reconnect: the offline test logs the character back in and finds it at the
   warpstone; the online test reads the save on disk.
8. Exit paths: the moved character keeps its activity-free state; refused when busy.
9. Economy: no items, coins or rewards involved.
10. Wire: the 38/12 bytes are `location_packet` (client reader `0x008e66e0`); the online test
    compares the exact message.
11. Unique ids: none created.
12. Others see it: the online move commits through the target's `commit_outcome`, which fans
    the pose out to viewers. Gap: the admin's own client is out of the session map during
    the move, so a nearby admin sees the new pose only at the target's next update.
13. End to end: offline move then login lands at Cobblestone Village (and, in the pets test,
    with the same roster adopted by the session).
14. Values in data: no new tunable; destinations are the warpstone table.
15. Canaries break production code (see test results).
16. Session plumbing: unchanged; only the login predicate was extracted unchanged.
17. One player's error: a failure is a reply to the admin; the target session goes back into
    the map in every case.
18. Rules on the type: `AdminMove.rotation` documents `None`.
19. Hot paths: none.
