# T472 - Buff rows: the tag id is the row's instance id

Attempt 1 (Opus lane), worktree cut at autopilot tip `1a33a76`. No earlier patch existed. Amended
once for the review blocker below.

Two byte changes to every server-built 38/16 row:

1. **Framing (review fix).** The row is now header, tag id, **i32 blob length 85**, then the 85-byte
   `ClientEffectTag` blob: 97 bytes, not 93. Without the length the client read the first blob int
   as the length and dropped the packet, so no server-built buff icon could ever draw (before this
   task: length 0 plus 81 trailing bytes; after the first commit: length = tag id).
2. **Instance id.** The first blob int (`unknown_1`, the client's instance id) is the row's tag id
   instead of 0. A job buff and a power-up buff active together are two buff-bar rows, and a client
   cancel names the right one.

Tag ids, allocation, durations, icon, name, composite effect, the 85-byte blob, 38/17 and expiry
are unchanged.

## What changed

- `src/restoration/piece_056.rs`
  - `ADD_EFFECT_TAG_LEN = 4 + 4 + 4 + CLIENT_EFFECT_TAG_LEN` (97).
  - `encode_add_effect_tag` writes `CLIENT_EFFECT_TAG_LEN` as an i32 between the tag id and the
    blob. The comment cites `0x008d8870 -> 0x008bfc00` and the strict parse at `0x0093a5fd`/`0x008f8ef0`.
  - `decode_add_effect_tag` reads the length at 8 and returns `BadLength { expected: 85, .. }`
    unless it is 85. It reads the blob at 12.
  - `EffectRequest::to_payload(tag_id)` writes `unknown_1: tag_id`. `StatusLedger::apply` already
    allocates the tag id (or reuses it on a refresh) before it builds the payload.
  - `StatusLedger::restore` sets `unknown_1` to the row's tag id, so a stored row with 0 still
    resends the right instance id. This makes the field's doc comment true on every writer.
  - Doc comment on `EffectTagPayload::unknown_1` names it as the instance id and cites both
    captured rows (rule 18). GAPS lines updated. Nothing renamed.
- `src/abilities.rs` `build_effect_tag`: `unknown_1: tag_id`, and the reader comment now names the
  length (`008bfc00`). Both live writers go through it: job ApplyEffect (`apply_one`, tag = effect
  id) and power-ups (`encounter/power_up_use.rs`, tag = `slot.definition_id`).
- Tests
  - `tests/piece_056.rs`: size pin 4+4+4+85; profile-row test compares against `[12..]`.
  - New `captured_startup_tags_match_the_codec_and_the_startup_writer`: the two retail 97-byte
    packets (hex checked equal to the `.bin` files) decode, carry `unknown_1 == tag id`, re-encode
    byte for byte, and equal `startup_catalogues::build_effect_tag` output after its 7-byte tunnel
    prefix. So both writers agree on real bytes. This test is stronger than the reviewer's
    suggested coin-boost round trip, which was built from reconstructed fields.
  - Malformed test: a blob length of 84 is refused.
  - Stack test: two applies each carry their own tag id. Refresh test: the same instance id.
    Restore test: a stored `unknown_1 = 0` is resent as the tag id.
  - `tests/abilities.rs` `expected_apply_effect`: pushes 85 after the tag id, then `[tag_id, tag_id, ...]`.
  - `tests/power_up_use.rs` Super Shield: `tag[4..8]` = definition id, `tag[8..12]` = 85,
    `tag[12..16]` = definition id. This goes through the real `handle_in_world` path.
- Untouched: `startup_catalogues::build_effect_tag` and the startup snapshot. They replay the
  captured blobs as they are, and their framing was already right.
