## Guild dispatch, parsing and client state

`00b1ee10` dispatches guild-family messages by sub-opcode. It routes status updates (17, `00b1d7d0`), name updates and accepted names (18/19), full data (22, `00b1ec10`), errors (23), invite notifications (24, `00b1e7e0`), member locations (25), invite cancellation (26), acceptance/decline notifications (27/28), deletion notification (29), paid rename reply (30), player status (31, `00b1ce80`), can-create (32), client case 33, and admin version (41). Case 33 emits `GuildDialog:Show` and falls through into case 32; this is client dispatch behavior, not evidence the original server sent 33. The original client constructs BaseGuildPacket with family 0x81; the vault note [[Research/Pieces/090 Guild lifecycle]] records the corroborating preserved server enum and separates it from community-only numeric additions.

The packet readers in this shard recover payload mechanics, not every field meaning. `00b1d210` reads two u16 values, a fixed record, and a bounded length-prefixed blob. `00b1d2d0` clears the prior list, reads a count and item dwords, then decodes item bodies. `00b1bf30` purges the 10-bucket GuildRole map, reads a count, inserts each dword key, and parses a 0x18-byte role entry. `00b1bd30` consumes two u16 values plus one boolean byte, matching the one-byte body width of GuildCanCreateGuildPacket (32). `00b1bdb0` bounds and reads a counted array. Keep guild/member item semantics open where the record does not distinguish them.

The manager constructor `00b1e3b0` creates `BaseClient.Guilds` and `BaseClient.GuildMembers` data sources, a 100-bucket guild-name map, and pointers used by handlers. `00b1d030` replaces the cached name entry for a key pair and publishes the update through `00984200`. `00b1e960` looks up a name, throttles misses using the 32-bucket pair/time cache maintained by `00b1bba0`, constructs GuildNameRequestPacket, and calls `00b1e4e0`. The latter is a generic tunneled-world sender: it serializes the record header and u64 payload, constructs PacketTunneledClientWorldPacket, then sends it. `00b1bba0` refreshes the timestamp even when the key already exists; the `0x3d` age comparison is in the clock helper's low dword and is not evidence of a wall-clock duration.

`00b1e730` and `00b1e160` decode full guild data, including the leading identifier pair, bounded fields, counted list, and GuildRole map; `00b1ec10` replaces matching cached state and updates the name cache. `00b1ea80` builds GuildMemberLocationRequest from cached entries, excludes the client identifier pair, selects rows with +0xb4 set, and sends via `00b1e600` only when the +0x280 gate is set. The matching location-update payload is bounded by `00b1d370`. These show client request and response parsing, not server-side membership rules.

`00b1d7d0` maps member status codes 1..7 to join/remove/quit/promote/demote/online/offline client updates and localized notices. `00b1ce80` parses GuildPlayerStatusUpdatePacket and, for a looked-up player, compares the returned guid pair against client fields +0x3a0/+0x3a4. Only the match branch refreshes guild data; the alternate interface-result branch calls `0096ab60`, while a guid mismatch simply skips refresh. Interpreting those fields as local-player guid is layout-based inference, not a packet field name.

### Invite handling and wire hypothesis

`00b1e7e0` parses GuildInviteNotificationPacket (sub-opcode 24) and queries the inviter. A zero query result reaches `00a0bd70`, whose thunk registers the GAQGuildInvite action. A nonzero result constructs GuildInviteDeclinePacket (sub-opcode 9) and sends it through `00a0ed50` when client field +0x280 is nonzero. Thus this shard includes a client-side decline path; it is inaccurate to say the response path is absent. The inviter query's meaning and the +0x280 gate remain unknown.

Wire-linked hypothesis only: the original server delivered an invite notification, and the client either registered an invite action or sent a decline according to the query result. This proves neither original server policy nor a prompt outcome. It depends on the sub-opcode dispatch at `00b1ee10`, parser `00b1d210`, and branches in `00b1e7e0`. The community packet names are third-party wire labels, not recovered original server logic.

The community catalogue names sub-opcodes absent from the archived enum (notably 23, 27 and 28); retain the vault note's unverified status. Client switch cases prove handling, not historical server contract.
- Exact meanings of the two leading u16 values in several guild records, the full-data list item type, inviter-query return semantics, and the manager's +0x280 gate remain unresolved.
- Commerce packet receive behavior and purchase server policy are not established by these constructors, destructors and table helpers. This-adjusting thunks `00b20070`, `00b20080`, `00b20090`, `00b200a0`, and `00b20120` load ECX from `[ECX+8]` and jump to their decoded targets; their subsystem ownership is unknown. `00b20100` loads ECX from `[ECX+8]` and jumps to `009a09f0`; its Lua-string callers do not establish the target feature. `00b20420` has the same shape and is used by `00a42470` while matching nudge records.
