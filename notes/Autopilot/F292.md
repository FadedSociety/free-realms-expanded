## Client evidence (IDA, verified this run)

No opcode or field is added. The tests assert existing quest packets; the
builders were checked field by field against the client readers:

- Common 49/x header `0x00c7acd0` reads a u16 family, then an i32 subtype
  (6 bytes total).
- 49/8 `ObjectiveActivated`: body reader `0x00c7aeb0` reads three dwords
  (quest, objective, required) then a bool; the wrapper `0x00c7b570` is called
  from the quest dispatcher `0x00c7cd40+0x7a0` (case 8). `0x00c7a910` is not a
  reader: it looks up the objective and sets `result[52] = 1; result[54] = a4`
  (activate/apply). Full body 6 + 13 = 19 bytes.
- 49/9 `ObjectiveUpdate`: reader `0x00c7af60` reads four dwords (quest,
  objective, current, progress float), a bool and one trailing dword; 6 + 21 =
  27 bytes.
- 49/10 `ObjectiveComplete`: reader `0x00c7b070` reads four dwords and a bool;
  6 + 17 = 23 bytes.
- 49/4 `QuestComplete`: reader `0x00c7b420` -> body reader `0x00c7b230`
  (common header + one i32 quest id).
- 49/13 `QuestEnd`: reader `0x00c7b990` reads the common header, a u64 actor
  (`6..14`), quest id (`14..18`), end text (`18..22`), one more dword
  (`22..26`), the reward bundle (`0x008e7930`) and a trailing float; dispatcher
  case 13 calls `ShowQuestEndScreen` (`0x00a95420`). The tests assert actor,
  quest id and end text only; the reward bundle and trailing float are not
  pinned.
- 38/14 job row: `0x008d86e0` reads a 4-byte header (`0x008d81b0`: two u16) then
  six dwords; the helper's profile/rank/progress semantics are (R).
- 38/19 coin balance: constructor `0x0089e670` reads one i32 after the header
  (recorded in `notes/Autopilot/T240.md`).

The earlier T256 note called the 49/13 fourth dword "animation"; IDA shows a
dword plus a reward bundle, so that wording was corrected (the exact semantics
of the dword are (R)).

## Security threat note (secure-code-guardian)

Attack surface the suite drives (all client-triggerable): `36/10` shared-field
abilities (slot, target u64), `26/8`/`26/10` interactions (target, choice i32),
`26/6` dialogue rows and `49/14` turn-ins. Nothing is granted from those fields:

- the kill is the server's own alive-to-dead HP transition; the definition id,
  level, max health and reward rows are server content, never packet fields;
- the target must be in the session's known set, in range/cooldown/weapon gate
  and in the same zone/instance;
- the quest event is server-generated with `count: 1`; the engine caps each
  objective at its required count; a zero definition is skipped at the producer
  and a negative one is refused at load (test 6); a repeated turn-in pays nothing
  and leaves the save bytes equal (test 5);
- refusals change nothing: test 3 replays the lethal request, the alternate
  corpse route and two ticks and compares the whole saved state; test 7 asserts
  A's refused bind keeps the old saved ledger (for retry), A's NaN-position
  request changes neither A's state nor the field HP, and B is still credited in
  the same field;
- 18 coins / 25 Brawler job XP are paid from the shipped quest record exactly
  once, asserted through the production `49/14` turn-in;
- a kill-time event cannot abort the shared tick for a valid session (proof
  above); the tick's own `?` hardening is lead-owned.
