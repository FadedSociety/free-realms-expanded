## Security Note

A hostile client can send 26/24 with any i32 recipe id, a wrong-length body,
replayed starts, or a completed movie sequence after an administrator placement
reload moved or removed the station. This task changes no parser and adds no
selector, item, reward or save path:

- `recipe_book::decode` accepts exactly eight bytes; any other length is a
  rejected packet.
- The client supplies only the recipe id. Learned recipes, active job, rank,
  owned ingredients, station proximity and idle services are server facts.
- 26/24 starts with the shared `Gameplay::activity_busy()` gate;
  `recipe_book::start` re-checks the activity and services before mutating
  anything.
- Completion re-checks the active job and a station resolved from current
  actors and placements. After a move/remove, `apply_smelting` returns `Err`
  before consuming or granting; the gateway drops the staged clone and sets
  neither save flag (asserted by snapshot equality and both flags).
- The reconnect test now feeds the snapshot through the production save store,
  so a schema save/load change that broke the persisted `SmeltingState` fails
  the round-trip assertion. The store is server-side state; no client bytes
  reach it.
- The completion refusal is silent by design and is now documented; it still
  changes nothing. The ordinary `26/42` Close and login cancellation both
  release the run without paying.
- No new `application_handler` selector, so no new `app_fuzz` seed is needed.
