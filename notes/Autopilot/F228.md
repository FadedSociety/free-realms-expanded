# F228: starter outfit items resell for 0 coins

Fixes the T010 review blocker (`lab/autopilot/reviews/4dbf262-T010.md`): selling a free starter
weapon, reselecting the job to re-grant it, and selling again printed unlimited coins. The
2026-10-20 decision keeps starter items sellable, but every item in any job profile's
`starter_items` sells for 0 coins wherever the player got that copy. The re-grant and
`ensure_outfit` are unchanged; no one-time entitlement was added.

## What changed

- `src/profiles.rs` (owner of the starter table): `all_starter_items()` returns the union of every
  profile's `starter_items`; `starter_items_in(directory)` reads that union from the content
  directory's `profiles.json` (absent file means no starters; an invalid file fails closed).
- `src/coin_shop.rs` (owner of sell prices): `CoinShop::new` zeroes the resale price of every
  starter item in the loaded `StoreCatalogue` once, through
  `StoreCatalogue::zero_starter_sell_prices`. A row with no sell price stays unsellable (`None`);
  purchase/member prices are untouched. The sell and buy-back paths needed no new branch: they
  already read this catalogue (165/5 -> `sell_with_merchant`, 165/12 -> the recorded unit price).
- `data/content/stores.json`: the 10 starter ids that had a store row now have
  `sell_price_coins: 0` (`4266, 4622, 4914, 19253, 21324, 21683, 68360, 68430, 75030, 75091`),
  tagged `F228` in `source_tags` with the new legend entry. Purchase prices unchanged.
- `data/content/vendors.json`: the two vendor rows that quote item 75030's store sell price
  (NPCs 9500000255, 9500000277) now quote 0, so the vendor coverage table matches `stores.json`.
- `scripts/content_check.py`: loads the starter union from `data/content/profiles.json` when
  present, else the round70 play package's `profiles.json` (same 14 starter profile tables as the
  full w118 package), and reports `starter_item_sell_price` as an **error** for any store row
  whose starter item still has a nonzero sell price. `--strict` therefore fails that regression.
- New `tests/starter_items.rs` drives the real gateway path: learn Archer from its trainer, sell
  the starter bow (0, removed), reselect the active job (re-granted) and sell again (0), buy the
  same item from a merchant (purchase price unchanged) and sell it (0), then buy and sell a
  non-starter (its normal 7 coins). The fixture deliberately keeps 375 in its synthetic
  `stores.json` so the test proves the server rule, not the data edit. It also refuses to sell
  the equipped starter (state unchanged) and then sells it after unequipping.
- `src/bin/osfr_gateway/w173_chat_settings_routing.rs` (test-only): the account-budget test used
  to spend the burst with ten separate requests and then check one request from a second
  connection. The budget refills 5/s on the wall clock, so one refilled token could admit that
  single request; this reproduced locally in 1 of 6 runs with `left: 1, right: 0`, exactly the
  integrator's failure, and is not caused by the sell rule. The same-account and other-account
  checks now send the bucket's full burst as one ten-child bundle: a shared bucket drops the whole
  bundle on the first refusal (a few refilled tokens cannot pass it), while a per-connection
  bucket admits all ten; the other account's ten replies prove the bundle path is effective. No
  production budget code changed.

## Client evidence

- 165/5 sell body: client sender `0x00c76dd0` fills two dwords (merchant id, as the client's
  null GUID pair) plus item instance and quantity, then `0x00c75a70` copies fields; there is no
  client price field. The server price is therefore authoritative.
- Re-checked on the final tree with `ida_query.py`: `sub_C76DD0` stores four dwords
  (merchant GUID pair, item instance, quantity) and no price; `sub_C76820` copies them through
  `sub_C75A70`. `sub_C74EF0` reads the completion's result/item dwords and dispatches
  `sub_C71F30`, which reads the record's quantity, price and remaining dwords.
- 165/6 completion: readers `0x00c74ef0` + `0x00c71f30` read result/item, then the record's
  quantity (+0xc), price (+0xe) and remaining (+0xd). The test reads the price at wire offset 48.
- The 0-coin rule itself is reconstructed policy (R), per the 2026-10-20 decision. No client
  behaviour sets a resale price for starter items; the pre-existing half-of-cost rule is the (R)
  `R3` source tag, which this change replaces with `F228` on the affected rows.

## Secure-code-guardian threat note

A hostile client can send 165/5 with any instance id, quantity, merchant id or replay. It cannot
name a price: the server resolves the definition from its own inventory row and reads the sell
price from the loaded store catalogue after `zero_starter_sell_prices`. Quantity 0, above the
stack, above available (consumed/stored), equipped, rental, no-sale, uncatalogued and non-positive
instance requests keep their existing refusals and change nothing. A replay finds no item and is
refused. Buy-back uses the recorded 0 unit price, so sell/buy-back cannot create coins. 66/43 buy
requests still debit the catalogued purchase price (unchanged) and ignore the client's price.
Starter ids are content-derived from every profile, so a newly added starter is covered without a
code list; only server content and the character save can change the outcome. The 375 -> 0 data
edit removes the advertised price as well, so no client is told it can recover the old value.

## Checklist

1. **Refusal changes nothing.** The test snapshots the gateway, sends a sell of the *equipped*
   starter, asserts the same refusal code and an equal snapshot, then sells it successfully after
   the unequip as a canary. No new refusal was added; the existing invalid/quantity/equipped
   refusals in `vendor_sell` still pass.
2. **Rollback covers all state.** No transaction or shared mutable state was added. The zeroing
   happens inside the catalogue the shop owns before it serves any request.
3. **Apply deltas.** No snapshot restore was added; the sale path still consumes the exact
   instance and credits the computed price (0) on the staged inventory.
4. **Busy rules are mutual.** No new activity or gate; nothing to add to `occupation.rs`.
5. **Every entry path gated.** Both the gateway 165/5 path and direct `CoinShop::sell` use the
   same zeroed catalogue, and buy-back uses the recorded 0 price. Purchase (66/43 and 165/4) is
   unchanged and still checks stock, shop, zone, range, coins, quantity and bag.
6. **Reachable in production, tested through it.** `tests/starter_items.rs` sends 26/8, 26/10,
   26/13, 42/2, 165/5 and 66/43 through `Gateway`, then reads the real inventory and save state.
   The w173 check sends a ten-child application bundle through the real `dispatch_message`
   budget-before-staging path.
7. **Survives reconnect.** The feature adds no persistent state: the starter set is re-derived
   from content at every login and the sale itself is already saved by the gateway. Existing
   `vendor_sell` reconnect coverage still passes.
8. **Every exit path restores.** No new activity, timer or session state.
9. **Economy safety.** Payout is server-derived; quantity, ownership, equipped, rental, no-sale
   and available-copy checks are unchanged; the client cannot supply a price. The test proves the
   starter pays 0 from three origins and a normal item still pays its catalogued 7.
10. **Wire format.** No packet layout changed. The test parses 165/6 at the recovered reader
    offsets (price at 48), and the existing 165/5/66/43/66/44 reader tests still pass.
11. **Unique ids.** No ids minted outside the existing inventory allocator.
12. **Others see changes.** Selling/equipping already uses the existing directed visibility path;
    this change only alters a price value.
13. **Content works end to end.** The trainer grants the bow, the job selection succeeds, the
    three sales remove the item and pay 0, the merchant purchase debits 10, and the non-starter
    sale pays 7. Assertions are on final coins and item counts.
14. **Values live in data.** The starter ids come from `profiles.json`; the rule is the set, not
    a compiled list. No tuning constant was added. The 0 is data/policy, and the content checker
    guards the rows.
15. **Canaries break production code.** The Rust canary removed the production zeroing call and
    failed at the price assertion; the checker canary changed a real store row and failed the
    checker. Both reverted.
16. **Hands off session plumbing.** No changes to `gateway.rs` or `bin/osfr-gateway.rs`. The only
    gateway-side edit is inside the test module `src/bin/osfr_gateway/w173_chat_settings_routing.rs`
    (the refill-race check); no session creation, teardown, transaction or save ordering changed.
17. **One player's error never stops the server.** No tick or shared-state code touched; sell
    refusals are per-request replies.
18. **A type's rules live on the type.** `Profiles` owns the starter union;
    `StoreCatalogue::zero_starter_sell_prices` owns the price rule and documents that `None` stays
    unsellable. The test's helpers only read state.
19. **Hot paths stay cheap.** One `profiles.json` parse per `CoinShop` construction; zero work
    per packet or tick beyond the existing price lookup.

## Open gaps

- The W118 generator that produced `stores.json` is not in the repository (also recorded in
  `notes/Research/Ride Sources.md`). The 10 row edits are therefore manual; a regenerated file
  would restore the old reference price. The runtime rule still pays 0 for a play package whose
  profiles.json is present; the bundled `data/content` has no profiles.json, so a regenerated
  bundled row would rely on this data edit or the checker's `--strict` gate. The generator must
  add the same rule when it returns.
- A non-shipped play package with its own nonzero `stores.json` pays 0 but its 66/42 merchant
  window may still display the old reference price. The shipped `data/content` rows are zeroed;
  the window's price field is documented as an opaque/reference value (R). Displaying the rule
  from that second parser would need the starter set passed into `NpcInteraction`, which this
  task's owning-module boundary did not require.
- The checker's default profile table is the round70 play package (identical 14 starter profile
  tables to w118). If a future package adds starters, point the checker at its `profiles.json`
  (it prefers `data/content/profiles.json` when that file exists).
- The full `gateway_npc_offer_runtime` target was not run to the end: its unrelated runtime tests
  stalled under three other workers' concurrent builds, so the run was stopped. Its
  `w173_chat_settings_routing` subset (7/7) passed, as did the complete `osfr-gateway` bin suite
  (47 passed, 1 ignored) and `bot_smoke` (52 passed, 3 ignored), which compile and run the same
  module. The integrator's full suite remains the final check.
