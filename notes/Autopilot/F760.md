## Security note (secure-code-guardian; 66/27 is new client input)

- A hostile client can send any store id, bundle id, count and item-id list. The existing
  `marketplace_request_is_well_formed` 64-byte Marketplace cap runs before the parser;
  `decode_content_request` also bounds the body (4 KiB), requires the exact 66/27 header and
  exact end-of-frame, and refuses a count above 8. The item-id list is skipped against the body
  (an over-claimed count is an `Err`), never stored, never allocated.
- Reply selection is server-owned: the store id must equal the configured store and the bundle
  must be a listed bundle; the definition is that listing's item id from the loaded inventory.
  A client id cannot alias a bundle, select an unlisted definition, or amplify the reply beyond
  the request's ≤4 entries in one 64-byte packet.
- No coins, items, wallet, save or session state changes (`changed: false`); malformed input is a
  per-request `Err` (the existing 66/1, 66/3 convention). No `unwrap`/panic on client or content
  data: the canonical encoder returns `Err` for a bad row.
- The 66/28 is never sent as a count-zero packet (the client logs it as a malformed base packet).
