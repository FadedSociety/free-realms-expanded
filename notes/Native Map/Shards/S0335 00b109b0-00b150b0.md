## Systems and connections

- lib.soeutil.container dominates the range. RTTI identifies SoeUtil::List<ChatNode,10> and SoeUtil::List<ClientChatProcessor::SpamInfo,256> plus their unbounded -1 bases. The corresponding pools use distinct slot strides: 0x38 bytes for ChatNode (00b112d0, 00b113f0) and 0x28 bytes for SpamInfo (00b13cd0, 00b13df0). Each has a red-black tree of block descriptors, a free-list, and helpers to allocate a block when empty and release it when all slots are free. The matching successor/predecessor, rotation, insert, erase, and balancing routines appear at 00b10bd0–00b11120 and 00b135d0–00b13b20.
- 00b11530/00b11540 and 00b13f30/00b13f40 are adjustor thunks: bytes show add ecx,0x10 followed by a jump to the shared pool pop/push body. They are not ordinary call wrappers. Scalar deleting destructors at 00b12840 and 00b14020 call their destructor bodies, test flag bit 0, and conditionally free. Shared destructor bodies at 00b12770 and 00b13f50 install both specialization and base vtables.
- ui.chat connects chat history and spam checking. 00b14200 creates or finds a keyed ChatNode list, evicts its head at count 10, and appends a new record. 00b13500 constructs the inline-256 SpamInfo pool. 00b12b70 computes a character edit-distance matrix; ClientChatProcessor virtual handler 00b164b0 normalizes that score by message length and compares it with its duplicate threshold. The handler also owns the SpamChatBlocked callback and rate fields. This is client-side filtering evidence, not proof of server moderation.
- net.chat contains receive and send paths. 00b14350 constructs BaseChatPacket, parses its bounded input, and dispatches payload modes 1–5. 00b11600/00b140c0 decode the PacketChat body; 00b117a0/00b14130 decode TellEchoPacket. 00b11810 and 00b11ab0 route parsed channel/whisper messages through callbacks and UI presentation. 00b120e0 formats the local tell confirmation and invokes OnReceiveWhisper. 00b14fa0 serializes PacketChat; shared send helper 00b15340 wraps the serialized bytes in a gateway packet and submits it. 00b12ad0 writes the first two 16-bit fields.

## Packet and server-contract inference

The original client parser/serializer and catalogue agree on PacketChat subtype 1 (15/1); 00b14fa0 writes the extra field only when the channel field is 8. The client receive dispatcher also handles concrete modes 3, 4, and 5; mode 2 constructs ChatPacketEnterArea, which is absent from the current packet catalogue. These are client wire behaviors. The supplied Research/Pieces/088 Chat channels.md note documents the PacketChat field order and explicitly keeps recipient routing as reconstruction policy.

Hypothesis: the original server accepted the client's 15/1 PacketChat requests and returned type-15 chat/tell variants that the client dispatches. This depends on the client send/receive paths, the pinned packet catalogue, and the chat note. No original server implementation or authoritative server trace was recovered here, so acceptance, routing, moderation, and tell-echo policy remain unverified.
