## Findings

1. **The native commands and the relocation packets line up frame-for-frame.** Decoded from the wire: `001426.bin` sequence 40 carries the chat command `realm goto Mae`, and `001428.bin` sequence 1283 answers with the 38/12 packet; `001487.bin` sequence 68 carries `realm goto Cooking Table`, and `001489.bin` sequence 1286 answers with the second 38/12 packet. Both packets are 38 inner bytes (`26 00 0c 00`), position W=1.0, rotation W=0.0, `Teleport=1`, `Unknown=0`, inside the standard `[05 00 01][u32 length]` tunnel.
2. **The arrivals satisfy the sampler contract on the live socket.** Mae arrival `[-2113.63599, -56.52175, 212.43661]`: 4.0000 m from Mae, closest other actor the Cooking Table at 4.8995 m (≥ 4.5), facing dot 1.00000. Cooking Table arrival `[-2110.04077, -56.61908, 214.18481]`: 4.0000 m from the table, closest other actor Mae at 6.3211 m, facing dot 1.00000. Both finite. Notably the Mae arrival is *not* the angle-0 approach direction: with the character's saved facing `[-0.97995, 0, -0.19923]` the approach sample would land roughly 1 m from the Cooking Table, so the sampler skipped forward and chose the +90° sample — the margin rule demonstrably acted natively, not just in the unit tests.
3. **The current prompt was the intended actor.** `standoff-mae-menu.png`/`_small.png` shows the `Mae Farnum` prompt ("Press X", radial Interact) with the confirmation line "Developer teleport: Mae Farnum (GUID 5715144128442925060) at 4.00m"; `standoff-cooking-table.png`/`_small.png` shows the `Table` prompt after the second command with both confirmation lines. The dry-run input log `external-inputs.jsonl` records `click 640 770` and `click 640 494` after each teleport (prompt then radial Interact), and `cooking-offer.png` shows the native cooking offer ("Cooking: Strong Arm Stew") opened from the table, i.e. the prompt leads to the expected interaction.
4. **No progress or supplies moved.** `standoff-before.json`, `standoff-mae-after.json`, `standoff-mae-interaction-after.json` and `standoff-cooking-table-after.json` all carry the same gameplay block (`gameplay_equal_to_before=True` for all three later snapshots), with stage 13 accepted, `counts=[1,4,4,0]`, `completed=false`, discoveries `[1,2,3,4]`, 259 coins and 34 inventory items. `standoff-mae-after.json` and `standoff-mae-interaction-after.json` are byte-identical (`98ecdb17d9c9`), so the Mae prompt interaction changed neither position nor progress. The later retry state (`cooking-retry-offer-state.json`) keeps `completed=1`, `next_instance_id=46000006` and an `Offered` instance 46000005 with no stats — a repeat offer, not progress.
5. **The relocations persisted, including the client's height adjustment.** The server log shows `character_saved` for each relocation arrival and for the client's follow-up movement. The first guid-1 movement after the Mae packet (`001435.bin`, sequence 43) is the arrival with Y raised from the actor's `-56.52175` to `-56.25703` (+0.26472 m); after the table packet (`001498.bin`, sequence 72) Y becomes `-56.25893` (+0.36015 m from the table's `-56.61908`). The saved snapshots equal those last accepted movements exactly, so the server kept the floor-corrected position rather than the raw actor-Y standoff. Each relocation also produced one stale in-flight movement with the pre-teleport position (`001433.bin`, `001496.bin`) before the corrected one; that is the ordinary client echo, but it means the settled arrival matters for persistence — a crash inside that one-frame window would persist the previous position.
6. **Small, non-blocking observations.** `character-before.json` and `standoff-before.json` differ only in the last f32 digit of rotation Z (`-0.19923116` vs `-0.19923112`), the first-movement float jitter already known from earlier runs. The confirmation text and screenshots show the arrival at 4.00 m as designed, and the actor-Y standoff is still a standoff, not a floor proof; the client supplies the floor correction.
