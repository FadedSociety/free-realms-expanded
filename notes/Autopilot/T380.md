# T380: the Marketplace "Rides" category lists its bundles

## Summary

Native run `lab/runs/client-baseline-20261021T053319Z`: SHOP! showed the **Rides** category but
"There are currently no items in this category...". The catalogue bytes were right; the client
never copied the store into its StoreItems list.

Root cause (IDA, shipped 2014 `FreeRealms.exe`):

1. The StoreItems data source (`BaseClient.InGamePurchase.StoreItems`, ctor `009a8880`) fills its
   bundle-id list only in its StoreItemRoot observer `0099aa60` (vtable `0180e2c0` slot 6,
   observer registered on `BaseClient.InGamePurchase.StoreItemRoot` at `009a898a`). That observer
   does nothing unless manager byte `+0x3E828` (manager initialised, `00b471e0`) **and** byte
   `+0x3B45D` (commerce processor ready) are set; only then it calls `009a3650` (copy store 1's
   bundles) and marks the list dirty.
2. `+0x3B45D` is set by `00d56de0`, called from `00b2c340` in the manager tick `00b335f0` once a
   store has arrived (`+0x3E82C`, set by `00b3b320` after a clean 66/5) and system support has
   started (`+0x3E82E`, set by `00b303e0` during init). So it becomes 1 one tick **after** the
   66/5 that already fired the StoreItemRoot refresh (`00b3b320` -> `0099a790`). That refresh
   found the processor not ready, and nothing refreshed StoreItemRoot again.
3. The client's own refresh when the store screen opens is the 66/38 -> 66/39 round trip: the Lua
   binding `Opening` (`00c047a0` -> `00c03920`, subtype 38, bare header; trace `ts_ms` 123865
   `42002600`) asks, and the reply handler `00b3e490` (class `InGamePurchaseUpdateItemRequirementsReply`,
   ctor `00b2ffa0` with subtype `0x27`) refreshes StoreItemRoot (`0099a790`) and the category tree
   (`0099a7b0`) after a clean read. The server never answered 66/38, so the list stayed empty.
   Other StoreItemRoot refreshers are 66/4, 66/8, 66/32, 66/41 and 66/5 itself (xrefs of
   `0099a790`); none is sent on screen open.
4. That native run used the T329 binary (`b1d0299`; run started 05:33Z, F387 integrated 11:37Z):
   the catalogue went out once at world entry (`ts_ms` 95113) and SHOP!'s 66/10 got the wallet
   only (123856). On the current tip F387 sends the catalogue in every 66/10 reply instead, so the
   HUD's world-entry 66/10 arms the processor and SHOP!'s own 66/10 re-sends 66/5, whose
   `00b48700` -> `00b3b320` -> `0099a790` refresh should already fill the list (by the chain
   above; not run natively). 66/39 makes the fill not depend on an earlier 66/5: it is the
   refresh the client itself asks for on open, and the one the server never answered.

Fix:

- `src/coin_shop.rs`: 66/38 is answered with 66/39 (an empty counted list) when the Marketplace is
  on (`station_cash.enabled && marketplace.enabled_on_handshake`, now one private
  `marketplace_enabled()` shared with `marketplace_packets`). With it off, 66/38 still gets no
  reply. 66/38 must be the bare 4-byte header, like 66/10 and 66/18.
- `data/content/stores.json`: `station_cash.category_id` 1 -> **139**, the client's own Rides
  category: Lua `MarketplaceCategoryIds.RIDES = 139` (`ScriptsBase.lua:18045`), used by the mount
  screen's buy-more-rides link (`MarketplaceHandler:Show(MarketplaceEnum.STORE,
  MarketplaceCategoryIds.RIDES)`, `ScriptsBase.lua:35007`), and the Rides portal tile in
  `Resources/Marketing/ClientStorePortalCategories.txt` (row 3: name 27547, shortcut type 3,
  value 139, store 1). With id 1 both of those paths open an empty category 139.
- No change to `place_order`, wallet debit, the replay window or the busy rule.

Why an empty 66/39 list: the reply only overrides bundle byte +242 (view-only, `00b3e490` stores
`!purchasable`); 66/5 already sends 0 there, so listing the rides again would be a second copy of
the same flag to keep in sync. The empty list is a clean read, so the refresh still runs.

## Threat note (secure-code-guardian)

A hostile client can send 66/38 with any body. It is accepted only as the bare 4-byte header
(otherwise `Err`, nothing changes); it carries no id, price or quantity; the reply is a constant
8 bytes and touches no state. 66/39 is presentation only: `place_order` still revalidates the
store, bundle, server price, wallet, bag and busy table.
