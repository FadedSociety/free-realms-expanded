## Pixel-format routines

`0048741e`, `004877f0` and `00487b20` convert a colour and store it at an address supplied by the caller. Their format paths are similar but not interchangeable: `0048741e` and `00487b20` copy input bit 31 into output bit 15 for their `0x211555` fast path, while `004877f0` packs RGB 5:5:5 without that bit. In both `0048741e` and `004877f0`, tag `0x210444` first performs a `0xfff` masked merge and then falls through to the shared `0x7fff` merge; the final word operation updates the low 15 bits and preserves bit 15. A description that assigns only the `0xfff` mask to this tag is incomplete. The exact semantic distinction intended by those tags is unresolved. `00488095`, `004882dd`, `004884a4`, `00488686`, `00488a1f` and `00488ff6` convert, read or write values selected by format descriptors. `004890e5` clips a rectangle and fills rows for supported byte widths; a valid nonempty clipped rectangle returns 1 even when its bytes-per-pixel value skips the color-fill branches. `00489321` scans selected rows and columns using a value and mask; the caller's meaning for its output counts is unknown. `0048a020` copies twelve dwords; relating that block to the pixel descriptors used elsewhere in the shard is an inference.

Two alpha details remain unresolved in the binary evidence. The flag-0x800000 paths in `00488a1f` and `00488ff6` address the extra byte plane through descriptor field `[9]`, while `004890e5` uses `[10]`. In `004890e5`, virtual slot `+0x178` is called with `this` in ECX and stack arguments `&local_18` and `param_6`; the code treats EAX as an address and fills with the byte at EAX+3. It does not use an alpha byte returned directly in EAX. Also, the `0x214444` path in `00488ff6` masks a word with `0xfff` but does not use the supplied alpha value. `00489b9f` installs two vtable values, conditionally releases the member at `+0x1c`, then tail-jumps to `00526562`.

## Image and text streams

`0048ac76` reads a BMP/DIB header (`BM`, followed by accepted `biSize` values 0x28 or 0x6c), reads pixel data and makes GDI calls through a memory DC. It ignores GDI return values, and the exported pseudocode returns 0 even after those calls, so successful import is not established. `0048b14e` and `0048b287` read/write the 128-byte PCX header layout, consistent with this [PCX header reference](https://www.fileformat.info/format/pcx/corion.htm). `0048b48c` stages four rows at a time, calls slot `+0x1bc` with row count 4 before clipping the row count used by the splitter/encoder, splits planes and calls `0047e9ed`, whose code is PCX-style run-length encoding. A nonzero stream write is accepted, including a partial write. On normal completion it frees both scratch buffers and returns 1; on a zero-write failure it frees the first buffer but not the second and returns 0. No target in this shard proves which image writer consumes these chunks.

`0048b8ae` reads one character; on `#` it consumes through CR or LF and returns that terminator, leaving the next content character for a later call. `0048b920` accumulates decimal input in a 16-bit value and stores it only after reading a non-digit terminator. `0048ba3b`/`0048bb24` handle P3/P6 headers. The writer sends the max-value field through the decimal writer, so `0xff` becomes text `255`; it does not write a raw max-value byte. `0048bc02` copies P6 RGB bytes to B,G,R,0 and accepts any positive row-read count, including a partial row; its P3 path truncates values to bytes. Neither decode path rescales by maxval. The implementation therefore differs from the [Netpbm PPM specification](https://netpbm.sourceforge.net/doc/ppm.html) for samples requiring scaling and for P6 maxval above 255, where the format uses two-byte samples. `0048bd5e` writes P6 RGB rows and likewise accepts positive partial writes; its P3 path emits decimal channels. `0048bf0c` stages a 0x610888 surface, checks destination format/size and blits; `0048c04c` builds a P6 header with maxval 255. Their `00486164` calls initialize a local object and are not locks.

`0048c2de` and `0048c3d3` read/write TGA header fields but check only the final one-byte field operation before seeking by ID length; earlier field-operation results are ignored. `0048c4f5` is likely a color-map entry writer, based on header offsets +6/+8, the pack helper `0048c220` and its only recorded caller `0048c8ca`. That caller initializes color-map type to zero, so it skips the conditional call on the analyzed save path and processes image data through `0048c619`. The helper's returned byte estimate undercounts 15-bit entries, which it writes as two bytes. The [Library of Congress TGA description](https://www.loc.gov/preservation/digital/formats/fdd/fdd000180.shtml) points to the format specification; the local caller condition is the evidence for how this client path uses the header.
