## Behaviour and invariants

- One hand-over = one event. The step's `required` is 1 (the event), while `quantity` is how many
  bag units must leave. Counts only go up (`saturating_add(..).min(required)`), so a removal can
  never un-complete a `collect_item` goal; `npc_inventory_events` also counts increases only.
- A shortfall (fewer real units than `quantity`, rental-only stacks, no stack) consumes nothing,
  sends no event, leaves one chat line and lets the Talk proceed. The serialized state is
  byte-equal after it (`short_hand_in_changes_nothing`, which also proves the open NPC menu is
  not consumed).
- Atomicity: `deliver_staged` consumes on a cloned bag and sends the event on a cloned engine;
  both commit only after a credit. The unreachable fault case (an invalid event, and a valid event
  that credits no open step) is unit-tested beside the transaction, because the content loader
  bounds every field so a Talk can never build either event.
- An equipped item that is fully handed in is cleared by `Inventory::consume` itself (38/6 + 38/4),
  so the wand-on-body case (3020021, locale 100018) needs no extra code.
- Reload: the bag and the quest counters are one `GameplayState`; `save_and_reload` proves both.
- Abandon after a hand-over removes the quest and refunds nothing.
- Ordering: only the active ordered step can take items; a later delivery step waits for its turn.
- The busy rules are unchanged: `npc_select_26_10` refuses before the router when the shared
  occupation table says busy, so the hand-over cannot start inside another activity.
- Only the talking player's state is touched; another session in the same fixture keeps its bag
  and progress byte-equal.

## (R) rules and decisions

- `quantity` and `item_id` come from the quest JSON, never from the client; the NPC comes from
  the server-resolved content key of the clicked actor.
- A rental stack is never handed in: the engine's collect credit already ignores rentals, and a
  rental is not owned. The shortfall test covers the rental-only bag.
- Abandoning after a hand-over refunds nothing, matching how content already treats a spent quest
  item; the lead may decide otherwise.
- Purchased/other stacks of the same definition across the bag are all eligible: the step names a
  definition, and any owned non-rental units satisfy it (edge 3).
- The shipped data record: quest 3020021, step index 2 of its 4-step line, NPC 9000000203
  (Silverray - the record's giver and, with no `quests_accepted` row, its turn-in actor), item
  30480 (the wand the objective spec's craft step names), quantity 1 (one crafted wand). Marked
  (R) in the step's `source` evidence. The record stays `enabled: false`: its other steps, its
  reward rows and its prerequisite chain wait for the data pass, and an enabled quest needs a
  non-empty 49/13 reward (the reachability gate refuses an empty one).
- Overlapping deliveries: the event carries NPC, item and units and `event_matches` compares all
  three, so steps that differ in units are credited one at a time; two enabled steps with the same
  NPC and item are refused by the reachability audit. No shipped record overlaps (only 3020021 has
  a delivery step, and it is disabled).

## Threat note (secure-code-guardian)

What a hostile client can send: at most the existing 26/10 Talk selection, `(runtime actor GUID,
menu option id)`. It cannot name an item id, a quantity, a quest, a target NPC or a result.

- Unknown or forged runtime GUID: `content_npc_key` maps only a live content NPC; otherwise the
  router does not reach `talk_to_npc` and no delivery is attempted.
- Out-of-range or wrong option: `npc_interaction::select` proves range and that this exact option
  was offered for this actor; a selection it refuses is not committed (the existing rule).
- Busy player: `busy_interaction_refusal` (the shared occupation table) returns before the
  router, so a hand-over cannot run inside an encounter, crafting station, minigame, kart race,
  trade or vendor window.
- No open delivery: `pending_delivery` returns `None`; nothing is read or written.
- Shortfall or rental-only bag: nothing is consumed and no event is sent; one fixed chat line.
- Replay: after the step is credited the ordered step moves on (or the quest completes), so a
  repeated Talk finds no pending delivery and takes nothing.
- Item id and quantity are content-owned and validated at load (positive id, quantity
  1..=MAX_COUNT, non-empty provenance); `validate_event` re-validates them. Only instance ids
  read from the talking player's own bag are consumed, one stack at a time.
- Economy: the diff grants nothing. Items only leave the bag in the same staged transaction as
  the credit, and all rewards stay on the existing turn-in transaction. Kill-switch: none needed;
  disabling the quest record in content stops it.
- No secret, token, key or client data is involved; no new packet or log line carries identity.
