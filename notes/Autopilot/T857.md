# T857: a JSON bridge inside the real client, so native tests can be driven by name

The client's UI Lua now exposes a small file protocol: a command file with JSON lines is read on
the UI tick, and one JSON result line per command (same id) is appended to a result file in the
run folder. The Python driver sends `state`, `click` (dialog row or radial/housing button by name),
`chat` and `interact`, and a `demo` sequence records the whole Samantha flow. Everything is
lab/harness code: no server, gameplay, save, reward, coin, item, role, chat or trade module changed.
No Rust file changed and the four spine hubs are untouched.

## The bridge protocol

- `<run>/lua-bridge-commands.jsonl`: one object per line, `{"id": "...", "cmd": "state"}` etc. The
  command file is append-only; the bridge keeps a byte offset and a partial-line buffer.
- `<run>/lua-bridge-state.jsonl`: one result per command with the same `id`; a `ready` line at load
  and id-less error lines for unparseable input. `id` is echoed as given (text-compared).
- `state` reports `zone`, `position`, `heading`, `closest`, `target`, `dialog` (shown, body, rows),
  `radial` / `housing` (shown, buttons with index/text/event) and `windows` (handler windows that
  advertise `isShown`/`visible`/`active`, plus `UIWindow.openedWindows`). Missing values are omitted.
- `click` resolves a row/button by exact text, then case-insensitive exact, then a unique
  case-insensitive substring, or by `index`; a click on a closed dialog or a hidden menu, or an
  unoffered/ambiguous row, is an error and calls no UI function. Dialog clicks use
  `DialogHandler:SelectOption(slot)` (the Flash path); radial clicks use the menu's own
  `OnUserEvent("radialMenuClick", eventId)` (which also closes the menu).
- `chat` calls `Ui.ProcessChatCommand`; `interact` calls `Ui.DoClosestInteraction`. `key`/`move`
  answer an explicit unsupported error: the client Lua has no synthetic-key or movement entry point.
- Bounds: 15-frame poll, 256 KiB read per poll, 64 KiB line, 64 commands per poll, 8 rows/buttons,
  24 windows. The `answered` ids are rebuilt from the result file at load, so a reloaded bridge
  skips an already-answered command instead of replaying a chat or click.

## Reconstructed (R) rules

- **(R) The bridge is test-only glue.** It adds no game behaviour; every action is the client's own
  Lua path. The original 2014 UI had no such bridge, so no original-server flow is being replayed.
- **(R) `state.windows` is a heuristic.** It lists handler tables whose common visibility field is
  set and any open browser windows; it is not an exhaustive window inventory. Dialog and radial
  contents are exact (captured from the client's own Set*/setButton calls).
- **(R) The dialog slot is passed as `SetChoiceText`'s first argument.** The native display's loop
  order and the stored row-id slot are the same in `009f5ae0`/`009f6aa0`; a client that ever passed
  a different order would make the by-text click select the wrong slot, which is why the bridge
  records the argument rather than counting calls.
- **(R) Demo flow.** `realm goto` is an existing developer command and needs a dev/role-gated server;
  `interact` opens the closest interaction through the prompt's own Lua call. The NPC name in the
  demo comes from the task brief, not from a player log.
- Native client load of the composed source was **not** run by this worker (the lead controls the
  native client). See Open gaps.

## Demo

The real native transcript is the lead's step (no native client was run here). The command is:

```text
python scripts/run-local-baseline.py ... --lua-probe --rust-gateway --content <content> ...
python scripts/lua_bridge.py <run> demo
```

The demo waits for an in-world position, sends the brief's `realm goto` line through the chat path,
waits until the closest interaction target is the NPC, opens the prompt, reads the radial buttons,
clicks the Talk button by name, reads the 26/3 rows, clicks the first row that is not Goodbye (or
`--page`), and reads the re-shown body. Every request/result pair is printed and appended to
`<run>/lua-bridge-demo.jsonl`. `tests/test_lua_bridge.py::DemoTests` runs the same sequence against a
file-protocol client stand-in to pin the driver logic; its 10-step transcript is a driver test, not
native evidence.

## Security note (secure-code-guardian)

Attack surface: the command file in the run folder, writable by the local harness user; there is no
network listener and no game-protocol input. Hostile content considered: invalid/truncated JSON, a
missing or non-scalar `id`, unknown commands, huge lines/files, clicks on rows that were not offered,
ambiguous labels, empty/oversized chat text, and `key`/`move`. Refusals: the JSON decoder and every
command run inside `pcall`, the poll is bounded in bytes/lines/commands, unoffered or ambiguous clicks
error before any `SelectOption`/`OnUserEvent` call, chat is limited to 1..1000 bytes and goes through
the client's existing chat path (the server applies its own policy), and the bridge never opens a
path supplied by a command and never evaluates code. The result file and transcript are written to
the private run folder, not the repository. No secrets, session tokens or player names are recorded;
`closest`/dialog text are the client's own UI values and stay in the lab run folder.

## Open gaps

- Native load and the demo transcript remain the lead's acceptance step. The composed source is
  parsed by the lab checker and by a stock Lua 5.1 compiler, and the bridge logic runs in stock Lua
  5.1.5, but only the real client can confirm its `io.open("../...")` cwd and the UI calls.
- The `windows` list is the heuristic above; it is not a complete window inventory.
- `key`/`move` are deliberately unsupported; a future Frida hook could add them, but no client Lua
  entry point was found. The prompt click (`interact`) covers the interaction path.
- The demo's closest-target check assumes the client's dataset returns the NPC's display name; if a
  localised name differs the demo stops with a clear timeout, and the lead can click Talk manually
  and still use `state`/`click` by name.
- `--page` is needed only when the first non-Goodbye row is not the intended page.

## Checklist

1. **A refusal changes nothing.** `test_refused_commands_run_no_client_action` sends unknown,
   `key`, `move`, an unoffered dialog click and an empty chat plus a malformed line; the stub's UI
   action log is empty and every answer is an error. The errors are written before any UI call.
2. **Rollback covers all state.** No transaction or shared mutable state: the bridge keeps only its
   poll offset, last dialog/radial capture and answered ids; refused commands never reach a client
   action. The server's own transactions are untouched.
3. **Apply deltas.** N/A: no payout, inventory, coin or position is written by the bridge; clicks and
   chat are the client's existing actions.
4. **Busy rules are mutual.** N/A: no activity is added; the server's busy table is untouched.
5. **Every entry path is gated.** `--lua-probe` is the only path: `validate_lua_probe` checks the
   package hashes and the composed source, and `apply_lua_probe` verifies the original run copy and
   the composed hash before writing. No second injection path.
6. **Reachable in production, tested through it.** `run-local-baseline.py --lua-probe` calls the
   overlay; the tests drive the real `validate_lua_probe` and the real Lua bridge (through
   `OnUpdate` and the command/result files) plus the Python client over the same files. The native
   client remains the lead's run.
7. **Survives reconnect.** The command/result files outlive a session; `loadAnswered` rebuilds the
   answered ids from the result file, and `test_a_reload_does_not_repeat_an_answered_command` proves
   a second load of the bridge does not replay a click. Gameplay saves are untouched.
8. **Every exit path restores the player.** N/A: the bridge performs one UI action and the client's
   own paths close menus (`OnUserEvent`/`Pop`); it never enters or exits gameplay, warps or holds a
   transaction.
9. **Economy safety.** N/A: no item, coin, XP, reward or quantity is read or written; `click` selects
   only rows the client itself displayed, and `chat` is the ordinary chat path.
10. **Wire format matches the client reader.** No game wire change. The JSON protocol is pinned by
    the tests (ids, partial lines, UTF-8 and `\u`, malformed input, timeouts); the UI calls use the
    cited client functions (`Ui.DialogSelect` slot, radial event id, `Ui.ProcessChatCommand`).
11. **Unique ids.** Command ids are `pid-time_ns-sequence`; the result echoes the id; the Python
    client matches by text and the test asserts uniqueness/correlation. Dialog row slots are the
    client's own 0..4 values, not invented ids.
12. **Others see changes.** N/A: the bridge adds no fanout; the actions it calls (chat, click) use the
    client's normal path, whose server broadcast rules are unchanged.
13. **Content works end to end.** `DemoTests` asserts the final page body (not an intermediate flag)
    through the file protocol; the native demo is the lead's step.
14. **Values live in data.** No gameplay values are added. The poll/byte/line bounds are harness
    protocol constants, documented next to the protocol in `lua_bridge.lua`; they are not tuning
    content and never reach the server.
15. **Canaries break production code.** The wrong dialog slot canary made the real Lua test fail
    with `dialog\t1`/`dialog\t3`; the reversed page-choice canary made the Python test fail with
    `'Goodbye' != 'Cooking: Strong Arm Stew'`. Both were reverted and the suites are green.
16. **Hands off session plumbing.** No `src/bin/osfr-gateway.rs` or `src/gateway.rs` (or any Rust
    file) changed.
17. **One player's error never stops the server.** N/A: client-side only. For the harness itself,
    every command, hook and poll is `pcall`'d, so a malformed command or a failed UI call writes an
    error line instead of breaking the client UI.
18. **A type's rules live on the type.** No Rust type is involved. The protocol's file names and
    bounds are declared once in `lua_bridge.lua` beside the protocol; `lua_bridge.py` repeats the
    two file names with a comment to keep them in sync (they are a cross-language protocol, not a
    struct). `compose_probe_source` is the one rule for the composition and documents it.
19. **Hot paths stay cheap.** Per UI frame the wrapper only increments a counter and tests a modulo;
    every 15 frames it opens/reads/closes a small file, and when nothing changed it allocates nothing
    and returns before building a line. `state`'s table scan and JSON encoding run only for a state
    command. No per-tick game state is cloned or compared.
