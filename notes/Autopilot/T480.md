# T480: pay each collection's captured completion reward once

Sonnet builder, tip 83cd0bc. The research pack at `lab/fleet/out/brief-research/T480.md` was written
against tip 1e2def7 and is stale: `collection_pickup.rs`, `collection_catalogue.rs` and
`collection_coin_pickup.rs` all exist now, so the prerequisite holds. Its other points are answered below.

## What changed

- `CollectionCatalogueContent::completion_grant(collection_id, player_guid, gender, unlocked, item_known)`
  (`src/collection_catalogue.rs`) builds the `RewardGrant` from the catalogue row:
  - coins: `reward.coins` (R), client reader `008e7930`: after the success byte at `+0x74`, the first dword
    goes to `+0x50`, which getter `0091c2e0` returns as the coin amount (second dword to `+0x48`, stars,
    `0091c290`). Both decompiled with `ida_query.py` this run. Our encoder writes the same slots.
  - items: gender 2 gets `female_item_definition_id` when present and defined; everything else gets the
    captured item (R). An id the item catalogue does not define is skipped, so it cannot refuse the rest.
  - XP: to the named profile (not the active one), only when that profile is unlocked, because
    `apply_grant` would refuse the whole grant for a locked one (R).
  - never paid: tokens, `collection_add`, `quest_add` (meaning unknown, R).
  - display: the collection's own `icon_id` and `name_id`; guids are the player.
- `handle_collection_coin` (`src/gameplay/collection_pickup.rs`) now runs the pickup on a staged clone of
  `Gameplay` and commits it only on success. `record_collection_entry` builds the grant, calls
  `ProgressionExtras::collect` (whose completion path applies it under key `collection:<id>`), then sends the
  38/10 followed by the reward packets and adopts the paid state through `adopt_reward_state`.
- A `GrantFailure` from the completing click refuses the whole pickup and changes nothing. A full bag says
  `Your bag is full. Make room before collecting that.`; any other failure (coin or XP overflow) says
  `You cannot collect that right now.` and logs `collection_reward_refused`. The coin stays clickable.
- Load logs the captured reward items that have no definition once (`collection_reward_items_skipped`:
  12410, 38816, 38817). The catalogue already stores them as `item_definition_id: null`.
- `tests/collection_coin_pickup.rs::completing_a_set_records_completion_once` expected no reward packet on the
  last coin; it now expects them only there.
- New `tests/collection_rewards.rs` (8 tests).

## Checklist

1. Refusal changes nothing: the click runs on a clone that is dropped on refusal; full-bag and XP-overflow tests
   compare the whole save plus the visibility revision before and after, and check the coin is not hidden.
2. Rollback covers all state: ledger, inventory, coins, XP and visibility are all on the clone; `collect` itself
   commits the ledger only on `Ok`.
3. Deltas, not snapshots: `adopt_reward_state` adopts the snapshot taken in the same click, with nothing in
   between; the existing fishing and quest paths work the same way.
4. Busy rules: unchanged, the busy check precedes the click (existing test).
5. Every entry path gated: the only entry is the 26/8 click, behind busy, range and zone checks. Rewards come only
   from the ledger transition, never from a client field (the request carries only the coin guid).
6. Reachable and tested through the real route (`Gameplay::handle_in_world`).
7. Survives reconnect: `completed` is in the saved ledger; the relog test and the "completed but an entry
   returned" test pay nothing. The `collection:<id>` key lives only on the per-click snapshot (the gameplay
   adoption does not persist keys), so the saved `completed` set is the real once-only guard.
8. Exit paths: nothing long-lived is started.
9. Economy: free grants are one-shot per character per collection; item ids and counts come from bounded data.
10. Wire: no new bytes. The 38/10 is unchanged; the bundle comes from `encode_display_bundle` (reader `008e7930`).
11-12. Not applicable: no instance ids; the coin is personal, so nothing is broadcast.
13. Content end to end: items land in the saved bag, coins and XP in the profile, asserted in the tests.
14. Values live in data: rewards are catalogue rows (load bounds in `collection_catalogue.rs`); the bag capacity is
    the shared `reward_bag_capacity`.
15. Canaries break production code (above).
16. No session plumbing touched.
17. One player's error: overflow and a full bag are refusals, not `Err`; the `Err` path remains only for invalid
    data and propagates as it did before.
18. Type rules: the grant rules sit on `completion_grant`'s doc comment.
19. Hot path: not on a tick.

## Threat note

A hostile client can send a coin guid at will. The request is decoded as before and only a placed coin the
server showed this player, in range, not busy, not already collected, reaches the ledger. The reward never
reads a client value. Replay (same click, relog, reconnect) is stopped by the saved `completed` set. Overflow of
coins or XP is refused with nothing changed, never an error out of the handler.
