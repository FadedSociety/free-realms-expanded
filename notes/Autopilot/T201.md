## Threat note (secure-code-guardian)

Attack surface: any client can send 26/8 (click an actor) and 26/10 (choose an option) with an
arbitrary u64 target and i32 choice at any time from any position.

- Unknown/forged target GUID: the 26/8/26/10 path resolves the target through the server's
  `NpcVisibility` content-key map; an id that is not a spawned content actor yields no menu and
  teaches nothing (tested: wrong NPC, forged choice).
- Forged/stale choice: `NpcInteraction::select` requires the choice id to be an option of the
  currently open interaction for that exact NPC (`InvalidOption`/`NoInteraction`), and re-checks
  zone and the 12 m range on every selection. The client can never name a profile id: option ->
  trainer comes from server content. Tested: forged id, wrong NPC, out of range, stale menu.
- Rank/busy bypass: the new-tip NPC router refuses 26/8 and 26/10 while any shared activity is
  live (`Gameplay::busy_interaction_refusal`), so a busy player never receives Dewey's menu and
  cannot reach `learn_job`; `learn_job` still re-checks the same shared busy table, and
  `Profiles::learn` re-checks `requires`. A rank-4 request is refused with "level 5 Brawler" and
  changes nothing (tests + canaries 1/2). The row's rank is a content value the loader bounds
  1..=20; unknown prerequisite profiles and rank 0/21 are load errors (existing
  `malformed_trainer_files_are_refused_at_load`).
- Replay: a second Learn is `AlreadyKnown` before any grant, in-session and after reload (tests).
- Economy: the unlock grants only starter definitions from the server's `profiles.json`; owned
  pieces are equipped rather than re-granted and missing pieces are granted at most one each, with
  no client-supplied id or quantity. No coins, no tradeable value, no client-reported outcome.
- Atomicity: the unlock runs on the request's staged `Gameplay` clone and commits only when the
  whole request succeeds, so a later failed child cannot leave an unlock or starter items behind
  (existing bundle test). No new persisted field, no new permission, no session change.

## Checklist

1. **A refusal changes nothing.** `refused_learn_changes_nothing` snapshots the whole save
   (`serde_json::to_vec(snapshot)`) and compares it after under-rank, forged-selection, wrong-NPC,
   busy and out-of-range refusals; the under-rank refusal is repeated to prove the open menu was
   not consumed. The a2 canary breaks the router's shared busy gate
   (`busy_interaction_refusal` -> `false.then(...)`) and the busy case then fails its
   "no 26/9 menu" assertion; canary 1 removes the row the feature needs. The a1 rank canary is
   recorded above. `AlreadyKnown` leaves state identical in
   `dewey_learns_warrior_through_the_npc_menu` and after reload.
2. **Rollback covers all state.** The unlock and starter grant run on the request's staged
   `Gameplay` clone (`handle_npc_packet` commits only when `learn_job` reports `changed`); no
   `Rc`/`RefCell`/`Arc` or side table was added. The open menu is session state inside that same
   `Gameplay`, so the existing bundle rollback covers it (existing test).
3. **Apply deltas, never restore snapshots.** `learn_job` inserts one id into `unlocked` and
   equips/grants from the live inventory; nothing restores an old inventory, coin or position
   snapshot.
4. **Busy rules are mutual.** No new activity was added, so no `Occupation` variant is needed.
   The new-tip NPC router refuses 26/8 and 26/10 while any shared activity is live, and
   `learn_job` re-checks the same table before any change; the test starts a real Mining run and
   proves both frames are refused with the save unchanged. Learning is not an activity, so the
   reverse direction is unchanged.
5. **Every entry path is gated.** `trace_path` shows the only `Profiles::learn` chain is
   world dispatch -> NPC packet -> `learn_job` -> `learn`; the router's shared busy gate covers
   both the click and the selection before the menu is consulted, `learn_job` re-checks busy, and
   `Profiles::learn` re-checks `requires`. There is no automatic or event-driven trainer path,
   and reconnect loads the persisted `unlocked` set rather than re-granting.
6. **Reachable in production, tested through it.** The tests load a real `Gateway` from a
   content package and send the real 26/8 -> 26/10 frames; the spawn comes from the production
   `NpcVisibility::load` and the click identity through `content_npc_key`, which only knows
   spawned actors.
7. **Survives reconnect.** `warrior_unlock_survives_reload` saves with `game_store::save`,
   reloads with `load_or_create` + `Gateway::load_gameplay`, and asserts Warrior stays unlocked,
   the active job is unchanged, the gameplay snapshot is identical and a second Learn grants
   nothing.
8. **Every exit path restores the player.** Learning never switches the active job or moves the
   player (asserted); refusal, `AlreadyKnown`, reload and out-of-range all leave the character
   where it was. No occupation was introduced, so no stuck state is possible.
9. **Economy safety.** The grant comes only from server `profiles.json`; already-owned starter
   pieces are equipped instead of re-granted and each missing piece is granted at most once.
   There is no client-supplied item id, quantity or result, and no coins. The free pieces are
   class-bound starter gear and cannot be re-granted (AlreadyKnown precedes the grant; reload
   test).
10. **Wire format.** No packet changed. The 26/9 label field is parsed at the documented 28-byte
    record offset and asserted to be 412471; the AddNpc body is parsed with the production
    reader-derived parser and its actor/model/name are asserted. Client reader `0x00921a10` reads
    the u64 actor id, then the i32 name id and model id (the same order as
    `startup_world::NpcSpawn`); `0x01804c14`/`sub_97B520` format and resolve `Global.Text.%d`; the
    26/10 constructor `0x00a36f80` and 26/6 constructor `0x009f5890` are cited above. The row only
    supplies those already-parsed values.
11. **Unique ids.** No instance/GUID is created; 9000000076 is the existing content key used once,
    in the project's synthetic actor range. `content_check --strict` reports 0 duplicate-guid
    errors and the spawn table's own duplicate check passes.
12. **Others see changes.** The spawn enters the existing directed visibility path; a test
    asserts a nearby viewer's 35/2 packet carries actor 9000000076. Nothing else visible changed.
13. **Content works end to end.** The final outcome is asserted: 32 unlocked, only 32 added, the
    "You learned the"/outfit message, the label id in the real menu, and the persisted state.
14. **Values live in data.** The trainer, rank and spawn are content rows; the loader keeps the
    1..=20 rank bound and profile checks. No timing/cap constant was added to Rust.
15. **Canaries break production code.** Canary 2 breaks `Gameplay::busy_interaction_refusal`
    (new-tip production code) and canary 1 removes the content row the feature needs; both failed
    real assertions and every file was restored byte-identically (sha256 printed and matched).
    The a1 rank canary is recorded above.
16. **Hands off session plumbing.** `src/bin/osfr-gateway.rs` and `src/gateway.rs` are untouched,
    as are save ordering and transactions.
17. **One player's error never stops the server.** No shared-tick or fanout code changed; refusals

18. **A type's rules live on the type.** No struct field was added or reinterpreted. The name-id
