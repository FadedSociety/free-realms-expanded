# L057: new accounts are members by default; `osfr-account member` sets one account (lead)

Brief: `lab/autopilot/opus/lead-briefs/accounts-are-members-by-default.md`. Base: L056 `e499f08`.

## Why

L056 showed the stock client ignores the slot count the server sends. `ClientLoginManager::OnLoginAuthReply`
(`0x009542d0`) overwrites the payload's member flag with the login reply's outer IsMember byte and sets
MaxCharacters = `1 + 2 * IsMember` (re-checked in IDA for this task: `0x00954375` reads the IsMember argument,
`0x0095437d` `setnz cl`, `0x00954383` stores it as the member flag, `0x00954394` `lea ecx, [ecx+ecx+1]`,
`0x00954398` stores MaxCharacters). Every account was created non-member, so nobody could reach the creator
through "Add a Character". Lead decision (2026-10-22): every new account is a member (R). the owner may override it in
one place, `AccountFlags::NEW_ACCOUNT`.

## What changed

- `src/account.rs`: `AccountFlags::NEW_ACCOUNT` (membership on, underage off, open chat off), the one default for
  every account-creating path. `#[derive(Default)]` is unchanged (all false), so tests and fixtures that build
  `AccountFlags::default()` stay non-members, and stored accounts load exactly as saved (the struct has no serde
  defaults; `deny_unknown_fields`).
- `src/login.rs` `LoginService::authenticate_account`: flags are `{ underage, open_chat from config,
  ..AccountFlags::NEW_ACCOUNT }`. The same value feeds all three creation sub-paths: no store yet, a store that
  lacks this login name, and the legacy save migration (`migrate_legacy_account_store`).
- `src/bin/osfr-account.rs`: `create` uses `AccountFlags::NEW_ACCOUNT` (it used `default()`; underage and open chat
  stay false as before). New subcommand
  `osfr-account member --store <accounts.json> (--account-id <id> | --handle <handle>) --state <on|off>`, same
  flag style as `set-role`. It parses and validates every option before the lock, takes `AccountStoreLock`, loads
  the store, resolves exactly one account (by id, or by `login_handle_hash` of the handle), sets only
  `flags.membership` through `AccountStore::set_membership_offline`, saves through `AccountStore::save` (validate,
  then `character_store::replace_bytes`, atomic) and prints `account <id> membership on|off`. Unknown id or handle,
  an invalid state, or both selectors are refused before any write.
- `src/account_store.rs`: `set_membership_offline(account_id, member)`, the twin of `set_account_role_offline`
  (NotFound for an unknown account, never routed from a packet).

Other creators checked: `scripts/bundle/make_bundle.py`, `scripts/stress/run.py` and `launcher/tests/auth.rs` all
provision through `osfr-account create`, so they now make members too. Nothing else in `src` or `launcher/src`
calls `create_account` (rg + graph). `AccountStore::load_or_migrate` takes flags from its only production caller,
`migrate_legacy_account_store`, which passes the login flags through.

Downstream effect of a member account (all existing code, nothing new wired): the login reply byte 6 is 1 (L056),
so the client stores MaxCharacters 3 and opens the creator; at character select the gateway reloads the store and
sets `GameRuleSet::new(MembershipState::new(true, None))` (member-only gates open, the same as
`GameRuleSet::default()` already is) and `is_member` for the player presentation. Coin shop member prices
(`coin_shop.rs` `set_member_status`) have no production caller yet, so shop prices do not change with this task.

## Slot cap: client says 3, server allows 6 (R)

`slots.max_characters` stays 6 for both creation paths. A member's client logs
`AccountInfo: The user that is logged in is a member, can have a maximum of 3 characters ...` (format string
`0x017e7a88`, only xref `0x0071941b` in `ClientAccountManager::OnAccountInfo` `0x00719330`), while the server
allows 6. That is harmless: the only client gate is `CharacterSelect:OnUserEvent` "addCharacter" →
`GetMaxCharacters() > 1` (`ScriptsBase.lua:16204-16222`), which never compares with the current count, and
`CharacterSelect:Populate` (`ScriptsBase.lua:16187-16201`) lists every row the server sends. The server is the
only authority on the count (`account_store.rs` `insert_character`, status 6 TooManyCharacters). Lowering the cap
to 3 is a separate the owner call; nothing here depends on it.

## Operator use

Stop `osfr-login` first (it holds `accounts.json.lock` for its lifetime, so `member` refuses while it runs), run
`osfr-account member --store <runtime>\accounts.json --account-id <id> --state on`, start login again. The gateway
reads the store at each character select, so it needs no restart; the player's next login sees the change.

## Security

Threat note (secure-code-guardian, security-reviewer):

- **New-account defaults (server-side only).** Membership comes from `AccountFlags::NEW_ACCOUNT`, never from a
  client field. Login only authenticates the configured local session name or a broker-verified handle; the broker
  never creates accounts (`issue_challenge` needs an enrolled key), so the auto-create path stays limited to the
  host's own loopback name. New accounts still get role Player (`create_account`); membership grants member
  content only, which is the intended policy, not a role or admin bit.
- **Operator command trust boundary.** `osfr-account` is host-only (filesystem ACLs are the authority, as for
  `set-role`). Every option is checked before the store is touched; the handle goes through `login_handle_hash`
  (3-32 of `[A-Za-z0-9_-]`); refusals return before `save`, so a refusal changes nothing (test compares store bytes
  for five refusals). It runs under `AccountStoreLock` and saves atomically through the validated `save`.
  Output and errors carry only the account id and on/off, never the handle or a key.
- **Login reply oracle.** Unchanged: a refused login and a refused broker token still send IsMember 0 without an
  account lookup (L056 test `login_reply_carries_account_membership_in_the_byte_the_client_reads` still passes).
  Membership of a real account is only visible to that account's own successful login.
- **Stored data.** Existing stores load unchanged (no serde default, no migration); login never rewrites flags of an
  existing account (test: `member off` survives the next login). No new log lines; nothing secret logged.
