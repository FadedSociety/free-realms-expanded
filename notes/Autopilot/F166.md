# F166: a racing tick must not rewrite the character save

## What changed

A kart race ticks at 20 Hz. Every racing tick stamps `WeaponState::last_tick_ms`
(`src/kart_weapons.rs`, called from `WeaponState::tick` through `KartService::tick`), and the kart
branch of `Gameplay::tick_world` reported `changed = before != *kart.state()`. So every racing tick
looked like a persisted change: `Gateway::tick_at` set `state_changed`/`gameplay_changed`, the
gateway bin (which defers only pose-only changes) rewrote the whole character file 20 times a
second per racer.

- `src/kart_weapons.rs`: `WeaponState` no longer derives `PartialEq`; the manual impl compares the
  persisted fields (`weapons`, `effects`, `next_id`) and excludes the session-local tick clock. The
  field doc and the impl doc state the rule, so the next field added to the type is decided here.
  No flag was added to `KartService`.
- `src/gameplay.rs` (hub): the kart branch of `tick_world` keeps the same comparison and gains a
  two-line comment naming the invariant. Net hub growth: +2 lines, no new branch.
- `tests/kart_npc_entry.rs`: two synthetic `Gameplay`-level tests (real `handle_in_world` + `tick`
  path) on a temp copy of the lab gameplay content with this file's synthetic kart package on top.
- `tests/kart_weapons.rs`: the serde round-trip test pins `last_tick_ms` explicitly, because
  equality no longer covers it.

## Behavior

- A racing tick with no event returns `changed == false` and no replies, while the weapon clock
  still advances (asserted `race_clock == now_ms`).
- Start (countdown -> racing), finish + reward claim, and abort still return `changed == true`.
  Abort returns to the world (`scene_zoning`), clears `active`, restores the prior job, and leaves
  the phase `Aborted`.
- Reconnect mid-race (save taken between two clock-only ticks) restores `Racing`, keeps
  `previous_job`, and the next tick advances the clock without requesting a save.
- Cost per tick: no new allocation or clone; the state equality now compares one fewer `u64`
  (`last_tick_ms`) and the same vectors/scalars as before.

## Evidence and reconstruction

No client opcode, packet field layout, enum value or reader/writer changed. This is a server-side
save-decision change, so no new IDA trace applies; the recovered weapon wire layout (documented and
tested in `src/kart_weapons.rs`) is untouched and its codec tests were re-run. Rule marked
reconstructed:

- (R) A session-local tick clock is not persisted progress: it is re-stamped on every racing tick,
  it is bounded again by `WeaponState::validate_for` on restore, and no award depends on it.

## Threat note (secure-code-guardian)

Client input parsing, saves, coins, items, rewards, roles, chat and economy paths are unchanged. The
only hostile-client consideration: a hand-edited save with a nonzero `last_tick_ms`, empty
`weapons`/`effects` and `next_id == 0` now compares equal to an empty `WeaponState` where the old
equality differed. That shape is only consulted by `KartService::restore` when `weapon_effects` is
false; `validate_for` still bounds the clock to the race window and the state can carry no weapon,
effect, id or grant, so it cannot mint an item or a payout. Every refusal path and every economy
path are untouched; the forged-clock refusal test still passes. No player names or chat text are
recorded.

## Open gaps

- Countdown ticks still advance `schedule_cursor`/`countdown_sent`, so a tick that emits a
  countdown frame can still report `changed`. Those are one-shot schedule frames (about five per
  race), recomputed from absolute server time on restore, and none is an economy grant; the 20 Hz
  racing churn this task targets is gone. Closing them would need a field-by-field snapshot
  comparison or a dirty flag, which the brief preferred to avoid.
- The private/ignored `kart_gameplay` fixtures were not available (`OSFR_KART_PLAYABLE` and
  friends); the new non-ignored test uses the lab `opening-journal-text-v2/content` that
