# T825: card lobby follow-ups (92, 137, 503) and the starter collection sync (lead brief, Opus builder, 2026-10-27)

## Why
Native 2026-10-27 ~15:05Z: the T813 lobby push works. The card window shows the Casual Games Lobby, and the Collection screen
opens, empty. The client then sent classes 92 (its own Join), 503 and 137 (three times), which went unanswered. Every reader
below was decoded with Hex-Rays on a scratch copy of the TCG DLL database. Every server body is golden-tested against its
reader before it is sent: an unreadable body stalls the connection for good (receiver `10192500`).

## Client facts (TCG DLL)
- **137 `LobbyCommand_ChangeStatus` v1** (creator `1015eac0`, reader `1015ea00`, writer `1015ea60`, execute `1015e810`): the
  LobbyCommand level (three headers, AccountID), then int status.
  - The client sends it on every screen change (`1037c540`: screen 2 hub -> 3, screen 3 lobby -> 2, screen 6 -> 7, ...).
  - A server copy sets the player's status (`10001360`) and raises event 25.
- **92 Join requests**: the client's own `LobbyCommand_Join` v4 with account, group, role, and the rest empty (no property set).
  - `10371960`: group 1, role 1, as soon as it learns group 1.
  - `1036fff0`: from its lobby-list slots `10370090`/`103700b0`, role 1.
  - `103717e0`: observer, role 3.
  - `1032dde0`: back from a game, role 1.
  - The answer the client waits for is the server's Join announcement (event 5, `10371cd0`). For its own account and group 1
    that opens screen 2, the hub. Other groups open the screen their lobby type selects (type 4/9 none, 5 tournament dialog,
    7/8 event screens, a match group the match dialog), and an ordinary lobby type opens the lobby screen (3).
- **503 `AccountCommand_UploadAvatarImage`** (creator `10016720`, reader `10016810`, writer `10016890`): the account level,
  then a byte count and the image bytes. Sent by `102a9710` when the client learns the root group. The client execute
  (`100165d0`) is a no-op, and no response class exists.
- **Sync family** (`SynchronizationService`): three headers (level `101d7090`/`101d70d0`), no account level.
  - **83 Start v3** (reader `101da040`, execute `101d9e70` -> `101dbbb0`): instance count, ModID, account, int.
    - The client loads or creates the account's collection (`101db320`, named by account id) and compares its instance
      count (`10072190`, tradable instances) and ModID (`10070de0`).
    - On a match it sends 86 Complete; otherwise it sends 87 Update.
  - **84 StartInstances v2** (`101dadf0`, execute -> `101dbc80`): account, collection type (1 online, 3 trade), count, ModID.
    The client clears the collection, raises event 27, and sends Update.
  - **85 SendInstances v2** (`101d94c0`, execute -> `101dc290`): base archetype, count, instances (`10077f00`: count, then
    `InstanceID`s), non-tradable instances, delivery id. The client files each instance under its archetype's
    `CollectionItem`, raises event 28, and sends Update.
  - **86 Complete v2** (`101d77c0`, execute -> `101db550`): delivery id. The client stamps the StartInstances ModID, writes its
    local collection cache (`1006f1c0` -> `1006e510`, the `tcg/data/collections/<account>.cln` files), and raises event 29.
  - **87 Update v1** (`101db190`): headers only.
- **`InstanceID`**: class 350 v1, one header (reader `101476a0`, writer `10147700`). Fields: Archetype ID, Series ID, Instance
  Number.
- **`CollectionItem`**: class 52 v7 (reader `100784f0`, writer `100764f0`). Fields: ArchetypeID, quantity desired, foils
  (bool as int), instances, non-tradable instances. Below v7 an int follows ArchetypeID, and below v4 the lists differ. It is
  the client's per-archetype container and is not sent in the sync.
- **`CollectionData`**: class 51 v3 (reader `10073200`). Fields: strings CollectionID, Name and Notes; a map of archetype id
  to CollectionItem; owner account id and name; collection type; ModID.
  - A parser with exactly this layout reads the client's `tcg/data/collections/default.cln` to the last byte (356,892 bytes):
    2,207 archetypes, 16 instances each (two have 100), series 0, instance numbers 0..15.

## Change
- `card_service.rs`:
  - `change_status` echoes the status for the connection's own account.
  - `join_request` decodes the group and role prefix.
  - `UPLOAD_AVATAR_IMAGE`.
  - The four sync bodies: `sync_start`, `sync_start_instances` (type 1), `sync_send_instances` (one delivery; instance
    numbers 0..copies per archetype, series 0) and `sync_complete`.
  - `collection_mod_id`: SplitMix64 (`crate::hash::mix64`) over the starter list. It is positive and non-zero, and changes when
    the list changes.
- `card_game.rs`: `Lobby.collection` (optional, R) lists `{archetype_id, copies}`. Bounds: positive and distinct ids, 1..=16
  copies (the default collection's count), at most 100 archetypes.
- `card_listener.rs`: after login, the listener handles the client's 137, 92, 503, 87 and 86 itself:
  - 137 is echoed.
  - 92 is logged as `card_join_request` (group, role) and not answered. The server knows one group, the root group 1, whose
    membership it pushed at login. A server Join for it would move the client from the lobby to its hub (screen 2).
  - 503 is answered by silence.
  - The sync: Start right after the lobby (when the lobby names a collection), then one step per client Update
    (StartInstances, SendInstances, Complete). A client Complete after the Start means its cached collection matched, so
    nothing is sent.
  - One `card_sync` event per connection ("sent" or "cached", counts only).

## Threat note
Nothing new is trusted:
- The status echo always names the connection's own account and goes only to that connection. The client's account field
  is ignored.
- The Join request is only logged (ids).
- The avatar bytes are dropped. Frames stay capped at 64 KiB: an avatar image larger than that would close the connection as
  `bad_frame` (R, not seen natively).
- The sync sends server data only.
Persistence: none. The starter is data, and the instance ids are derived (series 0, numbers 0..copies), so every login
yields the same ids. The client caches the collection under the ModID and skips the transfer when it matches. No character
save changes.

## Structure
One serde struct and one bound loop in the card content. Pure codec functions in `card_service.rs`. In the listener: one
`SyncStep` enum, one `lobby_command` method and `synced`. Join requests have their own budget in F800's per-kind counters
(`AnsweredKind::JoinRequest`) and are logged through F800's `log_answer`, which checks the budget before building the event,
so a capped frame allocates nothing. The `card_lobby` and
`card_sync` events happen at most once per connection. No new file.

## Starter collection (R, for the native package's `card_game.json` lobby block)
The client data holds no starter deck list. The skirmish setup `104ab920` names "Digital Starter - Machine/Nature" decks,
which are not in `tcg/data/decks`. So the starter is chosen from archetypes that the client's archetype store
(`tcg/data/archetypes/storage.dat`, one zlib record per archetype) defines and its `tcg/data/collections/default.cln` also
lists. The pick is 15 archetypes × 2 copies = 30 cards (10 creatures, 3 tricks, 2 resources):
100009946, 100009948, 100009951, 100009952, 100009955, 100009956, 100009957, 100009960, 100009961, 100009963 (creatures);
100010026, 100010033, 100010042 (tricks); 100009988, 100009995 (resources).
The ids in the 1003xxxxx range of `default.cln` (763) have no local definition, so they were avoided.
