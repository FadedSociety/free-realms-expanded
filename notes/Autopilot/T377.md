## Threat note (secure-code-guardian)

The change adds no parser and no new client input path; it enables two data rows
that already travel the reviewed Talk/quest paths. A hostile client could send:

- **A forged 49/2 accept** for E5/E6 with no open offer: `accept` requires
  `pending_offer == quest`; test 4 snapshots the whole typed state and serialized
  save and asserts equality.
- **A forged or premature 49/14**: `finish_turnin` requires the server-opened
  `pending_turnin`; before the scout/return and for an unstarted quest it is a
  no-change refusal. A replayed 49/14 after payment is also a no-op (tests 2/3).
- **A client-claimed position or NPC**: the visit event is built from the server
  character pose passed to `on_location`, not from a packet claim; Talk advances
  only the content NPC id. Outside-radius, another-zone and non-target-NPC cases
  are asserted to change no typed state or save byte (test 4).
- **A near-cap wallet**: `apply_grant` uses checked arithmetic and the i32 wire
  bound; the grant is refused with no coins/XP/item and the pending screen stays
  retryable (test 4). The 8-coin/20-XP amounts are server-authored content, never
  client quantities.
- **A duplicate grant**: the `quest:<character>:<quest>` key and `Completed`
  status make the replayed request inert; the reward has no item, so no free
  sellable gear and no bag-capacity bypass.
- **Another player's chain**: state, pending screen and reward key are
  character-owned; test 5 proves A's offer/accept/visit/turn-in leaves B's state
  and wallet byte-identical.

No validation was relaxed. The tests are test-only and read the shipped content;
the fixture copies live under the system temp dir and are removed on drop.
