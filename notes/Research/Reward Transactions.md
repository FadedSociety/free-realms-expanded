# Reward Transactions

Snapshot: 2026-10-13. This note records the isolated W10 transaction API. It is not save-layer integration or native acceptance.

Workflow: Ponytail reused the loaded inventory/profile models and writers; Caveman kept the report concise; reverse-engineering was applied through the read-only `nmq dis` check below. Game recon, web research and asset-pipeline work were not applicable to this packet/state API.

## Evidence and implementation boundary

- The reviewed client guide says the reward bundle is presentation data; spendable coins, profile XP/rank and inventory changes arrive separately as client-update messages `38/19`, `38/14`, `38/18` and `38/2`. The guide has no captured reward traffic, so server decisions and packet order remain inferred.
- Client reader `008e7930` reads the success byte, then bundle fields including coins at object offset `+0x50` and stars at `+0x48`. The guide records the 69-byte empty bundle body, entry count, type-id/body sequence and final dword. `python -I scripts/native_map/nmq.py dis 008e7930 256` independently shows the reader storing the first byte at `+0x74` and the following dword at `+0x50`; `notes/Build Guides/Gameplay/Rewards and Collections.md` provides the full field and entry layout.
- Existing `inventory.rs::Inventory::grant_coins` emits the current `38/19` balance. `Inventory::grant` validates definition ids and stack limits, uses the saved non-reused instance counter, and emits `38/2` for a new stack or `38/3` for an update. `profiles.rs::Profiles::experience_packets` emits rank `38/18` before the full `38/14` profile update. The 100-XP rank curve and rank-20 cap are reconstructed, not client-recovered.
- Existing `game_store.rs::save` serializes one version-3 character/gameplay snapshot and replaces the file atomically. It has no grant ledger, account transaction coordinator or injected write-failure seam. The API returns a staged state only; the caller must persist inventory, profiles and applied grant keys in one snapshot before sending the returned messages.

## W10 API

`prototype/osfr-tools/src/rewards.rs::apply_grant` clones a runtime `RewardState` holding the loaded `Inventory`, `ProfileState`, caller-persisted `applied_grant_keys` and configured bag-slot count. It validates inventory definitions, positive counts, profile unlock state, arithmetic/wire bounds, display entry type/body minimum and bag capacity. Inventory operations retain the existing allocator and message encoders. An error returns no new state, so callers can discard the staged result without partial mutation. `RewardState` is a runtime wrapper, not a save document; integration copies its inventory snapshot, profile state and key set into `GameplayState` before `game_store::save`.

Messages are returned in this order: coin `38/19`; per-profile rank `38/18` then XP `38/14`; item add/update; family `50`, subtype `1` display bundle. This order, zero tint for simple grants, XP summed into bundle stars, the successful bundle flag, locked-profile refusal, the 256-byte grant-key bound, and the configured stack-slot limit are reconstructed policy **(R)**. Duplicate keys return a cloned unchanged state and no packets **(R)**. Callers must derive stable keys from server-owned objective/run state, never client text.

Display rows are caller-supplied serialized entry bodies, each prefixed here by its type id. The body must match that entry's client reader. A success byte of 1 requires the extra u32 on Item and Chest rows; this module checks known type ids and the 34-byte base minimum but does not parse each entry subtype. The 50/1 writer emits zero for unresolved fields and a 1.0 multiplier, matching the existing ordinary-toast writer. Whether those server defaults are historically correct is unknown **(R)**.

## Migration order and exact current sinks

1. **Persist the idempotency ledger first.** Lead integration adds `applied_grant_keys` to the saved gameplay state, migrates the current version-3 JSON envelope without dropping existing inventory/progression/counters, and tests that a failed save leaves the live state unchanged. Keep the gateway's save-before-send ordering. W10 alone does not meet Build Ledger item 11's injected-write-failure acceptance gate.
2. **Replace the shared grant helper and the pending quest sink.** Migrate `gameplay.rs::grant_reward` and `gameplay.rs::apply_quest`. The quest path currently clones inventory and quest state, uses `Inventory::grant_bundle`, then acknowledges the reward; the new state and acknowledgement must still commit together. Derive its key from the server-owned quest reward id.
3. **Migrate opening and encounter rewards.** Migrate `gameplay.rs::apply_opening` and `gameplay.rs::apply_encounter`. Opening rewards currently grant coins/items and add 25 profile XP in separate calls; profile unlock starter-item grants in `apply_opening` must remain staged with the unlock/equip changes. Keep `opening.rs::OpeningReward` as an outcome/content record, not a transaction sink.
4. **Migrate crafting and activity settlement.** Migrate `gameplay.rs::apply_smelting`, `gameplay.rs::apply_mining`, `gameplay.rs::apply_harvesting`, `gameplay.rs::apply_cooking` and `gameplay.rs::apply_forging` through `grant_reward`. Their ingredient consumption, engine/run state and product grant must continue to commit from the same outer staged gameplay snapshot. `cooking.rs::CookingTransaction` remains an outcome record.
5. **Migrate the chest grant and its display.** Extract the consume-key/chest and selected-item transaction from `mystery_chest_loot.rs::MysteryChests::handle`, called by `gameplay.rs::handle_mystery_chest`, so consumption, item allocation and the 50/1 display packet share one staged result. `mystery_chest.rs::item_reward` is a display writer, not a grant sink; replace or adapt it only when the new row encoder can fill the allocated item instance id and item presentation fields.
6. **Migrate the specialized kart payout.** Replace the economy staging in `kart_rewards.rs::claim_race_reward` after `RaceSession::claim_reward` and registered-payout checks succeed. Preserve its race claim authority and map the returned coin/profile-XP messages and `kart_rewards.rs::reward_bundle_toast` presentation into one grant. The registered payout amounts are reconstructed policy in the kart implementation.

The API does not migrate `gameplay.rs::apply_identity`: it installs/equips character-creation attachments rather than settling an earned reward. It also does not make the current reconstructed quest, chest, crafting or kart payout tables historical facts.

## Checks and remaining gates

The isolated `tests/rewards.rs` suite covers a combined coin/item/profile-XP grant and ordered packets, same-key retry, bag-capacity refusal without input mutation, coin overflow refusal, empty 69-byte bundle body plus 3-byte header, and row framing. Its catalogue and player/profile records are synthetic. It does not prove save-layer atomicity, gateway registration, original server policy, complete entry-body validity, or native UI presentation. Those remain lead integration and native acceptance gates.
