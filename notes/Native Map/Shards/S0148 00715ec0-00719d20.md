# S0148 (00715ec0..00719d20) - ClientAccountManager login flow and its SoeUtil containers

Read-only static mapping of the 15 targets in this shard against the shared Ghidra export
(`nmq`), with the small functions decoded from raw bytes. Nothing here is native-run evidence.

## What lives in this range

`ClientAccountManager`, the client's account / login / character-select manager, plus the SoeUtil
container instantiations it owns.

* `00715ec0 ClientAccountManager::Run` - the per-frame state machine (switch on the state dword at
  `this+0x22270`, loop while it is below `0xfd`). It names itself in its own log lines
  (`ClientAccountManager::Run(state=ClientAccountManagerStateStoreNewCharacter)` and
  `...ClientAccountManagerConfirmCharacterDelete`) and drives the whole flow: character-select and
  creator screens through the Lua entry `FUN_009797a0` (`CharacterSelect:Show`, `CharacterSelect:Hide`,
  `CharacterCreate:StartInGameFlow`, `CharacterNameScreen:Show/Hide`,
  `CharacterCustomNameScreen:Show/DisplayText`, `CharacterCreatePopups:Show`, `HUD:LoadingWorldAssets`,
  `MiniMap:ToggleEnabled`, `FreeRealmsLogo:Show/Hide`), the delete-wait counter `this+0x53a50`,
  `ClientAccountManager::CreatePlayer` (`FUN_007140c0`), `ClientAccountInterface` item setup
  (`FUN_0071fd60`), then releases `this+0x22034` and `this+0x2226c` and ends with the Lua entry
  `HUD:ShowLargeLoading` (or the `0xfd` exit branch).
* The class vtable `017e7ccc` (`ClientAccountManager::vftable`) has exactly eight slots, all of them
  login-server reply handlers:

| slot | address | handler (own log string) |
| --- | --- | --- |
| 0 | 00719330 | account-info result: member / max-characters / admin flags |
| 1 | 00719550 | character list of the account (guid + appearance) |
| 2 | 00711ca0 | server list (`No Servers Available`, `Server %d of %d`) |
| 3 | 007100c0 | `OnRequestCharacterCreate: result=0x%0x` |
| 4 | 00710e20 | `OnRequestCheckName: result=%d` (already recorded in `Pieces/050`) |
| 5 | 00711220 | `OnRequestCharacterLogin: result=0x%0x` |
| 6 | 007198b0 | `OnRequestCharacterDelete: result=0x%0x` |
| 7 | 0070ea10 | `OnRequestFriendsList: result=0x%0x` |

  Slots 2-5 and 7 are outside this shard; they were read only as context. Note that slot 0 is **not**
  a scalar deleting destructor - that rule of thumb does not hold for this class, and `0071a8f0`
  (with `008a6440` as its scalar deleting destructor) is the manager's own destructor body.
* Container behind the character list: `SoeUtil::List<ClientAccountManager::AccountInfoGameCharacterAndFriendsDetails,-1>`
  (vtable `017e575c`) and the derived `...,8>` instantiation (vtable `017e7c54`).
  This shard has its constructor `007199f0` (called from the `ClientAccountManager` constructor
  `0071a530`; it zeroes +4/+8/+0xc and constructs the sub-object at +0x10), destructor body
  `00719980` (unwind-funclet callers) and scalar deleting destructor `007199b0`.
* Tree index primitives of the same container, no strings and no RTTI of their own:
  `00719ac0` in-order successor, `00719b00` predecessor, `00719b40` unlink-node-replacing-with-child,
  `00719b80` / `00719bd0` left / right rotation, `00719c30` whole-tree sum of the per-node dword at
  +0x14 starting from 8, `00719c90` find-last-key-<=-search-key, `00719d20` colour fix-up.
  Node layout: key +0, parent +4, left +8, right +0xc, colour word +0x10 (bit 0 = black).
  This is the same structure already labelled `TreeRotateLeft` / `TreeRotateRight` at 009ac2b0 /
  009ac300, so these are further instantiations of one SoeUtil tree, not MSVC `std::map` code.

## How the pieces connect

`Run` drives states on the reply handlers' results; the handlers set the state through `FUN_0070c8b0`
(`-->state transition from "%s" to "%s"...`). `00719550` switches to state 5 on a list result 1/3 and
to state 7 on result 2 or an error; "success" also sets the has-characters flag `this+0x53f15` that
`Run` reads in state 0x13. The account flags land in `this+0x22280/84/88`, the same triple the
`AccountInfo_DS` datasource exposes (IsMember / MaxCharacters / IsAdminAccount, `Pieces/095`).

The cached character list is a doubly linked list: head `this+0x22290`, next `+0x62b0`, prev `+0x62b4`,
count `this+0x22298` (proved by `Run` cases 5/7/0x13 and `FUN_00715d80`/`FUN_00713fc0`).
`00719550` drains it and rebuilds it from the reply records; `00719330` and `007198b0` drain it on a
new account info / on a successful delete. Node record size in the SoeUtil pool is `0x62b8`
(`0071a1c0` allocates `n*0x62b8+0x20`, `0071a3b0` divides a pointer difference by it).

## Wire and server-contract inferences (hypotheses)

No packet opcode constant appears in any of the 15 functions, so no `wire` entry was claimed. The
pairings below depend on the missing dispatcher and are stated as hypotheses:

* `00719330` consumes (result, `isMember`, `maxCharacters`, `isAdmin`) in exactly the order the
  pinned community serializer `Sanctuary.Packet.Common/Login/AccountInfo.cs` writes them, and
  `Pieces/095` shows the client reads those three fields. Depends on `00719330` and the unknown
  dispatch site.
* `00719550` consumes (result, list of guid + name + appearance rows). The community catalogue
  describes `CharacterSelectInfoReply` (opcode 12) as status + bypass flag + entity list, and
  `Research/Native Character Selection Labels.md` records that the client logs these fields before
  copying the record - but the result enum here is `{0,1,2,3}` with 2 = "account has no characters",
  which is not proven to be opcode 12's status space.
* `007198b0` consumes (flag, 64-bit guid). The community catalogue describes `CharacterDeleteReply`
  (opcode 10) as key + `int32` status + payload. On failure the client routes the guid into a
  per-bucket table at `this+0x53eb0` and shows the web-service error with next state `0xe`.
* Nothing in this range proves which opcode reaches which slot, and `Run` itself contains no opcode
  either - it reacts to the state machine only.

## Contradictions and cautions

* Do not read `00719980` as the `ClientAccountManager` destructor: it destroys only the list member.
  The manager's teardown is `0071a8f0` + `008a6440` (shard S0149).
* `ClientAccountManager::vftable` slot 0 is a reply handler, not a deleting destructor, so the usual
  "slot [0] = scalar deleting destructor" reading would mislabel `00719330`.
* `00719b40` prefers the left child when both children are non-null in the decompiled form; at its
  only call site the node is a leaf, so the "at most one child" precondition holds in practice.

## Open questions

1. Which packets feed slots 0/1/6, and where the opcode switch lives (the missing dispatcher would
   turn the hypotheses above into `wire` evidence).
2. Is `00719330` + `00719550` one packet delivered in two callbacks, or `AccountInfo` plus
   `CharacterSelectInfoReply`?
3. What node+0x14 counts (block capacity is likely) and why `00719c30` starts its sum at 8; both
   depend on the pool code in S0149 (`0071a010`, `0071a1c0`, `0071a340`, `0071a3b0`).
4. What the `,8` versus `,-1` template argument of `SoeUtil::List` selects.
5. Subsystem choice: the whole family is filed under the existing `net.login` (login-server
   protocol layer), but the lead may prefer a distinct bucket such as `game.account`, since `Run`
   also drives UI and asset loading.
