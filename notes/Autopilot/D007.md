## Security note (secure-code-guardian)

Threat: a hostile client can send the same frames as before - movie payloads
(`39/14`), launch/connect/level/next-level frames (`39/5`, `39/6`, `39/x`), the
four-byte Results Close (`26/42`), a node click (`26/8`), blocked
job/equipment/interaction families while a movie runs, and `realm exit` /
other `realm ` chat. The merge adds no parser and trusts no client quantity.
`apply_type8` still takes its reward only from the engine's server-owned
`Type8Transaction` built from the configured outputs and server quota; forged
`FRServer_ScoreSet` / `FRServer_GameWon` / `FRServer_GameOver` strings remain
inert (type8 gateway suites assert this). The job check, material consumption,
grant, resource quest events, minigame-win event, job XP and node payment keep
their order; a refusal returns `Err` before any mutation and the gateway keeps
its pre-frame snapshot. No save format, id allocator or persisted field
changed. The node path still stages `Gameplay` on a clone and assigns it only
after the apply succeeds.

## Canary

Requested canary: swapped the two `reward_grant` arms in the merged match
(Mining called `harvesting::lifecycle::reward_grant(..., HARVESTING_GAME_ID, 0)`,
Harvesting called `mining::lifecycle::reward_grant(..., 0)`) with the exact
bytes backed up. Result: **all four named suites stayed green** -
`type8_gateway` 10/0, `type8_harvesting_gateway` 11/0, `gathering_payout` 8/0,
`gathering_nodes` 8/0. Reason: for gameplay's uses the two grants are
observationally identical. Both map `transaction.grants` to the same item rows;
both per-win XP constants are 25 (`mining_lifecycle.rs:22`,
`harvesting_lifecycle.rs:17`); the only remaining difference, `RewardDisplay`
and the XP map key, is discarded because `apply_type8` / `grant_reward` /
`award_job_xp` use only `grant.items`, `grant.job_xp.values()` and the active
profile. The ignored W104 hooks use fake transactions with the same rows, so
they would not see it either. The literal swap is therefore a semantic no-op
and cannot be a failing canary under today's content and constants.

Canary that does break production: changed the merged profile check from
`Some(gather.job())` to `Some(Gather::Mining.job())`. `cargo test --test
gathering_nodes` failed (7 passed, 1 failed, cargo exit 101):
`an_ordinary_player_gathers_from_a_node_is_paid_once_and_the_node_grows_back`
panicked at `tests/gathering_nodes.rs:702` with
`assertion left == right failed: Mushrooms paid` (the Chef case no longer paid).
Restoring the exact backup bytes made the same suite pass 8/0. The canary broke
production code, not the test; the final diff contains no canary change.
