## Packet flow across the shard

- **00ba5eb0 -> registration:** flag zero hides race HUD, stops sounds, drains transient race lists, and resets state. A nonzero transition creates race sound emitters and sends the register-player request. The corrected Research/Kart Entry Register Prerequisites.md explicitly rejects the earlier interpretation that zoning with flag zero registers; the activity-state path passes nonzero.
- **00ba6300 -> countdown:** a pending timer at +0x1b8 counts down while +0x1c2 is set. On expiry the client updates Countdown:SetCount, clears the pending flag, and submits the local racer id plus the countdown value. Research/Kart Race Service.md records the captured client echo path; this does not identify what the original server did with it.
- **00ba6530 -> state/results:** the processor switches on race state at racer+0x1624, updates UI/camera and submits player-state messages on transitions. During running states it calls 00ba48a0. Its screen trigger uses lap-limit <= completed laps; Research/Kart Native Progress Codec.md distinguishes this from the results-row predicate.
- **00ba48a0 -> per-frame client claims:** the code constructs 33/7 gate-hit, 33/17 pickup-hit, and 33/8 vehicle-hit packets from local racer/vehicle state and submits them. It also submits 33/6 vehicle data and constructs 33/19 use-item and 33/24 boost-award requests through callees. The existing vehicle-input note records the 33/7 and 33/17 payloads as client-reported positions, not proof of server acceptance.
- **00ba64b0 -> reset request:** constructs an empty VehicleRacePacketResetNpcsRequest and submits it only when the gateway is available.
- **00ba7460 -> 00ba7370 -> received vehicle setup:** the wrapper prepares a bounded reader and returns parse status; the reader consumes the vehicle definition, owner id, four vectors, and two tail bytes. The cited configuration note maps this to inner subtype 33/11 and relates owner ids to the 33/14 racer roster.

The exact client-side send/receive path is recovered. Any original-server behavior below remains a hypothesis because no original server code is available. An implementation that used the client gate/pickup claims to advance a route or grant an item would need to validate participant ownership, timing, route/object state, and position plausibility; the client sender alone does not reveal which checks the original server performed. A server likely answered registration and supplied racer setup/state for the 33/11 parser, but that depends on the outer 33 dispatcher and other packet handlers, not just this shard. The existing Kart Native Race Service note is a reconstruction, not evidence of the original server state machine.
