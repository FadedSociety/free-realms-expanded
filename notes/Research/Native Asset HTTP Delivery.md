# Native asset HTTP delivery

The original client's `.z` asset response is **an eight-byte game header followed by a normal zlib stream**. Bare zlib, raw DEFLATE and gzip are incorrect for this delivery path. This result is corroborated by pinned community source, the preserved native reader, and an actual public HTTP body that was reproduced byte-for-byte.

## Exact body and HTTP response

```text
offset0:  A1 B2 C3 D4        four-byte magic, big endian 0xA1B2C3D4
offset4:  decoded length    four-byte big-endian integer
offset8:  RFC1950 zlib stream (DEFLATE + Adler32, ordinary windowBits15)
```

Minimal Python construction for a verified, nonempty raw asset:

```python
body = bytes.fromhex('a1b2c3d4') + struct.pack('>I', len(raw)) + zlib.compress(raw, 6)
```

Serve the body with status200, `Content-Type: application/octet-stream`, and `Content-Length` equal to the actual body length. The observed community response has **no Content-Encoding**. Compression belongs to the game body, so HTTP middleware must not transparently decompress or add another encoding layer. Source files, generated bodies and provenance stay under the private lab. The HTTP handler should resolve only allowlisted verified catalog names, check the requested CRC against the decoded asset, and retain SHA256 provenance.

The manifest/query CRC is the decoded asset's CRC32. The row's size is the compressed response-envelope size. For the current failing `human_m_head_caucasian_08.dds.z?2961482716`, expected raw CRC is2961482716; the manifest's8996 is **not** the DDS raw length. The asset recovery agent owns obtaining and checking that missing raw texture.

## Independent evidence

1. Pinned [Sanctuary ZLib.cs](https://github.com/Open-Source-Free-Realms/Sanctuary/blob/4f028dcc274f628b65ef665fd59b184f5f3d3e3e/src/Sanctuary.Core/IO/ZLib.cs) explicitly writes the magic, big-endian input length, and a level6 zlib stream when prefixing is enabled. Its decompressor recognizes that prefix and skips eight bytes. Source is AGPL-3.0; the small verifier here implements the evidenced wire format with Python's standard library rather than importing the server implementation. Avoid blindly copying buffer-length arithmetic from the community wrapper; use the actual generated byte length.
2. Preserved native `FUN_010ebd70` (original pseudocode line2574099) requires more than eight input bytes, checks big-endian magic0xA1B2C3D4, and reads bytes4..7 as the output length. `FUN_010ebee0` (2574162) passes input+8 and length-8 into the zlib1.2.3 inflater. `FUN_010ee080` (2575309) initializes inflate with windowBits15. The native `AssetDeliveryIndirect::DecompressJob` worker `FUN_01099fd0` (2508093) calls these functions before the write job. Raw/decompiled evidence remains outside Git at `lab/reports/native-assets-functions.c` and `.json`.
3. Ordinary unauthenticated GET of [public manifest.txt.z](https://osfr.editz.dev/assets/manifest.txt.z) at2026-10-08T07:10:18Z returned200. It was saved without modification as `lab/reports/public-manifest.txt.z`; headers and verification are `public-asset-envelope-probe.json`. No browser impersonation, credentials, proxy, challenge bypass or archive download was used.

## Reproduction and review

From the project root:

```powershell
& '..\lab\tools\wiki-env\Scripts\python.exe' scripts\check-native-asset-envelope.py '..\lab\reports\public-manifest.txt.z' --expected-raw '..\lab\reports\public-manifest-decoded.txt' --expected-crc 3387611285 --self-test
& '..\lab\tools\wiki-env\Scripts\python.exe' scripts\check-native-asset-envelope.py '..\lab\reports\fairy_m_head_caucasian_01.dds.z' --expected-raw '..\lab\extracted\community-pack-check\Assets_008\fairy_m_head_caucasian_01.dds' --expected-crc 3316298551 --self-test
```

Both pass. The verifier checks bounded decoded length, raw CRC, source bytes, exact stream termination and encode/decode round-trip. Both checks reject seven invalid variants: wrong magic, wrong declared size, truncation, appended bytes, damaged zlib checksum, bare zlib, and prefixed raw DEFLATE. The checker is a standalone research utility and does not start a server or modify client files. Evidence/hashes are also recorded in `lab/reports/native-asset-envelope-verification.json`.

Research queries included `Free Realms .z asset delivery` in the local universal-modder knowledge base; web searches for `github FreeRealms asset server .z zlib`, `Free Realms .z asset decompress manifest`, `Free Realms A1B2C3D4`, and `ForgeLight zlib header`. The broad web searches were mostly unhelpful. The [pinned FR ADR Toolkit notes](https://github.com/edenfps/fr-adr-toolkit/blob/5acfdf8d6006fa6f43d1d3605f076a6be7393e72/ASSET_FORMATS.md) identify zlib but omit this outer header. The [XeNTaX Free Realms DME archive](https://github.com/XeNTaXBackup/XeNTaXBackup.github.io/blob/2c6074a1bcb085e77f527fcf620620a4ee1e76da/markdown/Free%20Realms%20DME%20format_3728.md) and [ZenHAX Clone Wars pack thread](https://www.zenhax.com/viewtopic.php@t=3621.html) were consulted; they cover model/pack formats and supply no HTTP envelope details. No forum attachments were fetched. Pinned Sanctuary source and the actual native/public-body oracles resolve the format gap.
