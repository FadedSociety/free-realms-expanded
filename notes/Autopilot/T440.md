# T440: a group member's battle start invites the others (Shared World slice 5)

the owner's party-consent rule: nobody is pulled into a run. A grouped player's Go now offers every
other eligible member the original join prompt; Accept enters the starter's World instance,
Decline (or silence) changes nothing.

## What changed

- `src/encounter_invite.rs` (new owner): strict codecs for 41/102 and 41/103 (exact lengths, accept
  byte 0 or 1) and the bounded pending table `Invites` (invitee GUID -> inviter, run instance,
  encounter id, deadline; one live row per invitee, no silent replace, capped at the session
  count, 30 s).
- `World` holds the table (`invites_mut`); `collect_empty_instances` sweeps it every step: a row
  dies on expiry, when either player is no longer placed (disconnect), or when the inviter is no
  longer in its run (run retired or left). No session-teardown code was touched.
- `bin/osfr_gateway/encounter_invites.rs`: after a committed message, `answer` for any 41/103 in it,
  then `offer` when the message started a run. Accept stages `Gateway::stage_encounter_join` on a
  clone of the member's gateway and commits it through the member's own `commit_outcome`.
- `src/gateway/encounter_join.rs`: `joinable_run`, `can_join_group_battle`, `stage_encounter_join`
  (the Go gates, then `stage_instance_transfer` into the inviter's instance, which `commit_outcome`
  binds as the member's run instance).
- `gameplay/field_battle.rs` / `encounter/field.rs`: `can_join_group_battle`, `join_group_battle`
  (Go gates without the start screen, then `begin_field_battle`), `joinable_run`.
- `gateway.rs`: label `(41,103) => "encounter_invite"` (also what lets the message reach
  `outcome.applications`), stale comment on `stage_instance_transfer`.
- Tests: codec/table units in `encounter_invite.rs`; `tests/shared_instance_invites.rs` (two real
  sockets, plus a World-level test that the sweep voids a row on inviter leaving the run, either
  player's disconnect (`leave`) and the deadline); app_fuzz seed `encounter_invite`.

## Client layouts (IDA; every address read this run)

Both packets: header = u16 family 41, u16 subtype, i32 word A, i32 word B (reader `008d6690`,
writer `00913db0`).

| packet | fields after the header | evidence |
|---|---|---|
| 41/102 in (28 bytes) | u64 `+0x18` (unused by the client, default `dword_1BE7B10`, zero), i32 `+0x20` locale string id of the encounter name, i32 `+0x24` countdown | ctor `00a9a0b0`, reader `00a9f920` -> `00a9ceb0`; dispatcher `00aa36c0` case 0x66 calls the reader with `a4 = 0`, so the client refuses trailing bytes |
| 41/103 out (21 bytes) | word A zero (ctor `008b6da0` -> `008a2fd0(0x67)`), word B `client+0xc10`, u64 `+0x18` from a virtual accessor on `client+0xc8`+84 (R: the character GUID, unverified, so ignored), accept byte `+0x20` | writer `00a97720`, field writer `0091b870` (`00913db0` header, `008fb810` u64, byte), sender `0092a600`; accept 0/1 from `00a09650` / `00a096a0` |

- `+0x20` is looked up in the client string table (`String#%d not found` otherwise) and becomes the
  `minigame` token of the `GAQEncounterInvite` pop-up (`00a88300` -> `00a0d810` -> `00a0d550`, the
  only user of the string at `0x018124a4`). The server sends the battle's `title_id` (96:
  42056, "Troll Summoner Madness!"). `+0x24` goes to `00a7d830`, which raises
  `HandlerGroupScreen:ActivateEncounterRequest(timeout, name)` (`ScriptsBase.lua:24845`: it calls
  `SetEncounterStartTimer(timeout)`); zero or less deactivates.
- `client+0xc10` (word B) is written by 41/107 (`00aa36c0` case 0x6b stores header word B into
  `*(client+3088)`), and this server sends 41/107 on every field-battle start screen
  (`encounter/field.rs` `encounter_header(107, ..)`) and in the dungeon path (`encounter.rs`). A
  real reply therefore carries the instance of the last battle start screen the client opened, NOT
  zero. An earlier draft of this note said the battle path never sends 41/107; that was wrong
  (review blocker, fixed): no reply header word is a match key. The same word is the second header
  int of 41/109 (the existing 41/109 rule: 0 or the run).
- `00a97720` also shows the client's own wording, the accept/reject chat lines, and refuses to send
  at all while the player is in a minigame (locale key `GroupEncounterMustLeaveMinigame`, string
  `0x018184c4`). A busy member therefore never answers; the server does not wait for one.
- `00a09650` / `00a096a0` use `00a97720` only when the invite item's u64 equals the zero sentinel
  (`dword_1BE65C0/C4`, also zero); otherwise they call `00a979a0` (the matchmaking reply). The
  ordinary encounter item is built with the zero u64 (`00a88300` passes `dword_1BE7AB0/B4`), so it
  takes the 41/103 path.
- `00aa2980` is NOT 41/102: it is the EncounterMatchmaking response dispatcher (vtable `0x01818850`
  region; case 9 reads a u64 plus a string id and calls `00a88330` then `00a7d830`). It shares the
  popup with 41/102 but is driven by the matchmaking-family packet. 41/129 and family 141 are not
  touched.
- The Lua handlers give Accept to `GroupScreen.ActivateEncounter()` and Decline to
  `GroupHandler:DeactivateEncounterRequest()` (`ScriptsBase.lua:25160-25167`).

## Recovered vs reconstructed

- Recovered: both layouts above; the pop-up path; the title id source.
- (R) 30 s deadline; countdown value 30 (unit unverified in the swf; the server deadline decides).
- (R) 41/102 header words carry (encounter, run) and the u64 carries the inviter: the client reads
  and ignores all three, so they only make the packet self-describing for tests.
- (R) the 41/103 u64 is the responder's own GUID. The server does not read it (the accessor is unverified and it would add no security: the responder is the session).
- (R) a busy or ineligible member (busy start gate, no combat job, level floor, unavailable
  prizes, other zone) gets no invite. A knocked-out member passes the offer and is refused on
  Accept by `begin`.
- Interim (slice 6): the joined member fights their own copy of the enemies; only the World instance
  (scene, chat, visibility) is shared.

## Threat note (secure-code-guardian)

A hostile client can send 41/103 at any time with any fields. The responder is always the session's
character. Refused or inert: no invite for that character; an expired, replayed or already-answered
invite (consumed on first answer; the reply's header words and GUID are ignored, they are client
controlled and word B is a stale instance in real play); a wrong length or accept byte 2; a reply after the party, the starter's run
or the starter's session is gone; a member who became busy or lost the combat job. Nothing in the
packet names the instance to enter: the run comes from the server-held row and is rechecked
against the starter's live run and World location. Decline and expiry never touch the party,
zone, instance, pose or save. An invitee cannot be flooded: one live invite each, 16 rows in all,
rows expire in 30 s. The starter's session never fails because of a member's full send queue.

## Checklist

1. A refusal changes nothing: Accept is staged on clones (gateway clone, gameplay clone inside
   `stage_encounter_join`) and committed by `commit_outcome`, which already rolls back on a failed
   save. Every inert reply is asserted to leave B's location, three membership views, party and
   save bytes equal and to send nothing (`assert_inert`, eleven cases). The one deliberate state
   change on a matched-but-failed Accept is that the invite is consumed (the client already closed
   its prompt); decided, not hidden.
2. Rollback covers all state: the pending table is mutated only by `offer` (after the starter's
   commit) and `answer` (consumption); a failed join leaves the gateway, gameplay and World
   untouched because they were staged. No shared cell was added.
3. Deltas, not snapshots: the join runs the real `begin` on the member's current gameplay; no old
   state is restored over live state.
4. Busy rules: both `offer` and Accept use `activity_busy()` (the `Occupation` table), so kart,
   derby, soccer, crafting, mining, housing and a running encounter block the invite and the join.
5. Every entry path gated: the member's Go gates (combat job, level floor, prizes, busy) run on
   offer and again on Accept; group membership and the starter's live run are rechecked on Accept.
   Test: the no-combat-job member gets no invite while the combat-job member does.
6. Reachable in production, tested through it: both tests drive real sockets through
   `Server::step`, the real `dispatch_message_inner` and `commit_outcome`.
7. Survives reconnect: nothing durable was added. The invite is process-lifetime by design; a
   disconnect removes a player's rows at the next step (sweep) and the party policy (disconnect
   leaves the party) is unchanged. The sweep is tested at World level (`the_world_sweep_voids_an_invite_...`); a real socket disconnect was not driven.
8. Exit paths: Accept uses the existing run exit (41/109 returns the member to their return
   location, which `begin` recorded in the member's own engine); Decline leaves them where they were.
9. Economy: no grants. The member's prizes come only from their own run's outcome.
10. Wire format: layouts cited above; byte-level unit tests pin both (offsets 12..20, 20..24,
    24..28 for 102; 12..20 and 20 for 103).
11. Unique ids: the run instance is World's allocator; the table never mints ids.
12. Others see changes: the member's transfer goes through `commit_outcome`, which fans out the
    leave/join of the registry exactly as any transfer.
13. Content end to end: the socket test uses the shipped battle 96 row and asserts the final
    outcome (B in the starter's instance with the zone 9600 scene), not a flag.
14. Values in data: the 30 s deadline and the countdown are one compiled constant
    (`TTL_MS`), not content data. Unsettled: a tunable would need an `Options` field (every test's
    `Options` literal would change) or a content file; left for the lead.
15. Canaries: break `Invites::answer` (skip the expiry or the consume-once) and both the unit tests
    and the socket test fail (see Gates run); reverted.
16. Session plumbing: `end_session`, session creation and transactions are untouched. The hub
    call is one line after the existing post-commit block; `commit_outcome` is called as
    `admin_move` calls it.
17. One player's error never stops the server: `offer` ignores a member's queue error; `answer`
    returns `Err` only from the member's own `commit_outcome`, which already ends only that
    session. Malformed replies are dropped by the strict decoder.
18. Type rules on the type: `Pending` / `Reply` carry the rule in their doc comments (which words
    are matched when zero); `Invites::answer` is the single place that decides a match.
19. Hot paths: see Structure (cost).

## Open gaps

- Review blocker fixed (word B): the reply's header words and u64 are no longer match keys. The
  run comes from the server-held row and is rechecked against the inviter's live run; the socket
  test accepts with a stale word B, a wrong word A and another GUID and still enters A's run.
  "A leaves the run, then B accepts" is inert at socket level; the World sweep voids the row at the
  next step and `answer` rechecks the inviter's live run as a second guard (the socket test cannot
  isolate the recheck from the sweep).
- Brief divergence, justified: the brief lists a reply with a wrong run or foreign GUID as inert. The code treats such a
  reply as a plain Accept or Decline of the one server-held invite. IDA: writer `00a97720` sends `*(client+3088)` as word
  B, and 41/107 (`00aa36c0` case 0x6B) fills it with the last battle instance, so word B is stale in real play and the
  reply fields cannot be match keys. Safety rests on the session-derived responder plus the rechecks above.
- Unsettled: a battle with `title_id <= 0` would show no name in the client (guard `v56 > 0`). `answer` does not run
  `sync_tracked_target` or the achievement settle that the ordinary Go path runs.
- Unchanged, lead's call: the 30 s TTL is a compiled constant (an `Options` field like
  `group_invite_ttl_ms` would match other invite windows); a matched Accept that then fails a gate
  burns the invite silently; `answer` does not recheck that the invitee is still in the offer's zone
  (`begin` records the return location, so it is not a hole).
- Native (lead): B sees the original prompt, Decline keeps party, HUD and location, Accept loads B
  into A's scene. Not run; run it with a B that has already opened a battle start screen (stale word B).
- `shared_world_membership.rs:475`'s forged 13-byte 41/103 was not run here: that file writes its
  scratch saves under `lab/reports/`, outside this worktree. The same bytes are asserted inert in
  `shared_instance_invites.rs` ("short"), and the label change cannot turn a bare accept into a join
