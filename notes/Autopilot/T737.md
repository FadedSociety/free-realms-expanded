# T737 - Enemy health fitted to the gameplay video's hits-to-kill

2026-10-26. Lead's evidence: `lab/references/quest-lines/enemy-hp-video.{json,md}`,
per-frame readings in `lab/fleet/out/hp-frame/`, frames in
`lab/video-archive/out/<video>/frames/<second>.jpg`.

## What changed

- `data/content/enemies.json`: nine observed rows gain the content-band `level`
  their video fight was filmed at, and Queen Verda's authored `max_health` drops
  540 -> 260 (fitted, see below). Ten rows gain a `(R) T737` sentence in `source`
  citing the video id, seconds and the effective health/hit arithmetic.
- `src/encounter.rs` (hub, net +6 lines, 2972 -> 2978, ceiling 2997): the world
  and dungeon load now passes `scale.health_factor(a.level)` to `scale_enemy`
  instead of `1.0`. Before, an enemy row's `level` was ignored at that load
  point, so a level-20 dungeon row died in one tier-5 hit; field enemies already
  scaled with level (`field_content.rs:161`). Enemy *damage* stays as authored
  (no video measures it). `Actor.level`'s rule is documented on the field.
- `tests/common/field_enemy_fixture.rs` (shared): `with_world_enemies(rows)`,
  `scale(edit)` and `load_encounters()`; `load()` now calls `load_encounters()`
  (3-line refactor). No re-declared helper in the new suite.
- `tests/enemy_health_video.rs` (new): the ten observed rows are read from the
  shipped `enemies.json` and put in `encounters.json` as world enemies, loaded by
  the real `EncounterEngine::load`, then killed with real `attack` swings at the
  video's player level/job. Also: data reload moves the fight; out-of-bounds
  `enemy_health_scale` refuses the load.
- No new application family/subtype, so no `app_fuzz` seed was needed.

No `combat_scale.json` value changed. 3.72 already fits once the level applies:
a level-20 180-health row gives 180 x 14.27 x 3.72 = 9,555 effective health, and
a level-20 Ninja basic is 2,382, i.e. four to five video-range hits. The value
and the bound (0.01..=100) are the existing data knob the tunability test moves.

## (R) rules

  authored health with the player health curve, exactly like a field enemy.
  Evidence: the high-band fights are level-20 players in difficulty-5 (or
  difficulty-4) dungeons, and the video health (5k-33k for 180-1,020 authored
  rows) only falls out of the curve at level 16-20. The loader ignored the level
  before, which is why every high-band row died in 1-2 hits.

## Video evidence caveats (read this before trusting a level)

- The `levels_read` values in `enemy-hp-video.json` are not reliable enemy
  levels. The `5` seen in the level-20 frames is the **membership badge** (yellow
  five-point star beside the player portrait, e.g. `OawnLys6j-o/00402.jpg`,
  `BJy3sgpdqpw/00084.jpg`), not the target's level. The dungeon difficulty 5
  comes from `data/content/dungeons/*.json` (`"difficulty": 5`) and matches the
  video's dungeon banners ("Cray Coven", "Dark Spore D..."). Only the Cray
  Marauder (3) and Nettleseed Pest (14) target-badge reads look like target
  levels; both are used as ranges, not pins.
- The Elder Mugwort window's floating numbers are over a Warthog Thugger in
  `OawnLys6j-o/00402.jpg` while the boss bar is Mugwort's; the 17,729 estimate is
  therefore a range, not a health reading. The same frame shows the membership
  badge wrongly read as level 5.
- Frame spacing is two seconds: hits are missed (sums run low) and one rising
  number can span two frames (counted once). Group fights (Foreman Ironfist has
  two attackers, FiWCkh0St38 has two) are noisier; the ranges are widened.

## Security note (secure-code-guardian)

- Client input never reaches the changed code. `Actor.level` and
  `max_health` come from server-authored JSON at load; no packet field, no
  player-chosen row, no level in any client message. A hostile client cannot
  pick an enemy row or make it tougher/weaker.
- Hostile *content* is bounded: `validate_actor` caps authored `max_health` at
  1..=100,000, `health_factor` clamps the level to 1..=20 even if a row carried a
  wild value, and `CombatScale::load` refuses `enemy_health_scale` outside
  0.01..=100 (tested in the new suite and in the existing
  `an_invalid_scale_file_refuses_the_load`). Worst in-bounds effective health is
  ~1.4e8, inside u32; the load still succeeds, but that is a content-file
  problem, not client-triggered.
- No reward, coin, item, role, save or chat path is touched. A longer enemy
  fight grants nothing extra; rewards still come only from the server-side
  defeat path. Shared-field enemies (the only rows other players see) are
  unchanged: they were already level-scaled, and the encounter loader change
  touches per-session world/dungeon content only.
- Saves: `restore_enemies` keeps a saved enemy's absolute health and clamps it to
  the loaded max (`tests/combat_scale.rs::saved_enemy_health_survives_a_scale_retune_in_both_directions`),
  so a retune never restores an old full-health snapshot over live damage.

## Checklist (re-read against the diff)

1. Refusal changes nothing: no client request path is added; the only refusals
   are content-load refusals, which return `Err` before an engine exists. The
   out-of-bounds test asserts the load refuses; no live state exists to change.
2. Rollback: no transaction. The loader builds or rejects a whole engine; the
   hot-reload path (`Gameplay::reload_content`) already stages on a clone and is
   not touched.
3. Apply deltas: no payout/exit. Enemy health is recomputed at load; saved health
   is preserved and only clamped to the new max, never replaced by a snapshot.
4. Busy rules: no new activity. N/A.
5. Every entry path gated: the only path to enemy health is
   `EncounterEngine::load`; the test uses it. No parallel loader.
6. Reachable in production, tested through it: `EncounterEngine::load` +
   `EncounterEngine::attack` are the production path; the fixture puts shipped
   rows into a real `encounters.json`. Gap: the ten rows are not placed in live
   content (noted above).
7. Survives reconnect: no new persisted state; saved enemy health is already
   clamped at load and the existing retune test covers both directions.
8. Every exit path: no session/exit change; enemy health has no exit state.
9. Economy safety: no rewards/items/coins touched; a longer fight cannot create
   a grant, and all kills still go through the server defeat path.
10. Wire format: no packet or field change. The `35/5` enemy HP packet already
    carries current/max; the loader only changes max.
11. Unique ids: fixture GUIDs are 9_000_000_001+ and distinct from field GUIDs;
    shipped GUIDs untouched.
12. Others see changes: shared-field actors are unchanged (already level-scaled);
    world/dungeon enemies are per-session. No broadcast path touched.
13. Content works end to end: the test asserts the final outcome (health 0 after
    N production swings, every swing `changed`), not an intermediate flag.
14. Values live in data: levels and Queen Verda's health are JSON; the curve and
    enemy scale are in `combat_scale.json` with existing bounds.
15. Canaries break production code: the canary reverted the production call, not
    the test; 2 tests failed, then the revert made them pass.
16. Hands off session plumbing: no `src/bin/osfr-gateway.rs` / `gateway.rs`
    session, teardown or save-order changes.
17. One player's error never stops the server: no tick or shared-tick code
    changed; all new work is at load and returns `Err`.
18. A type's rules live on the type: `Actor.level` now has a doc comment stating
    that both the field and world/dungeon loaders scale health by it and only the
    field loader scales damage; the loader call site repeats the rule.
19. Hot paths stay cheap: the change is load-time only (a `powf` per actor,
    <= 48 world/dungeon actors and unchanged field cost), zero per-tick or
    per-packet work.
