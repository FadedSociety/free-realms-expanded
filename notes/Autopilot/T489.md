# T489 - Pet tricks: 53/7 perform, 53/8 gesture report, 53/14 favourites, 53/15 and 53/20 kinds 5 and 6 (Opus lane, 2026-10-27)

Built on T488 (`27c64f17`, pet grooming and petting) and T772. Skills applied: ponytail (full, incl. the review pass on the diff),
secure-code-guardian (threat note below).

## Client evidence (checked in IDA this pass)

- 53/7 writer `00b5ff50` (ctor `00b50a10`, subtype 7) and 53/8 writer `00b5ffe0` (ctor `00b50c20`, subtype 8): one u32 after the
  header, the trick id (serializers `00b5a590`, `00b5a5f0`). `00b5ffe0` also writes the pet handler's state word `+0x12ac` = 4.
- `Pet.PerformTrick` `00c06890` -> `DispatchPetActionRecord` `00b5fb30`: the id must be positive, the active pet needs a row with
  the enabled byte, a row whose type dword is 2 goes to the toy path, any other to `UnlockPetTricksAfterGesture` `00cc7420`.
  `00cc7420` sends 53/7 and then 53/8 with the same id back to back; when the owner is in water or flagged busy it fires the
  local `PetsHandler:UnlockTricks` and sends nothing. So a refusal answer is a server choice.
  `FinishPetGestureState` `00cc9a90` sends 53/8 when the drawing round ends (or only fires the local unlock when no trick is
  selected). The grade is not in either body.
- 53/15 reader `00b55ab0`: five u32 at +0xc..+0x1c (pet id, kind, trick id, text id, value). Handler `00b5ce60` case 15
  (`0x00b5e68b`): the kind (second word) switches at `0x00b5e6b5`. Kind 1 (`0x00b5e7cc`) builds `PetOrderDoTrick` with `trickName`
  = the text of the **fourth word** and posts it as `WorldSay`; kind 2 (`0x00b5e6f0`) fires `PetsHandler:TrickSuccessResult` with
  the text of the fourth word and the **fifth word** as a number; kind 3 calls `00b59070` (`PetsHandler:UnlockTricks`, zeroes
  `+0x12b8`). The first and third words are not read by this case (the handler takes the pet from `+0x84`). `ScriptsBase.lua`
  has no `TrickSuccessResult` function (nor `SetFavoritePetTrick`), so kind 2 is inert in the shipped Lua.
- Result strings: `PetTrickGestureSettings.txt` RESULT_BAD 90155, OK 90157, GOOD 90161, GREAT 90163. The locale
  (`locale-id-to-text.json`) has 90155 "Poor" and 90163 "Amazing!!" only.
- 53/20 `00b5ce60` -> `00b58220`: the packet's pet id must be a pet in the client's list (lookup `009f8d30` at `0x00b5ebed`),
  else the notify is ignored. Kind 5 (`0x00b5ecef`) is `00b53710(1)` only (marks the pet actor, no event); kind 6 `00b56a00`
  clears the mark and the state word and fires `PetsHandler:UnlockUtilities` (T488 evidence). Kind 3 of 53/15 does **not** clear
  `+0x12ac`, so the 53/20 kind 6 is what returns the state word from 4 to 0 (T488's strokes send that word as `mode`).
- 53/14: writer `00b5f670` (ctor `00b51290`) refuses a UI slot outside 1..4 and sends active pet id, slot - 1, trick. The inbound
  case 14 (`0x00b5e595`..`0x00b5e5ce`) does `cmp slot, 4; jg skip` (signed) and stores the trick at pet record `+0x88 + 4*slot`:
  slot 4 would write `+0x98`, the first utility slot, and negative slots write before the array. The server stores and echoes
  only 0..=3. The UI only changes from the echo (the event fires from the inbound handler), so a refusal sends nothing.
- Animations: `Pets.json` TrickAnimations (OSFR reference, commit `10f129e7`, sha256 `06b120e3...`) hold 287 rows for the 65 models
  that have tricks. `scripts/pets_import.py` now checks each row against the client: the pet and owner animation ids must be
  `AnimationTypes.xml` slots (e.g. 5004 `pet_trick_01_level4`) and the model's ADR must declare the pet slot's name (the pattern
  `piece_098::scan_animation_slots` reads). 287 of 287 pass, none dropped; every ADR was in the lab, so no row is marked (R)
  for a missing ADR. Brief said 65 models: correct (the fleet pack's "20 blocks" was a capped search).

## Behaviour

- 53/7 accepts when: `care.trick` exists; a pet is summoned; the owner is not in water and not busy (`Gameplay::blocks(pets)` via
  `PetBusy`); no feed, groom or trick runs; the pet's model has an animation row for the trick; the pet is not vanity (R); the pet
  knows the trick. Then, in order, to the owner: 53/15 kind 1 (the trick's `name_id`), 53/20 kind 5, the owner animation (35/8
  through `piece_052::animation_packet`, also to viewers). `PetWire.accepted_trick = Some(id)` at this moment (T788 hooks it in
  `handle_pets`; nothing else sets it). Nothing is saved or granted.
- World tick (`care_tick` -> `trick_tick`): at `start_delay_ms` the pet animation (owner and viewers); when the pet animation
  has run `duration_ms` (so the end is delay + run, as OSFR times it (R)) 53/15 kind 2 (text 90163, value 0), 53/15 kind 3 and
  53/20 kind 6. A late tick sends the animation first, then the end, once.
- Every refusal answers only 53/15 kind 3 and 53/20 kind 6 (naming pet 0 when no pet is out) and changes nothing. A feed or
  groom started while a trick runs is refused with their kind 6, and a trick while they run.
- 53/8: ignored unless it names the running trick **and** the pet animation has begun (R: `00cc7420` sends it right behind
  53/7, and ending there would cut every trick off before its animation); then it ends the trick at once with the same end
  packets. For the trick that ended within `gesture_grace_ms` (20 s: the drawing round force-ends 20 s after it starts, R) it
  answers kind 3 and kind 6 again, because the client sets its state word to 4 on every 53/8 and only a 53/20 kind 2, 4 or 6
  clears it. Everything else (other trick, no trick, past the window) is dropped silently. It never rewards.
- Dismiss, a replacing summon and zoning (`care_end_packets`) send the two unlocks, entering water sends them and marks no
  save; a disconnect drops the session (it lives in `ActivePet`, which every summon replaces, so no timer outlives its pet).
- 53/14: the pet must be owned, slot 0..=3, the trick known. It persists and echoes `53/14 (pet, slot, trick)`. A trick the model
  row lists as known is added to `learned_tricks` as it is chosen, so the roster rule "a favourite is a learned trick" holds
  for old saves. Any refusal sends nothing.

## Threat note (secure-code-guardian)

A hostile client can: send 53/7 for any id (an id with no row, an unknown, vanity or foreign trick is refused with two small
packets and no state change); flood 53/7 (one session at a time; each refused call costs one `Arc` clone and early returns, the
same as feed refusals; an accepted trick pays nothing, so a flood only repeats animations at most once per delay + run time of
at least a second); send 53/8 for another trick, before the animation, with no session or after the grace window (dropped with
no answer); send 53/8 for the running trick after its animation began (the trick ends early, which is the only effect, and
rewards nothing); repeat 53/8 inside the 20 s window after an end (two small packets each, no state); send 53/14 with a slot of
4 or more, signed-negative slots, a pet it does not own, trick 0 or a trick the pet does not know (dropped silently, nothing
stored; slot 4 would have reached the client's first utility slot through the echo). The pet id is never taken from 53/7 or
53/8; the actor and owner guids come from the session. Times are the server's own clock, added with saturating arithmetic and
bounded by 30 s rows validated at load. Nothing is granted, so there is no economy surface.

## Checklist

1. A refusal changes nothing: `try_trick` returns `None` before any write (the one assignment follows every check); the refusal
   only builds two packets. Tests assert roster and bag equality for every refusal cause and that the tick never sends anything
   afterwards; a refused favourite returns before the roster is touched (roster equality asserted for eight causes).
2. Rollback covers all state: the session is one field of `ActivePet`, written once at acceptance; nothing else is staged.
3. Deltas: nothing is restored from a snapshot; the only roster write is the favourite (and the idempotent learned insert).
4. Busy rules are mutual: a trick refuses while a feed, groom or trick runs and while busy or in water; feed and groom refuse
   while a trick runs (one `ActivePet::interacting`, tested both ways). No new `Occupation`: the shared `blocks(pets)` is the gate.
5. Entry paths: 53/7, 53/8, 53/14 arrive only through `Gameplay::handle_pets` -> `handle_at_ms`; the tick only through
   `care_tick`; the old `handle` (no clock) refuses the three requests. Zoning, dismiss, summon and water all go through
   `care_end_packets` / `stop_trick`.
6. Reachable and tested through production: `tests/pet_tricks.rs` drives `handle_at_ms`, `care_tick` and, in one test, the real
   `Gameplay::handle_in_world`, `pet_tick` and `settle_pets` (replies and `nearby`). The pet label comes from `DECODED_SUBTYPES`;
   `app_fuzz` seeds cover 7, 8 and 14.
7. Survives reconnect: nothing of the session is saved by design; the favourite is in the roster (reload tested); a reload
   mid-trick has no session, no unlock to send and no stale timer (tested).
8. Every exit restores: end by time, early 53/8, dismiss, replacing summon, zoning and water each send the unlocks; a refusal sends
   them at once; a disconnect drops the state. No path leaves the panel locked (the unlocks are 53/15 kind 3 and 53/20 kind 6).
9. Economy: no coin, item or XP is touched; a 53/8 cannot reward; the client grade is not read; Pet Trainer XP is not built.
10. Wire matches the client reader: 53/7 `00b5ff50`/`00b50a10`, 53/8 `00b5ffe0`/`00b50c20`, 53/14 `00b5f670`/`00b51290`/`00b55a20`,
    53/15 `00b55ab0` (case 15 of `00b5ce60`), 53/20 kinds 5 and 6; byte-level asserts in `trick_requests_decode_with_exact_lengths`
    and the sequence test (every packet compared as words).
11. Unique ids: none added; animations target the owner guid and the existing pet actor guid.
12. Others see changes: the owner animation (at acceptance) and the pet animation (on the tick) go to `shared`, which
    `pet_outcome` / `pet_tick` forward as `nearby`; asserted through `Gameplay`. The care packets stay owner-only.
13. End to end: a dog's trick runs name line, lock, both animations, result and unlocks (asserted as the exact packet list),
    and the pet can perform again afterwards.
14. Values in data: `care.trick` (grace, result text, value) and the per-model rows (ids, run time, delay); only the 30 s sanity
    bound and the client's kinds are code.
15. Canaries break production code: see the list above; each was reverted and the suite re-run.
16. Session plumbing: untouched (no change to `gateway.rs`, `bin/osfr-gateway.rs`, saves or teardown).
17. Tick safety: `trick_tick` returns nothing and never errors; all times use `saturating_add`/`saturating_sub`; a clock at
    `u64::MAX` and a backwards clock are tested.
18. Type rules: `TrickState` documents what is session only; `animations_valid` is on `PetModel`, `valid` on `TrickConfig`;
    `ActivePet::interacting` is the one definition of "a care action is running".
19. Hot path: the tick adds a copy of the small `ActivePet` and a match when idle (no allocation); a 53/7, 53/8 or 53/14 costs one
    `Arc` clone and a scan of at most 165 models and 16 rows.

## Open (R) and gaps

- All `care.trick` numbers are (R); the animation run times and delays come from the OSFR reference, not a client table. The end
  at delay + run, the 53/8 early end, the 20 s grace and the kind 2 text (90163, value 0, inert today) are first choices, tunable.
- A stray 53/8 that matches no recent trick is dropped, so a client whose 53/7 was refused and which then sends a late 53/8
  could keep its state word at 4 until the next 53/20 kind 2, 4 or 6. Not seen in the client flow (a refusal's kind 3 resets
  the round), noted for the native check.

  toy-action rows (53/33) are not in this task.
- Not driven by a real client. Native check: summon a dog, press a trick (no drawing) and watch the owner then the pet animation,
