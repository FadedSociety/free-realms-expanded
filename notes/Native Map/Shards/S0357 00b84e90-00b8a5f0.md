## Clusters in this range

**ProjectileManager (00b84e90).** One large virtual method, `ProjectileManager::vftable[1]`.
It averages target positions from two possible sources (an explicit list on the
update context, or the list object at `this+0x1ac`), divides the accumulated
vector by the entry count with SSE `divps`, applies the gravity scale
`DAT_017ea718` times a scalar from `FUN_008b3180`, stores the result as the
projectile velocity at `param_3+0x50..0x5c` relative to its position at
`+0x60..0x6c`, and builds a 0x140-byte per-tick object that is handed to the
owner's vtable (slot 4 of the object at owner+0x54) and then freed. Whether that
object is a wire message or a local effect record is unresolved.

**Leaderboard (00b856f0..00b86880).** The in-game leaderboard is the web fetch
described in note 019, not a game packet: `00b85d50` loads
WebResources/GameLeaderBoardUrl into a 512-byte buffer and creates the request
object; `00b85e80` logs and throttles the request (1000 ms, `RequestLeaderBoard,
sending: %s`); `00b86880` (`ClientLeaderBoardManager::OnGetResult`) appends a NUL
to the collected bytes, parses them into a DOM, finds the `result` node and calls
`00b86720`, which reads `totalPages` into response+0x1c and loops `entry` nodes
through `00b86390`/`00b86300`.

The response wrapper (`00b864d0` ctor, `00b86540` dtor) owns a
`SoeUtil::Array<LeaderBoardResponse::EntryLine,0,1>` member at +0xc (vtable
01823ad4; data +0x10, count +0x14, capacity +0x18). The 0x70-byte entry layout is
proved by the ctor 00b85ce0 (StringFixed64 at +8; scalars at +0x5c/0x60/0x64/0x68;
8-byte key at +0/+4 with defaults DAT_01be9ef8/efc), the copy ctor 00b86040 and
the accessors 00b856f0/00b85710/00b85730/00b85750/00b85770/00b857c0.

Attribute-to-offset mapping from 00b86390 (`guid` -> +0, `rank` -> +0x60,
`id` -> +0x5c, `score` -> +0x68, `type` -> +0x64; the attribute-name pointers are
01823b4c (guid), 0181da90 (rank), 017eda64 (id), 017eda5c (name),
017ee664 (type) and the literal 01823b44 "score", all verified in .rdata). The UI column switch at
00cded50 (LeaderBoardEntryDataSource::vftable[4], outside this shard) consumes
these getters; its column order (rank, name, guid, score, id, type) matches the
HighScoreItem property order recorded in note 019, but the mapping is an
inference, not a proven contract.

**Vehicle / garage (00b86a80..00b87b50).** `GarageManager` (ctor 00b86d40,
deleting dtor 00b86ff0, Start 00b877d0 with the `VehicleGarage:Start` script
event, Stop 00b86da0). Four request packets are built and sent:
`VehiclePartPacketRequestVehicleConfig` (base ctor arg 1, ctor 00b86a80, sender
00b87310), `...EquipmentArrayUpdate` (arg 3, ctor 00b86b30, sender 00b87420),
`...SelectVehicle` (arg 5, ctor 00b86be0, sender 00b87530) and
`...RemovePartFromSlot` (arg 6, ctor 00b86c90, sender 00b87640). All four senders
share one envelope: serializer `FUN_008d4a40(0x10000000)`, payload writers
00b87080/00b87130/00b87190/00b87230, `ClientGateway::PacketTunneledClientPacket`
construction (0089adc0) and send (00925640). The opcode constants exist only in
the constructors; the senders carry no opcode constant, so their records cite the
tunneled client packet class instead.

Trigger paths: 00b877d0 (garage start, requests opcode 1), 00b87970 (equipment
array push, opcode 3), 00b87a30 (select vehicle then a fresh config request,
opcode 5; also writes player+0x47c/+0x480 for selector 1/2), 00b87b50 (remove
part, opcode 6). The `+0x280` field on the object at garage+0x10 gates the actual
send, i.e. the same manager code runs headless without a connection.

**Mannequins (00b87d70..00b885c0).** `MannequinManager` derives from

## Cross-function wire and server inferences

- The reward family is receive-only in this client: the dispatcher 00b8a640
  builds a packet per subtype and calls the entry points above. Any server-source
  reasoning therefore describes what the original server must have sent, not
  what the client sends.
- Subtype 6 accumulates: the note records the handler adding the two delta words
  to caches at +0x3c/+0x40, and the reader fields (+0x1c, +0x20, +0x24) are the
  three words it reads. The first word of each deferred row (00b88a70) and the
  first word of subtype 6 remain unresolved in this shard as in the note.
- Subtype 7 is panel-driven: granted coins (+0x1c) plus a row list whose second
  word is summed; the client never computes the amounts itself.
- The vehicle requests (opcodes 1/3/5/6) are client-to-server and gated by a live
  connection; the opcode bytes are only provable from the constructors, so any
  server reconstruction must pair ctor opcode + tunneled envelope (PacketTunneledClientPacket).
- The leaderboard is an HTTP fetch controlled by client configuration, so it
  needs no server packet, matching note 019.

## Contradictions and corrections against existing notes

- No contradictions found with note 019 or the reward notes; addresses the notes
  cite (00b85d50, 00b88a70, 00b88ad0, 00b89190, 00b892b0, 00b89340, 00b894a0,
  00b899f0, 00b89ca0, 00b85f-range) behaved as described.
- New detail: the note lists only four handled subtypes; this shard additionally
  shows the subtype-0 constructor 00b88ad0 and the shared ctor-with-subtype
  00b88b40, i.e. the subtype byte is written by the client object itself, so an
  unknown subtype cannot be distinguished from subtype 0 by construction alone.
- The 0x140-byte object in ProjectileManager::Update (00b84e90) is not claimed to
  be a packet; earlier notes do not cover this function, so no conflict exists,
  but reviewers should not read a wire role into it.
