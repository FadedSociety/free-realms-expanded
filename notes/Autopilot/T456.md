# T456 - Pet Browser record: real icon, name text, image, tint, tricks and item classes (lead build, 2026-10-26)

Lead build on T455 (`3ec70963`), which sits on T454; this patch is only the record work.

## Client order (decompiled this pass)

`00912cf0` (record reader) consumes, with the record offset each field lands at: u32 id (+0x00), u8 sex (+0x04),
u32 icon (+0x08), four 4-byte needs (+0x20, +0x24, +0x28, +0x2c), u8 members-only (+0x30), the trick list
(`008fcdb0` -> +0x34: i32 count, then per row a u32 key and the element read by `008ce1a0`: eight u32 and a u8 known
flag), the equipped id list (`008db130` -> +0xbc), the item-class list (`008fc8c0` -> +0xe4), the name string (+0x0c),
u32 (+0x1c), u32 tint (+0x100), a string (+0x108), u32 image set (+0xfc), u8 vanity (+0x104), u32 attachment group
(+0x118), u8 tutorial (+0x11c), then 4 u32 favourites (+0x88) and 8 u32 utilities (+0x98). The brief's three open
points: (a) +0x1c is written as the adoption item's name text id; (b) the +0x108 string (resolved by `sub_7961D0`) is
written as the model's default tint alias (R); (c) +0x04 is filled from the model's Models.txt GENDER value (R).
The eight trick u32 are written in the Pets.json row order [id, icon, name id, skill level, unknown5 (the toy flag),
unknown6, tooltip id, order], the order OSFR's natively accepted serializer uses; the order word is the row's
position in the model list (the rows are stored in Unknown8 order) (R).

## What changed

- `src/pets.rs`: `append_pet_record` writes that order from the T454 catalogue: the model's icon, the item's
  members-only flag, the model's trick rows (known when the data says so or the pet learned it) followed by any
  learned trick the model list lacks (old saves keep their tricks visible), the model's item-class rows, the item's
  name text id, the pet's tint (else the model default, else the species icon tint), the model's tint alias, the
  item's image set (else the species icon), the model's vanity flag, attachment group 0 and tutorial 0 (R).
- `Pet` gains `#[serde(default)] tint: Option<i32>`: a pet adopted from a tinted item (53/32) keeps that tint; old
  saves load unchanged (test).
- An accepted rename's 53/10 also goes to viewers (`PetWire.shared`); a rejection stays private.
- A plain 53/4 summon ends the owner's replies with 53/9 then 53/5 (the actor still comes first).
- `tests/support/pet_inventory.rs`: `with_tinted_items` (the shared fixture gains the tint column).
- `tests/pet_routing.rs`: its list decoder is retargeted to the corrected record (the +0x04/+0x30 bytes, item-class
  rows, the tint alias string, +0x08 is the icon not the species id, the known flag per trick row) and the summon
  test to the 53/9-then-53/5 tail. These pinned the old placeholder bytes the brief replaces.

tinted pet shows its tint, vanity pets read as vanity, and renaming a pet updates its nameplate for a second client.

## Checklist

1. A refusal changes nothing: a rejected rename sends only the private 53/10 refusal and the roster; the 53/32
   refusal path is unchanged; the record writer is read-only.
2. Rollback: the tint is written to the adopted pet only after the staged 53/32 adoption committed.
3. Deltas: no snapshots are restored; the tint is set once (`None` -> the item's tint).
4. Busy: unchanged (summon and adoption keep the existing `PetBusy` gate).
5. Entry paths: the record is built by `list_packet` for every sender (world entry, summon, adoption, rename).
6. Real path: tests drive `handle_with_inventory` (53/32) and `handle` (53/4, 53/6), the calls gameplay makes,
   and decode with a reader written from the client's `00912cf0`.
7. Reconnect: `Pet.tint` is `#[serde(default)]` in the saved roster; an old roster without it loads and lists.
8. Exits: no new activity; nothing to restore.
9. Economy: presentation only; no grants.
10. Wire: every record field cites `00912cf0`/`008ce1a0` with its offset; tests decode byte by byte and assert no
    trailing bytes.
11. Ids: no new ids.
12. Others: an accepted rename's 53/10 now reaches viewers (`shared`); a rejection stays private.
13. End to end: icon, image set, name text, tint, members-only, vanity, named tricks and item classes come from
    shipped data and are asserted against pets.json and the locale table.
14. Data: every value comes from `pets.json` (T454 catalogue); no new code constants.
15. Canary: writing the species id back at +0x08 (production writer) fails the Char test.
16. Session plumbing: untouched.
17. Tick safety: not on a tick.
18. Type rules: the record layout lives in one writer, `append_pet_record`.
19. Hot path: the record is built only when a roster is sent, not per tick.

(R) choices are named above (sex, tint alias, trick order word, attachment group, tutorial).
