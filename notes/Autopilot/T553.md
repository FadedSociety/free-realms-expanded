## Verify-first answers

1. **Terrain binding (IDA): option (a).** The ProxiedCharacter initialiser `sub_968C80` takes the terrain
   object id (`this+521`, the field the admin overlay prints as 'TerrainObjectId: %u' at `0x0180329c`,
   `sub_8DE1E4`) and a replace flag. With a nonzero id it looks the object up in the zone's terrain table
   (vtable +68). Found and replace 0: it copies the object's transform and makes the terrain object itself
   the character's actor (the `LABEL_29` path), building no model, so model 274 is never drawn a second
   time. Found and replace nonzero: it builds a new actor from the model at the terrain object's
   transform. Not found yet: no actor, and `ProxiedCharacter::Process` `sub_973200` retries the lookup
   every tick until the zone has loaded (log string 'could not find actor for terrain object ID %u after
   zone finished loading'). So the plots are the client's own terrain objects and a nonzero
   `terrain_object_id` with replace 0 binds to them: the plots send it (an earlier pass of this task kept
   it as content only, which would have drawn model 274 on top of the terrain plot). (R) the packet
   fields behind `sub_968C80`'s arguments (id = the dword before the `has_attachments` byte, replace = the
   byte after `model_customization`) are matched by name and by the replace branch's behaviour, not traced
   instruction by instruction (the 0x92f460 caller is not a function in the IDB). Native check pending.
2. **Board selection.** Before: `begin_gather(gather, ..)` called `engine.begin(job)` on the single
   shared engine whose game id is fixed to 111 by `HARVESTING_GAME_ID` (`gameplay.rs` load) and by
   `Type8Engine::load` (`content.game_id != game_id` refused). Now: the engine holds every game of its
   file, and a node's pool names the game; the mushrooms name none and start the file's own 111.
