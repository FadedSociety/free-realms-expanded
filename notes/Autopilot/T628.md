# T628: the flaky moderation rig and the two bot tests

Test-only change (no production code, no content, no wire format). Skills: ponytail (full), investigate-first
(evidence from the failing integrator logs before editing), test-behaviour-not-implementation. The secure-code-guardian
threat note does not apply: nothing a client can send changed.

## What was wrong (evidence)

Moderation rig (`l042_moderation.rs`): every failing log (`lab/autopilot/logs/int-batch-175531` .. `211926`) prints
`{"event":"session_ended",...,"reason":"idle_timeout"}` for the rig's sessions just before the panic, and the failing
test finished in 374 s. `Server::step` ends a session after `last_activity.elapsed() > 60 s` (`osfr-gateway.rs` ~3836).
The rig enters at `dispatch_message`, past the packet path that refreshes `last_activity`, so a loaded host that stalls a
test past 60 s idles out every rig session, and the next `send`/`drain` finds none (`expect("live session")`, `unwrap()`,
`all(live)`). Production's timeout is right; the rig has no client to keep the budget alive. T450 (4bbf0ce) already added a
refresh inside `Rig::step`; no moderation failure was logged after it. This task makes that fix the one shared helper and
covers every other rig that steps a clientless session.

Breadcrumb test (`bot_acceptance_1016`): `wait_log_outcomes` slept 50 ms per poll without servicing the bot. A bot that
only sleeps never retransmits (the file's own comment on `save_when` says so), so one lost or late request datagram
stalls the wait until its 20 s deadline: `...: no gateway event/outcome` at `:529`, four different claims over five logs.

Pet test (`pet_bots`): it waited a fixed 1.5 s for the gateway to write the first login's logout save before seeding a
pet into that save. A slower gateway writes the logout save after the seed and erases it, so the summon finds no pet and
`a.wait_for(pet actor)` times out (`pet_bots.rs:587` in `int-batch-185316`). `mount_bots` and `bot_acceptance_1016` already
wait for the gateway's `session_ended`/`client_disconnect` event (`logout`); this copy of the rig predates that.
The pet and mount rigs also lack the above-normal priority `bot_acceptance_1016` gives its gateway and login children
(its comment: 5 s handshake window), matching their `service did not print listening` and `login: no reply` failures.

## Tests and proof

- New `moderation::tests::a_stall_past_the_idle_budget_ends_no_rig_session`: backdates every session's `last_activity`
  by 61 s instead of waiting, and asserts the rig step keeps them, and that the bare production `Server::step` ends them
  (so the cause is pinned, and the production timeout stays covered).
- Canary 1: removing the refresh from `test_support::step` fails that test with `reason":"idle_timeout"` and the same
  assertion the integrator logged (`rig.live`).
- Breadcrumb test: the duplicate claim's first datagram is now dropped on purpose (`drop_next_matching`), so every run needs
  the wait to retransmit, and asserts it was dropped.
- Canary 2: putting the sleep back in `wait_log_outcomes` fails the test with `the duplicate client objective: no gateway
  event/outcome`, the exact message of `int-batch-195742`.
- Loaded runs (no artificial load: the three loops ran at once beside cargo builds and the other builders, each test
  binary copied out of the build dir): `moderation` x20 (8 tests each, 105-126 s per run) 20/20 green; `pet_bots`
  `a_saved_pet...` x20 green; `client_objective_breadcrumb...` x20 green with the dropped datagram (x20 more before
  it was added). Also green: `admin_move`, `isolation`, `f160`, `tick_stats`, `l011`, `quest_reward_save` (24 tests),
  `bot_smoke` `gateway_runner::moderation` + `isolation` (11), `mount_bots` (3), `spine_rules`, `cargo test --no-run`.
  The brief's "show the old rig fails under the same load" is answered by the two canaries (deterministic) instead of
  by generating CPU load, which the autopilot rules forbid.
- (R) The pet test's cause is inferred from the logs and the identical fix in the sibling rigs; it has no deterministic
  canary (a canary would need a slow gateway). The above-normal priority is likewise a mitigation, not a proof.
