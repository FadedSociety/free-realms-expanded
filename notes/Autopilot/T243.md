# T243: Preflight the whole battle prize bundle against bag capacity

## Outcome

`Gameplay::battle_prizes_available` now asks the inventory owner whether **one
clone of the live bag** can grant **all** previewed `(item, quantity)` prize rows,
in order, through the same `grant` path a real payout uses. A prize row that
passes the old single-row `Inventory::accepts_reward` check can no longer slip a
battle start through when the combined bundle needs a stack the bag does not
have (or would exceed `MAX_ITEMS`).

The new check sits inside the one existing gate (`battle_prizes_available`), so
the client Go start screen, the activity portal, the developer `realm battle`
command and the balance simulator all get it. The refusal path is unchanged: the
battle is not started, the existing `UNAVAILABLE_BATTLE_PRIZE` message is sent,
and the start screen reopens where one was open. No packet, opcode, field or
content JSON changed.

## What changed

- `src/inventory.rs` (+34/-2, 1478 lines): `MAX_ITEMS` is now `pub` with a doc
  comment naming its two enforcement points (`validate_state`, `grant`); a new
  private `MAX_REWARD_BUNDLE = 16` mirrors the encounter reward loader's row cap
  with a comment naming that owner; new
  `pub fn accepts_reward_bundle(&self, items: &[(i32, u32)]) -> bool` clones the
  inventory, applies `grant(0, definition, quantity)` per row in order on the
  clone and returns `false` on any error. Inputs are validated first: a
  non-positive definition, a zero quantity or more than 16 rows is `false`. The
  live inventory is never touched. `accepts_reward`'s doc now points at the
  bundle method for whole payouts.
- `src/gameplay/field_battle.rs` (+12/-5, 135 lines): the existing
  `EncounterEngine::battle_prizes_available` closure still runs the per-row
  catalogue/stack check; it now also records each accepted pair in a local
  `RefCell<Vec<_>>`, and after the encounter-level check passes the method asks
  `self.inventory.accepts_reward_bundle(&pairs)`. Empty bundles (cave encounters
  with no `battles` row) still fit.
- `tests/battle_prize_bag_preflight.rs` (new, 790 lines): the five required
  gates below, driving the real gateway frames.
- `notes/Autopilot/T243.md`: this report.

No hub file changed. `src/gameplay.rs` 6143 lines, `src/encounter.rs` 3322,

## Security threat note (secure-code-guardian)

What a hostile client can send here: a 41/108 Go body with arbitrary dword
values, a 41/109 leave, a 167/1/2 Play with a forged activity id, or a
fabricated 41/114-derived Go. None of those values is trusted:

- The battle id Go starts comes from the **server-owned** pending start screen
  (`take_pending_battle` also re-checks the marker radius); the 41/108 body's
  encounter/instance values are not read by the prize gate.
- The previewed `(item, quantity)` rows are **operator content**
  (`field_battles.json` prizes), never a client field. The client cannot choose
  the item, its quantity or the bundle length.
- `accepts_reward_bundle` refuses a non-positive definition, a zero/oversized
  quantity, an unknown definition, an over-stack row, more than 16 rows, or any
  `grant` failure including a full bag. It returns `false`; it never panics and
  never unwraps client data.
- The preflight mutates only a clone. The live inventory, coins, profiles,
  encounter, pending screen and save are unchanged on refusal (tests 1, 2 and 5
  assert snapshot-byte equality; test 5 also proves one player's refusal leaves
  another player's state byte-identical).
- Cost bound: a start attempt applies at most the previewed rows (the content
  loader caps a battle at 4 prizes) to one bag clone; this runs on start
  attempts only, not per tick, and each session's existing packet/rate budget
  bounds replays. A refused Go reopens the same screen, so it also grants no
  repeat attempt counter or cooldown progress.
- The coin component is deliberately **not** preflighted (see open gaps); it
  cannot be influenced by the client either.

## Open gaps

- **Coin cap is out of scope**, as the brief allows: the bundle preflight models
  only item stacks. All shipped battles pay 25 coins and the cap is
  `i32::MAX`, so no shipped row can hit it; a future data row that does would
  still fail atomically at payout. This residual is **not** fully closed for
  coins.
- **The payout grants one prize, the preflight checks all previewed rows.** The
  battle wheel picks one row at win time, so the bundle preflight is stricter
  than today's payout. This is the requested conservative slice; a future
  preflight could model the wheel's one-row pick instead.
- **A ~4095-stack bag does not fit the 1 MiB save envelope**
  (`game_store::MAX_SNAPSHOT_BYTES`; the pretty item JSON alone is ~1.3 MiB).
  The test therefore builds the live bag through the production
  `Gateway::load_gameplay` restore path and compares the snapshot payload rather
  than calling `game_store::save`. This is a pre-existing capacity/save gap,
  not introduced here; a live session can reach the state through grants before
  its next save. A production fix would raise or stream the save envelope,
  which is a separate task.
- Every shipped field-battle prize is uncapped, so the combined-stack case is
  only reachable today through `MAX_ITEMS`; the regression introduces a real
  bounded catalogue row to exercise the stack half of the bundle rule.
- No native client run; IDA was available for the four targeted reads above.
