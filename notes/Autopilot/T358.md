# T358: grade dungeon, minigame, item, recipe and gather targets in the enabled quest audit

## What changed

Test-only slice. The T314/F343 audit now proves the target ids it only
field-bounded before: `complete_dungeon`, `finish_minigame`, `collect_item`,
`equip_item`, `craft_recipe` and `gather_resource`. `client_reported` and
`visit_position` stay printed residuals (the first has no shipped server id
table; the second's geometry is the split loader's own bound). No production
file, content file, save, packet, selector or hub changed; the shipped enabled
set was already valid, so no content fix was needed.

## (R) reconstructed rules

- `(R)` The target-id sets are the shipped content ids the owning production
  loaders can actually produce; an id outside them is treated as an
  unreachable target, not as a client error.
- `(R)` `chess::GAME_ID` (20) and the derby `game_id` (39) are accepted as
  shipped minigame ids because the brief names them and both activities are
  content rows. The current server only emits `FinishMinigame` from fishing,
  kart, mining, harvesting and settled soccer (`gameplay.rs` 39/18 body, the
  lifecycle `grant_quest_events`); chess and derby have no emitter today. No
  enabled quest targets either, so the shipped audit is unaffected.
- `(R)` The three `CraftingJob::opening_recipe_id` fallbacks are valid
  `craft_recipe` events because `Gameplay::apply_craft` emits them when the
  learned recipe row has no stable id. They are listed in `recipes.rs`, not
  `recipes.json`.
- `(R)` The local gather drop keys and the harvesting game id are production
  policy/constants in `gameplay.rs`, not shipped data tables; the audit pins
  the same values with an owner comment rather than inventing a content file.

## Threat note (secure-code-guardian)

No client input, save, packet, session or reward path was added. The audit is a
read-only test over shipped content; the fixture writes only under
`CARGO_TARGET_TMPDIR` and removes itself on drop. A hostile client cannot reach
any of this: it cannot choose a target id, quantity, result, reward or
serialized state, and nothing here grants coins/XP/items or starts a session.

The graded ids themselves are a content-trust boundary: a bad dungeon,
minigame, item or recipe id now fails the gate instead of offering a quest whose
reward is dead content. The fixture's canaries deliberately remove or corrupt
scratch rows and assert the refusal; they do not touch `data/content` (the two
manual canaries were restored with recorded hashes). The only server constants
mirrored in the test are the private harvesting game id 111 and the three local
gather keys, both commented with their production owner.

## Open gaps

- **No shipped item catalogue.** `data/content` has no `inventory.json` /
  `item-catalogue.json`, so the shipped item set is empty and the item branch is
  exercised only by the scratch fixture. When an enabled item quest or a
  catalogue ships, the audit grades it automatically; until then the shipped
  run prints `0 item`.
- **`client_reported` remains residual.** Its `client_id` is a 45/7 trigger
  selector judged by the client, not a row in a shipped server id table. The
  target test prints it so the gap stays visible.
- **`visit_position` is not graded here.** The split loader rejects
  out-of-range geometry (`visit_geometry_bounds_are_enforced` drives it), but
  there is no shipped zone/point id table to resolve the destination against,
  so the kind stays in the printed residual set.
- **Chess/derby emitters.** The brief names chess 20 and derby 39; both are in
  the accepted set, but the current server does not emit `FinishMinigame` for
  either. A future quest must not rely on them without the owning activity
  adding the event.
- **Two enabled-but-unreachable records** (`3020014`, `3100020`) stay reported,
  not enabled or repaired; they need their disabled predecessors authored.
- **Local gather drops** are production policy keys in `gameplay.rs`, not a
  shipped data table; the test mirrors 1001/1002/1003 with a comment.
- **No native run.** The lead owns the client; this slice is a Rust content
  gate, and no client-visible behavior changed.
