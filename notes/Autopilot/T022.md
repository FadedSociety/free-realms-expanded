# T022 - Route chess (registered, not routed)

## Result

Chess is reachable from the client's activity-portal Play request and runs the
whole shared minigame lifecycle for single-player rows:

`167/1/2 Play` -> `39/16` info -> client `39/5` -> `39/17` + `26/12`
(`game_chess.gfx`) -> `39/14` `OnConnectMsg` / `OnStartGameMsg` -> moves ->
`OnGameWonMsg` -> client `FRServer_GameOver` -> `39/18`, `39/47`, `39/19` and
the coin payout -> client `26/42` Close.

`chess.rs` is still the only rules authority. The new `chess_service.rs` joins
it to `MinigameRuns`; `activity_portal.rs` can now publish non-battle rows;
`gameplay.rs` routes chess packets, blocks other activities while a table is
open, and stages every change on a clone.

## Reconstructed rules (R)

- Portal id = client minigame row id (20/66/67); they do not collide with the
  battle ids 96, 12301 or 12302.
- Portal category 0 and the `chess_detail.dds` / `chess_thumb.dds` art names;
  the type row's `CATEGORY_ID` is 0 and the client has no board-game category.
- Human colour is white; row 20 pays 10 coins, 66 pays 25 and 67 pays 50 on a
  win. Amounts are placeholders in `chess.json`, not recovered values.
- Only single-player rows are published. Two-player pairing is out of scope.
- Score and stars are 0 (never recovered). The payout is a coin grant through
  `MinigameRuns::finish` + `rewards::apply_grant`, followed by the ordinary
  wallet and reward-display packets.
- A win pays only after the server's own terminal result and the client's
  `FRServer_GameOver` acknowledgement; `39/18` is the quest event source.
- The run ledger is session-only (not saved). A reconnect starts with no run;
  no stale terminal packet can replay.

## Security decisions

- Every movie packet is staged on a cloned `Gameplay`; a refusal or malformed
  frame changes neither the table nor the wallet. The gateway's staged game is
  discarded on error.
- `39/14` for a foreign instance is rejected; movie traffic before `39/5` and
  after settlement is inert.
- `OnMoveComputerMsg` with four zero bytes no longer grants a win. The server
  checks its own legal-move list first; a forged no-move reply is a silent
  refusal.
- Client moves are validated by `chess.rs`; the client never names a winner.
- No player names or chat text were added to code, tests or this note.
