## Security threat note (secure-code-guardian)

A hostile client can send arbitrary `26/8`, `26/10`, `26/6`, `49/2`, `49/14`, `35/x`-shaped
bytes, replay a valid turn-in, name another quest, or try to force a spawn/recovery. The
fix does not trust any of it:

- Visibility rows are server content filtered by the player's zone and position; a client
  cannot request the `49/13` replay or choose its actor.
- The replay is built from saved server state (`pending_turnin`) and the quest definition;
  the runtime speaker is resolved from server content spawns. A wrong/stale definition
  fails closed (`None`), not with a client-supplied actor.
- Talk reopening still calls `begin_turnin(quest_id, key)`, which requires the actor to be
  the definition's turn-in NPC. `49/14` settles only the exact pending quest through the
  existing `quest:<character>:<quest>` idempotent grant key; a replay cannot pay twice.
- The three refusal tests snapshot the serialized state. An unoffered menu choice changes
  nothing and leaves the menu usable; a replayed hit on a defeated enemy changes nothing.
- No new item, coin, role or reward path was added.
