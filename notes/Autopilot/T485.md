# T485 - Pet care panel: fit kit items (53/16), feed (53/19) with 53/20, water (53/28), live 53/3 needs (lead build, 2026-10-26)

Lead build on T456 (`f7e82ee1`, which sits on T455 `b621363f` and tip `7d416a61`); this patch is only the care work.

## Client evidence (checked this pass)

- `Pet.EquipUtility` (`00c077a0`): the Lua slot argument has 199 subtracted when above 199, so utility slots are
  1..=7 (shampoo 200 -> 1, conditioner 201 -> 2, bowl 204 -> 5, food 205 -> 6, vitamins 206 -> 7); the pet word is
  the active pet's id (`00a10970`); the item word is Lua argument 1 parsed from a string (`0101cd50` ->
  `00738e70`). ScriptsBase.lua `equipItem` passes the same id to `Ui.ClearItemNewFlag(b)`, the client's inventory
  item key, so the server reads it as the owned instance id (R). Inbound `00b55b80` reads the same shape: u8 flag,
  then three u32.
- Need order: PetListDataSource's value getter `00ccc680` reads FoodNeed at record +0x20, GroomNeed +0x24, PlayNeed
  +0x28 and Mood +0x2c, the order our record and 53/3 writers already use. The 53/3 handler itself sits in an
  undefined IDA region; its straight copy to +0x20.. stays (R).
- Kit rows (shipped catalogue `lab/reports/item-catalogue-20261015`): bowl 11 slot 204, Simple Pet Food 1835 slot
  205, Simple Pet Shampoo 1836 slot 200, conditioner 10521 slot 201, all class 73; dog model 364 lists class 73.
  Our 35/34 reply row carries class at +44 and slot at +52 (after the 12-byte header), which is what
  `Inventory::kit_facts` reads from the parsed row.
- Legacy Param1 of every food/shampoo row equals the utility slot; food Param2 runs 50..400 (1835: 120).
- Kind 3's timer word is not used: this server sends kinds 1, 2 and 6 only.

## What changed

- `src/pets.rs`:
  - `PetRequest::Utility`/`Feed`/`Water` decode subtypes 16 (13-byte body), 19 (8) and 28 (1 byte, 0 or 1); any
    other length or value is an error like the existing arms. `DECODED_SUBTYPES` lists every decoded subtype and
    the gateway's pet label reads it.
  - `handle_at_ms`: the gateway route with the millisecond clock (`handle_with_inventory` keeps the seconds form
    and wraps it). 53/16 fit needs an owned, non-vanity (R) pet, slot 1..=7 and an owned item of type 4 whose
    definition slot is slot + 199 and whose class the model lists; it echoes 53/16 (flag 0, pet, slot, item).
    Remove clears the slot (echo flag 1, item 0). A refusal re-echoes the unchanged slot and changes nothing.
  - 53/19: bowl (slot 5) and a configured food (slot 6) fitted, the pet summoned, not vanity, not in water, not
    busy (`Gameplay::blocks(pets)` via `PetBusy`), no feed running -> 53/20 kind 1. Every refusal -> kind 6.
  - `care_tick` (called from `Gameplay::pet_tick`): at `feed_effect_ms` the food is consumed through the existing
    `care` (one unit, the bowl kept, the slot cleared when the stack empties, 53/3 sent, `changed` set); at
    `feed_end_ms` 53/20 kind 2. Live needs: a decayed copy of the pet (the roster is never written) goes out as
    53/3 when it moved by `status_epsilon` and `status_interval_ms` passed (the first one right after a summon).
  - A dismiss, re-summon or zone change during a feed sends kind 2 (`care_end_packet`) and nothing is consumed
    afterwards; a disconnect drops the session state.
  - 53/28 calls `set_in_water` for a summoned pet.
  - `care_items` restore bound is now a sanity cap of 1000 (Param2 scale); the bar still clamps at the maximum.
- `data/content/pets.json`: `care` block (feed_effect_ms 900, feed_end_ms 6000, status_interval_ms 1500,
  status_epsilon 0.5, all R, with bounds in `CareTiming::valid`); food 1835 restore 120 from Legacy Param2 with
  reference provenance (ClientItemDefinitions.json @9e082025391177d5a33ee18c714ddd06b457a695, sha256 40a3cc79...,
  row 1835). 1836 and 10521 keep the (R) 25/35.
- `src/inventory.rs`: `kit_facts(definition) -> (type, slot, class)`.
- `src/gameplay/rides.rs`: `handle_pets` passes milliseconds; `pet_tick` runs `care_tick`; `settle_pets` ends a
  running feed. `src/gateway/companions.rs`: the pet tick passes `changed` through, so the apply step is saved.
- `src/gateway.rs`: the pet label reads `pets::DECODED_SUBTYPES` (+ label asserts for 19 and 28).
- `tests/support/pet_inventory.rs`: `with_kit_items` (kit rows with type 4, slot and class).

## Native check

Fit a bowl and Simple Pet Food in the pet's care panel, press Feed: the panel locks, the pet eats, the food count
drops by one and the food bar rises; the panel unlocks after about 6 s. Feeding without a bowl, or while swimming,
unlocks the panel at once. The need bars move while the pet is out.

## Checklist

1. A refusal changes nothing: fit refusals mutate nothing (only the echo); feed refusals only send kind 6; tests
   assert roster and inventory equality.
2. Rollback: the apply step goes through `care`, which stages the roster and inventory on clones and commits both
   only after the consume succeeds; feed state is session-only on `ActivePet`.
3. Deltas: the food restore is added to the live need and the inventory consumes one unit from the live stack;
   nothing earlier is written back.
4. Busy: a feed refuses while `Gameplay::blocks(pets)` is set (minigames and the activities that gate pets), in
   water, or while a feed runs; summoning stays gated as before.
5. Entry paths: 53/16 and 53/19 only arrive through `Gameplay::handle_pets` -> `handle_at_ms`; the apply step
   only runs from the world tick for the summoned pet; a reconnect starts with no feed running.
6. Real path: gateway -> `Gameplay::handle_pets` -> `PetService::handle_at_ms`, and `Gateway::tick_at` ->
   `pet_tick` -> `care_tick`; pet_care drives those entry points, pet_wired drives `Gameplay::pet_tick`.
7. Reconnect: fitted kit items are in the roster (saved); the apply step marks a save via the tick outcome; tests
   reload before and after the apply step.
8. Exits: dismiss, re-summon and zoning send kind 2 and drop the feed; a disconnect drops the session state;
   every refusal unlocks the panel (kind 6).
9. Economy: feeding grants nothing but need points; one food per feed, the bowl is never consumed; a duplicate
   53/19 is refused.
10. Wire: 53/16 `00c06ea0`/`00b55b80`, 53/19 `00b5f720`, 53/28 `00b60350`, 53/20 `00b55cc0`/`00b5ce60`, 53/3
    `00b555a0`; byte-level asserts in pet_care.
11. Ids: no new ids; the pet id and the client's item key are echoed back.
12. Others: care panel packets are private to the owner; nothing here changes what viewers see.
13. End to end: a fitted bowl and food feed the pet, the food bar rises and one food leaves the bag.
14. Data: feed delays, refresh gap and threshold live in pets.json `care` with bounds; the food restore in
    `care_items`.
15. Canary: dropping the 53/20 unlock in `start_feed` (production code) fails four refusal tests.
16. Session plumbing: untouched; the gateway change is the pet label and the pet tick's `changed` flag.
17. Tick safety: `care_tick` never returns an error; a failed apply consumes nothing and the feed still ends.
18. Type rules: care timings validate on `CareTiming::valid`; need decay is one function (`decayed`) for the saved
    roster and the live view.
19. Hot path: `care_tick` holds the shared `Arc` content (no copy) and reads decayed needs without cloning the pet;
    it allocates only when it sends a packet.
