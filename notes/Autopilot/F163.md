## Security threat note

A hostile client can replay `41/108`, forge encounter/instance values, send an
arbitrary activity id to portal Play, call the admin `realm battle`/`realm sim`
commands, click any marker GUID, or replay results Close.

- Go uses only the server-owned pending battle; the request body is not trusted.
- Go takes the pending screen (which validates the marker distance), then the
  prize gate runs before zoning, before instance allocation and before any
  inventory grant. A refusal restores the same screen through
  `reopen_battle_screen`; the repeated-Go assertion proves the pending battle
  remains usable. Both a missing definition and an unstackable quantity are
  refused.
- Portal Play uses the published activity catalogue and admission first; the
  developer commands are role-gated.
- Prize ids and quantities come from operator content, never from the client.
  `accepts_reward` asks the loaded catalogue, and `grant_bundle` remains atomic
  (clone, validate, commit) if a future content path ever reaches payout.
- `realm sim` works on a clone and grants nothing.
- Refusal tests snapshot the complete gateway state before and after hostile
  requests and assert equality.
