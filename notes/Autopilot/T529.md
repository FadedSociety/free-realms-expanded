# T529 — Coin shops never sell an item the server cannot make work

**Outcome.** `CoinShop::buy_once` now asks what the item is after its existing row and definition
check. Type-2 pet rows sell only when the bundled pets content binds the id; type-19 rides and
type-16 house lots never sell for coins. A refused buy answers the existing `RESULT_INVALID_ITEM`
failure (165/6 for 165/4, 66/44 status 0 for 66/43), takes no coins, grants nothing and writes no
save. The 165/10 coin merchant list now hides the same refused rows, so the window and the buy
cannot disagree.

## Security threat note (secure-code-guardian)

- **What a hostile client can send:** 165/4 or 66/43 with any positive item id, quantity and
  transaction id, including an id the shipped client would not show. The rate is bounded by the
  SOE receiver and the existing packet caps.
- **Why the new path is safe:** the id must pass the existing positive-id, `stores.json` row and
  client-definition checks, and then `sale_block`. The type comes from the server's catalogue and
  the bound-pet set from the bundled pets content; the client cannot name either. An unreadable
  definition maps to a refusal (`Some` reason), never an `Err`, so one bad request cannot become a
  session `internal_error`. The refusal returns before staging any inventory/coins; the reason is
  not sent to the client (the existing invalid-item / 66/44 false reply is). Nothing is logged with
  payload text.
- **Refusal changes nothing:** tested by snapshot equality, `gameplay_changed == false` (no save),
  unchanged coin balance and bag, a failing 165/13 probe for the refused transaction, and a
  successful buy-back of a sale seeded before the refusal (so an existing ledger entry survived).
  The canary below proves the assertions depend on the production gate.
- **Window advertising:** 165/10 now omits the refused rows, so the client cannot present a buy
  that the server will always refuse. A hostile client can still send it; the gate refuses it.

## Checklist

1. **Refusal changes nothing** — tested: `!gameplay_changed` (no save), full `Gateway::snapshot`
   equality, coin/bag equality, no 165/13 entry for the refused transaction, and a pre-seeded sale
   still buys back. The canary breaks the gate and these assertions fail.
2. **Rollback covers all state** — `buy_once` returns before staging anything on a refusal; the
   new check adds no `Rc`/`RefCell`/`Arc` side state. The bound set is immutable content data built
   in `new`.
3. **Apply deltas, never restore snapshots** — not applicable: no payout or exit was added; the
   success path still debits the live wallet and grants into a staged clone as before.
4. **Busy rules are mutual** — not applicable: this is a purchase gate, not a new activity; no
   `Occupation` variant, no busy window was added. The existing vendor/shop path keeps its checks.
5. **Every entry path is gated** — the check sits in `buy_once`; graph + source confirm its only
   callers are `buy`, `buy_vendor` and the 165/4 route (`handle`/`handle_coin_store`), and 66/43
   reaches `buy_vendor` through `Gameplay.npc_merchant_buy_66_43`. Tests drive 165/4 and 66/43.
6. **Reachable in production, tested through it** — tests use the real gateway, the shipped Gloria
   vendor record/NPC file, real `stores.json` prices and the real catalogue; no internal service
   call performs the action.
7. **Survives reconnect** — the gate is derived from static content at every shop construction, so
   there is no new session state to persist; a reconnect rebuilds the same set. No new save field.
8. **Every exit path restores the player** — no new activity or exit. A refusal leaves the open shop
   usable: both tests buy back a pre-seeded sale after the refusal, which requires the shop/range
   session to still be valid.
9. **Economy safety** — no coins taken, no item granted on refusal (asserted); the success tests
   assert the exact server price debit and the grant of the expected item; type and binding are
   server content, never a client field.
10. **Wire format matches the client reader** — no new fields. The new tests reuse the
    shared reader-derived builders/parsers in `tests/common/gateway_vendor.rs` (165/4 and 165/13
    were moved there by F707; 165/12, 66/43 and 66/44 were already shared) and the 165/10 decode
    asserts the window contents.
11. **Unique ids** — not applicable: no instance/GUID is created by this change; successful buys use
    the existing inventory allocator.
12. **Others see changes** — not applicable: a purchased bag item is private to the buyer; no outfit,
    mount or actor spawn changes, so no broadcast path is involved.
13. **Content works end to end** — gate (b) buys a pets-bound type-2 row and asserts the grant; gate
    (c) buys type-29 furniture and asserts the grant; gate (d) covers every shipped vendor row.
    Pet adoption itself is the pets planner's scope.
14. **Values live in data** — blocked item types are client/protocol constants, not tuning; prices
    and stock stay in `stores.json`/`vendors.json`. No timeout, cap or window was added.
15. **Canaries break production code** — the canary was a real `return None;` in `sale_block`, and
    four tests failed; the test does not manufacture the failure.
16. **Hands off session plumbing** — `src/bin/osfr-gateway.rs` and `gateway.rs` are untouched; no
    change to session creation, teardown, transactions or save ordering.
17. **One player's error never stops the server** — a presentation error is mapped to a refusal
    `Some(reason)`, not `?`; the gate is per-request and returns `Ok` for refusals. The tests send
    blocked ids through the real dispatch and the session survives. No shared tick code changed.
18. **A type's rules live on the type** — `pet_items` and the `sale_block` contract are documented
    on the `CoinShop` side; the client type values and their policy citations are on `sale_block`.
    The content test pins the reviewed unsellable rows.
19. **Hot paths stay cheap** — per buy: one definition lookup + one `BTreeSet` lookup; per shop
    open: one `sale_block` per advertised row (F707 correction: this is a second
    `inventory.presentation` per row, after `npc.rs:1289`, so it replaces no work); per session:
    three bundled-pets parses (F714 correction): `CoinShop::load` (`gameplay.rs:1000`, parsing in
    `coin_shop.rs:265`), `PetService::new` (`gameplay.rs:1183`) and `Gameplay::adopt_pets`
    (`gameplay/rides.rs:213`, called from `src/bin/osfr-gateway.rs:956`), plus the set build in
    `CoinShop::new` (17,476 store rows x 113 species rows, simple integer `contains`). Hoisting
    the shop's parse would leave two. Nothing runs per tick.
