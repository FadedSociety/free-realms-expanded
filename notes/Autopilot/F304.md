### Finding 1 (BLOCKER): the pattern id is validated where it is loaded

`RecipeCatalog::load_runtime` builds `item_definitions` from the recipe file
itself (`src/recipes.rs:198-210`), so the existing `item_reference` call for
`recipe_item_definition_id` (`src/recipes.rs:498-505`) always passes for a
pattern id that came from the same record. A private `recipes.json` with
`"recipe_item_definition_id": 0` or `-1` therefore loaded, and `wire_rows`'
fallback `u32::try_from(pattern_id).unwrap_or(0)` (`src/recipes.rs:296-302`)
emitted item definition id 0 — not the "positive validated pattern id" F289's
checklist and security note claimed.

The fix is at the root: `validate_recipe` now rejects
`recipe.recipe_item_definition_id.is_some_and(|id| id <= 0)` in the same
invalid-id check as the other ids, and the `Recipe` field doc states the rule so
the next field added has a precedent. `None` still loads and means "never emit
a wire row", which is what the two shipped records with no pattern rely on.
The production loaders (`Gameplay`, `cooking`, `smelting`, `forging`) all call
`RecipeCatalog::load`, so the check holds on every path.

The regression test mutates a copy of the shipped `data/content/recipes.json`
(pattern 848 → 0 and → -1), writes it as a packaged `recipes.json`, and calls
the production `load_runtime`; it asserts the refusal message names the pattern.
The shipped file has no non-positive pattern id (32 records, 2 `null`, the rest
positive), so no content changed.

does not invent those mappings; the test comment, `F289.md` and this note list
them as the open gap.

## Security threat note (secure-code-guardian)

- **What a hostile client could send:** a recipe id in 26/24, a malformed 26/24
  length, zero/negative/extreme ids, or a replayed win. F304 adds no parser,
  opcode or field. The new test sends Chef recipe 70 from a Miner; the existing
  route tests send 0, -1, 12345, `i32::MIN`, `i32::MAX`, short/long bodies and a
  request from outside the station.
- **Why the refusals hold:** `recipe_book::start` checks learned, active job,
  idle services, station range, rank and exact inputs before any service call;
  every refusal returns `Err(Refusal)` and only appends a chat line. The new
  test asserts the full snapshot and both save flags are unchanged, so the
  refusal cannot consume an offer, item, cooldown or run.
- **Content boundary:** the private `recipes.json` is server-owned. The new
  load-time check means a hand-edited file can no longer make `wire_rows` emit
  item definition id 0 via a non-positive pattern; `u32::try_from` still cannot
  wrap. No client-provided value reaches the pattern id.
- **Economy:** no grant, sell, coin, reward, trade, role or chat policy changed.
  The wrong-job refusal happens before `begin_recipe`, so nothing is consumed or
  paid; the canary showed the removed gate would have started the craft.
- **Isolation:** validation runs at content load, not in a tick; a bad file
  refuses the load instead of panicking per player. `app_fuzz` (20 passed) still
  runs the hostile corpus.
