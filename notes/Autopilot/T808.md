# T808: card login reply hardening and ping echo (lead brief, Opus builder, 2026-10-27)

## Why
Research on the 81 reply (2026-10-27): our 81 v5 layout is read by the DLL, but four things would still break a native run once
T805 lets the login through:
- A success with account id 0 crashes the client: the handler `10179530` -> `10068ac0` stores no player for 0, and `10007ed0`
  then writes through a null player. `guid & 0x7fff_ffff` is 0 for a guid whose low 31 bits are zero.
- After login the DLL sends `NetworkCommand_Ping` (112) at once and every 10 s (`1037c490`); only a server copy resets its
  counter (execute `1018fe80` -> `10068dd0`), and at 60 the player sees "60 seconds have elapsed without a response".
- A refusal used code 1, "Authentication Failure ... verify the entered login information", which is about a password that
  this login does not have.
- A refused connection stayed open until the 30 s login deadline.

## Change
- `src/card_service.rs`
  - `account_id(character)`: `(character - 1) mod i32::MAX + 1`, which is never 0, positive and deterministic. The account
    store's sequential guids (from 1) map to themselves.
  - `reply` takes `logged_in` and a `character_for` closure that returns the character. The account id is computed in the one
    place the 81 is built, and the success code stays 0 (76 would open username registration, `103c9750`).
  - Refusals carry code 63, the client's message "Your session is not valid." (message factory `1038a440`, case 63). Code 70
    ("already been used") was not used, because a spent ticket is deleted and cannot be told from an unknown one.
  - Ping (112): decoded from the DLL. The creator is `10190080`, the id `1018fdf0` returns 0x70 and the version `1018fe40`
    returns 1. The reader `1018ffe0` and the writer `10190020` read and write ONE header, because the class has no family
    level: the writer calls the header writer `1019de90` once. The header is followed by one compact int, the spoof value.
    Once `logged_in`, the service checks it reads exactly that and answers `(112, 1, spoof)`. Before login the ping is left
    unhandled.
- `src/bin/osfr_gateway/card_listener.rs`: passes `logged_in`. Once a refused 81 is written, the connection closes
  (`card_closed reason:"login_refused"`). An echoed ping logs `card_ping` (under the existing 16-per-connection cap).

## Threat note
The launch ticket stays the only credential: random 64-bit, single use, TTL, one per character. Closing on refusal limits a
connection to one ticket guess; before, a stranger could repeat guesses on one socket for 30 s. The ping echo answers only a
logged-in connection, has the same size as the request (no amplification), and must decode exactly. The account id is not a
secret. Two characters share an account id only past `i32::MAX` characters.

## Structure
No new file. One pure function (`account_id`), one private codec function (`ping_echo`), one const each for the refusal code
and the ping class. The listener changes one closure, one match on the redeem outcome, and one event arm.

## Gates
- `tests/card_service.rs`: `every_character_gets_a_non_zero_account_id`, `a_ping_is_echoed_only_after_login` (golden
  `20 07 01 22 4D`, refused before login, a ping with trailing or missing bytes is an error), and refusal code 63.
- `--bin osfr-gateway card`: `a_login_is_accepted_only_for_the_ticket_redeem_names` (63, `login_refused` close, EOF at the
  client, guid `1 << 31` gets a non-zero account id), `a_card_ping_is_echoed_once_logged_in` (unhandled before login, golden
  echo after), and `card_login_events_name_the_character_never_the_ticket` (two connections now).
- Canaries, one per change, each failing as expected: low-31-bit account id (the listener login test), no ping arm (both ping
  tests), code 1 (unit and listener tests), no close (the listener login test).
- card_service, card_launch, startup_messages, gateway, app_fuzz, spine_rules, `cargo test --bin osfr-gateway card`,
  `cargo test --no-run`.

## Next native run
Server: `card_login ok:true character:<guid>`, then a `card_ping` about every 10 s (16 logged per connection) and no
`card_closed`. The client shows "Entering main lobby..." with no "Login Failure" box and no "60 seconds" message after a
minute. It stays on that screen until the lobby slice. A refused login shows "Your session is not valid." and its connection
closes at once (`card_closed reason:"login_refused"`).

## Lobby slice (next; nothing sent yet)
Every lobby command uses the LobbyCommand family level (reader `10156340`, writer `10156390`): three headers (its own, the
LobbyCommand level, then the NetworkCommand level `1018aa90`/`1018aac0`), then int AccountID (`+4`). The class fields follow.
- 291 `LobbyCommand_ChangeLobbyDisplay` v1 (id `1015e370`, version `1015e3c0`, reader `1015e5f0`, writer `1015e640`, execute
  `1015e400`): the family level plus int GroupID (`+8`). The execute raises event 70 with the GroupID and, when the lobby
  manager (singleton `10174790`, map at `+4`, find `101717d0`) knows the group, makes it current (`10068cd0`, which asserts
  "lobby"). The lobby filter `10372d70` turns event 70 into `changeScreen(3, GroupID)` (`1037e5a0`), unless a WALobbyScreen
  for that group is already shown (`102b9330`). Decoded here; still needs a golden test.
- 94 `LobbyCommand_AddGroups` (id `10157810` = 0x5E, reader `101583f0` -> list reader `10158350`, writer `101576d0` -> list
  writer `10157510` -> per-element `1019e0f0`, execute `101578b0`, 636 lines): defines the groups the manager looks up.
  Property sets use integer and string lists (`kIntegerListTypeID`, `kStringListTypeID` asserts), and accounts are created
  through the player table (`10018430`, assert "account"). The element layout is still to decode.
- 92 `LobbyCommand_Join` (alias 0x154; reader `10163b20`, writer `101638d0`, execute `10163220`): the family level, int `+8`
  (group), int `+0xC`, string `+0x10`, object `+0x2C` (`10009c00`), string `+0x3C`, property set `+0x5C` (compact 0 plus
  its writer, or compact 1 when absent), int `+0x58`. The execute asserts `mPropertySet` and the account, and logs
  "Join: couldn't get group" for an unknown group.
- The client must already know the player (created at login from the 81's account id, `10068ac0`) and the group. The lobby
  screen's methods resolve the group through `101717d0` (`102b9500` connects its `updateLobbyInfo()`/`updateChildren()`
  signals; `102b9930` uses it unchecked; `102ba4a0` null-checks), so an unknown group risks a null use (R).
- Minimal sequence (R on order): after the 81 success, 94 AddGroups with one lobby group G, then 92 Join (this account, G),
  then 291 ChangeLobbyDisplay (G). Golden-test each body against its reader first: an unreadable reply wedges the
  connection for good (receiver `10192500`).
