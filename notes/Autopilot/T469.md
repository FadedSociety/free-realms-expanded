# T469 - Send the retail game clock in the time-sync reply (sky runs at 8x)

## What changed

- `src/game_clock.rs` (new): `GameClock { rate, epoch_unix }`, `Default` (rate 8, epoch 1221361670),
  `load(directory)` (optional `game_clock.json`, 4 KiB bound, strict fields, schema 1), `checked()`
  (rate 1..=16, epoch >= 0) and `sync_reply(now_unix)`, which returns the unwrapped 52 message:
  u16 52, i64 Time = rate x (now - epoch), i32 rate, u8 0.
- `data/content/game_clock.json` (new): rate 8 and epoch 1221361670, with provenance in `source`.
- `src/gameplay.rs`: a `game_clock` field filled by `GameClock::load(npc_content)` in
  `Gameplay::load`, plus the `game_clock()` accessor. `npc_content` is the content folder, or the
  repository `data/content` when a lab package has no NPC tree, so the shipped file also applies to
  dev runs.
- `src/gateway.rs` `Event::Time`: the 4 inline reply lines are replaced by the clock's
  `sync_reply(seconds)`, using the session gameplay's clock or `GameClock::default()` when there is
  no gameplay. The before-login refusal and both system-clock errors are unchanged.
- `src/lib.rs`: `pub mod game_clock;` (CRLF kept).
- `tests/app_fuzz.rs`: `time_sync_sends_the_content_game_clock`.
- `tests/gateway.rs`: `time_response_uses_current_seconds_and_original_packet_shape` pinned the old
  frozen reply (Time = unix, rate 0, flag 1), so attempt 1 broke it at integration. It is now
  `time_response_runs_the_game_clock_in_the_original_packet_shape` (same 7-byte wrapper pin, body
  equals `GameClock::default().sync_reply(now)`, rate 8, flag 0).

## Client evidence (IDA broker, 2026-10-22; re-checked 2026-10-24 for attempt 2)

- Reader `0x00bd1700`: u16 at +4, i64 at +8/+0xC, i32 at +0x10, bool at +0x14 (`*v9 != 0`).
  That is 15 bytes, and the byte test pins exactly this layout.
- Apply `0x00bd1830` first calls vtable +36 (SetFromUnixTime `0x010bd270`) with
  `(Time lo, Time hi, 0)`. It then sets `this[24]` (+0x60, scale) = ServerRate and sets the byte
  at +0x64 to UseClientTime (it toggles only when the value differs).
- `0x010bd270` returns at once while +0x64 is set. Otherwise the time of day comes from
  `0x007026b0(Time, .., 1)` (localtime64, local flag). The flag-1 argument scales the result with
  `scale * (s % (86400/scale))`, but the apply passes 0, so this path is not used here. The only
  flag-1 caller is the ctor `0x00bd1bf0`, which runs while the scale is still 8.
- AdvanceClock `0x010bd380` only clears its accumulator while +0x64 is set. Unfrozen, it advances
  the day-second at +0x58 by `scale * ms / 1000`, wrapping at 86400. Rate 0 never advances it
  (`v4 > 0` is false).
- Ctor `0x010bd190`: `this[24] = 8`, and the byte at +0x64 = 0.
- `0x007026b0`: `if (a1 > 0x793406FFF)` sets 1970-01-01 00:00 and returns 0. The comparison is
  unsigned, so a negative Time also gives 1970.
- Cadence: `0x00bd1b40` (PeriodicTimeReport) sends a request when `this[2] - this[4] > 5`.
  `0x00bd16d0` (freshness) is `<= 10`.
- `0x00bd1830` has only one xref, the vtable at `0x0182674c`. In the server, nothing else reads
  the 52 reply: `rg` for `Event::Time` and for 52-reply bytes finds only the gateway arm and
  `app_fuzz` `follow_up`, which checks the opcode only.

### Corrections to the brief

1. The cap is `0x793406FFF` = **32535244799** (3001-01-01 07:59:59 UTC, MSVC `_MAX__TIME64_T`).
   The brief's 32535215999 is 8 h short. The code uses the client's hex constant.
2. "Time <= cap for every now up to 2100 at rate 16" cannot hold without a clamp: 16 x
   (4102444800 - 1221361670) = 46097330080. `sync_reply` now clamps Time to `0..=cap` (R, see
   below). The test checks rate 16 up to `i64::MAX`, and checks that the default rate 8 is still
   exact (not clamped) in 2100.
3. "Rate 0 would divide by zero in `0x010bd270`": that path needs flag 1, and the apply passes 0.
   Rate 0 freezes the sky instead (AdvanceClock never advances), so it stays refused.
4. The sync cadence is about 6 s (`> 5`), not 11 s. The 11 s continuity test still holds for any
   gap.
5. The research pack called commit 2cd13f1 unverified. It is in
   `lab/references/Sanctuary-main-20261019`: "Retail replies (2014 captures) sent Time =
   ServerRate * (unix - zone epoch) with no timezone offset". Only the values were used, not the
   code.

## (R) choices

- `epoch_unix` 1221361670 (2008-09-14 03:07:50 UTC): the value comes from the Sanctuary-main
  2cd13f1 commit message. We hold no capture.
- Rate bounds 1..=16: sanity bounds. 0 freezes the sky; 16 is an arbitrary ceiling.
- Clamp: a Time past the localtime64 cap is held at the cap (the sky stops) instead of jumping
  to 1970. At rate 8 this first happens in 2137 (at rate 16, in 2073).
- Clock skew (now < epoch) sends Time 0. A negative product (only possible on an unchecked
  `GameClock`) also clamps to 0.
- No time-zone compensation, as in retail. Each player's sky is offset by their own UTC offset.

## Structure

- Graph (`autopilot-int`): `search_graph` "time sync game clock ServerRate UseClientTime" found no
  existing owner (only soccer/kart game timers). `trace_path wrapped` is ambiguous across test
  copies. `rg` found the single production consumer, the `Event::Time` arm.
- New owner module: `src/game_clock.rs`. The hub only gets dispatch: `gateway.rs` net -2 lines,
  `gameplay.rs` net +5 (field, load line, 3-line accessor; 35 lines under the ceiling). Nothing
  was moved out of `gameplay.rs` to offset it, because moving unrelated code in a hub that seven
  parallel builders edit risks merge conflicts. If the lead wants this exactly net-zero, the
  accessor can become a `pub(crate)` field (+2).
- Deleted: the inline reply bytes in `gateway.rs`.
- Not hot-reloadable: `realm reload` does not re-read the clock. A new login picks up the file
  (`Gameplay::load`). Add it to `content_reload` when live sky tuning is wanted.

## Threat note

A hostile client can only send 52 requests. The body is parsed and ignored, and the reply depends
on the server clock alone. A flood costs one 22-byte reply per request, under the existing bundle
budget. Before login, a request is refused as it was before.
