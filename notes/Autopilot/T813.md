# T813: card window from "Entering main lobby..." to the lobby screen (lead brief, Opus builder, 2026-10-27)

## Why
After T805/T808 the card login succeeds, but the DLL does not leave the session dialog by itself. It shows "Entering main
lobby..." until the server drives a screen change (research 2026-10-27, `10372d70` event 70). Every reader below was decoded
with Hex-Rays on a scratch copy of the TCG DLL database before anything was sent: an unreadable body wedges the connection
for good (receiver `10192500`).

## Client facts (TCG DLL)
- **LobbyCommand level** (reader `10156340`, writer `10156390`): the three class headers (own, LobbyCommand, NetworkCommand
  `1018aa90`/`1018aac0`), then int AccountID.
- **94 `LobbyCommand_AddGroups` v1** (id `10157810`, version `10157860`, reader `101583f0`, execute `101578b0`): level, then a
  list (`10158350`: compact count, then each element polymorphic: peek class id `10097860`, factory `100940b0`, the object's
  own reader at vtable +0x24).
- **`Lobby`** (class 103, registered as 0x67, creator `10156110`, ctor `10155ff0`, version 3 `10155f60`). Reader `10155710`,
  writer `101558e0`, one header. The fields, in order:
  - five optional property sets (`1000dd90`: compact 1 = absent, 0 = a polymorphic object);
  - five role lists (General, Player, Observer, Moderator, Staff; `1000a2c0`: count, then ints);
  - int Containing GroupID, int GroupID, int eLobbyTypeID;
  - v>1: an optional deck (`100a5190`);
  - v>2: int tournamentRound, int subState.
- The Lobby object is a QObject with PersistentComponent at +8 and Sortable at +12. Its has-property (`1014ba30`) and
  get-property (`1014fcb0`) read the first property set and return "absent" when it is null. The AddGroups execute uses an
  empty default set for absent ones (`101baa50`).
- **AddGroups execute**: raises event 3 (containing, group, type). Children are linked only when the containing group is
  known. `10171b60` files the group by GroupID in the lobby manager (singleton `10174790`, map +4, find `101717d0`).
  Properties 4028/4029/4033 (member accounts and names) are read only when present.
- The event-3 handler `10371960` sends the client's own 92 Join request for group id 1 (the client's root lobby). It also
  sends `AccountCommand_UploadAvatarImage` (`102a9710`) when an avatar image is pending.
- **92 `LobbyCommand_Join` v4** (version `101637c0`, reader `10163b20`, writer `101638d0`, execute `10163220`): level, then
  int GroupID, int role, and by version:
  - v>1: a string;
  - v>2: an int list;
  - v>3: the name, an optional `PropertySet`, and an int.
- **Join execute**:
  - A non-empty name asserts `mPropertySet` and the account (`10018430`), sets the player's property set and name, and
    raises event 16.
  - When the group is known and the account is the client's own, it makes the group current (`10068cd0`).
  - It raises event 5 and adds the member (`10155590`, which asserts `kInvalidRole != role`; the execute turns 0 into 1).
  - An unknown group only logs "Join: couldn't get group".
- **`PropertySet`**: class 23, version 1. Reader `101ba700`, writer `101b99a0`, one header, then a map (`101b9f70`: count,
  then key plus a polymorphic `ValueData`).
- **291 `LobbyCommand_ChangeLobbyDisplay` v1** (id `1015e370`, version `1015e3c0`, reader `1015e5f0`, writer `1015e640`,
  execute `1015e400`): level, then int GroupID.
  - The execute raises event 70. `10372d70` turns it into `changeScreen(3, GroupID)` (`1037e5a0`), unless that lobby screen
    is already shown (`102b9330`).
- **Lobby screen**: setup `102b9500` looks the group up and connects its `updateChildren`/`updateParticipants` signals, then
  calls vtable +0x100.
  - In the WABaseLobbyScreen vtable (`1069730c`), slot +0x100 (at `1069740c`) is `102b9930` (updateLobbyInfo). It passes
    the `101717d0` result to `10153050` without a null check.
  - `102ba4a0` null-checks, and `102b9b60` returns the raw lookup.
  - So the group must be filed before 291.

## Change
- `src/card_game.rs`: the launch block takes an optional `lobby` (`group_id`, `lobby_type`, `role`: R values from data). Bounds:
  group ≥ 1, role 1..=5 (0 is the client's invalid role), type 0..=255. Without it, a login stops after the 81, as before.
- `src/card_service.rs` `lobby_entry(account, lobby, name)`: the three bodies, in order.
  - 94: one Lobby (103 v3) with five absent property sets, five empty role lists, containing group 0, the group, the type,
    no deck, round 0 and sub-state 0.
  - 92: group, role, empty string, empty list, the 411's character name, an empty `PropertySet` (`27 01 01 00`), and 0.
  - 291: the group.
  - The account id is the 81's (`account_id`), so Join takes the client's own-account path.
- `card_listener.rs`: the listener keeps the launch block's lobby. The first successful login on a connection writes the 81
  and then the three frames, and logs one `card_lobby` event (peer, character, account, group: ids only).

## Threat note
Nothing new is accepted from the client: the lobby is pushed only after the launch ticket was redeemed (T805), once per
connection. The name echoed in Join is the client's own 411 character name, sent back to the same connection. The pushed values
are server data. The `card_lobby` event carries ids only. No new input is parsed.

One serde struct and one bound in the card content, one pure codec function, one listener method. No new file.

## Native run
The native package's `card_game.json` launch block needs `"lobby": {"group_id": 1, "lobby_type": 1, "role": 1}` (R).
- Server: `card_login ok:true`, then `card_lobby` with group 1, then a `card_command_unhandled` class 92 (the client's own
  Join request for group 1), then `card_ping` about every 10 s.
- Client: the session dialog gives way to the lobby screen (WALobbyScreen) with "Matches: 0" and the player listed.
- Unverified (R):
  - the title text, which comes from a client provider keyed by group id (`103e7780` vtable +56);
  - whether type 1 is the right root lobby type;
  - whether the client wants an answer to its own Join request.
