# T373: prove two players run the same dungeon marker independently

## Result

One default-suite file, `tests/two_player_dungeons.rs`, proves the current
model is a **session-local** encounter: two in-process `Gateway`s (two
characters) click the same static Sheep Watch marker (battle `12350`, T319),
each owns its pending screen, instance, arena actors, HP/target/cooldown,
results, payout, quest credit and return pose; a third late joiner sees only the
static marker; and one player's malformed packet or mid-fight disconnect leaves
the other fighting.

**No production file changed.** The diff is the test file and this note.

**Correction after the F396 review (this revision).** The original note claimed
the field battles were only "validated one player at a time". That was false,
and so was the claim that the copied start/fight/economy helpers could not be
cut. The two-session model was already covered before this suite:

- `tests/sheep_watch_dungeon.rs:858-928` opens the same Sheep Watch marker with
  two gateways, enters both, wins with the first through real 36/10 attacks,
  asserts the second's economy/run/save are unchanged, disconnects the first,
  wins with the second and asserts the first is unpaid.
- `tests/bixie_hive_dungeon.rs::a_second_player_runs_its_own_instance_and_is_paid_once`
  (lines 1029-1098) runs two sessions independently and pays each once.
- `tests/bixie_hive_dungeon.rs::a_second_session_sees_the_marker_not_the_arena`
  (lines 1251-1306) proves a second and a late session receive only the static
  marker, never the arena actors.
- `tests/brawler_mongo_chain.rs::two_players_win_separately_and_credit_only_themselves`
  (lines 1721-1773) proves per-player quest credit for a marker battle.

The suite now keeps only the assertions those do not make, and it reuses the
canonical `tests/common/field_battle_fixture.rs` helpers that landed before its
parent (F388, `a3d3075`) instead of re-declaring them. Deleted local copies:
`click_marker`, `go_and_enter`, `running_instance`, `strike_once` (the one
remaining hit is inlined in test 6), `fight_to_win`, `results_lifecycle`,
`won_flag`, `Economy`, `economy`, `assert_payout`, `add_npc_packets`,
`reply_bytes`, `enemy_guids`, and the hard-coded `MARKER`, `MARKER_GUID`,
`ARENA_ZONE`, `ARENA_ARRIVAL` and `FIELD_BATTLE_JOB_XP`. The row now supplies
the marker GUID/pose and arena zone (`marker_of`), `open_battle` pins the
41/114 start screen byte-for-byte, `enter_battle` pins each arena actor's 35/2
and the running 41/114 refresh, `fight_to_win` walks to the row's
`zone.position`, and `assert_payout` takes the active profile from the snapshot.
The six test names are unchanged (they are in `protected-pass.txt`).

The six tests:

1. `two_players_start_the_same_marker_with_independent_encounters` - A and B
   each open their own start screen through `open_battle` (the screen names
   their seeded instances 41 and 108 and matches the row's
   title/icon/description/difficulty at bytes 47..71) and Go through
   `enter_battle` (which pins every row actor's 35/2 and the running refresh).
   A's click/Go changes none of B's snapshot, save payload, position, zone or
   pending screen; B's Go still works after A started; a forged 41/108 with no
   open screen is inert and changes no byte, and an out-of-range Go (A walks
   50 m away) changes no byte, after which A reopens the marker and starts.
   A's and B's active instances stay separate.
2. `a_win_or_loss_in_one_encounter_does_not_affect_the_other` - both sessions
   carry the shipped `Brawler: Delinquent Dilemma` goal. B takes a real hit
   (its enemy HP drops). A wins through the ordinary 36/10 path and is paid and
   credited 2/4; B's snapshot/save/wallet/quest/active encounter are identical
   to the state captured before A's win. B is then knocked out by its own arena
   tick (real enemy damage, `39/18` won=0, `39/47/19`) while A sits on its
   results: the loss pays/credits neither player and does not change A. B
   closes its lost run and returns to B's own pose; A closes its win and
   returns to the marker; A's payout never reaches B.
3. `both_get_their_own_payout_and_return_to_their_own_pose` - A and B start
   with different saved quest counters (1 and 0) and different pre-entry poses
   (marker and marker+1.41 m), both win. A live `realm coins 7` grant during
   the results screen survives A's Close (no old snapshot restored) and never
   reaches B. A's Close returns A to the marker; B stays in its won arena; B's
   Close returns B to B's own pose. Each save carries only its own
   coins/XP/items/quest counters (3 vs 2). Replaying A's Close and A's Go pays
   nothing and does not start B; reloading both through `game_store` +
   `Gateway::load_gameplay` restores each own state with no live encounter.
4. `a_third_late_joiner_sees_no_arena_actors` - a third session entering the
   field at the marker receives exactly one 35/2 AddNpc for the static marker
   (parsed through the production `startup_world::parse_add_npc`), no arena
   actor GUID in any reply byte, and no 41/114 running encounter. Its 26/8
   click opens only its own start screen; its own Go starts its own instance
   and leaves A and B untouched.
5. `one_players_disconnect_or_bad_packet_does_not_stop_the_other` - five
   malformed packets (truncated 26/8, 36/10, 26/42, 41/109 and a header-only
   36/10) are refused for A alone with an empty reply and byte-identical
   snapshot/save. A's mid-fight save/reload (the production reconnect path)
   drops A's run without paying and returns A to A's pre-entry pose. B keeps
   moving, lands a real 36/10 hit and is still fighting; A can start a fresh
   battle afterwards (no stuck pending state). The win/disconnect continuation
   for B is `sheep_watch_dungeon.rs:858-928`, not repeated here.
6. `the_route_uses_no_dev_commands` - a normal-player session (dev tools off,
   `AccountRole::Player`) is refused `realm win` and `realm battle 12350` with
   zero state change, and the same `realm win` is refused mid-fight while the
   encounter stays `Fighting`. The complete start/fight/return path then runs
   through ordinary client requests only (26/8, 41/108, 36/10, 26/42) and the
   real attacks pay the win; every route outcome reports zero developer-command
   denials.

Scope: two or three **in-process** `Gateway` values on the production
`Gateway::handle_at` dispatch. The shared-world fanout after that
(`Server::step`, `world`/`players` interest, `contain`) is owned by the
`osfr_gateway` inline suites (`isolation.rs`, `t020_group_routing.rs`) and is
not claimed here (F396 review finding 4).

## (R) reconstructed rules

- The session-local encounter is this build's reconstructed model: `pending_battle`,
  the open start screen and the instance counter are per `Gameplay`/per
  character save, and the arena is the session's own zone-9600 scene. The Build
  Ledger (2026-10-15) records "Arena battles are still per player" and that the
  world `instance_id` is always 0 while `world::World` is unused; the 41/114
  instance id asserted here is `EncounterState::next_instance_id` from the
  character save, not a world instance. Shared World C11 says the same
  ("Arena state and instance counters are per EncounterEngine"). Retail
  group/world instancing is not recovered and is not added here.
- The test instance seeds 41/108 are (R) test values; a production character
  save starts at `next_instance_id = 1` (`EncounterEngine::load`), so two fresh
  characters commonly share instance 1 in their own saves. The suite seeds
  distinct counters to make "each start packet names its own instance"
  observable without claiming a global instance id.
- Both sessions' arena actors carry the row's static GUIDs (a per-session copy
  of the same authored actor ids). That is the existing field-battle model, not
  a new actor-id namespace.
- The saved quest counters (1 and 0 seeded, +2 Alpha Wolf defeats per win) come
  from T319's `enemies.json`/quest mapping; the shipped goal counts kind
  `930050` and the two Alphas advance it (tests 8/9 of T319).
- Coins/prizes are the existing `field_battles.json` row (25 coins, one wheel
  prize); the 50 job XP is `encounter.rs::BATTLE_JOB_XP` (R, half a rank on the
  local curve), the same engine policy the other field-battle suites assert.
  No tuning was added.

## Threat note (secure-code-guardian)

No production parser, save, reward or role rule was changed; the suite drives
the existing attack surface and asserts the refusals. A hostile client could
send:

- a forged 41/108 Go with no open screen: the server ignores the payload ids
  and starts nothing (test 1: empty reply, byte-identical snapshot/save). With
  an open screen, Go starts only that session's own pending battle; a client
  cannot name another session's encounter/instance, and test 3's cross-Go on B
  after B closed is inert.
- malformed 26/8/36/10/26/42/41/109 bodies: each is a single, non-bundled
  application message, so the gateway drops the handler error for that session
  alone. Test 5 asserts an empty reply and byte-identical snapshot/save for
  every packet, and B keeps fighting. A bundled malformed child still follows
  the existing `contain` session-disconnect rule (unchanged; not exercised
  here because it is `bin/osfr-gateway.rs` session plumbing).
- a replayed Close or Go after a finished run: pays nothing, starts nothing
  (test 3). The pending screen is consumed by the first Go (session-local
  `take_pending_battle`).
- a third session joining the field: receives only the static marker, no arena
  actor GUIDs and no other player's running encounter (test 4); it cannot be
  pulled into another fight. This is the in-process world-entry reply; the
  shared-server fanout is covered by the `osfr_gateway` suites.
- a client-reported result: never used. Rewards are applied only from the
  server-verified 36/10 kills and the arena's own `Lost` tick; test 3 asserts
  exact coin/XP/prize deltas, one prize from the row's pool, and that a live
  coin delta survives Close instead of restoring a snapshot. B's wallet and
  quest counters never move from A's win/Close.
- ids: instance ids come from each character's own save; the suite seeds
  distinct values and never aliases the public-world instance.

## Open gaps / deviations

- Two in-process `Gateway`s, not two UDP sockets: the production path is the
  same `Gateway::handle_at` packet -> gameplay dispatch. The **shared-world
  fanout** (`Server::step`, `world`/`players` interest, `contain`) is not
  exercised here; it is owned by `src/bin/osfr_gateway/isolation.rs` (a
  panicking session ends alone and the other sessions keep stepping) and
  `t020_group_routing.rs` (routing). This suite's independence claims are
  scoped to the session-local encounter, not the world fanout.
- No native client run (out of scope); no full-suite run (the integrator does
  it).
- The exact instance values 41/108 are test-seeded per-save counters, not
  recovered production ids; production characters start at 1.
- The `Lost` results path is now driven (test 2, arena tick). The `realm retry`
  / 41/122 revive after a loss is not driven here; `brawler_mongo_chain`
  (`a_loss_or_retry_does_not_credit_the_completion`) owns it.
- The Shared World design note proposes a future per-run arena/instance
  coordinator (lead-only). This suite deliberately pins today's per-session
  model, so when that coordinator lands these tests become the migration
  acceptance surface and will need to be revisited; that is a design change,
  not a defect found here.
- The Build Ledger's native two-client check is still pending; no native client
  was run for this slice.
