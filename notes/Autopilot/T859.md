# T859: serve card-face art from the player's own client (2026-10-28)

## Why

T855 found the 15 starter cards' faces are `images/card/<id>.jpg` in the client's TCG
asset-delivery cache set (`assets/assetpack000_manifest.txt` over
`assets/assetpack000W_*.pack`), and that the card window never asks for them, so the
sprite draws `image_placeholder.png`. The lead's decision is to serve the player's own
files, never to ship client art.

## Bottom line

1. **The route is implemented and tested.** The harness (`scripts/asset_delivery.py`,
   `scripts/run-local-baseline.py`) and, as a separate patch, the launcher's responder
   (`notes/Autopilot/T859-launcher.patch`, applied in `../lab/tmp/launcher-public`) now
   announce the client's own pack rows the pack actually holds and serve those bytes at
   the existing `<bucket>/<name>?<crc>` route. A row is offered only when it appears in
   the client's own `assets/assetpack000_manifest.txt` **and** the client's own pack holds
   that exact name **and** the row's CRC equals the pack entry's CRC. Nothing is invented.
2. **Blocking fact for the native check: the supplied client holds the bytes for only
   one of the 15 starter faces.** `assets/assetpack000W_000.pack` (64,094,605 bytes, the
   same size the preserved `OSFR.Client.zip` lists) contains 2,128 of the manifest's
   9,756 rows: 72 of the 1,423 `images/card/*` rows, and of the 15 starter ids only
   `100009956` (Star-Throwing Ninja, 23,315 bytes, CRC 1,239,448,507). The other 14 faces
   existed only on the retail TCG asset server and are in no preserved local source
   (checked: the client tree, the original archive's pack, `../lab/extracted/client-assets`,
   `../lab/references/TCG-Files`, `../lab/references/cdn-mirror-20261027`,
   `../lab/references/asset-cache/http-raw`). The acceptance "Collection shows art for the
   starter cards" therefore cannot be met for 14 of 15 from the player's files; that is a
   lead decision, not something this route can fix.
3. **Second open item (R):** the card window's own delivery (`AssetDelivery::IndirectLoader`
   in the TCG DLL) takes its manifest from a **compiled** base URL, which production sets to
   the retail patch host, not from `IndirectServerAddress`. The merged manifest is still
   the only reply the harness can give and is what the game's own `AssetDeliveryIndirect`
   consumes, but a native run is needed to prove the card sprite's loader reads it. T855 §4
   assumed the harness `/manifest.crc` replaces the card loader's index; the DLL code does
   not support that for the card loader (IDA wins over that note).

## Client evidence (all addresses are `FreeRealmsTCG.dll`, image base 0x10000000, read from
`../lab/working/ida/tcg/FreeRealmsTCG.dll.asm`, input sha256 `22F0E8F9…`)

- **Card art path builder 0x1041C080** (neighbours assert `.\graphicsitems\zpcardsprite.cpp`):
  playable kinds build `:/images/card/<id>.jpg` (`QString` 0xA1... at asm line 1956170),
  pod ids map to `:/images/pod/<id>.png`, and the check below decides whether that path or
  the placeholder is returned. The `> 0x5FA74E0` (100,300,000) branch retries
  `id - 0x493E0` (the +300,000 hero ids).
- **Manager check 0x102B44E0** walks `WAAssetManager`'s provider vector and calls provider
  vtable +0x30. The manager (ctor **0x102B61D0**, global getter **0x102B6310**) registers
  `WAFileAssetLoader` (its `has` is `QFile::exists`, 0x102B2FA0) and `WASOEAssetLoader`.
- **`WASOEAssetLoader` ctor 0x102B4A30** creates `AssetDelivery::IndirectLoader`
  (**0x10143B20**) with folder `assets`, set `assetpack000`, and the base URL in
  `dword_108038FC`; it also creates `WASOEAssetLoaderHandler` (0x102B6370, pushes an asset
  into the manager by `:/<path>`) and starts a timer. Its `has` is **0x102B56D0**
  (`QString::mid(2)` = strip `:/`, then delivery vtable +0x3C) and its `load` is
  **0x102B5BC0** (vtable +0x3C then +0x40 = local pack; else request +0x20).
- **`dword_108038FC`** is written only in **0x10218DF0**, from the TCG command line's
  `--realm=` environment switch (`loc_10219C50`, switch cases at 0x10219C63..0x10219D0A).
  Production (the default, and the MMO client passes no `--realm=`) selects
  `http://fr.patch.station.sony.com/patch/freerealmstcg/live/assets/` (string at asm line
  2963479). The `--host=fr` argument maps a *game* id, not the asset base.
- **`IndirectLoader::Initialize` 0x10140150**: requires the base to start with `http://`
  (RemoteDelivery, 0x1013C960) or `file://` (FileRemoteDelivery, 0x100D3A70), else logs
  `Invalid host URL specified "%s"`; opens local pack groups `%s/%s` = `assets/assetpack000`
  and `%s/%sW` = `assets/assetpack000W` (the shipped `assets/assetpack000W_000.pack`), then
  calls delivery vtable +8 = **0x100D2AA0**, which requests `manifest.crc`.
- **Manifest CRC handler 0x101429B0**: builds `%s/%s_manifest.txt` when a folder is set
  (`assets/assetpack000_manifest.txt`), reads it, and compares its CRC to the received one;
  on a match it parses that local file (**0x10142660**). On a mismatch the delivery
  downloads `manifest.txt.z`/`manifest.bin` (**0x10142B90** builds `%s/%s_manifest.%s`,
  verifies the received CRC, writes the file, parses it). The manifest row form is
  `name,crc,wire_length` (the same form the harness already serves for `Assets_manifest.txt`).
- **Name lookup 0x101404F0**: exact name first, then `name + ".z"`; the second lookup sets
  the compressed flag. `has` **0x10141E60**, local-pack load **0x10141F30**, async remote
  fetch **0x10141830** → **0x10141F30**-adjacent request builder `%03u/%s` (0x100D3940).
  This is why announcing a row raw (`images/card/<id>.jpg`) is sufficient: the exact-name
  lookup finds it and the pack load succeeds locally.
- **The game's own delivery is a different class**: `AssetManagement::AssetDeliveryIndirect`
  (EXE strings 0x01885060 `AssetDeliveryIndirect::GetAssetData failed, asset not in
  manifest: %s`, 0x018851b4/0x018851c4 `%s_manifest.txt`, 0x018858a0 `manifest.crc`,
  0x01885918 `%03u/%s`, 0x01885920 `manifest.txt.z`). The TCG UI's preload list
  `Resources/TradingCardAssets.txt` is requested through it (run log
  `client-baseline-20261028T030110Z/Logs/FreeRealms.log`, line 570: `asset not in
  manifest: TradingCardAssets.txt`); it contains `.lst`/`.dds` UI assets only, no
  `images/card/*` (the extracted 108,547-entry client catalog has no `.lst`/`.txt` naming
  `images/card` or `images/pod`).
- **The native runs show no card-art request.** Run
  `client-baseline-20261028T030110Z` (`manifest.json` `asset_http_counts`): `/manifest.crc`
  x1, `/tcg/manifest.crc` x1, world/housing assets; no `images/card/*`. A miss in the
  delivery index is silent (the sprite falls back without an AssetFailure row), matching
  the DLL's `has`-before-request order.
- **T849's `Resources/TradingCardAssets.txt` is not a starter-face list.** Its 151 `.dds`
  are the loot-art id range (100020285…, see T855 §2's RCC loot ids) plus 39 `thumb_*` and
  45 `.lst` UI lists; it names no `images/card/*`. The 15 starter ids appear nowhere else
  in the extracted client catalog (108,547 rows) other than `images/card/100009956.jpg`.
- **Pack format**: big-endian directory blocks (absolute next-block offset, entry count,
  then length-prefixed name + BE offset/size/crc32), exactly what `osfr-tools catalog`
  already reads (`prototype/osfr-tools/src/main.rs` `read_index`). The new readers mirror
  that, with bounds, cycle and name checks.

## What changed

- `scripts/asset_delivery.py` (+~120 lines): a `ClientPack` source built from the client's
  own `assets/assetpack000_manifest.txt` + `assets/assetpack000W_*.pack`
  (`read_pack_index`, `PackSource`, `_pack_path`), merged into the served manifest in raw
  form, served at the existing per-file route only for allowlisted names with the
  announced CRC, plus a `.z` envelope for a `.z` request. `.z` rows are announced raw
  because the pack holds raw bytes; the exact-name lookup (0x101404F0) finds them.
- `scripts/run-local-baseline.py` (+3 net lines): passes the run's client copy to
  `AssetDelivery`, announces the merged manifest CRC and body, and records
  `asset_manifest_client_pack_rows` in the run manifest.
- `tests/test_asset_delivery.py` (+~110 lines, `ClientPackTests`): only rows the pack
  holds with a matching CRC are offered; raw and `.z` serving; refusals (unknown name,
  wrong CRC row, in-pack-not-in-manifest, wrong query CRC, `..`, `%2e%2e`, `\`, non-numeric
  bucket) with a before/after check that refusals change nothing; corrupted pack bytes are
  never delivered; a missing client leaves the old behaviour unchanged; the pack reader
  refuses cycles and truncated packs.
- `notes/Autopilot/T859-launcher.patch`: the matching change for the launcher's own repo
  (`../lab/tmp/launcher-public`): `src/assets.rs` serves `/manifest.txt.z`, merges the

- No Rust server file changed; no hub file changed (gameplay.rs, bin/osfr-gateway.rs,

## (R) rules and open gaps

- (R) The card window's `WASOEAssetLoader` reads the harness-announced manifest: its own
  base URL is compiled (retail patch host) and the shared client's `/manifest.crc` is the
  game delivery's. The code says the reply that makes a row resolve is a manifest row plus
  the per-file fetch; only a native run can confirm which delivery the sprite ends up
  reading. The merged manifest is a superset of the client's own, so it cannot remove a
  row the client already knew.
- (R) 14 of the 15 starter faces are not in the supplied client (counts above). If the
  lead wants those faces, the options are a preserved retail TCG asset source (none in
  this lab from the checked places) or accepting placeholders; serving the player's files
  cannot conjure them.
- Open: the two `.jpg.z` starter rows from T855 (100009957, 100010042) are also absent from
  the pack, so the raw-form rewrite was not exercised against those on real data.
- Open: `TradingCardAssets.txt` itself is still absent from `Assets_manifest.txt` (run
  20261028T030110Z), so the TCG UI preload list fails through the game delivery. It is a
  local `Resources/` file, not a pack row; out of scope here.

## Threat note (secure-code-guardian)

New networked surface is the loopback asset responder (harness `AssetsHandler`, launcher
`Responder` binds `127.0.0.1`). A hostile local process (or any client-side caller) can
send arbitrary request targets. What it can send and why it is refused:

- `images/../../secret`, `..%2f`, `%2e%2e`, backslashes, absolute paths, `C:` paths,
  device names (`CON`, `NUL`, `COM1`), `.`/trailing-space names, control characters, very
  long names: refused by `_pack_path` (Python) / `patch::valid_path` (launcher) before any
  lookup, and the name is never resolved as a filesystem path — the pack entry it selects
  comes from the pack's own directory block.
- A name in the manifest that the pack does not hold, a row whose CRC disagrees with the
  pack entry, or an in-pack name that the manifest does not list: not offered at all.
- A wrong or missing `?crc` query, or a non-numeric bucket: refused, so a stale manifest
  cannot be answered with bytes for a different version.
- Corrupted pack bytes: the harness raises `ValueError`, which `AssetsHandler` catches,
  counts as `<rejected_asset_source>` and answers 404; the launcher returns `None` (404).
- Bounds: pack manifest ≤ 8 MiB (launcher 64 MiB shared limit), one entry ≤ 16 MiB
  (harness ≤ 128 MiB), directory block count bounded, entry offsets bounds-checked, no
  links/hard links, no writes to the client folder. The launcher's new code never
  `unwrap`s client data; the pack index is built once and treated as immutable.
- Client art is never committed: the diff and patch contain names, ids, CRCs and code
  only; the bytes are read from the player's own install at runtime.

## Checklist

1. **A refusal changes nothing.** The new route refuses before reading or caching anything
   (name → allowlist → manifest row → CRC agreement → query CRC). Tests assert that after
   each refusal the row is still not offered and a valid request still serves the same
   bytes (harness `test_pack_requests_outside_the_allowlist_are_refused_and_change_nothing`,
   launcher `launched_client_gets_the_card_art_its_own_pack_holds` missing-target checks).
   No menu, offer, counter, item or cooldown exists on this path.
2. **Rollback covers all state.** No transaction; the pack index and manifest are built
   once at start and never mutated per request. N/A beyond that.
3. **Apply deltas, never restore snapshots.** No inventory/coins/position touched. N/A.
4. **Busy rules are mutual.** No gameplay activity added. N/A.
5. **Every entry path is gated.** One dispatch for every request (`AssetDelivery.get` /
   `body`) and every path applies the allowlist, CRC agreement and query CRC. Tested at
   both responders.
6. **Reachable in production, tested through it.** Harness: `AssetsHandler.do_GET` calls
   `asset_delivery.get` (the tested function) and serves `served_manifest` at
   `/manifest.crc`/`/manifest.txt.z`; the launcher test drives the real TCP responder.
   The native acceptance remains the lead's run.
7. **Survives reconnect.** No session state; the responder is per-run/per-launch. N/A.
8. **Every exit path restores the player.** No player state. N/A.
9. **Economy safety.** No grants, items, coins or rewards; the only new outputs are image
   bytes the player's own install already holds. No client-reported values are trusted:
   CRCs and sizes come from the client's own manifest/pack and must agree.
10. **Wire format matches the client reader exactly.** Manifest CRC body is
    `crc32,len\r\n` (native 0x010a1980 split; 0x0109bd00 compares to
    `%s_manifest.txt`); the manifest envelope is `A1B2C3D4` + BE raw length + zlib
    (reader 0x010ebee0); rows are `name,crc,wire_length` (the client's own
    `assetpack000_manifest.txt` form and the local-manifest reader 0x101429B0); the
    per-file request keeps the existing `%03u/%s?crc` form (0x100D3940). Byte-level tests:
    `test_only_rows_the_pack_holds_with_matching_crc_are_offered` (manifest form/envelope),
    `test_allowlisted_pack_names_are_served_raw_and_compressed`, launcher
    `launched_client_gets_the_card_art_its_own_pack_holds` (envelope and raw body).
11. **Unique ids.** No instance/GUID/lifecycle ids. N/A.
12. **Others see changes.** Local asset responder; nothing broadcast. N/A.
13. **Content works end to end.** The offered rows are exactly the pack's entries
    (2,128/2,128 real-data check) and the served row decompresses to a JPEG; the final
    outcome "face art appears" is the lead's native check and is limited to the one starter
    the client holds (documented above).
14. **Values live in data.** No timeout, window, cap or gameplay value added to code; the
    allowlist is the client's own manifest (data). The two size bounds are safety limits on
    untrusted input, marked `(R)`.
15. **Canaries break production code.** Python canary broke `_add_client_pack`'s CRC
    admission → tests failed; launcher canary removed the query-CRC check → its test
    failed; both reverted and re-run green.
16. **Hands off session plumbing.** No session creation/teardown/transaction/save ordering
    touched.
17. **One player's error never stops the server.** The harness runs the responder in a
    daemon thread and catches `OSError`/`ValueError` per request; the launcher serves each
    connection in its own thread and returns 404 on any failure; no panic path on client
    data (`unwrap` is absent in the new code; `unwrap_or(true)` only refuses on a
    link-check error). No shared-tick code touched.
18. **A type's rules live on the type.** `PackSource` documents "one asset's bytes inside
    the client's own pack"; `PackEntry` documents the same; the module docstring states the
    allowlist and CRC-agreement rule for the merged rows; the merge/announce rule is on
    `_add_client_pack`/`merged_manifest`.
19. **Hot paths stay cheap.** Nothing runs on a tick. A request reads only its own pack
    entry (card faces ~23 KB) and the harness caches the body (64 MiB bounded cache); the
    index is built once (2,128 entries). No per-request full-state copy.
