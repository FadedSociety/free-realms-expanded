## Hash and list behavior

The twelve IString bucket-cleanup functions (008e2710-008e3220) share one body shape. Their outer bound is 0x100 (256) except 008e3220, which uses 0x80 (128). Each visited bucket head is cleared before its chain is drained to null; the positive-count gate is checked before the next bucket, not inside the current chain. Each node's IString vtable is reset and its shared-buffer reference count decremented. Raw bytes at 008e2710 show the final-reference call sets ECX to the IString subobject at node+4, pushes the buffer-header pointer, and calls vtable slot +8; Ghidra's displayed `uVar4` second argument is the stack-cookie value and is not passed. The following container cleanup call uses the container in ECX and pushes the node. Thus 00401d30 is the alignment-0 IString backing-buffer release path, not the container node deallocator. For the particle-manager map, caller 0090eeb0 installs a map whose slot +8 resolves to 008bc550 (alignment 4); for the mesh-manager map, caller 0090f390 installs a map whose slot +8 resolves to 008bca00 (alignment 4). The manager call pseudocode also shows a cookie argument to 008e2710/008e2c90, but their bytes set ECX to the embedded map at manager+0x440 and push no argument. The generic cleanup records therefore describe the verified virtual dispatch instead of treating 00401d30 as the node-free target.

The wrapper at 008e2e50 drains the head at collection+8 through 008cbec0 until empty; that helper uses an XOR-derived bucket index masked with 0x3ff (1024 buckets). At 008e4650, bucket-chain unlink occurs only when the target is found. If traversal reaches null, the function still repairs list links, decrements count, destroys the IString, and dispatches node cleanup, leaving the bucket chain unchanged. Tail append/unlink routines show their head/tail/count fields and link directions directly (008e0b00, 008e4720, 008e47b0). 008e45e0 pops the free-list head and decrements the pool count; when tracking is enabled and the tree lookup places the node in a managed 0x60-stride block, it also decrements the block counter at +0x18.

The repeated-row parser at 008e3c30 first calls 00723600, whose body repairs doubly-linked neighbors and updates head/tail/count without hash buckets. It then reads a signed row count and calls 0072ddb0 with the list in ECX. That helper calls the allocator vtable slot +8 with the list in ECX (its displayed cookie argument is not passed), appends the returned node and leaves it in EAX; the parser moves EAX to ECX and pushes the reader for 008cc760's four bounded u32 reads. The old helper label says HashList_RemoveAll, but the inspected body establishes a linked list only; no hash key or bucket update appears in this path.
