## Threat note (secure-code-guardian)

Attack surface: the item-bar request bodies (42/15, 42/16, 42/6, 36/10 bar 2) and operator-authored
quest JSON.

- The client names only an owned instance id. A hostile client can confirm any id repeatedly; a
  refusal now leaves the pending confirmation (session state) unchanged, but `consume` re-checks
  the live inventory before spending: ownership, non-zero remaining count, alive, recast, and the
  effect row's stack bounds (`EffectStack::admits`). Keeping the pending bypasses none of them.
- The pending is keyed to the checked instance, so a forged/other instance's 42/15 cannot spend
  it; the checked instance's later confirm still has to pass `consume`. The old `take()` also
  let a mismatched confirm destroy the legitimate pending — itself a refusal that changed state,
  which review rule 1 forbids.
- A forged 36/10 bar-2 target guid is still refused by the existing self-target guard (client
  `0x00a35600`); test `forged_target_is_still_refused`.
- The single-use reachability gate closes a "gate says reachable, emitter can never fire" hole in
  operator data. It reads ids only; no client input participates.
- No new grant, coin, trade, reward or session-plumbing path.
