## Verify-first observations

- `learn_job` calls `Profiles::learn` (unlock only) and `grant_starter_outfit`; with an
  empty `starter_items[137]` it reports "Its starter outfit is unavailable, so it
  cannot be selected yet." The 26/13 switch rechecks `has_required_profile_slots(137)`
  before committing and is refused. The test asserts both.
- `character_eligibility` supplies only the **active** profile to
  `CharacterEligibility`, so a `job` gate on 137 could never be met after a trainer
  unlock; removing the gate is the smallest reachable route without private content.
- The reward is still `job_xp: {"137": 25}`. A paid turn-in therefore requires 137 to
  be unlocked: `rewards::apply_grant` (base) refuses a locked profile, and F249's
  `locked_job_profile` turns that into a no-grant refusal with the pending screen
  released. No test here takes that path because this worktree predates F249.
- The catch event is still the server's `FinishMinigame { 599 }` from
  `fishing_service::settle_catch`; the two forged 39 forms now carry the real 599 id,
  so they would match the objective if a client frame ever reached `npc_minigame_win`.
- `npc_minigame_win` only scans the *replies* the server produced after a paid catch;
  a client 39/18 or 39/14 never enters that helper. The forged-frame test proves the
  persisted state is byte-identical.

## Security threat note (secure-code-guardian)

- Attack surface: a hostile client can send 26/8, 26/10, 26/6, 49/2, 49/14,
  39/5, 39/6, 41/109 and 138/2/6/7/14 at any time. F270 adds no parser, selector,
  packet family, objective kind or client-supplied quantity. The only behaviour
  change is a content offer gate: 3070003/3070004 are no longer restricted to the
  active 137 profile.
- Why that is safe: the offer still comes only from Reed's server-side 26/8 -> 26/10
  -> 26/6 -> 49/1 path; 49/2 is accepted only for an offered quest and rechecks the
  remaining requirements (none here); the 49/13 end screen is opened only by the
  server's own Talk objective completion; 49/14 needs that pending screen and the
  per-character grant key. A forged 49/2/49/14, a wrong in-range NPC and replays
  leave the snapshot byte-identical (asserted).
- Reward profile: the content map names profile 137 and `apply_grant` only grants XP
  to an unlocked profile. On the autopilot tip F249's `rewards::locked_job_profile`
  refuses the turn-in without a grant (and releases the pending screen) when 137 is
  locked, so a character who accepts before learning cannot receive XP. In this
  worktree (before F249) the same state is an `InvalidData` error and the tests never
  take it; this task must land on the F249 tip, which it does.
- Client-reported results are still not authority: forged 138/14 is rejected as an
  unknown fishing sub-opcode; forged 39/18 and 39/14 carry the real 599 id and change
  nothing because `npc_minigame_win` only inspects server-generated replies after a
  paid catch. The catch count/items/coins come from `settle_catch`.
- Busy rules are the existing `Occupation::Fishing` table; an active round refuses
  Reed's menu (asserted), and the chapter is only playable after 39/6/41/109.
- No save file is written directly; the tests use the existing typed `GameplayState`
  snapshots, and production writes stay in `character_store::replace_bytes`.
