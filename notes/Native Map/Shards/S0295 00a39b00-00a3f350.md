## Review corrections and open questions

- 00a3a1a0 adjusts `this` to +0x30, destroys the embedded profile-item map, then conditionally frees the `ClientProfileData` node. The node type follows constructor/layout helpers 00a3a070/00a3a140; no direct caller is recorded, and map erase 00a3a4b0 uses the separate aligned-free hook 00a39e50. Loader 00a3a580 checks reader errors only at each loop's start: a failing row is still inserted/parsed, and a final-row error returns with the error flag set and a possibly partial table.
- 00a3bb00 is called by map erase 00a3c130 and scalar-delete cleanup 00a3c090, not assignment helpers. It releases/nulls the member only when the pointer is non-null and `DAT_01be1090` is nonzero.
- Cookie-bearing decompiler arguments were checked against bytes: 00a3a020 and 00a3a0f0 add 0x30 to ECX before calling 008ea780, with no stack argument; 00a3a710 forwards the original ECX to 00a3a6a0; 00a3a820 forwards ECX to 00a3a760 and restores it in EAX. The owner of 00a3a0f0 has no recorded caller or direct RTTI anchor, so its record is neutral and speculative.
- At 00a3dca0, Ghidra renders the `0089adc0` constructor call with a cookie-derived pseudo-argument. The bytes show the real receiver is the local packet object in ECX; the routine initializes that wrapper, calls send helper 00925640, resets its vtable to `ClientGateway::BasePacket::vftable`, saves/restores the send result, and then calls 00894560 solely to destroy the temporary byte array. The item-definition label is supported by caller 00a3ddd0, so the function name remains generic.
- Set vtable thunks 00a3c580/00a3c590 add 0x0c to ECX before jumping to 008f37a0/008f3810. In particular, 00a3c590 is not itself a node-free routine. Buffer hook 00a3e760 takes two stack arguments, uses the pointer, ignores the other, calls free with alignment 4, and returns with `ret 8`. Copy constructor 00a3efb0 copies the three dwords at +0x28..+0x30 between the first and second IString copies.
- Vtable slot 0 at 00a3d870 is the `ClientItemDefinitionManager` cache lookup, not a deleting destructor: its body hashes the id to a bucket and returns the matching +0xb4 key node. Constructor/cleanup shape does not match scalar deletion.
- 00a3b410 returns the matching record's +0x18 field; its Lua caller identifies that use as `GetGroupIdFromItemId`, while the body itself stays generic. 00a3e160 restores `BasePacket::vftable` from an EH cleanup path, but does not establish how many equivalent bodies exist. 00a3e6c0 scales the requested count: ceil(1.25x) below capacity, floor(1.2x) when capacity exceeds requested*4/3, otherwise reuses the buffer.
- Open questions: profile field meanings and header semantics; exact pending-tree type (00a3ac50); the announcement payload catalogue binding; malformed-profile recovery; and original server behavior behind client wire contracts.
