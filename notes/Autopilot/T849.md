# T849: card faces show no art or rules text (research + one-line preload fix, 2026-10-27)

## Why

The native card window logs in, lists the lobby, and its Collection/Deck Builder show the 15 starter
cards x2 with name, cost, type and count, but every card face is the placeholder tree and the rules
text panel is empty. The client requested no card art (`Client/Logs` has no AssetFailure/404 rows).
The task was to find the source of the art and rules text in `FreeRealmsTCG.dll`/the client, say what
the server or install is missing, and implement the smallest fix only if the evidence is clear.

## Bottom line

The 39/16 offer named the wrong asset list. `TradingCardGameAssets.txt` is a real main-pack list
(`Assets_009.pack` entry 3,843, 1,523 bytes) but it contains 77 `TCGNarrator*.mp3` narration files,
not card art. The client's card art list is `TradingCardAssets.txt`: the main client
`Resources/TradingCardAssets.txt` (3,864 bytes) names 45 TCG `.lst` UI lists and 151 `.dds` card
images, and the card manager itself hardcodes that name (`FreeRealms.exe` `00ad4f50`, string at
`00ad4f9e`, loader `00ae7950`). The server now sends `TradingCardAssets.txt` in 39/16.

This is a one-line default change in `card_game.rs`; no protocol layout, save, economy or session
code changed. The native outcome (whether the client now requests and paints the `.dds` cards) is the
lead's next native gate; see the follow-up brief below.

## Client evidence

Addresses are `FreeRealms.exe` virtual addresses for the launcher/card manager and
`FreeRealmsTCG.dll` image addresses (base `0x10000000`) for the card renderer.

### 1. Where a card face's art comes from

- **DLL path builder `sub_1041C080` (0x1041C080).** It asks the card for property `0x12C` (300); when
  present the value is a string used as `%1` in `:/images/card/%1.png`. Otherwise it uses the card id
  as `%1` (`.jpg` for ids above `0x5FA74E0`, after subtracting 300,000 in the 3/4 hundred-thousand
  ranges). The path is checked through the DLL's `WASOEAssetLoader` (`sub_102B6310` returns the
  singleton; `sub_102B44E0` asks its entries), and when the path is absent the function returns
  `:/images/card/image_placeholder.png` — the placeholder tree.
- **Card face loader `sub_1041C6F0` (0x1041C6F0).** It loads the requested image (or the placeholder
  when its `QImage` is null) and hands it to the card widget through `sub_103C0A00`; the text
  properties are added through `sub_1039E7A0`/`sub_1039D880`.
- **The installed `tcg/cards.rcc` cannot paint the starter cards.** The extracted manifest
  (`../lab/content/tcg/rcc-resources.json`) has 414 entries: 403 `.png` (201 numeric art ids —
  mostly virtual-reward/booster icons — plus templates, icons, boosters, `image_placeholder.png`,
  and 11 fonts) and no `.jpg`. The starter ids `1000099xx`/`1000100xx` have no
  `images/card/<id>.png`; `100011276` (an art-linked id) is a virtual-reward icon, not a playable
  card face. The fallback in `sub_1041C080` therefore returns the tree for every starter card.
- **The card art list is `Resources/TradingCardAssets.txt`.** Counted from the client copy:
  196 lines, 45 `.lst`, 151 `.dds` (39 `thumb_*`). The TCG pack has a **different** file with the
  same name: `AssetsTcgW_000.pack` entry 0, 1,295 bytes, whose 56 lines are `tcg\...` patch paths
  (`../lab/content/tcg/raw/pack_00/000000.txt`). The old 39/16 value
  `TradingCardGameAssets.txt` is `Assets_009.pack` entry 3,843, 1,523 bytes, 77 `.mp3` narration
  names (`../lab/extracted/client-assets/pack_21/003843.txt`).
- **Client flow.** `009bfdb0` handles 39/16 (readers `009bfc50`, `009b2340`, `009bdd70`), starts the
  mini-game loader `009beb70` (`MiniGame:PlayerStartMiniGame`) for a non-empty preload name, and the
  loader's state machine is `009bf5e0`. The preload string is stored at info `+0x270` and read as a
  length-prefixed string (`009bdd70`; helper `00894b10`). `00ad4f50` state 1 then loads
  `TradingCardAssets.txt` (`00ad4f9e`) through `00ae7950` (`00ae7950` calls `00402ce0` with the name
  and `00ae6ab0` to start the load); state 2 sends 39/37 (`009bf590`) once the list is loaded.
- **Native evidence for the gap.** In the 2026-10-27 23:06Z run
  (`../lab/runs/client-baseline-20261027T230650Z/manifest.json`), the asset server answered
  `/tcg/manifest.crc` 200 once and the housing assets (200/404), but there is **no**
  `/tcg/TradingCardAssets.txt` or `.dds` card-art request. That is consistent with the 39/16
  preload naming the narration list: the card art list was never the list the loader loaded.

### 2. Where the rules text comes from

- **Display lookup `sub_100372A0` (0x100372A0).** This property-to-text dispatcher builds
  `title_%d` for property 1, `game_text_%d` for property `0x276` (630), and `lore_%d` for property
  `0x283` (643) from the card's display id (`[esi+8]`, adjusted by removing the encoded 100M digit
  group where present), then resolves it through the client's translation manager
  (`sub_1029D510` -> `sub_1023B050`; the translator singleton is `sub_103D1980`). Property `0x12C`
  (300) is the art-name string above.
- **The card definition itself carries the text.** `tcg/data/archetypes/index.dat` /
  `storage.dat` (zlib rows; 1,391 index rows) decode the card record. The record begins with the
  `PersistentComponent` class (0x15FA4, version 7) and carries the display strings in `Expression`
  objects (classes 0x23/0x25/0x26; `../lab/content/tcg/analysis/dll-registration.tsv`). Example:
  the record for `100009948` contains `[Spend 0] >> My foe attacks.` and
  `[Y]: Ready one of my allies.`; `100009946` ("Soaring Eagle") has the name and the flavor text
  only. The card's rules text is therefore in the card definition, not generated by the server.
- **The TCG locale `tcg/locale/en_us_data.dat` also has the strings.** The `.dir` header says
  `## Count: 5092`; rows are `<numeric id>\tucdt\t<text>`. "Soaring Eagle" is id 3559688322,
  "Here one moment, a spot in the sky the next." is 2917486685, "Lazy Guard" is 1927863588. The
  locale ids are not the card ids; the client's localizer maps the built `title_%d`/`game_text_%d`
  key to the numeric row. The exact hash/lookup in `sub_1023B050` was not decoded (R).
- **`msgStorageen`/`ruleStorage` are not the card face's text.** They are the engine's message and
  rule stores: `sub_101C5D70` loads `ruleStorage`/`ruleIndex` (`sub_101C5FF0` rebuilds them), and
  `sub_10182410`/`sub_10181650` load `msgIndexen`/`msgStorageen`. A byte search of
  `msgStorageen.dat` (102,000 bytes) and `ruleStorage.dat` (844,325 bytes) found none of the card
  display strings ("Soaring Eagle", "Here one moment", "[Spend 0]"); they hold the engine's
  messages/rules, not the UI card text. The card's `Expression` objects reference rule/action
  objects; they do not feed the collection text panel.
- **(R) why the panel was empty.** The panel is filled through the card's text property/asset list
  and the list also carries `TC_toolTipDB.lst` and the card images. With the narration list named
  in 39/16, the card art list (and its `.lst`/`.dds` set) was not loaded, so the card renderer fell
  back to the placeholder face and left the text area empty. The next native run distinguishes
  "art list only" from "locale key" (see below).

### 3. What our server or install is missing

- The server was naming the **narration audio list** in 39/16 instead of the client's card art list.
  This is the one small server change made.
- The card art `.dds` files themselves are not in the installed main pack/CDN scan we checked:
  `100020285..`/`100021407..`/`thumb_*` names are absent from
  `../lab/manifests/rust-asset-catalog.tsv`, `AssetsW_000.pack`'s manifest,
  `../lab/references/cdn-mirror-20261027` and
  `../lab/reports/missing-art-20261027/fetch-results.csv`. If the next native run requests them and
  the asset server 404s, the lead must supply/serve the card art files (client assets are not
  committed to this repository). This is the main open gap.
- No 81/83-86 field is missing for this symptom: the 15 starter cards, their names, cost, type and
  counts display correctly from T825's sync and the client's local records. `CollectionItem`
  (class 52 v7) is not sent in the sync and carries no art field; the `InstanceID` series/copies
  match the client's `default.cln`. The launch block's `preload_file` was the only wire value that
  named the wrong list. The shipped `data/content/card_game.json` has no launch block, so no
  content edit is needed; a private native package that explicitly sets the old name must omit it or
  use `TradingCardAssets.txt`.

## Threat note (secure-code-guardian)

The changed value is server data in the 39/16 offer. A client cannot set it; the content loader
bounds `launch.preload_file` to 1..=64 ASCII bytes and the default is a constant. A hostile client
can still send 39/5/39/37/39/6 as before; the run/ticket gates (T782/T795) are unchanged, a refused
request changes nothing, and no save, item, coin or reward path is touched. The preload name makes
the client's asset loader fetch assets; the asset server must keep its existing path confinement
(T795's harness serves only the TCG manifest from the run copy). No new network surface, secret or
client-controlled path was added. Client art/packs are not committed.
