Their ownership/identity remains `unknown`; address adjacency is not used to label either.
- The array cleanups at `00a5da90`, `00a5dcc0`, and `00a60940` run only when the global manager pointer at +0x16c is non-null; pointer releases happen twice only when manager field +8 is nonzero, while counts are reset regardless. The meaning of that manager field remains unknown. The owner class for aggregate cleanup `00a61dd0` and the embedded-array owner cleaned by `00a5eaa0` is not exposed by RTTI. Template/member names are not promoted to the enclosing class.
- The capacity allocators `00a5ddf0` and `00a61480` use the same policy: with flag clear they grow to floor(5*request/4) when below request, reuse up to floor(4*request/3), and choose floor(6*request/5) above that threshold (which may shrink); with flag set they reuse only on exact capacity equality, return null for zero request, otherwise allocate the requested count. The exact meanings of several decoded structure fields, transformed handles, list element types, state byte toggles, and sentinels remain unknown. No emulated server behavior is treated as original SOE server logic.
- No contradictory vault note was found for this shard. The only community context queried was the local wiki page `Pirate's Plunder`; it describes the player-facing game but does not resolve these binary fields or server semantics.
