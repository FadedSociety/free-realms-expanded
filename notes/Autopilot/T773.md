# T773: town greeters send their explainer pages

Native check 2026-10-26 22:07Z (binaries 6a3172b5): a town greeter such as Snowpetal/Frostpetal in
Snowhill says her welcome line but not the how-to text that explains the town's game. The greeting
was already wired (W126/T280/T299: `NpcRecord.greeting_string_id` -> `DialogueContext.body_string_id`
-> the 26/3 body), and Frostpetal's recovered line literally says "select whatever option you want
to learn about" while the dialog offered only Goodbye. This change gives a greeter a data-driven list
of explainer pages: one extra 26/3 response row per page, and a click re-renders the same dialog with
that page's body.

## Reconstructed rules (R)

- **The greeter -> page binding is reconstructed.** The original server's NPC scripts did not ship
  (`FreeRealms-Legacy` keeps only `welcomer.lua`; Sanctuary keeps a proximity-greeting script for
  Frostpetal), so no original tips list exists. The page *text* is the client's own; selecting which
  pages a greeter offers is this server's judgement, kept in data and marked `(R)` in each row's
  `field_sources`.
- **Response ids.** 300 is the Goodbye row and 301 the quest-offer row (`npc_interaction`), so the
  tips rows start at 310 and run in array order. The five-dword row layout (`[id, 17, text, 0, 18]`)
  is the recovered `AddResponseNode` tuple (`notes/Research/Pieces/071`).
- **Replaying the dialog.** A selected page is answered with a second 26/3 that keeps the same rows,
  so the player can read another page or pick Goodbye. The client has no dialog-phase id; no capture
  of the original multi-page greeter exists, so this flow is reconstructed (the reader and handler
  above prove the client renders a second 26/3).
- **Bounds.** Four pages: four rows plus Goodbye is the client window's five buttons. A quest-offer
  dialog shows the offer row instead of the pages (that window draws its own bubble).

## Threat note (secure-code-guardian)

Attack surface is the client-chosen 26/6 dialogue row, which is new only in that it can now name an
explainer id. A hostile client can send:

- **Any i32 as the row.** `NpcInteraction::explainer_page` only matches ids the open dialogue itself
  sent (`ActiveInteraction.topics`, filled by `select()` from content). An unoffered value returns
  `None`, the router answers the ordinary 26/4 close, and nothing else happens: no body id of the
  client's choosing is echoed back, no item/coin/quest/position changes.
- **An explainer id without talking first.** With no active interaction there are no topics, so the
  same ordinary close; the new test drives this on a fresh `Gameplay` and asserts the saved state is
  unchanged.
- **A different NPC's explainer id.** The ids come from the record of the NPC whose menu is open, so
  another greeter's page is not reachable through this dialogue.
- **Malformed 26/3/26/6 lengths.** Unchanged parsers: 26/6 is exactly 8 bytes with the family header,
  content is loaded once and `validate_npc` refuses a zero id or more than four pages, so a bad
  content package fails the world load instead of sending junk to the client.
- **Flooding the row.** Each accepted row costs one 26/3 encode (93 + 20*n bytes) and no save, no
  coin/item, no tick work; the existing per-account packet limits are unchanged.

No secrets, no client files, no external text: every page id is a stock locale key.

## Checklist

1. **A refusal changes nothing.** `a_refused_explainer_row_changes_nothing_and_keeps_the_npc_usable`
   snapshots `Gameplay::state()` (inventory, quests, profiles, ...), sends an unoffered row
   (`i32::MAX`), asserts the close-only reply and an identical snapshot, then Talks again and gets the
   greeting. A row sent with no open dialogue is likewise close-only with an identical snapshot. No
   counter, offer, item or cooldown exists on this path.
2. **Rollback covers all state.** The only new state is `ActiveInteraction.topics`, inside the cloned
   `NpcInteraction`; `Gameplay` already stages a clone per request and rolls it back on `Err`. No
   `Rc`/`Arc` side table was added (the content table stays immutable behind the existing `Arc`).
3. **Apply deltas, never restore snapshots.** N/A: the feature pays nothing and restores nothing; the
   rewrite only sends a different locale id.
4. **Busy rules are mutual.** N/A: no new activity. The existing `busy_interaction_refusal` still
   gates every 26/8/26/10 before the dialog, and nothing here starts an activity.
5. **Every entry path is gated.** The graph shows one player-facing greeter path
   (`talk_to_npc` -> `dialogue_packet_with`); the opening scene and the dev command build contexts
   with no topics. Range/zone still checked by `NpcInteraction::interact`/`select` (and re-checked by
   `explainer_page`'s reliance on the open interaction); range is proven by the real-path test
   standing on the NPC's own position.
6. **Reachable in production, tested through it.** The suite drives `Gameplay::handle_in_world`
   (26/8 -> 26/10 -> 26/3 -> 26/6 -> 26/3) and the `NpcInteraction` service the router calls; it does
   not call `dialogue_packet_with` directly.
7. **Survives reconnect.** N/A: nothing persists; the pages are static content and the dialog is
   session state. A reconnect re-reads the same rows (the suite reads them from content).
8. **Every exit path restores the player.** Goodbye, close (26/4), a refused row and a fresh Talk all
   leave the character free with no stuck state: `close_dialogue`/`consume_active` clear the
   interaction (and its topics), and the test Talks again after each.
9. **Economy safety.** No coins, items, XP or rewards. The server sends only content ids; a client
   cannot choose a body id.
10. **Wire format matches the reader.** No new packet shape: the existing five-dword 26/3 row carries
    `[id, 17, text, 0, 18]`, the same layout as Goodbye, and the 26/6 i32 is the recovered reader's
    field (`009f5890`). The suite decodes with the production `decode_dialogue_26_3` and pins the ids.
11. **Unique ids.** No instance/GUID created. Response ids are unique within one dialog (310..313) and
    disjoint from Goodbye 300 and quest 301.
12. **Others see changes.** N/A: only the clicking player's dialog; no actor, outfit, mount or job
    change, so no visibility broadcast applies.
13. **Content works end to end.** The test asserts the greeting body, the four/two page rows, each
    page body after a click, and that Goodbye still closes; the final outcome (the body id the client
    renders) is asserted, not a flag.
14. **Values live in data.** The pages and their order are content (`explainer_topics`); only the
    client protocol bound (4 pages, id base) is code, next to the existing Goodbye/quest ids.
15. **Canaries break production code.** The canary changed the production response-id base and failed
    the real-path suite; it did not manufacture its own failure.
16. **Hands off session plumbing.** No change to session creation, teardown, transactions or save
    ordering.
17. **One player's error never stops the server.** No shared-tick or other-player code; every failure
    path returns `Err` (an `invalid` io error) or the ordinary close, and the new code has no `unwrap`
    on client data (`explain` uses `expect` on a value the same function just computed).
18. **A type's rules live on the type.** `NpcRecord.explainer_topics` carries its doc comment (order
    fixes the response id) beside `greeting_string_id`; `DialogueContext.explainer_topics` and
    `ActiveInteraction.topics` are documented; `validate_npc` owns the bounds.
19. **Hot paths stay cheap.** Per-tick cost 0. Per Talk: one clone of up to four two-u32 topics into
    the cloned interaction. Per page click: one `explainer_page` lookup (linear over <= 4), one 26/3
    encode (93 + 20*n bytes) and no save.
