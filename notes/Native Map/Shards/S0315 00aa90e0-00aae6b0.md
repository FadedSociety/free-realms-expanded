## SoeUtil container instantiations (lib.soeutil)

Every `SoeUtil::Array<T,N,1>` vtable in this range has the same four slots: [0] scalar deleting destructor,
[1] reserve (returns buffer, writes capacity through an out pointer; growth 5/4 up, shrink 6/5 down with a
>4/3 hysteresis), [2] free-storage, [3] a triple-dword swap that tail-dispatches through the other object's
slot +0xc when its flag is set (00aa90e0, 00aa9360, 00aa94c0, 00aa9610, 00aa9c80, 00aa9e20; same shape as the
peer-labelled `SwapTripleAndNotify` at 00b538d0). Dynamic arrays store buffer/size/capacity at +4/+8/+0xc;
the inline-capacity variants (N=32/64/128) keep their storage at +0x10 and their free slot skips that address
(00aa93d0, 00aa9530, 00aa9680, 00aa9cf0, 00aa9e90, plus the two-stage destructors 00aaba70, 00aabbe0, 00aabdb0).

Element types and sizes proven by the allocation constants: `HouseCustomName` 0x34, `HouseKeywordEntry` 8,
`HouseSearchEntry` 0x68/8-aligned, `ExplodingFixture`/`AppPhysics::RayHit`/`AppPhysics::ConvexHit` 0x30/0x10-aligned,
`SoeUtil::StrongType<unsigned __int64,SoeUtilSignatureCharacterGuid,0>` 8-aligned, `unsigned int` 4-aligned.
The same 0x30-byte arrays get a "reserve and move" variant that preserves elements (00aabca0, 00aabe70) and bulk
appenders (00aac620, 00aac680, 00aac7b0).

Node/allocator stubs all route a fixed (size, align) pair through FUN_006fb9c0 -> FUN_006fb860 (virtual slot +4),
else the global manager DAT_01bdf280, else FUN_006fb950(size, align); the free twins call FUN_00401c00(pointer, align).
List/HashList/HashMap instantiations seen: `List<StrongType<unsigned int,SoeUtilSignatureEffectDefinitionId,1>,-1>`
(node 0xc/4), `List<PlayerHousingInstanceInfo,-1>` (node 0xa0/8), `HashListMap<int,IString<char>,16,-1>` (0x20/4),
`HashListMap<int,Array<unsigned int>,10000,-1>` (0x20/4), `HashListMap<int,HousingProcessor::CouplingDisplayData,1024,-1>`
(0x2c/4), `HashMap<int,FixtureByTypeEntry,16,-1>` (0xc0/8), `HashMap<int,FixtureByGroupEntry,16,-1>` (0xb4/4).
00aa9730 initialises 16 inline 0x30-byte nodes for the `HashMap<int,FixtureByTypeEntry,16,16>` built by 00abe6d0.

## Server-contract inferences (hypotheses)

* Placement flow (with the two notes): client saves fixtures on 127/5 and asks names on 127/17; the server answered
  placements with 127/40 (fixture record) plus 127/44 (house info), removals with 127/41 and refusals with 127/53.
  The 94-byte tail of 127/40 and the fields of 127/14/17/57 are still unrecovered; nothing here proves when the server
  chose to send 53 (denial) rather than 40 (acceptance).
* Rating service: 174/20, 6, 7, 8, 12, 16 are client requests; the reply classes are not in this shard. The literal
  `RatingSystem.HousingId` shows the service was reference-data driven, so the original server likely resolved the
  system by name before listing/voting candidates.
* Admin/request packets 127/57 and 127/14 are constructed in 00aca5d0 and 00ac3f40 respectively; 00ac3f40 is a proven
  send path (connected-flag gated), so 127/14 is client-to-server. 127/57's direction is NOT proven.

## Contradictions / corrections for the vault

* Catalogue/note naming: the community catalogue has no `HousingPacketFixtureUpdate` class (the notes use that name);
  the validator-clean wire record for 00aad200 therefore carries opcode 40 with packet=null.
* Note 027 says the snap function quantises x and z only; the decompile agrees, and additionally shows an optional
  local-space rotation through the matrix at +0x40d0 gated by the byte at +0xeedd (not mentioned in the note).
* The rating (base 174) and report (base 68) base opcodes are new relative to the vault notes and the catalogue; the
  catalogue's `net.packet.report` subsystem had exactly one function before this shard.
