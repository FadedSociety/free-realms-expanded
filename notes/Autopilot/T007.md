## Salvage review findings that were fixed

- The salvaged 141/3 join read the queue id from body `+0x14`. IDA says body `+0x0c`
  (details below). The old offset tested a 28-byte request; the real fixed prefix ends
  at 16 body bytes (`u64`, `u32`, queue id).
- `Listings::from_activities` published every portal row. The portal also publishes
  chess (20/66/67) and soccer (42/43/44) rows, which are not matchmaking queues. It now
  filters `Kind::Battle`.
- The salvaged gateway arm `(Some(101), Some(9))` can never match a real 101/9 frame,
  because the u16 at bytes 2..4 also contains the first lobby-type byte. Fixed with the
  one-byte-sub guard.
- The salvaged fuzz seed for 101/9 had a 4-byte header; family 101 is `u16 + u8`,
  so the seed is now 7 bytes with a non-zero lobby type.
- The salvaged tests assumed the old three-battle content fixture. The shipped
  `field_battles.json` has six battles; the routing test now derives its expected ids
  from that file.
- The salvaged handler built `Listings` for every in-world packet. A cheap
  `handles(inner)` family gate (and `inner.len() >= 3`) now returns before allocation.
  The app-fuzz corpus caught a 2-byte 101 cut as an index panic during this refactor;
  the length check and a unit pin were added, and the final fuzz run is green.
- Removed the unused `Listings::rows()` accessor.

## Recovered native facts (IDA)

Addresses are file VAs in the preserved 2014 client.

- 141/1: request body is the 8-byte connection pair; existing codec and preserved
  capture (`notes/Research/Matchmaking Service.md`); client sender `00a7fb90`.
- 141/2 row: reader `00a9d9c0` reads nineteen u32 then two bytes; list reader
  `00a9d4f0`/`00aa1050`; response ctor `00a9f1d0`. Reused, unchanged.
- 141/13 request: `00a83b80` constructs sub-op 13 via `00a7fd30`, sends through
  `00a83670`, which writes the two u16 header words (`00a82a90`) then the 8 bytes at
  packet `+0x10` (`008fb810`). Frame is 12 bytes. The ctor does not initialize the
  8 bytes, so the adapter treats them as opaque and echoes them (R).
- 141/14 reply: ctor `00a9df30`; reader `00a9d590` reads a u64 and two
  `008dab40` arrays (u32 count + u32 values).
- 141/3 join: `00c08e30` stores the selected queue id at packet `+0x24`;
  `00c08cf0` serializes the request subobject at packet `+0x10` through `00c08910`.
  `00c08910` writes the u64 at request `+0x08`, the u32 at `+0x10`, then the queue id
  at `+0x14`; relative to the 4-byte message header the queue id is body `+0x0c`.
  **IDA contradicts the salvaged note's body `+0x14`; IDA wins.**
- 41/129: `00a28d00` -> `00a26890`: 12-byte encounter header plus two u32 = 20 bytes.
- 41/130: ctor `00aa3500`; reader `00aa3640` -> `008d6690` (12-byte header) plus
  `00aa3390` (u32 count). An empty reply is 16 bytes: 41, 130, two zero header words,
  zero count.
- 101/9: `00bb1a40` -> writer `00bb11b0` (header `00bb0e90`) writes u16 family,
  u8 sub, then the u32 lobby type = 7 bytes. The client's receive handler ignores
  sub-ops 5, 9 and 10, so no reply is correct.

## Reconstructed rules (R)

- Only `activity_portal::Kind::Battle` rows are queued. Queue id, name id, description
  id and icon id come from the same field-battle row. Chess and soccer stay in the
  activity portal.
- Each queue is solo: match type 0, min/max players 1, min/max teams 1, zero delay,
  seven zero parameters, zero unused dwords, member-only false. Statistics are two
  zero arrays, one slot per published queue. These are placeholders until queue
  membership exists.

  original locale row was recovered.

- 101/9 is acknowledged by the handler label only; no reply and no state.
- A recognized but malformed request is an `InvalidData` error (rejected per packet),
  not treated as idle and never partially applied.

## Threat note (secure-code-guardian)

- Hostile input: truncated or trailing 141/1, 141/3, 141/13, 41/129 and 101/9 frames;
  a forged 141/3 queue id; an arbitrary 8-byte 141/1/141/13 key; oversized 141 bodies;
  unknown families and subtypes.
- Refusals and bounds: `handles` requires at least three bytes and one of the three
  owned families; each known request has an exact or minimum body prefix; every read
  goes through `get`-checked helpers; `Packet141` caps at 1 MiB; the catalogue caps
  activities and `MAX_WIRE_ROWS` caps counts. No loop consumes a client count without
  a bound.
- A join is pure: the handler takes `&self`, stages no clone, touches no queue, item,
  coin, cooldown or position, and returns only a chat line. The routing test snapshots
  the serialized `GameplayState` before and after every forged id; the canary proves
  the assertion bites.
- The client cannot choose a queue row: rows are derived from server content, and the
  forged queue id is only retained in the refusal value (never used to look up state or
  echo text). The list key is echoed only to the same session.
- No lead-only module was changed; no save, trade, identity or account path is touched.
