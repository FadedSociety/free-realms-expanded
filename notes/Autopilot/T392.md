# T392: a kart race can be left mid-race

## Finding

The original had a mid-race exit, and the server must answer it. The retail racing capture
(`lab/references/OpenSourceFreeRealms/ofrserver/Packets/packets_racing_minigame.pcapng`, decoded by
`lab/reports/analyze-original-minigames.py` into `lab/reports/original-minigame-packets/racing-*`)
holds one race that the player left after lap 1 (laps only 0/1, lap limit 3, no finish frame):

| frame | t (s) | dir | inner bytes | meaning |
|---|---|---|---|---|
| 306 | | S->C | `29006b00 3e000e00 f0030000` | 41/107 EncounterZoneIsReady (encounter 917566, instance 1008) |
| 42898 | 111.135 | C->S | `1a001400` + `29006d00 00000000 f0030000` | 26/20 + **41/109 EncounterParticipantRequestExit** [0, 1008] |
| 42925 | 111.305 | S->C | `29007900 3e000e00 f0030000 00` | **41/121 EncounterParticipantTerminateEncounter** [encounter, instance, flag 0] |
| 42928-42933 | 111.34 | C->S | 141/1, 26/x, `270007 3e000e00 ffffffff ffffffff` (39/7), 41/109 again, 167/1 x2, 26/42 | the client's teardown follow-ups |
| 42954 | ~111.4 | S->C | op31 zone transition (FabledRealms) | back to the world |
| 44446 | 120.956 | S->C | 35/20 flags 1 | racing bit cleared (already recovered, `kart_gateway::player_status`) |

(The 26/20 at 42898 was recovered from the index sha256: `050001040000001a001400`.)

Before this change our server ignored 41/109 during a race (`handle_kart_entry` only exited on
`realm exit`, 26/42 and 39/7), so the client's quit did nothing.

## Client chain (IDA, `ScriptsBase.lua`)

- Exit UI. Race processor `sub_BA6530` state 8 calls `Countdown:Show` (`0x00ba6740` area, string
  `0x01810fa4`). `Countdown:Show` (Lua 37183-37195) sets `HUD.inMiniGame = true` and calls
  `MinigameTitleBar:Show()`. The title bar (`MinigameTitleBar.gfx`, AS2 class
  `minigame.windows.MinigameTitleBar`, decompiled with ffdec into scratch) has `m_ExitButton`:
  first click shows the confirm text (string 103018), second sends `ExitGame` ->
  `MinigameTitleBar:ExitGame` (Lua 49330) -> `Ui.QuitMiniGame()`. For type 10 the bar sits at
  y = -50 (Lua `OnResize`), where the hidden top bar would be. `FRUtilNavigation` stays hidden: the
  native `MiniGame:ShowMiniGameHud` (`sub_9B6AA0`) for type 10 calls only `HUD:hideMain`,
  `GameDock:SlideOffScreen`, `StarCounter:Show`, `RaceStarCounter:Position` (never
  `HUD:showMinigame`). The Escape panel drops options/ticket/bug/teleport for types 10-13
  (Lua `ExitPanel:UpdateSettings`), so Credits + Exit Game is original behaviour.
- `Ui.QuitMiniGame` = `sub_939100`: when the manager (`client+0xf8`) has a current state whose
  `+0x61` (in progress) is clear it sends 39/6 (`sub_9BE8E0`, the crafting quit); otherwise it marks
  the state leaving (`sub_9AD420`, `+0x2b8`), sets `client+0x944` and sends
  EncounterParticipantRequestExitPacket (ctor `008a31a0` -> `008a2fd0(0x6d)`, RTTI at `0x01801690`)
  with first word 0 and second word `*(client+0xc10)`.
- `+0x61` is set to 1 by `sub_9BEB70` ("MiniGame:PlayerStartMiniGame", `*(state+97) = a3`), called
  with `a3 = 1` from the 41/114 dispatcher case (`00aa36c0` case 0x72). Our race logs
  PlayerStartMiniGame (`lab/runs/client-baseline-20261021T073154Z/client/Logs/FreeRealms.log:619`),
  so the race takes the 41/109 branch.
- `client+0xc10` is written by dispatcher `00aa36c0` case 0x6b (41/107) from the packet's second
  word (`*(client+3088) = v50`), i.e. our `kart_gateway::loaded` instance id.
- 41/121 (`00aa36c0` case 0x79, ctor `00a98d40`, body reader `00a9fa00`): flag byte set shows
  "TookTooLong"; then `sub_938FE0(client, 0)` (state `+0x700` is 1 after `sub_9BEB70`, so not the
  39/6 branch) runs Lua `MiniGameHandler:EncounterCancelled` and resets the encounter, and
  `sub_8D2730` -> `sub_9BD240` (HandleMiniGameLeave) drops the local MiniGameState. That is the
  source of the client's follow-ups in the capture. Body reader `00a9ecd0`: encounter header
  (`008d6690`), then one bool byte; 13 bytes in all.

## Exit UI: what the server sends, what hides it (second builder, 2026-10-21)

- The bar is client-driven. `Countdown:Show` runs from the race processor's server-state switch
  (`0x00ba6530`, second jump table; state 8 branch sets local state 8 once, then calls
  `Countdown:Show`/`Countdown:Reset`). The server's part is GameState 33/1 = 8. Retail sent it at
  frame 21972 (t 33.671 s); our race sent the same 8-byte frame `2100010008000000` in the native
  run (`server-trace.jsonl`, 00:36:46.193 trace clock = 01:36:46 client clock). So the server
  already sends what makes the client show the title bar; no extra packet exists to add.
- The only thing that hides it again: `HUD:hideMain` while `HUD.inMiniGame` runs
  `HUD:hideMinigame` -> `MinigameTitleBar:Hide()` (Lua 21470-21490, type ~= 12). Native callers of
  `HUD:hideMain` (string `0x0180ec80`): `MiniGame:ShowMiniGameHud` `sub_9B6AA0` (type 10 arm),
  plus two cutscene/camera paths (`0x00ad11e3`, `sub_AD2D30`, `sub_CC9330`) unrelated to racing.
  `sub_9B6AA0` runs from SetMiniGameReady and from OnGameStarted (`sub_9B9550`, 39/17 via
  `sub_9BF890` case 0x11). In the native run both `ShowMiniGameHud` lines
  (`FreeRealms.log:884`, `:917`) come before `StartHandler:Show` (`:934`), and none follows
  `OnGameStarted` (`:935`). During the race (Go to the 10-minute return) the server sent only
  family 33 frames. No Lua race HUD table (RaceTimer, RaceOrder, RaceItemSlots, RaceBoostBar,
  RaceStarCounter, StarCounter) touches the title bar. So the static chain says the bar should
  show after the countdown, and nothing our server sent hides it. Why the lead's run shows no bar
  stays open (see Open).
- Difference from retail, not changed here: retail's Go (41/108, frame 715) came from the start
  screen before zoning (op31 frame 723) and the server sent 39/23 (frame 15449), never 39/17,
  during that race. Ours shows the start screen inside the loaded track and answers Go with 39/17.

## (R) choices

- (R) A quit is honoured in every active race phase (preparing, countdown, racing, finished but
  closed later), like the existing `realm exit`/39/7 paths. The capture shows only a racing quit.
- (R) Only first word 0 is accepted: both client writers (`00939100`, `009bd240`) send 0; the
  original server's tolerance is unknown.
- 41/121 is sent only for the client quit (capture-backed). The timeout abort and `realm exit` do
  not send it; the flag-1 "TookTooLong" form looks like the original timeout answer, not used here.

## Threat note (secure-code-guardian)

A hostile client can send 41/109 at any time. It only ends its own active race through the
existing exit (no payout: the race is aborted before any claim; the gate cooldown and claim ledger
are untouched). Foreign instance, nonzero first word, replays after the exit and a wrong width
change nothing (a wrong width is an `Err` on a staged clone). It cannot name another player's race
(state is per session) and cannot trigger a reward.
