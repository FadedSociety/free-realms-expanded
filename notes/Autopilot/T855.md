# T855: card face art — each starter card's art id, and why the face is still the placeholder (research, 2026-10-28)

## Why (the symptom, native 2026-10-28 ~03:15Z)

After T849 the Card Duelist Collection shows every starter card's name, cost, type, count and rules
text, but every face is still `image_placeholder.png` (the tree). The card window made no asset
request for card art: the T849 run's asset log has 30 distinct paths / 68 requests, none of them
`images/card/*` or `1000xxxxx.dds`, and its only card-related request is `/tcg/manifest.crc`
(../lab/runs/client-baseline-20261027T230650Z/manifest.json `asset_http_counts`). Brief T855: find
each starter card's art id, check it against `tcg/cards.rcc`, and fix the server side if the art is
there.

**Outcome: the art ids are the 15 archetype ids themselves, and they are absent from `cards.rcc`.**
The same 15 ids' art *is* shipped in the client, but as `images/card/<id>.jpg` in the asset-delivery
cache (`assets/assetpack000W_000.pack`), which is a different set from `cards.rcc`. The card sprite
asks the asset-delivery index for the `.jpg`, the index (as served by our harness) does not list it,
and the sprite silently falls back to the placeholder. No wire field selects card art, so there is
no server-side Rust change to make. The list and the two asset-server options are below; this ends
NEEDS-LEAD per the brief. No `.rs` file changed.

## Bottom line

1. Playable-card faces are **not** RCC images. The card sprite (`zpcardsprite.cpp`, art-path method
   `0x1041C080`) builds `:/images/card/<id>.jpg` for card kinds 5/6 (creature/resource/trick) and
   `:/images/card/<art-name>.png` for the loot/booster kinds 2,3,4,7,8,9. All 15 starters are
   playable cards (kind 5/6), so the client asks for `images/card/<id>.jpg`.
2. `tcg/cards.rcc` holds only loot/booster art: 414 resources = 403 `images/card/*.png` + 11 fonts
   (../lab/content/tcg/rcc-resources.json, source sha256 `4383c893…`). Its 217 numeric image entries
   are 202 unique ids: 12 booster/starter-deck ids (2,900,001…5,900,001) and 190 loot ids
   (100,011,272…100,023,657). None of the 15 starter ids is present, and the RCC holds no `.jpg`.
3. Every one of the 15 starter ids **has** `images/card/<id>.jpg` (two stored `.jpg.z`) in the
   client's asset-delivery cache manifest `assets/assetpack000_manifest.txt` (520,869 bytes, 1,423
   `images/card/*` rows; ../lab/working/OSFR.Client/OSFR Client/assets/). The art exists locally;
   the delivery *index* the card window consults does not know it.
4. `CollectionItem` (class 52 v7) has no art field, and the 83–86 sync does not send one; the sync
   sends `InstanceID` (class 350 v1) = (archetype, series, number). The client's own collection files
   use the same shape and the same archetype ids for these cards, so the wire is not the cause.

## 3. The card sprite's two art paths (client evidence)

All addresses are `FreeRealmsTCG.dll` image addresses (base `0x10000000`), read from the preserved
IDA database (../lab/working/ida/tcg, input sha256 `22F0E8F9…`).

- **Art path builder `0x1041C080`** (a `ZPCardSprite` virtual; its neighbours assert
  `.\graphicsitems\zpcardsprite.cpp`). It switches on **property 797 (0x31D) minus 2**:
  - value 2 (booster): special ids `0x1CFDE1/0x1CFDE8/0x5F61310` map to `booster.png`/`booster_beta.png`/`booster_sample.png`;
    otherwise property 300 (0x12C) as a string, else the card id, then `:/images/card/<x>.png`.
  - values 3, 4, 7, 8, 9 (loot): property 300 string, else the card id, then `:/images/card/<x>.png`.
  - values 5, 6 and anything outside 2..9 (playable cards): property **569 (0x239)**; the pod ids
    `0x5F608FB…0x5F60911` map to `:/images/pod/<id>.png`, everything else to
    `:/images/card/<id>.jpg`.
  Common tail: if the asset loader has the name, return it; else if the card id is **greater than
  `0x5FA74E0` (100,300,000)** retry `:/images/card/<id - 0x493E0>.jpg` (the +300,000 hero ids);
  else return `:/images/card/image_placeholder.png`.
- **The same property 797 selects the frame** in `0x1041ADF0`: values 2–4, 7 and 8 get
  `:/images/card/template_loot.png` (9 too, through a second block that also sets the loot frame);
  the default case (5, 6) gets `template_creature_*` /
  `template_resource_*` / `template_trick_*` after comparing the card's archetype class with
  `0x15FDA/0x15FDB/0x15FDC` (creature/resource/trick), with special-cased hero ids at
  `0x5F63F46`/`0x5FAD326`/`0x5F63FA3`/`0x5FAD383`. So 5/6 are the playable kinds and our 15 cards
  take the `.jpg` branch; the loot cards are 2/3/4/7/8/9. (R) the runtime branch was not captured
  per card; this is read from the two switch tables plus the fact that `cards.rcc` art (`.png`) is
  loot/booster-only.
- **The loader check** is `0x102B44E0(manager, path)`: it walks the manager's provider vector
  (`WAAssetManager` constructor `0x102B61D0`: `WAFileAssetLoader` + `WASOEAssetLoader`) and calls
  provider vtable `+0x30` with the path. `WASOEAssetLoader` is constructed at `0x102B4A30` with the
  literals `assets` / `assetpack000`; its "has" (`0x102B56D0`) strips the leading `:/`, converts to
  the delivery key and asks its `AssetDelivery` instance (vtable `+0x3C`); its load (`0x102B5BC0`)
  uses `+0x38`/`+0x40`. A miss here means `0x1041C080` returns the placeholder **without any HTTP
  request** — an asset that is not in the delivery index is never asked for. That matches the run:
  the only TCG-set request is `/tcg/manifest.crc` (brief) and the main set's `/manifest.crc`.
- **The exe hands assets in** through `WASOEAssetLoaderHandler` (`0x102B6370`), which converts a game
  asset path to `:/<path>` and pushes its bytes into the same manager. The 39/16 preload list (T849,
  `TradingCardAssets.txt`) is the list the exe loads for this; the `.lst` files it names expand to
  TCG UI `img*.dds`/`.gfx` assets (sampled: `TCCW_CollectionCardRenderer.lst` = 27 `img*.dds` plus
  its `.gfx`), not to `images/card/*.jpg`.

## 4. Why our harness never sees the `.jpg`

(R) The card window's `WASOEAssetLoader` uses the asset-delivery cache set `assets/assetpack000*`
(the client's downloaded pack), whose local manifest is `assets/assetpack000_manifest.txt` — it
lists the card art. The asset-delivery client compares its local manifest with the CRC the server
announces for that set. Our harness (`scripts/run-local-baseline.py`) serves
`client/Assets_manifest.txt` (9,479,368 bytes, the UI asset set) at `/manifest.crc`, and
`tcg/AssetsTcg_manifest.txt` (the TCG data/RCC set) at `/tcg/manifest.crc`; the assetpack set's
manifest is never announced, so after the CRC mismatch the card window's delivery index is replaced
with the UI set's manifest, which has no `images/card/*` rows. The 1,423 card rows in its own cache
manifest then cannot be found and the sprite falls back. This is consistent with the run: no
`images/card/*` request and no AssetFailure row (a miss in the index is silent). It is **not**
verified in-client; the native harness is lead-only, and the exact provider that the card window
queries is the one open question.
