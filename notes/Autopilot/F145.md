## Client evidence (IDA)

- **49/2 QuestReply C>S.** Writer `0x00a91630`: copies four bytes from
  `this+0x0c` (quest id) and one byte from `this+0x10` (accept); constructor
  `0x00a86400` stores those two parameters. `npc_interaction.rs:1103`
  (`decode_quest_reply_49_2`) requires exactly that 11-byte packet (u16 family
  49, u32 subtype 2, u32 quest id, u8 flag), rejects length/prefix mismatches,
  `quest_id == 0` and `flag > 1`. The code's native capture example
  `31 00 02 00 00 00 d5 c6 2d 00 01` matches the writer.
- **47/15 quest-limit message S>C.** Dispatcher `0x00a91bf0` case 15 reads one
  body byte: `1` shows `QuestLimitMember`, `2` shows `QuestLimitNonmember` and
  calls `QuestHandler:NotifyNonmemberQuestLimitReached`. Family-47 header reader
  `0x00a8b240` consumes u16 family + u8 subtype, so the existing
  `[47, 0, 15, 1|2]` encoding is exact. Byte test: `tests/quest_engine.rs:385`.
- **49/3 QuestAdd S>C.** Reader `0x00c7cc80` (prefix `0x00c7acd0`, body
  `0x0093c840`) ends with a select bool. The engine only emits the typed
  `QuestAdd` intent; the existing gameplay builder is unchanged, and the
  refusal test asserts no 49/3 prefix is sent.

## Reconstructed rules

- (R) A developer offer's bypass belongs only to its own pending offer. A
  successful accept consumes it; a decline consumes it; a later ordinary offer
  never inherits it. It is deliberately not persisted (dev-only).
- (R) A limit refusal at accept time preserves both the pending offer and any
  developer override, so raising the cap is enough to retry even when the other
  requirements are still unmet.
- (R) A refused accept still sends the 26/4 EndDialog reply used to restore the
  client HUD, but changes no server state and requests no save.

## Security note (secure-code-guardian)

Hostile input on this path: a forged or stale 49/2 with an arbitrary u32 quest
id and accept byte.

- **Malformed:** `decode_quest_reply_49_2` rejects any length other than 11, a
  wrong `[49,0,2,0,0,0]` prefix, id 0 or flag > 1 before the engine sees it.
- **Forged:** `accept` requires `state.pending_offer == Some(quest_id)` and
  `is_enabled` (known definition, non-empty objectives, not disabled). A quest
  the server did not offer returns `Unavailable` with `changed = false`.
- **Stale / newly ineligible:** eligibility is rebuilt from server-owned
  profile/job/membership state before NPC handling
  (`gameplay/npc_quests.rs:107`, called at `gameplay/npc.rs:52`), and `accept`
  re-checks requirements and the active-quest limit at accept time. A refusal
  returns before any field write and keeps the offer, so the client cannot
  trade a stale offer for a quest start.
- **Limit:** the count and the member/non-member cap come from the server
  (`game_rules.policy.quest_limits`); 47/15 carries only the membership-derived
  selector, never a numeric cap or player id.
- **Developer override:** only with `--dev-tools` (`gameplay.rs:4407`), only for
  the exact pending dev-marked quest; it bypasses the requirement checks by
  design, not the active limit, and now cannot leak into a later ordinary
  offer. This is a development tool, not an authorization boundary.
- **Persistence:** the gateway derives save flags from `changed`
  (`gateway.rs:1541/1648/1777` -> `gameplay_changed`); refusals return
  `changed = false` and no save is staged. No item, coin, counter or cooldown is
  touched by a refusal.
- No unwrap on client data in the path; the one `expect` is guarded by the
  `pending_offer` invariant. No secrets, SQL, XSS, auth or crypto code applies.
