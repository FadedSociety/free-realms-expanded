## Production path and why each assertion proves S12/L8

`Session::commit_outcome` (`src/bin/osfr-gateway.rs:1704`) saves the staged character
snapshot at line 1951 (inside its `prepared` closure) **before** installing
`self.gateway = staged_gateway` (line 1993) and `*world = staged_world`
(line 1994), and before queueing replies (line 2011 onward). The 49/14 handler
(`src/gameplay/npc.rs:223`) applies `QuestEngine::finish_turnin`
(`src/quest_engine.rs:1937`), which uses `rewards::apply_grant`
(`src/rewards.rs:93`) on a cloned inventory/profile/quest state, so the whole
reward is staged on the gateway clone that `dispatch_message_inner` builds
(`src/bin/osfr-gateway.rs:1653`).

1. **Control** — `a_working_turn_in_pays_coins_items_and_xp_once` accepts through the
   real 26/8 -> 26/10 -> 26/6 -> 49/2 path, completes the Talk objective, releases
   the 49/13 end screen with 26/6, then sends 49/14. It asserts exact +41 coins,
   +1 item 8, +25 profile-1 XP, `Completed`, pending cleared, and that the save
   bytes changed between the pending state and the paid state. A repeated 49/14
   changes neither the snapshot nor the save.
2. **Failed save changes nothing** —
   `a_failed_save_leaves_the_character_and_save_unchanged` first commits a control
   quest, then stages a second quest and breaks the next save. It asserts the
   request fails with an `os error` (so it reached the save), that no client success
   reply was queued, whole-`Snapshot` equality, coins/items/XP/quest/pending
   equality against the live pre-turn-in state (which already carries the first
   quest's payout, so a stale entry snapshot would differ), and byte equality of
   the on-disk good save.
3. **Only that session ends** — `a_failed_save_ends_only_that_session` builds the
   t020 `server_rig` world with A and B, replaces both sessions' gateways with
   pre-staged pending-turn-in gateways and their own save paths, and sends A's
   49/14 as a real reliable datagram through `Server::step`. It asserts A's key is
   gone, `active_sessions`/`joined`/`players`/`chat_sessions`/`session_keys` have no
   A row, A's good save is byte-identical, both survivors keep their world rows, a
   second step runs, B's save file is still byte-identical to B's good save (A's
   failure cannot touch the bystander's file), and B then turns in its own quest
   successfully (paid, its own save rewritten).
4. **Reconnect** — `a_failed_save_does_not_consume_the_turn_in` loads the good save
   in a fresh `Session::new`, asserts the quest is still `Active`, pending, and
   unpaid, then turns it in successfully with exact deltas and a changed save; a
   replay after that pays nothing. Test 5 does the same-session and reconnect replay
   after a successful turn-in.
5. **Full-bag refusal** — `a_full_bag_refuses_the_turn_in_and_changes_nothing`
   asserts no completion packet, whole-snapshot equality, quest active + pending,
   100 items and byte-equal save, then re-interacts to prove the session and NPC
   menu are intact.
6. **Harness pin** — `the_save_failure_harness_is_the_real_commit_path` reads the
   real `src/bin/osfr-gateway.rs` and asserts the production save call occurs before
   `self.gateway = staged_gateway;`, and that this test module drives
   `Session::dispatch_message` (not a private helper).

## Security threat note (secure-code-guardian)

- **Attack surface:** the changed code is test-only; it exercises the existing 49/14
  turn-in route. A hostile client can send 49/14 with an arbitrary/zero quest id, at
  any time, repeatedly, before the objective is complete, with a full bag, or while
  another quest is pending. None of those fields select the save path or the reward
  amount; the server's `pending_turnin` and the quest's own stored state are the
  authority.
- **Why a hostile request cannot profit:** `finish_turnin` requires
  `pending_turnin == quest_id`, the definition to exist and be completed, and the
  job-JP profile to be unlocked; `apply_grant` is keyed by
  `quest:<character_id>:<quest_id>` and refuses locked profiles, unknown item
  definitions and a reward that exceeds the 100-stack bag. A turn-in that fails any
  of these runs on the gateway's cloned `Gameplay`; nothing is saved. The full-bag
  test proves the refusal changes no coin, item, XP, quest or pending state, and
  the replay tests prove the same 49/14 cannot be paid twice in a session or across
  a reconnect.
- **Economy:** rewards come only from the server-side `finish_turnin` grant; no
  client-reported result is honoured by this path. The control asserts exactly one
  coin/item/XP grant and the duplicate case asserts zero. The broken save is a
  host-side path (a file/directory name), not a client field, so a client cannot
  choose where or whether the save runs.
- **Isolation:** the save error is returned as an `Err`, never `unwrap`ped on
  client-controlled data; `Server::step`'s `contain` ends only A and B keeps
  playing and saving. The full-bag handler error is already contained by
  `Gateway::handle_at` as a logged rejection for that request.
- **No production change:** no parser, route, save-ordering or economy code was
  added. If the test found a defect the brief said to stop and report
  `AUTOPILOT: NEEDS-LEAD`; it found none.

## Checklist

1. **A refusal changes nothing.** The failed-save test snapshots the full canonical
   `Snapshot` and the on-disk good save bytes around the failure and asserts
   equality; the full-bag test does the same and also asserts no completion packet
   and an intact session. Canaries made both sensitive: restoring the save path in
   the failure test made it red, and raising the production bag capacity to 101 made
   the full-bag test red (the reward was then granted). Stage-on-a-clone is the
   production behaviour read in `commit_outcome`/`Gateway::handle_at`.
2. **Rollback covers all state.** The test asserts coins, item instances, profile XP,
   quest status, pending turn-in and the whole `Snapshot` together. No `Rc`/`RefCell`
   side table was added; the staged `Gameplay`/`Gateway` clone is the only mutation
   surface and is discarded on the failed save.
3. **Apply deltas, never restore old snapshots.** The failed-save comparison is
   against the live pre-turn-in state after the first quest's committed payout
   (1,041 coins, 25 XP), not an older entry capture; a stale snapshot restore would
   show 1,000 coins and 0 XP. The control's deltas are exact.
4. **Busy rules are mutual.** N/A. No new activity, `Occupation` variant or busy
   check was added; the test uses the existing NPC/quest router, and
   `gameplay/occupation.rs` is untouched.
5. **Every entry path is gated.** The test drives the only production turn-in entry
   (49/14 through `Session::dispatch_message`/`Server::step`); it adds no parallel
   path. The server case proves a reconnect loads the saved pending state and pays
   it through the same entry. The full-bag refusal is refused by the same handler
   gate as before.
6. **Reachable in production, tested through it.** Gateway -> `Session::dispatch_message`
   -> `commit_outcome` -> `save`, and the server case delivers a real SOE reliable
   datagram into `Server::step`. The two server sessions' pending states are staged
   with `Gateway::handle_at` only as fixture setup; the actions under test go through
   the real session dispatch. `the_save_failure_harness_is_the_real_commit_path`

   `dispatch_message`.
7. **Survives reconnect.** The pending turn-in and quest status live in

   nothing, and the failed save/save-failure paths pay nothing. The reward item is a
   real catalogue definition and the fixture never touches an item the character
   does not own.

    `00a97ef0` and base reader `00c7acd0`; 49/13 reads speaker 6..14 and quest id

11. **Unique ids.** N/A. This change adds no instance id, GUID or lifecycle id. The
