## The lead decision (why NEEDS-LEAD)

Both blockers are lead-only policy changes and `lab/autopilot/lead-signoffs.md` has no F181/F207
entry. The lead is offline, so no sign-off is obtainable; the rules for this run reserve budget,
rate-limit and save-policy decisions for the lead. Three facts frame the decision:

1. **The persisted count is the lead's baseline, not a new F207 choice.** `git log -S 'pub
   observations: u32' -- prototype/osfr-tools/src/kart_service.rs` finds only the baseline commit
   `ffef740` ("Baseline: Rust server, tools, content and notes as of 2026-10-15"). In `git show
   ffef740:prototype/osfr-tools/src/kart_service.rs`, `snapshot()` writes `observations:
   self.observations`, `restore()` restores it and bound-checks it, and the pickup arm increments it
   before the race-window check. F148 moved the increment after the window check (blocked as a
   budget change in `2d497df-F148`); F181 restored the increment order but moved the storage to a
   per-session counter (blocked in `4527cab-F181`); F207 restored the baseline storage and added
   the save-inert rule (blocked here). So the review's premise that F207 introduces a new budget
   scope does not match the history: the persisted shape is the one the lead's baseline shipped,
   and F207 removes F181's unsigned deviation.
2. **The anti-flood scope argument is moot in production.** Every login loads the gameplay with
   `Gateway::load_gameplay` (`src/bin/osfr-gateway.rs:937`), whose `Gateway::load_internal`
   (`src/gateway.rs:902`) calls `Gameplay::abandon_kart_for_reconnect` (`src/gameplay.rs:1524`):
   the saved race is aborted and `active` is taken before the client can send a frame. The code
   graph (`...-autopilot-int`) lists the inbound callers as
   `src/bin/osfr-gateway.rs::{load_gateway_from, load_gateway_template}` and
   `src/gateway.rs::{load, load_gameplay, load_internal, load_with_startup_snapshot, reset_session}`.
   A new entry (`KartGateway::begin`) builds a new `KartService` with `observations = 0`. The F181
   review's relog-refill scenario (restore with a fresh allowance, repeat) therefore cannot happen
   under either policy: there is no restored race to refill. `KartService::restore` is reached only
   from `KartGateway::load` (`src/kart_gateway.rs:342`), i.e. the same load that abandons the race.
3. **The save-inert rule is the genuine new decision.** `KartGatewayState::changed_for_save`
   (`src/kart_gateway.rs:124`) compared through `ServiceSnapshot::save_decision_eq`
   (`src/kart_service.rs:863`, exhaustive 29-field destructure) and `WeaponState::save_decision_eq`
   (`src/kart_weapons.rs:870`) excludes the observation count, the last weapon pose and the session
   weapon clock from the save trigger. That changes which persisted fields request a character save
   and creates a crash-loss bound (the excluded values ride the next real change and the
   end-of-session save). The review's finding 2 asks for exactly this sign-off. Reverting it would
   (a) put back one character save per observation/bulk frame — the F148/F181 amplifier — and
   (b) lose `an_observation_commits_the_persisted_budget_without_a_save`,
   `kart_timeout_refusal_is_save_inert_at_the_gateway` and
   `clock_only_racing_ticks_do_not_request_a_character_save`, which the integrator added to
   `lab/autopilot/protected-pass.txt` and now refuses to lose.

**The lead's options.** (A) Add a sign-off row accepting the persisted observation count
(baseline shape, spent slots saved by the next real change / end-of-session save; crash-loss bound)
and the save-inert observation/pose/clock rule. No code change is needed; the suites are green.
(B) Direct the F181 per-session counter and/or per-frame saves instead; the same commit must change
the three protected test names above (and the integrator will rebuild the protected set from the
green run). (C) Debounce the save in `src/bin/osfr-gateway.rs`; that is lead-only session plumbing,
not a builder change.
