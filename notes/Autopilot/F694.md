# F694: fix the T522 review findings (33295a2)

Review: `lab/autopilot/reviews/33295a2-T522.md`. All five findings were addressed; none was wrong.

## What changed

1. **BLOCKER: a refused meta reward still reported a change.** `record_collection_entry` records the
   source entry first, and its completion's `adopt_reward_state` sets `Outcome.changed`. The T522
   meta `collect_entry` then runs; when it is refused (for example the source's 70348 makes the
   hundredth bag stack and the meta's 70349 finds none), the old branch replaced `replies` but
   returned the same `Outcome`, so `changed` survived a discarded transaction and the gateway could
   write a character save for a refused click.
   - `src/gameplay/collection_pickup.rs`: the `GrantFailure` branch now returns a fresh
     `Outcome` containing only the system refusal chat; nothing from the discarded stage escapes.
   - The refusal log moved into `record_collection_entry` (`log_refused_entry`), so it names the
     entry that actually failed: the clicked source entry, or the meta entry (2177 in the
     regression). The previous log always named the source coin entry.
   - `tests/collection_rewards.rs`: `a_meta_reward_refusal_changes_nothing_and_the_retry_pays_once`
     completes the first seven Elite sets, pads to 99 occupied stacks, records seven of 291's eight
     entries, then clicks the last coin. 291's 70348 fits (the hundredth stack) and 309's 70349 does
     not. It asserts the refusal chat, `!out.changed`, an unchanged `GameplayState` and visibility
     revision, 291/309 uncompleted, no source entry 2066 or meta entry 2177 recorded, no 70348 or
     70349 held, and the coin still visible. It then relogs with one free stack, repeats the click,
     and asserts both rewards and both ledger entries land once; a replay is silent.
2. **MINOR: provenance for the meta rule.** `completion_grant` now says `collection_add` is not paid
   and (R) drives the T522 map. `notes/Autopilot/T522.md` gained the core (R) rule and its data
   evidence, and no longer implies the client citation proves the effect.
3. **MINOR [STRUCTURE]: duplicate/multiple `collection_add` targets.** `meta_map` now dedupes a
   source's rows per target (a repeated row counts once) and refuses a source that still names more
   than one accepted target; the map can no longer silently keep the last pair. The refusal is a
   load error like the catalogue's other structural refusals.
   `tests/collection_catalogue.rs::meta_map_dedupes_repeats_and_refuses_two_targets` covers both:
   `[309, 309]` still yields 14 pairs and 284 -> 2170, while `[309, 10_000]` (with a synthetic
   accepted target 10_000) is refused at load.
4. **MINOR: hidden no-op fixture branch.** `Fixture::bundled()` is the explicit constructor for the
   bundled coin map/catalogue; the `unchanged` no-op and its doc line are deleted. `Fixture::new`
   and the tuning constructor share `Fixture::build`.
5. **MINOR: vacuous assertion.** `map_has_exactly_14_pairs` no longer asserts `meta_entry(298)`
   (298's own reward has no `collection_add`); it asserts that no mapped value is 298's ambiguous
   entry 2104, 2105 or 2106, which is what the 295-297 scenario actually exercises.

No content JSON and no hub file was edited.

## Threat note (secure-code-guardian)

- A hostile client controls only the 26/8 click target guid. It must name a coin in the server's
  coin map, currently visible to that player, in the open world, within the pickup range, and the
  player must not be busy; otherwise the click returns before the staged clone.
- The entry id, meta entry id, collection ids and reward ids all come from server-side catalogue
  data, never from the request. A client cannot name a meta entry or a reward.
- The new refusal path returns a fresh `Outcome` with only the refusal chat: it cannot mark the save
  changed, hide the coin, consume an attempt or leak discarded reward state. The regression test
  snapshots the whole state and visibility revision and asserts equality.
- A malformed catalogue (a source naming two accepted targets) is refused at load, not at a client's
  request; there is no new client-controlled input and no new `unwrap` on client bytes (the existing
  fixed-slice unwrap stays behind its length check). Only server entry ids and the `GrantFailure`
  reason are logged, never payload contents.
- The meta reward is paid only from the saved ledger's completion in the same staged transaction;
  the retry test proves 70348 and 70349 are granted exactly once, and a replay pays nothing.

## Checklist

1. **A refusal changes nothing.** The blocker test snapshots state and visibility, asserts
   `!out.changed`, an unchanged snapshot, untouched 2066/2177/291/309, no rewards and a visible coin
   for the late meta refusal; the existing full-bag test covers the source-reward refusal. Canary
   confirmed the test catches the old behavior.
2. **Rollback covers all state.** The click is one staged `Gameplay` clone assigned only on success;
   the new refusal returns a fresh `Outcome`; the map lives in the read-only shared
   `Arc<CollectionWorld>`. No new shared mutable state.
3. **Apply deltas, never restore old snapshots.** `collect_entry` calls `reward_snapshot()` per entry
   and adopts it immediately; the retry test starts from the post-refusal state and pays exactly
   once. No earlier snapshot is restored.
4. **Busy rules are mutual.** No new activity, occupation variant or busy gate; the existing
   `activity_busy` check is unchanged and the meta entry is internal to the gated 26/8 click.
5. **Every entry path is gated.** There is still one record path, the 26/8 coin click, with the same
   zone/range/busy gates; the meta entry is derived server-side and adds no client path.
6. **Reachable in production, tested through it.** The new request-path test drives the real
   `Gameplay::handle_in_world` 26/8 route (the same route the gateway dispatches), not internals or a
   copy of the logic; the loader test drives the real `CollectionCatalogueContent::load`.
7. **Survives reconnect.** The late-refusal test relogs after the refusal with the saved state and
   retries; the all-sets test relogs and replays every coin. Both ledger entries are in
   `ProgressionExtrasState`.
8. **Every exit path restores the player.** A refused click leaves the coin visible and clickable;
   the retry completes and pays both rewards; a replay is silent. Hiding on success is the existing
   unchanged `npc_visibility.remove` path covered by `collection_coin_pickup`.
9. **Economy safety.** Entry, meta and reward ids are server data; the client supplies only the coin
   guid. The test asserts no 70348/70349 before the refusal, exactly one of each after the retry, and
   no second grant on replay.
10. **Wire format matches the client reader.** The 38/10 layout is unchanged and was re-checked
    against `0x008d8570`; the existing test pins the exact 2170 bytes.
11. **Unique ids.** No production id is allocated by this change; the test fillers use unique ids and
    raise `next_instance_id` above them.
12. **Others see changes.** Collection state and coin hiding are personal (T450 (R)); nothing new is
    broadcast.
13. **Content works end to end.** The all-sets test still asserts all eight set rewards and the
    backpack; the retry test asserts the final 70348/70349 grants and both ledger entries.
14. **Values live in data.** No new production tuning constant; the map comes from
    `collection_catalogue.json`. The two-level bound and the single-target rule are structural
    policy documented on `meta_map`.
15. **Canaries break production code.** The three canaries changed `collection_pickup.rs` and
    `collection_catalogue.rs` themselves; the observed failures are above and the code was reverted.
16. **Hands off session plumbing.** No session, teardown, transaction or save-ordering file was
    touched.
17. **One player's error never stops the server.** The meta refusal returns a per-player chat/`Err`
    inside one session's staged state; no shared tick work and no new client-data `unwrap`. The
    regression runs a full request and asserts the refusing player's state, not a shared failure.
18. **A type's rules live on the type.** The map's one-to-one and duplicate/two-target rules are
    documented on `meta_map` and the `meta` field; `completion_grant` documents that
    `collection_add` is not paid but drives the map; the `Outcome` field policy is applied in one
    refusal branch with its reason.
19. **Hot paths stay cheap.** No per-tick work or new clone; the map is load-time and the extra work
    happens only when a click completes a collection.
