# T447: collection catalogue from our own login capture

## What changed

- **New data** `prototype/osfr-tools/data/content/collection_catalogue.json` (555,475 bytes, LF,
  generated, sha256 `23be83b2...a250e`). It holds 253 collections (ids 10..313, in capture order) and
  1,815 entries. It also has each collection's completion reward, the provenance and the gaps.
- **New module** `src/collection_catalogue.rs`, registered with one line in `src/lib.rs`.
  - Typed file schema (`deny_unknown_fields` everywhere).
  - Loader `CollectionCatalogueContent::load(dir) -> io::Result<Option<Self>>`, which builds the
    existing piece_074 `CollectionCatalogue` through `insert`. It adds no second catalogue type.
  - Exposes `catalogue()`, `collections()`, `collection(id)`, `entry(id) -> (entry, collection)` and
    `entry_for_item(item) -> Option<i32>`. The last answers only when exactly one entry links the
    item.
  - Nothing at runtime calls it: the feature is dormant, and an absent file returns `Ok(None)`.
- **New tests** `tests/collection_catalogue.rs`:
  - five gates that read only the committed file;
  - the ignored generator and drift oracle `regenerate_or_check_collection_catalogue`.
    - It needs `OSFR_GATEWAY_REFERENCE` and reads the join inputs from that folder's
      `lab/references` siblings.
    - With `OSFR_REGENERATE_COLLECTIONS=1` it rewrites the file. Otherwise it asserts the file is
      byte-equal to what it would write.
  - It reuses `startup_selfdata::parse_self`, so there is no second parser.
- **Doc fixes**:
  - `src/restoration/piece_074.rs` module doc: captured ids, item links and rewards now live in the
    catalogue file.
  - `src/restoration/piece_038.rs` gap list: the reward rows and entry item ids now point at the
    catalogue.

### File shape

- **Collections.** Each row is `id, name_id, description_id, category_id, icon_id, icon_tint_id,
  flag6, entries, reward`. These come from record dwords `+0x9c, +0xa0, +0xa4, +0xa8`, the icon pair
  (`008caaa0`) and `+0xb8` (`009099d0`).
  - `flag6` (R): it is 1 on 251 rows and 0 on 277 and 278.
- **Entries** (`008dacc0`, stream order DefinitionId, Index, CollectionId, NameId, icon pair, unknown
  dword, Collected).
  - Fields: `id, index, name_id, icon_id, icon_tint_id, item_definition_id, item_link`, plus
    `item_link_note` when the item is null.
  - The collected byte is the captured player's state and is never stored.
  - The generator asserts, per row, that key == DefinitionId, that CollectionId is the parent and
    that the unknown dword is 0.
- **Reward** (`008e7930`):
  - `coins`: fixed dword 0.
  - `items[{item_definition_id, count, female_item_definition_id?}]`: kind 1.
  - `xp[{profile_id, amount}]`: kind 3.
  - `tokens[{token_id, count}]`: kind 12.
  - `collection_add`: kind-10 tails.
  - `quest_add`: kind-6 tails.
- **Gaps:**
  - `reward_items_missing_from_legacy` [12410, 38816, 38817];
  - `null_item_links` {no item with this name: 299, ambiguous name: 100};
  - `collection_add_not_captured` [122, 124, 125, 126, 127, 130, 131, 132, 133, 137, 140, 221, 242,
    292]. This one is new: these are collection-add targets with no captured record. A later pickup
    or completion task must not assume they exist.
- **Item links:** 1,087 come from `sanctuary` and 329 from `legacy-unique-name`. Every category-1
  entry has a null item.

### Deviations from the brief (IDA wins)

- **The brief's `kind6_tails` (R) is `quest_add`.**
  - `0103c070` case 6 builds `0103a780`, which sets vtable `0187E350`.
  - That vtable's slot `0187e384` is `0103bb50`, which formats `"QuestID=%d"` from `+0x44` (the
    tail).
  - The seven tails are 1288..1292, 1221 and 1526.
- **Coins is client-evidenced as the bundle's coin slot.**
  - `008e7930` stores dword 0 at `+0x50`.
  - Reward vtable `018056ec + 0x50` (`0180573c`) is `0091c2e0`, which returns `+0x50`.
  - `00b89ca0` (BaseClient::HandleRewardPacket) calls that slot and formats the value under the
    `"coins"` key.
  - **(R):** that the original server paid it on completion. Collection 10 has 9, which matches
    Lxzxrus `RewardCoins`.
- **"Indexes contiguous" means a permutation of 1..=n, not capture order.** Collections 244-260, 277
  and 278 list their entries in a non-sorted index order. The loader checks that the sorted indexes
  equal 1..=n with n <= 8.
- **The reward entry common dwords** (`0103c460`) are:
  - the icon pair, through `008caaa0` into `+0x14`/`+0x18`;
  - then `+0x10`, `+0x20` (count/amount), `+0x24` (item/profile/token id) and `+0x28`.

  The build guide's `[+0x04]`, `[+0x08]` for the pair is off. `Token` prints `TokenId` from `+0x24`
  (`0103b950`), and `CollectionAdd` prints `CollectionID` from `+0x44` (`0103b800`).

### (R) choices

- `flag6` meaning is unknown.
- Token meaning is unknown.
- Coins paid on completion (the slot itself is client-evidenced).
- The names "count" (`+0x20`) and "amount" for xp are community names. They are consistent with
  Sanctuary `RewardPoints` 50 and Lxzxrus `RewardExperience` 50.
- Load bounds are sanity bounds:
  - item/token `count` 1..=100;
  - xp `amount` 1..=100,000;
  - `coins` 0..=100,000.
- The join rule (Sanctuary, then unique Legacy NameId, then null) is community data. It carries
  per-row provenance in `item_link`.
- Female reward items come only from Lxzxrus `RewardItemIdsGirls`: 265 18040->16529,
  271 17210->15561, 273 1496->1415, 274 17271->15379.

### Threat note

The file is server content, not client input; no client packet reaches the loader. Even so, a bad or
hostile content file is refused whole, and nothing is built when it is:

- a bounded read (`take(1 MiB + 1)`, so there is no metadata/read race);
- `deny_unknown_fields`;
- schema version 1;
- categories through `insert`;
- unique collection and entry ids;
- index permutation 1..=n with n <= 8;
- reward bounds, with the collection id named in every error.

The loader grants nothing and touches no player state.

## Checklist

1. **Refusal changes nothing.** The loader builds locals and returns `Err` before anything exists,
   and there is no shared state. `loader_refuses_bad_files` covers each refusal: duplicate entry
   across collections, index 0 and 9, category 11, unknown field, coins/xp/item/token bounds and
   over 1 MiB. Each runs on a temp copy, with a passing control copy. Canaries 2 and 3 apply.
2. **Rollback covers all state.** N/A: there is no transaction or player state.
3. **Deltas, not snapshots.** N/A: nothing is granted.
4. **Busy rules.** N/A: there is no activity.
5. **Every entry path gated.** N/A: no route calls the loader yet (dormant by design, per the brief's
   "Keep unchanged").
6. **Reachable in production.** Deliberately not wired, per the brief. The tests drive the real
   loader on the real committed file.
7. **Survives reconnect.** N/A: there is no session state.
8. **Exit paths.** N/A.
9. **Economy safety.** Reward values are bounded on load. The catalogue grants nothing; later grant
   paths must still apply rewards only from server-verified completion.
10. **Wire format.** No wire change. The file mirrors the client readers cited above, and the drift
    oracle pins it byte-for-byte to the captured template.
11. **Unique ids.** Collection ids are unique (through `insert`). Entry ids are unique across the
    whole file (the loader's own check, tested with canary 2).
12. **Others see changes.** N/A.
13. **Content end to end.** N/A until a consumer exists. The gates assert real rows: collection 10,
    265, 284, 311-313 and the item link for 11081.
14. **Values live in data.** Rewards are in the JSON and tunable within the load bounds.
15. **Canaries break production code.** Canaries 2 and 3 break `collection_catalogue.rs`. Canary 1
    breaks the generator's join, which is the code that produces the data.
16. **Session plumbing.** Untouched.
17. **One player's error never stops the server.** Not on a tick path. A load error is an `io::Error`
    for the caller.
18. **Rules on the type.** Field docs on `Collection`, `Entry` and `Reward` say what is kept and what
    is not (the collected byte, display bytes).
19. **Hot paths.** Zero per-tick cost. `entry` and `entry_for_item` are `BTreeMap` lookups;
    `collection` is a linear scan of 253 rows (no caller yet).
