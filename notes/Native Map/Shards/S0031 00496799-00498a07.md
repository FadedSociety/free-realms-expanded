# S0031 findings: display-system bitmap family (00496799-00498a07)

Repair 2 (independent review) corrected three labels. The earlier lock/upload reading of
004974be and 0049767b was wrong: the +0x128 virtual call is the class's release, not a
storage producer. The corrected mechanism below is re-derived from the machine code of
`lab/runs/client-baseline-*/client/FreeRealms.exe` (vtable and data reads only; no Ghidra
import) plus the export's pseudocode.

## What this range is

Nine bitmap pixel/format functions of one display-system surface class. They share the
9-dword descriptor reachable at object+0x44 (an embedded copy at +0x14). The subsystem is
`engine.gds`, matching the accepted labels of the direct helpers in this area:
0047bbc4 `CopyGBitmapInfoHeader` and 00489bed `ClassFactory4C` are both `engine.gds`, and
the render-support callers 004104a3/00410733 that consume the sibling reader 004963f2 are
`engine.gds` too. There are no strings or RTTI names in this range.

## Storage protocol (replaces the earlier lock/upload reading)

- 0047ca5e (slot +0x11C) allocates a new storage for its receiver: it releases any
  previous binding through slot +0x128, computes the pixel size from the format word,
  calls `CreateDIBSection` (bits pointer into descriptor[9], HBITMAP into object+0x54) or
  a plain allocator for bit-31-flagged formats, optionally allocates a width*height alpha
  plane into descriptor[10] with strides [7] = 1 and [8] = width, and binds
  object+0x44 = object+0x14.
- 0047cc98 (slot +0x128) releases: for an embedded descriptor it calls the +0x50 callback
  if present, then `DeleteObject(object+0x54)` or frees the plane buffers at
  +0x38/+0x3C unless the format word carries 0x2000000, and clears the pointers. The
  destructor 00486328 uses it on field [0x11].
- 0047bbc4 copies the 9-dword header (accepted label `CopyGBitmapInfoHeader`).

With that, 004974be (resize) and 0049767b (crop) read as: build a stack temporary of the
same class, allocate its new storage with 0047ca5e (current format word, requested or
clipped extent), copy the surviving rows from the current planes into the temporary
planes, release the object's old binding through slot +0x128, transplant the temporary
header/planes/palette/HBITMAP into the object, clear the temporary's ownership so its
destructor frees nothing, rebind +0x44 and restore the format (and origin), destroy the
temporary. For 004974be the sequence is visible at instruction level: 0x4975d7 saves the
old format/origin, 0x4975db calls slot +0x128, 0x4975ea copies the temporary header
(ECX = this+0x14), 0x4975ef..0x4975f8 move the plane pointers, 0x49761e..0x497632 move
the HBITMAP/+0x58 and zero the temporary's +0x44/+0x54/+0x58, 0x497635..0x497648 restore
format and origin, and 0x497657 destroys the temporary at [ebp-0x68].

## Cross-function contracts

- Channel map: the same 4-nibble loop lives in 00496799 (inlined), 00498a07 (inlined) and
  00497a74 (out of line). Per output byte: 0 = fill-colour channel, 2/3/4/5 = fixed fill
  channels, 6 = luma (5*b0 + 16*b1 + 11*b2) >> 5, 1/7 = keep, bit 3 = invert.
- Separate alpha (format flag 0x800000): 00496799 reads/writes the byte through *param_3;
  00497eb6 attaches it via field[8]*y + field[7]*x + field[9]; 00498603 returns it;
  00498a07 stores `param_4 >> 0x18` into it. 0047ca5e installs [7] = 1, [8] = width for
  the alpha plane, but the readers index it from field [9], which does not match the
  allocator's [10] plane pointer; treat the plane-base convention as unresolved.
- Sub-byte formats: the byte address uses the duplicate tables 01af51ec / 01af9e84
  (byte-identical for the used indices: x >> 3 for 1-bpp, x >> 2 for 2-bpp, x >> 1 for
  4-bpp), the sub-pixel index is x & 7 / x & 3 / x & 1 (index bytes at 01af6fe3 = 7,
  01af6ff5 = 3, 01af7019 = 1), and the mask/shift tables are 01af6fec + 01af6fe4,
  01af6ffe + 01af6ff6, 01af7022 + 01af701a. Caution for a port: as stored, the 2-bpp and
  4-bpp shift arrays (00 00 01 01 and 01 00) do not normalise the masked value to the
  sub-pixel range, so their exact decode pairing needs one more check before reusing.
- Format word shape: low 16 bits spell per-channel bit depths
  (444/555/565/1555/4444/0888/8888/8555/8565), 0x40000 = palettised, 0x800000 = separate
  alpha; the composed constants 0x210444, 0x410888, 0x610888, 0x618888, 0xa18444,
  0xa18555, 0xa18565, 0xc18888 are handled explicitly.

## Open questions

1. The class still has no name: no RTTI string covers vtable 01769ba0; the slot map above
   is read from the image rather than the export.
2. The separate-alpha plane base/stride convention (fields [7]/[8]/[9]/[10]) is
   inconsistent between the allocator and the readers and needs a caller or runtime probe.
3. Flag bits 0x10000, 0x200000, 0x400000, 0x80000 (formats) and 0x100000, 0x2000000
   (descriptor) are observed but not proven.
4. The stored 2-bpp/4-bpp shift arrays do not normalise sub-pixel values as written; the
   exact pairing of masks and shifts should be re-checked against a live pixel trace.
5. 00496799 and 00497a74 have no callers or vtable entries; confirm whether they are dead
   out-of-line emissions or reached through a computed pointer before porting them.
