# T721: speed up the slowest tests so every integration batch is shorter

## Summary

The integration suite's test phase is bounded by a long tail of test binaries. Three costs
dominated that tail, and all were paid many times over:

1. **The gateway binary's `#[cfg(test)]` session modules ran in eight integration harnesses.**
   Every harness that embeds `src/bin/osfr-gateway.rs` also runs the gateway's ~138 session
   tests, on top of its own handful. Those copies are duplication: the same tests run against the
   same code in `unittests src/bin/osfr-gateway.rs`. The repository already had the mechanism
   for this (`test_support::bin_test_target`, used by T461/T478/T519/T258): an embedded copy
   prints `embedded gateway copy skipped` to stderr and returns early, while the bin's own target
   runs the body. T721 extends that guard to every remaining session test, so the embedded copies
   stop paying for the bin's suite and the bin target still runs each test exactly once. No test
   is removed, renamed or ignored: every name still appears and passes.
2. **Every split-quest bind re-read 25 MB of NPC rows for data it never uses.**
   `QuestEngine::from_split_content` reads each `npcs/*.json` row for its id and quest bindings
   only, but the shipped `data/content/npcs` is 25 MB (17 zone files). `tests/support/
   npc_quest_chain.rs` binds one engine per fixture session, and `enabled_quest_menu_offers`
   binds 37 of them (one per job/chain-size layer), so that file alone re-read the NPC catalogue
   37 times. The fixture now builds a narrowed catalogue once (all quest files, the four small
   side files, and exactly the NPC rows that carry a quest binding) and every
   `Fixture::game`/`game_as` bind reads that: 25 MB of NPCs become 20 KB of bindings, while every
   giver/turn-in mapping and every cross-check against `data/content` stays. `Shipped` in the
   test still loads the untouched catalogue for positions, names and expectations.
3. **`job_trainers`' trainer loop re-read the content per trainer.** The loop staged each
   trainer's save with a fresh `Gameplay::load`; only `profiles` differs between trainers, so the
   base state and profile table are loaded once and cloned per trainer.

## Measurement method

`--report-time` is nightly-only (this toolchain is stable 1.99.0), so the suite was measured with
a temporary harness outside the workspace (`%TEMP%\T721\`):

- `cargo test --no-run --message-format=json` lists every test executable.
- A full-suite pass runs each executable with `--test-threads=4` — the integrator's
  `RUST_TEST_THREADS` (`lab/autopilot/integrate.sh`: `parallel_suite.py $((nproc/4)) 4`) — four
  binaries at a time, stamping every libtest result line. libtest dispatches a binary's tests in
  order and keeps four in flight, so the test whose result prints as the j-th line started when
  the (j-4)-th printed: its duration is that gap, which is what `--report-time` prints.
- The "before" binaries are the accepted tip (90cac972), built in this worktree's private build
  dir and then **copied aside** before the rebuild, so before and after can be run back to back
  on the same machine.

Environment caveat: this box ran a concurrent integration batch and a stuck foreign build
(`lab\build\exp-nightly` linkers) for most of the session, so absolute times are inflated against
`lab/autopilot/logs/suite-times.json`; before and after were measured the same way, and the
integrator's own record is quoted where a quiet-box number exists.

## What changed

- **`src/bin/osfr_gateway/*.rs` (19 test modules)**: the embedded-copy guard
  `if !bin_test_target("<tag>") { return; }` added to the 94 session tests that still ran in
  embedded copies (t020 15, tests.rs 10, t199 10, l042 8, t006 8, w173 7, quest_reward 6, w163 5,
  tick_stats 4, f160 3, client_area 3, l011 3, isolation 3, lead_trade 3, l039 2, f120 1, f276 1,
  dormant 1, style_card 1). Boombox (`t461`...), `t458` and `t507` already guarded through their
  rig constructors; no guard exists in `src/bin/osfr-gateway.rs` itself, so the bin target runs
  every body.
- **`tests/support/npc_quest_chain.rs`**:
  - new `Fixture::quest_catalogue()`, and `Fixture::game_as` binds it. The narrowed catalogue is
    built once per fixture (idempotent) with all quest files, `jobs.json`, `job_browser.json`,
    `quest_markers.json`, `breadcrumb_quests.json` and one generated `npcs/bindings.json` holding
    only the rows that name a quest (25,084,732 bytes of NPC files become ~20 KB; 17 files become
    1). `quest_binding_rows()` reads those rows once per test binary (`OnceLock`), so the 25 MB
    scan is paid once, not once per fixture.
  - `content_position` caches each `npcs/<file>.json` document for the test binary: 72 call sites,
    and each call used to re-parse a 2-3 MB zone file.
- **`tests/job_trainers.rs`**: the trainer loop loads the base save and the profile table once
  instead of per trainer.
- **`tests/gathering_payout.rs`**: the two phase loops keep one fixture and one staged save per
  game; each phase still gets its own gateway and its own reconnect.
- **`notes/Autopilot/T721.md`**: this note.

No production file changed. No hub file (`gameplay.rs`, `gateway.rs`, `encounter.rs`,
`bin/osfr-gateway.rs`) changed: the guards live in the `#[cfg(test)]` submodules under
`src/bin/osfr_gateway/`, and the catalogue helper is test-only.

## Threat note (secure-code-guardian)

No production path changed. The gateway's request parsing, refusals, saves, coins/items, rewards,
roles and wire bytes are untouched; each guarded test body is byte-identical where it runs, and the
narrowed catalogue only feeds a loader that reads those exact fields. A hostile client cannot reach
any of this: the changes are compiled only in test targets (`#[cfg(test)]` / `tests/`).
