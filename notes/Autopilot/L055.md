# L055: login create/delete reload the account store before writing (lead)

Character create (opcode 5) and delete (opcode 9) in `LoginService::handle` used to clone the store
cached at login, mutate the clone and save the whole document. `osfr-login` gives every peer its own
`LoginService` (`bin/osfr-login.rs`, `Session::new` / `options.service()`), and on the unauthenticated
loopback path every peer logs in as the one local session and shares one store file. So a session that
logged in before another session saved would overwrite that save: a lost character, a reused guid, a
name or slot check passed on stale data, and `identity.json` (account 1 / guid 1 mirror) rewritten. A
stale save could also drop an account created by another login since. The broker path already reloads
before every request (`Session::application` calls `options.service_for(handle)`); this fix puts the
reload in `LoginService`, where both paths route.

## What changed

- `src/login.rs`:
  - New `LoginService::reload_account_store` (lines 274-289). It loads `config.account_store_file` with
    `AccountStore::load`, re-runs the account lookup (`account_id_by_login_hash` of the logged-in
    session name must still give the session's account id) and only then replaces the session cache.
    It returns `Err` and leaves the cache alone if the file is missing, invalid, or maps the account to
    another login.
  - Opcode 5 (line 362) and opcode 9 (line 480) call it after the packet is fully parsed and before
    `store_and_account()`. The existing code then clones, runs `account::create_character` /
    `account::delete_character` (slot, name and ownership checks) on the fresh copy, saves only on
    Created / Deleted, and sets the cache to the saved copy, as before.
- `tests/login.rs`: `service_with_paths` takes the local session name (`service_as`,
  `login_request_as` helpers), plus four tests (below).

Unchanged: every wire reply (create 6, delete 10, list, select, name check), the save path
(`AccountStore::save` → `character_store::replace_bytes`), the lock rules, and `bin/osfr-login.rs`.

## Client evidence

No new client fact is needed: the change is server-internal persistence and the replies are byte-for-byte
the existing builders (`login::create_reply`, `account::delete_character`). The delete reply's client
consumer is `0x007198b0` (`OnRequestCharacterDelete: result=0x%0x`, success flag + guid; on failure it
shows the error state 14), per `notes/Native Map/Shards/S0148 00715ec0-00719d20.md` and IDA decompile.
The tests assert the existing codes: create 4 = NameTaken, delete 1 = Deleted, 2 = NotOwnedOrMissing
(`account.rs` `client_code`, both (R) as before).

## Security

Threat note (secure-code-guardian, security-reviewer):

- **Hostile client input.** Create and delete parse the whole packet (`r.end()`, `NativeCreation::decode`)
  before the reload, so a malformed packet costs no disk read. The reload takes no client value: the path
  is server config and the lookup key is the server-held session name. The guid in a delete is checked
  for ownership on the fresh copy (`remove_character` compares `owner_account_id`).
- **Lost update / cross-session overwrite (the bug).** Every create and delete now starts from the file.
  `osfr-login` handles one request at a time on one thread (`run` loop), so nothing in the process saves
  between this load and the caller's save. The broker mode's process-wide `AccountStoreLock` still keeps
  the offline writer out; the unauthenticated loopback mode keeps its existing no-lock rule (see Open gaps).
- **Account lookup guard.** If the file now maps the session's account id to another login (store
  replaced or restored after login), create and delete return `Err` and write nothing. Without it, a
  session would create or delete characters in another login's account.
- **Refusals change nothing.** A refused create (name taken, slots full, invalid, unsupported server) or
  delete (not owned / missing) writes nothing; tests compare the store and identity file bytes before and
  after. A refusal does refresh the session's read cache to the file contents, the same view a fresh
  login would get; nothing persisted changes.
- **No new oracle or enumeration.** Replies and their codes are unchanged. NameTaken now also covers
  names another session saved, which the name check already reports to a fresh login. A delete of a guid
  the account does not own answers 2 whether the guid exists or not, as before. The new `Err` (lookup
  mismatch) ends that peer's session exactly like the other `authenticated account is unavailable`
  errors; it reveals nothing about other accounts.
- **Logs.** No logging added. A load error string reaches the opt-in trace as `reason` like every other
  handler error; it is an io or JSON position message, never file contents, names or keys.
- **Saves stay atomic.** The save is the unchanged `AccountStore::save` (validate, 1 MiB bound,
  `replace_bytes`).
- **Cost.** One bounded (1 MiB) file read and JSON parse per create or delete request, which the broker
  path already pays several times per request; never per tick, and packets are rate-limited per peer.

## Open gaps

- List (11), select (7) and name check (16) still read the login-time cache. They are read-only, and the
  gateway reloads the store and refuses a selected character that is no longer there
  (`bin/osfr-gateway.rs` `select_character_from_login`), so no write or binding can come from a stale
  read. Reloading there too would show other sessions' changes sooner; left out to keep this diff small.
- Two `osfr-login` processes in unauthenticated mode on one store file are still not locked against
  each other (pre-existing; only broker mode takes `AccountStoreLock`).
- The lead-L055 worktree did not exist when this run started; it was created at the given base with
  `git -C autopilot-int worktree add --detach` (the `claim.sh` pattern).
