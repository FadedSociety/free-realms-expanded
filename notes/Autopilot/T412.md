## Tests (what each proves)

1. `the_turn_in_grants_two_of_the_item_once_and_the_save_keeps_them`:
   - The full real chain runs and then the turn-in. The player switches to Brawler before
     the offer, saves and reloads at the pending end screen (nothing paid; pending kept),
     then switches to Archer before the 49/14.
   - The 49/14 pays exactly +2 of item 65822, +7 coins and +3 Brawler XP. XP on every
     other profile is unchanged (the T202 rule).
   - A second save/reload keeps the stack, coins, XP and `Completed`.
   - A replayed 49/14 or 49/2 changes neither state nor save bytes.
2. `the_offer_and_end_screens_keep_the_base_bundle_and_grant_nothing`:
   - Offer, accept and end screen move no coins, XP or items.
   - The 49/1 bundle (decoded with the production reader) and the 49/13 bytes `26..95`
     both equal `QuestEngine::quest_reward_bundle`. That bundle is the 69-byte base with
     coin word 7, star word 3 and row count 0. This is the T318 display-row gap,
     characterized, not changed.
3. `a_full_bag_refuses_the_turn_in_without_partial_coins_or_xp`:
   - With 100 stacks (`fill_bag`), the 49/14 is refused, and so is a truncated 49/14.
     Save bytes are equal, the quest stays `Active` and the pending screen is kept.
   - Selling one filler stack at the shipped vendor Melninster (9_500_000_045) through
     the real 26/8 -> 26/10 Shop -> 165/5 path frees a slot. The same turn-in then pays
     once, on top of the sale's coins, and a further 49/14 changes nothing.
4. `an_unknown_item_definition_is_refused_without_partial_coins_or_xp`: three reward rows
   that the loader accepts but the inventory refuses:
   - an absent definition (999999);
   - 2 of item 8 (`max_stack` 1);
   - a good 65822 row before an absent row (proves the staged grant is dropped whole).

   Each one refuses the 49/14 with byte-equal state and the pending screen kept. The
   refused session's `Gameplay::tick` still runs, and player B in the same content is
   paid quest 3999991 in full.
5. `a_malformed_reward_is_refused_when_the_catalogue_loads`: these all make the bind fail
   with `InvalidData`, so no such quest is ever offered:
   - count 0;
   - a negative definition (`QuestEngine::new` validation);
   - a `u32::MAX` + 1 coin sum;
   - a `u32::MAX` + 1 job-XP sum (checked sums in `definition_from_content`).
6. `two_players_each_get_their_own_item_reward`:
   - Before B has any screen, B's 49/14 changes nothing and A's pending screen survives.
   - B's full bag refuses B and does not block A, who gets exactly 2. B gets 0.
   - B sells a filler, then gets its own 2. A's count stays 2.
7. `a_live_inventory_change_before_the_turn_in_survives_the_grant`: after the end screen
   opens, a real vendor sale removes the seeded filler item and adds coins. The turn-in
   then pays `live coins + 7`, and the sold item stays sold (the T250/T258 rule: deltas
   on live state).
8. `the_gate_uses_no_dev_commands`:
   - The session cannot run `teleport`/`here`/`give`/`coins`/`item`/`offer`.
   - Every request shape the suite and its helpers send is a non-chat (non-15/x) packet.
   - The whole loop, including the vendor sale, ends with no chat reply and no pending
     screen.

## (R) choices

- **Item 65822 instead of item 8.** Definition 8 has `max_stack` 1 in the opening
  catalogue (`lab/references/opening-anvil-placement-v1/content/inventory.json`).
  `Inventory::grant_with_tint` refuses a count of 2 ("reward exceeds maximum stack"), so
  the brief's `items: [{8, 2}]` could never pay. I used 65822 (`max_stack` 10, a
  captured definition the opening character does not own). The test asserts
  `accepts_reward(65822, 2)` and `!accepts_reward(8, 2)`. Item 8 x2 is kept as a pinned
  refusal case.
- **Brawler unlock.** The brief says Brawler is unlocked by default. This holds in this
  fixture: the 26/13 switch to 43 commits with no seeding. Archer is seeded into
  `unlocked` the way T301 does, so the turn-in happens on a job that is not the reward
  profile. The switch back to Adventurer is refused by the fixture's outfit check
  ("missing a required Chest or Legs item"), so Archer is used instead.
- **Vendor sale as the live change.** I found no non-dev Gameplay path that grants an
  item mid-quest without a second quest. The real 165/5 sale removes an item and moves
  coins, and it also frees the bag slot for the full-bag retry. Instead of a walk, the
  test passes the vendor's content location as the `CharacterState`, as the quest-chain
  suites do for every NPC.
- **Refusal shape.** `assert_turn_in_refused` accepts either `Err(InvalidData)` (today)
  or an unchanged `Ok` (T382's planned player-local refusal). In both cases it requires
  byte-equal save state, quest `Active` and the pending screen kept, so T382 can land
  without breaking this suite.
- Quest ids, giver ids, title/end-text ids, positions and amounts are test content, not
  retail values.

## Threat note (secure-code-guardian)

A hostile client controls only the 49/14 quest id and its length, the 165/5 instance and
quantity, and the timing.

- **Replayed 49/14.** It pays nothing. `pending_turnin` is cleared on payment, and the
  `quest:<character>:<quest>` grant key is checked before any grant.
- **49/14 for a quest without a pending screen.** It is denied (`NoPendingTurnin`), and
  another player's pending screen is not reachable: each grant key and state is
  per-character.
- **Truncated 49/14.** It is refused by `decode_quest_end_reply_49_14` before any state
  is touched.
- **Full-bag turn-in.** No coins or XP leak, because `apply_grant` stages coins, XP and
  items on one clone and drops it whole on any failure.
- **Content-side bad rows.** Count 0, negative ids and overflowing sums cannot be loaded.
  Absent or over-stack items cannot be granted.

## Open gaps

- **The pending screen is stuck after a content-error refusal.** After an unknown-item
  (content error) refusal, the pending end screen stays. `QuestEngine::abandon` refuses a
  quest whose turn-in is pending (`Unavailable`), so today that character cannot leave
  the quest until the content is fixed. The brief's edge case 9 ("an abandon of the
  pending quest still works") does not match the current code. T382 (running) owns that
  seam (`a_content_error_can_still_be_abandoned`), so this suite does not pin either
  behaviour.
- **Combined 0x19 bundles end the session.** `Gateway::handle_at` drops a Gameplay `Err`
  for a plain message: the staged game is not installed and the session survives (T258
  proved this for the full bag). For a combined `0x19` bundle it re-raises the `Err`, and
  that ends the session. T382's brief describes the plain case as session-ending; the
  code says otherwise. The lead should reconcile this when T382 lands.
- **T318 display row.** The item display row is still absent from 49/1/49/13
  (characterized above). It needs a content/lead decision.
- **Infra (lead).** The stage recompute routed T412 to review with no commit over
  `runs/T412.base`. Check any other task whose base file was written at the same time.
