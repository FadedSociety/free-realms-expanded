## Evidence (client, IDA)

- Header: both cases sit in the 35 dispatch switch `0092F540`; the body readers start with `008d6830`, which reads two
  u16 (35 and the subtype), same as 35/3 (`world.rs` builds `[35, 0, 3, 0]`). Both reader calls pass `a4 = 0`
  (`009320c0`, `00932214`), so the client rejects a packet with trailing bytes: the encoders emit exact lengths.
- 35/10: case `009320ac`, ctor `008d06d0`, body `009213e0` -> `0090aa90` (i32 count, rejected when above the bytes
  left, then `008db310` per element). Element order, confirmed in the decompile: u64 guid (+0), bool compact (+0x28),
  i32 type (+0x1C), then only when compact is false i32 +8, +0x10 (image), +0xC, +0x14, +0x18, bool +0x20, i32
  +0x24, and last bool +0x29. 39 bytes per element, 4 + 4 + 39 n in all (header, count).
- Handler (`00932136`..): the guid goes through `00984960` on `[esi+0xC0]` and a missing actor is skipped, so
  part 2 must send 35/10 after the NPC's spawn. Non-compact: +0x10 must be > 0, `01025670` looks it up on
  `[esi+0x140]` (the NotificationImages table) and the matching image draws. With f (+0x20) false it first calls
  `00960170` with (+0x10, +8, type lookup `00bb51a0`); the fork sends f false and a 0, so this slice does too. What
  `00960170` draws for a = 0 is not settled (R).
- `01025670` matches the key at node+32, the table's `#ID` column, and returns node+4 (`IMAGE_ID`). The wire value is
  therefore the `#ID`: 2 shows image 20, 6 shows image 19 (`Resources/NotificationImages.txt` rows 2 and 6, one
  layer, minimap on). The brief says "+0x10 is the image id"; true in the sense of that key.
- 35/11: case `00932200`, ctor `008d07c0`, body `00919d10` -> `008fc330` (i32 count, then `008db550` per 16-byte
  element: u64 guid, i32, i32). The handler reads only the guid (`00932250..`: `00a8e540`, `00984960`...). Matches
  the fork (guid and two zero i32).
- Fork values (behaviour only, no code): compact false, type 0, a 0, d = NPC name id, f false, g 0, trailing false;
  image 2 for available and 6 for active. The sub-text name id (e) is written 0 (R): this slice has no sub-text.

## (R) choices

- '?' (TurnIn) beats '!' (Available) when both apply.
- '?' also marks the formal turn-in NPC of an enabled active quest whose objectives are all done (a kill or collect
  quest has no Talk step), before the end screen opens; once it opens, only the pending actor shows '?'. The brief
  listed Talk targets and the pending actor only.
- Active quests that are not enabled (no objectives) mark nobody; offers go through `can_offer`, so disabled,
  prerequisite, level, job, limit and a pending offer elsewhere hide '!'.
- At most 256 entries per packet; more returns `None`. The winged class-quest '!' is not built (id unknown).
- The brief names `tests/support/npc_quest_chain.rs` `Fixture` and `saved()`. `marker_for` takes `&QuestEngine`, which
  `Gameplay` does not expose, so the rule tests build a synthetic `QuestEngine` (and the shipped catalogue through
  `from_split_content` for disabled quests); purity compares `QuestEngine::state()` before and after.

Threat note (secure-code-guardian, no client input is parsed here): the only external input is the content file;
it is size-limited, schema-strict (`deny_unknown_fields`) and bounded. A hostile client cannot reach these functions
until part 2, and the packets carry no client-supplied data.
