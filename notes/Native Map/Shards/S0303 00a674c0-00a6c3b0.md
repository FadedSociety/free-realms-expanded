## Classes and subsystem layout

`ShipCombatProcessor` construction/destruction is anchored by its RTTI vtable at `00a6b8a0`/`00a6bcb0`. The destructor frees the six member buffers at `00a6bcb0`: EventId arrays at `+0x3cc`, `+0x3dc`, and `+0x3fc`; DockEvent at `+0x3ec`; Vector2 at `+0x40c`; ActorId at `+0x41c`. It drains the player list inline and calls the player-map destructor. The separate list destructor `00a6afc0` is vtable-backed but only reached by EH unwind funclets; it is not called from the processor destructor. `00a6b070` is another unwind cleanup wrapper around the player-map destructor.

The state machine at `00a6b0c0` drives local Pirates UI and physics transitions. `00a6b5f0` clears match state, lists, and interfaces; its `+0x308` release is conditional on both the client pointer at `+8` and buffer at `+0x4c` being null. `00a69480` computes readiness from processor state bits and predicates, then sends a changed `ShipCombatPacketUpdatePlayerGameStates` through `00a67ff0`. Raw x86 at `00a69480` contradicts the previous decompiler-based claim that the caller-supplied mask is ORed into readiness: `test ecx,ecx; jnz` skips `or eax,ecx` for every nonzero value, while a zero value adds nothing. Thus the `0x80` and `0x400` arguments from `00a6b0c0` do not establish forced readiness bits. This qualifies the system note's direction label for `00a4ee00`: the shard shows the same `ShipCombatPacketUpdatePlayerGameStates` class/sub-opcode 3 being constructed and sent by `00a69480`, so that constructor is used on an outbound path as well as any receive path. This may be a bidirectional message or a reused packet class; the native client alone does not settle it. The note's broader server-coordination statement remains a hypothesis, and this shard supplies no server implementation or confirmation of aggregation policy.

Array and list helpers remain mechanically named where class ownership is not local. In particular, `00a68dc0` calls its element reader with the destination slot in ECX and the bounded reader on the stack; the old decompiler-parameter description reversed that relationship. The structure handler `00a68950` first scans the fort list for a duplicate, then `00a55190` searches a linked structure chain rooted at processor `+0x84` (next at node `+0x90`, key at `+0x20`). That lookup is not a player-map owner resolution.

## Wire observations and server hypotheses

Packet constructors and handler routing establish several client-side message shapes. `00a678f0` constructs `ShipCombatPacketCreateProxiedShip` with sub-opcode `9`; parser `00a69b90` reads the payload, and handler `00a6c3b0` requires full consumption, a non-null identifier, and a nonnegative dword at packet `+0x1c`. It inserts only after `00a55390` finds no existing entry; processor `+0x14` and the object's bit 0 are updated only under the local-condition branch. This supports the hypothesis that the original server sent a proxied-ship announcement, depending on the constructor, parser, and dispatcher route `00a6d270`; authority and lifecycle rules remain unknown.

`00a67ee0`, `00a67ff0`, `00a68100`, and `00a68210` construct `PacketTunneledClientPacket` gateway envelopes on send paths. `00a69380` uses the header-only helper for client-side player registration/removal. `00a69870` and `00a69980` send the two-string ship-selection request, and `00a69980` also caches a local selection index; evidence does not show that index is sent or later used by the server. `00a69480` sends a changed readiness word. These client transmissions support protocol-shape hypotheses only, not original server behavior.

The packet catalogue contains the gateway tunnel classes but no matching ShipCombat inner packet classes. For inbound handlers and nested payload readers in this shard (`00a67a70`, `00a677c0`, `00a683d0`, `00a68950`, `00a68dc0`, `00a69b90`, `00a69cf0`, and `00a6c3b0`), the dispatcher/call graph establishes parsing context, but does not justify recording the outer gateway envelope as the packet parsed by each function. Their `wire` fields are therefore empty; exact inner class/opcode mapping remains open. Existing system note `notes/Native Map/Systems/net.packet.shipcombat.md` maps opcode family `94` (`0x5e`) and known constructor sub-opcodes; this shard's local dispatch context is consistent with that map, while the gateway catalogue remains only outer-envelope evidence.

Community emulator packet names remain wire-format references, not original server logic: [FreeRealms-Legacy README](https://github.com/raisingkaines/FreeRealms-Legacy/blob/main/README.md).
