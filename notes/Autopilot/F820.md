## What changed (one block per finding)

2. **MINOR, vacuous "raised need" assertion.** `tests/pet_wired.rs` no longer pins the constant
   100.0. It records the pre-feed food need from the live roster document, asserts it is below the
   maximum (so the feed has room to raise it), and after the whole-document reload asserts the

   skipped need restore now fails the test (canary 2). The F778 note's claim is corrected.
3. **MINOR, 53/16 clear only covered the active pet.** `PetService::care_tick` used to snapshot
   only `self.pet(active.pet_id)` before `care`. `spend_one` clears an emptied instance from
   **every** pet that fitted it, and `kit_item` does not prevent one instance from being fitted on
   two pets, so the second pet's care panel could keep a ghost food. `care_tick` now remembers
   every `(pet, slot)` whose utility slot holds the food and, after `care`, echoes a 53/16 clear
   for each slot that actually lost it. It derives the echo from the post-apply roster, so it
   sends nothing for a slot that was not cleared. Regression test
   `tests/pet_care.rs::feeding_the_last_food_clears_every_pet_that_fitted_it` fits one food
   instance on two dogs, feeds the summoned one, empties the stack, and asserts both roster slots
   are `None` and exactly one clear per slot is sent (`pet 1 slot 6`, `pet 2 slot 6`); the bowl
   stays. The existing one-pet clear test still passes unchanged.
4. **MINOR, (R) not marked in the source comment.** The comment now marks the care-panel inference
   `(R)` and keeps the recovered client citation (`sub_B5CE60` case 16, write at `00b5ea69`). The
   `care_tick` doc comment now says an emptied stack echoes every slot that lost it.

## Client evidence (IDA this pass)

The clear echo now addresses pets other than the summoned one, so this pass re-checked that the
client's 53/16 handler looks a pet up by the id word and writes that pet's record:

- `disasm 0x00b5ea2b` (`sub_B5CE60` jumptable case 16): calls body reader `sub_B58140` at
  `0x00b5ea45`; at `0x00b5ea55`-`0x00b5ea60` pushes the parsed pet id (`this+16`, the second word)
  as the argument to `sub_9F8D30` on the pet collection (`this+0x64`) to find the record;
  `0x00b5ea69`-`0x00b5ea77` loads the item word and the slot word into
  `[record + slot*4 + 0x98]`. The lookup is by the carried pet id and the slot is not
  bounds-checked, so a clear for any owned pet updates that pet's record - which is why the fix
  sends one per cleared pet and still refuses no-echo for out-of-range slots.
- `decompile sub_B55B80`: after the `sub_B55280` header, the body is u8 flag at +12, u32 pet id at
  +16, u32 slot at +20, u32 item at +24. This is the field layout `pet_utility_packet` writes.
- The 53/16 wire itself is unchanged (flag, pet, slot, item), so no byte-level format change.

## Threat note (secure-code-guardian)

Attack surface of the changed code: a hostile client can fit a 53/16 utility, send a 53/19 feed,
and wait for the world tick.

- The only new output is server-authored 53/16 clears, emitted after a feed the server itself
  applied through `care` (owned instance, fitted in the active pet's slot, recorded food rule, one
  unit consumed). The client cannot name the pet, slot or item of a clear; both come from the
  server roster and the item the feed actually consumed.
- Fitting the same instance on two pets is allowed and is exactly the reviewed case; the server
  clears the real state and now tells the client about every cleared slot. A client cannot make a
  clear appear for a pet it does not own: `care_tick` only reads `self.roster`.
- A feed whose food left the bag still reaches no `care` and sends no clear (existing test
  `a_feed_announces_the_meal_once_and_a_food_that_left_the_bag_says_nothing`), so a forged 53/19
  cannot spend a slot or trigger a clear.
- No client-supplied quantity, id or result is trusted, and no new refusal path was added, so there
  is no new "refusal changes something" surface.
- No secrets, names, chat text or lab paths were added.
