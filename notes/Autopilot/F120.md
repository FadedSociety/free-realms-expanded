# F120: T029 fishing hour-cap reconnect blocker

## Review finding

The single BLOCKER in `277c27a-T029.md` was correct: `FishingService::reset_all()` cleared
both the session count and the rolling-hour timestamps, and a fresh `Gameplay` started with
no history. A character could therefore reconnect and bypass an enabled hourly cap.

## What changed

- `src/fishing_service.rs`: reconnect now clears only `PaidCatches.session`. The rolling-hour
  timestamps survive `disconnect`, `reset` and `reset_all`. `hour_history` and
  `restore_hour_history` transfer the character ledger; restore rejects an oversized or
  out-of-order history and leaves the existing ledger unchanged on refusal.
- `src/gameplay.rs`, `src/gateway.rs`: narrow accessors connect the service ledger to a
  fresh loaded instance without adding it to `GameplayState`.
- `src/bin/osfr-gateway.rs`: `SharedWorld` owns `fishing_hours`, keyed by character. Each
  message restores the gateway's ledger from that state, and each committed outcome copies
  the updated history back. This survives reconnect and save reload for the server process
  lifetime. Committed updates also discard entries whose timestamps left the hour window.
- `data/content/fishing_spots.json`: the cap provenance text now states the hour ledger is
  keyed by character and is not refreshed by reconnect.
- `tests/fishing_entry.rs`: service-level regression proves reconnect clears only the
  session count, preserves hour history, refuses a malformed restore without mutation, and
  resumes payment after expiry.
- `src/bin/osfr-gateway.rs`: gateway regression drives two real sessions over one shared
  world: paid catch, save, fresh load from disk, capped refusal within the hour with unchanged
  snapshot/file bytes, then a paid catch after the hour expires. Inventory, coins and
  Fisherman XP are unchanged by the refusal.

## Reconstructed rules (R)

- The optional hour cap remains an operator policy, not recovered original behavior.
- Hour history is character-scoped and survives reconnect; session-window counts reset with
  the login session.
- A blocked catch takes the no-payout escape path and does not request a save.
- The process-lifetime ledger is not durable across a server restart.

## Threat note

- The client cannot send a timestamp, cap limit, item id or catch result. Its only cap-relevant
  action is a 138/7 reel-in, which requires the server's own 138/6 cast -> bite -> hook state.
- An unauthenticated handshake session carries the template guid (account 1's character guid).
  The lead's owner gate (`313d8cc`) refuses publication; F153's regression ticks such a session
  before login and restores a forged non-empty history, then asserts the ledger is unchanged.
- `restore_hour_history` rejects guid 0, an oversized or out-of-order history and leaves the
  existing ledger unchanged.
- The cap is checked before `apply_grant`; a refused catch pays no item, coins or XP and requests
  no save.

## Checklist (F120 feature; F186-corrected)

1. **A refusal changes nothing:** the gateway regression compares snapshot, save bytes and world
   ledger before/after the capped catch; the lead's restore runs on the live gateway before
   staging, copies only server-owned history, and changes no gameplay state.
2. **Rollback covers all state:** the ledger is in `SharedWorld`, published into `staged_world`
   and installed only after the save succeeds; no shared side table.
3. **Apply deltas, never old snapshots:** only the character's timestamps are replaced; no
   inventory/coin/position snapshot is restored.
4. **Busy rules are mutual:** fishing already has an `Occupation` row; no new activity.
5. **Every entry path is gated:** the cap is in `settle_catch`, reached from the production
   `enter`/`route` path; `begin` is the low-level test entry (T029).
6. **Reachable in production, tested through it:** the regression drives `Session::dispatch_message`,
   `Session::tick`, save/load and a second session.
7. **Survives reconnect:** the test catches, drops the session, ticks a fresh session before
   login, logs in, refuses the capped catch and pays again after the hour.
8. **Every exit path restores the player:** fishing disconnect/reset clears only the session
   count; the ledger is not a lock or location state.
9. **Economy safety:** cap checked before `apply_grant`; no client quantity; blocked catch pays
   nothing and the test asserts inventory/coins/XP.
10. **Wire format:** unchanged; 138/2, 138/6, 138/7 bodies match `00b6b720`, `00b6b7e0`,
    `00b6b8b0`; result reader `00b66be0`, presentation `00cd0150`.
11. **Unique ids:** none allocated by this change.
12. **Others see changes:** not applicable; private accounting only.
13. **Content end to end:** paid catch, capped refusal with notice, paid catch after expiry.
14. **Values in data:** cap and window in `fishing_spots.json`; `HOUR_WINDOW_MS` is the
    reconstructed 3,600-second window (F186 records the compiled constant as a lead-owned
    `(R)` exception because the hub sweep and the service must agree).
15. **Canaries break production:** two F153 canaries changed production code and failed their
    tests; both were reverted (details in `F153.md`).
16. **Hands off session plumbing:** F120 failed this finding. The lead fixed the ownership gate
    in `313d8cc`; F153 then failed it again by rewriting the staged transaction and publication
    policy, and **F186 corrected that** by reverting the hub to the lead's shape. The current
    tree keeps creation/teardown/save ordering and the `313d8cc` policy unchanged.
17. **One player's error never stops the server:** restore errors return from that session's
    dispatch only; the lead's publication cannot fail; the whole-ledger sweep is the lead's
    existing per-commit path, not a new one.
18. **Type rules live on the type:** with F186's revert the ledger is again the lead-owned
    `BTreeMap` field; `PaidCatches` field docs still explain session vs hour. A single-owner
    type needs lead sign-off.
19. **Hot paths cheap:** per dispatch one Vec is cloned for the lead's restore; per commit the
    lead's whole-ledger retain sweeps expired timestamps. The shipped cap is disabled, so the
    common Vec is empty.
