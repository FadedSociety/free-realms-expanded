# T520 — Style cards, part 3: store try-on (42/11) and 35/65 at world entry

Status: implemented, focused gates green. Native store check is the lead's (3 steps in the brief).

## What changed

- `src/gameplay/style_card_use.rs`
  - `Gameplay::handle_style_card` now accepts 42/11. A preview is any type 12 catalogue row that
    passes the same eligibility checks as a use (`StyleCard::record`: gender usage, model/race and
    a known mapping); **ownership is not required** because it is a store try-on. A successful
    preview returns exactly one 35/39 with the sender's guid and preview 1, to that sender only.
    Every refusal (unknown definition, non-type-12, wrong gender/race, unsupported slot, no tables
    or no look yet) returns an empty `Outcome`: no reply, no state change, no card spent. The
    preview path runs before any mutation, so `changed` stays false and `nearby` stays empty.
  - `Gameplay::customization_data()` builds the 35/65 for the current look (`style_cards::customization_data`).
    `None` when the client tables are off (server without `--resources`) or no identity/look is
    loaded yet.
- `src/gameplay.rs` (+2 lines, no other change): `out.replies.extend(self.customization_data());`
  in both `initialize_world` initialization branches — the opening campaign next to the ability
  activation, and the no-opening branch (the round70 fixture and any server without
  `opening.json`). The special scene loads (housing/fishing/soccer/kart) return earlier and do not
  send it; they are reached after a normal entry, and every later zone entry runs this function.
- `tests/style_card_preview.rs` (new): `customization_data_at_world_entry` (human and pixie: one
  35/65, record ids 0-6+8 / 0-6+7+8, item ids 0, every field decoded by a reader-faithful decoder;
  no repeat on a replayed load, tick or 125 location report; none without tables),
  `preview_reaches_self_only_and_saves_nothing`, `refused_previews_send_nothing_and_change_nothing`,
  `customization_data_after_relog_has_the_new_look`.
- `src/bin/osfr_gateway/style_card_use.rs` (+1 test): 42/11 through the real session dispatch with
  a near viewer: one preview to the player, the viewer gets nothing, snapshot and save file
  byte-identical.
- `tests/app_fuzz.rs`: one 42/11 seed (`gameplay.handle_in_world`, no new selector).
- `src/style_cards.rs` needed no change: part 1's `customization_change`/`customization_data`
  already encode both packets; the preview reuses them.

## Security threat note (secure-code-guardian)

Hostile 42/11 input is one client-chosen i32 definition id (plus the envelope). What it can try:
- **Unknown/not-a-card/ineligible id** → `definition_record`/`StyleCard::from_row`/`record`
  refuse; the handler returns an empty outcome (asserted by snapshot equality in
  `refused_previews_send_nothing_and_change_nothing`). No information is echoed back, so the
  request is not an item-existence oracle.
- **Forged strings/params** → impossible: the returned record's slot, mapping, gender and every
  string come from the catalogue row and the client tables, never from the packet. Mapping strings
  are bounded (≤512 bytes, no NUL) inside `StyleCard::record`.
- **Ownership abuse** → no ownership is required, but a preview never consumes, grants or saves
  anything; the only state it can touch is the sender's own client-side preview. It cannot reach
  another player: the guid is the session's own `character.guid` and the packet is returned in
  `Outcome.replies` only (never `nearby`); the bin test drains a near viewer and gets nothing.
- **Flood** → no new limiter (per the brief). The generic per-connection packet/byte budgets still
  apply; `ActionBudgets` does **not** list family 42 (that is W173-adjacent chat settings, and the
  brief's "per-account application budget (W173)" does not exist for 42), so nothing new was added
  rather than inventing a limiter.
- **Malformed length** → ends the session, the same rule as every other inventory request
  (`decode_request`), so the gateway never sees a partially applied preview.
- 35/65 content is entirely server-owned (saved look or identity); client input never reaches it.
  Nothing is persisted by this task.

  already shown (slots 0-6/8). A server preview reply for the same look is harmless.
