# T442 - Launcher: the launched client finds its asset manifest (L024 part 1)

## What changed

Option (a) from the brief: a loopback asset responder that lives as long as
the launched client.

- New `launcher/src/assets.rs` (`Responder`). It binds `127.0.0.1:0`, answers
  `/manifest.crc` with `crc32,len\r\n` of the client's own `Assets_manifest.txt`
  (read once at start), and answers `/<digits>/<name>[?crc]` with the bytes of
  `<client>/indirect-assets/<name>`. Everything else gets 404. It serves until
  dropped, at most 64 connections at once. Each connection must deliver its
  whole request head within one absolute 5 s deadline, and file bodies are
  streamed rather than loaded into memory.
- `launcher/src/lib.rs`: only the wiring. `LaunchPlan::build` starts the
  responder and sets `IndirectServerAddress=<responder url>` in `Baseline.ini`.
  Every other URL still goes to `127.0.0.1:9`. `launch(self)` returns
  `(Child, Responder)`, so the responder lives as long as the client.
- `launcher/src/main.rs`: `Launcher.child` holds `(Child, Responder)`. The Play
  message now says to keep the launcher open. If `try_wait` fails, the launcher
  now keeps the child and its responder, because the client may still be
  running. Before, it dropped both.
- `launcher/src/patch.rs`: `valid_path` is now `pub(crate)`, so the responder
  uses the same filename policy as patching.
- `launcher/README.md`: a paragraph on the responder.
- `launcher/src/tests.rs`: five new tests, plus one changed assertion in
  `preparation_preserves_inputs_backs_up_and_filters_auth`.

An earlier builder was cut off and left this diff uncommitted. I reviewed it
and kept it. I then added the hard-link refusal and the connection cap, and
changed the lamp request to the `.dds.z?crc` form the client really sent.

### Review fixes (lead review, round 1)

- **Blocker: absolute deadline for the request head.** The reviewer was right.
  The old `serve()` had a 5 s timeout per `read` call inside
  `BufReader::read_until`, so a sender that dribbled one byte every few seconds
  kept its slot for up to about 8192 x 5 s. Now there is one loop. Before each
  read it sets the read timeout to whatever is left of a 5 s deadline (the same
  idea as `remaining(start)` in auth.rs). It stops at `\r\n\r\n`, at 8192
  bytes or at EOF, and then parses the first line. The client always ends its
  head with `Host: %s\r\n\r\n` (0x00d31140, format string at 0x0183f034), so
  `\r\n\r\n` is the right terminator. Reading the whole head before replying
  still avoids the reset that closing on unread bytes would cause. New test:
  `trickled_request_cannot_hold_a_slot`.
- **Bodies stream** (minor). `body()` returns the file's length (from its
  metadata) and a `File::take(length)` reader, which `io::copy` sends. A held
  slot now costs one copy buffer instead of the whole body (up to 64 MiB each
  before). `LIMIT` now bounds only the one-time read of `Assets_manifest.txt`.
- **Accept loop** (minor). An accept error now sleeps 100 ms, so a lasting
  error such as WSAEMFILE cannot busy-spin a core. A `Slot` drop guard frees
  the connection slot however the thread ends, panics included. Connection
  threads start through `thread::Builder::spawn`: if a thread cannot start, the
  closure (and with it the guard) is dropped and the accept loop keeps going.
  Before, `thread::spawn` would have panicked inside the accept thread and
  stopped the responder.
- **Tests** (minors). `get()` now compares the `Content-Length` header line
  exactly instead of as a substring. The unconditional
  `!Baseline.ini.exists()` assert is gone: `build` never writes, so it could
  not fail. New `junction_asset_folder_is_refused` makes `indirect-assets/`
  itself a junction to a folder outside it, and asserts a 404.
- **Nit.** The tuple binding for `folder`/`stopped` is now two plain `let`s.
- **main.rs `try_wait` error** (minor). See the main.rs bullet above.
- **Not changed:**
  - `regular()` still compares paths case-sensitively, so a hand-made
    `Indirect-Assets` folder would make every asset 404. Canonicalizing the
    folder first would resolve a junctioned folder too and so defeat the
    junction refusal. The patcher creates the folder with the manifest's case.
    This is the same for every launcher file checked by `regular()`.
  - The `Content-Type` header stays, for parity with the harness.

## Client evidence (IDA, ida_query)

- Request names: the client's strings include `manifest.crc` (0x018858a0) and
  `manifest.txt.z` (0x01885920), and nothing else for the manifest. The
  request is sent by 0x010a2060, which calls `sub_10A1E00("manifest.crc", ...)`.
- Reply parsing: 0x010a1980 splits the manifest.crc body at `,` (44) and passes
  CRC and length to 0x0109bd00.
  - On a non-200 reply it logs "Failed to request url ... retrying" and tries
    again while it has retries left.
  - On a final failure it passes (0,0), and 0x0109bd00 stops with "Failed to
    receive the manifest crc file." That is the code-27 exit from run
    20261008T015537Z.
- 0x0109bd00 formats its local file as `%s_manifest.txt` (0x018851b4). If that
  file's CRC (`sub_704A40`) equals the served CRC, it keeps the local manifest
  (`sub_109B650`). Only on a mismatch does it ask for `manifest.txt.z`.
- Run 20261021T193008Z shows that standard CRC-32 matches: the harness served
  `123886846,9479368` (zlib.crc32), and the client's only manifest request out
  of 339 was `/manifest.crc`.
- Asset URL: 0x010a09c0 builds `%03u/%s` (0x01885918) from a name hash mod 1000
  and adds the CRC query. Harness requests look like
  `/960/sg_bixie_fence_tall_01_lod0.dme.z`.
- GET line: 0x00d31140 sends `GET %s HTTP/1.1` (0x0183f034), then an optional
  User-Agent and `Host`. 0x00d30100 copies the path after the host without
  escaping, so names with spaces arrive raw (648 manifest names have spaces).
- Status line: the client accepts both `HTTP/1.0 ` and `HTTP/1.1 ` (0x0183ef80,
  0x0183ef8c) and reads `Content-Length:` (0x0183eef8).
- Body: 0x0109b400 strips `.z` and marks the asset compressed, which means the
  A1B2C3D4 envelope read by 0x010ebee0. Other names are raw.
- Harness reference: `scripts/run-local-baseline.py:170-226`. It also answers
  one request per connection with HTTP/1.0 status and Content-Length, then
  shuts down writing. The responder copies this behaviour, which was proven in
  run 193008Z.

## (R) choices

- **Assets folder.** The served folder is `<client>/indirect-assets/`, not "the
  bundle's asset folder". The launcher runs on a friend's machine, which has no
  bundle, and today's bundle (`scripts/bundle/make_bundle.py`) has no client
  asset folder. A realm's pinned patch manifest can fill
  `indirect-assets/<name>`, because patch paths may contain `/`.
- **Bodies are served byte for byte.** A `.z` file must already be the wire
  envelope. This keeps the launcher free of a zlib dependency (Cargo.toml must
  not change). The harness compresses with zlib level 6, and in run 193008Z all
  6 of its envelopes came out exactly the size the manifest lists
  (`wire_bytes == manifest_wire_bytes`). So whoever builds the payload can
  produce identical files the same way.
- **`/Assets_manifest.txt` is not served,** although the brief lists it.
  - The client never requests the manifest by its local name; see the strings
    above.
  - The CRC is computed from the same file the client hashes, so the mismatch
    path (`manifest.txt.z`) cannot be reached.
  - Patching must finish before Play (`patch_allows_play`), so the file cannot
    change between building the plan and the client's check.
- **Names** must pass `patch::valid_path`, be a single component under a
  numeric bucket, and be a regular file that is not linked (no symlink,
  junction or hard link) and resolves inside the folder (`regular`). There is
  no `%` decoding, because the client never escapes.
- **Limits.** `LIMIT` is 64 MiB per body; the largest manifest wire size is
  11,053,184 bytes. `CONNECTIONS` is 64; past that, a connection is closed
  without an answer and the client's retry covers it. The request head must
  arrive within one absolute 5 s deadline (`HEAD_TIME`). The write timeout is
  30 s per write call. `LIMIT` (64 MiB) now applies only to the in-memory read
  of `Assets_manifest.txt` (9,479,368 bytes in run 193008Z); asset bodies
  stream, so they have no size bound.

## Threat note

Any local process can reach the port. The listener binds 127.0.0.1 only.

- **Reads stay inside the folder.** A request can only read a non-linked
  regular file inside `indirect-assets/` with a patch-safe name. A hard link is
  refused because it could alias any file this user can read, such as key
  files.
- **Refused targets** (tested): `..`, `\`, `%2f`, `%5c`, `%2e%2e`, absolute
  Windows and forward paths, `C:%5C...`, the absolute-form `http://...`, nested
  paths, `NUL`, `::$DATA`, root files like `/ClientConfig.ini`, and non-GET
  methods.
- **Threads.** A local process can tie up at most 64 threads.
  - **Request side.** A connection that has not sent its whole head within 5 s
    of being accepted is closed, however slowly its bytes arrive (tested with a
    byte every 400 ms).
  - **Reply side.** The write timeout is 30 s per write call, not an absolute
    deadline. A local process that asks for a large asset and then reads it
    slowly (a little at least every 30 s) can keep that slot until the whole
    body is sent. Memory stays bounded, because bodies stream through one copy
    buffer. I did not add an absolute reply deadline. The client reads replies
    through its routed-packet handler (`HttpConnection::OnRoutePacket`
    0x00d30680), and I could not establish how fast it drains a large body, so
    a fixed deadline risks cutting off a real download.
  - **Starvation is still possible.** No per-connection bound stops a local
    process that simply reconnects. 64 sockets that each idle or trickle for
    5 s and then reconnect keep every slot busy, and connection 65 (the
    client's) is closed unanswered. The deadline raises the cost from one
    connect per slot per about 11 h to one every 5 s, which is still trivial.
    The only real fix is to serve the client's process alone: map each peer
    port to its owning PID (`GetExtendedTcpTable`) and compare it with the
    `Child`'s PID. That is a lead decision. A local process that wants to deny
    the game can already do so in other ways, such as filling the disk.
- **Nothing else is touched.** The responder never writes, never parses
  anything beyond the request line, and never touches login, keys, AUTH2 or
  net_policy.

## Checklist

1. **Refusal changes nothing.** The responder never writes. A missing
   `Assets_manifest.txt` makes `build` fail (tested). `build` never writes
   files (only `apply` does), so the test no longer asserts that
   `Baseline.ini` is absent: that assert could not fail. Refused requests
   return 404 with an empty body (tested, with a canary).
2. **Rollback.** Not applicable: the responder holds no state that could be
   rolled back. `apply()` rollback is unchanged.
3. **Deltas.** Not applicable: no inventory, coins or position.
4. **Busy rules.** Not applicable: launcher, not gameplay.
5. **Entry paths.** There is one: Play calls `build`, `apply` and `launch`
   (trace above). Screenshot mode never builds a plan.
6. **Reachable in production.** `Launcher::play` uses `LaunchPlan::build`. The
   test drives `build` and `apply`, reads the URL back from `Baseline.ini` as
   the client does, and sends raw GETs in the client's request format.
7. **Reconnect.** Not applicable. The responder lives in `Launcher.child`; when
   the client exits, `child` is cleared and the drop closes the listener
   (tested).
8. **Exit paths.** If the client exits, the responder drops. If launch fails,
   the plan and its responder drop. If the launcher closes, the responder
   drops; the README and the Play message say to keep it open. If `try_wait`
   fails, both are kept and Play stays disabled, because the client may still
   be running. Restarting the launcher clears that state.
9. **Economy.** Not applicable.
10. **Wire format.** Every field is cited above (0x010a1980, 0x0109bd00,
    0x00d31140, 0x0109b400). The byte-level test checks
    `3421780262,9\r\n` = zlib.crc32(b"123456789"), as the harness computes it,
    plus an exact status line and Content-Length.
11. **Unique ids.** Not applicable. Each launch binds its own ephemeral port.
12. **Others see changes.** Not applicable.
13. **End to end.** Not verified natively; the lead keeps the native run
    (L024 step 5). Locally the test proves that manifest.crc and the
    fence/lamp/space-name requests get the right bytes.
14. **Values in data.** `LIMIT`, `CONNECTIONS` and the timeouts are compiled
    (R) safety bounds, not gameplay values.
15. **Canaries.** All four canaries broke production code (see Gates).
16. **Session plumbing.** Not touched.
17. **One error never stops the server.** A failure on one connection ends only
    that connection's thread (`let _ = serve(..)`). The `Slot` guard frees its
    slot even on a panic. A thread that cannot start is skipped
    (`thread::Builder`). An accept error backs off for 100 ms and the loop
    continues. Nothing calls unwrap on request data.
18. **A type's rules on the type.** `Responder` documents its lifetime rule.
    `Launcher.child` carries a doc comment saying the responder lives exactly
    as long as the client.
19. **Hot paths.** No server tick is involved. Each request holds an 8 KiB head
    buffer and streams its body through `io::copy`, so memory per connection
    does not grow with the file size. The head scan is at most 8192 bytes per
    read.

## Open gaps

- **48 manifest names can never be served.** They contain `& ' ! + ^`, for
  example `sg_starting_housing_trim&floor_01.dds.z` and
  `sg_starting_housing_walls&roof_01.dds.z`. `patch::valid_path` refuses them,
  so they can be neither patched nor served. Neither is in the local packs
  (catalog.tsv). Widening the policy is a lead decision on the patch filename
  rules.
- **Proxy mode is not handled.** If the client has a proxy set
  (0x00d30100 `this+13 > 0`), it sends the absolute URL and gets 404. The
  harness does the same, and no proxy is configured by default.
- **The payload is not built yet.** Nothing produces `indirect-assets/` today.
  The 6 assets that harness run 193008Z served, plus the creator tables and
  `custom/`, are L024 step 3 (client preparation).
- **Reply-side slow reader and reconnect starvation** (lead decision; see the
  threat note). The fix would be a peer-PID check.
- **The native run is the lead's.** It should confirm that the code-27 exit is
  gone and that no new 404s appear compared with run 193008Z.
