# T790: an `any_of` objective counts any one of several targets

## What changed

An objective can now name 2 to 8 same-family alternatives and count all of them toward one
total. The alternatives are server ids only; the client still receives the existing 49/9 and
49/10 counters, so no packet shape changed.

- `src/content.rs`: `ContentGoal::AnyOf { id, count, alternatives, source }` (JSON kind
  `any_of`) with `AnyOfTarget` = `TalkToNpc { npc_id }`, `CollectItem { item_id }` or
  `GatherResource { resource_id }`. `validate_any_of` is the one authored rule: 2..=8
  alternatives, one family, positive unique targets, count 1..=MAX_COUNT. Both quest loaders
  call it. The flat loader additionally resolves talk ids in the NPC set and collect ids in
  the item set, exactly like the plain kinds; gather ids stay the quest engine's job.
- `src/quest_engine.rs`: `ObjectiveKind::AnyOf { alternatives: Vec<ObjectiveKind> }` holding
  leaf kinds. `event_matches` returns the first matching alternative's count (a
  `CollectItem { quantity: 3 }` counts 3; one event never counts twice). `valid_objective_kind`
  refuses a nested `any_of`, a non-leaf alternative, a mixed family and out-of-bounds lists.
  `ContentGoal::AnyOf` maps to it in `definition_from_content`.
- Talk rules now live on the type: `ObjectiveKind::talk_targets` / `talks_to`. The quest-NPC
  index, the T543 conversation lookup, the turn-in/end-screen target rule,
  `quest_markers::marker_for` and `quest_journal::locate` all use them, so a talk any-of
  marks every alternative and pins the first one.
- Tests: new `tests/quest_any_of_objectives.rs` (13 tests at T790: the named edge cases, a
  real paid fishing catch, ordered quest, reload, marker rule; F862 added the lower and count
  bound tests, 15 now); `tests/enabled_quest_reachability.rs`
  now grades `any_of` leaves against the NPC, item and gather sets with three scratch
  canaries; `tests/tracked_target.rs` pins the first talk alternative;
  `tests/support/fishing_packets.rs` gained the minimal fish-inventory fixture.

### (R) rules

- (R) The 2..=8 bound, the one-family rule, positive unique ids and the count bound are
  server sanity bounds; every actual alternative and total comes from the quest JSON. The
  census row 8 names up to three targets, so eight is generous headroom.
- (R) Journal and marker semantics follow the existing single-target rules: the pin is the
  first talk alternative (there is no recovered client "any" marker), while every talk
  alternative gets the '?' marker.
- (R) `event_matches` first-match (not sum) is the no-double-credit rule. The content loaders
  refuse a repeated target; the runtime keeps first-match as defence in depth, which
  `one_event_counts_once` exercises with a hand-built duplicate list.

## Threat note (secure-code-guardian)

A hostile client cannot invent an alternative, a count or a family: all three are
server-authored content loaded at startup and validated by both loaders (2..=8, one family,
positive unique ids, count 1..=MAX_COUNT). A client can only cause the ordinary existing
events the plain goals already accept: an in-range NPC Talk, a server-verified inventory
grant (the inventory diff, not a client claim), a server-graded gather, or a server-settled
fishing catch. `validate_event` still bounds every event id positive and every quantity
1..=MAX_COUNT; a non-member id/family returns 0, changes no counter and emits nothing
(`non_member_changes_nothing`, canary-checked). Progress saturates at `required`; a repeat
after completion is a no-op. No new packet parser, no client quantity and no save field was
added.
