# T404: Take Me There answers the client's kind-2 path request

2026-10-21

## Result

The quest panel's **Take Me There** sends a 98/1 path request with kind 2. The
server answered kind 1 only, so kind 2 fell through and the client drew
nothing. `Pathing::answer` (`src/pathing.rs`) now answers kind 2 exactly like
kind 1: the same checks, the same rate budget, the same ground-following path,
with kind 2 echoed in the 98/2 reply so the client hands it to its Take Me
There reader (`009cead0`). Kind 1 is unchanged. Kinds 0, 3, 4 and others are
still "not ours" (`None`), as before.

The brief's premise holds (kind 2 gets no reply). Its guess that kind 2 is a
teleport is wrong: kind 2 asks for a **route**. The point-of-interest teleport
is a separate request the client decides and sends on its own (op-90), and the
existing warpstone code already answers it. No teleport was added.

Changed files (all under `prototype/osfr-tools`):

- `src/pathing.rs`: `KIND_BREADCRUMB` (1) becomes `KINDS` ([1, 2]); the module
  doc now holds the recovered kind-2 flow and drops the wrong "kind 2 is the POI
  teleport request".
- `tests/pathing.rs`: two new tests; kind 2 removed from the "not ours" list.
- `src/gameplay/developer_teleport.rs`: one new test that goes through
  `Gameplay::handle_in_world`; the old "kind 2 is not this module's" assertion
  is removed.
- `tests/app_fuzz.rs`: one more `pathing` seed (the kind-2 request).

## Rules marked (R)

- Kind 2 gets the same reconstructed path as kind 1: a straight line every 5 m
  on the height grid. The original server's route for kind 2 is not recovered.
  The client needs only a start-to-`to` polyline, because it appends its own
  remaining route.
- The reply echoes `aux`. Neither `009cead0` nor the dispatcher reads it; the
  echo of `kind` is required, because the dispatcher routes the reply by it.
- The shared budget of 4 answered requests per second, for both kinds together,
  is unchanged.

## Security note (secure-code-guardian)

A hostile client can send kind 2 with any vectors, as often as it likes. It
gets nothing that kind 1 did not already give:

- The same parse refuses truncated or overlong packets.
- Non-finite values are refused, the 300 m 4D limit applies (overflow refused),
  the start must be within 300 m of the server's own position for the player,
  and both ends must be on the zone's height grid.
- Every refusal is silent and spends no budget, and nothing else changes.
- Kind 2 shares the 4-per-second budget with kind 1, so mixing kinds cannot
  double the rate.
- A reply has at most 61 points (cap 80), so at most 991 bytes go out for each
  55 bytes in.

The server never moves, teleports or rewards anyone for kind 2. A teleport
still needs the separate op-90 request and its warpstone checks.

## Checklist

1. A refusal changes nothing. Kind-2 refusals return before the budget is
   touched. The test sends each refusal 10 times and then gets the full
   budget. The canary is above.
2. Rollback covers all state. The only state is the `Pathing` budget, and it
   changes only on an answer. No shared state.
3. Apply deltas, not snapshots. Nothing is restored over live state.
4. Busy rules are mutual. Does not apply: this is no activity and changes no
   player state, the same as kind 1. The client gates its own teleport branch,
   and the server's op-90 handler has the busy table.
5. Every entry path is gated. Both client entry points (`00c17c70` and
   `00c17c00`) reach the server only as this 98/1 kind 2, through the one
   `answer` that holds every check.
6. Reachable in production, tested through it.
   `take_me_there_is_answered_like_the_breadcrumb` drives
   `Gameplay::handle_in_world`.
7. Survives reconnect. Does not apply: no persisted state. The budget is
   per-session, like kind 1.
8. Every exit path restores the player. Does not apply: the player is never
   moved or flagged.
9. Economy safety. Does not apply: no items, coins or rewards.
10. Wire format matches the client reader. The reply is read by `008faf30` and
    consumed by `009cead0`. The byte-level test checks the exact 47-byte reply
    for the 5 m case (header, kind 2, aux, count 2, the client's own two
    vec4s).
11. Unique ids. Does not apply.
12. Others see changes. Does not apply: the trail is the requester's own.
13. Content works end to end. The reply carries a non-empty path for an
    on-grid request, and the client appends and draws it. The native re-check
    (click at 350 m) is the lead's step.
14. Values live in data. No new values. `STEP`, `MAX_PER_SECOND` and the range
    are the existing W164 constants, unchanged.
15. Canaries break production code. The canary reverted the filter in
    `src/pathing.rs`.
16. Hands off session plumbing. Untouched.
17. One player's error never stops the server. Refusals are `Err` values. No
    `?` path changed, and no tick code changed.
18. A type's rules live on the type. `KINDS` sits next to `answer`, and its doc
    names both writers.
19. Hot paths stay cheap. One extra compare per 98/1 packet.
