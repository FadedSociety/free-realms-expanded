## What changed

- `prototype/osfr-tools/src/identity.rs` (lead-only; needs the lead's sign-off):
  - `Resources::load` reads the two pinned community tables
    (`CharacterCreateCustomizationSkinTone.txt`, `CharacterCreateCustomizationFaceType.txt`)
    from the resource root, checks their SHA-256 against `PINNED_CREATOR_TABLES`, and joins each
    row's ITEM_ID through `CharacterCreate/CharacterCreateItemMappings.txt` to the item
    definition's PARAM2. The result is the allowed skin ids {1..6} and head ids {1,2,3}.
  - `PINNED_CREATOR_TABLES` holds the same two (path, SHA-256) pairs as the overlay's `OVERLAY`
    in `scripts/bundle/client_overlay.py` (T443). The test tree is built by that overlay's own
    `install`, so re-pinning or moving a table on one side alone fails the test (see Gates).
  - `Resources::resolve` refuses a creation whose skin (choice 5) or head (choice 1) is not in
    those sets. `account::create_character` turns that into create status 2 (Failed) before
    `insert_character`, and `LoginService` only saves the staged store on success. A refusal
    writes nothing.
  - Fail closed: if the tree holds any allow-list input (item mappings or either pinned table),
    it must hold all of them, hash-matching and fully resolving, or `Resources::load` fails. A
    stock client tree therefore needs the overlay installed. A tree with none of them (synthetic
    fixtures, today's bundle `login-resources`) creates unfiltered, as before.
  - Saved identities are not re-validated. The check runs only at creation.
- No launcher or harness change. T443 already installs SkinTone/FaceType at `Resources/` root and
  StartingSets in `Resources/CharacterCreate/` through `client_overlay.install`, which the
  harness calls before it starts osfr-login with `--resources client/Resources` (both under
  `native_login`, run-local-baseline.py:83-87 and :222-233).
- New `prototype/osfr-tools/tests/creator_allow_list.rs` (3 tests). The fixture is the harness
  tree: stock client tables from `lab/working` (including the stock root SkinTone/FaceType),
  then `client_overlay.install` on top, exactly as the harness does.
- Work item 049: the allow-list test asserts the derived sets equal `SUPPORTED_SKIN_TONE_IDS` and
  `SUPPORTED_HEAD_IDS` from `src/restoration/piece_049.rs` (included by `#[path]`, as
  `tests/piece_049.rs` does). The BOUNDARIES text in that module and its test now says login
  creation enforces those sets (derived from the pinned tables) and refuses head 4.
- `tests/login.rs`: a comment on the ignored private oracle
  `private_actual_native_creation_resolves_against_supplied_resources` says
  `OSFR_CREATOR_RESOURCES` must be a client `Resources/` with the overlay installed. A stock tree
  now fails `Resources::load` there.

## Client evidence (IDA, ida_query)

- Creation packet: `sub_705A10` (called at 0x007187af) -> `sub_956590` -> writer 0x00954bd0
  (called at 0x00956602). The writer emits four strings (record +0x0/+0x24/+0x48/+0x6c), then
  21 dwords from +0x90. The record sits at ebx+0x5387c, so choices are 0x5390c..0x5395c. This
  matches `NativeCreation::decode`.
- Choice 1 (head, +0x53910) is set at 0x0071875b..0x00718768, choice 2 (hair) at 0x00718775,
  and choice 5 (skin, +0x53920) at 0x00718796..0x007187a9. Each one is `[definition+0x218]`.
- +0x218 is ItemDefinitions column 25 (PARAM2). The row parser 0x0072e050 stores the 26th
  token at `this+536`, and the column order matches the file header (SLOT -> +48, as the
  server already reads).
- Item-mapping rows (parser 0x007255e0): column 0 is stored at +20 and ITEM_ID (column 5) at
  +36. Loader 0x00723860.
- ChangeItem 0x0071f030: case 1 (skintone) and case 9 (head) go mapping -> `+36` definition ->
  `+0x218` -> SkinToneMappings/HeadMappings alias (`sub_725A70`).
- Table locations: 0x008ec05d pushes "Resources/" to 0x00982f10. That function formats
  "%s%s.txt" (0x009830c9) from the name built by 0x0097f570 ("CharacterCreateCustomization" +
  category suffix, 0x0180b638). So the customization tables are read from `Resources/`. The
  mapping and definition tables come from `./Resources/CharacterCreate/` (0x017e802c, 0x0071efb0).

- Data check (supplied tables): the pinned SkinTone rows give ITEM_ID 214..219 -> 77484..77489 ->

## Threat note

A hostile or modified client can send any 21 integers in the opcode-5 create body. Before this
change, any id present in SkinToneMappings/HeadMappings passed (skin 7/8, China heads 4..8). Those
appearances reference textures that are missing from the delivered packs. Skin 8 crashed a native
first-profile load (Character Creation Audit), so another player's client that draws the character
could fail too. Now the server accepts only ids that the hash-pinned tables offer. A tampered or
unpinned table on the host fails startup instead of widening the list.

## (R) choices

- (R) The allow-list is a flat set per field (skin ids, head ids), not per race/gender row.
  HeadMappings 1..3 are `<race>_<gender>` templates and every pinned row reaches only those ids,
  so a per-row check would refuse nothing more today.
- (R) Trees without any allow-list input stay unfiltered. This compatibility rule keeps the
  synthetic fixtures and the current bundle working. See the open gaps.
- Derivation from the pinned tables (the brief's choice) rather than piece_049's constants: the
  constants would also cover the bundle without a tree. The test asserts both agree, so either
  can become the source later; that choice is the lead's.

## Checklist

1. A refusal changes nothing. The test snapshots every file under the temp root (outside the
   client tree) before 6 refused looks and asserts equality after each one. The character list
   stays empty, and an allowed look then creates. Canary C breaks it.
2. Rollback covers all state. Creation is staged on `store.clone()`, and the refusal returns
   before `insert_character`. No side tables.
3. Deltas, not snapshots: does not apply (no payouts or positions).
4. Busy rules: does not apply (login-time creation, not a world activity).
5. Every entry path is gated. The only path to `resolve` is `LoginService::handle` (opcode 5) ->
   `account::create_character`, for both dev and key-pair logins. Per the graph, there is no
   second creation path.
6. Reachable in production and tested through it. The refusal test drives `LoginService::handle`
   with a real opcode-5 request on the harness tree built by the overlay's own installer.
7. Survives reconnect: does not apply (nothing is stored on refusal, and the allow-list is
   rebuilt from files at every load).
8. Exit paths: does not apply (a refusal leaves the session in the creator with status 2, as
   before).
9. Economy safety: does not apply to coins or items. Client ids are validated against
   server-side tables only.
10. Wire format: unchanged. The field mapping is cited above (0x00954bd0, 0x007186a4..0x007187a9).
    The existing login tests cover encode/decode.
11. Unique ids: does not apply (guid allocation is unchanged).
12. Others see changes: does not apply.
13. Content end to end: an allowed look creates and replies `create_reply(1, 1)`.
14. Values in data: the allow-list comes from the pinned tables, not from constants. The only
    constants are the two pins, kept equal to `OVERLAY` by the test.
15. Canaries break production code: A edits `client_overlay.py`; B, C and D edit `identity.rs`.
16. Session plumbing: untouched.
17. One player's error never stops the server. A refusal is an `Err` that becomes status 2 for
    that request. osfr-login calls `Resources::load` at startup (osfr-login.rs:793), for each new
    UDP session (:475) and, in key-pair mode, before every authenticated request
    (`service_for`, :767). A bad tree fails startup. A tree that changes mid-run fails the
    affected session or request (a `Session::new` error is dropped at :860; a failing
    `handle` removes that session at :872), not the server.
18. A type's rules live on the type: `Resources::pinned_looks` documents when it is `None`; the
    order of `PINNED_CREATOR_TABLES` is documented against `[skins, heads]` in `resolve`.
19. Hot paths: one `BTreeSet::contains` pair per creation request. Each `Resources::load` (see 17;
    per request in key-pair mode) now also reads ItemMappings (10 KB) and the two tables
    (about 2 KB) and hashes the two tables, on top of the 50 KB ItemDefinitions it already read.
