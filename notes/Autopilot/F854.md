## Client evidence checked in IDA

The F854 change does not add or alter a packet field; it stops treating a value as a
fact. The relevant client behaviour is that a movie payload is forwarded verbatim:

- `sub_C08480` (0x00c08480) is the ActionScript callback wrapper: it takes the string
  from the movie object and calls `sub_9BE6B0` with `length + 1`.
- `sub_9BE6B0` (0x009be6b0, string `MiniGame:SendPayload`) copies that string into the
  outgoing movie payload without parsing or validating it, so a modified cooking or
  smelting movie can send any `FRServer_GameWon` score and any `FRServer_StatUpdate`
  timer. That is why the server must not turn either into a quest fact.
- The 39/18 layout is unchanged from T787; the review re-ran the reader: wrapper
  `0x009b7ec0` -> body `0x009b48b0` (shared `0x009b2340` header, `u8 won`, three
  dwords). No byte was added or removed.
- IDA did not contradict the notes.

## (R) rules and decisions

- (R) A recipe's craft facts are a property of its job: only Blacksmith (forging) has a
  server-side score and timer. Chef and Miner runs report their game id and no result
  fact, even though the 39/18 they send to the client contains display values.
- (R) An authored `require` must set at least one bound. An all-unset requirement is a
  content error, not a legal "no constraint" spelling.
- The derby conversion rule (score dropped outside the sanity bound, no elapsed,
  participant's own knock-out) now lives on `DerbyParticipantResult`; the kart shape
  lives on `MinigameResult::finished_at`.

## Threat note (secure-code-guardian)

What a hostile client can send: the movie payload (`39/14` text via the native
`MiniGame:SendPayload` path) and the `34/16` derby contact records.
- A player with an active cooking or smelting run can send any
  `FRServer_GameWon\t<score>\t0` and any `FRServer_StatUpdate` timer. Until F854 the
  server built a 39/18 from those values and a `min_score`/`max_elapsed_seconds`
  objective could credit from them. Now `apply_craft` withholds the result event for
  those two jobs, and the content gate refuses such a bound on their ids, so neither
  path can turn a client number into a quest fact.
- A forged 39/18 frame is still ignored by the quest funnel: `npc_minigame_win` and
  `npc_minigame_result` inspect only the server-built replies of a settle that already
  paid, and the engines accept only their own in-phase protocol.
- Forging, mining and harvesting measure their own score/time server-side; chess
  reports a server-measured elapsed time and a server-zero score; kart reports its own
  race clock; a paid fishing catch reports no fact.
- Derby contacts remain bounded by the service (fresh pose, range, cooldown, max
  damage, alive victim) and the result row is the owner's. Placement/knock-out are
  server-computed but non-discriminating in the one-human demo (documented).
- No new client input parser, no `unwrap` on client data, no item/coin/role/chat path.
  The new refusal is a load-time `Err`; the settle paths return `Ok` without a credit.
