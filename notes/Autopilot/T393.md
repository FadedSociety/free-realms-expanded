# T393: fishing start dialog never becomes ready

## What changed

The lead's native run (`lab/runs/client-baseline-20261021T083406Z`) showed Go fish! opening the
original start screen whose button stays on "Loading..." forever. The client log stopped after
`MiniGame:JoinGame` / `MiniGame:PlayerStartMiniGame`; it never reached `MiniGame:SetMiniGameReady`.

The fix is in the shared lifecycle `src/minigame.rs`, for every `RunMode::Encounter` run (fishing
type 21 and soccer type 12; Flash runs are unchanged):

- **Offer:** after the 39/16 info record, send **41/107** (EncounterZoneIsReady), the bare encounter
  header `u16 41 | u16 107 | i32 encounter | i32 instance` (12 bytes). This calls the client's
  `HandlerMiniGameStart:setReady`, which turns "Loading..." into Go.
- **Go (39/5):** after the existing 41/2, also send **39/17** `[instance, -1, game]` (the same
  writer Flash runs already use, native-accepted). It is the packet that starts a state created by
  39/16 and shows the game HUD.

`encounter_packet` is a small helper now shared by 41/2 and 41/107. `fishing_service.rs` changes
only doc comments. No reward, range, busy or rule changed.

| File | Change |
|---|---|
| `src/minigame.rs` | 41/107 after the encounter offer; 39/17 after 41/2 on Go; `encounter_packet` header helper |

## Client evidence (IDA, `ida_query.py`)

- `009bfdb0` HandleMiniGameJoinGame (39/16) logs `MiniGame:JoinGame` and calls `009beb70` with its
  third argument 0, so the state's encounter byte `+0x61` is clear and client `+0x700` becomes 2.
- `009beb70` logs `MiniGame:PlayerStartMiniGame`, calls Lua `:setNotReady` and `:show`. It sets
  manager state 3 (ready) only for types 1, 2, 17 and 22, or state 1 (wait for preload) when the
  preload count is positive. Fishing 21 with an empty preload gets neither, so `009bf5e0` never
  reaches its state-3 branch, which is the only other caller of `009b0cc0`.
- `00aa36c0` encounter dispatcher, case 0x6b: `00a9f990` decodes the header only (`008d6690`:
  u16, u16, i32, i32; it must consume the whole body), then calls `009b0cc0`, stores the instance
  at client `+0xc10` and records the encounter id in a set (`009b4350`).
- `009b0cc0` logs `MiniGame:SetMiniGameReady` and calls Lua `HandlerMiniGameStart:setReady`
  (`ScriptsBase.lua` `MinigameStartHandler.setReady` -> `MinigameStartScreen:SetLoading(false)`).
- Go: `MinigameStartScreen:StartGame` -> `Hide(2, true)` -> `Ui.StartPendingEncounter` ->
  `00938f00`. With `+0x700 == 2` it calls `009be7d0` (`MiniGame:RequestStartGame`), which sends
  39/5 through `009bdc60(5, -1, -1)`. Only `+0x700 == 1` (encounter) would send 41/108 instead.
- 41/2: `00aa36c0` case 2 -> `009b9500`, which acts only when `+0x61` is set. So 41/2 alone never
  starts a 39/16 state. The other effects of case 2 are `008a9200` (sets client byte `+0x780` from
  the body's last byte) and `008a8a30` (one loader flag).
- 39/17: `009bf890` case 0x11 -> `009b9550(header id)`. It looks the state up by its id, logs
  `MiniGame:OnGameStarted`, sets `+0x62` and calls `009b6aa0` (`MiniGame:ShowMiniGameHud`).
- Kart already sends 41/107 the same way (`kart_gateway.rs` `loaded`), and the vault guide records
  that "41/107 clears the start-panel loading overlay in native runs"
  (`notes/Build Guides/Gameplay/Kart Racing.md`).

The 41/107 also stores the instance in client `+0xc10`. That value is read only by the 41/108 and
41/109 senders, which run only for encounter-flagged states (`00938f00`, `Minigame Framework.md`
Closed row). Fishing quit stays 39/6 and Close stays 26/42.

## (R) choices

- (R) 41/107 goes out in the same reply batch as the 39/16, before the start screen's SWF has
  finished loading. Kart's native run had ready before `StartHandler:Show` and still showed Go.
  Native re-check is the lead's step.
- (R) 41/2 is still sent on Go, as before. On a 39/16 state its only effects are the two flags above.
- (R) The encounter id is still the spot's game id (`FishingService::enter`, unchanged).

## Threat note

No new client input is parsed. The client's 39/5 is still checked by `MinigameRuns::handle_client`:
the exact 15-byte width, the current instance, group and game -1, and the Offered state. The added
packets are server-built from the server's own run ids. A refused entry (busy, out of range) sends
neither packet and changes nothing (tested).
