## Method

1. **Locale ids versus guide hashes.** The build guides cite raw
   JenkinsLookup2 hashes. Each chosen number was resolved through
   `lab/reports/locale-id-map.json` (`hash_to_ids`), the `{id,text}` row in
   `lab/reports/locale-id-to-text.json`, and a direct line in the read-only
   stock client `lab/working/OSFR.Client/OSFR Client/locale/en_us_data.dat`.
   The test recomputes `JenkinsLookup2("Global.Text.<id>")` with
   `world_text::locale_hash` and requires the hash, the physical line and the
   id-to-text body to agree.
   **Line convention:** the recorded lines are T246's convention
   (`str::lines()`: each `\n` terminates a line, so the locale file's 38
   lone-LF records count as lines). T298/T299 used a `split("\r\n")` index;
   the two indexes differ after a lone LF (for example hash 409884327 is line
   10844 under T246's method and 10829 under the CRLF-split one). This note and
   test use T246's method, matching the research note the task names.
2. **Speaker rule (T246).** A line counts only when (a) the speaker is named in
   the line/identifies themselves, (b) the region/job guide's quest row names
   the NPC as the giver and the line is that quest's intro/offer speech, or
   (c) the guide quotes or lists the line for that NPC. Near-lines and
   third-person sentences that merely name the NPC were rejected.
3. **Quest-offer inference `(R)`.** For Ranger Ricardo, Maple Sugarleaf and
   Uncle Irving the greeting id is the quest record's
   `intro_text_string_id` (`chef.json` 3050012, `card_duelist.json` 3040028,
   `adventurer.json` 3000018), whose giver is bound to the NPC in that record;
   the guide's quest row independently names the same giver. The quest intro
   binding is itself reconstructed (the quest records tag the
   intro/description/end-text ids as T-1/T+1/T+2 backfill `(R)`), so the
   speaker link for those three is inferred, following T246's precedent.
   Hartley's guide row marks the giver "by wording"; Papa Salt, Bo and Tamara
   have first-person offer lines in the same client block as their quest
   objectives.

## Security threat note (secure-code-guardian)

- Hostile client input on this path is the existing 26/8 target GUID and the
  26/10 NPC GUID/option pair. The router resolves the target through server
  content (`content_npc_key`), requires an open menu for that exact NPC, and
  rejects a malformed packet (`InvalidPacket`), unknown NPC (`UnknownNpc`) or
  out-of-list choice (`InvalidOption`) with `Err`. The new test asserts those
  refusals leave the same open menu usable and that Talk afterwards returns the
  row's own body.
- No greeting id or text comes from client bytes: each is a `u32` read from
  server content, so a client cannot inject text, choose a locale id, or force
  an allocation from an attacker-controlled size. A zero/absent greeting
  yields body 0 and never borrows another row's text (test
  `a_zero_or_missing_greeting_falls_back_to_no_body`).
- No save, coins, items, rewards, roles, chat, trade or broadcast state is
  touched. The change only adds static rows read at load; there is no
  per-player state and no new entry path. The stock client locale resolves
  every id, so no overlay/fallback path is introduced. Loader bounds are
  asserted by `the_content_stays_within_the_loader_bounds`.
