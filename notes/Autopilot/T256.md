# T256: shared-field kills credit the killer's active kill quests

## Skills applied

- **Ponytail (full):** one guard in the existing `strike_damage` ->
  `apply_encounter` -> `npc_quest_event` path; no new quest path, packet family
  or persisted state. The F292 blocker fix then deleted the suite's duplicate
  copy of the canonical NPC quest fixture instead of keeping a second one.
- **secure-code-guardian:** threat note under "Security note" below. A hostile
  client cannot report a kill, definition id, actor health, quest id or count;
  the kill is the server's own alive-to-dead HP transition.

## Result

A shared-field kill now reaches the killer's own quest engine exactly like a
solo kill already did. `EncounterEngine::strike_damage` used to push the
defeated definition into `EncounterOutcome.defeated` only when
`shared_sender.is_none()`, so every shared-world kill (the live open-world
path through `with_shared_fields`) produced an empty `defeated` vector and
`Gameplay::apply_encounter` never emitted the killer's
`QuestEvent::KillActorKind`.

The change is one guard in the existing `hp == 0` block: the self-only
`remove(guid)` reply still depends on `shared_sender.is_none()` (the shared
field owns the removal broadcast), `boss_display`, `forget_target`, the drop
roll and every T240 reward line are untouched, and the definition is pushed
only when positive. A shared kill therefore now drives the existing
`apply_encounter` -> opening `Defeat` event and
`npc_quest_event(KillActorKind { actor_kind_id, count: 1 })` path; no second
quest path, packet family or persisted state was added.

Killer-only, deliberately: the other player's engine never runs A's `strike`,
so B receives no `defeated` event. The shared field's HP/death/respawn
broadcast is unchanged; group-wide quest credit is the later slice named in
the brief.

T240 (commit 4876383) is merged in this tree. Its `KillCredit` and
`claim_kill_credits` reward path still pays coins and active-job XP exactly
once per credited player and was not duplicated or restored.

A definition of 0 is now skipped at the producer. The content loader allows a
field actor with `definition_id: 0` (`validate_actor` refuses negatives only),
and `OpeningEngine::on_event(Defeat)` refuses a non-positive definition; before
this slice the solo path would have errored on such a kill, and the shared path
would have hidden it behind the guard. The filter makes both paths ignore it
without an error, a panic or a quest advance.

## Client evidence (IDA available, no new wire bytes)

The slice adds no opcode, packet field or actor field. A kill reaches the
client through the existing quest objective packets. The F292 follow-up moved
the layout builders into `tests/support/npc_quest_chain.rs`, where the tests now
pin every byte of the 49/8, 49/9 and 49/10 bodies and the identity fields of
49/13. IDA re-checked for F292 (an earlier note cited the 49/8 apply function as
its reader; corrected here):

- 49/9 QuestObjectiveUpdate: common header `0x00c7acd0` (u16 family/subtype =
  `49,0` then an i32 subtype = `9`), reader `0x00c7af60` reads quest id,
  objective key, current counter, progress float, a bool and one trailing dword
  in that order; apply `0x00c7a990` stores the counter at objective `+0xd4` and
  the progress at quest `+0x28`. The full body is 6 + 21 = 27 bytes.
- 49/10 QuestObjectiveComplete: reader `0x00c7b070` (same prefix, then quest id,
  objective key, progress float, one dword, bool; 6 + 17 = 23 bytes). The fifth
  kill's 49/10 is asserted in test 1.
- 49/8 ObjectiveActivated: `QuestMessage::ObjectiveActivated`. The body reader is
  `0x00c7aeb0` (three dwords + bool: quest, objective, required, notification),
  reached through `0x00c7b570` from the quest dispatcher `0x00c7cd40` case 8;
  `0x00c7a910` is the activate/apply step, not a reader. Full body 6 + 13 = 19
  bytes; the fifth kill asserts the Talk objective activation.
- 49/4 QuestComplete: reader `0x00c7b420` -> body reader `0x00c7b230` (common
  prefix plus one i32 quest id). The reconnect turn-in asserts the 49/4.
- 49/13 QuestEnd: reader `0x00c7b990` (actor u64 `6..14`, quest id `14..18`,
  end text `18..22`, one more dword `22..26`, then the reward bundle through
  `0x008e7930`, then a trailing float); dispatcher `0x00c7cd40` case 13 calls
  `ShowQuestEndScreen` `0x00a95420`. The reconnect test asserts the actor, quest
  id and end text only; it does not pin the reward bundle bytes. 49/14
  QuestEndReply constructor `0x00a864c0`, sender `0x00a97ef0` (existing pin).
- The brief labels `0x00c7bd10` a "49/3 objective update" reader. IDA and the
  Build Guide both show `0x00c7bd10` is `ApplyQuestAddPacket` for 49/3
  QuestAdd; objective progress is 49/9/49/10 above. IDA wins; the server still
  emits the 49/3 QuestAdd unchanged on accept/login, and this slice adds no
  49/3 traffic on a kill.
- Combat/actor packets are unchanged and untested for new fields: 32/7
  AttackProcessed, 35/5 enemy HP, 35/8 animation, 35/3 remove, 38/19/38/14
  T240 rewards, 41/114 reader `0x009bdd70`, 35/2 AddNpc constructor
  `0x0091cac0` / body reader `0x00921a10`.

## Security note (secure-code-guardian)

Threat surface: a hostile client can send `36/10` abilities, `26/8`/`26/10`
interactions and `26/13` job switches on the shared field. It cannot report a
kill, a definition id, an actor's health, a quest id or an objective count. The
definition pushed into `defeated` is the server-owned field actor row's
`definition_id` from trusted content; the kill is the server's own
alive-to-dead HP transition; the quest event is generated by the server with
`count: 1` and the quest engine caps the counter at the objective's required
count. The sender used for the field simulation is the authenticated session
GUID (`handle_shared_field` receives `character.guid`), never a body-supplied
guid or the enemy's last-hitter list.

Refused/ignored: a non-lethal hit, an evade/return-home actor, a corpse hit
(the existing `s.health == 0` early return), an out-of-range/cooldown/weapon
refusal, an unknown target, a definition of 0 (skipped at the producer), a
replay of the lethal request, a repeated shared tick and a second turn-in. A
per-player apply failure still returns the request error, and the gateway
commits only its staged `Gameplay`/field clones, so the other player's session,
the shared field runtime and the save are unchanged. No coin, item, reward,
trade or save-ordering code was touched, and the `defeated` event is private to
the killer's session (no new fanout).

## Open gaps

- Group-wide credit for other group members is deliberately not in this slice;
  only the engine that lands the lethal hit receives `defeated`.
- No native client run. The wire is unchanged and every packet field the tests
  assert is pinned to the client reader above.
- The content loader still admits `definition_id: 0`; this slice makes the
  kill path ignore it, but a future content rule could reject it at load.
- The three pre-existing shared-field tests with "no personal credit" in their
  names (`w127_exact_death_respawn_clock_and_no_personal_credit`,
  `t032_private_instance_field_is_one_shared_death_for_two_members`,
  `area_and_dot_damage_share_hp_and_never_deliver_personal_credit`) still pin
  T240 *reward* credit; since T256 the lethal hitter's engine reports its own
  `defeated` event (quest credit). F292 added a comment at each test; rename
  only when the integrator's protected-pass list is refreshed.
- The shared tick still calls `gateway.tick_shared_effects(...)?` in
  `Server::tick_shared_fields` (`src/bin/osfr-gateway.rs`). The kill-time quest
  event cannot fail in a valid session (the producer only emits positive
  definitions, the loader refuses negative ones, and
  `QuestEvent::KillActorKind` validates a positive id with count 1), so this is
  not a reachable per-player error today. Hardening the tick to log-and-skip
  that session is a lead-owned `osfr-gateway.rs` change and is not part of this
  diff.
