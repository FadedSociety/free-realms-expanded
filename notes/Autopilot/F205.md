## Review disposition

1. **BLOCKER (one player's settlement error faults the shared field): fixed.**
   `Gameplay::sync_achievement_progress` is now a two-step operation:
   `try_sync_achievement_progress` stages the complete award on a clone of
   `ProgressionExtras` and commits it only after every claim and title succeeds;
   `sync_achievement_progress` catches a capacity refusal, logs it, and returns
   `Ok`. No caller can receive an `Err` from achievement settlement, so the
   `apply_encounter` call inside `Gameplay::tick_shared_effects` /
   `receive_field_damage` can no longer fault `Server::tick_shared_instance`.
   A failure leaves no title, claim or completed counter behind; the moved
   counter is re-observed by a later transaction (a counter-moving request or
   the login sync).
   - Regression: `tests/titles_claims.rs::settlement_capacity_failure_defers_the_award_without_failing_the_transaction`.
     It fills the 256-row claim inbox with server-issued claims, drives the real
     `Gateway::handle_at` request path (`realm level 20`), and asserts the job XP
     commits, no title/claim is added, then claims one row, saves/reloads and
     asserts the login sync awards the deferred title and queues its claim.
   - Canary: replacing the deferral with `Err(error)` made the test fail at
     "the request still answers"; restored.
   - Limitation: no shared-field reward producer exists in the current content
     (T102 is lead-owned and still pending), so a field-level refusal cannot be
     synthesized through the public path. The shared seam calls the same
     `apply_encounter` -> `settle_achievement_counters` -> settlement functions;
     the fix makes that path infallible. T102 should add the field-level case
     when field kills actually pay.
2. **BLOCKER (F121 budget/session dispatch is lead-only): not fixable by a
   builder; left for the lead.** F205 does not change the dispatch, the budget,
   or the F157 tests that pin them. The F121 change is inherited from the parent
   commit; approving or replacing it is the lead's decision under the
   session/security rule. This is why the final status is NEEDS-LEAD.
3. **MINOR [TESTS] (definition rows use the production serializer as ground
   truth): fixed.** `tests/titles_claims.rs` now pins item 8's exact 178-byte
   `ClientItemDefinition` row (`DEFINITION_8_ROW`) and decodes its leading
   fields in the client's order (`decode_definition_header`): id 8, name 2252,
   description 45980, icon 1764, tint 228, model `bowl_basic.adr`, texture
   `bowl-bones`, gender 0, type 4, and the two flag bytes at `+0x2c`.
   `decode_definitions_response` compares the response row to the fixture for id
   8 instead of only to `Inventory::definition_record`. The fixture test only
   passes if the catalogue row still has that layout and those bytes.
4. **MINOR (duplicate `150/7` progress packets): finding is wrong; no duplicate
   exists.** `try_sync_achievement_progress` appends a transition's packets only
   inside `if !transition.newly_completed.is_empty()`. A progress-only
   observation therefore emits no `150/7` packet from either the
   `apply_encounter` settlement or the enclosing transaction settle; the second
   settle re-observes the moved counter but emits nothing. I did not persist
   progress-only counters: that would add save-shape churn for no packet change.
   - Regression (requested progress-only case):
     `tests/soccer_entry.rs::progress_only_tick_reward_does_not_emit_achievement_progress`
     drives a real soccer win at rank 18 -> 19 (below the level-20 threshold),
     asserts zero `150/7` on the win tick and on the following tick, and asserts
     the win still moved the rank counter.
5. **MINOR [NOTES] (false "items 17-19" claim): fixed.** `notes/Autopilot/F157.md`
   now says "item 17 and the Structure section", with a correction note. Its
   item 17 was also corrected: the F157 settlement did run inside the shared
   tick; F205 makes it infallible.
6. **MINOR [TESTS] (tick-awarded title not tested across save/reload): fixed.**
   The tick regression now saves the selected title through the gateway's own
   `save_with_pet_roster` path (the path the session uses at

## Threat note (secure-code-guardian)

- Achievement counters come only from server-owned job rank and completed
  quests; a client cannot move one. Claim ids/grants and title bindings come
  from server content, never from the wire. The client can fill neither the
  claim inbox nor the title book; a full capacity is server state.
- A capacity refusal now defers the award: it grants no item, coin or title,
  logs only a static reason, and leaves the character save unchanged until the
  next authoritative settle. No client quantity or id is trusted.
- The pinned definition fixture is server content; a hostile client cannot
  choose a definition row. The `108/6` response still authorizes every requested
  id before describing it (F157 regression unchanged).
- The deferral test uses the admin-only `realm` command to move job XP; ordinary
  players cannot invoke it. The production trigger is job XP and quest
  completion.
