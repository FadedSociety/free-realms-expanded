# F226: Fix T021 review blockers (8bfcb80): soccer payout overwrite and instance ids

## Review disposition

`lab/autopilot/reviews/8bfcb80-T021.md` raises one BLOCKER with four findings.
This brief covers findings 1, 2 and 4; finding 3 is lead task L012 and was not
touched. All three in-scope findings are valid and are fixed.

1. **Payout overwrote changes made during the match.** Valid. The soccer
   `Session` kept the `RewardState` snapshot taken at entry and
   `Gameplay::tick_world` adopted it wholesale at full time, so a trusted
   `108/3` claim (or a trade) made during the match was replaced by the
   pre-match bag and profiles. Fixed by deleting the snapshot: `Session::begin`
   no longer takes rewards, `Session::tick` reports `settlement_due`, and
   `Gameplay::tick_world` settles in the same staged tick with a snapshot taken
   from the live session state (`Session::settle(guid, &live)`). The grant is
   applied on top of the current inventory/profiles.
2. **Public-instance aliasing.** Valid. `soccer_service::entry_scene` used
   `id: 0`; `Gateway` copies that into `state.zone_id`, and
   `World::prepare_membership` maps zone 0 to the public instance. The scene now
   uses `SCENE_ID = 47_000_000`, a server-owned id that is not a shipped
   regional zone id (0..17 in `data/content/zones.json`), and
   `Gameplay::current_zone` reports the arena while a match owns the session.
   `Gateway::runtime_zone` therefore registers the arena and the membership
   path gives every entry its own unseeded solo instance instead of the public
   one. `SCENE_ID` is a protocol identity next to the other reconstructed entry
   scene constants, not a tuning value. A save taken mid-match now stores this
   arena scene id and cannot load until L012 recovers the return pose (Open
   gaps); the brief assigns that recovery to the lead.
4. **Lifecycle instance id 1 reused every match.** Valid.
   `SoccerService::new` restarted `next_instance_id` at 1 for every match, so a
   replayed `39/6` (or `39/5`) quit from match A addressed match B. Run ids now
   come from a process-wide `AtomicI32` starting at `FIRST_INSTANCE_ID =
   47_000_001` in `offer_minigame`; each match gets a fresh id and the stale
   packets no longer match the new run.

Dead state removed with the fixes: `ParticipantRun.rewards`,
`SoccerService::next_instance_id`, `SoccerService::reward_state`,
`Session::reward_state`, `Session::settled`, and
`LifecycleResult.reward_state` (it was assigned but never read; lifecycle
packets never pay).

## Threat note (secure-code-guardian)

Client input on this route: family-76 soccer bodies (positions, control intents,
shot/pass state), `39/5`/`39/6`/`26/42`/`41/109` lifecycle packets with a
client-chosen instance id, `167/1/2` Play with an activity id, and `108/3`
claims with a tracker id and claim ids.

- Run identity: lifecycle packets must match the run id the server allocated.
  That id now comes from a process-wide monotonic counter, so a hostile client
  cannot replay a quit/start from an earlier match to cancel or restart a later
  one; the two-match test asserts that.
- Payout integrity: the old code restored the entry snapshot, so a client could
  time a claim to have a paid reward silently reverted (and it could undo a
  trade). The payout now applies the server-owned grant to the live bag and
  wallet, inside the staged `Gameplay` clone that is only installed on success.
  A client cannot choose the grant, the score or the result: `finish_minigame`
  reads the server authority's outcome and refuses a loss carrying a grant.
- Isolation: the arena no longer aliases zone 0, so the match is not part of
  public-world presence/proximity and cannot be reached through overworld
  membership assumptions.
- Refusals: an unknown claim id still produces `108/4` result `0` and mutates
  nothing (snapshot equality asserted, canaried below); a malformed or
  out-of-order soccer packet is refused by the existing authority with no state
  mutation.
- No new client-parsed field, quantity or id is trusted by this change.

## Checklist

1. **A refusal changes nothing.** `a_refused_claim_during_a_match_changes_nothing`
   snapshots the gateway, sends a `108/3` for an unqueued id, asserts the
   `108/4` result is 0 and the snapshot, coins and claim ledger are unchanged,
   then proves the match still pays exactly once. Canary F226-D showed the test
   fails if the refusal result is corrupted. The existing soccer refusal tests
   (`forged_entries_and_client_goals_change_nothing`,
   `quitting_before_a_result_cancels_without_a_payout`) still pass.
2. **Rollback covers all state.** The settlement runs on the `Gameplay` clone
   staged at the top of `tick_world` and is installed with `*self = staged`
   only after both tick and settle succeed; the session keeps no shared
   `Rc`/`RefCell` reward state and the deleted snapshot cannot escape.
3. **Apply deltas, never restore old snapshots.** The payout now applies the
   grant to a snapshot taken from the live session immediately before adoption
   in the same tick, so coins/items gained during the match survive. Canary
   F226-C reproduced the old overwrite (`left: 15, right: 40`) and the test now
   asserts the live result.
4. **Busy rules are mutual.** Soccer is already an `Occupation` row with
   start/warp/ride/pets/location gates; no activity gate changed. The `108`
   claim path is a claim, not an activity, and it is intentionally allowed
   during a match now that it cannot be overwritten.
5. **Every entry path is gated.** The only soccer entry is still the activity
   portal Play (`167/1/2`) through the existing admission/`warp_blocker` check;
   no parallel entry was added. The payout is downstream of the same session.
6. **Reachable in production, tested through it.** The new tests log in and send
   real gateway frames (`Gateway::handle_at`): login, `13`/`10`, `167/1/2`,
   `39/5`, family-76 input and ticks, then assert the payout. Membership is
   checked through `Gateway::runtime_zone` (the exact input to
   `Session::commit_outcome`) into `World::runtime`/`prepare_membership`.
7. **Survives reconnect.** The durable pieces (coins, items, claim ledger) are
   in the character save and asserted after the payout. The mid-match *pose* is
   finding 3 / lead task L012; a save taken mid-match cannot load until L012
   lands (see Open gaps). Ignored regression
   `a_mid_match_save_reloads_back_into_the_world` pins the requirement.
8. **Every exit path restores the player.** Quit (`39/6`), results Close
   (`26/42`) and the win path all return the player to the pre-match world via
   the unchanged `exit_soccer`; the disconnecting client drops the session and
   the match pays nothing. The known gap is the L012 reconnect case above; this
   is why the run ends NEEDS-LEAD instead of READY.
9. **Economy safety.** The grant is content data and is paid only from the
   server authority's finished outcome (one win per run, unique run key). No
   client-reported result, quantity or id reaches the grant; a rejected loss
   carrying a grant is refused. The live-state settlement closes the window
   where a paid claim could be reverted by the payout.
10. **Wire format matches the client reader exactly.** No layout changed.
    `0x008e4ae0` re-read confirms the id is the 4-byte field after tutorial and
    unknown; the entry-frame test decodes the frame and pins `SCENE_ID`.
11. **Unique ids.** Run ids are process-wide monotonic from `47_000_001`, never
    reused in a process (two-match test); the arena scene id is separate from
    run ids and not 0 or a public zone id.
12. **Others see changes.** Zoning into and out of the arena already uses the
    gateway's transfer path (the shared world leaves the player); with the
    distinct scene id the match no longer appears as overworld presence, which
    is the reviewed isolation fix. No new broadcast was added.
13. **Content works end to end.** The portal publishes the row, Play zones into
    `sg_soccer`, the match is played to a server-scored win, the payout and the
    claim survive together, and Close returns to the world; asserted on final
    coins/items, not intermediate flags.
14. **Values live in data.** No new tuning value. `SCENE_ID` and
    `FIRST_INSTANCE_ID` are protocol identities documented as server policy
    (R), beside the existing entry-scene constants.
15. **Canaries break production code.** F226-A/B/C/D changed production code
    (`soccer_service.rs`, `soccer_entry.rs`, `gameplay.rs`,
    `progression_extras.rs`) and each targeted test failed for the intended
    reason; all were reverted.
16. **Hands off session plumbing.** `src/gateway.rs` and
    `src/bin/osfr-gateway.rs` are untouched (`git diff` lists neither), and no
    `abandon_*_for_reconnect` function was changed.
17. **One player's error never stops the server.** The change adds no work in
    the shared tick or for another player. A settlement error returns `Err`
    from that player's tick into the existing `contain` isolation boundary; it
    is not used as a `?` out of `server.step()`.
18. **A type's rules live on the type.** `Session` documents `scene` (sent to
    the client and staged by the gateway) and `settled` (one payout, session
    only); `SoccerService::finish_minigame` documents that the grant uses the
    caller's live reward state; `TickResult::settlement_due` documents the
    two-phase settle.
19. **Hot paths stay cheap.** Per soccer tick the session clone is unchanged;
    no inventory clone unless full time is reached (once per match), and
    `current_zone` adds one constant-time check on a non-per-packet path.
