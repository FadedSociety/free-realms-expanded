# L054: SOE Group (0x19) child lengths follow the client's variable length (lead)

The gateway and login Group decoders now read a child's length the way the client writes it. A child of
exactly 255 bytes (`FF 00 FF`) used to be misread as the start of the 4-byte form, so the bundle was
refused or split at the wrong place. Multi (opcode 3) is unchanged and now pinned.

## What changed

- `src/soe.rs`: new `variable_length(bytes) -> Option<(value, prefix_len)>`, a direct copy of the client's
  rule:
  - one byte below `FF`;
  - otherwise `FF hi lo`, big-endian;
  - only `FF FF FF` selects the big-endian u32 that follows.
  - It returns None when the bytes end inside the prefix. It is a slice pattern match only: no
    indexing, no unwrap, no allocation.
- `src/gateway.rs` `application_messages` and `src/login.rs` `ciphertext_messages`: the 7-line
  `== 255` / `== 255` reader becomes one call to the helper plus `take(prefix)`. Every existing bound
  is unchanged:
  - gateway: frame length 2..=1 MiB, at most 128 children, each child 2..=1 MiB, nested bundles
    refused, empty bundle refused;
  - login: frame at most 64 KiB + 1, at most 64 children, each child 1..=64 KiB + 1, nested groups
    refused, empty group refused.
- Test encoders that copied the wrong rule now follow the client writer:
  - `tests/gateway.rs` `bundle()` now mirrors PutVariableValue (one byte below 254, `FF hi lo` below
    65535, otherwise `FF FF FF` + u32). That makes the existing `real_bundle_prefix_variants...` test
    send the client's `FF 00 FF` for its 255-byte child through `Gateway::handle`.
  - `tests/coin_store_siblings.rs` `bundle()` no longer writes a 255-byte message as `FF 00 FF 00 00 00 FF`.
- Not changed (premise checked): `session.rs` Multi `flatten` keeps its one-byte child length.

## Client evidence (IDA, this task)

- Reader: GetVariableValue `0x010daea0`. If `a1[0]==FF && a1[1]==FF && a1[2]==FF` it reads a big-endian
  u32 from `a1[3..7]` (7 bytes). Otherwise, after `FF`, it reads a big-endian u16 from `a1[1..3]` (3
  bytes). Otherwise it reads one byte.
- Writer: PutVariableValue `0x010dae40`. Values of 0xFE and above become `FF`. Then values of 0xFFFF and
  above become `FF FF` + a u32; anything else becomes a u16. So 254 is `FF 00 FE` and 255 is `FF 00 FF`.
- Group receive: dispatcher `0x010e3dd0`, jump-table case 25 at `0x010e46d9`. It calls `0x010daea0` per
  child (`0x010e46ec`), checks the prefix and the child against the end of the buffer, and recurses into
  the dispatcher. On overflow it calls `0x010e3930` with reason 7.
- Group send:
  - SendCoalesce `0x010e6910` writes `00 19`, then PutVariableValue(len) + data for each child.
  - Reliable Send `0x010e77e0` coalesces any message up to `this+0xDC`.
  - The channel ctor `0x010e5f20` sets that limit to `MaxDataBytes - 5`.
  - Flush `0x010e6870` strips the header when there is only one child.
  - So the real client does send 255-byte children inside Groups.
- Multi: case 3 at `0x010e4294` is `movzx ecx, byte ptr [eax]`, a one-byte length. Pinned by
  `multi_child_length_stays_one_byte_at_255`.

## Security

Threat note: a hostile client controls every byte of a Group, both in the gateway (after the reliable
reassembly, bounded to 1 MiB by `soe::MAX_LOGICAL_MESSAGE`) and in pre-auth login (unauthenticated,
before RC4).

- **Truncated or malformed prefixes** (`FF`, `FF xx`, `FF FF FF` + fewer than 4 bytes): the helper
  returns None, which becomes an `Err` before anything is taken. No panic, because there is no indexing
  inside the helper. The caller's `&bytes[offset..]` is in bounds by its loop condition (`offset < len`;
  login `r.offset < bytes.len() - 2`).
- **Huge declared lengths** (`FF FF FF FF FF FF FF`): the value is checked against the existing child
  bound before `take`. `take` uses `checked_add` and returns a slice, so nothing is allocated from the
  declared length. On 64-bit, `u32 as usize` is lossless.
- **New accept surface**:
  - `FF 00 FF` + 255 bytes: the real client's encoding, refused or misframed before.
  - `FF FF FF` + u32: before, this read as u16 65535.
  - Every accepted child still goes through the same per-child checks: `parse_message`, the
    nested-bundle refusal, the role-change unbundling rule, the budget, and in login the nested-group
    refusal and RC4.
  - Inputs that only the old wrong rule accepted (`FF 00 FF` + u32) are now read as a 255-byte child
    and stay fully bounded.
- **Refusals change nothing**: the split runs before any gameplay clone or session change.
  `app_fuzz::unchanged` asserts this for each new seed (snapshot equal, no panic).
- **No new oracle**: the two new error strings are static and carry no input bytes. `osfr-login`
  traces a refused frame with its reason only (`body_head_hex: null`) and ends the session, the same as
  for every other framing error before this change.
- **Logs**: no new logging and no secrets.
- **Saves**: not touched.
- **Session plumbing** (creation, teardown, transactions, save order): untouched.
- **Other components**: `trace.rs` and `bundle_budget.rs` only test `starts_with([0, 25])`, so they
  cannot disagree with the split.

## (R) choices

None. Every rule above comes from the cited client functions. Accepting non-canonical forms (`FF 00 05`,
`FF FF FF 00 00 01 2C`) matches the client reader, which does not require canonical encodings.
