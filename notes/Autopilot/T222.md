# T222 - power-up use key

## What changed

The client has no dedicated combat power-up key: a held kind is a **job action-bar slot** the server defines, and `ActionBarSlot3` (default **3**) sends `36/10` bar 1, slot 2. T222 wires that request server-side, shows the kind in its own slot only while held, applies the kind's `power_ups.json` effect once, and puts the authored job row back. No job row moves. The research and the client evidence are in [[Research/Power-up Use Key]].

- `src/power_ups.rs`: `SLOT` (2), the synthetic 36/13 definition base and `Slot`, `PowerUps::slot`, and a validation rule that a stored (non-`auto`) kind must carry a name and icon so it can be shown.

## (R) reconstructed rules

- The slot itself is client evidence (ActionBarSlot3, default 3, 36/10 bar 1 slot 2); using the **slot 2 job ability row** as the power-up's home is the recovered "add super shield to bar" behavior, but our `job_abilities.json` places a job ability there (that content is (R)), so slot 2 shows the kind only while held and the row returns otherwise.
- Damage tier: the active fight's battle tier (a field battle's `difficulty`, 1..5; the overworld and the cave are tier 1) indexes `damage_by_tier`, and the current basic already carries the job level's weapon scale, so the curve is applied once. F263 corrected this rule; the T222 commit had indexed with the job level and double-applied the curve. The values, burn tuning, stun length, shield duration and speed are the reconstructed `power_ups.json` values.
- Super Shield's `speed_pct` is display-only: no server-side movement-speed model exists. The invulnerability is a `SkillBuff` with `taken = 0.0` (the existing mitigation fold).
- The held kind is session-only (W158 design): never written to the character save, cleared by a reconnect, never tradable or duplicable.
- The synthetic definition id is `90_000_000 + name_id` (clear of authored job definition ids 3784..24097); the original server's id is unrecovered.

## Security threat note (secure-code-guardian)

What a hostile client could send at the power-up path, and why it is refused or harmless:

- **A forged kind, effect or quantity:** impossible; the request is `36/10` with a slot only. The kind and every number come from the server's held state and `power_ups.json`.
- **A forged target guid / ground position:** the target and position are ignored; the effect is centred on the server's own player position. Ground-mode requests (32 bytes) are refused before this code by `abilities::unsupported_cast`.
- **A replay or burst:** the kind is set to `None` *before* any effect runs, so a second request cannot duplicate it. It falls through to the normal job-slot handling (and on an empty slot gets the 36/1 refusal); there is no energy, cooldown or attempt counter to farm.
- **Malformed or oversized frames:** `unsupported_cast` and `shared_action` validate the two recovered lengths (24/32) and exact headers first; malformed frames return `Err` and the staged clone is dropped (staged `Err` reaches the gateway's per-session `internal_error`, not another player).
- **Use while knocked out / after a finished battle / on a noncombat job:** a 36/1 failure and no mutation; the kind stays held and the bar is not resent because the hold did not change. Only a completed, living, in-world use consumes it.
- **Reload that removes the kind or its table:** the next use clears the stale hold and sends the restored bar; it never applies an effect from a missing table.
- **Shared-field use:** gated to the field zone and a non-instance fight, applied through `with_shared_fields` with the sender's kill ledger, and the damage packets use the existing broadcast path. A personal state (the held kind) never leaves the owner's engine.
- **Persistence/duplication:** the held state is not saved and there is no trade/drop/bag path to it.
