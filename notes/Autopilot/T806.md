# T806: a placed fixture is drawn by its own NPC, and its rotation is the client's Euler lanes (native 2026-10-27)

## Why
Native 2026-10-27 ~07:55Z (T799 accepted the placement): the owner placed the Chicken (item 70429, model 535) on the
Wilds Condo lawn at (99.5, -0.972, -26.75). The preview went green, the click was accepted (127/2 -> 127/40 + 127/44,
count 5), and "the housing placed the chicken but then it disappeared into the void".

Root cause: the client draws a fixture only from the NPC a 35/2 AddNpc spawns. The 127/40 (and the 127/28 instance) hold the
fixture's data and name that NPC by the record's NPC-guid field (`FixtureInstance` +216). The server sent the records and
never the NPC, and wrote 0 in the field. The preview object is local and goes when the click is accepted, so nothing was
left to see. The four kit blocks had the same flaw (never drawn).

Evidence (run `lab/runs/client-baseline-20261027T075151Z`, frames decoded with the SOE seed of that session; retail
`p2.pcap`, the 127/28 of a 2015-fixture castle plus its 9 placements, reassembled the same way):

- Our 127/40 (240 bytes) decodes cleanly with the instance layout of `sub_AB6F40`; it has the same shape as the 253-byte
  kit-block 127/40s (the size difference is two alias strings only). So the codec was right: the record was not the fault.
- The client's own run logs (`FreeRealms.log`, `Housing.log`, `ActorFailures.log`, `AssetFailure.log`) hold no fixture, model
  or asset failure for the chicken or the blocks, so the model loaded (the preview used it) and nothing refused the record.
- Retail: each of the 2015 instances has its own 35/2 whose actor id equals the record's NPC guid (2015 of 2015); they arrive
  before the 127/45/28/43 on entry. A placement answers 127/40, 127/44, then 35/2, 35/9, 35/20; a pickup 127/41, 127/44,
  then the 35/3 of that NPC.
- Client: `sub_AC8340` (the 127/40 handler) only files the record (`sub_105D5C0` by fixture guid, `sub_105DE10` by the NPC
  guid at +216) and creates no actor. The 127/51 handler `00ab8dc0` finds an *entity* by its guid (`sub_984960`) and moves it;
  p2.pcap's 127/51 carries the NPC guid, while the client's 127/3 and 127/5 carry the fixture guid.
- Rotation: `+80` of the record is Euler (yaw, pitch, roll in radians, then 0): retail instances hold 1.5708, 3.1416, -0.3285,
  and the client's 127/2 sends zeros for an unrotated item. `+192` (tilt) is the facing they imply,
  `(sin y cos p, -sin p, cos y cos p, 0)`; the client computes it itself in `sub_105CD30` (`sub_776970`). 2015 of 2015
  retail instances satisfy it, and the retail AddNpc has `rotation` = that tilt and its own `tilt` = the Euler rotation
  (2015 of 2015). Our server mapped the client's zeros to `[1, 0, 0, 0]` (a one radian yaw as Euler) and sent tilt
  `[1, 0, 0, 0]`, and refused any real turn (a quarter turn, 1.5708, is no unit quaternion).

## Change
- `src/housing_service.rs`: `fixture_actor_guid` (the fixture guid with bit 55, which `mint_fixture_guid` keeps clear, so no
  new saved id); `FixtureActor` (`Spawn` = 35/2, `Remove` = 35/3) and `ServiceOutcome.actors`, filled by enter (one per standing
  fixture), place (one) and pickup / pickup all (a removal each); `fixture_actor` builds the AddNpc from the item row with the
  values every retail fixture AddNpc shares (hidden nameplate, interactable, range 100, `active_profile` 144, `has_tilt`, ...);
  the 127/40 and 127/28 records name the actor and carry the retail pair rotation / facing tilt and an empty customization
  (the look rides the actor; the T518 alias block is gone); the 127/51 move reply names the actor; `housing_transform` keeps
  the client's rotation lanes and derives the tilt.
- `src/housing.rs`: `FixtureTransform` rotation is the Euler lanes (default zeros, tilt `(0, 0, 1, 0)`); `validate_transform`
  bounds the angles like positions and keeps the unit check for the facing only.
- `src/housing_native.rs`: `PositionUpdate.fixture_guid` renamed `actor_guid`, with the client evidence in its doc.
- `src/gameplay/housing.rs`: `encode_replies` appends the actors after the housing records (the retail order).
- Not done (R, listed in `notes/Research/Housing Core.md`): the actor's name string id (0), the 35/9 and 35/20 follow-ups, the
  35/16 effect after a move, live updates to a second visitor, and a migration of lots saved before T806 (a saved
  `[1, 0, 0, 0]` now means a one radian yaw until the item is turned; no migration, the lot is dev data).

## Structure
No new module and no new saved state: the actor guid is derived, the actors ride the existing outcome, the session layer
appends them. One `facing` helper shared by the record, the actor and the stored tilt. The unit-quaternion check on the
rotation went; nothing else about the validation changed. Retail-pinned values are named in the doc comments with the
capture they come from; the lead-tunable policy (default tint, name id 0) stays in the config row.

## Security-relevant decisions
- Every actor packet is built from the character's own lot and sent only to that session. The actor guid is derived from the
  server-minted fixture guid and sets a bit the minter keeps clear, so a client-supplied guid can never name another
  player's actor; the client still sends only fixture guids (127/3, 127/5), checked against the lot as before.
- Rotation lanes are finite and bounded by `MAX_FIXTURE_MAGNITUDE`; the derived facing is validated unit length before a
  placement commits. A NaN lane is refused by the codec before the service sees it.
