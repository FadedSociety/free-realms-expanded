## (R) rules

- The per-pet actor id formula (`owner ^ tag ^ pet_id << 32`) is an allocation rule; the client only
  requires uniqueness while the actor is live. The same pet keeps its id across dismiss, a zone
  change and a reconnect, so the re-summon re-creates the actor the client already knows.
- The row rotation uses content `tag_id` as the first id and increments it; the content value is
  2,100,000,000, above the buff-tag range `consumable_effects` uses (1.0e9..1.5e9) and its
  world-tag range (1.5e9..2.0e9), so a 38/16 row can never alias either. No other tuning numbers
  were added.
- Which icon and composite effect the buff uses is content (`icon_id`, `composite_effect_id`).
- The composite effect is attached to the owner (the runner), not the pet.
- On the first buff step the batch is `38/16 tag`, `38/16 next`, `38/17 tag`: the client notifies on
  a *new* tag id only, so the middle insert is what makes the data source read the first, already
  parsed row before it is dropped.

  window (the viewport must not lock and the player must not enter the void), open the trick menu on
  it, and see the tricks list; watch the buff icon and the foot beam while the buff runs and their
  disappearance when it ends.
- The rotation relies on the pre-parse row not being recorded by the buff bar under the id its blob
  will carry: the record constructor zeroes the icon (+0x68), so the first notification adds
  nothing, and the row's instance id (+8) is only written by the blob parse (a recycled record can
  leave a stale instance id, which costs one no-icon entry that the next notification clears). If
  the client instead recorded the row under its final instance id before parsing, the parsed row's
  `AddAbilityEffect` would be suppressed; then the fix would be a dummy heartbeat row instead of
  the rotation. The native check above settles it.
- Two extra packets per buff start and one per refresh (a row and a removal). At a 4 s cadence this
  is negligible; the composite effect is not restarted on refresh.
- The pet's *own* movement speed and the `35/2` spawn are unchanged.

## Threat note (secure-code-guardian)

A hostile client can send only the pet requests the router already decodes (53/4 summon/dismiss,
53/6 name, 53/16 utility, 53/18 groom, 53/19 feed, 53/22 tactile, 53/24 UI mode, 53/28 water,
53/32 adopt, plus the T489 trick verbs). None of them names an actor id, the buff row, its tag,
icon, name, composite effect or the actor formula: the actor id is derived from the authenticated
character guid and the server-assigned pet id; the buff is computed from the saved roster, the
server clock and validated content. A refused request still stages changes on a clone and commits
nothing (the T532 refusal test snapshots `Gameplay::state()` and the roster document and asserts
both equal, with no row, removal, stat or composite packet). The new packets are server-to-client
only; the only client-visible widening is still the owner's own movement allowance (bounded as T532
documented). The content tag bound (`> 2e9`) and the rotation's `checked_add` keep an overflowing id
from wrapping into the effect-tag ranges.

## Checklist

1. **Refusal changes nothing.** The T532 refusal test (`a_refused_pet_request_leaves_the_buff_and_the_pet_alone`)
   snapshots live state + roster and asserts equality after an unowned summon, with no row,
   removal, composite or stat packet. A refusal can at most let an already-due buff refresh happen
   (time-driven, not request-driven); no buff value is taken from the refused bytes.
2. **Rollback covers all state.** The buff (including the live tag id) and the actor id live in
   `PetService`, inside the `Gameplay` value the gateway clones per message; nothing is shared.
3. **Apply deltas, never restore snapshots.** The stat is recomputed from live content + the live
   bonus at send time; the buff end only removes the ids it holds.
4. **Busy rules are mutual.** No new activity; the buff is a passive consequence of a summoned pet
   and the pet router's existing gates are unchanged.
5. **Every entry path gated.** One evaluation point (`happy_buff_tick`) is reached from the request
   path, the world tick and the zone path; `reset_session` clears it. No packet can start it.
6. **Reachable in production, tested through it.** The suites drive `Gameplay::handle_in_world` /
   `pet_tick` / `settle_pets` and `Gateway::handle_at`; the switch test drives the real 53/4 route
   and the new actor is read out of the world's pet table in the F762 test.
7. **Survives reconnect.** The buff must not survive (tested); the pet roster and its tricks are
   saved as before and reloaded.
8. **Every exit path restores.** Dismiss, mood drop, zoning and reconnect each remove the row and
   the composite effect (or drop the session); a resummon starts a fresh step.
9. **Economy safety.** No items, coins or XP are touched.
10. **Wire format.** 38/16 and 38/17 reuse `build_effect_tag`/`encode_remove_effect_tag`; 35/41/42
    reuse the recovered `encode_add_composite_effect`/`encode_remove_composite_effect`; tests decode
    every packet with those decoders. The add reader `008d7ad0` was re-read this run and matches the
    existing pinned encoder's order.
11. **Unique ids.** Pet actors are unique per (owner, pet); buff rows rotate above 2.0e9 (content
    `valid()` enforces the base). The two other server tag ranges were read in code:
    `consumable_effects::BUFF_ID_BASE` 1.0e9 and `WORLD_TAG_BASE` 1.5e9 with `ID_RANGE` 5e8, so
    1.0e9..2.0e9 - the buff cannot alias either; the composite effect is keyed by the content tag.
12. **Others see changes.** The composite effect is added/removed on the broadcast path as well as
    the owner's, so nearby players see it (tested). The row remains owner-only (a HUD row).
13. **Content works end to end.** The tests assert the row contents, the composite packet and the
    speed stat, and that a trick on the switched pet is accepted and plays on the new actor.
14. **Values live in data.** Icon, name, tag base, duration, refresh, mood, bonus and the composite

15. **Canaries break production code.** Three, listed under Gates above; each edits `src/pets.rs`

16. **Hands off session plumbing.** No change to `gateway.rs`/`bin/osfr-gateway.rs` session code.
17. **One player's error never stops the server.** The tick returns `Option`, never `Err`; the

18. **A type's rules live on the type.** `HappyBuff` documents every field (including the composite
    effect and the rotating tag base), `HappyBuffLive` documents that it is session-only and what
    its tag id means, and `pet_guid` documents the per-pet rule.
19. **Hot paths stay cheap.** With no pet and no buff the tick is two `Option` checks; a refresh
