## Method and (R) rules

1. One greeting per NPC, chosen because the line's speaker is proven, not
   because it sits near the NPC.
2. For the seven quest-intro rows the greeting is the quest's 49/1
   `intro_text_string_id` bound to `giver_npc_id`; those intro bindings are
   reconstructed (T-1/T+1/T+2 locale backfill) and the speaker link is
   inferred from the quest record plus the guide's giver row. Each row says so
   in its `(R)` source.
3. `(R)` every row uses one recovered speaker line as the fixed default Talk
   greeting; the original server greeting/phase table was not recovered, so a
   quest phase does not change the first-click body and no text is invented.
4. The lines are server content; a client never supplies a locale id.

## Client evidence (IDA, read-only broker, re-decompiled for T316)

- 26/3 handler `0x00aa12e0` calls reader `0x00a9ef10` and then
  `0x009f5ae0` (ShowDialogFromPacket).
- Reader `0x00a9ef10` stores the first payload dword at object `+16`
  (`*(_DWORD *)(this + 16) = *v3`) and advances the cursor by 4.
- `0x009f5ae0` passes `*(_DWORD *)(a2 + 16)` to the `Global.Text` lookup
  `0x0097c1e0` immediately before `:SetDialogText`; that is the first dword
  after the four-byte family/subtype header, matching
  `encode_dialogue_26_3`'s `initial_dwords[0]`.
- `gameplay/npc.rs::dialogue_packet_with` writes `context.body_string_id`
  into that dword; `patch_npc_actor` only overwrites bytes 12..20 with the
  runtime actor GUID. The byte order is pinned by
  `tests/npc_interaction.rs::dialogue_26_3_synthetic_fixture_round_trips_exact_native_field_order`.

## Security threat note (secure-code-guardian)

- This slice changes no parser, save, coin, item, reward, role, chat or trade
  code. The only new values are static server-side `u32` locale ids and their
  evidence strings; the client never supplies a locale id.
- Hostile client input on the path is the existing 26/8 target GUID and the
  26/10 NPC GUID/option pair. The router resolves the GUID through
  `NpcVisibility::content_key`, requires an open menu for that exact NPC, and
  rejects an unknown GUID (`UnknownNpc`) or an out-of-list option
  (`InvalidOption`). The test asserts a refused `i32::MAX` choice does not
  consume the open menu and the next Talk still returns the blank body.
- A greeting cannot be borrowed from another row: the body is the clicked
  row's own `greeting_string_id` (`None` for the two blank controls) and the
  in-world packet carries 0 for them.
- The client cannot inject text, HTML, a path or an arbitrary locale id. The
  source gate requires `Global.Text.<id>`, recomputes the hash and finds it on
  the cited dat line, so a raw hash (which would render blank) fails the test.
- No player state, no new entry path and no allocation from attacker-controlled
  size. Loader bounds (8 MiB/file, 32 MiB total, 20,000 rows) are unchanged and
  asserted. All 17 ids resolve in the stock client locale, so no overlay or
  fallback path is introduced.
