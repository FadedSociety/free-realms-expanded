# T789: `use_ability` / `use_item` quest objectives, first slice

## What changed

The quest engine already had `ObjectiveKind::UseAbility`, `ObjectiveKind::UseItem`,
`QuestEvent::UseItem` and `QuestEvent::UseAbility`, but the content layer could not author
either and no non-test code emitted one. This slice closes that loop for the two reachable
shapes: a job ability used on an enemy definition, and a single-use item actually spent from
the item bar.

- `src/content.rs`: new `ContentGoal::UseAbility { id, ability_id, count,
  target_actor_kind_id: Option<u32>, source }` and `ContentGoal::UseItem { id, item_id,
  count, source }` (JSON kinds `use_ability`, `use_item`). Bounds live in `validate_goal`:
  positive ability/item, count 1..=`MAX_COUNT`, optional target positive, provenance required.
- `src/quest_engine.rs`: `ObjectiveKind::UseAbility` and `QuestEvent::UseAbility` gain
  `target_actor_kind_id: Option<u32>`. The split loader maps both content goals, the opening
  adapter supplies `None`, and `event_matches` requires a target objective to see the same
  enemy definition while an objective without a target matches any. `valid_objective_kind`
  and `validate_event` bound the new field.
- `src/item_bar.rs`: `Reply` gains `used_definition: Option<i32>`, set from the same
  `Use.spent` flag that sets `changed`. A boombox press and every refusal leave it `None`.
- `src/gameplay/quest_use.rs` (new, 54 lines): `Gameplay::emit_item_use` and
  `Gameplay::emit_ability_uses`, the only two callers of the new code. The item path is wired
  in `gameplay/item_use.rs` after the reply is built; the ability path is wired in
  `Gameplay::apply_encounter`, the one funnel used by the solo 36/10 request, the shared-field
  request and the tick paths.
- `src/encounter.rs`: `EncounterOutcome::abilities_used: Vec<(i32, Option<u32>)>` (one field,
  no logic). `src/encounter/skills.rs`: `job_ability` records the primary resolved target's
  `definition_id` and pushes one entry only after every refusal (285/286/287/288);
  `merge_skill_outcome` carries the list.
- `tests/quest_use_events.rs` (new): 13 tests driven through `Gameplay::handle_in_world`
  (36/10 targeted ability, 42/6, 42/16, 42/15, 36/10 bar 2), `Gameplay::handle_shared_field`
  and the NPC offer/accept/turn-in path. Request bytes come from the production encoders
  `item_bar::use_wire`; the catalogue is the production split loader.
- `tests/support/quest_target_sets.rs`: `Targets::{abilities, enemy_kinds}` from
  `job_abilities.json` and `enemies.json`.
- `tests/enabled_quest_reachability.rs`: the gate resolves `use_ability` (ability and optional
  enemy target) and `use_item` (catalogue item), with three new fixture canaries and an
  authored-record sweep for the disabled records.
- `tests/support/quest_catalogue_fixture.rs`: one resolving ability row, one enemy definition
  and a second catalogue item for the new goals.
- `data/content/quests/archer.json`: quest 3010011 now authors its two cited steps (defeat
  definition 1294, Explosive Arrow 62019 on 1294). The record stays `enabled: false` (see
  gaps).
- `scripts/content_check.py`: accepts the two kinds and validates the optional
  `target_actor_kind_id`.

## Reconstructed rules `(R)`

- (R) An accepted cast's `target_actor_kind_id` is the primary resolved target's
  `definition_id` (the same id `KillActorKind` uses). An area cast names the selected target,
  not every splash victim.
- (R) A single-use item credits only when the bar actually spent it; a non-single-use row, a
  boombox press and every refusal emit nothing. The quantity is always 1 because the bar
  consumes exactly one.
- (R) 3010011 counts: one kill and one cast, because the text gives no numbers.
- (R) `vitamins` in 3090008 is the Medic ability 62002 (name id 24061 "Vitamins"), not an item;
  it is not authored here because the rest of that record needs slice 2 (non-enemy targets).

## Threat note (secure-code-guardian)

Attack surface: the ability-cast and item-bar request bodies, and quest JSON authored by the
server operator.

- The client never sends an ability definition id: 36/10 names a bar and slot, and the server
  resolves the slot against `job_abilities.json` and the active job's level. A forged slot
  yields a refusal or another server-chosen ability; the credited id cannot be client-chosen.
- The client never sends an item definition id: 42/15/42/16 name an owned instance id, the
  definition comes from the server inventory, and the cast gate is `ItemBar::consume`. A forged
  target guid on bar 2 is refused by the existing self-target check (test
  `forged_target_is_refused`), so no event and no spend.
- Target kind is read from the resolved actor, not from the packet's target field.
- Quest event ids come from the split content loader with bounds (`ability_id`/`item_id` > 0,
  count 1..=`MAX_COUNT`, target positive or absent). A malformed event is refused before any
  counter moves; a refusal changes nothing.
- No new grant, coin path or reward path: rewards still come only from the turn-in.
- Server-authoritative outcomes only: an accepted cast or a spent item. A client cannot report
  either result.
