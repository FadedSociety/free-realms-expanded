## Verify-first: two brief assumptions are contradicted by the code

The brief says "pick one with coins + job XP + one item" and test 1 should assert
`reward_bundle_body.len() > 69`, and "confirm the reward's `RewardDisplay.rows` are
built by `definition_from_content`"; and test 2 should offer a quest with no reward.

- `quest_engine::definition_from_content` builds `RewardGrant { coins, items, job_xp,
  display: RewardDisplay { .., rows: Vec::new() } }` and never synthesizes a
  `RewardBundleRow` from an item grant. `from_opening` (`stage.reward`) is the same.
- `src/content.rs::RewardGrant` has `#[serde(deny_unknown_fields)]` and no display-row
  field, so a content record cannot author a row at all.
- No enabled quest authors an item reward; every enabled reward is coins and/or job XP,
  both of which live in the 69-byte base.

Consequence: a real content offer can only be 69 bytes (with real coin/star/GUID/name
words). `len() > 69` is unreachable through the NPC path in this base. The tests were
adapted honestly: the real-path reward test asserts the 69-byte body **equals the
shared encoder** and that the coin word (bundle+1..5) is 5 and the star word (+5..9) is
20, not zeros; the "rows append" case is pinned by the inline builder test with a
synthetic engine, which is the only construction that can carry rows today.

The empty-reward case has a fresh base problem: only two enabled records have empty
`rewards` (3100020 and 3020014), and both require a prerequisite that later content
disabled (3100019 / 3020013), so neither is offerable from a fresh save. The test
offers the real record 3100020 after restoring the historical save state in which its
prerequisite was completed — `repair_counters`/`validate_state` accept a completed
unavailable quest with empty counts, which is exactly a save that predates the
content disabling its quest. This keeps the real 26/8 → Talk path and real content
without inventing a quest record; no production path or content file was changed for
the test. (The previous attempt's fixture, 3130032, is no longer empty after T314.)

## Security threat note (secure-code-guardian)

Attack surface: only the normal NPC/quest client frames are involved (26/8, 26/10,
26/6, 49/2, 49/14). The client never sends a reward, a coin amount, an item id or a
bundle.

- A hostile client cannot choose which bundle is shown: `offerable_quest_for_talk`
  picks from the NPC's own `quest_ids_given` plus `quest_ids_for_giver`, filtered by
  `can_offer` (giver, prerequisites, level, job, membership, limit, pending offer). A
  forged 49/2 must match `pending_offer`; a forged 49/14 must match `pending_turnin`
  and every objective count (existing gates, re-exercised by `quest_offer_gates` /
  `quest_job_xp`).
- A malformed bundle cannot be minted by the player. Content cannot author display
  rows (`content::RewardGrant` has no such field and `deny_unknown_fields`), and
  `validate_definition` already rejects at load a coin reward above `i32::MAX`, an XP
  sum above `i32::MAX`, and item counts outside `1..=i32::MAX`. The encoder also
  refuses unsupported row types, oversized bodies, `> 1024` rows and overflowing XP
  sums. The only reachable malformed row today is a synthetic engine (inline test):
  the offer builder returns `InvalidPacket`, sends no 49/1, and does not panic.
- A replayed 49/14 pays nothing: the reward uses the idempotent
  `quest:<character>:<quest>` grant key (test 3 asserts coins/inventory/XP are
  unchanged around the replay).
- Nothing the player can trigger writes a save on a refusal. The encoder error path is
  an `io::Error` that ends only that session through `contain` (no save write, no
  commit); the persisted save therefore stays byte-identical. Note: the 26/6 offer arm
  calls `engine.offer` before `append_npc_quest_outcome` builds the packet, so if a
  future content schema makes an encoder error reachable, the in-memory
  `pending_offer` would be set before the error. No player can reach that today; when
  rows become authorable, stage that arm (or encode before mutating).
- No new persisted state, no new ids, no client quantity or item-id handling, no
  cross-player data. The test-only prerequisite save state is built in the test
  process; production load code is unchanged.
