# T776: fishing does not start after arriving, and the Fish Finder lists no fish

Native check 2026-10-26 22:07Z (binary 6a3172b5): Go fish! at the Wintery Basin guide zoned the
player into `sh_fishing_medpond`, the minigame started (`MiniGame:OnGameStarted`,
`ShowMiniGameHud`), but no cast packet (138/5 or 138/6) ever left the client and the Fish Finder
panel was empty. The server trace holds the whole round: `39/5`, `41/2`, `39/17`, `35/20` with
bit 22 on, `138/2`, and the server's `138/3` (317 bytes = 7 Wintery Basin rows), `138/1` and the
two `138/11` schools. So the round and registration were live; the data the Fish Finder reads
was not usable.

## Root cause

**1. Every fish name id was a raw locale hash, not a numeric `Global.Text.<id>`.**
`0x0097bca0` builds the literal key `Global.Text.%d` from the id we send and hashes it. The old
`fishing.json` `name_id`s (`3684473514` Flutterfish, `1323940429` Slugmud Skipper, …) are the
locale's *raw* `ugdt` row hashes, so `Global.Text.3684473514` is not a locale key: the name
lookup fails and the client renders its `<STRING … NOT FOUND>` fallback (the Fish Finder Lua
only drops a row whose name is exactly `-1`). The catch card has the same lookup. The seven
138/3 rows the client received therefore had no usable name; icons were `icon_id: 0` for every
species and the row type was a reconstructed `1001..` filler.

**2. The Fish Finder rows are refreshed by 138/4, and we never sent it.** In the client's
register case (3), `0x00b6cf9e`/`0x00b6cfa5` assign and rebuild the entry list, but only case 4
(`0x00b6d009`/`0x00b6d010`) also calls `0x00cd4480`, the extra data-source refresh that case 3
does not. The played server sends `RegisterPlayerResponse`, `UpdateData` and then its own
`FishInfoUpdate`; ours sent only the first two. On top of that, the 138/3 integer array (read by
`0x008dab40`) was empty, so the client created no fish model actor at registration; a played
response carries the three underwater-fish models.

There is no server-side cast gate that could have blocked the client: the registration config is
the client's own compiled defaults (min/max cast 3/20, camera 6.0/0.445/1.85/0.2), which
`0x00b67a00` copies to processor +0xB0/+0xB4 and +0xEC..+0xF8, and `FishingService::handle`
accepts a 3..20 m cast from the spot anchor (the real-path test below casts 10 m). The native
cast itself is still the lead's client-side check (see Open gaps).

- `type_id` = the recovered client item id of the species. The client only uses it as the row
  key and passes it to `Ui.FindSelectedFish`; our catch items are the size-graded 680xx ids, so
  the finder key is not necessarily the granted item (same as the played server).
- The `FishCatchable` byte is `fisherman_level >= minimum_level` (the client's column 4); the
  played server sends true for every row and leaves level gating as a TODO. Ours keeps the
  level flag and a test pins that both values occur at level 1.
- The lure-hint column stays 0: no per-fish lure requirement text id is recovered.
- The 138/3 preload list is the distinct `models.fish_by_grade` (1670 thin, 1671 medium,

- `MAX_TEXT_ID = 6,000,000` is a sanity ceiling only: the locale scanner covers that range and

## Security note (secure-code-guardian)

- **Surface.** The changed production code handles only the client's existing 138/2 register,
  already gated to an active `RunState::Playing` round created by the busy/range/eligibility
  checked `enter`. No new client field is parsed; the fish list is server-built from bundled
  content. A forged 138/4 is impossible (server→client only) and a duplicate 138/2 still returns
  no replies (`Outcome::Duplicate`).
- **Hostile content is refused, not partially applied.** `registration_reply`/`fish_info_reply`
  return `Err(InvalidValue)` when the session's area or a species key is missing, so a malformed
  bundled table produces a per-packet refusal, not a partial list or a panic. `validate_content`
  now also refuses a zero/raw-hash `name_id`, a zero `icon_id` and an empty source tag; the
  6,000,000 ceiling and the positive icon keep a client-controlled value out of the text/icon
  lookup.
- **No trust in the client.** Name ids, icon sets, types and catchable flags are server content.
  The icons/names are display-only; no reward, coin, item or XP path changed, and no client
  quantity or id is read by this diff.
- **No secrets/player data.** The content contains client locale ids, image-set ids and item
  ids; no player names, chat text, saves or keys.
- **Abuse scope.** Nothing here is player-triggerable beyond the existing registration; a
  reconnect or refusal changes no persisted state.
