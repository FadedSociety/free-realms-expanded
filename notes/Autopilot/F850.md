## Threat note (secure-code-guardian)

This change touches client input parsing (53/26) and movement of a server-owned actor. What a
hostile client could send:

- **53/26 with any body.** The decoder checks the 17-byte length before indexing, requires the one
  flag value the client writes (0), and rejects non-finite or `|v| > 1e6` floats with `Err`, so the
  session logs a refused request and no state is written (no panic, no index). A flood costs one
  small allocation per refused click and no state change.
- **A well-formed but hostile click.** It is refused with flag 0, before any write, unless it is
  8-40 m from the **server's** live owner position (4D, so a forged fourth component counts), at
  least 10 m from the last **accepted** click, no farther from the pet than `click_max_m`, and
  walkable on the server's heightfield. The walked height comes only from the heightfield, never
  from the client's y.
- **Fine-grained click spam.** The 200 ms interval and the 10 m displacement (both from the client's
  own sender gates C/D and A) rate-limit accepted moves; a refusal consumes neither, so a refused
  click cannot advance the pet or the rate-limit state.
- **A gridless zone.** Every click there answers 0, so a zone without a heightfield cannot be used
  to move the pet arbitrarily; in a gridded zone holes are refused.
- **State effects.** Nothing is granted (no coins, items or XP), no save is written by a click, the
  reply is private to the owner, and the actor guid/owner position come from the session, never from
  request bytes.

No new attack surface in login/session/transport; no lead-only module touched.

## Checklist

1. **A refusal changes nothing.** Both refusal paths return `reply(false)` before any write; the
   over-limit, malformed, no-grid, interval and new step-band tests assert `(active_follow_state,
   view)` equality (and the saved document for a click), and the step-band test then accepts a 10 m
   click. Canary 3 broke gate A and failed it; canary 2 broke the hole rule and failed its test.
2. **Rollback covers all state.** The click state (`Click { position, at_ms }`) and the go pose live
   in `ActivePet`, one session copy; a click writes no save, roster or shared `Rc`/`RefCell`/`Arc`.
3. **Apply deltas.** An accepted click records a destination; the step moves from the current pose
   and the live owner position is an input, never restored over newer state. No snapshot overwrite.
4. **Busy rules are mutual.** A click is a movement command, not a new activity; the existing
   `blocks(pets)` gate (occupation table) still decides whether a pet can be out and the pet-window
   mode still pauses the step. No new `Occupation`; no new gate to keep in sync.
5. **Every entry path is gated.** 53/26 arrives only through `Gameplay::handle_pets` ->
   `PetService::handle_at_ms` -> `follow_location`; the no-clock `handle` refuses it; no test-only
   route. The pet tick reaches the same `advance`; gates run before `go_to`.
6. **Reachable in production, tested through it.** `a_clicked_spot_is_walked_to_through_the_world_tick`

   world tests use the same `world_with` helper and `pet_tick`; `app_fuzz` routes 53/26 through the
   gateway (seed already existed; no new selector).
7. **Survives reconnect.** Nothing here is persisted (pose, go, click, blocked clock are session
   state); `reset_session` drops the active pet, and an accepted click keeps the saved document equal
   (asserted). No persisted rule to test.
8. **Every exit restores.** Arrival + timeout, owner-moved resume, every warp (blocked, climb,
   teleport, far), dismiss, replacing summon and zoning clear or drop the go/clock; tests cover the
   timeout, owner resume, blocked warp and the 50 ms warp.
9. **Economy safety.** No coin, item or XP is touched; no client-reported result is read; the target
   is validated and only the pet's own session pose moves. (The review confirmed no economy effect.)
10. **Wire format matches the client reader.** The request stays 4 x f32 + u8 0 (17 body bytes),
    asserted with truncation, trailing byte, flag, NaN/inf and 1e7 cases. The reply is now header +
    4 f32 + flag = 20 bytes, matching `00b578d0` (`sub_8E2410` reads four dwords, then the +32
    flag); it is asserted as exact bytes, through the reader-shaped `read_can_go_reply`, and the old
    9-byte body is asserted rejected.
11. **Unique ids.** None added; frames and the reply naming use the existing owner-derived pet actor
    guid. The reply's payload is the click vector, not an id.
12. **Others see changes.** Every go frame goes through the existing `follow_owner` private+shared
    push; the reachable test asserts `private == shared` for every 125; the 53/26 reply is private
    only (asserted).
13. **Content works end to end.** A real `Gameplay` summons, accepts the click, walks the pet within
    0.2 m and resumes on the owner move; the service test asserts the wait and the timeout; the new
    cliff and hole tests assert the *final* position/warp, not an intermediate flag.
14. **Values live in data.** `min_click_step_m` (10.0) joins the eight `follow` values in
    `data/content/pets.json` with `FollowConfig::valid` bounds; only the 1e6 parser bound, the
    4096-sample safety bound, the 1e-4 epsilon and `STILL_EPS`/`ARRIVE_M` are code constants.
15. **Canaries break production.** Six, listed under Gates; each broke production code (not the
    test), failed the named test, and was reverted with a byte-identical restore.
16. **Hands off session plumbing.** `gateway.rs`, `src/bin/osfr-gateway.rs`, saves and teardown are

17. **One player's error never stops the server.** `step` returns a pose and never errors; time math

## Open (R) and gaps

- Not driven by a native client. The can-go flag (`+0x12f9`), the pet's walk and the reply are the
  native check: summon, click 8-40 m away, watch the reply 1, the walk and the wait; click a cliff
  and watch 0.
- The owner vector's fourth component is not readable server-side; the 4D band treats it as 0 (R).
  A real client whose owner/click fourth components share a nonzero value would see the server band
  shift by under ~1 m at the top edge only (numbers differ by less than 0.5 m for |w| <= 1).
- The server's gate A compares against the last **accepted** click; the client's cache also updates
  for a click it computed but did not send (a failed band/direction/interval gate), so the server can
  refuse a real client's follow-up that is 10 m from an unsent click (R, stricter only).
- The client's gate C (`a3[2] <= 0.5`) has no server counterpart: the vector it tests is not sent
  and its slot/axis meaning is unresolved; the heightfield check substitutes.
- In a gridless zone every click still answers 0 (R); the pet follows at the owner's height there,
  and a gridded hole now refuses the step.
- `step_up_m`/`step_down_m`/`sample_m`/`resume_m`/`go_timeout_ms` remain (R) (OSFR PR #152 for the
  first three; first choices for the last two). `min_click_step_m` is the client's own 10.0.

## Security-relevant decisions

- The reply's 16 payload bytes echo the request's own four floats; the client handler ignores them,
  so this adds no trust and no information beyond what the client sent.
- The 4D band and gate A are refusal-only (flag 0, no state) and both run before the heightfield
  sampling, keeping a hostile flood cheap and side-effect free.
- The walked height remains heightfield-only, so the client's y can never place the pet.
