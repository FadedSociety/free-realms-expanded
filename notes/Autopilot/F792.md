## Threat note (secure-code-guardian)

The hostile client controls the 165/4 item id, tint/context and quantity, the 66/43 item id,
quantity and transaction id, and the chat text it sends. Refusals and why:

- The item must be in the server's store catalogue and the active inventory catalogue; the price
  is always the server's `stores.json` price (member price only from the session flag).
- Quantity 0 and > i32::MAX are refused; for a bound pet item, quantity above the server-side
  roster room is refused before money or items move, and an unset room fails closed.
- Adoption never trusts a client instance id: it only walks instance ids the server's own
  `Inventory::grant*` reported in this transaction, then consumes those instances. A client can
  not name a pet, a species, a model, a tint or a roster slot.
- The 53/5 record is built from the server's roster; its sex byte comes from the bundled models
  table, not the request.
- `realm give` is already gated by `may_run` (dev tools/account role); the new room refusal is an
  additional server check, not a new entry path.

## Checklist (19 items)

1. **Refusal changes nothing.** Covered by `a_full_roster_refuses_a_pet_buy_before_money_moves`
   (snapshot + save unchanged), `a_pet_buy_without_a_known_roster_room_is_refused` (inventory
   unchanged) and `realm_give_refuses_pet_items_the_roster_cannot_hold` (snapshot unchanged). Both
   gates have canaries above.
2. **Rollback covers all state.** Adoption mutates only `Gameplay::pets` and
   `Gameplay::inventory`; the gateway stages a clone of the whole `Gameplay` in `Gateway::handle_at`
   and commits only on success. The new `granted` lists are local to the handler outcome and are
   drained into that same staged outcome; no `Rc`/`RefCell`/side table was added.
3. **Apply deltas.** Adoption consumes from the live inventory (`Inventory::consume`) and inserts
   into the live roster; it never restores an earlier inventory or position snapshot. The Crab and
   `realm give` tests assert the item is gone and the pet is present after the save.
4. **Busy rules are mutual.** Not applicable: no new activity was added. Pet adoption is a step in
   an existing buy or grant, and `gameplay/occupation.rs` is untouched.
5. **Every entry path is gated.** 165/4 and 66/43 both reach `CoinShop::buy_once`, so the room gate
   is shared; both also announce the live room through `sync_pet_room` before the buy. `realm give`
   checks the room directly. The 66/3 Station Cash order is T486's and is not hooked here (known
   gap, stated below); it cannot use `buy_once`, and the new `Option` room makes a later `buy_once`
   caller fail closed.
6. **Reachable in production, tested through it.** The tests use `Gateway::load_gameplay` +
   `handle_at` with client-shaped chat, 165/4 and 66/43 packets; `realm give` goes through the
   opening handler after the fixture copies the production opening files.
7. **Survives reconnect.** Both the Crab and `realm give` tests save through `Gateway::snapshot`
   and reload `gameplay` plus `pets` through `Gateway::load_gameplay` + `adopt_pets`; the roster and
   model survive and the item stays consumed. The existing `pet_zoning`/`pet_wired` suites still
   pass.
8. **Every exit path restores the player.** Not applicable: adoption is not an activity and has no
   cancel/timeout/win state. Refusals leave the character free (asserted above); disconnect uses
   the unchanged session reset.
9. **Economy safety.** Quantities are validated, prices come from the server catalogue, and
   adoption touches only instance ids reported by the server's own grant. No client-reported
   results or fabricated impacts are used. Tests above (full roster, fail closed, over-room grant)
   assert the item and coins are unchanged on refusal.
10. **Wire format matches the client reader.** No field was added or removed. The 53/5 record's
    bool at +4 is checked against IDA `0x00912cf0` and byte-level-tested in
    `tests/pet_list_record.rs`.
11. **Unique ids.** Item instance ids still come from
    `inventory::instance_ids::allocate_from_snapshot`; pet ids from the roster's monotonic
    `next_pet_id`. No id is hardcoded to `1`, and the public-world instance is untouched.
12. **Others see changes.** Not applicable: the roster itself is character save state, not another
    player's visible actor. The active pet's actor path is unchanged; no broadcast was added.
13. **Content works end to end.** The shipped Crab buy creates a real roster pet with model 1667
    and its vanity flag, consumes item 7885, sends 53/5 and reloads. `realm give 70352` does the
    same for the Char and reloads.
14. **Values live in data.** No new timeout, window, cap or tuning constant. The roster size is the
    existing `MAX_PETS`/roster state and the store's pet binding is existing `pets.json` content.
15. **Canaries break production code.** Both breaks were in production (`CoinShop::buy_once` and
    `Gameplay::realm_give`), not manufactured in tests; both failed the named test and both files
    were restored byte-for-byte.
16. **Hands off session plumbing.** No change to `src/bin/osfr-gateway.rs` or `src/gateway.rs`;
    session creation, teardown, transactions and save ordering are untouched.
17. **One player's error never stops the server.** Adoption runs only inside one player's staged

18. **A type's rules live on the type.** `InventoryOutcome.granted`, `CoinShopOutcome.granted` and
    `Outcome.granted_items` each document `(instance id, units)` and who drains them;
