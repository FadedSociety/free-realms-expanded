# T032 Shared world: field runtime per instance

## What changed

- `world::World` now keeps a pristine `field_seeds` population per scene zone beside the
  existing `fields: BTreeMap<InstanceId, SharedFieldState>` runtimes.
- Installing a seed initializes the public instance. Committing membership lazily clones the
  zone seed into the member's private instance when the instance has no runtime yet. The seed
  is never cloned into session state, and combat updates one instance runtime only.
- `Server::tick_shared_fields` now walks every field-backed instance. The previous fixed
  `field(0)`, `take_field_packets(0)`, recipient check, NPC view and resave paths are replaced by
  the instance currently being ticked.
- NPC view synchronization skips sessions outside that instance. A transfer resets the old
  known-NPC view; a pending transfer now counts even when the scene zone is unchanged, so a
  same-zone move to a child instance correctly replays that instance's current actors.
- Added test-only instance health/clock/child hooks. No production client can choose its
  instance, and an instance without a zone seed remains without a field runtime.
- Added `tests/shared_field_interest.rs` coverage:
  - a non-ignored two-member world test proving the child runtime is one shared state, a second
    member does not reset HP, both observers see one death, and public HP is unchanged;
  - an opt-in two-bot socket scenario using the existing private play bundle.
- The shared field fixture now supplies a valid numeric/ambient NPC record and empty vendor
  stock, and gives the synthetic Brawler an owned class-71 weapon so the existing W113 weapon
  gate does not turn the shared-field route test into a weapon-eligibility test.

## Design: one population per zone, one arena run per group (R)

The single-writer rule remains: `Server::step` mutates world state on one thread. A
`SharedFieldState` belongs to `(zone_id, instance_id)` and is not stored in a session or
`SharedWorld` clone.

1. **Public space.** Each public scene has one public instance and therefore one field runtime.
   Its actor GUIDs, HP, motion, effects, respawn deadlines and contributions are canonical for
   every ready member of that public instance. Player quests, inventory, health/energy and
   cooldowns remain per character.
2. **Private/group instances.** A group run gets one child instance allocated by `World`.
   Membership is the authority for which players may observe or mutate its field runtime.
   Different child instances have separate runtimes even in the same scene zone; this is the
   isolation boundary for later group arenas.
3. **Group arena direction.** The group leader starts a battle; the server allocates or reuses
   that group's run instance and sends an in-game invitation. Accepting members enter the same
   instance, declining stays put, and a different group gets a different instance. The arena
   encounter/phase/enemy list should move through the same instance-keyed seam before shared
   arena combat is claimed playable. That move is not part of this first slice: today the field
   population is shared per instance, while the arena encounter state is still owned by each
   player's `Gameplay`.
4. **Lifecycle.** A field runtime is installed when the first member commits to a seeded
   instance. It is removed with that private instance during empty-instance collection. The
   seed remains immutable for later instances. Reloading content while an instance is active is
   a separate, lead-reviewed operation.
5. **Packet scope.** Field packets are emitted only to ready, world-loaded sessions whose
   membership instance matches the runtime being ticked. Client-supplied instance IDs are never
   accepted. A missing/unseeded instance is a no-op with no field mutation.
6. **Progression boundary.** This slice pays no field credit, items or XP. Existing personal
   encounter/quest handling remains unchanged. Durable multi-character payouts remain a later
   slice with an atomic batch boundary.

## Recovered and reconstructed facts

- C: `world.rs` already stored fields by instance and already had the membership, allocator,
  ready and empty-instance seams. The old gateway path hard-coded instance `0` for the runtime,
  packet queue, view lookup and tests.
- C: field combat, actor population, packet writers, interest views and the single writer already
  existed. This change reuses them; it does not add a second combat engine or scheduler.
- (R) Public instance policy: one shared instance per public zone, one field population per
  instance. Child instances receive independent copies of the zone seed.
- (R) Group arena policy: one child instance per active group run, with membership and scene
  transition committed together; a later slice must move arena encounter state onto that same
  instance key.
- (R) A same-zone instance transfer is a client scene change and must reset the old NPC view
  cache even though the zone number did not change.

## Open gaps

- Arena encounter HP/waves/results are still per-player; only the field runtime is per-instance.
  Group arena allocation, invitation/acceptance and shared arena combat are design-only here.
- The live group flow does not yet route a battle start to one group run. The same-zone
  child-transfer path exists for the test and server-owned future entry path, not a player-facing
  arena invitation.
- `field_enemies.json` is a zone-0 field seed in this slice. Zone-specific arena/dungeon seeds
  and their authored actors remain to be loaded and validated.
- No native two-client run was possible. The private socket test is the acceptance gate here;
  the lead still needs a native client trace/video for the shared kill.
- Field credit, loot and quest participation remain intentionally disabled for shared deaths.

Security-relevant decisions: no launcher, login, account, identity, session, SOE, trade,
character-store, studio or manifest files were changed. Instance selection remains
server-owned; field recipients are filtered by authenticated membership, readiness and
world-load state; unseeded instances are inert; and no client-provided instance or actor
identity can authorize a runtime mutation.
