## Data source groups

- Achievements (`00ce4e30`-`00ce6e50`): `AchievementMostRecentDataSource` collects and sorts candidate rows by fields at `+0x1c` and `+0x18`, then refreshes at most four entries (`00ce4e30`). Category source nodes expose category metadata and localized text (`00ce5ad0`, `00ce6020`, `00ce64b0`). Summary rows expose totals/completed counts and derive integer percent as completed × 100 / total (`00ce6c70`). `00ce6800` scans current achievement records and invokes `AchievementsHandler:SetTotalPoints`; this is local UI aggregation, not evidence of a server reward calculation.
- Item filters (`00ce6eb0`-`00ce7400`): the datasource exposes Id, Name, Option Count, and Options, reads the count from its manager, and serializes option fields including `HasValueRange`, `ValueRangeStart`, and `ValueRangeEnd` (`00ce7030`, `00ce7230`).
- Progressive quests (`00ce7ea0`-`00ce8d30`): three independent data sources expose definition, slot, and prize-slot rows. Their columns include seconds remaining, active slot, objectives, key-bundle eligibility, claim eligibility, and prize progress (`00ce7ea0`, `00ce7f70`, `00ce8020`, `00ce8460`, `00ce85f0`, `00ce8860`). This establishes the client UI projection only; these functions do not show the source packet or authority for the displayed values.
- Activity lists (`00ce8e90`-`00ceaa40`): two 128-bucket hash-list maps own ordinary and scheduled datasource references. List rebuild code populates All, Featured, Preferred, MemberOnly, custom, and Scheduled collections from activity fields (`00cea5f0`-`00cea720`, `00ceaa40`). `ActivityFinderDataSource` exposes profile id, quest id/title/description, and profile rank (`00ceaab0`, `00ceab40`). This agrees with [Pieces/031 Job catalogue](../../../../project/notes/Research/Pieces/031%20Job%20catalogue.md), which uses ActivityFinder rows for job-unlock quest selection but still identifies original `BaseClient.ActivityFinder` rows as missing evidence. No unlock ids or server-side data were inferred here.

## Area properties and packet path

Area property handlers load, apply, remove, and log `RoomTypeId`, physics values (`JumpHeightScalar`, `GravityScalar`, `BounceScalar`, `BounceVelocityCap`, `AutoJump`), `StartTimer`, and `RegionOverride` (`00ceae00`-`00ceb370`, `00ceb810`-`00ceb8d0`). The physics load path parses numeric strings with `atof`, updates live object fields, and clamps a nested value to 250 (`00ceb120`).

When the timer property runs, `00ceb740` constructs `PacketClientAreaTimer` with first field 1 or 2 according to `StartTimer`, then submits it through the client gateway when the gateway pointer exists. `00ceb500` serializes three fields and an embedded field; `00ceb610` wraps the result as a tunneled gateway packet. The `nmq packet` catalogue has no `PacketClientAreaTimer` entry and these functions expose no opcode constant. Therefore the records leave the catalogue `wire` mapping empty and mark the unresolved mapping on the sender record; assigning opcode 1, 2, or size `0xac` would exceed the evidence. The original server contract is unknown. Any claim that these values start/stop a server timer remains a hypothesis requiring the missing opcode/catalogue mapping and server-side behavior evidence.
