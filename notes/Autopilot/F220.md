Status: both BLOCKERs and all five MINORs are fixed; every focused gate is green on the final
state and both canaries failed the intended production break before being reverted. The chess
daily budget itself is unchanged and stays covered by the lead's 2026-10-19 sign-off

## Findings and what happened

1. **BLOCKER — the daily ledger used process uptime; fixed.** `ChessService::settle` now takes its
   day from `utc_day()` (`SystemTime::now()` since `UNIX_EPOCH`, unix ms / 86_400_000) through
   `ChessService::today`, never from the gateway's monotonic `now_ms`. `now_ms` still measures the
   run's elapsed time only. Tests pin the day with `ChessService::set_day` and the new
   `Gameplay::seed_chess_day` hook (the same shape as the existing `seed_chess` test hook).
   Regression: `tests/chess_route::the_daily_cap_applies_after_a_real_win_and_a_save_round_trip`
   wins through `Gameplay::handle_in_world` with `now_ms = 2_000` and an injected day `20_000`,
   asserts the persisted ledger is `{ day: 20_000, .. }`, reloads `GameplayState` (the restart
   analogue, `now_ms` back near zero) with a near-cap same-day ledger and gets no grant, then
   reloads a `day - 1` ledger and gets paid again. `tests/chess::the_daily_cap_...` covers the same
   day rules at the service level. The near-cap fixture is computed from the shipped content (see
   finding 5). No budget value, cap rule or payout shape changed; the sign-off above covers the
   persisted ledger and paid accounting this fixes. Note: a pre-F220 save's `day` was an uptime
   bucket, so it will not match the wall-clock day and the first paid win starts a fresh ledger;
   no coins move.
2. **BLOCKER — a failed OS-entropy seed failed the whole character/world/template load; fixed.**
   `ChessService` now stores `tables: Option<ChessTables>`; `with_state` passes the real
   `ChessTables::entropy()` result to a private `with_entropy`, and a failed source leaves chess
   closed instead of returning `Err` from `Gameplay::load`. The rows stay published, and `begin`
   answers `EntryDenied::Unavailable` before it offers anything, so the rest of the character and
   server-template load stands. There is no predictable fallback seed. The refusal is sticky for
   the loaded service (a reconnect retries); no retry loop was added. Test:
   `chess_service::tests::an_unavailable_os_seed_closes_chess_without_failing_the_load` passes a
   real failing `io::Error` source and asserts the rows, ledger and active state are unchanged.
   This is the load behaviour F177 changed without sign-off, so no lead-only change is kept:
   `Gameplay::load`, `gateway.rs` and `src/bin/osfr-gateway.rs` are untouched and their existing
   `?` is now reachable only for real content/ledger corruption.
3. **MINOR — stale F140 sign-off sentence; fixed.** The F177 amendment in
   `notes/Autopilot/F140.md` now records the 2026-10-19 lead acceptance and the F220 correction
   instead of "still needs lead sign-off"; the false `(R)` line "UTC day boundary
   (`now_ms / 86_400_000`)" now names the wall clock. An F220 amendment in `notes/Autopilot/F177.md`
   records the correction without rewriting that run's history.
4. **MINOR [SECURITY] — wrong RNG guarantee; fixed.** `power_ups`'s `Rng` doc now says SplitMix64
   is not a CSPRNG, that chess uses it only as an anti-replay stream, that stream recovery could
   predict replies, and that the bounded daily cap limits what that is worth. The OS-seeded
   constructor is unchanged.
5. **MINOR [TESTS] — hard-coded award/cap; fixed.** The route cap test reads `success_coins` for
   row 20 and `daily_reward_coins` from the shipped `chess.json` via `chess_content()`,
   `chess_row_coins()` and `daily_reward_coins()`, and builds the near-cap ledger as
   `cap - award + 1`, so a content change moves the test with it.
6. **MINOR [STRUCTURE] — duplicated play loop; fixed.** The move/terminal loop moved into
   `tests/support/chess_bot.rs::play_line` (takes the send closure); both
   `tests/chess::play_to_end` and `tests/chess_route::play_greedy_game` use it. Acknowledgement
   and the 26/42 close stay with each caller because their outcome types differ.
7. **MINOR [TESTS] — replay test no longer touched production entropy; fixed.** The fixed-seed 1-8
   cases stay (deterministic), and one `ChessService::with_state` (OS-entropy) replay of the
   recorded line asserts the line is no longer a win.

## Security threat note (secure-code-guardian)

- A hostile client cannot choose the ledger day: it is the server's wall clock and no packet or
  save field the client sends carries it. A tampered server-side save can only move that
  character's own payout window; `paid_coins` is still bound-checked on restore, and a grant still
  requires a server-verified terminal position plus the client's acknowledgement.
- A failed OS entropy source no longer fails the load and never falls back to a fixed seed: chess
  is simply closed until the character reloads. A host with a broken `getrandom` cannot be forced
  into a guessable opponent, and chess can no longer take down world entry or the server template.
- SplitMix64 is not a CSPRNG. An observer who recovered its state could predict later computer
  replies; the doc now states that instead of denying it. The daily coin cap bounds the profit,
  and every payout still needs the server-verified result.
- Movie traffic outside `Playing` stays inert and every refusal is staged on a clone, so the new
  `Unavailable` refusal changes nothing.
