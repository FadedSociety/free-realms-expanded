# F576: fix the T361 review blockers (commit bb6c691)

Review: `lab/autopilot/reviews/bb6c691-T361.md`. Attempt 1 left no commit, notes or patch

## What changed

- **Blocker 1 (per-footstep sync), fixed.** `Gameplay::apply_opening` no longer refreshes
  quest eligibility and scans job-level goals unconditionally. It calls the new
  `npc_quest_profiles_changed` only inside the reward loop (after the 25 XP) and inside the
  unlock branch when `Profiles::unlock` actually unlocked something. A movement packet with
  no opening reward or unlock now does neither. The graph shows `apply_opening` is also
  reached from `tick_world`, `tick_shared_effects` and `receive_field_damage`, so the old
  call also ran per shared-field tick; that is gone too.
- **Finding 7 (pre-existing per-packet eligibility refresh), fixed in the same change.** The
  refresh moved with the sync. Every eligibility consumer (`QuestEngine::offer`, `accept`,
  `can_offer` through `offerable_quest_for_talk`, the 49/15 breadcrumb start) is reached
  only through `Gameplay::handle_npc_packet`, which refreshes eligibility on entry
  (`gameplay/npc.rs:76`), so membership time is still current when it matters.
- **Blocker 2 (silent XP paths), fixed.** `adopt_reward_state` (soccer settle, fishing
  catch, chess result, derby completion) and the profile-replacing branch of
  `handle_progression_extras` (claims) now call `npc_quest_profiles_changed` when, and
  only when, they replace `self.profiles`.
- **Finding 3 (one rank-change place), partly.** `npc_quest_profiles_changed`
  (`gameplay/npc_quests.rs`) is the one "profiles changed" notification: eligibility
  refresh plus the job-level sync. It replaced the hand-written pair in `realm level` and in
  both kart claim paths. The two kart paths also refreshed eligibility on every kart tick and
  every 33/41 packet; the refresh now runs only on a paid claim (`claim_reward_with_event`
  changes profiles only on a payout, which always returns `minigame_id`). `award_job_xp`,
  accept, turn-in and bind keep their own calls (different ordering and conditions). A full
  single rank-change method that also owns `sync_player_level` and the ability bar is still
  the lead's planned refactor.
- **Finding 4 (later ordered job-level step), fixed by failing closed.**
  `validate_definition` refuses an ordered quest whose job-level goal is not the first step.
  Split-catalogue quests are always ordered (`definition_from_content` sets
  `ordered: true`), so for content this means "job_level must be objective #0". W5 has one
  step and still loads.
- **Finding 5 (reachability arm), fixed.** `Targets` gains `profiles`, the `profiles[].id`
  rows of the profile content's `profiles.json` (`Profiles::load` owns the file and exposes
  no id list, same pattern as the raw `kart_entry.json`/`fishing_spots.json` reads).
  `Targets::load` takes the profile content root explicitly; `Catalogue::load` passes
  `reference_content()` as before. The `job_level` arm is now an inline membership check;
  the 33-line `job_level_violation` helper and its rank-curve self-check are deleted. New
  canary G: a job-level profile that jobs.json names but profiles.json does not declare
  (99) is the only violation; the control (fixture job profile 4) has none.
- **Finding 6 (load error vs disabled), fixed.** `tests/job_level_quest.rs` now asserts
  `QuestEngine::from_split_content(...).is_err()` for every malformed case and keeps
  `is_enabled` only for the clean case. It also adds the finding 4 case (a job-level goal
  after an ordered talk step must refuse the whole load) and its control (a job-level goal
  as step #0 followed by a talk step loads).
- Docs corrected: the `sync_job_level_objectives` comment now names the payout path and
  says a movement packet reaches it only when the opening paid or unlocked; the
  `open_job_level_objectives` comment names the load rule.

T361's note (`notes/Autopilot/T361.md`) claims the sync ran only at a level change,
accept, turn-in, reward settlement or bind, and that every XP site notifies. Both claims
were false at bb6c691 (review findings 1 and 2) and are true after this commit. That note
is left as T361's own record.

## Cost per tick / per packet

- Movement packet with no opening reward or unlock: zero quest scans, zero eligibility
  rebuilds (before: one `CharacterEligibility` build with a `BTreeMap`, one walk of the
  quest map and one `Vec` per active quest, per packet and per shared-field tick).
- Kart tick / kart packet without a paid claim: zero eligibility rebuilds (before: one per
  tick and per packet).
- A payout that replaced profiles: one eligibility rebuild and one quest-map walk, the same
  cost as the existing accept/turn-in path. Payouts are event-rate, not tick-rate.

## Threat note (secure-code-guardian)

- No new client input. The sync reads only `Profiles::rank` from server state; a 45/7
  claim still cannot name a job-level goal.
- Calling the sync from payout paths cannot pay anything: it only emits
  `QuestEvent::JobLevel`, which advances a counter; the reward still needs the 49/14
  turn-in with the server-made pending turn-in.
- Every new call site sits inside an existing staged transaction (soccer settle on the
  `staged` clone; fishing, chess, claims and kart packets through the gateway's staged
  `handle_in_world`; derby inside its tick/handle path; the kart tick on `staged`). An `Err`
  drops the clone. The sync cannot fail for a valid goal: `JobLevel` events carry
  `profile_id > 0` from validated content and a rank in 1..=20.
