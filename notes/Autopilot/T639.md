# T639: combat on the live scale

One tunable data file, `prototype/osfr-tools/data/content/combat_scale.json`, now sets player damage, tier levels, heals, player
health and the enemy scales. It carries out the proposal of `notes/Research/Damage Scale.md` (T637) with the lead's choices A1, A2,
B, C and D. Skills used: ponytail (full), lean-structure (graph/hub budget), test-behaviour-not-implementation.

## Structure

- Graph: the code index was not queried (this builder had no graph tools); `rg` found every user of `PLAYER_MAX`, `level_health`,
  `weapon_tier` and `profile_stats` (all in `src/encounter.rs` and `src/encounter/{skills,shared,power_up_use,field_content}.rs`).
- New module `src/encounter/combat_scale.rs` owns the file: loader, sanity bounds, `profile_stats`, `tier_factor`,
  `health_factor`, `level_health`, `scale_enemy`. The engine holds one `CombatScale` (`scale` field).
- Hub budget: `src/encounter.rs` 3162 -> 3134 lines (-28; ceiling 3198). `PLAYER_MAX`, `level_health`, `weapon_tier` and
  `profile_stats` moved out of it. No change to `gameplay.rs`, `gateway.rs` or `osfr-gateway.rs`.
- Where the file is read: `EncounterEngine::load(directory)` reads `directory/combat_scale.json` if present, otherwise the
  bundled `data/content/combat_scale.json` (the same rule `gameplay.rs` uses for the field content: the opening bundle
  lives in `lab/`, the field content in `data/content`). Neither present, or an invalid file, is an `Err` that refuses
  `Gameplay::load`; an invalid file in the directory does not fall back to the bundled one. No compiled default exists.
- Enemy rows are scaled once, where each loader builds them: `encounters.json` world and dungeon enemies
  (`encounter.rs` `load`), field enemies and field battles (`field_content.rs`).
- Deleted: the three constants/functions above and the 8-row `profile_stats` damage table; the source-text pin of those rows in
  `tests/piece_054.rs` (reach rows are still pinned, now in `combat_scale.rs`).

## Pacing check

- A field enemy keeps its hits-to-kill and hits-to-die at tier boundaries: authored 180 health / 25 damage against a level-1
  Medic: 3 hits to kill (was 3), 35 to die (was 36, small level-1 damages round: 25 x 0.5 = 12.5 -> 13).
- Inside a tier band the new gate bites: enemy damage follows the tier but enemy health and player health follow the
  four-level curve, so at levels 5-7, 9-11, 13-15 the player hits one tier softer than before. Example, authored 180 / 25 field
  wolf at level 5 against a level-5 Medic: old 2 hits to kill, 21 to die; new 3 hits to kill (1172 health / 488), 36 to die
  (22 damage against 788 health). Fights last about 1.5x longer for the player and are much less dangerous. This is the lead's
  decision D (tier by level band, until the equipped weapon is tracked); flagged for review. `job_wins` in
  `tests/encounter_job_skills.rs` had to follow it: its same-level pack now scales with the tier ladder, and the Medic's
  Triage (energy-bound, one cast per 25 s) cannot clear a pack scaled by the old health curve at level 10.

## Attempt 2: fight-driven tests moved to the new scale

The integrator's full suite found tests that script a fight against the old numbers (a fixed hit count, a literal health, a
packet or time budget). They are fixed without touching what they prove: rewards, refusals, pins and shared deaths assert
exactly what they did.

- Kill loops strike until the enemy is dead, with a bound computed from `combat_scale.json` (`health.div_ceil(strike) + 1`):
  `playtest_first_hour` (`kill_wolf` now takes `&mut now` and returns the killing swing), `opening_cave_replay` (`clear_cave`
  bound from the cave's own rows), `quest_pin_battle_objectives` (A swings until the wolf falls).

  `opening_cave_replay` (cave rows), `field_camp_separation` (starter hit = authored damage x `enemy_damage_scale`).
- A fixture that meant "N hits" is built from swings, not from the old damage: `shared_field_kill_quest_credit` (`wolf(.., swings)`
  and `authored_for(swings)`: the first authored health whose scaled value reaches the middle of that swing) and
  `shared_field_interest` (E is the three-hit wolf in every interest fixture, `hp_after(hits)` for the ladder, ignored socket
  tests included). Tuning the scale keeps every hit count.
- `enemies::opening_wolf_messages_match_encounter_engine_byte_for_byte` proves a message layout between two engines; `EnemyEngine`
  (tests only, not wired into production) keeps its own unscaled numbers, so the encounter engine runs on a scratch copy of the
  content with an identity `combat_scale.json` (the content directory's own file wins over the bundled one).

## Checklist (worker-rules 1-19)

1. Refusals change nothing: the loader is pure (`Err` before any engine exists); `set_player_job` clamps in place. Tested: invalid files refused.
2. Rollback covers all state: no new shared state; `scale` is a plain clone-able field inside the engine, so staged reloads clone it.
3. Deltas, not snapshots: not applicable (no payout or exit path changed).
4. Busy rules: not applicable (no activity added).
5. Entry paths: every damage path (basic, abilities, power-ups, DoT) reads the same `scale`; the heal path is one place (`skills.rs`).
6. Reachable in production, tested through the real engine and `Gameplay::load` suites (`w64`, `bandit_hideout_dungeon`, battle audits).
7. Reconnect: no new saved state. An old save above the new maximum is clamped by `set_player_job` (tested); the early return
   no longer skips the clamp when the maximum is unchanged.
8. Exit paths: unchanged.
9. Economy safety: no item or coin change; damage and health values are bounded (1..100,000, 100..100,000, 0.01..100).
10. Wire format: unchanged (health and damage are the same packet fields).
11. Unique ids: not applicable.
12. Others see changes: unchanged paths.
13. Content end to end: shipped `combat_scale.json` loads in the production load path (`Gameplay::load` suites).
14. Values live in data: every value is in `combat_scale.json` with source rows and sanity bounds. Reach (3.0 / 20 / 30) stays code, as before.
15. Canary: the invalid-file test breaks production by editing the file, plus an unedited canary that must load.
16. Session plumbing untouched.
17. One player's error never stops the server: the scale is read-only after load; rounding uses `as u32` saturation, enemy
    rows are bounded by the existing `validate_actor` (100,000 / 1,000) before scaling.
18. A type's rules live on the type: `CombatScale` decides tiers, health curve and enemy scaling in methods.
19. Hot paths: no per-tick work added. `profile_stats` is a map lookup per attack; `tier_factor` is computed in `set_player_job` only.

Threat note: `combat_scale.json` is server-side content only; a client cannot send any value into it. A malformed file refuses
startup instead of loading partial numbers.
