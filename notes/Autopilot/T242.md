## Security threat note (secure-code-guardian)

Attack surface: the normal NPC/quest frames only (26/8, 26/10, 26/6, 49/2,
49/14) plus movement, which the gateway validates before `on_location`.

- A hostile client can forge `49/2 accept` for 3160004 before 3160003 completes:
  refused by the prerequisite gate and by `pending_offer`, with no save change
  (tested).
- It can forge `49/14` for any quest id: refused unless that exact quest is
  `pending_turnin` and complete; a replayed 49/14 pays nothing because the
  reward uses the idempotent `quest:<character>:<quest>` grant key (tested).
- It can replay 49/2/49/14 after completion: `Outcome.changed` false and the
  serialized `GameplayState` is byte-identical (tested).
- It cannot complete the search objectives with a packet claim: `visit_position`
  is not `client_reported`, so no 45/7 id exists for it; the only input is the
  server-validated pose delivered to `on_location`. Radius and zone are content
  rows, not client values.
- It cannot buy the offer by naming a quest: `offerable_quest_for_talk` picks
  from the NPC's own giver list plus `can_offer`; there is no direct-offer path.
- No client quantity or item id is read by this chapter. Coin/XP values are
  content rows bounded at load (`coins <= i32::MAX`, known job profile, positive
  unique objective ids, runtime goals with provenance); the malformed-record test
  proves each refusal happens at content load, not at request time.
- Refusals consume nothing: the open NPC menu, the pending offer, and the held
  end screen all survive (tests).

## Checklist

1. **Refusal changes nothing.** `forged_or_missing_objective_events_change_nothing`
   snapshots the whole serialized `GameplayState` around a forged accept, a
   replayed accept, a premature turn-in, a forged second-quest turn-in, an
   out-of-range visit, a missing-objective visit and a wrong-NPC talk; every one
   leaves the bytes identical. F268 added the missing wrong-NPC `saved`
   snapshot; both wrong-NPC talks now assert it. `assert_no_offer` also proves a
   refused Talk keeps the open 26/9 menu usable (same option still starts a Talk).
2. **Rollback covers all state.** No transaction changed. The turn-in is the
   existing `rewards::apply_grant` transaction over `RewardState`; the tests show
   a refused 49/14 leaves quest state, inventory and profiles byte-identical.
3. **Apply deltas, never restore snapshots.** The payout is applied through the
   grant transaction on the live inventory/profiles; the reconnect test captures
   coins/XP before the disconnect and asserts the final value is *captured + 2 x
   reward*, not a replayed snapshot.
4. **Busy rules are mutual.** N/A: no new activity. The chapter runs inside the
   existing NPC Talk path, which already refuses while an activity is busy
   (`busy_interaction_refusal` in `gameplay/npc.rs`); no gate was added or
   bypassed.
