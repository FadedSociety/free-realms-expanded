# F269: Fix review blockers in T243 (commit 68e688d)

Review: `lab/autopilot/reviews/68e688d-T243.md`. Every finding was valid; none is
disputed. The blocker and both minors are fixed, with a regression test and a
production-code canary for the blocker.

## Findings and resolution

1. **BLOCKER (structure): `accepts_reward_bundle` re-implemented the bundle
   commit loop.** Fixed by reusing the canonical owner:
   `Inventory::accepts_reward_bundle` is now
   `items.len() <= MAX_REWARD_BUNDLE && self.clone().grant_bundle(0, items).is_ok()`.
   The duplicated per-row `grant` loop and the redundant
   `definition <= 0 || quantity == 0` guard are gone; `grant_bundle` already
   refuses both through `grant_with_tint` (unknown definition / zero quantity),
   so the row bound is the preflight's only own rule. Any future bundle rule
   added to `grant_bundle` now reaches the start preflight and the payout
   together. Regression test: `the_preflight_answers_like_the_payout_path`
   (test 6) asserts the two public methods agree on every bundle in a matrix.
   No helper split was needed: `grant_bundle`'s staged body already is that
   helper and the preflight calls it on a clone; a separate non-cloning variant
   would add a second entry point only to save one clone per start attempt.
2. **MINOR (structure): `MAX_REWARD_BUNDLE` provenance was imprecise.** The doc
   now names both real owners with lines: dungeon `reward_items` at 16
   (`src/encounter.rs:1011`) and field-battle `prizes` at 4
   (`src/encounter/field.rs:308`), and states that `grant_bundle` has no row cap,
   so 16 is the preflight's deliberate defensive bound. Test 6 also asserts that
   this is the **only** deliberate difference: `grant_bundle` pays a 17-row
   bundle, the preflight refuses it.
3. **MINOR (test): fixed fixture root could be rebuilt by a concurrent test
   process.** The root now carries `std::process::id()` and a per-process
   `AtomicU64` serial, so a concurrent test binary in the same build dir cannot
   delete or rebuild another process's content. No `Drop` cleanup: the two
   content roots are shared by several tests in one process through the static
   cache, so a per-`Fixture` drop would delete a directory another test is
   loading; the roots are `CARGO_TARGET_TMPDIR` build scratch (two per
   test-binary run) and the existing `remove_dir_all` still clears our own name.

## Security threat note (secure-code-guardian)

What a hostile client can send here, and why it changes nothing:

- The trigger is a **client-triggered start attempt** (41/108 Go after an open
  start screen, or a forged 167/1/2 Play with any activity id). The battle id is
  never taken from those bytes: Go starts the server-owned `pending_battle`
  (which also re-checks the marker radius) and the portal resolves the id
  against the published list. A forged id is refused before the preflight.
- The `(item, quantity)` rows come from operator content
  (`field_battles.json` prizes, loader-capped at 4 rows and `MAX_PRIZE_QUANTITY`
  per row); the client cannot choose an item, quantity or bundle length.
- The preflight runs the canonical `grant_bundle` on a **clone**: every invalid
  row, unknown definition, over-stack row, full bag or overflowing bundle is a
  `false` return, never a panic, `unwrap`, error escape into the session tick, or
  partial live grant. The 16-row bound also caps the work a single start
  attempt can cause (no unbounded loop over a caller-supplied list).
- Refusal happens before `encounter.begin`/`apply_encounter`; the live bag,
  coins, profiles, encounter, pending screen and save are unchanged (tests 1, 2,
  5 assert saved-byte equality; test 5 also proves one player's refusal leaves a
  second player's state byte-identical).
- No session, save-ordering or security module is touched; the coin component
  stays out of the preflight exactly as in T243.
