  has five buttons; with a quest row three pages fit. No capture of a quest-giver greeter dialog

  reader/handler (a second 26/3 is accepted) and from `dialog.lua` (re-show updates the open window).

  dialogue and starts from a fresh Talk (nothing is persisted).

## Threat note (secure-code-guardian)

Attack surface is the client-chosen 26/6 row id, unchanged in shape. A hostile client can send:

- **Any i32 as the row.** `explainer_page` only matches response ids in the rows this dialogue
  actually encoded (`ActiveInteraction.dialogue.rows`). An unoffered value returns `None`, the router
  answers the ordinary 26/4 close, and nothing else happens: no content id of the client's choosing is
  echoed back, no item/coin/quest/position changes. The close clears only this session's dialog.
- **An explainer id without talking first.** No active interaction means no recorded rows, so the
  same ordinary close. The suite drives this on a fresh `Gameplay` and compares the saved state.
- **A different NPC's explainer id.** The recorded rows belong to the open interaction's NPC, so
  another greeter's page is not reachable.
- **A page id the dialog did not fit.** With a quest row and four content pages, only three pages get
  rows; the fourth id is not in `pages` and gets the ordinary close.
- **Malformed 26/3/26/6 lengths.** Unchanged parsers: 26/6 is exactly 8 bytes with the family header;
  26/3's count is capped at `MAX_DIALOGUE_CHOICES`; content is loaded once and `validate_npc` refuses
  a zero id or more than four pages, so a bad content package fails the world load.
- **Flooding the row.** Each accepted page costs one row lookup (at most five) plus one 26/3 encode
  (93 + 20*n bytes) and no save, no coin/item, no tick work; the existing per-account packet limits are
  unchanged. A replay clones at most five rows.

No secrets, client files, absolute home paths or personal data; every page id is a stock locale key.
No new private code from AGPL projects.

## Checklist

1. **A refusal changes nothing saved.** `a_refused_row_changes_no_saved_state_and_the_npc_reopens`
   snapshots `Gameplay::state()`, sends `i32::MAX` and a page row with no dialogue, asserts the
   ordinary close-only replies and identical snapshots, then Talks again and gets the greeting and the
   same rows. The refusal consumes only this session's dialog (`pending_quest_choice`/the active
   interaction), which is the pre-existing `unknown_choice_closes_without_change` contract
   (`quest_dialogue_chains`, green); no saved value, item or quest changes.
2. **Rollback covers all state.** The only new state is `ActiveInteraction.dialogue` on the cloned
   `NpcInteraction`; `npc_select_26_10` already clones and commits the interaction only on `Ok`, and
   the gateway stages a `Gameplay` clone for the request. No `Rc`/`Arc`/`RefCell` side table.
3. **Apply deltas, never restore snapshots.** N/A: the feature pays nothing and restores nothing; it
   only sends a different locale id and row list.
4. **Busy rules are mutual.** N/A: no new activity. `busy_interaction_refusal` still gates 26/8/26/10
   before any dialog; nothing here starts an activity.
5. **Every entry path is gated.** `trace_path` shows one player-facing greeter Talk path
   (`talk_to_npc`); the opening scene and the dev command build contexts with no topics. Range/zone is
   checked by `NpcInteraction::interact`/`select`; a page click replays an already-open dialogue and
   does not re-check range (stock locale text only; documented as a gap, not a safety defect).
6. **Reachable in production, tested through it.** The suite drives `Gameplay::handle_in_world`
   (26/8 -> 26/10 -> 26/3 -> 26/6 -> 26/3) with the bundled split quest catalogue bound, so the quest
   givers' real quest row is covered; it decodes the production bytes.
7. **Survives reconnect.** N/A: the pages are static content and the dialog is session state. A
   reconnect starts with no open dialogue and re-reads the same content rows.
8. **Every exit path restores the player.** Goodbye, 26/4, a refused row and a fresh Talk all leave
   the interaction cleared (`close_dialogue`/`consume_active`), and the tests Talk again after each.
9. **Economy safety.** No coins, items, XP or rewards; a client cannot choose a body id or item.
10. **Wire format matches the reader.** The five-dword row `[id, 17, text, 0, 18]` is unchanged and
    pinned byte-for-byte by `expected_samantha_dialogue` (301/310/311/300, 173 bytes); the 26/6 echo
    is `009f6aa0` (test citations corrected). The suite decodes with the production
    `decode_dialogue_26_3`.
11. **Unique ids.** No instance/GUID created. Response ids are unique in one dialog: 310..313, 300,
    301.
12. **Others see changes.** N/A: only the clicking player's dialog; no actor, outfit, mount or job
    change.
13. **Content works end to end.** The tests assert the greeting body, the quest row, every page label
    and body, the replay with the same rows, and Goodbye closing; the locale pin asserts each id is a
    real non-blank stock `Global.Text` row and each page body is distinct.
14. **Values live in data.** Pages and order are `explainer_topics`; only the client protocol bound
    (five buttons, response-id base) is code, beside the existing 300/301 ids.
15. **Canaries break production code.** The quest-row drop in `dialogue_rows` failed three real-path
    tests with the missing 301 row; restored byte-identically and the suite went green.
16. **Hands off session plumbing.** No session creation, teardown, transaction or save-ordering change.
17. **One player's error never stops the server.** No shared-tick code; every failure returns `Err` or
    the ordinary close, and there is no `unwrap` on client data.
18. **A type's rules live on the type.** `ActiveInteraction.dialogue`, `OpenDialogue.rows/pages` and
    `DialoguePage` carry doc comments; `dialogue_rows` owns the five-button budget and the order;
    `MAX_DIALOGUE_CHOICES` bounds both the encoder's decoder and the row builder.
19. **Hot paths stay cheap.** Per-tick cost 0. Per Talk: one `dialogue_rows` (at most five rows, one
    topic clone) and one record into the cloned interaction. Per page: one linear lookup over at most
    four topics, a clone of at most five rows, one 26/3 encode; no save and no content read.
