## Security

Threat note (secure-code-guardian / security-reviewer):
- **Client input.** No client byte reaches `Snapshot.pets`. The roster changes only through
  `PetService` mutators, which already validate ownership and content; the summon/rename/adopt
  requests and their refusals are unchanged (pet_routing, pet_wired, f161 pass unmodified in
  substance).
- **Refusals change nothing.** A refused pet request returns `changed: false`, so the session
  writes nothing: the new f161 test asserts the file bytes are identical across a refused
  adoption, even with a deferred pose pending (canary D below). A failed write (f161 Windows
  share-mode test) leaves the document byte-identical and the live session unchanged.
- **Atomicity.** One `replace_bytes` carries character, gameplay and roster, so a spent adoption
  item can never exist without its pet or the reverse (f161 restart test, 17c test). Housing is
  re-read and kept inside that same write.
- **Load is validated.** `from_document` maps a malformed roster to the static
  `unreadable pet roster snapshot` (no serde message echoing document values into logs), and
  `from_saved` runs `content.validate()` + `validate_roster` as before. A bad roster fails that
  character's load only.
- **`None` semantics.** `None` keeps the disk roster; nothing removes a pet today, so a stale
  `None` can never resurrect or drop a pet. A roster-shrinking feature must send `Some` (field
  doc).
- **Trade journals.** A journal entry now carries the roster. Journals are server-written in the
  save directory, and recovery replays them through the same `save`. Recovery does not validate
  the `pets` value, but the next load does (`from_saved` + `validate_roster`). A hand-edited
  journal can therefore only break that one character's load, and editing it already needs
  write access to the save directory, which could change any save. Old journals parse (no `pets` key); a new journal with a roster does not parse
  on a pre-S17 binary (`deny_unknown_fields`), recorded in the Build Ledger.
- **`expect`.** `document_value`'s `expect` cannot fire. `PetRoster` holds only integers,
  strings, `f32` needs, sets, fixed arrays and a `u64`-keyed map, all of which `to_value` accepts.
  `serde_json::to_value` turns a non-finite float into null instead of erroring, and
  `validate_roster` keeps the needs finite in any case. The brief asked for `expect` over
  `.ok()` so that a broken roster can never silently save as `None`. If the `expect` ever did
  fire, the session's panic isolation would turn it into that one player's `internal_error`.
- **No new oracle, no secrets in logs, no new dependency, no Cargo change.**

## Checklist

1. Refusal changes nothing: f161 17c test (file bytes equal across a refused adoption with a
   deferred pose pending; canary D) and the f161 share-mode test (failed write leaves file and
   live session unchanged); pet_routing/pet_wired refusals assert `!changed`.
2. Rollback covers all state: the roster lives in the staged `Gateway`'s `PetService`, cloned
   with the gateway; the snapshot is built from the staged gateway and installed only after the
   save succeeds (unchanged ordering). S17 adds one risk: every save now writes the live roster,
   so an in-memory roster change made without `changed` would reach disk on the next unrelated
   save. Before S17, that save kept the disk roster. I checked every mutator. `PetService::handle`
   and `handle_with_inventory` stage on `next = self.clone()` and assign it only on success, and
   only with `changed: true`. The one exception is `UiMode`, which touches only the session-only
   `ui_mode` and never the roster. `Gameplay::settle_pets` clones too. Gameplay calls no other
   roster mutator. The live roster therefore always equals the last saved one.
3. Deltas, not old snapshots: the roster written is the live staged roster; `None` writes nothing
   over the disk value; no earlier capture is restored.
4. Busy rules: N/A, no activity or gate change.
5. Every entry path: one load path (`load_gateway_from`, used by single-character and
   account-bound sessions) and one save function; every production `save(.., gateway.snapshot())`

6. Production path: the 17c test drives `Session` dispatch -> `commit_outcome` -> `save`.
7. Reconnect: f161 restart test (roster from the document, active pet reset, summon by id works).
8. Exit paths: unchanged; logout/tick flush use the same `save(snapshot())` and keep the roster

9. Economy: adoption item and pet land in one write (f161 restart + 17c); no grant change.
10. Wire format: N/A, no bytes changed.
11. Unique ids: N/A.
12. Others see changes: N/A, presence broadcast untouched.
13. End to end: the adopted pet is saved, reloaded and summoned after restart (f161).
14. Values in data: N/A, no tuning value added.
15. Canaries break production code (gateway.rs, game_store.rs, osfr-gateway.rs, pets.rs).
16. Session plumbing: lead-only change, as the brief directs; save ordering is now simpler (one
