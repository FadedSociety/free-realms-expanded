# T620 - Six human female creator outfits get item class 0, so a character wearing one cannot enter the world

## What changed

- Cause (attempt 1 and the lead note, reproduced here): the second character was never the problem. World entry
  equips the creator outfit on profile 1 (`Gameplay::apply_identity`), and `inventory.rs` `equip` refuses a class
  that profile 1's `allowed_classes` lacks. Human female clothing sets 30-35 (definitions 77679-77696) reached the
  package with `class_id` 0, so any character, first or second, who picks one of them is disconnected with
  `equipment does not match profile or slot`.
- Where the 0 comes from: `scripts/prepare-opening-base.py` imports creator rows missing from the base catalogue
  out of `CharacterCreate/ItemDefinitions.txt`, and column 9 (ITEM_CLASS) is 0 for these 18 rows. The other 81
  clothing-set items have class 1.
- `scripts/prepare-opening-base.py` (LF kept):
  - Reads `CharacterCreateItemClothingSets.txt` (FEET/LEGS/CHEST_ITEM_ID, all 36 sets, every race and gender) once.
  - An imported creator row with ITEM_CLASS 0 that a clothing set equips gets class 1 (R). Its ids are recorded in
    `inventory.json` `provenance.creator_definitions.reconstructed_class_1`.
  - New audit after the starter audit: every clothing-set item must exist and match profile 1's `slots` and
    `allowed_classes`, which is the same check `inventory.rs` `equip` makes. Otherwise the script stops with
    `creator clothing [ids] cannot be equipped on profile 1`.
- `scripts/test_prepare_opening_base.py` (new, same pattern as `test_content_check.py`): runs the generator on a
  temporary copy of the private lab inputs. It asserts that the 18 rows come out as class 1 and are listed as
  reconstructed. A canary (row 201 set to class 5 in the copied creator table) must stop the generator with the
  audit's message. It skips when the lab is absent.
- Nothing in Rust changed. `inventory.json` is not checked in to `prototype/osfr-tools/data/content`. It ships only
  in generated lab content (`lab/references/rust-opening/inventory.json` and package `content/inventory.json`).
  **The lead must re-run `prepare-opening-base.py` and rebuild the package after merge.** The brief's conditional
  Rust test (every set equips through `apply_identity`) does not apply, because the repository has no real content
  for it to load.

## Client evidence

- The client ships no full item catalogue. The only item-definition table it reads is the creator table:
  string `ItemDefinitions.txt` at `0x017e9048` has one xref. That xref is in `LoadItemDefinitions` `0x00724b80`,
  which is called only from the character creator's `LoadAllDefinitionFiles` `0x00724d80`, and that function
  also loads the ItemMappings, ItemTypes, ClothingSets and StartingSets tables. Rows are built by the
  type-switched factory `NewItemDefinition` `0x00724a80`. The full catalogue reaches the client from the server
  (`PlayerUpdatePacketItemDefinitions` RTTI `0x01b3b8e0`, `BaseClient.AllItemDefinitions` `0x0183584c`).
  `lab/working/OSFR.Client/OSFR Client/Resources` has no other item-definition table; `VehicleItemClasses.txt`
  covers vehicles only. Because no client source has a non-zero class for these 18 rows, the rule is class 1 (R).
- Class is wire dword 9 (byte 32). The before/after generator outputs differ only at byte 32 of these 18 rows
  (0 -> 1), plus their `sha256` and `class_id`. `wield_type` stays 0, as for every class-1 outfit.
- Reference only, not used as a source: Legacy `ClientItemDefinitions.json` lists class 1 for all 18, and
  `data/content/stores.json` sells 77680-77696 for 270 coins. Those store purchases would also have failed to equip
  before this fix, because they use the same definition rows.

## (R) rules

- Creator clothing-set rows with ITEM_CLASS 0 get class 1, the class of the other 81 set items, which profile 1
  allows.
- The rule covers only clothing-set members, not every class-0 creator row. 167 other class-0 rows are type-12
  appearance definitions (skin, hair, face and so on). Legacy disagrees about them (85 have no class, 82 have
  class 1), and world entry never equips them, so they keep the client's 0.

## Open

- `scripts/build_item_catalogue.py` applies its own client overlay, so `item-catalogue.json` still has class 0 for
  these 18 rows. At runtime this is hidden, because `Inventory::load` puts `inventory.json` rows first
  (`or_insert`, inventory.rs about line 420). It would only matter if a row ever left `inventory.json`.
- Lead-only observation (no edit): `identity::Resources::resolve` accepts any creator-table row whose slot matches
  a clothing slot, not only clothing-set members; `pinned_looks` pins only skins and heads. A modified client can
  pick a type-12 class-0 row and break its own new character at world entry. This harms only that client's own
  character.

## Threat note

The change is offline content generation; it adds no client input. A hostile client still chooses only among
creator-table ids that `identity::Resources::resolve` accepts, and `inventory.rs` `equip` still refuses any class
or slot that profile 1 lacks. The server check was left unchanged (option B rejected). The new audit stops a bad
row at generation time instead of letting it surface as a disconnect.
