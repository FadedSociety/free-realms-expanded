## Threat note (secure-code-guardian)

Hostile input: a client can send `33/7`/`33/17` frames with any guid, position and replay rate,
including frames timed after `max_race_ms` but before the 20 Hz timeout tick. Before F119/F148 each
such frame incremented a persisted counter (`attempts` for `33/7`, `observations` for `33/17`);
`KartGateway::handle` copied the changed `ServiceSnapshot`, `Gameplay::handle_kart_entry` compared
the snapshot and reported `changed`, and the gateway wrote a character save. That is a save-write
amplifier on unauthenticated input and corrupts the bounded budget a reconnect would load.

Why it is refused now: the phase, budget-ceiling and race-window checks are pure preconditions and
run before either increment. Only in-window attempts spend a budget, so the flood guard still bounds
abuse while a precondition refusal changes nothing. The owned-guid, finite-position, movement and
ordered-gate checks are unchanged; a hostile position still cannot advance a gate, finish a race or
pay a reward. A refused claim returns no reply. The regression tests assert the complete service and
gateway snapshots plus the save flags, and both canaries break the ordering and fail.

> F181/F207 superseded the pickup half of this paragraph: every evaluated `33/17` frame (including
> timed and pre-Go ones) now spends a **persisted** observation slot, and the spend is save-inert
> through `KartGatewayState::changed_for_save`. See [[F207]].
