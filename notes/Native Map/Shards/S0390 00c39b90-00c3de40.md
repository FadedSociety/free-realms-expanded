## What the range is

One contiguous run of the client's in-game purchase store ("GameCommerce" / InGamePurchaseStore;
the community/emulator catalogue calls the same feature "CoinStore"):

- `00c39c80` `ClientInGamePurchaseStoreManager::Initialize` - points the marketing-data updater at
  `MarketingDataClientSchema.xml`, logs to `MarketingDataDefinitions.log`, sets the
  "automatic data reload enabled" byte at this+0x37bb8.
- `00c39b90` / `00c3b530` read single definition rows from a data source (`image`, `image_tint`,
  `oob_data`; `shortcut_id`, `shortcut_type`, `shortcut_value`, `store_id`, `oob_data`).
- The store definition object `GameCommerce::StoreDefinition<AppStoreBundleDefinition,512>`
  (vtable 01831120) with ctor `00c3b2f0` and dtor `00c3abc0`.
- The manager object that owns stores and definition lists: chain head this+0xc094, entry key
  entry+0x2806c, next entry+0x28070, entry ctor `00c3dde0` (runs the store-definition ctor and
  stores the key). Removal `00c3b790`, unregister `00c39e20`, maintenance `00c3b6c0` plus the
  sweeps `00c39e70` / `00c39ed0` / `00c3af60`, bundle-available callback `00c3b720`.
- Five `SoeUtil::HashListMap` instantiations used as slot pools + hash lookups for the definition
  types, and two more map/dtors in the tail (category-node map, billboard-definition map).

Everything in this range is fed from local marketing data tables, not from the network: the
outside loaders name `mrkt_store_billboard`, `mrkt_store_billboard_panel_vw` and
`mrkt_store_portal_category_vw` (00c40410, 00c400c0, 00c3ff10) and the manager ctor 00c41fc0
names `marketingdata.reload.txt`.

## The five HashListMap slot pools (the big template family)

Each instantiation is the same machinery: a red-black tree of pool blocks keyed by the block's
payload address, a singly linked free list of slots, and a hash bucket array for the map's real
keys. Block = 0x1c header (key/parent/left/right/colour/capacity/used) + N slots of `stride`;
map+8 = entry list head, map+0xc = free slots, map+0x10 = auto-shrink flag byte.

## Contradictions / clarifications for the vault

- `notes/Native Map/Systems/ui.coinstore.md` documents only the S0401 wire handlers (29
  functions). This shard adds the non-wire data-model layer of the same feature; assigning it
  `ui.coinstore` keeps the feature in one place, with `engine.containers` for the template/pool
  internals. If the lead prefers `game.coinstore` for the data model, only the `subsystem` field
  changes - no evidence depends on it.
- Naming: the client classes are `GameCommerce`/`ClientInGamePurchaseStoreManager`; "CoinStore"
  is the emulator-catalogue name. Records use the RTTI names found in the binary.
- `SoeUtil::HashListMap` is not a plain hash map: it is a slot-pool allocator (free list +
  red-black block tree) plus a hash bucket array. The RB-tree helper names are derived from the
  code (colour bit at +0x10, rotations, fix-up cases), not from the template name.

## Open questions

1. Slot payloads are opaque here: the strides (0x5c/0x80/0x24/0x6c) and the initialisers
   (00c38f80, 00c350e0, 00c35140, 010784e0 - all outside the shard) define what each slot holds.
2. The large store-entry objects (key at +0x2806c) have no anchored class name; only the
   embedded `StoreDefinition<AppStoreBundleDefinition,512>` part is RTTI-proven (00c3b2f0).
3. `ImageDataDefinition` virtual slot 3 (00d672c0) is an empty stub in this build, so the
   `oob_data` string read by 00c39b90/00c3b530 is discarded; the original retail build may have
   used it differently.
4. Which definition lists the sweeps 00c39e70/00c39ed0/00c3af60/b6c0 actually hold depends on
   the out-of-shard loaders 00c402b0/00c40360/00c40410; the shard proves the mechanics
   (counter at +0x34, predicates 00c387f0) but not the per-list content.
5. The four embedded-slot counts (16/16/4/4) and growth clamps look tuned for expected row
   counts; nothing in the code states the intent.
