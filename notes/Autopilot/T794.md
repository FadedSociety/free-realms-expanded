# T794: vendor buys and quest item events (Opus builder)

## What the brief got wrong, and what was real

The brief (from the mechanics census) said a vendor buy never raises the quest item events, so a bought item never
advances a "collect item" objective. Tracing every caller says otherwise: `handle_npc_packet` has one caller,
`handle_in_world_inner`, and that caller already did `before = inventory.clone(); handle_npc_packet(..);
npc_inventory_events(&before, ..)` for every NPC-family packet (W104). The 165/4 coin buy and the 66/43 vendor buy both
go through it, after `adopt_gained_pets`, so a bought item counted at the tip, once, and a bought pet item (consumed by
T772 first) counted nothing. Proof: the new real-path buy tests pass on the unmodified tip code.

The brief's literal fix (an explicit `npc_inventory_events(&before, ..)` in each buy path) would therefore count every
purchase twice. Measured: with those two lines added, buying 2 of the objective's item counted 4.

The real defect the same generic call had: it also ran after a 165/12 buy-back. A buy-back returns what a 165/5 sale
took, at the sale price (`sell_unit_price` in, `sale.unit_price` out), so sell + buy-back is free and counted the
returned item as a new one. Looping it would finish any collect objective for an item the player owns and the
store buys. Measured on the tip: one round trip, coins unchanged, count 1 -> 2.

## Change

- `Gameplay::handle_npc_packet` (src/gameplay/npc.rs, the router that owns the 165/x and 66/x families) now wraps the
  routing (renamed `route_npc_packet`, body unchanged): clone the inventory, route, then raise the item events.
  A 165/12 buy-back skips the raise. `handle_in_world_inner` lost its three lines of snapshot and raise (gameplay.rs -2).
- A sell needs no case (decision asked for by the brief): `npc_inventory_events` counts gains only
  (`saturating_sub`), so a loss lowers nothing, the same as every other inventory loss (item requests, consumption).
  A sell also cannot equip (equipped items are refused), so the wrapper's call after a sell is a no-op.
- Events stay once per transaction, after the commit point the buy already uses, inside the gateway's staged clone: an
  error from the raise drops the whole staged request like any other failure in `handle_in_world`.
- Tests: `tests/shop_sale_safety.rs` (Gloria fixture, gateway, the real 165/4 and 66/43 buys) and one shared fixture
  method `VendorFixture::install_collect_quest` (a synthetic accepted collect quest in the fixture's own content).

(R) choices: a 165/12 buy-back is not an acquisition (recovered facts: 165/12 request writer `0x00c759c0`, sender
`0x00c76600`, RTTI `CoinStoreBuyBackRequestPacket` `0x01b72fbc`; the opcode number 12 is the repo's existing constant
`COIN_STORE_BUY_BACK`, not re-derived here: the writer takes its family and subtype from the packet object, not from
its own body). Whether the original credited a buy-back is unknown; crediting it can only be abused, so it is off.

Open: no enabled shipped quest has a `collect_item` objective yet. The two census quests (3020003, 3010032) still use
a visit stand-in (T274) or have no objectives (3010032 is disabled); switching them to a real purchase objective is a
content slice, now unblocked.

## Threat note

A client cannot name what counts: events come from the server's own inventory delta, never a client claim. Hostile
sequences: a 165/12 buy-back spam or a sell/buy-back loop (now credits nothing and costs nothing to repeat, so nothing
to farm); a buy/sell loop (costs the sell/buy price gap each round); a refused buy (insufficient coins, unknown or
unsellable item, full pet roster) leaves the inventory untouched, so no delta, no event, no save (tested via snapshot
equality). A bought pet item is consumed by adoption before the delta is read.
