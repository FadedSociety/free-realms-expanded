## Threat note (secure-code-guardian)

Hostile input: a client can send `33/17` pickup claims with any guid, NaN or teleport position and
any replay timing (pre-Go, in-window, post-window), and can flood valid `33/6` bulk frames on the
reliable path or the recovered direct `5/1` tunnel. F181 kept the budget only in memory, so a
reconnect regained the full 120,000-slot allowance; the pre-F181 code persisted the budget but
wrote a character save for every accepted frame. Both are closed here:
`ServiceSnapshot::observations` is saved and restored (bound-checked on load: a value above
`max_observations` is refused as corrupt), and `changed_for_save` masks the budget and the last
weapon pose from the save trigger.

Why it is refused now: the guard is a `u32` inside `KartService`, updated with `saturating_add`,
inside the staged `Gameplay` clone; the unchanged authority checks (owned guid, phase, finite
position, movement credit, queue cap, ordered gate, server clock) still decide every grant, and no
client-reported quantity reaches a reward. Observation refusals return no reply and grant nothing;
the only mutation is one documented flood-budget slot (and the pose on an accepted `33/6`), which
is committed to the saved race without a save. Reconnecting restores the spent count, so a flood
cannot reset by relogging; an unclean crash loses only the slots spent since the last save (the
next real change and the end-of-session save are the write points). The remaining pre-existing
amplifier is the in-window refused `33/7` `attempts` slot, which still marks a change and requests
one save per claim; that is a lead-owned budget/persistence decision and is recorded under Open
gaps. No `?`/`unwrap`/panicking path was added to the observation handling.
