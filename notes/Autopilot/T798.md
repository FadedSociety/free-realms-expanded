# T798 - Card login without a password: the login sends the card window its session ticket (lead brief, native + research 2026-10-27)

Native run 2026-10-27: the Trading Card Game window opened (T795) but showed the manual username/password dialog. The card DLL
starts its session login (411) by itself only for a non-empty `--sessionID` (DLL `1037b5f0`, session dialog `103c9140`). The exe's
card manager `Startup` (`00ad47f0`) builds `--sessionID` from the play client's session ticket (+0x310) and `--username` from the
station name (+0x454); both were empty because no server message ever filled them.

## Client facts (re-verified against `FreeRealms.exe` for this task)

- The only writer is the receive switch `009471a0` case 82 (`009485f9`): it reads the packet with `00908580` -> field reader
  `008e4e40` and, only when the read had no error, copy-assigns the four strings (`sub_6F9E60`, calls at `00948633`, `00948646`,
  `00948659`, `0094866c`) into play client `+0x30C` (session ticket), `+0x450` (station name), `+0x3E8` and `+0x41C` (realms).
- Packet class `PacketUpdateClientSessionData` (ctor `008dc510` stores opcode 82 at `+4`; four string members at `+8`, `+0x11C`,
  `+0x230`, `+0x344`, stride 0x114 = a 256-byte inline buffer, R). Reader `008e4e40`: a u16 opcode, then four strings, each an i32
  length (negative = read error) and that many raw bytes, no terminator, nothing after. Verified with IDA decompile of `008e4e40`
  and `00908580` and the disassembly of `009485f9` and the switch head `00947210` (82 is not in the default-case list).
- Nothing else sets these strings (research: `lab/runs/claude/card-session-ticket-20261027/final.md`, static scan; a runtime watch
  would settle it). The names "session ticket" and "station name" come from the consumers (R).

## What changed

- `src/startup_messages.rs`: `build_update_client_session_data(session, station, realm_a, realm_b)` -> the tunnelled 82.
- `src/card_game.rs`: `session_data_packet()` draws 16 bytes from the OS (`getrandom`, as `LaunchTickets::mint` does), formats them
  as 32 lowercase hex characters and builds the 82 with that ticket and the station name and both realms empty (R). A failed draw
  is an `Err` (the login fails closed), never a fixed or empty ticket.
- `src/gameplay/card_launch.rs`: `Gameplay::card_session_data()`: `Some(packet)` only when the session has card launches (the card
  content has a launch block), else `None`.
- `src/gateway.rs` (hub, +3 lines): `Event::Login`, after the login-phase startup messages, appends that packet to the replies.
  It is inside the existing `!logged_in` branch, so it goes out once per login (a repeated login message sends nothing, a
  `reset_session` relogin sends a fresh ticket). It is not a snapshot index: the 46-message startup snapshot is unchanged, and
  without a launch block a login's replies are byte-identical to before (test).
- `src/trace.rs`: family 82 joins `sensitive_payload`, so no tracer (gateway trace, `app_out`, Studio inspector) shows the ticket
  as hex. Before this the ticket's ASCII could appear in `body_head_hex` whenever the text heuristic did not trip.
- Tests: `tests/startup_messages.rs` (golden bytes, 255-byte edge, over-limit refusal), `tests/card_launch.rs` (three gateway
  tests), `tests/common/field_battle_fixture.rs` (`Fixture::login_session` returns the login's replies; `session` now builds on it).

## Threat note (secure-code-guardian)

- What the ticket is: a per-login random token, 128 bits from the OS, shown to the client in the 82 and then passed by the client
  to the card DLL as `--sessionID` and echoed in the card login's 411 and the 414 gateway request. It is not remembered by the
  server and compared with nothing.
- Why it is not a credential: the card login is authorised by the one-time launch ticket the game server mints on the client's
  39/37 (T764) together with the character id, redeemed once in the character's live session. The card service only echoes the
  session id back. A test shows the 82's ticket redeems nothing, with the right character id and while a launch ticket is
  outstanding, and that the launch ticket still redeems afterwards. It is never the launcher `SessionId`, the gateway ticket, the
  launch ticket or anything derived from them.
- Where it goes: sent once on the player's own gateway connection; written by the exe to its own card logs and put on the DLL's
  command line (visible in the client's own log); sent by the DLL in plain TCP to the card listener. The server never logs it:
  the card listener already names neither ticket nor session id, and the packet is now redacted in every trace. An attacker who
  reads it gains nothing the card login accepts.
- Hostile client: the 82 is server-to-client only; no new client-controlled input is parsed. A client that ignores it keeps the
  manual dialog. Strings are length-checked (<256) in the builder.
- Station name and realms stay empty (R): `--username` would put an account handle on the DLL's command line and in client logs
  for nothing the card service uses. Fill string 2 later only if the native run shows the DLL needs it.

## Checklist

1. A refusal changes nothing: no new refusal path; `handle_at` stages everything on clones, so an `Err` (no randomness, or any later
   child) drops the whole outcome including the 82 and the login can be retried. The 82 touches no saved or gameplay state.
2. Rollback covers all state: the ticket is not stored anywhere, nothing to roll back.
3. Apply deltas: n/a, nothing restored over live state.
4. Busy rules: n/a, no activity added.
5. Every entry path gated: the only path is `Event::Login`, in the `!logged_in` branch, gated on card launches; the reconnect
   relogin (`reset_session`) goes through the same branch. Test: with and without the launch block, and a repeated login.
6. Reachable in production, tested through it: the tests log in through `Gateway::handle_at` on a production-shaped session root
   (`Gateway::load_gameplay` with a content directory whose card file has the launch block, the same loader the binary uses).
7. Survives reconnect: session-only by design; a new login sends a new ticket (tested: two logins, two different tickets).
8. Exit paths: n/a, no state to restore.
9. Economy safety: n/a (no items, coins or rewards). The ticket authorises nothing (tested).
10. Wire format matches the client reader: reader `008e4e40`, handler `009485f9`, switch `009471a0`; byte-level golden test of the
    builder (opcode, four strings, order) and an exact layout check on the gateway's real 82 (50-byte body: opcode, 32-byte
    ticket, three empty strings).
11. Unique ids: the ticket is random per login; test asserts two logins differ. (Collision odds are 2^-128; nothing depends on
    uniqueness.)
12. Others see changes: private to the logging-in player; nothing is broadcast.
13. Content works end to end: the end-to-end effect (card window logs in by itself, listener logs `card_login`) needs the native
    run; the server side is tested to the packet the client reads. Not claimed beyond that.
14. Values live in data: no tunable value; the ticket length is a protocol-shaped constant (16 random bytes, 32 hex characters).
15. Canaries break production code: run and reverted. Ungated send (`card_session_data` always `Some`) failed
    `a_login_without_a_card_launch_block_sends_no_session_ticket`; removing 82 from `sensitive_payload` failed
    `the_session_ticket_authorises_nothing_and_is_never_traced`; swapping the session and station strings in the builder failed
    `update_client_session_data_is_four_counted_strings_after_opcode_82` and the two gateway tests that read the ticket; a constant
    ticket failed `a_card_login_sends_one_fresh_session_ticket_last`.
16. Session plumbing: gateway.rs gets one in-branch append in `Event::Login`; no change to session creation, teardown,
    transactions or save ordering. The lead reviews it as a login-path change (brief).
17. One player's error never stops the server: the only fallible step is the OS random draw; it returns `Err` that fails that
    player's login like any other `handle_at` error (the same pattern as the launch-ticket mint), no panic, no unwrap on client data.
    The builder's `assert!` guards server constants only (the ticket is 32 bytes, the rest are empty).
18. A type's rules live on the type: no struct fields added.
19. Hot paths: runs once per login, not per tick or packet; one 16-byte draw and a 57-byte packet.

Skills applied: ponytail (full, with the review pass: the builder keeps four parameters only to pin the field order in the golden
test; the station and realms are passed empty), secure-code-guardian (threat note above).

## (R) choices and open gaps

- (R) Station name and realm strings empty. If the native card window still shows the manual dialog or the DLL wants a name, string 2
  is one argument in `session_data_packet`.
- (R) The 82 goes last in the login-phase batch. The client handles it in the same switch as the other startup messages (12, 43, 57,
  67, 166); whether the original server sent it at login or later is unknown (research, "what stays unknown").
- Not settled here (research item, separate): how the DLL reaches our card listener (realm string 3 selects the DLL's environment;
  empty selects the live Sony names) and what the in-exe Treasure War client (type 23) does with a non-empty string 1.
- Native check after merge: `ClientTCG.log` Startup line shows a non-empty `Session Ticket:` (harness redacts it);
  `FreeRealms.log` "TCG Start command line:" gains `--sessionID=...`; the card window shows the session-login dialog; the card
  listener logs `card_gateway_request` then `card_login`.
