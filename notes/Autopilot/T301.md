## Security threat note (secure-code-guardian)

Attack surface: a hostile client can send arbitrary 26/8, 26/10, 26/6, 26/13, 49/2,
49/14, 45/7, 39/x and 50/1 bodies, choose a target GUID, position and timing, and replay
any of them. The suite asserts the rewarded outcome comes only from server state:

- **Turn-in authority.** 49/14 pays only when `QuestState.pending_turnin == quest_id`;
  the pending value is set only by the server's own completion Talk (`on_event` ready +
  giver), the reward amount/item/profile come from the saved quest definition, and
  `rewards::apply_grant` is keyed `quest:<character_id>:<quest_id>`. Premature, wrong
  quest, wrong NPC, repeated and post-relog replays were all asserted to change no byte.
- **Kill authority.** Quest credit is `QuestEvent::KillActorKind` emitted by
  `apply_encounter` from `EncounterOutcome.defeated`, which the engine fills only on its
  own alive-to-dead HP transition for a positive production definition. A forged target
  GUID, an out-of-range attack, a zero definition and a client claim (45/7) advanced no
  counter; a forged 39/18/39/14 and a forged 50/1 bundle did nothing.
- **Economy.** Coins, item and job XP are granted only by `finish_turnin` ->
  `apply_grant`, which uses checked arithmetic and the production bag capacity. The
  full-bag case is refused atomically (no coins/XP/item, pending kept, state and
  `saved()` bytes equal; the bag is at exactly 100 stacks after F339). The reward item
  exists in the real inventory catalogue and is not already owned, so the +1 assertion is
  about a real new stack; a replay cannot double-pay.
- **Refusals.** The refused actions in tests 2, 3, 4 and 7 are asserted to change neither
  the whole `GameplayState` nor its serialized bytes; a refusal `Err` is only accepted
  when it is `InvalidData`, never a panic or a partial write. The zero-definition kill is
  an accepted kill with no quest credit (no 49/9/49/10), not a refusal. No `unwrap` is
  applied to client-controlled data in production by this task (no production change).
- **Client-reported results.** 39/18 and 39/14 are consumed only from the server's own
  settlement replies in `apply_encounter`, not from a client request; the tests send
  well-formed positive-id packets. 45/7 can move only a `client_reported` goal (W175,
  reconstructed policy); the first-hour quest has none, so its server-owned defeat
  objective cannot be claimed. This test does not claim that a `client_reported` goal is
  server-verified — the engine deliberately trusts the client for that goal class.
- **No dev command.** The suite's local packet shapes are checked not to be chat requests
  (family 15), the kill and turn-in replies are checked to contain no 15/x chat/system
  line, and the fresh character cannot run any developer command (`Gameplay::may_run`
  false for offer/teleport/here/broadcast/cheat/give/npx).
