Both dispositions are closed; I verified the current sources and the current note text rather than the earlier snapshots.
2. **Packet schema is writer-exact, confirmed three independent ways.** From the pinned sources the application message is `u16 LE opcode 38`, `u16 LE sub-opcode 12`, `f32 LE x4` position (X, Y, Z, W=1), `f32 LE x4` facing (X, Y, Z, W=0), one byte `Teleport = 1`, one byte `Unknown = 0`; 38 bytes total, before the gateway's `[5,0,1][u32 length]` tunnel wrapper. 4. **Resolution, refusals and the keyword boundary are non-mutating.** Target selection is exact name, then GUID, then unique prefix, then unique substring, all filtered to the character's current zone, and only zone 0 is accepted (`dev_teleport.rs:11-13,34-70,129-190`). Ambiguous, unknown, cave-zone, empty, over-specified and non-finite targets reply without touching the snapshot; the `goto` keyword now requires end-of-string or a whitespace boundary (`dev_teleport.rs:35-41`), and the saved RED for that fix reverts only the boundary hunk and shows both the unit test (`gotomae must fall through to the ordinary handler`) and the gateway test (`gotomae must not mutate`, snapshot showing the pre-fix relocation from the Queen to Mae) failing, with the file restored to the same `a6c5498b…` hash and both tests green again (`red-02-keyword-boundary.log`).
5. **The relocation is a bounded standoff that lands in interaction range and faces the actor.** Arrival is 4.0 m from the actor horizontally at the actor's own Y, i.e. inside the campaign's validated 12 m interaction radius; the builder notes it does not parse collision and does not claim a verified floor. My independent recomputation from `opening-anvil-placement-v1/content/opening.json` for Mae Farnum (GUID 5715144128442925060, position `[-2112.839, -56.52175, 208.5168]`, radius 12) gives distance 3.9998 m and facing dot 3.9998 > 0 for the first-freeze arrival, and the finite/unit/degenerate-origin cases are unit-tested. The arrival-selection rule was later refined to the sampled sampler; the standoff distance, actor-Y and facing properties still hold, and the standoff supplement at the end of this note supersedes the specific arrival and line references.
6. **Relocation itself cannot grant progress.** `OpeningEngine::set_location_without_events` (`opening.rs:598-608`) only validates the position and rewrites the remembered origin; it never calls `on_event`, so it cannot accept quests, award discoveries/rewards or change counts. A direct opening-level test now proves the boundary: `on_position` at a real discovery fires it (state changes, message emitted) while `set_location_without_events` at the same position leaves state equal and rejects a non-finite position without mutation (`tests/dev_teleport.rs:445-478`). The gateway-level tests additionally assert the whole gameplay snapshot is unchanged by the relocation and by a follow-up movement confirmation at the arrival point.
7. **Refusal states cover craft movies, live encounters, knockout and unloaded sessions.** While cooking, smelting or forging is active, the existing gates answer `realm …` with "Close the … game before other opening actions" and return before the developer command runs (`gameplay.rs` craft branches; unit test `gameplay::developer_teleport::crafting_movie_refuses_relocation_and_keeps_state`). `relocation_block` refuses an active encounter and a knocked-out character (`gameplay.rs:669-684`), and application messages cannot reach gameplay before the world is loaded (`gateway.rs` `if !loaded { continue; }`), so an unloaded session cannot relocate.
8. **Staging, persistence and restart are atomic and agree with the packet.** `Gateway::handle_at` decodes every child first, applies to clones, and commits only after all children succeed (`gateway.rs:552-557,571-704`), so a relocation bundled with an invalid child leaves the gateway (and therefore the saved snapshot) untouched — asserted by `private_dev_teleport_bundle_is_atomic_and_restart_keeps_the_position`. The binary saves the staged snapshot before queueing any reply (`bin/osfr-gateway.rs` handle path), and the same `state.position`/`state.rotation` values are used for the packet, the live state and the save. The restart test saves, reloads through `game_store`, re-enters the world normally, and re-runs the command with the position preserved.
9. **Evidence quality of RED/GREEN is good.** `red-01-behavioral.log` is a genuine behavioral RED — the failing assertion is the missing `38/12` packet, not an API compile failure; the two API compile errors in `compile-01.log` were fixed separately in `compile-02.log`. `green-03`–`green-05` cover 5→6 ignored integration tests plus 22 lib tests post-format; `full-suite-final.log` records 34 targets, 185 passed / 0 failed / 35 ignored; my own `cargo fmt --check --all` exits 0 and my own `cargo test --test dev_teleport -- --ignored` runs 6/6 green on the frozen tree.

## Exact message schema

The relocation emits the pinned Sanctuary `ClientUpdatePacketUpdateLocation` unchanged (`lab/references/Sanctuary` revision `4f028dcc274f628b65ef665fd59b184f5f3d3e3e`):

| bytes | field | source |
| --- | --- | --- |
| `26 00` | base opcode 38 | `Sanctuary.Packet/BaseClientUpdatePacket.cs` |
| `0c 00` | sub-opcode 12 | `Sanctuary.Packet/BaseClientUpdatePacket/ClientUpdatePacketUpdateLocation.cs` |
| 16 bytes | position X, Y, Z, W (f32 LE), W = 1 | `PacketWriter.Write(Vector4)` |
| 16 bytes | facing X, Y, Z, W (f32 LE), W = 0 | `PacketWriter.Write(Quaternion)` |
| `01` | `Teleport` bool = true | `ClientUpdatePacketUpdateLocation.Serialize` |
| `00` | `Unknown` byte, writer default | `ClientUpdatePacketUpdateLocation.Serialize` |

Total 38 bytes. The client's own constructor agrees on the identity: the native constructor sets the base word to `0x26`, the sub-opcode to `0xC`, and zero-initialises the trailing byte field (`lab/decompiled/client/FreeRealms/pseudocode.c` lines 973123-973133 and 973664-973682). The gateway wraps this in the standard tunnel `[5,0,1][u32 little-endian length][inner]` before transport. Pinned source hashes verified by me: `ClientUpdatePacketUpdateLocation.cs` `ec6ffc8e…`, `BaseClientUpdatePacket.cs` `f089a567…`, `PacketWriter.cs` `3752e60d…`, `TeleportCommand.cs` `311be82c…`, `PacketZoneTeleportRequestHandler.cs` `e20e1b10…`. Reply order on the wire is this packet first, then the confirmation chat reply (`gateway.rs:671-687`), matching the pinned handler and asserted by the integration test.
