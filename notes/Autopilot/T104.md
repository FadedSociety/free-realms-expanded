# T104 Group invite expiry

## What changed

- `src/social_lists.rs`: pending group invites retain their monotonic
  `created_ms`. Expiry is lazy: `invite_to_group` and `respond_group_invite`
  remove expired rows before they use capacity or answer a response. Family 40
  has no invite-timeout notice, so expiry emits no packet.
- The default lifetime is 60,000 ms. It is configured by
  `--group-invite-ttl-ms N`, bounded to 1,000..=600,000 ms, and applied by
  `Server::new` before sessions are accepted.
- 40/4 response parsing retains the echoed group id. A stale pop-up carrying an
  older group id receives 40/5 code 3 and does not consume a replacement
  invitation from another group.
- The earlier `Session::commit_outcome` expiry call is deleted. No session
  transaction, save ordering, teardown or tick maintenance path was changed.
- `tests/group_invite_expiry.rs` covers the literal 59,999/60,000 ms boundary,
  request-side capacity release, late-response refusal, persistence neutrality
  and configured bounds.
- `src/bin/osfr_gateway/t020_group_routing.rs` drives late accept, replacement
  invite, stale accept and stale decline through the real family-40 route
  without a cleanup tick.

No application selector was added, so no new `app_fuzz` seed is required.

## Reconstructed rules

- (R) An unanswered group invite expires at the configured monotonic duration.
  The 59,999 ms offset remains valid at the default; 60,000 ms expires it.
- (R) Expiry only removes the pending row. It does not disband the group,
  change membership, move either character, write social persistence, or spend
  action budget. Pending invites remain volatile and are never saved.
- (R) Expiry is silent. A late or stale response receives the existing 40/5
  code 3 refusal; no timeout opcode or extra wire field is invented.
- (R) The lifecycle is bounded to 1,000..=600,000 ms so a misconfiguration
  cannot make invitations effectively eternal or expire instantly.

The client guide records group pop-ups in the 300 s GAQ class and a 60 s
visible window. The server reservation policy and default remain reconstructed.

## Security threat note

A hostile client can send arbitrary target names, replayed 40/4 responses,
forged group ids, repeated accepts/declines, malformed lengths and oversized
configuration values. Names are bounded and resolved through the authenticated
identity directory. Response values use the server-bound character guid, never
the packet sender guid. A response must match the current pending invitation's
group id; late, repeated or forged responses receive the existing code 3
without consuming a replacement invitation. Configuration is parsed as `u64`
and rejected outside 1,000..=600,000 ms. Refusals do not alter membership,
profiles, persistence, capacity, or another player's invitation.

## Checklist

1. **A refusal changes nothing.** Late accept is tested through the router
   against unchanged roster, group mappings and profiles. A forged/stale group
   id leaves the replacement invitation pending. Invalid TTL values leave the
   prior setting intact. Canary 1 (response-side expiry removed) and canary 4
   (invite-side expiry removed) made the refusal/replacement tests fail, so both
   call sites are live; canary 2 proved the stale group-id guard is live.
2. **Rollback covers all state.** No transaction or shared side table was
   added. Social service mutations remain inside `SharedWorld`, and the global
   commit-time call was removed.
3. **Apply deltas, never restore old snapshots.** The change removes one stale
   invitation row and applies the new response result; it never replaces a
   profile, roster or saved social document with an older clone.
4. **Busy rules are mutual.** Group membership is not a new activity and does
   not occupy the player. The shared occupation table is unchanged.
5. **Every entry path is gated.** Client invite and response both enter through
   `route_application` and run expiry plus identity/branch checks. No automatic
   or reconnect path creates an invitation.
6. **Reachable in production, tested through it.** T020 tests call
   `Session::route_application`; `Server::new` applies the configured lifetime.
   No internal-only copy of the route is tested.
7. **Survives reconnect.** Pending invitations are volatile by design and are
   cleared on disconnect. Membership persistence is unchanged; the expiry test
   asserts the saved social document is byte-identical.
8. **Every exit path restores the player.** Expiry changes no location,
   membership or activity state. Accept failure leaves the target ungrouped and
   the existing party intact.
9. **Economy safety.** Group invites and responses grant no coins, items or XP;
   no client quantity or item id is involved.
10. **Wire format matches the client reader exactly.** 40/5 is one dword at
    `0x00909090`; dispatcher `0x0093daf0` case 5 at `0x0093e8c8` maps dword 3 to
    the not-invited branch at `0x0093e924`. 40/4 retains the existing group-id
    field: writer `0x00a97250` writes it through `0x00a95c50` between the two
    NameData blocks and the accepted byte; the route test sends that exact
    packet shape.
11. **Unique ids.** No new instance id is introduced. The existing server
    allocator still supplies group ids, and response checks bind to that id.
12. **Others see changes.** Expiry is silent and changes no visible roster,
    outfit, job, mount or actor state. Successful membership behavior remains
    covered by the existing T020 fanout tests.
13. **Content works end to end.** Invite, accept/refuse, replacement and late
    response reach final roster outcomes through the real router.
14. **Values live in data.** The lifetime is operator configuration with a
    default and bounds; no behavioral timeout remains compiled into the expiry
    call.
15. **Canaries break production code.** All four canaries changed production
    branching or configuration use and failed the relevant behavioral tests
    before restoration.
16. **Hands off session plumbing.** The commit-time call was deleted, so the
    diff leaves `Session::commit_outcome` at its pre-T104 behavior. No session
    creation, teardown, transaction or save-ordering code was edited.
17. **One player's error never stops the server.** Malformed, forged, repeated
    and expired requests return typed social results or are dropped by the
    existing parser; none can propagate a panic from client-controlled data.
18. **A type's rules live on the type.** `SocialService` owns the lifetime field,
    its bounded `set_group_invite_ttl` setter and the expiry check. The field
    doc comment says it is host policy copied with the service and never
    persisted, so a future field is decided by the same rule.
19. **Hot paths stay cheap.** Expiry runs only on a 40/1 invite or a 40/4
    response over the bounded pending-invite map; it does no clone, allocation
    or save. The removed commit-time call is why no global state is walked on
    every tick.
