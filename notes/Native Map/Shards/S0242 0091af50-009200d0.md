## 1. Wire framing recovered in this range

The PlayerUpdate dispatch `0092f460` (BaseClient slot 69) calls three small wrappers that
build a reader over the packet body; tracing which switch case calls each wrapper binds the
records to concrete packets:

| Dispatch case | Packet | Wrapper | Body reader |

| 0x27 (39) | PlayerUpdatePacketCustomizationChange (35/39) | `009254e0` | `0091aff0` |

The ClientUpdate dispatch `009392c0` constructs ClientUpdatePacketActivateProfile (38/21) in
its case 0x15 through `0091bfe0` and then parses the body with wrapper `00925550`, which
calls `0091b080`. `0091b080` reads two i16, a length-prefixed blob (pointer+length at
+0xc/+0x10) and a count-prefixed list, then three i32 — a layout that matches the
attachment data the packet class also holds.

Two further handlers are bound by their own evidence: `0091e1a0` is BaseClient slot 75 and
applies a stat update: it constructs ClientUpdatePacketUpdateStat (`008ea870`), parses two
i16 header words, an 8-byte entity key and a typed value list (`0090a540`), looks the
entity up by key (`00984960`) and writes the values into that entity's +0x474..+0x494 and
+0x67c fields. `0091e060` is BaseClient slot 77, the 102/2 lobby-definition handler already
documented in `Research/Kart Lobby Definition Framing.md`; this shard confirms the call
chain (`008d67a0` header gate, `008f74c0` tunnel unwrap, `00919b60` five-table body).

Server contract hypothesis spanning these functions: the original server pushed 35/7 and
35/39 records keyed to the local player, 38/21 profile activations, 38/7 stat lists and
102/2 lobby tables. Each inference depends on the dispatch case (which the client code
proves) plus the matching reader or handler named above; none of them is a captured frame.

## 2. Reward bundle family (ClientRewardBundle / RewardBundleBase)

`0091c110` constructs RewardBundleBase (vtable `018056ec`; ClientRewardBundle's vtable
`01823e2c` shares the same slots). Field map proven here: intrusive list head/tail/count at
+0x38/+0x3c/+0x40 (`0091c5e0` add, `0091c680` remove, `0091c5b0`/`0091c5c0` count/head),
reward amounts at +0x48 (XP/stars) and +0x50 (coins), reward kind at +0x54 — the last three
matching the reward-toast note, whose cited getters `0091c290`, `0091c2e0`, `0091c380` are
in this shard. Two 8-byte id pairs live at +0x80/+0x88 with copy-out/set accessors
`0091c530`..`0091c590`, and two `SoeUtil::List<SoeUtil::StringFixed<256>/<512>>` members at
+0x94/+0xa4 with `0091c720`/`0091c7c0` appending string entries. The field at +0x4c is a
third accumulator whose meaning is not in the note and stays unresolved.

The bundle is embedded in the quest record shapes: `0091c8b0` (+0x18, called by the raw
reader `00922810` and by QuestObjectiveAddedPacket::Construct), `0091c940` (+0x30, plus a
`SoeUtil::HashList<ObjectiveData,16,0>` at +0xe8, called by the full-self loader `00940c60`
and QuestAddPacket::Construct), `0091c9f0` (parallel variant with two id pairs), and
`0091c7e0` (packet-side holder with the bundle at +0xc0, constructed right after operator
new in `009392c0`/`00944fe0`). Together with `0091bb40`/`0091bbb0` (both cited by
`Research/Native Journal Live Objective Keys.md` for runtime quest creation) this ties the
client's quest pipeline to the same reward model the reward packets use.

   inside the object (`FUN_00913db0`, `FUN_0090b0f0`, `FUN_0090b190`), but the opcode words
   themselves are only visible once the owning packet class constructor is known; their
   wire entries were left empty on purpose.
2. `0091d920` restores BaseFotomatPacket/BasePacket vtables yet also destroys the
   +0x700e0 buffer initialized by the PacketSnapshotRequest constructor `0091d8c0`; whether
   it is `~BaseFotomatPacket` or the derived packet's teardown is not settled.
3. The direction of the Fotomat snapshot request (`0091d8c0`, sub-type 4) is inferred from
   the class name only; no captured frame of that sub-type was matched.
4. RewardBundleBase's +0x4c accumulator and the id pairs at +0x80/+0x88 still lack
   semantics; the reward note does not cover them.
5. The owner of the third container instantiation (`0091ff60`..) lives outside this shard.
