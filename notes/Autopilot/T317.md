  display `sub_9F5AE0`.

## Method and (R) rules

1. One greeting per NPC, chosen because the line's speaker is proven, not
   because it is nearby.
2. Five rows use a content quest record's 49/1 `intro_text_string_id`: medic
   3090027 (Callahan) and 3090019 (Docaloc), postman 3130017 (Enve), fisherman
   3070027 (Dooba) and miner 3100028 (Snorg). Those intros are reconstructed
   content (`scripts/quest_text_backfill.py`), so each is checked two ways: the
   quest record's `giver_npc_id` + `intro_text_string_id`, and a job-guide row
   that names the NPC as giver and contains the same hash. The test asserts
   both, so a wrong T-1 intro cannot pass (the brawler 3030026 failure).
3. The other seventeen rows: sixteen cite a guide row that names the NPC and
   contains the line's hash (region guides, plus Kart Driver 142 for Bill,
   Brawler M6 133 for Andrew and Adventurer E16 139 for Chugug). Reginald's
   cited row names him but does not quote the hash; his locale line
   self-identifies ("my name is Reginald"), which the test requires for him
   only. `another_npcs_valid_locale_line_is_rejected` proves a valid line for a
   different speaker fails.
4. `(R)` every row uses one recovered speaker line as the fixed default Talk
   greeting. The original server greeting/phase table was not recovered, so a
   quest phase does not change the first-click body and no text is invented.
5. `(R)` the five quest-intro speaker links are inferred through reconstructed
   quest text, not a recovered NPC-speech table; the guide quote is the
   independent check. Chugug uses a different guide-quoted line from the same
   quest (93809), so his greeting is not the reconstructed intro.
6. `(R)` all 22 rows are fixed defaults; there is no client choice, no fallback
   to another row and no locale overlay.
7. Jammie (104270) and Esther (407023) were bound by T317 from reconstructed
   quest intros whose guide rows do not quote them. F349 leaves them blank
   rather than trust a T-1 backfill; both are listed as unbound with the reason.

## Security threat note (secure-code-guardian)

- This slice changes no parser, save, coin, item, reward, role, chat or trade
  code. The only new values are static server-side `u32` locale ids and their
  evidence strings; the client never supplies a locale id.
- Hostile client input on the path is the existing 26/8 target GUID and the
  26/10 NPC GUID/option pair. The router resolves the GUID through
  `NpcVisibility::content_key`, requires an open menu for that exact NPC key,
  and rejects an unknown GUID (no menu) or an out-of-list option
  (`InvalidOption`). The fallback test sends `i32::MAX` and then selects Talk on
  the same still-open menu (no second `interact`) and gets the unchanged empty
  body; an unknown NPC id is refused and the menu still works.
- A client cannot choose or inject the body: `greeting_string_id` is a `u32`
  read from server content, so a hostile client cannot inject text, choose a
  locale id or trigger an allocation from an attacker-controlled size. Nothing
  is consumed or mutated by a refusal; the greeting is read-only static content.
- The source gate rejects a raw hash (the evidence must name
  `Global.Text.<id>` and the test resolves that id three ways), so a field that
  would render blank cannot pass. No player name, chat text, HTML or path enters
  the packet; the evidence strings are provenance and the tests/tests data
  contain no player names.
- Loader bounds (8 MiB/file, 32 MiB total, 20,000 rows) are unchanged and
  asserted. All 22 ids resolve in the stock client locale, so no overlay or
  fallback path is introduced. No per-player state and no new entry path.
- F349 changed only the test and content. The strengthened proof reads
  repository guide notes and the stock locale, never client input; it is a
  build-time provenance gate, not a runtime path. The test's refusal case still
  asserts that an invalid 26/10 selection changes nothing and the next Talk on
  the same open menu returns the same body.
