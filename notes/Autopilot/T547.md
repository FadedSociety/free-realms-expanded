## Security note (threat model, secure-code-guardian)

A hostile client can send only the existing 26/8 interaction with an arbitrary u64 target. The
new veins add no parser: the target must be a guid this player's loader placed (the guid space
is fixed server-side), the player must be in the open world, within the type's 12 m range, not
busy, and a Miner with the Miner job active; every refusal returns `Denied` text and changes no
state (staged on a clone in `handle_gathering_node`). Appearance values come from repository
content, are bounded at load (scale 0..=100 finite, alias <=120 bytes), and cannot be set by a
client. The new spawn ids (33585+) are in the mining file's own tag space and cannot collide with
the old ids 1..5, so a click cannot alias a different node. Rewards are unchanged: the server
owns the board, quotas and payout; nothing is taken from the client's report. `cursor_id` is not
sent, so it cannot affect the client.

Validation checkpoints applied (secure-code-guardian workflow):

- Authorization: the non-Miner and wrong-job paths are refused by the existing `admit` gate and
  tested (`a_non_miner_click_is_refused_and_changes_nothing`); no role or job check was relaxed.
- Input handling: the only client value is the target guid; it must equal a server-placed node
  guid, and a forged id falls through to the NPC menu path (`Denied::Gone` when absent).
  Appearance/scale/alias/range values are repository content, not client data, and are bounded
  at load (an out-of-bounds value refuses the whole node file's load, as the existing bounds do).
- Logging/secrets: no secret, key or per-device value is in the diff; refusals use the existing
  system-chat text, and nothing sensitive is logged.
