# T899 - NPC cursors, shop/combat markers, subtitles and dispositions from Sanctuary Npcs.json (Sonnet builder, 2026-10-30)

Skills applied: ponytail (full, review pass on the diff). No client input is parsed and nothing is granted or charged, so
secure-code-guardian does not apply (threat note below).

## What changed

A new content file `data/content/npc_presentation.json` holds one row per NPC name string id: hover cursor (`cursor_id`,
`relevance_flag`), the 35/10 rows the NPC shows (`notifications`), the line under the name (`sub_text_name_string_id`) and the
AddNpc `disposition`. `src/npc_presentation.rs` loads and validates it (`Presentation::new`), applies a row to a spawn
(`Presentation::apply`) and writes the 35/12 entry (`encode_cursors`). `world.rs` `NpcVisibility::load` calls `apply` for
every drawn regional row and every extra spawn; `VisibleNpc::draw_packets` now sends 35/2, then the 35/10 (existing), then the
new 35/12. Values the NPC row sets itself (an extra's `sub_text_name_string_id`, its own `notifications`) win over the table.
An absent file is an empty table; a bad or repeated row refuses the whole load (`NPC presentation: name id N: ...`).

The file is generated from Sanctuary `src/Resources/Npcs.json` at main 3b3aec3 (AGPL-3.0-or-later; source line in the file,
credit in NOTICE) and joined to our NPCs by name id: 153 rows (130 cursors, 57 with notifications, 91 subtitles, 3 dispositions),
for the 1,533 distinct name ids of our regional rows and extras. They reach 10 drawn regional rows and 542 extra spawns (name-id join count).

`placed_cakes.rs` `cursor_relevance` now calls the shared `encode_cursors` (same bytes, one 35/12 writer less).

## Client facts (IDA, this task)

- 35/12 entry reader `008db5e0`: u64 guid, u8 has-cursor, an i8 cursor id only when set, u8 flag. `00962f30` stores the id
  (or -1) at actor `+0x708` and the flag at bit `0x10` of `+0x145`. The id is a signed byte, so rows above 127 are refused.
- 35/10 handler (`00932100`-`00932157`): the record's `+0x10` (the third value on the wire) at 0 or less skips the whole row.
  Sanctuary names that value `IconState` and the second one `IconId`, so a row is `image_id = IconState`, `state = IconId`
  (the same order `npc_notifications.rs` already documents and quest markers use natively: state 0, image 2).
- `NotificationImages.txt` (client `Resources`) was read to confirm every imported image key exists (385 keys).

## Choices

- Notification kinds kept: 1 (shops: 36 rows in the table), 3 (combat: 3), 6 (minigame and harvesting areas: 18) and 7 (trainer;
  none of ours). Dropped: kinds 0 and 2 because they are the quest-giver badge; ours are per-player 35/10 and 35/11 from
  `quest_markers.rs`, and a fixed badge would stay on NPCs whose quests are disabled. Kind -1 is refused by
  `Notification::validate`. Sanctuary rows with an `IconState` of 0 (veins, plants, trainers, Robgoblin Junkpile) are dropped
  because the client skips them; the vein and warpstone markers keep their own content rows (T555).
- The join key is the name id; a name id can have several Sanctuary rows (e.g. 313, 2061, 4412, 4560, 4893, 5103), and the rows
  that carry no data are skipped, so the join takes the one row with data (no two data rows disagree on the fields kept).
- Only Sanctuary rows with `HasCursor` set give a cursor. Twelve warpstone rows (legacy-format: `CursorId` 17 but no `HasCursor`,
  so Sanctuary sends no cursor, `BaseZone.cs` copies `HasCursor`) were dropped from the table in the review fix; warpstones keep
  their own content rows (T555) and show no hover cursor.
- Only notification kinds 1, 3, 6 and 7 are imported (the lead may confirm; kinds 0 and 2 are the quest badge, see above).
- Quest cursor 5 per player (retail swaps the cursor for a quest giver) is not built; it is pull-list item 48.
- `relevance_flag` is carried as captured (Sanctuary `RelevanceUnknown2`, 28 rows): its meaning is not recovered (R).
- Disposition 0 is applied to a drawn friendly body (red name). T892 already takes the camp enemies it routes out of the passive
  table (`exclude_actor_guids`), so those keep the hostile 35/2 of the field-enemy path. Only 3 of our name ids have a Sanctuary
  disposition row (the other hostile definitions are name ids we lack: ENEMY-DEFINE); bodies of those left in the passive table
  now show red as in the original but have no fight route (rule 7: no spawn is added or moved).
- The same row sets a hover cursor on props that have no server handler (plants, decor). That is what Sanctuary sent from
  captures; clicking such a prop still logs `unknown_runtime_guid`, as before.
- Subtitle ids (`SubTextNameId`, `ReferenceId`) are Sanctuary's; their English text was not re-read from the client locale (R).
- Gloria (pet merchant) has no Sanctuary row, so she is still without a shop marker: that is T890 (a marker from our own vendor
  data). T890's `mark_shops` replaces a same-kind row, so the two compose.
- Regional rows with a non-`legacy_data` placement never spawn (world.rs), so their rows are unused until placed.
- Studio-placed NPCs (`npc_placements.json`) and harvest nodes keep their own presentation; the table is not applied to them.

## Threat note

The table is server content read at load; no packet from a client chooses a cursor, marker or disposition. The 35/12 entry is
written from the NPC's own runtime guid. Bounds: cursor id at most 127, disposition 0..=2, notification rows validated by
`Notification::validate` and capped at 256, file size capped by `read_rows` (16 MiB), repeated name ids refused.
