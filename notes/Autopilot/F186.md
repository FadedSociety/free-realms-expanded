## Threat note (secure-code-guardian)

- A hostile client can send 138/2 register, 138/5 cast-anim, 138/6 cast, 138/7 reel, 138/15
  special and the shared minigame lifecycle/menu packets. It cannot supply a timestamp, a cap
  value/id, an item definition, a catch result or a character guid. Its only cap-relevant action
  is a reel-in, which requires the server's own cast -> bite -> hook state; replays and
  out-of-order reels are refused and pay nothing.
- A production account-store handshake session carries the template guid (the first account's
  character) before login. The lead's owner gate refuses publication unless the session has
  selected a character, its gateway guid matches its bound character, and `active_sessions` names
  it. Because this test's options have no account store, it sets the same `selected_character`
  state explicitly (the review's focused-test remedy) and proves both halves independently:
  `selected_character = false` while active owner, and a selected non-owner. Both leave the
  ledger unchanged; canaries 1 and 2 prove each assertion.
- `restore_hour_history` rejects guid 0, an oversized history and out-of-order timestamps and
  leaves the existing ledger unchanged on refusal.
- Refusal order: `settle_catch` checks the cap before `apply_grant`; a capped catch pays no item,
  coin or XP, sends the escape result and requests no save. The transaction assertions (full
  snapshot, coins, XP, save bytes, ledger) are in the regression.
- The ledger is not durable across a server restart and the publication is not atomic with the
  character save; both are explicit lead-owned gaps below, not claimed as fixed.
