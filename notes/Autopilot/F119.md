# F119 review fixes for T028

## Review disposition

The single BLOCKER in `lab/autopilot/reviews/0c547ad-T028.md` is valid. A gate claim after
`max_race_ms`, but before the next 20 Hz tick, incremented the persisted `attempts` counter before
returning `RaceTimeout`. That made the refusal mark gameplay changed and trigger a character save.
There were no MINOR findings.

## Changes

- `prototype/osfr-tools/src/kart_service.rs`: the phase and flood-budget checks still run first,
  but `race_elapsed` now runs before `attempts` increments. A timeout or pre-Go clock refusal is
  therefore pure; an in-window claim still spends one attempt before movement validation.
- `prototype/osfr-tools/tests/kart_service.rs`: the timeout regression now compares the complete
  service snapshot before and after the refused claim. The old test incorrectly expected
  `attempts` to increase.
- `prototype/osfr-tools/tests/app_fuzz.rs`: added a full `Gateway` regression that starts the
  synthetic kart race, sends an otherwise valid gate claim past the race window, and requires no
  replies, no `state_changed`, no `gameplay_changed`, and complete gateway snapshot equality.
  `state_changed` is the server path's save trigger.

## Reconstructed rules

- (R) The packet path and tick path share one whole-race time window. A claim at or beyond that
  window is refused without changing the persisted race snapshot.
- (R) The bounded gate-attempt counter counts in-window claims. Phase and race-window refusals are
  pure; movement and later semantic refusals retain the existing bounded-attempt behavior.
- Existing (R) rules remain unchanged: one ordered gate claim advances the race, a timeout aborts
  without a reward, and the 20 Hz tick still performs the abort after the window closes.

## Threat note (secure-code-guardian)

A hostile client can send `33/7` gate claims with any claimed position, an arbitrary replay rate,
and a time after `max_race_ms` but before the next 20 Hz tick. Before this fix each such pre-tick
timeout claim incremented the persisted `attempts`; `KartGateway::handle` copied the changed
snapshot, `Gameplay::handle_kart_entry` reported `changed`, and the gateway wrote a character save.
Repeated frames were therefore a save-write amplifier on an unauthenticated input and corrupted the
bounded attempt budget. The fix makes the phase, budget-ceiling and race-window checks pure
preconditions; only in-window attempts spend the bounded flood budget. The owned-guid, finite
position, movement and ordered-gate checks are unchanged, so a hostile position still cannot advance
a gate or pay a reward. A refused claim returns no reply and changes no state.
