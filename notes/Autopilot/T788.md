- `sub_B5FB30` (`00b5fb30`, `DispatchPetActionRecord`): the trick id must be positive, the summoned
  pet must own a trick row with that id (`+0x2c == id`) whose enabled byte (`+0x20`) is set; a row
  whose type dword (`+0x10`) is 2 goes to the toy path, every other row is passed to `sub_CC7420`.
  A refusal returns 0 before any packet.

  sends `sub_B5FF50(a2)` and then `sub_B5FFE0(a2)` with the same trick id.
- `sub_B5FF50` (`00b5ff50`, 53/7 writer, ctor `sub_B50A10` -> `sub_B50670(7)`): one u32 after the
  header, `v5[3] = a2`, the trick id. `sub_B5FFE0` (`00b5ffe0`, 53/8 writer, ctor `sub_B50C20`):
  the same id; it also writes the pet handler state word `+0x12ac = 4`. Neither body carries a
  grade, so the server can only judge "this trick was requested".

  trick id (client writer `00b5ff50`; server decoder `pets.rs` `PetRequest::decode` case 7, already

## Behaviour and invariants

- One accepted 53/7 = one `QuestEvent::PetTrick`; the engine credits only an open `PetTrick`
  step with the same id, one count per accepted request, capped at `required`. A late 53/8 is
  the client's gesture report and never emits the event.
- A refused 53/7 (unknown trick, no summoned pet, a blocked pet, a trick already running) reaches
  no engine: the serialized `GameplayState` stays byte-equal (asserted).
- The busy rule is the existing table: `handle_pets` reads `self.blocks(|gates| gates.pets)`, and
  the new code adds no activity. The blocked test enters a real chess row (`167/1/2`) so the
  shared table closes the pets gate.
- Progress is saved because `append_npc_quest_outcome` sets `out.changed` from the engine outcome;
  a reload between the trick and the turn-in keeps the credit (asserted).
- The turn-in path is unchanged: after the trick the next Talk at the giver opens the held 49/13
  and 49/14 completes the record (asserted, empty reward rows pay 0).

## (R) rules and decisions

- The objective key is the **trick id the client sends**, not a trick name. `pets.json` gives the
  same name several ids (one per species/model family): dog Speak 17, cat Speak 3006 and so on.
  The record's trick is chosen per the objective text: dog quests use the dog rows (11, 12, 16,
  17), cat quests the cat rows (3001, 3003, 3004). This is reconstructed content mapping, marked

- 3120017's offer text says both cats and dogs can do Handstand; only the dog id (14) is authored.
- 3120011's middle how-to step (locale 90554) names no server-side event and is dropped; the trick
  step and the settled Talk to Vidor are authored.
- 3120019 (Handstand at maximum skill) is a pet-state goal, out of scope, untouched.
- Count 1 comes from the singular "the trick" in each objective text, not a chosen number.

## Threat note (secure-code-guardian)

What a hostile client can send: a 53/7 body is one attacker-chosen u32 trick id (and a 53/8 with
the same id), for the summoned pet only. Refusals and why:

- Unknown/forged trick id: `PetService::try_trick` needs the trick row in the summoned pet's model
  and the pet to know it; otherwise `accepted_trick` is `None` and no event is emitted.
- No pet / another player's pet: the request names no pet at all; the service uses the session's
  roster and the authenticated `character.guid` (the actor GUID is derived, never read from the
  packet). Another player's session cannot reach this engine.
- Blocked pet (minigame/activity) or a trick already running: `handle_pets` passes the shared
  `gates.pets` busy flag and `try_trick` refuses both; no event, no save.
- A 53/8 can only end a running trick early (T489); it carries no grade and never emits the quest
  event, so a client cannot fabricate the outcome. The objective means "the server accepted the
  perform", never "the client graded it well".
- No reward is paid by this feature. The turn-in pays the quest record through the existing
  transactional rewards path; this diff adds no coins, items or grants. Counts are clamped to
  `required` by the engine, and the event id is compared exactly (u32).
- No new packet bytes, no client-reported quantity, no persisted client field.

## Checklist

1. **Refusal changes nothing** - every refusal test snapshots `saved(&game)` and asserts equality
   (`unknown_trick_credits_nothing`, `blocked_pet_credits_nothing`; also the running-trick refusal
   and post-completion case). Canaries covered each refusal path.
2. **Rollback covers all state** - the engine changes only `QuestState.counts/status`, which is
   inside `GameplayState`; the gateway stages a clone and the pet session adds no side table that a
   refused 53/7 can escape (a refusal updates only the session's `TrickState`, which starts at
   `Idle`). No `Rc`/`RefCell`/`Arc` state added.
3. **Apply deltas, never restore snapshots** - no payout code; the engine increment is
   `saturating_add(...).min(required)` and the reward path is untouched.
4. **Busy rules are mutual** - no new activity; the trick uses the existing `gates.pets` and
   `interacting()` rules, proven against a real chess activity in `blocked_pet_credits_nothing`.
5. **Every entry path is gated** - the only path that emits `QuestEvent::PetTrick` is
   `handle_pets` from `accepted_trick`; no NPC/automatic/reconnect path emits it, and the engine
   accepts only open steps.
6. **Reachable in production, tested through it** - tests drive `Gameplay::handle_in_world` (53/7,
   26/8, 26/10, 26/6, 49/2, 49/14) and `Gameplay::pet_tick`, not internals.

8. **Every exit path restores the player** - this diff adds no exit path; the trick session's

9. **Economy safety** - the event pays nothing; rewards come from the quest turn-in through the

10. **Wire format matches the client reader** - no packet bytes changed; 53/7 is T489's one-u32
