## Security threat note (secure-code-guardian)

- A hostile client can only trigger repeated load/readiness transitions of its
  own session. The view path reads the instance from server membership and the
  actor set from server field state; it accepts no client instance id, GUID,
  removal target or position. The worst case is bounded 35/3 messages for
  actors that session already knew, and an empty view until it is ready again.
- A full reliable queue is now a per-recipient logged refusal, so a client that
  stops acknowledging can no longer freeze the shared field or other players'
  deliveries. It also cannot make the server drop another player's actor: the
  skip leaves the refused viewer's known set intact for a later retry.
- No save, inventory, coin, reward, role, chat or persisted state is touched;
  the test helpers are `#[cfg(test)]` and absent from the shipped binary.

## Checklist

1. **A refusal changes nothing.** A full queue on one viewer leaves its
   `known_npcs`, view cache, membership, field and saves untouched; the new
   unit test asserts the snapshot equality and the retry. No NPC menu, offer,
   attempt or item is involved in this view path.
2. **Rollback covers all state.** The view path has no staged transaction: it
   only queues packets and then updates the session's view cache; a refusal
   skips the update. `hidden_view` is a pure function of the known set.
3. **Apply deltas, never restore old snapshots.** The change queues removals
   and additions from the current field/session state; nothing captured earlier
   is written back over live inventory, coins or position.
4. **Busy rules are mutual.** No new activity; this only reconciles an existing
   shared-field view on readiness/load loss, so the occupation table is
   unchanged.
5. **Every entry path is gated.** The reconciliation runs only inside
   `Server::tick_shared_instance` for the session's server-assigned instance;
   the predicate `field_recipient_matches` is the same one used for field
   delivery, and no client request can name an instance or actor.
6. **Reachable in production, tested through it.** The unit regression drives
   `Server::tick_shared_fields` (the exact 20 Hz entry `Server::step` calls)
   and then `Server::step`; the socket regression drives the live gateway.
7. **Survives reconnect.** No new persisted state; the view cache is
   reconstructed from membership/field state on the next tick after a
   reconnect, and the readiness-only socket cycle re-adds the actor
   automatically once the session's own commit restores readiness.
8. **Every exit path restores the player.** Readiness returning re-adds current
   actors; disconnect/transfer paths keep their existing membership handling.
   The world-load-loss-only case still needs a client reload, as before.
9. **Economy safety.** No coins, items, rewards or client quantities involved;
   test helpers are `#[cfg(test)]`.
10. **Wire format matches the client reader exactly.** Reuses the existing
    31-byte 35/3 writer and the exact-byte assertion in the socket regression;
    no new fields. Reader provenance is in `## Client evidence`.
11. **Unique ids.** No ids allocated; the removal repeats the known actor GUID
    only.
12. **Others see changes.** The change only removes the affected viewer's own
    stale actors; the other viewer's reconciliation is asserted unchanged.
13. **Content works end to end.** No content or reward change; the socket test
    asserts the resulting AddNpc and HP 300 after restoration.
14. **Values live in data.** No new timeout/window/cap or compiled tuning value;
    the view policy is structural.
15. **Canaries break production code.** Both canaries above changed production
    code (queue containment, readiness predicate), not the test.
16. **Hands off session plumbing.** No change to session creation, teardown,
    transactions or save ordering; only the tick's view/delivery containment
    changed.
17. **One player's error never stops the server.** The regression injects a
    full reliable queue for one viewer during the same-instance readiness-loss
    window: the field is not added to `faulted_fields`, the other viewer is
    reconciled and its removal is queued, both sessions remain, and the next
    shared tick and a following `Server::step` succeed. The canary restoring
    `?` reproduces `field_faulted` and the test failure.
18. **A type's rules live on the type.** The invalid-view rule is now a method
    on `NpcVisibility` next to `shared_view`; the per-session view-cache fields
    keep their existing single update site after successful delivery.
19. **Hot paths stay cheap.** Nothing extra is cloned per tick: `hidden_view`
    allocates one removal per known actor (bounded by the 64-actor view cap) and
    only when the viewer is invalid; the normal tick still reuses the cached
    revision/position/fields and returns early. A clogged viewer adds one log
    line per tick until its queue drains, not a state clone.
