## What changed

- **Blocker 1 (locked-profile legacy turn-in).** `QuestEngine::finish_turnin`
  (`src/quest_engine.rs:1949`) pre-checks the quest reward's `job_xp` against the live
  profile snapshot and returns a clean, grant-free refusal when a non-zero reward names
  a locked profile: it clears `pending_turnin` (and its actor), leaves the quest
  `Active`, sends no reward/complete packet, and reports `changed: true` so the released
  handshake is saved. The old path propagated `apply_grant`'s
  `Err("reward XP references a locked profile")` out of `handle_npc_packet`, leaving
  `pending_turnin` set across the error and blocking both retry-after-unlock and
  `abandon`. The unlock rule is **not** duplicated: the new
  `rewards::locked_job_profile` (`src/rewards.rs:81`) is the single predicate, used by
  `rewards::apply_grant` (which still refuses independently) and by this pre-check.
  I deliberately did not add a bind/load quest migration: the review allowed either, and
  the grant-time refusal is the only place with the authoritative unlocked set (the
  split loader builds the engine before profile content is bound, and the
  `profiles = None` path has a synthetic snapshot). A pre-T202 save can now turn in after
  the job is unlocked, or abandon the quest, instead of wedging.
- **Blocker 2 (fourth copy of the test harness).** See the port note. T202 now reuses
  `npc_quest_chain.rs`; `tests/common/content_copy.rs::copy_tree` is the single copy
  helper. ~340 lines of duplicated harness are gone from the T202 file.
- **Blocker 3 (removed 49/13 assertion).**
  `src/gameplay/w64_regional_quest_tests.rs:1217` again asserts
  `end_screens[0].len() == 99` and asserts the stars dword at `31..35` is 20 for quest
  3000021. The T202 wrapper `release_end_screen` now asserts the 99-byte reader length,
  the configured `end_text_string_id`, and the stars dword for every T202 turn-in.
  `reward_bundle_displays_each_configured_job_xp_total` is the byte-level test: it builds
  all 12 configured quest end screens from the real content and checks quest id at
  `14..18`, coins at `27..31` and stars at `31..35`. The T202 report's claim that existing
  tests were "not weakened" (`notes/Autopilot/T202.md:59-60`) was wrong for this
  assertion; this note corrects it. `T202.md` is otherwise untouched (notes ownership).
- **Minor 4 (refusal proof + positive path).** Every job-refusal check uses the shared
  `assert_no_offer`, which re-sends the same 26/10 menu choice and requires a second
  26/3, proving the refusal does not consume the open 26/9 menu, and asserts the save
  bytes are unchanged. `chef_trainer_unlock_opens_the_job_gate_and_pays` opens the Chef
  gate through production: it learns Chef from the `job_trainers.json` row (label
  413021), proves unlocked-but-inactive is still refused, switches with 26/13, then
  offers/accepts/completes/turns in quest 3050011.
- **Minor 5 (duplicate job_xp rule + strict audit).** `content::job_xp_profile_unknown`
  is the single profile-key predicate used by `content::validate_reward` (content-DB
  loader) and `quest_engine::definition_from_content` (both split and content-DB
  loaders). `scripts/content_check.py` now audits every quest reward's `job_xp`: keys
  must be positive `jobs.json` profile ids, amounts must be non-negative i32, and the
  merged per-grant total must fit the reward bundle's i32 field.

## Security threat note (secure-code-guardian)

- **Surface:** a hostile client can send 49/14 (and 49/2, 26/8, 26/10, 26/6) at any
  time. No new parser, selector, packet family, opcode or client-supplied quantity is
  added.
- **Why forged turn-ins are refused:** `finish_turnin` requires
  `pending_turnin == quest_id`; that field is set only by a server-observed Talk event,
  and the reward is granted under the existing per-character
  `quest:<character>:<quest>` key. A forged or replayed 49/14 changes no coin, item or
  XP state (asserted with save-byte equality in `refused_turn_in_changes_nothing` and the
  replayed packets in `locked_profile_turnin_is_refused_cleanly`).
- **Why the fix improves availability:** the old error path let a pre-T202 save (an
  active Chef/Kart/Ninja quest whose job was not unlocked) raise `Err` out of the request
  handler on every turn-in attempt and leave the pending handshake stuck. The new check is
  fail-closed (no grant, no completion), bounded, and trusts no client id or amount; it
  does not `unwrap` client data. The intended state change is only the server-owned
  pending handshake, which the review requested be cleared.
- **Content trust:** `job_xp` values are server-authored JSON. Both loaders and the
  strict audit reject unknown/negative profile ids and an over-budget i32 total, so a bad
  authoring value fails at bind (or in CI) instead of becoming a runtime error for one
  player. `apply_grant` still independently refuses a locked profile.
- No secrets, logging of player text/names, or token/identity handling is touched.
