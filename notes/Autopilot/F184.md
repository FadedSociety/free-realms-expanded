## Security threat note (secure-code-guardian)

A hostile client controls the chat family/subtype, channel, claimed sender and target
identities, claimed names, message text, claimed position and area/guild ids. The decoders
validate lengths and ignore the wire identity (sender GUID/name) in favour of the
authenticated session. This change derives every chat fact from server-owned state:

- name/`is_member` come from `ChatMember`, written only by `join_player` from the
  authenticated session, never from the packet;
- zone/position come from the registry row that accepted a validated pose; a forged
  position or an unauthorized `realm goto` does not touch it;
- group comes from `SocialService`, so a client cannot claim a group id;
- a left session has no `joined` entry, no chat row and no registry row, so
  `chat_session` returns `None` the moment `leave_player` runs.

The restored `joined` predicates are the same server-owned membership set as pre-D003;
`ride_fanout` now refuses a session that is not in it, and the five transaction conditions
use it instead of a second map. No item, coin, reward or client-reported outcome is
involved. Refusals (`resolve_*` errors, budget, spam gate, muted channel) still happen
before any record or delivery and change nothing; the existing t020 and w173 refusal tests
assert that and passed. No new `unwrap` on client data and no new `?` in the shared tick
were added.
