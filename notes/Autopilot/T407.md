# T407: Postman is learnable, and every job an enabled quest pays has a learn path

## What changed

Content plus tests. No production Rust changed.

| File | Change |
|---|---|
| `prototype/osfr-tools/data/content/job_trainers.json` | Postman row: `npc` 9000000091 (Flitter, Sanctuary), `profile` 4, `job` "Postman", `label_string_id` 412445 ("Become a Postman"), no `requires`, source with client ids, guide lines and the (R) policy. Appended; LF kept; no other row touched |
| `prototype/osfr-tools/tests/common/job_playtest.rs` | `install_starter_outfits` also seeds the play package's Postman list `[13137, 12827, 13197, 13317, 12957]` when the pinned reference has none (the T201/T202 pattern for Ninja/Wizard/Warrior) |
| `prototype/osfr-tools/tests/postman_trainer.rs` (new) | two tests, below |

Why: the only enabled Postman quest, 3130032 "Postman: Trail of Mail", pays 5 coins and 5 profile-4 XP.
No trainer row taught profile 4 and the opening save unlocks only `[1, 43]`, so `rewards::locked_job_profile`
refused every turn-in (the pre-existing `postman_trail_of_mail.rs` only passed by seeding the unlock).
An audit of every enabled quest (`QuestEngine::is_enabled`) against default + trainer-reachable profiles
found profile 4 the only gap (all other paid/gated profiles 1, 2, 11, 12, 14, 16, 32, 35, 43, 45, 48, 137
were covered).

## Trainer choice: Flitter, not Postmaster Vixie (deviation from the brief)

The brief named Postmaster Vixie (9000000174, Merry Vale). The evidence points elsewhere:

- Client locale (`lab/reports/locale-id-to-text.json`): 412445 "Become a Postman" (menu label, the same
  family as 412471 "Become a Warrior"). Its companion lines name **Felipe in Sanctuary**: 412446, 442230,
  384165, 384171. Three lines name **Flitter in Sanctuary** as the teacher: 46247 "Flitter can teach you how
  to become a postman.", 46248, 73595. Flitter's own greeting 24842 opens "If you'd like to work as a
  Postman...". No client line names Vixie as the job's teacher.
- Guide `notes/Build Guides/Content/Jobs/Postman.md`: line 24 (How to unlock: Felipe; alternates Flitter,
  Loryn), lines 33-35 (Trainers: Felipe unlocks the job; Flitter runs the Post Office; Vixie is the Merry
  Vale band trainer for levels 5 to 10), line 262 (Conflicts 2: wiki Felipe; client Felipe and Flitter).
- Content: Felipe (9000000086) and Loryn (9000000132) are `poi_anchor` (not drawn). Flitter (9000000091,
  `sanctuary.json`) is `legacy_data`, model 411 `fairy_f_courier_flitter_01.agr`, roles
  `quest_giver`/`trainer`, greeting 24842, so she passes the existing `is_drawn` rule with no new spawn.

So Flitter is the drawn NPC closest to the recovered unlock (same town and Post Office as Felipe, and named
by the client as a Postman teacher). This mirrors the Miner row (Therin is a `poi_anchor`, so a drawn Miner
trainer teaches). (R) Caveat kept in the guide: "NOT LIVE - Finding Flitter" marks the Flitter intro as an
older design; Felipe remains the live unlocker once he is drawn. Swapping the trainer (to Vixie, or to a
future drawn Felipe) is one `npc` value in `job_trainers.json` plus the `TRAINER` constant in the test.

## Tests (`tests/postman_trainer.rs`)

- `a_new_player_learns_postman_at_flitter_and_is_paid_for_trail_of_mail`: fresh opening save (Postman
  locked). Refusals first, each byte-equal on the save: far 26/8, 26/10 with no menu, an unoffered 26/10,
  a truncated 26/10. The still-open menu's 412445 choice then learns Postman (chat line, unlocked, active
  job unchanged, Chest 12827 and Legs 13197 owned once). 26/13 activates Postman (38/21 sent), 26/13 back to
  Adventurer. Then the real quest chain at Postmaster Lane / Postchug Runalug: 49/1 offer, 49/2 accept,
  Talk, 26/6 releases 49/13 (reward words 5/5), 49/14 pays exactly +5 coins and +5 profile-4 XP while
  Adventurer is active, no item granted; a replayed 49/14 changes nothing. Serialized relog keeps the save
  byte-equal; a second lesson at Flitter says "already know" and changes nothing (no duplicate outfit).
- `every_job_paid_or_gated_by_an_enabled_quest_has_a_learn_path`: from the shipped `quests/*.json`, with
  the server's own `QuestEngine::is_enabled`, collects each enabled quest's `job` and every `job_xp` key;
  a profile is learnable when the opening save unlocks it or a trainer row teaches it after a learnable
  prerequisite (fixed point over `requires`). Fails with `(profile, quest)` pairs; asserts it saw
  (4, 3130032) so it cannot pass vacuously.

Not duplicated (already row-generic and now running the Postman row too): `job_trainers.rs`
`trainer_rows_match_the_job_and_spawned_npc_content` (drawn, trainer role, job name),
`malformed_trainer_files_are_refused_at_load` (label 0, profile 9999, duplicates),
`each_listed_trainer_offers_the_job_and_unlocks_it_once`,
`an_ordinary_player_learns_each_trainers_job_once_and_only_switches_to_a_complete_outfit` (gateway frame
path, replay refusal), `gateway_refusals_leave_the_save_untouched` (busy via a live Mining run, far,
unoffered), and the two-session case inside `all_six_combat_jobs_learn_activate_fight_and_gain_xp`
(one character's unlock never unlocks another).

## Threat note (secure-code-guardian)

A hostile client can send 26/8 from far away, 26/10 without a menu, with an unoffered or truncated choice,
replay the learn, or replay 49/14. All are existing server refusals (range check, offered-option proof,
`LearnDenied::AlreadyKnown`, completed-quest ledger) and the test asserts the serialized save is unchanged
for each. The row grants only the job and the content starter outfit (reused when owned, so a second lesson
cannot farm pieces; starter pieces already sell for 0 per F228). The quest reward comes from server content
at 49/14, never from client values.

   far 26/8, 26/10 without a menu, an unoffered 26/10, a truncated 26/10, a replayed 49/14 and a second lesson
   after relog; each is byte-equal and the menu stays usable for the real choice. Busy is the existing
   row-independent gate, pinned by `job_trainers::gateway_refusals_leave_the_save_untouched`.
2. **Rollback covers all state.** Unchanged: `learn_job` runs inside `commit_if_changed` on a staged clone;
   the reward uses the `apply_grant` clone. No new state.
3. **Deltas, not snapshots.** `finish_quest` asserts coins and profile-4 XP as live value + 5 at 49/14, after a
   learn, two job switches and an outfit grant changed the save in between.
4. **Busy rules are mutual.** No new activity; the occupation table is untouched.
5. **Every entry path is gated.** The only unlock path is the real 26/8 -> 26/9 -> 26/10 trainer menu
   (range, offered-option proof, busy, already-known). No dev command, chat packet or parallel grant; the
   test sends none.
6. **Reachable in production, tested through it.** Every packet goes through `Gameplay::handle_in_world`;
   the gateway frame path for this row is also run by `job_trainers` (every listed trainer).
7. **Survives reconnect.** Serialized relog after the paid turn-in keeps the save byte-equal (job unlocked,
   outfit, wallet, XP, completed quest); the second lesson after relog grants nothing.
8. **Every exit path restores the player.** N/A: no activity; learning leaves the active job unchanged.
9. **Economy safety.** Exactly +5 coins/+5 XP once; the replay pays nothing; the quest grants no item

10. **Wire format.** No new or changed packet. Readers cited in the test header; re-checked in IDA this run:

11. **Unique ids.** N/A: no ids created.
12. **Others see changes.** No visibility code changed: learning switches no job and the 26/13 switch is the
    existing `stage_job_selection` path; this slice adds nothing another player sees.
13. **Content works end to end.** The chapter test asserts the final unlock, the 38/21 activation, the paid
