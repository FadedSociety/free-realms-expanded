# T856 - Leaving the card game crashed the client (0xC00000FD): the launch flag `+616` forced the dialogless 39/19 path

Native 2026-10-27 (the owner) and 2026-10-28 (`../lab/runs/client-baseline-20261028T030110Z`, manifest
`client_exit_code` 3221225725 = `0xC00000FD`): the card window's door -> "Exit TCG? Yes" killed the client. The run below is
the successful-login/lobby run (the card listener had logged in and sent the starter collection), so the crash is not a
login-state artefact.

## What the client does on exit (all addresses `FreeRealms.exe`)

The client's exit is native, not a Lua quit:

1. The door button runs the DLL's `WALoginScreen::on_exitButton_clicked` (qt_metacall `10516830`) -> `QWidget::close` of
   the card main window (`1037b000`).
2. The type-16 manager (PlayClient+0x104, vtable `0181a444`) notices the window count reach 0 in its update
   `00ad4f50` state 4: `010d1690` (RunFrame + window sync), `010d0c60` (count), then vtable slot 22 `00ad3e40`.
3. `00ad3e40` calls the DLL's `Shutdown` export (`1021e240`), `FreeLibrary` (`00fc53b0`), the host destructor
   `010d27a0`, restores the minigame sound (`00ad4e80`) and only then sends the leave:
   `009be8e0` -> `009bdc60(6, -1, -1)` (39/6, current instance).
4. The server answers 39/6 with 39/19; `009bf190` is the client's handler for it.

The run's last client packet is the 39/6 at trace ts 557077 (`27 00 06 41 c9 a2 03 ff ff ff ff ff ff ff ff`, instance
61,000,001). The server's 39/19 (`27 00 13 41 c9 a2 03 ff ff ff ff f3 01 00 00`) went out at 557080/557103 and was
retransmitted at 557362 (seq 3403/3406), never acked; `manifest.json` has no client-to-server frame after the 39/6
(`frames/005233.bin`, 557.766 on the frame clock). The client exited at 558.234. `client/Logs/FreeRealms.log` has no
`MiniGame:LeaveMiniGame` line after the 21:05:40 TCG start; the logger normally writes that line first in `009bf190`
(`009bf190+0x29`). The handler still ran or was about to: stdio buffering can lose the last line, and the stalled main
thread is what the timeline shows.

## Root cause: info flag `+616` = 0 selects the Lua no-end-game quit

`009bdd70` reads the five info flags into run bytes `+612..+616`; `00c42c60` copies `+616` to run byte `+2312`.
`009bf190` branches on `+2312`:

- `+2312` = 1 -> `009b7170` (`ShowMiniGameEndDialog`) -> Lua `:show` + `:setMiniGameEndData`; for type 16 that is
  `ScoreScreen:Show(status, 16)` (`ScriptsBase.lua` ~36571-36700), the ordinary end screen.
- `+2312` = 0 -> Lua `:QuitGameWithNoEndGameScreen` (string `0180f4c0`, invoked at `009bf190+0x20d`). That Lua path
  (`MiniGameHandler:QuitGameWithNoEndGameScreen` -> `QuitGame` -> `Ui.QuitMiniGame`) enters the native quit
  (`Ui.QuitMiniGame` binding `0182d1f8` -> thunk `00c17470` -> `00939100`), which for a started run calls `009ad420` to
  change/remove the current minigame state while `009bf190` still holds that state on its stack. The re-entrant teardown
  is what exhausts the stack (0.4 s of no client traffic, then `STATUS_STACK_OVERFLOW`). (R) which exact object
  `009ad420` frees, and the precise frame that overflows; the native stack capture is the remaining proof.

T782/T795 chose `+616` = 0 so the card window's result would not open an empty 39/18-style dialog. That was (R), and the
client's native behaviour says it is wrong: the retail server sends the generic flag value 1 for every run. T795 left the
revert clause for exactly this native signal ("If a native run shows the card window closing badly with 0, the revert is
`spec.flags[4] = 0`").

## What changed

- `src/card_game.rs` (`Launches::begin`): removed `spec.flags[4] = 0`; a card offer now keeps `RunSpec::empty`'s
  `[1, 1, 1, 1, 1]`. Doc explains the 39/19 consequence and cites the addresses.
- `src/minigame.rs` (`RunSpec::validate`): removed the `CardClient` exception; `+616` must be 1 for every mode. The
  exception was the only way a caller could re-create the crash.
- `tests/card_launch.rs`: the end-to-end handshake asserts the 39/16 flags are `[1, 1, 1, 1, 1]` (was `[1, 1, 1, 1, 0]`).
- `tests/minigame.rs`: renamed `only_a_card_run_may_skip_the_end_dialog_and_it_starts_after_its_ticket` to
  `every_run_keeps_the_end_dialog_and_a_card_run_starts_after_its_ticket`; a card spec with `+616` = 0 is now refused,
  and the ledger snapshot is compared before/after the refusal. The ticket/start half is unchanged.

No hub file changed (`gameplay.rs`, `bin/osfr-gateway.rs`, `encounter.rs`, `gateway.rs`: net 0 lines). No content row
changed: the flag is a wire value, not a tuning value.

## Threat note (secure-code-guardian)

A hostile client can send private 39/5, 39/6, 39/7, 39/37 and malformed 39/x headers. None of them can set the 39/16
flags: the server writes `RunSpec::flags` from its own default, and only `Launches::begin` creates a card spec. The
validator now refuses a spec whose `+616` is 0 before `offer` takes the instance id (the test snapshots the ledger to
prove a refusal changes nothing). The exit packet path is unchanged: only the session's own instance is owned, a repeat
39/6 sends nothing, and nothing reads a save, item or coin. The card listener is untouched.
