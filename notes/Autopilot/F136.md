## Security threat note

A hostile client can replay `41/108`, send arbitrary activity or battle ids to
portal Play, spam ordinary attacks, or replay results Close. Go starts only the
pending battle already opened by the server; Play checks the published catalogue
and admission rules; combat targets are resolved against live encounter enemies;
and a won fight cannot pay again. Prize ids and quantities never come from the
client. They come from operator content and are now checked against catalogue
membership before entry. The missing-prize refusal runs after Go takes the
pending screen (that call validates the marker distance) and restores the same
screen through `reopen_battle_screen`; the repeated-Go assertion proves the
pending battle is still usable. It happens before zoning, before instance
allocation, and before any inventory grant. `realm battle` and simulator remain
role/dev gated. Refusal tests compare the complete gateway snapshot before and
after each hostile request.

## Checklist

1. **A refusal changes nothing.** The invalid-prize test sends portal Play,
   `realm battle`, simulator and client Go, then compares complete gateway
   snapshots. Go also reopens `41/114`, proving the start screen was not consumed.
   The production canary enters the fight when the check is removed.
2. **Rollback covers all state.** The refusal happens before instance allocation
   or encounter mutation. Gameplay requests are already staged on a clone; this
   change adds no shared state or side table. Snapshot equality is asserted.
3. **Apply deltas, never restore old snapshots.** Victory assertions compare
   coin, prize-count and job-XP deltas. Mid-battle reconnect leaves all economy
   values unchanged and returns only the character location.
4. **Busy rules are mutual.** No new activity was added. Field battles still use
   the existing warp/activity admission and encounter-active gates. Existing
   `activity_portal_route` and shared-field tests pass.
5. **Every entry path is gated.** All four production `EncounterEngine::begin`
   callers for field battles call the shared prize preflight. The opening cave
   has no field-battle row and is intentionally unaffected. Client Go, portal,
   developer battle and simulator are all exercised.
6. **Reachable in production, tested through it.** Both designated battles are
   started and won through Gateway with `26/8`, `41/108`, zone-ready messages,
   `36/10`, and `26/42`. No internal `begin()` or `attack()` shortcut remains in
   the full-route tests. No new `application_handler` selector was added.
7. **Survives reconnect.** The Petty Yetis test saves and reopens mid-battle:
   the character returns to the marker in zone 0, the battle is released and the
   economy is unchanged. Both routes save/reopen after payout and retain the
   prize, coins and XP.
8. **Every exit path restores the player.** Mid-battle reconnect and results
   Close both return to the original marker in zone 0. Duplicate Close is a
   snapshot-preserving no-op. Existing encounter loss/retry tests remain green.
9. **Economy safety.** Rewards derive only from a server-owned won encounter.
   The gateway test observes exactly one allowed prize, the configured coins and
   50 Brawler XP. Post-win attack and duplicate Close add nothing. A missing
   catalogue prize cannot start from any production entry path.
10. **Wire format matches the client reader.** Addresses are cited above and in
    the test. The `41/114` test compares the exact serialized title/icon/
    description/difficulty/type fields at offsets 47..71.
11. **Unique ids.** This task adds no ids. The existing roster test checks every
    spawner and enemy GUID is positive and unique; marker-collision reload is
    rejected atomically.
12. **Others see changes.** No outfit, job, mount, actor-spawn or other visible
    state was added or changed by this task. Existing spawner publication is
    unchanged.
13. **Content works end to end.** Both battles spawn three server-authored
    enemies, send the objective, complete through server attacks, grant a
    non-empty prize plus coins/XP, return the player, and survive reconnect.
14. **Values live in data.** No timeout, cap, payout or tuning constant was
    added. Prize eligibility is derived from the content prize rows and loaded
    item catalogue.
15. **Canaries break production code.** The canary changed the production
    preflight to always accept; it did not fabricate a failure in the test. The
    gateway test then entered the invalid battle and failed. The change was
    reverted.
16. **Hands off session plumbing.** No session creation, teardown, transaction,
    save ordering or gateway-binary file was changed by F136. F163 briefly added
    a `#[cfg(test)]` tick-error hook in `src/bin/osfr-gateway.rs`; F190 removed
    it (review blocker: lead-only session file), so the binary has no change
    from this work. Creation, teardown, transactions and save ordering are
    untouched.

17. **One player's error never stops the server.** [Added by F163; corrected by
    F190.] The F136 preflight is read-only: it queries the loaded item catalogue
    and returns before the encounter, inventory or saved state changes. Go takes
    the open start screen first (the call validates the marker distance); a
    refusal restores that same screen. A field-battle
    reward is produced only by server-owned HP reaching zero and is applied by
    `Gameplay::apply_encounter` in that session's handler. `Inventory::grant_bundle`
    stages a clone and commits only on success; coins and quantities are checked.
    A reward failure is an `io::Result::Err` from `Session::handle`/`Session::tick`.
    A single application message is traced and dropped by `Gateway::handle_at`
    with its staged state discarded; a bundled message returns the error to
    `Server::step`'s per-session loop, where `contain` ends only that session
    (`Server::end_session`) while the other sessions keep running. Neither path
    escapes `Server::step`.
    F163 added, and F190 replaced, the tick-isolation regression:
    `a_failing_tick_save_ends_alone_and_the_server_keeps_running` in
    `src/bin/osfr_gateway/isolation.rs` fails a real production tick save (an
    unwritable deferred-pose path) with no test-only hook; the test asserts that
    session is gone with no world ghost, the other two remain, and the next
    `step` is `Ok`. It also added
    `a_reward_grant_failure_is_refused_without_changing_the_save`: the real
    `realm battle 411`/`realm win` route is driven with an invalid cave reward,
    the bundled request returns `unknown reward definition`, and the complete
    gateway snapshot is unchanged (no coins, items, XP or position move).
    The audit found one unpayable content form: a prize quantity above the item's
    `max_stack` passed the old definition-only gate and failed at payout. F163
    added `Inventory::accepts_reward`; the owner preflight now rejects it before
    entry. The regression
    `an_ungrantable_prize_quantity_is_refused_through_gameplay` drives the real
    `realm battle` and `41/108` paths and asserts the gateway snapshot is unchanged.
    No reward arithmetic or shared-tick code changed.
    Residual gap (F190 minor 4): the preflight does not model `MAX_ITEMS` or the
    coin cap, so those can still fail atomically at payout; see F163's open gaps.
