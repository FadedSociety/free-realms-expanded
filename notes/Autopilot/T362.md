# T362 — Roosey's coin merchant window: 165/10, not the 66/42 Station Cash list

**Outcome.** Roosey's Shop choice now sends the client's coin merchant list, 165/10, with her six
coin-priced rows and no timer. In the lead's native run the 66/42 list opened the **Station Cash**
presentation with an empty list. IDA shows why: 66/42 opens `NpcMerchantV2` in `"StationCash"` mode,
and its first dword is the *time left*. 165/10 opens the coin store
(`HandlerMerchant:Show("CoinStore")`). The brief's premise ("fill the 66/42 rows") was the wrong
message. Its own step 1 asks what selects the SC presentation versus a coin shop, and the answer is
the message family, so this change replaces the message rather than reporting blocked.

History: attempt 1 found 165/10. Attempt 3 fixed two wire-field mistakes. The first Opus run
removed the 165/4 replay cache (the native request has no per-request id, see below) and ported
`l011_vendor_save_failure.rs`. The second Opus run ported it to tip `9fd86278` and added the
reader-derived price pin. Its patch (`patches/T362-opus.patch`) then failed integration with
`__LOST__ tests/coin_shop.rs::buy_debits_exact_cost_and_retry_is_idempotent`, because it had renamed
that test. The same integration log's only red test, `shared_world_membership`
`chat_scope_derives_zone_and_position_from_the_live_registry`, was a `Timeout` in `Server::new`
start-up under load (`shared_world_membership.rs:126`). It does not touch the shop.

This run (Opus, third) applied that patch to tip `598531a` with `--reject`. One source hunk was

### Item definition price wire offset (`008e3760`, `008caaa0`)

`008e3760` reads, in wire order: dword 0 → +4 (id), dword 1 → +8, dword 2 → +12. `008caaa0` on
`this+16` reads dwords 3/4 → +20/+24. Then dword 5 → +28, dword 6 → +32, **dword 7 → +36 (0x24,
the price column 27 reads)**, +40, +44, +48, and flag bytes +52/+53 (NoSale +0x35). The serialized
price is therefore bytes **28..32** (`inventory.rs::DEFINITION_COIN_PRICE`).

### 165/4 buy (`00c77db0` → `00c77230` → `00c75ed0`)

`00c77db0` passes `00cf10d0` (the record scalar) and `00cf16c0` (the merchant GUID) plus the Lua
item id, tint and quantity to `00c77230`. `00c77230` refuses when the client definition cache lacks
the id ("BuyItem - Failed to find item definition id"). That is one more reason the shop pushes
uncaptured definitions. It zeroes the tint unless definition +0x9c is set. The body is header,
merchant u64, context, definition, tint, quantity (offset 24), and **nothing in it is unique per
request**.

The 165/6 reply does not change the context either. `00c78220` (dispatcher `00c791d0` case 6)
unserializes the completion, raises `NpcMerchantV2:OnBuy`/`OnSell` and `MerchantPurchased`, and on
success refreshes a list through `00cf1780` → `00cf16e0`. That path writes only its own list object,
never the merchant record at `+744` that `00cf10d0` reads. Only a new 165/10 (`00b33020`) rewrites
`+756`, and `NpcMerchantV2:Show` returns early while the window is visible. So a server-side cache
cannot tell a retry from a second buy, and every buy in one open window carries the same context.

## Security note (secure-code-guardian)

A hostile client can send 165/4 with any merchant, context, definition, tint and quantity, with no
shop open, from another zone, or repeatedly. It can also send 165/5/165/12 for items it does not
own. These requests are refused as before (authorization is unchanged by this task):
`check_coin_store` requires an open shop, an in-range NPC, a merchant equal to that NPC's key (or the
null sell form), the exact 28-byte body and an item in that NPC's `vendors.json` stock. `CoinShop`
then checks catalogue, `0 < qty <= i32::MAX`, checked price arithmetic, balance, stack and bag, and
commits only a staged inventory. With the replay cache removed, a repeated 165/4 is another paid
purchase. It costs the server price every time, so it cannot double-grant or bypass payment. 165/10
and the 35/37 push are server-to-client only. The client supplies no price, row or definition, and
the pushed records come from the shipped catalogue with the `stores.json` price written in.
