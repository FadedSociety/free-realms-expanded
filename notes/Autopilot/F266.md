# F266 - Fix review blockers in T008 (opcode-164 jump relay)

Review: `lab/autopilot/reviews/46df903-T008.md`. `46df903` is an ancestor of
this worktree; this diff is the fix on top of the newest `autopilot` tip.

## Findings

1. **BLOCKER 1 - a 164 followed by a 125 lost the jump - fixed.**
   The relay body is no longer built when the 164 is accepted. `handle_at` keeps
   the last accepted impulse in a per-request local and, after every child, builds
   the 40-byte body from the final committed `movement_state` and `state.guid`.
   A later 125 therefore cannot clear it, and the relay carries the final pose.
   Regression: `jump_relay_reaches_only_directed_viewers_and_is_throttled` (name
   kept for `protected-pass.txt`) sends a real `[0,25]` bundle
   `[164 P3 v3, 125 P4]` through `dispatch_message` and asserts exactly one 164
   at P4 with velocity 3.0. The old loss-pinning assertion is inverted.
2. **BLOCKER 2 - fanout inside the prepared transaction - fixed by moving it
   out.** The staged-world mutation and delivery list are gone from the
   `commit_outcome` closure. `dispatch_message_inner` takes the staged body before
   the commit and queues the directed deliveries only when `commit_outcome`
   returns `true`, in the existing post-commit hook next to the T199 broadcast.
   A refused transaction (`Ok(false)` or `Err`) queues nothing. No
   `commit_outcome` ordering, save, transfer-refusal branch or session plumbing
   was changed.
3. **BLOCKER 3 - staged `GatewayOutcome.jump` - fixed by removing the outcome
   field.** `GatewayOutcome` is unchanged. The relay body lives on the staged
   `Gateway` (the owner of the validated pose), is set only after the last child,
   and is taken once by the caller. A refused/failed request drops the staged
   clone, so no body can outlive a rolled-back pose.
4. **BLOCKER 4 - new client-triggered relay rate limit - fixed by deletion.**
   `PlayerRegistry::jump_ms`, `allow_jump`, `jump_relay::MIN_INTERVAL_MS` and the
   `leave` cleanup are removed. The relay is bounded by the same directed view and
   per-164 work as the pre-existing opcode-125 pose fanout
   (`PlayerRegistry::update_pose_with_state`), which has no per-session throttle
   either. A hostile 164 flood is no worse than a hostile 125 pose flood; the
   native 50 ms gate in sender `0092e670` is client-side and cannot be a server
   boundary.
5. **MINOR 5 - throttle/window tuning - resolved by deleting the window; the
   velocity cap is tightened.** Finite velocity is clamped to
   `MAX_VERTICAL_SPEED` = 100.0 (10x the 10 u/s 125 base) instead of refused; a
   finite out-of-range value must not disconnect the session. Tests pin both
   clamp directions, the Infinity refusal, the 60 ms second jump, and the
   `MAX + 1` relay reaching the viewer at exactly `MAX`. The no-viewer case is
   vacuous without a window and is still pinned by the directed-visibility
   assertions.
6. **MINOR 6 - native two-client acceptance - open gap.** This environment
   cannot drive two game clients; the lead's native run remains the gate for
   observer animation. No packet field changed.
7. **MINOR 7 - duplicated directed-view predicate - not changed.** The review
   marks it a lead follow-up. The predicates are not identical: `ride_fanout`
   also allows non-outfit packets to a recipient outside the directed view
   (`live_outfit_packet`). Folding it in would touch the lead-owned ride path for
   no behavior change.
8. **MINOR 8 - hub headroom - fixed.** `src/gateway.rs` is 2,238 (ceiling 2,242,
   net +3 from the tip's 2,235); the bin is 4,681 (ceiling 4,697, net +5). The
   previous attempt was 2,243 and failed the ratchet by one line; see below.

## Security threat note (secure-code-guardian)

A hostile client can send: a body naming another actor (refused: the session's
server-bound GUID is the first check); 39/41-byte or wrong-opcode bodies
(refused before staging); NaN/Inf position, direction or velocity, positions over
`MAX_POSITION_COMPONENT`, or a direction with a zero horizontal component (zero
keeps the prior direction - the 125 rule); a finite velocity outside +/-100
(clamped, never refused, so a legitimate large fall cannot disconnect); or a jump
aimed at making observers see motion (the recipient set comes from the server
registry's directed `knows_character` view of the sender's character, and the
sender is excluded; the GUID/pose in the body come from the server, not the
packet). A refusal returns `Err` before the staged Gateway is assigned, so no
pose, menu, offer, counter, item or cooldown changes (the real-dispatch test
snapshots the pose and drains the recipient for every refusal). The removed
throttle is not a new hole: opcode 125 already fans the same viewers per pose
change with no per-session limit, and the 164 uses the same directed view, one
40-byte body per recipient, so a 164 flood costs no more per packet than a 125
flood. The hot path costs one `Option` check for non-164 messages and, for an
accepted 164, one 40-byte body build and one bounded nearby/visibility query
after a successful commit. No secrets, names or chat text are involved.

## Checklist

1. **A refusal changes nothing.** Invalid 164s fail in `parse_message`/`decode`
   before `handle_at` assigns anything. The real-dispatch test snapshots the
   gateway state and drains the recipient for foreign GUID, NaN/Inf position or
   direction, out-of-bounds position, a 39-byte body and a trailing byte, and for
   the pre-Ready jump; each returns `Err`, leaves the pose unchanged, sends no
   164 and stages no body (`take_jump_relay()` is still `None`). Canary 2
   (foreign-GUID check removed) fails the unit refusal test.
2. **Rollback covers all state.** The relay body is a field on the staged
   `Gateway`; the staged clone is assigned only at the end of `handle_at` and
   committed only by `commit_outcome`. The new fanout runs post-commit and
   mutates nothing. No `Rc`/`Arc`/side table was added.
3. **Apply deltas.** The body is built from the final validated/committed pose in
   this request, never from a snapshot; no captured pose is restored.
4. **Busy rules are mutual.** Jump is movement with the same gates as opcode
   125; no `Occupation` row or gate changed.
5. **Every entry path is gated.** The only path is the tunneled client 164; the
   world-entry gate and `movement::validate` are shared with 125. There is no
   NPC/automatic/reconnect entry.
6. **Reachable in production, tested through it.** The binary test drives
   login -> Ready -> Loaded -> `dispatch_message` (including a real `[0,25]`
   bundle) and decodes the recipient's queued SOE replies, including the
   post-commit delivery path.
7. **Survives reconnect.** The relay body and impulse are per-request; nothing is
   saved. `leave` no longer owns jump state (the T008 window is gone), so a
   reconnect starts clean; the protected players test pins the directed view
   cleanup.
8. **Every exit path restores the player.** No activity, location change or
   stuck flag; a clamped jump leaves the character free and the existing position
   rules in force.
9. **Economy safety.** No item, coin, reward, grant or client-reported outcome is
   involved. Only validated pose floats and a clamped velocity.
10. **Wire format matches the reader exactly.** Reader `008e5ba0`, writer
    `009127f0`, constructor `008b3b70` are cited at the code; the unit test
    rebuilds the 40-byte body byte-for-byte; the binary test decodes the queued
    body (opcode/GUID/position/velocity/state/unknown).
11. **Unique ids.** No id allocator; the session-bound character GUID is used and
    a body naming another actor is refused.
12. **Others see changes.** The relay uses the existing directed-visibility rule
    (`nearby_sessions` + `knows_character`) on the real post-commit delivery path;
    the three-session test asserts the directed viewer gets it, a near non-viewer
    and the sender do not, and the recipient decodes it.
13. **Content works end to end.** Protocol feature, no content. The endpoint - an
    observer receives a decodable 164 at the final pose - is asserted, including
    the exact `[164, 125]` bundle scenario from the review.
14. **Values live in data.** The only retained value is the (R) velocity bound;
    there is no movement-policy content table (the 125 speed envelope is likewise
    compiled and documented). The window is removed rather than invented in data;
    flagged as an open gap.
15. **Canaries break production code.** Canary 1 edits the gateway impulse carry
    (the T008 loss); canary 2 edits `jump_relay::decode`'s GUID refusal. Both
    break production code, fail the named regression, and are reverted; results
    above.
16. **Hands off session plumbing.** No session creation, teardown, transaction
    ordering or save ordering changed. The T008 in-transaction fanout and the new
    rate limit are removed; the bin change is the post-commit delivery loop next
    to the T199 broadcast, and the gateway change is staged movement state (the
    same pattern as `movement_state`).
17. **One player's error never stops the server.** Decode/relay return `Err` for
    bad input (that session only); the fixed-size unwraps follow the exact-length
    check; the clamp prevents an overflow-style rejection; the post-commit loop
    returns `Err` only through the existing `queue_delivery` path, like the T199
    broadcast.
18. **A type's rules live on the type.** The `Gateway::jump_relay` field
    documents that it is built from the final pose and taken once after commit;
    `JumpUpdate` fields document untrusted/validated/clamped/opaque;
    `MAX_VERTICAL_SPEED` documents the (R) bound.
19. **Hot paths stay cheap.** Non-164 messages pay one `Option` check in
    `handle_at` and one closure map at the end; accepted 164s allocate one
    40-byte body and (post commit) do one bounded nearby/visibility query. No
    whole-state clone was added; the removed window also removed a map lookup.
