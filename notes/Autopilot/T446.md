# T446 - Collections wire: 38/10 AddEntry field order and the 38/9 Remove body

## What changed

- `src/progression_extras.rs`
  - `CollectionEntryUpdate` now has named fields in client wire order: `definition_id`, `icon_id`,
    `icon_tint_id`, `name_id`, `collection_id`, `index`, `unknown`, `collected`. Each field's doc
    comment gives its body offset and reader offset. `encode` writes them in that order (7 x u32 LE
    and a byte, 33 bytes with the header, same size as before). Before, `collection_id` was the
    first dword, so the client would have used it as the entry id and looked up a collection by
    our `fields[1]`.
  - `CollectionMessage::Remove { body: Vec<u8> }` is now `Remove { collection_id: u32 }` and
    encodes one u32. The "not recovered" comment is gone.
  - `CollectionProgression::collect` also requires `definition_id == outcome.entry_id`. Both id
    checks now widen to `i64`. Before, `u32::try_from(collection_id).unwrap_or(0)` let a negative
    catalogue collection id match a wire collection id of 0. A mismatch is refused as before:
    Err, ledger untouched. A doc comment on `CollectionEvent::wire_update` says it is checked and
    sent only for a newly collected entry, which is unchanged.
- `tests/progression_extras.rs`: the `update()` helper uses the named fields, three new tests
  (see Gates), and the old `Remove { body: vec![0] }` header check moved into
  `remove_body_is_one_collection_id`.
- `notes/Build Guides/Gameplay/Rewards and Collections.md`: the Add entry and Remove bullets and
  the 38/9 and 38/10 table rows, with the addresses below.
- Not changed: 38/8 Start, 38/11 RemoveEntry, titles, claims, achievements, piece_038, piece_074.
  Nothing is routed and there is still no 38/8 sender.

Field names: the login reader and the AddEntry copy fill the same entry offsets. Captured login row
for entry 41 (`lab/references/rust-gateway-reference/0007-login.bin`, sha256 f4b8b4ca..., key at
byte 8941) is key 41, then 41, index 1, collection 10, name 17056, icon 2124, tint 99, 0, collected
1. In login order those land in `e[0]`, `e[6]`, `e[5]`, `e[4]`, IconData, `e[7]`, bool. Mapped back
through `008c3fa0`, AddEntry body order is 41, 2124, 99, 17056, 10, 1, 0, 1. This order also matches
Sanctuary's `ClientUpdatePacketCollectionAddEntry.cs` (read as an order hint only, AGPL, no code
copied). A scan of the capture finds 1,815 chained 33-byte rows across 253 collections, and the
`unknown` dword is 0 in all of them.

## (R) choices

- `unknown` (body +24): meaning not recovered; 0 in every captured row.
- `collected = true` is required on every event update (existing event policy, unchanged).
- Labels by value, offsets client-proven: the IconData pair (`008caaa0`) is icon then tint by
  Sanctuary's order and the captured 2124/99; `name_id` because 17056 resolves as an entry name
  in locale (`notes/Research/Collections Achievements Titles.md:169`); `index` because it runs 1..n
  in all 253 captured collections.

## Threat note

A hostile client cannot reach this code: the server builds `CollectionEntryUpdate` from catalogue
data, and nothing routes 38/9 or 38/10 yet. The check in `collect` guards our own callers: a wire
update naming a different entry or collection, a negative ledger id, or a u32 that would wrap into
a negative i32 is refused before the ledger or reward state changes.

## Open gaps

- A future sender must make sure the client already has the collection (login self-data or 38/8)
  before it sends AddEntry: `009939a0` silently drops an entry for an unknown collection.
  Sanctuary sends 38/9 and 38/8 before its first AddEntry. Whether our login burst carries every
  collection is the job of the routing tasks.
