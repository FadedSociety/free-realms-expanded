## Client evidence
- Ctor `0x008a0fb0` is class `PlayerUpdatePacketRequestStripEffect` (RTTI at `0x018015c0`, vtable `0x018015c4`): `sub_89FBB0(33)` sets family 35 (+4) and sub 33 (+8).
- Sender `0x00934740` builds it on the stack, `v5[3] = id` (+0xC), `v5[6] = 0` (+0x18), sends via `0x00925fe0` only when `this+0x280` is set.
- `0x00925fe0` serializes with `0x00913b80`, which writes exactly one dword, the one at +0xC (`mov eax,[edi+0Ch]`, 4 bytes). So the body is `u16 35, u16 33, i32 id` (8 bytes). The dword at +0x18 is never serialized: the brief's "leaves +0x18 as 0" is true of the object, not the wire.
- IDA correction to the research pack: the Lua binding address in the brief (`0x00c18928`) is `0x00c188f0` in the function table; it does not change the wire.
- Cancel path in the Lua UI: `ScriptsBase.lua:25192` `Ui.RequestStripEffect(tonumber(b))`.

## Threat note
A hostile client can send 35/33 with any id, a wrong length, or spam: any id not in its own stack is ignored (no state, no packets, so it cannot strip another player's effect or a job/power-up tag; the stack is per session). Wrong length returns `Err(InvalidData)` before any mutation, for that session only; nothing is unwrapped. A repeat cancel is the unknown-id case. The apply refusal path (`admits`) leaves the stack untouched.

## Checklist

2. Rollback covers all state: the stack is a plain field of the cloned `Gameplay`; no shared cells.
3. Deltas, not snapshots: the stack mutates in place; no restore over live state. N/A beyond that.
4. Busy rules: not a new activity; cancel is routed before every activity (spec: activities do not block a cancel).
5. Every entry path gated: apply goes through `EffectStack::admits`; 35/33 is validated by `parse_strip` and ownership in `strip`. Tested through `handle_in_world`.

8. Every exit path restores the player: expiry, cancel and logout all end in no stuck visual (a logout drops the stack with the session; neighbours see the actor despawn).
9. Economy: no items, coins or rewards touched.
