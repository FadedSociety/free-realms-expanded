## Security

Trust boundaries touched, all through existing code paths:

- **127/23 from the client (hostile).** The body is empty (`00ac7af0`); the property granted is the
  server's `starter_property_id` from server-owned content. The client supplies no property id,
  lot guid or count. The lot guid is derived server-side from (owner, property)
  (`housing.rs:621`). A repeated 127/23 grants nothing (test: `again.changed == false`,
  state equal); a refused request is staged on a clone in `Gameplay::handle_housing` and changes
  nothing (existing `refused_requests_change_nothing` still passes).
- **Economy.** The free grant is one per (character, property); it cannot be farmed by repeated
  asks, reconnects or a second session (the lookup reads the saved lots). Lots are not inventory
  items and cannot be sold. An existing owner gains exactly one extra lot, bounded by
  `MAX_STATE_LOTS` (64).
- **No new oracle or enumeration.** 127/23 lists only the caller's own lots
  (`house_list(actor, actor)`); nothing reveals other owners' lots or content rows.
- **Saves.** Unchanged path: the lot joins `HousingServiceState` in the one atomic character
  snapshot (`character_store::replace_bytes`). The reload test proves a pre-condo save loads
  under the new content and keeps lot 1 byte-equal in the 127/39 list.
- **Scene / zone id.** Zone 25 is unique among lots and unused elsewhere in content; an
  unseeded lot scene gets its own membership instance, so it never aliases the public world.
- **Content trust.** houses.json is server content, parsed with `deny_unknown_fields`, a 1 MiB
  cap and per-row validation (names <= 256 bytes, finite coordinates). No secrets or player data
  in logs, tests or notes.
