## Inventory UI (`ui.inventory`)

`InventoryNavigationDataSource` is named by its constructor at `00a7c6e0`, which registers `Inventory.Navigation` and `BaseClient.Inventory`. Its four vtable groups are at subobject offsets 0, `0x30`, `0x34`, and `0x254`; the arrays are a node array at `+0x274` and visible-index array at `+0x284`. `00a7bb70` and `00a7bb90` expose row count and values, while `00a7c220` and `00a7c310` provide category/item columns. `00a7bfe0` refreshes changed row values through UI handles.

`00a7b930` rebuilds the index. With the filter byte `+0x295` and int `+0x298` both zero, it includes every node; otherwise it calls slot 3 on each node. `00a7ba90` is the `ItemGroupNode` slot-3 implementation: it looks up the item record, checks bytes/flags, invokes `00bae870` or `00bae8c0`, and applies the `+0xf4` selector rule. It ignores the passed filter-text pointer, so the earlier draft's text-search claim is unsupported. The other node type's slot-3 behavior and the meanings of the filter byte/selector remain open.

`00a7c530` tears down the datasource. Its pseudocode contains a count-guarded `_free` of the node-array data pointer and a separate memory-manager release path for the index array. Ghidra marks the `_free` path non-returning, leaving its relationship to the later node-array cleanup unclear; the record now reports that uncertainty instead of claiming both arrays follow one allocator path.

## Containers and unresolved ownership (`engine.containers`)

The five-bucket participant map inserts nodes at the tail of its doubly linked list in `00a80fe0`; `+0x80` is the forward link, `+0x84` the previous link, map head/tail are `+8/+0xc`, and bucket links use `+0x8c`. The earlier LRU-at-head description was wrong; no LRU meaning is established. `00a80b10` is an unreferenced head-drain loop calling `00a807a0`, not a proven destructor. The actual map destructor bodies `00a810b0`/`00a81210` have their own vtable/EH evidence and call erase directly.

`00a813e0` selects the left child when present, otherwise the right, and reconnects it to parent/root; it does not check that the node has at most one child. Its caller `00a818e0` must provide that condition. Tree ownership and whether the structure is red-black remain caller-side questions. The name lookups `00a81130`/`00a811a0` hash the input and compare stored hash keys before casting; the functions do not compare the original name bytes. Cast helpers `00a80c30`/`00a80d10` prepare a diagnostic on failure by calling object slot `+0x24`; the role of their second parameter is unresolved, and the diagnostic sink `00821dd0` is a stub, so actual logging is not established.
