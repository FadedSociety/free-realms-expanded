# F218: Fix review blockers in F206 (commit d8ff333)

## Result

Fixed the review's BLOCKER and all three MINORs. F206's new skip ran after `Profiles::load`, so a
T023 save whose pre-derby job had been removed from `profiles.json` — while still in the saved
`unlocked` set, as T023 left it — still failed login in `Profiles::load` before the skip could log.
`Gameplay::load` now hands the marker's id to `Profiles::load_with_retired_job`, which drops exactly
that one unknown unlocked id and its experience, logging it, before the strict snapshot check;
every other unknown id still fails closed. Two regressions cover the removed job and the T023
`active=49` skip; a third pins fail-closed for unrelated unknown unlocks. The report MINORs
(figures, stale sign-off wording, exit-path wording) are corrected in the F206 and F164 notes.

## Findings and fixes

1. **BLOCKER — removed, previously unlocked predecessor job still failed login.** Real, fixed.
   `Profiles::load` rejects an `unlocked` id absent from `profiles.json`. T023 both wrote
   `previous_job` and left the pre-derby job unlocked, so an operator removing that job from
   content failed `Gameplay::load` at the profile load before `restore_saved_derby_job` ran.
   - `Profiles::load_with_retired_job` (`src/profiles.rs:133-185`) takes the marker id, and when
     it is positive, absent from the content ids, and actually unlocked, removes it and its
     experience and logs. `Profiles::load` delegates with `None`, so every other caller and test
     is unchanged and keeps the strict fail-closed check.
   - `Gameplay::load` (`src/gameplay.rs:653-657`) passes `saved_derby.previous_job` at the profile
     load; the existing skip then logs and keeps the saved active job.
   - Regression: `tests/derby_route.rs::a_previous_job_removed_from_content_still_loads_the_t023_save`
     crafts the T023 shape through a real save document (`game_store::load_or_create`), removes the
     named job from the fixture's `profiles.json` while leaving it in `unlocked` (with 250 XP), and
     asserts the load succeeds, the saved active job stays, the retired id and XP are gone from the
     next save, and the active job is not the retired one.
   - Regression for the fail-closed scope:
     `the_retired_job_repair_leaves_other_unknown_unlocks_fail_closed` keeps an unrelated unknown
     unlock in the save and asserts `Gameplay::load` still returns `InvalidData`.
2. **MINOR [edge/test] — the T023 `active=49` skip is untested.** Added
   `a_t023_save_keeps_the_temporary_job_when_the_previous_job_is_locked`: the marker names an id

   26/13 switch). The log line now names the kept job (`src/gameplay/derby_session.rs:21-28`), and
   the doc comment records the deliberate choice: keep the saved job rather than invent a fallback
   outfit/job at load. This is the review's allowed "clear recovery message + assert the chosen
   behaviour" option.
3. **MINOR [report] — stale figures and sign-off wording.** In `notes/Autopilot/F206.md`:
   `git show --stat d8ff333` is 298 insertions / 25 deletions across seven files (the note itself is
   203 of the insertions), the hub is 6128 lines (ceiling 6151), and the restore call is

## Security note (secure-code-guardian)

Threat: the client cannot write save files or content, but a stale operator content package or a
tampered save can name a `previous_job` and list it in `unlocked`. The repair only *removes* an id
and its experience, and only when the id is positive, absent from `profiles.json`, and actually
unlocked; it can never add a job, XP, item or coin, and it cannot activate an id absent from
content. Any other unknown id still fails `Profiles::load` (`the_retired_job_repair_leaves_other_unknown_unlocks_fail_closed`),
the active job must still be in `unlocked`, and every refusal is logged, so a hostile save cannot
turn the tolerance into a bypass. No client quantity, item id or chat text is trusted or parsed
here. Unknown fields still fail closed through the existing `deny_unknown_fields` decoders.
