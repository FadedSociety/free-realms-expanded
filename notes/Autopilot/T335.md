# T335: prove the two-player playtest loop end to end

## Result

Six new default-suite tests in `tests/multiplayer.rs` drive the same real
`Server`/`Client` UDP harness as the existing multiplayer tests. Two real
sessions (characters 2 and 3) see each other, form a group, chat, kill one
shared field wolf, keep their own rewards and quests, and keep them across a
relog. Nothing in `src/` changed: the loop exposed no production defect, so no
fix outside the test tree was needed.

The six tests:

1. `two_players_see_each_other_with_the_real_name_and_job` - each receives the
   other's 35/1 AddPc with the account store's character name and model and the
   character's own saved active profile; A switches to the Brawler job (26/13);
   the current viewer receives the live 35/7; a third late joiner receives
   exactly one current AddPc for each player with the new active profile (43),
   not the pre-switch look.
2. `a_group_forms_and_party_chat_reaches_both` - the real 40/1 invite, 40/4
   accept, 40/4/40/9/40/8 fanout with a leader + both members in the roster;
   channel-4 party chat reaches both and echoes to the sender; a local say in
   range reaches both; a tell by name reaches the target. A duplicate invite
   (already grouped) and a stale 40/4 leave the group and pending state intact
   and the party still works.
3. `a_shared_field_kill_pays_both_and_credits_the_killer_once` - both hit one
   200 HP wolf inside T240's window; one shared death; each receives exactly
   one 2-coin/5-active-job-XP payout (the level 1-2 `field_kill_rewards.json`
   band, as deltas over the opening balance); the killer's synthetic defeat
   quest advances exactly once (49/9 at 6..18, saved count `[1]`); a replayed
   lethal hit and a corpse hit pay and advance nothing. The contributor's quest
   counter is deliberately not asserted (T302 may make it 1).
4. `each_character_keeps_its_own_coins_and_quest_after_relog` - A kills wolf
   one, A wounds wolf two and B lands the lethal hit, so A earns killer plus
   contributor payouts and B one; both turn the quest in through the ordinary
   Talk/26/6/49/14 path. Both sessions disconnect (the production
   `game_store` save) and reconnect through the gateway loader. Each keeps its
   own coins, Brawler job XP, item stacks (A one quest item; B a seeded
   distinct stack plus its own quest stack with different unique instance ids)
   and quest counter; fresh kills after the relog pay on top of each saved
   balance; a replayed hit on the old corpse pays nothing; the completed quest
   counter is unchanged.
5. `one_players_disconnect_or_bad_packet_does_not_stop_the_other` - A's
   malformed 36/10 (unknown action kind) is refused for A alone and changes no
   coin or quest byte; A then disconnects mid-action (only A's session ends);
   B still moves, says, and kills the same shared wolf for its payout while the
   server keeps stepping.
6. `the_social_loop_uses_no_dev_commands` - group, party chat, field kill and a
   real relog through ordinary client requests; every message both clients
   sent is scanned and contains no `realm` or `teleport` developer command.

Why `Client::drain` batches ACK servicing: the content-bound login sends the
typed self data and item definitions as ~600 transport packets. The old
harness stepped the server after every ACK; each step paid the server's 10 ms
socket timeout, so draining one session took >10 s and the other live
session's unacked AddPc hit the sender's 10 s retry limit. Batching 32 ACKs (the
sender window) per step is test-harness only and keeps both sessions alive
through the second login. The six tests then run in seconds.

## Security threat note (secure-code-guardian)

No client input parser was added or changed. The suite exploits the existing
attack surface to check the production boundary:

- **Malformed field request.** A 36/10 with an unknown action kind is a
  single, non-bundled application message; the gateway refuses it for that
  request (`gateway.rs` silently drops a single `handle_in_world` error) and
  changes no saved coin, item or quest byte. The test asserts the whole saved
  quest object and coin balance are unchanged and no payout/49/9 is sent. A
  bundled malformed child would end the sender's session; the disconnect case
  covers the session-boundary half: only A's session ends, its save is written,
  B and the server tick continue.
- **Stale/duplicate social requests.** A duplicate invite from the leader to an
  already grouped member returns the already-grouped result (3) and sends no
  40/1; a stale 40/4 generation returns result 3 and changes no roster or
  pending invitation; the party still routes afterwards. A hostile client
  cannot echo an old pop-up to consume a replacement invitation.
- **Chat.** The server rebuilds the sender identity from the session; the
  client-sent name records in the chat request are ignored. The suite's tells
  use the target character's own name and verify delivery only. Per-session
  spam pacing is production policy (the test spaces lines to obey it).
- **Rewards.** Coins, job XP and quest credit come only from the server-owned
  kill event (`credit_field_kill`/`claim_kill_credits`) and the server-built
  turn-in. Replayed lethal/corpse hits after the kill and after a relog pay and
  advance nothing. The kill is one shared death; the two payouts are exact
  deltas, not client-reported results.
- **Economy/id.** The quest item grant is one stack per character; the seeded
  B stack has its own instance id and the two characters' rewards do not alias.

No off-limits module (login, account, session, transport, trade, Cargo) was
touched.
