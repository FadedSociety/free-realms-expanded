## Range map

- **Mini-game tables and records:** `009b62a0` routes `MiniGameData.txt`, `MiniGameGroupData.txt`, `MiniGameGroupLinks.txt`, and `MiniGameTypeData.txt` to parsers `009b3290`, `009b4d00`, `009b3710`, and `009b34f0`. The table identities rest on that loader call. `009b2f60` constructs records with group-link and integer arrays. `009b3fe0`/`009b3240` construct and destroy a `HashListMap<int,MiniGameData*,100,-1>`; `009b4350` inserts key/value nodes and `009b42b0` removes them. `009b4f60` walks manager entries and calls the insert helper after a first-table key match; its domain meaning remains unknown.
- **Containers:** `009b2210` grows and relocates 0x48-byte elements; `009b4ad0` only grows score rows and constructs added entries. `009b5260` returns aligned inline storage for capacities up to 10 and allocates larger requests. Goal-state arrays use 0x110-byte elements (`009b22f0`, `009b5340`, `009b5390`, `009b5430`). `009b5d70` destroys destination score rows, appends source rows, and returns the destination.
- **Bounded readers:** `009b2340` reads a five-field header; `009b24a0` reads its two-i32 admin variant. Both `009b2340` and the shared prefix reader `009b2550` sign-extend a 16-bit value and an 8-bit value into dword fields (raw `MOVSX` bytes at `009b2340` and `009b2550`). The body readers from `009b25b0` through `009b2960` and `009b4600` through `009b46c0` extend that prefix with bounded fields. `009b56d0` through `009b5ac0` wrap these readers; nonzero `param_4` permits trailing bytes, while zero requires the cursor to reach or pass the end.
- **Score rows and packet flow:** `009b61a0` constructs the family-39/sub-opcode-47 end-score packet. The incoming handler path documented in `notes/Research/Native Combat Results Lifecycle.md` reaches `009bb030`, then `009b82d0`, then row reader `009b2b30`. On a negative or truncated row length, `009b2b30` sets error and moves cursor to end but still attempts five i32 reads at `+0x34..+0x44`; unavailable fields are zeroed. The lifecycle note and `notes/Research/Pieces/016 Minigame loss and retry.md` support the client-side parse path, not original server scoring or rewards. The packet catalogue has no matching mini-game class, and bare readers carry no opcode literal, so no packet class/opcode is guessed for those records.
- **Objective and result UI:** `009b6700` sets objective status 3, reformats text, updates counters under its field conditions, and conditionally emits `ObjectiveComplete`. `009b6950` sets status 4 and reformats text, but notification work additionally requires record byte `+0x28 == 0` and successful localization. `009b7170` normalizes statuses only under gates involving objective `+0x2c` and state byte `+0x63`; it groups records by byte `+0x28` and counts status 3 in each group. The two ratios are not identified as win/loss or completion/failure counts. Time comes from state `+0x74`; the values passed from `piVar3[0x1c]` and `[0x1e]` are dwords at byte offsets `+0x70` and `+0x78`.
- **Lua/UI and cleanup:** `009b6490` releases a temporary tagged Lua parameter for tags 3, 6, 7, or 8, resets its tag/payload, and emits `GameEvents:OnUnlockUI`; it does not clear external callback states. `009b6aa0` dispatches HUD Lua events by game type, and `009b6da0` computes a reward index and emits `ScoreScreen:StopLootWheelAt`. `009b5c10` calls the score-array cleanup with embedded receivers `this+0x34c` and `this+0x68`. `009b6140` calls record cleanup with receiver `this+0x18`. `009b6220` clears the score-array member at `+0x1c` after freeing it. In these and other calls in the shard, Ghidra's `DAT_01b839d8 ^ &stack...` values are `/GS` or SEH bookkeeping, not call arguments; raw call setup leaves the actual receiver in ECX and shows only true stack arguments.

## Existing-note comparison and open questions

`notes/Research/Pieces/016 Minigame loss and retry.md` describes the wire prefix as `u16 | u8`; the native readers sign-extend those 2-byte and 1-byte values into dword fields. Widths agree, but behavior for high-bit values differs; preserved common IDs do not resolve that edge case. The native score-row route agrees with `notes/Research/Native Combat Results Lifecycle.md`. The separate AS2 result behavior in `notes/Research/Native Crafting Results Lifecycle.md` does not conflict with this native end-dialog path.

Open questions: whether the signed extension is intentional for high-bit prefix values; semantic names for the score-row fields, manager keys, objective grouping byte/status values, and state dwords; schemas for the secondary tables; and original server scoring/reward behavior. The original server is unavailable, and no server inference is asserted here.
