# T634: Marketplace and coin prices from the wiki catalogue

## What changed

- New generator `scripts/build_wiki_prices.py` (`python -I`; `--check` only verifies, `--report PATH` writes the
  per-article lists). It reads three pinned inputs by absolute path and asserts their sha256, so any drift stops it:
  the wiki harvest `lab/references/freerealms-wiki/harvest/lists/catalog.json`, the client locale export
  `lab/reports/locale-id-to-text.json` (85,932 ids) and the runtime item catalogue
  `lab/reports/round70-native-20261016T061000Z/content/item-catalogue.json` (58,835 definitions). It edits only the
  changed lines of `data/content/stores.json` (LF kept; every untouched row is checked to round-trip byte for byte)
  and asserts the result (55 Station Cash rows, 1 coin row). A second run changes nothing (rows it priced carry the
  `T634` tag and are recomputed to the same values).
- `stores.json`: 55 rows get `sc_price` (the wiki regular price), `earn_only: false`, `price_provenance` (wiki
  name, URL, revision, the listed prices) and the `T634` tag (legend entry added). 1 row gets `purchase_price_coins`
  and `member_price_coins` with provenance. 58 lines changed in all.
- `tests/station_cash.rs`: three new tests (a clothing item lists at 1/4 and buying it grants it; an ambiguous-name
  item stays unpriced and refuses; a Coin Shop item that had no price sells at the wiki price, member and
  non-member). Two ride-only assertions were narrowed to rides (rows whose provenance names a ride) and the shipped
  listed count is now 145.
- `tests/ride_sources.rs`: `buying_each_ride_with_coins_grants_it` now buys only the ride listings (and asserts 81).
- `tests/test_wiki_prices.py`: the matcher on synthetic inputs (ambiguity, tint variants, sale price, coin-priced
  siblings, idempotence).
- No Rust source changed: `station_cash::place_order` already grants any non-deed listing through
  `Inventory::grant_with_tint`, the same inventory grant family the coin shop uses, so the order path needed no
  extension.

## Method and counts

Chain: wiki article name -> locale ids with that exact text -> item definitions whose NameId (the second dword of the
definition; client reader `008e3760` reads Id, NameId, ..., Cost, Class) is one of those ids -> `stores.json` rows of
those items. A name whose definitions (all of them, store row or not) span more than one Class is ambiguous. Tint
variants (same name, same Class) take the same price. The first listed price is the regular one and a second is the
sale price (of the 514 two-price Marketplace pages 480 fall by 10%, 21 by 11%, a few by 20 to 67%, and one rises); a list that rises, or has
more than two numbers, is skipped.

## Evidence

- Item definition layout: client reader `008e3760` reads Id, NameId, DescriptionId, icon id, icon tint, Tint,
  Unknown5, Cost, Class as the first nine dwords (IDA decompile; same order as the FIELDS list in
  `scripts/build_item_catalogue.py`). The generator asserts Id, NameId and Class against the catalogue's own fields
  for all 58,835 rows. All 56 priced items have Cost 0 in their definition, so no client or Legacy `Cost` is
  overwritten.
- Marketplace listing and grant: unchanged client-pinned code in `src/station_cash.rs` (`00b3fc60`, `00b3b6d0`,
  `00b48700`, `00b41860`, cited there).
- Wiki facts (price, revision) are content evidence; each priced row's `price_provenance` names the page and revision.

## (R) choices

- The first listed price is the regular price, a second is a sale (wiki convention; 480/514 pairs fall by exactly 10%). A
  coin pair `[a, a]` is read as one price.
- Ambiguity is decided by item Class across every catalogue definition with the name, not only store rows (strictest
  reading of "never guess").
- The member coin price of the filled coin row is the R2 floor rule from `member_discount_percent`.
- A row with a coin price never also gets a Station Cash price (the store loader refuses it, and clearing a Legacy
  `Cost` is not this task's call).
- Station Cash rows are all `no_sale: true` already (the loader requires it), so the NPC vendor does not buy them.

## Threat note

A hostile client can send any bundle id, store id, quantity, tint, gift recipient or coupon in 66/1 and 66/3. The
listing is built only from `stores.json` rows with a server-side `sc_price`; an id outside it, a quantity other than
1, a wrong store, a gift or a coupon is refused with the order failure and changes nothing (existing
`refusals_change_nothing`, plus the new ambiguous-name refusal test with a state snapshot). The price comes from the
server row, never the packet. The debit and the grant commit together on clones, and the replay window stops a
duplicated packet paying twice. The new rows are no_sale with no coin price, so a bought item cannot be flipped for
coins at a vendor (rule 9). The generator only reads pinned lab files and writes `stores.json`.

## Open gaps

1. **234 Station Cash articles are untouched because Legacy already gives their items a coin `Cost`** (for example
   Dog Tail: 49 SC on the wiki, 270 coins in the reference). The loader refuses a row in both currencies, and the ride
   rows set the precedent of clearing the coin price. Moving them to Station Cash means clearing a Legacy coin price
   on about 230 articles; that is the lead's call, and the generator can do it with one more rule.
2. The Marketplace has one category node, `Rides` (139), so the new items (and the lot deeds before them) show
   under it. A real category tree for clothing, furniture and pets needs the client's category ids.
3. Items the wiki lists but the client names differently (174 + 91 unmatched, 25 with no store row) stay unpriced.
4. Whether `NoTrade` is clear for the new items (the owner: Station Cash items can be traded) is the item catalogue's
   value; this task did not change it.
