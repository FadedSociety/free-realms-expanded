# T492: Realms Roll Boombox transforms nearby players (35/14, 35/15, AddPc)

Builder on the newest `autopilot` tip. The fleet pack (`lab/fleet/out/brief-research/T492.md`) is
stale: T459/T461/T463/T494 (boombox catalogue, presses, synchronized and independent dances) and
T512 (`PlayerPresentation::temporary_model`, AddPc +0x144) have landed, but the Realms Roll
transform had not. This run applied `lab/autopilot/patches/T492-a2.patch` as instructed; the
`boombox.rs` hunks and the `boombox_routing.rs` test append rejected because the tip has the newer
`Dance` enum (T494) and the T512 AddPc layer. Every rejected hunk was ported by hand onto the new
structure; both `.rej` files were deleted. The wire readers were re-decompiled this run.

## What changed

- `src/boombox.rs`
  - `Transform`/`Transformed`: model, reapply delay, `dance_sequence[0]`, and per-session guid,
    mount state, whether the base dance was sent, and the reapply deadline.
  - `Placed` owns `priority`/`range_m` for every box kind; the old `Dance::priority/range_m`
    copies are gone. `Dance::new` still returns `None` for a transform row.
  - One owner map now covers synchronized, independent and transform boxes: highest priority,
    then X/Z distance, then placement order. Synchronized/independent boxes need an on-foot
    dancer (and a allowed shown model); a transform box takes a mounted player too.
  - Entering: `set_temporary_model`, 35/14, then 35/8 base `dance_sequence[0]` (unless mounted)
    to `audience()` (subject + nearby sessions that know the character). Mount changes stop the
    dance and schedule one 35/14 re-send after `transform_reapply_ms`; dismounting re-sends the
    model and restarts the dance.
  - Leaving range, zoning, expiry, replacement and disconnect: the transform is released. 35/15
    then idle when nobody takes the player; 35/15 before the new 35/63 when a synchronized box
    takes over; a transform-to-transform hand-over lets the new box's 35/14 stand. A live
    consumable temporary appearance (T512) is put back with 35/14 after the box's 35/15.
- `src/players.rs`
  - `PlayerRegistry::temporary_models: BTreeMap<SessionId, i32>` — session-only AddPc layer.
    `set_temporary_model` (positive sets, zero/negative clears, unknown session ignored,
    idempotent) and `clear_temporary_models` for the tick panic path. Dropped on `leave` and on a
    zone change (the client drops the actor with the scene).
  - `build_add_pc` takes the boombox model and writes it at +0x144 when non-zero, else T512's
    `presentation.temporary_model`. Both field docs state the precedence.
- `data/content/boomboxes.json`: row 1180 (Realms Roll) now carries `dance_sequence: [3541]`,
  with the client citation (`AnimationTypes.xml:1054 emo_dance_rroll_01`, type 4). Model 1941,
  priority 100, reapply 2000, range 15 and duration 180000 were already in the row.
- `tests/boombox_catalogue.rs`: a transform row now requires exactly one `dance_sequence` entry,
  and the loader refuses a transform without one or with two. Every dance id is still checked
  against the client's AnimationTypes/AnimationGroups, and 1941 against Models.txt.
- `src/bin/osfr_gateway/boombox_routing.rs`: passes `&mut world.players`; the panic path drops
  the boxes and clears every boombox AddPc model. Adds three gateway tests through the real
  item-bar press, tick and session queues.
- `tests/players.rs`: AddPc tests for 1941 / 0 / clearing / unknown session / precedence over the
  T512 consumable visual. The existing oracle and plain-player golden bytes are unchanged.

## Wire evidence (IDA, re-checked this run)

- 35/14: dispatcher `0x0092f460` jump-table case 14 at `0x00930283` (ctor call `0x0093028a`,
  ctor `0x008b4370`); wrapper `0x008f75b0` -> reader `0x008d6890`, which calls header
  `0x008d6830` (two i16), then reads i32 into record +0x18, then u64 into +0x10/+0x14.
  Wire is `u16 35, u16 14, i32 model, u64 guid` = 16 bytes. Applier
  `ProxiedCharacter::SwitchToTemporaryAppearance` `0x0096bd90` compares record +0x18 and reads
  `this+324` (+0x144).
- 35/15: dispatcher case 15 at `0x00931452` (ctor call `0x00931459`, ctor `0x008b4310`); wrapper
  `0x008f7bd0` -> reader `0x008d7230`: header, u64 into +0x10/+0x14, i32 into +0x18, then
  applied by `0x0096a110(0)`. Wire is `u16 35, u16 15, u64 guid, i32 0` = 16 bytes.
- AddPc +0x144: writer `mov [edi+144h], eax` at `0x0091add1`; reader `0x0091aa10` stores the i32
  at `this+324`, immediately after the three role bytes and before the guild runtime at +328.
  Our +0x144 write and field order match.
- 35/8: existing `world_events::piece_052::animation_packet` (reader `0x00908a50`); flag bit 0 is
  the base animation, 21-byte packet.
- Golden bytes in `boombox::tests::transforms` are built independently of the encoders and
  asserted on real sends; gateway tests re-parse the drained frames.
- The fleet pack said `0x00930283`/`0x00931452` were near the call sites, not the case labels;
  IDA's disassembly labels both (`; jumptable 0092F540 case 14/15`). IDA wins.

## (R) rules

- The first 35/14 is immediate on entering range (the brief). Sanctuary's `BoomboxHelper` delays
  the first transform when `TransformReapplyDelayMs != 0`; the brief overrides that here.
- A mount change while transformed re-sends 35/14 once after `transform_reapply_ms` (brief).
  Sanctuary instead re-applies when the client reports the appearance missing.
- `dance_sequence[0]` is the transform dance (Sanctuary's `StartRealmsRollDance`). The 12667 ms
  Sanctuary duration is not carried: 35/8 base is an animation id, not a timed clip.
- A mounted player is transformed but gets no dance. On foot again the model is re-sent after the
  delay and the dance restarts.
- Release into another box: 35/15 without idle when a dance box takes them; nothing extra when
  another transform box takes them (it sends its own 35/14); 35/15 then idle when nobody does.
- A live consumable appearance is restored with 35/14 after the box's 35/15. While a box is
  applied, the boombox model wins in AddPc.
- Box placement, range, duration, priority and reapply are the JSON row's. Only wire constants
  (`IDLE_ANIMATION`, the AddPc tail) are compiled in.

## Threat note (secure-code-guardian)

No client message reaches this code: 35/14 and 35/15 are server-to-client only, and the trigger is
the 20 Hz tick. The model, dance, range, priority, reapply and duration come from `boomboxes.json`,
validated at load (models against Models.txt, animations against AnimationTypes/Groups, transform
kind/model consistency, one dance on a transform row, positive ids, finite/in-range numbers). A
hostile client can only change its own pose/mount through the existing validated movement/mount
paths and step in or out of range; it cannot choose the model, name another player, or exceed the
directed-visibility audience. Packets go only to `audience()`: the subject plus nearby sessions
that `knows_character`, so no blind broadcast. A receiving queue that refuses is logged and
skipped, never propagated. The press that creates the box is the existing T461 item-bar path
(own, on foot, not busy, recast; 36/1 refusal changes nothing). The temporary-model map is
session-only, ignores unknown sessions and non-positive models, is dropped on leave, and is never
written to a save. No new `unwrap` on client data; additions are saturating; the tick runs inside
`contain`.
