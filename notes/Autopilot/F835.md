  instances), 85 `[0x00, 0x02, 0x03]`. This is the regression test for findings 1 and 3.

## Client evidence (TCG DLL; IDA resolves only `FreeRealms.exe`, so the Ghidra TCG project was used)

The read-only IDA broker was queried first (`ida_query.py find
"StartInstances|SendInstances|SynchronizationCommand"`) and returned `no matches`: it only has the
EXE database, so it cannot answer for the TCG DLL (the review says the same). The lab's Ghidra TCG
project (`lab/content/tcg/ghidra-project`) supplied the evidence for the TCG DLL (SHA-256
`22F0E8F9DFC9CB398898E227FB9744B6DA1989E8DCFFF7B5FAE85E4BD162CD8B`, from the lab README); the
queries are reproducible from `DecompileF835*.java` scratch scripts (kept outside the repository).

- **85 `SynchronizationCommand_SendInstances` v2**: vtable `10671e84`, reader slot `+0x24` =
  `101d94c0`. The writer/describe `101d8d70` labels the fields in order: `Base Archetype ID`,
  **`Archetype Count`**, `Instances:` (list), `NonTradable Instances:` (list), `Delivery ID`. Its
  execute `101dc290` adds `param_4` (the count argument) to the collection counter at `+0x30`.
  The reader reads base archetype, then the count, then the instances list (`10077f00`), then the
  non-tradable list, then the delivery id.
- **84 `SynchronizationCommand_StartInstances` v2**: vtable `1067266c`, reader slot `+0x24` =
  `101dadf0`. The T825 note cited `101dadf0`, but the lab's Ghidra export had never created that
  function (it is the vtable's raw target); review finding 3 was right about that, wrong about
  `101dae80` being the reader. This task disassembled `101dadf0`: class headers (virtual `+0x10`),
  family header `101d7090`, then int -> `+4` (account), int -> `+8` (collection type), int ->
  `+0xc` (count), and for version > 1 an int -> `+0x10` (ModID). The writer/describe `101dae80`
  labels those four fields `AccountID`, `Collection Type`, **`Archetype Count`**,
  `CollectionModID`; the execute `101dbc80` stores the count at `+0x2c`, the ModID at `+0x44`, and
  raises event `0x1b` (27) with them.
- Consequence: a 15-archetype x 2-copy starter (30 cards) sends 84 count 15 and 85
  `[0, 15, 30, instances...]`; before this fix it sent 30 and `[0, 30, 30, ...]`, so the client's
  event 27/28 counters and any archetype-count logic were scaled by copies.
- IDA could not answer for the DLL; the decompiler corrects the T825 note: the note's 84 field
  semantics were wrong, while the address `101dadf0` was right (it is the vtable slot, not in the
  export's function list).

## Threat note (secure-code-guardian)

The change is server -> client encoding only; no new client field is trusted.
- A hostile client cannot choose either count: `cards` is the launch block's validated starter
  collection (`Content::validate`: distinct positive ids, 1..=16 copies, at most 100 archetypes),
  and both counts are derived from it. The i32 casts are safe under those bounds and the instance
  sum cannot overflow.
- The sync is only reachable after a successful 81: `Connection::lobby_command` starts with
  `let account = card_service::account_id(self.character?);`, and `self.character` is only set by
  a redeemed one-time launch ticket. A refused login gets only its 81 and the connection closes
  (T808); it never reaches `enter_lobby`.
- The 84/85 bodies are not decoded from client input; client 84/85 frames remain unhandled
  messages (capped log), and client 86/87 only advance the server's own state machine. 137's
  account is the redeemed character's, never the client's account field.
- The fix removes a client-state corruption: the wrong archetype count fed event 27 and the
  collection counter, which a client UI keys on. No server trust boundary moves.
- No persistence, coins, items, rewards or roles are touched. No refusal path changed, so "a
  refusal changes nothing" is unaffected.

## Checklist (19 items)

1. **A refusal changes nothing.** Not applicable: no refusal path or staged state changed; the fix
   is pure encoding. The listener's existing refusals (bad frame/message/login) are untouched.
2. **Rollback covers all state.** Not applicable: no transaction, save or shared state added;
   `SyncStep` is per connection and unchanged.
3. **Apply deltas, never restore snapshots.** Not applicable: no inventory/coins/position.
4. **Busy rules are mutual.** Not applicable: the card collection sync is UI state after the
   card login, not a world activity; the card run's busy behaviour (Launches) is unchanged.
5. **Every entry path is gated.** The sync is pushed only from `enter_lobby`, itself only after a
   successful 81, and `lobby_command` begins with `self.character?`. The refused-login test
   (`a_login_is_accepted_only_for_the_ticket_redeem_names`) shows a refusal gets only its 81 and
   a close; no sync path exists before login.
6. **Reachable in production, tested through it.** `a_card_login_syncs_the_starter_collection`
   drives a real TCP connection through `CardListener::poll` -> `serve` -> `enter_lobby` ->
   `lobby_command`, byte-equal to the codec; the wire golden is `the_collection_sync_bodies...`.
   Production enablement needs the lab/native launch block (finding 6), documented.
7. **Survives reconnect.** Not applicable: nothing is persisted; instance ids are derived
   deterministically (archetype, series 0, numbers 0..copies) and the ModID is a pure hash, so a
   reconnect re-syncs the same ids; the cached path is tested by
   `a_cached_card_collection_is_not_sent_again`.
8. **Every exit path restores the player.** Not applicable: no player state, position or busy
   flag is changed by the sync.
9. **Economy safety.** Not applicable: cards are not items, coins or rewards, and no client id or
   quantity is read; the counts come from validated server content.
10. **Wire format matches the client reader exactly.** Yes: byte-level goldens cite readers
    `101d94c0` and `101dadf0` (and writers `101d8d70`/`101dae80`); no extra or missing fields.
11. **Unique ids.** Not applicable: no ids are minted; the derived `InstanceID`s are stable per
    starter and no public-world instance is reused.
12. **Others see changes.** Not applicable: the card service is one connection's own session.
13. **Content works end to end.** The socket test asserts the complete Start -> 84 -> 85 -> 86
    exchange and the `card_sync` outcome. The 15-card starter itself is lab-package data (finding
    6); repository content intentionally has no launch block.
14. **Values live in data.** Both counts derive from the content starter; 100 archetypes and
    1..=16 copies are content validation bounds. No new compiled tuning or timeout.
15. **Canaries break production code.** Each canary listed in Gates changes the production
    encoder/bound, not the test, and the named test fails; then reverted.
16. **Hands off session plumbing.** No change in `src/bin/osfr-gateway.rs` or `gateway.rs`, and no
    session creation/teardown/save change. The listener is the T825-signed-off module; this diff
    only replaces one local expression there.
17. **One player's error never stops the server.** The codec returns `Vec<u8>` with no `?` in the
    shared tick; the listener's errors close only that connection. Counts are bounded by content,
    so the i32 arithmetic and instance sum cannot overflow.
18. **A type's rules live on the type.** `StarterCard`'s doc says archetype + copies; the two sync
    functions' docs name which field is the archetype count (and the writer labels that prove it),
    so a future field added to either body has a stated rule; `Lobby.collection` documents the
    starter and its bounds.
19. **Hot paths stay cheap.** No per-tick change; the bodies are built once per sync step per
    login (O(archetypes), <= 100), no new clone or allocation per tick, and the `if` replacement
    is equivalent.
