## (R) rules

- Order: AddPc first, then 35/13, then one 35/41 per aura, to that viewer only. The packets name
  an actor the client creates in AddPc, so they must follow it; OSFR's `b34d006` does the same
  (reference evidence, not recoverable from the 2014 binary).
- `scale == 1.0` exactly means "send no 35/13". The stack's live scale is bounded 0.25..=5.0.
- One 35/41 per started aura, using the stack's live world tag so the later 35/42 removes it.
- Expiry: `visual()` returns 0 / 1.0 / empty, `set_visual` clears the snapshot and the next
  viewer sees the plain AddPc (tested).
- Validation bounds: temporary model >= 0, scale finite and > 0, aura tag and composite > 0,
  at most 32 auras. These are sanity bounds, not recovered limits.
- The visual state is per session and not saved (the stack is session-only, T473/T474).

## Security threat note (secure-code-guardian)

- **What a hostile client could send.** Nothing new is parsed: the three values are server-owned
  and outbound only. 35/13, 35/14, 35/15, 35/41 and 35/42 are server→client in this code; the
  only inbound consumable packet is the existing 35/33 strip (T474). A client cannot name a
  model, a size, an aura, a tag or another player's GUID, and no AddPc field moved.
- **Why invalid values are refused.** `PlayerPresentation::validate` runs before every join and
  every `set_presentation`; a negative temporary model, a non-finite/non-positive scale, a
  non-positive aura pair or more than 32 auras returns `InvalidPresentation` and stores nothing.
  The tests assert the live presentation is unchanged after seven refused refreshes, and the
  join test asserts a refused snapshot registers no session. The 35/41 GUID and source are
  always `player.character_guid`, never packet data.
- **Recipients.** Follow-ups go only to the viewer that just received that subject's AddPc (the
  `current_view - old_view` branch). No broadcast, no new interest-radius path; a viewer who
  already sees the player receives no duplicate (tested).
- **Economy.** No items, coins, rewards, roles or cooldowns are touched; this is presentation
  replay for state the player already earned through T473's validated apply path.

## Checklist

1. **A refusal changes nothing.** `a_refused_visual_snapshot_leaves_the_live_presentation_
   unchanged` snapshots the joined presentation, attempts seven invalid refreshes (negative
   model, NaN/zero/infinite scale, zero tag, zero composite, 33 auras), asserts each returns
   `InvalidPresentation`, then asserts the stored presentation is still equal. The extended
   `oversized_and_invalid_presentations_are_rejected_without_joining` proves a refused join
   registers nothing. Canaries A and B break production code and fail the order test.
2. **Rollback covers all state.** The three fields live inside `PlayerSession.presentation`,
   which is inside the cloned `PlayerRegistry`; there is no `Rc`/`Arc`/side table, and the
   aura `Vec` is owned by the presentation.
3. **Apply deltas, never restore old snapshots.** `set_presentation` replaces the live snapshot
   with the current server state built from `visual()`; no earlier captured inventory, coins or
   position is written. The follow-ups are derived from the snapshot at send time.
4. **Busy rules are mutual.** No activity, occupation row or busy gate changed; presentation is
   not an activity.
5. **Every entry path is gated.** The only AddPc sender is `diff_messages`, and the follow-ups
   are attached inside its Spawn branch, so join, pose/zone entry and re-entry all get them.
   No second path exists (`search_graph build_add_pc`: one caller).
6. **Reachable in production, tested through it.** Production assembly is
   `Gateway::player_presentation` -> `PlayerRegistry::set_presentation` / `join_with_presentation`
   -> `refresh_views` -> `diff_messages` -> `build_add_pc` + `build_visual_followups`. The tests
   drive the real registry path; the gateway fill is not unit-tested because no production
   caller applies an effect yet (T474 gap) and the hub has no line budget for an inline test.
   Stated in Open gaps.
7. **Survives reconnect.** Nothing is persisted: the effect stack is session-only by design
   (T473/T474), so a reconnect intentionally starts with the plain AddPc. The registry snapshot
   is rebuilt at join.
8. **Every exit path restores the player.** Expiry (`tick` -> `changed`) refreshes the snapshot
   to 0 / 1.0 / empty; the test drives a real `EffectStack` through expiry and then joins a new
   viewer who sees the plain AddPc and no follow-ups. Cancel and logout are T474's existing
   paths; neither leaves the snapshot stale on the outbound side.
9. **Economy safety.** No items, coins, rewards or grants. The values are copied from
   `EffectStack::visual()`, which only holds validated specs; no client-reported result is read.
10. **Wire format matches the client reader exactly.** AddPc cites `0091aa10` (case 1 at
    `0092fec3` -> parser `00925380`); the byte test pins a plain player's AddPc to the pre-change
    frame (404 hex chars) and the order test pins 35/13 against reader `008d71b0` and 35/41
    against reader `008d7ad0` field by field (guid, tag, composite, source, unused zeros).
11. **Unique ids.** No ids are minted; the aura tag is the stack's live tag, which T473's
    monotonic allocator already keeps unique while live; no Guid is invented.
12. **Others see changes.** The snapshot refresh is the existing directed path (`set_presentation`
    on `gameplay_changed`); the new packets are sent only to viewers that just got that AddPc, in
    the viewer's normal delivery order (`Vec` order, preserved by `queue_delivery`).
13. **Content works end to end.** The order test asserts the final byte sequence a new viewer
    receives (AddPc with 169, then 35/13 2.0, then 35/41 with the composite) and the expiry test
    asserts the later viewer's plain frame - final outcomes, not intermediate flags.
14. **Values live in data.** No new tunable; the scale/model/composite come from the effect
    `Spec` (content/T474), and the only constants added are the 32-aura sanity bound and the
    test's golden bytes.
15. **Canaries break production code.** Canary A edits the AddPc writer, canary B removes the
    follow-up append in `diff_messages`; both fail the intended test and were restored
    byte-exactly (players.rs back to 36,216 bytes; suite rerun 19 passed).
16. **Hands off session plumbing.** No change to session creation, teardown, transactions or save
    ordering in `bin/osfr-gateway.rs` or `gateway.rs`; the gateway change is inside
    `player_presentation`, and the moved helper is a startup path lookup.
17. **One player's error never stops the server.** `visual()` and the builders are infallible and
    allocation-bounded; `validate` returns `Err` instead of panicking, and the registry returns
    messages rather than propagating errors. No `unwrap` on client data was added.
18. **A type's rules live on the type.** The three fields carry their own doc comments naming the
    `Visual` source, the wire slot and the validation rule; `validate` and `set_visual` are on
    `PlayerPresentation`, so a future field is decided there, not in a caller.
19. **Hot paths stay cheap.** Per tick: nothing in this diff (the stack's existing tick is
    unchanged). Per AddPc to a new viewer: one `Vec::new` and no allocation for a plain player;
    for a visible one, a 35/13 (16-byte inner) and one 36-byte 35/41 per aura, each tunneled
    once. `player_presentation` runs on join/`gameplay_changed` only, not per packet.
