## What changed

- `src/mounts.rs` (owner)
  - `MountService.last_sent: Option<(Vec<i32>, Option<u64>)>`, session-only. It holds the owned
    ride ids (ascending, as `owned_mounts` lists them) and the active ride GUID of the last 168/5
    sent. `reset()` clears it.
  - `list_packet` now takes `&mut self` and records `last_sent`. Every roster goes through it:
    spawn, put-away, refusal, world entry and sync. So the memo always matches what the client
    holds, and none of those sends can be followed by a duplicate.
  - `pub fn roster_sync(&mut self, inventory) -> Option<Vec<u8>>`. It returns the 168/5 only when
    the owned rides or the active ride differ from `last_sent`. It returns `None` before world
    entry, because the memo is empty until world entry sends the first roster.
  - Step 6: the private predicate `ride_lost`. It is true when the active ride (Spawned or Mounted)
    is of a mount that no longer has any owned candidate item (`is_owned`, the same test as
    `owned_mounts`).
  - `pub fn settle(owner, inventory, end)`.
    - It runs the existing `dismount_request` when `end || ride_lost`: 168/4 if the player is
      mounted, then DespawnRide, then a 168/5 that records the memo.
    - It then runs `roster_sync`. After a put-away that is always `None`, so one ownership loss
      sends exactly one 168/5.
  - `encode_mount_list` now takes the owned list that `list_packet` already built. The byte layout
    is unchanged.
  - `spawn` holds the mount as an `Arc` (`mount_arc`), so `list_packet` can borrow `self` mutably.
- `src/gameplay/rides.rs` (new, 15 lines): `Gameplay::push_rosters`. It pushes the pet roster and,
  unconditionally, the ride roster. It replaces both bare `self.pets.list_packet()` pushes in
  `initialize_world`. A character with no rides gets count 0.
- `src/gameplay.rs` (hub):
  - `mod rides;`
  - the two world-entry lines now call `self.push_rosters(&mut out)`
  - `settle_mounts` now calls `mounts.settle(...)` instead of an early return followed by
    `dismount_request`
- `src/startup_selfdata.rs`: comment only. `pre_action_records` is misnamed: it is the owned-ride
  list (`008e74c0` records) and still carries the captured rows. World entry overwrites the

### Why one call in `settle_mounts` instead of three `roster_sync` call sites (deviation, verified)

The brief asks for `roster_sync` at (a) `handle_in_world`, (b) the end of `Gameplay::tick` and
(c) the end of `handle_shared_field`. Step 6 goes in `Gameplay::tick` or `settle_mounts`. I put
both in `settle_mounts`, through `MountService::settle`, for three reasons:

1. **`settle_mounts` already runs after all three.**
   - The graph shows `Gameplay::settle_mounts` <- `Gateway::settle_rides` <-
     `Session::commit_outcome` <- `Session::dispatch_message_inner` / `Session::tick`.
   - `commit_outcome` (`src/bin/osfr-gateway.rs`) runs the shared-field action first, then
     `settle_rides`.
   - So one call covers every message, field action and tick.
2. **`Gameplay::tick` does not run in every content set.**
   - `Gateway::tick_at` (`src/gateway.rs`, "if !game.is_opening() && ... return") calls it only in
     the opening, kart, derby and soccer content.
   - `settle_rides` runs on every session tick.
   - So the trade commit (`lead_trade_commit.rs` -> `adopt_trade_inventory`) is put away on the
     next tick whatever the content.
3. **Split call sites would send two rosters for one loss.**
   - Example: (b) `roster_sync` in `tick`, then the step-6 put-away in `settle_mounts`.
   - Selling the ride or trading it away would then send a sync 168/5 (without the lost ride,
     while its actor is still out), followed by a second one from the put-away.
   - Deciding the put-away and the sync together in `settle` is what makes "exactly one 168/5"
     hold.

The hub also shrinks instead of growing by three lines.

## Client evidence (IDA, shared broker)

- **168/5 dispatch.** `00b06100` calls `00b05e00` at `+0x3e6` and `00b05600` at `+0x422`
  (xrefs).
- **`00b05e00` reader.** It calls `00b05830`, which reads an i32 count and then one `008e74c0`
  record per count.
  - So the brief's "records read by 008e74c0" is right.
  - The research pack's "probably wrong" is itself wrong: the call is indirect, through
    `00b05830`.
- **`008e74c0` record layout:**

  | Field | Type |
  |---|---|
  | id | i32 |
  | name | i32 |
  | image | i32 |
  | guid | u64 (+0x20/+0x24) |
  | members_only | bool (+0x28) |
  | tint | i32 (+0xc) |
  | tint alias | i32-counted string |
  | is_upgradable | bool (+0x29) |
  | is_upgraded | bool (+0x2a) |

  This matches `encode_mount_list` field for field. Gate (a) decodes the Wolf row with this layout
  and asserts that no bytes are left over.
- **`00b05600`.** It clears the store, copies every record, then refreshes the UI (`00cc39a0`,
  `00cc3a00`). It does not touch any actor.
  - So a count-0 list simply empties the store.
  - The order of a 168/5 relative to 168/4 or the remove-actor does not change client state.
- **`00b05bf0`.** This is only the destructor of the temporary packet.

## Threat note (secure-code-guardian)

- No new client input is parsed. 168/5 is server to client, built from the server inventory.
- A hostile client can only cause `settle` to run more often, by sending messages.
  - Each run is one pass over the inventory, plus one pass per remembered ride.
  - Nothing is allocated and nothing is sent unless ownership changed.
- A trade, sale or drop of the ride item can no longer leave the giver riding a ride it does not
  own. The next settle puts it away, and observers see the despawn and 168/4 through the existing
  `nearby` fanout.

## Checklist

1. **A refusal changes nothing.** No refusal path was added. The existing refusal still sends the
   roster; its send now records the memo, because the memo is "what the client holds", not game
   state. The memo test covers this (its canary is 5).
2. **Rollback covers all state.** `last_sent` is a plain field of `MountService`, inside
   `Gameplay`, so it is cloned and rolled back with the staged gateway. No shared cells.
3. **Apply deltas, never restore snapshots.** Not applicable. Nothing restores inventory or
   position. The put-away reads the live inventory.
4. **Busy rules are mutual.** Not applicable: no new activity. The existing ride gates
   (`occupation.rs` `ride`) still feed `end`.
5. **Every entry path is gated.**
   - `settle` runs after every message, field action and tick (graph above).
   - Grants (dev give, vendor, Station Cash, rewards), drops and the trade commit are all covered
     by it.
   - World entry covers relogs (gate c).
6. **Reachable in production and tested through it.**
   - The tests drive `handle_in_world`, `tick`, `adopt_trade_inventory` and `initialize_world`,
     plus `settle_mounts`, in the gateway's commit order.
   - The Scaled Dragon case is service level only, because of the catalogue limit.
7. **Survives reconnect.** The memo is session-only by design and cleared in `reset`. Re-entry
   resends the list (gate c, canary 3). Nothing new needs saving.
8. **Every exit path restores the player.** On a lost ride the existing put-away runs: rider
   dismounted, actor removed, state Empty. Gate (d) asserts `!is_mounted` and no `ride_view`.
9. **Economy safety.** No grants or prices are touched. Ownership is still read only from the
   server inventory. A traded-away ride can no longer be kept out.
10. **Wire format matches the client reader.** Field order was checked against `008e74c0` via
    `00b05830` and `00b06100` (see Client evidence). Gate (a) decodes every field and asserts no
    trailing bytes. The `tests/mounts.rs` byte-exact list test still passes.
11. **Unique ids.** Not applicable: no new ids. The ride GUID is unchanged (`ride_guid`).
12. **Others see changes.** The lost-ride put-away goes out through `ride_outcome` to
    `Outcome.nearby` and the gateway's `settle_rides` fanout. Gate (d) asserts the despawn, and
    168/4 when mounted, in `nearby`. The roster stays private (`MountEffect::nearby`).
13. **Content works end to end.** Gates assert the final rows, the final `is_mounted` and the
    final `ride_view`.
14. **Values live in data.** Not applicable: no new tunables. Ride candidates come from
    `mounts.json`.
15. **Canaries break production code.** All five canaries edit `src/mounts.rs` or
    `src/gameplay/rides.rs`.
16. **Hands off session plumbing.** `gateway.rs` and `osfr-gateway.rs` are untouched. The existing
    `settle_rides` hook is reused.
17. **One player's error never stops the server.** `settle` is infallible: no `?`, no unwrap, no
    arithmetic.
18. **A type's rules live on the type.**
    - The memo's meaning and its update rule live on `MountService` (field doc, `list_packet`,
      `reset`).
    - "Which sends count" is decided once: every roster goes through `list_packet`.
19. **Hot paths stay cheap.** Each call of `settle` after a message or tick costs:
    - an active-ride check
    - one pass over the inventory stacks, each a `BTreeMap` lookup (about 210 keys)
    - one `is_owned` pass per remembered ride

    It does no clone and no allocation when nothing changed: the empty `MountOutcome`, `RideWire`
    and `Outcome` vectors do not allocate. An owned list is built only when a roster is actually
    sent.
