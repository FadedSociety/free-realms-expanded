# T482: the Rides panel lists one row per owned ride item

The 168/5 roster now has one row per owned ride item (inventory instance), with that instance's tint and the item's own
catalogue alias, and a 168/6 summons exactly the instance whose row id it carries. Skills used: ponytail (full),
secure-code-guardian (hostile row ids), lean-structure.

## Structure

- Graph: not queried (this builder had no graph tools); `rg` found every user of `ActiveRide`, `list_packet`, `is_owned`,
  `owned_mounts` and `MountService::new` (`src/mounts.rs`, `src/gameplay/rides.rs`, one build site in `src/gameplay.rs`).
- Owner: `src/mounts.rs`. Catalogue helpers `owned_rides`, `is_ride_row`, `owned_instance`, `lowest_instance`; the service
  gains `spawn_row` (168/6, one instance), keeps `spawn` (lowest owned instance of a ride) and `spawn_by_item_definition`
  (lowest owned instance of that item), all three finishing in `spawn_instance`; `spawn_guard` is the old guid and
  restriction check, unchanged in order.
- `src/inventory.rs`: `Inventory::look(definition_id) -> Option<ItemLook { texture, tint_alias, default_tint }>`, read from
  the loaded `Definition` (the fields `write_attachment` sends). No new parsing.
- Looks reach the roster through the service, not `RideContext` (R: a deviation from the brief). `list_packet`,
  `roster_sync`, `settle` and `dismount_request` all build the roster without a context and the protected tests call
  them with an `InventoryState` only, so `MountService::load(path, &Inventory)` reads the look of every ride item once
  and `encode_mount_list` falls back to the ride's alias for an item with no catalogue row. `RideContext` is unchanged.
- Hub budget: `src/gameplay.rs` -3 lines/+2 (net -1; the mount service is built by `MountService::load`). `src/gameplay/rides.rs`
  needed no change.
- Deleted: the definition-level `is_owned` (replaced by the instance check) and the ride-id memo.
- Kept: `MountCatalog::owned_mounts` (public; `list_is_derived_from_owned_inventory_items` uses it). Nothing in production
  reads it any more.

## What changed

- 168/5 rows: id = `InventoryItem.id`; name, image set, members_only, is_upgradable, is_upgraded from the ride; guid = the ride
  actor on the active instance's row only; tint = `InventoryItem.tint`; alias = the item's catalogue alias, else the ride's.
  Rows are the instances with `count > 0` and `id > 0` whose item maps to a ride, ascending by id. Layout unchanged
  (client reader `008e74c0`; list reader `00b05600`).
- 168/6 id = a row id. The client echoes whatever row id its list held: `00bff6f0` sends the Lua id with the log line "Lua Spawn
  and automount: id %d", writer `00b05a80` puts one i32 on the wire (read back through IDA: it copies 4 bytes of the packet's
  +0xc field). An unknown, unowned, zero-count, zero, negative or non-ride id is refused by `spawn_row` with the existing
  roster refresh and notice (`MountService::handle`), and changes nothing.
- 168/8 picks the owned instance of that item with the lowest id.
- `ActiveRide` gains `instance_id`. `mount()` (board time) and `ride_lost` (every settle) now check that instance, not any item
  of the ride.
- Roster memo (T424): `SentRoster { rows: (instance id, item definition, tint), active_guid }`. `roster_sync` resends when a
  ride row appears, vanishes or changes tint, or the active guid changes. It still allocates nothing when nothing changed:
  one pass over the inventory, a binary search per ride row. A row's alias and the ride fields are fixed by the item
  definition, so the triple is every live field (documented on the struct).

## Threat note (client-controlled input)

A hostile client can send any i32 in 168/6: another player's item id (instance ids are per inventory, so it is unowned here),
a stale id after a trade, 0, a negative id, or a ride/item definition id that happens to equal an instance id. `spawn_row`
accepts only an id that is an owned (`count > 0`), positive-id inventory row whose item definition maps to a ride, so the worst
outcome is summoning a ride the player owns. Every other value is refused with the roster refresh and a notice, with no
state change and no debounce consumed.
