## Threat note

- Hostile client input: it can send 138/2 register, 138/5 cast-anim, 138/6 cast, 138/7 reel,
  138/15 special and the shared minigame lifecycle/menu packets. It cannot send a timestamp, a
  cap limit/window, an item id or a catch result. Its only cap-relevant action is a reel-in,
  which the service accepts only after its own Cast -> bite -> hook state; replays are refused as
  out-of-order and pay nothing.
- Reconnect: a handshake session carries the template guid, which equals the first account's
  character guid. The lead's owner gate refuses its publication; the regression ticks such a
  session before login, and the same test restores a forged non-empty history that the gate must
  ignore.
- The shared ledger is server-owned. `restore_hour_history` rejects guid 0, an oversized history
  or out-of-order timestamps and leaves the existing ledger unchanged (existing test).
- Refusal order: `settle_catch` checks the cap before `apply_grant`, so a refused catch pays no
  item, coins or XP; the gateway test asserts snapshot, save bytes and ledger are unchanged.

## Checklist

1. **A refusal changes nothing.** The gateway regression snapshots inventory/coins/XP, file bytes
   and the world ledger before the capped catch and compares after. **F186 correction:** the
   restore is back on the live gateway before staging (the lead's shape), not on the staged
   clone; it copies server-owned history, and a refused request still changes no gameplay state.
   Existing refusal tests pass.
2. **Rollback covers all state.** `FishingHourLedger` lives in `SharedWorld` and is published into
   `staged_world` inside the `prepared` closure; `*world = staged_world` only runs after save
   success. No `Rc`/`RefCell`/`Arc` side table.
3. **Apply deltas, never old snapshots.** The ledger replaces only the character's timestamp list
   with the committed server history; no inventory, coin or position snapshot is restored.
4. **Busy rules are mutual.** Fishing is already an `Occupation` row; F153 starts no new activity
   and changes no gate.
5. **Every entry path is gated.** The cap is inside `settle_catch`, reached from the one
   production `FishingService::enter`/`route` path used by the NPC menu; `begin` is the low-level
   test entry (documented in T029) and is not routed from gameplay. The ledger restore runs
   before `handle_at` on every dispatch, including reconnect.
6. **Reachable in production, tested through it.** The regression drives
   `Session::dispatch_message` with real tunneled application packets, `Session::tick`,
   save/load and a second session; it calls no internal service helper directly for the auth path.
7. **Survives reconnect.** Same test: the first session catches and saves, the session is dropped,
   a fresh session ticks before login (ledger unchanged), logs in, restores the history, and the
   capped catch is refused; after the hour a catch is paid again.
8. **Every exit path restores the player.** Fishing's `disconnect`/`reset` clear only the session
   count; the round teardown already existed. The ledger is not a lock and the player remains
   free to start another activity.
9. **Economy safety.** Cap check before `apply_grant`; no client quantity/id reaches the ledger;
   the blocked catch pays nothing. Inventory/coins/XP assertions are in the test.
10. **Wire format matches the client reader.** No wire field changed. The test packets match the

11. **Unique ids.** No new instance or lifecycle id.
12. **Others see changes.** Not applicable: the ledger is private server accounting; no public
    actor, outfit, mount or job changes.
13. **Content works end to end.** The test pays a catch, refuses the second within the window with
    the player-readable notice, and pays again after expiry; final coins/XP are asserted.
14. **Values live in data.** `catch_cap.enabled/window/max_paid_catches` stay in
