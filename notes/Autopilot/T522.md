# T522: Elite sets tick their meta collection (309 Elite Explorer, 306)

## What changed

- `src/collection_catalogue.rs`: `CollectionCatalogueContent` builds `meta: BTreeMap<i32, i32>`
  (source collection id -> meta collection entry id) once in `load` through `meta_map`:
  - sources are the collections whose `reward.collection_add` names a target T;
  - T must be captured, have as many entries as it has source sets, each source must name
    exactly one T entry by equal `name_id` (else by equal `icon_id`: (R), 309 has no name
    matches), and no two sources may name the same entry;
  - pairs whose source is itself an accepted target are dropped to a fixpoint, so a completion
    cascade is at most two levels and cannot loop.
  - `meta_entry` / `meta_pairs` are the read accessors.
- `src/gameplay/collection_pickup.rs`: the one-entry record body moved into `collect_entry`;
  `record_collection_entry` now, after a completion, looks up `meta_entry` and records that entry
  through the same staged path (`CollectionEventOrigin::CollectionBundleEntry`). The meta
  collection's own completion pays its reward through the unchanged `completion_grant`/`collect`
  path (309 pays item 70349). Both entries and both reward adoptions commit in the same staged
  transaction as the click. `load` logs the accepted target ids once.
- Tests: `tests/collection_rewards.rs` (14-pair map, 284 -> 2170 order and save, all eight sets
  pay 70349 once with a silent relog replay, full-bag refusal leaves 309 untouched) and
  `tests/collection_catalogue.rs` (a deeper chain whose source is another target is dropped).

No content JSON was edited. No hub file was edited.

## Reconstructed rules (R)

- Completing a source set records the entry its kind-10 `collection_add` target names (the 309/306
  effect). The client citation `0x0103b800` only proves the row carries `CollectionID=%d`: the
  effect is reconstructed from the captured catalogue's 14 matched pairs (8 icon matches
  284-291 -> 2170-2177, 6 name matches 299-304 -> 2150-2155), not from a recovered apply function.
- The 309 mapping by `icon_id` is (R). It is data-derived: no hand list of sets or entries exists
  in the code, so a corrected catalogue changes the map without a code change. A source with two
  accepted targets is refused at load, because a completion records exactly one meta entry.
- The cascade depth of two is policy from the brief, not recovered client behaviour.
- The meta event's `CollectionBundleEntry` origin label is (R); the ledger does not branch on it.
- The existing 38/10 `collected=true` field policy (T450/T480) is unchanged.

## Threat note (secure-code-guardian)

A hostile client controls only the 26/8 click target guid. The guid must be a coin in the
server's own coin map, currently visible to that player and within the pickup range in the open
world; the entry id, the meta entry id and every collection id come from the server-side
catalogue, never from the request. Refusals (busy, wrong zone/out of range, full bag, XP/coin
overflow, unknown entry) return before or inside the staged clone, so neither the source entry
nor the meta entry, reward, bag or visibility changes; the snapshot assertions cover the full-bag
case twice. A replay is silent because the saved ledger's `collected`/`completed` sets are the
once-only guard for both entries, and the map's depth prune means a completion can never loop.
Item 70349 is a captured data reward (no client value), granted only after the saved ledger
completes 309 and only if the content set has a definition for it.

## Checklist

1. **A refusal changes nothing.** The whole click is staged on a clone and only assigned on
   success. Two full-bag tests cover both failure points and snapshot state and visibility before
   two refused completing clicks: one refuses the source reward at 100 stacks, the other (99
   stacks) lets 291's own 70348 through before 309's 70349 is refused. Both assert `!out.changed`,
   an unchanged snapshot, untouched entries (including 2177/309) and a visible coin; the 99-stack
   test then makes room and retries to prove 70349 is granted exactly once. A later (meta) refusal
   returns a fresh refusal outcome, and the refusal log names the entry that failed.
2. **Rollback covers all state.** The clone holds the ledger, bag, profiles, wallet and
   visibility; the map lives in the read-only shared `Arc<CollectionWorld>`. Refusals before the
   clone (busy/range/zone) and errors inside it discard everything.
3. **Apply deltas, never restore old snapshots.** `collect_entry` takes a fresh
   `reward_snapshot()` per entry and adopts it immediately; no earlier snapshot is restored.
4. **Busy rules are mutual.** No new activity and no occupation gate; the existing click gates
   (`activity_busy`, zone, range) are reused unchanged.
5. **Every entry path is gated.** There is one record path (the gated 26/8 coin click); the meta
   entry is not client-named and runs inside that same path.
6. **Reachable in production, tested through it.** The tests drive
   `handle_in_world` 26/8 clicks and assert the packets/ledger from the real record path.
7. **Survives reconnect.** Both ledger entries are part of `ProgressionExtrasState`; the all-sets
   test relogs with the saved state, replays every coin and asserts silence and no extra item.
8. **Every exit path restores the player.** No activity/location state is added; a refused click
   leaves the coin visible and clickable, and a successful one only hides the coin as before.
9. **Economy safety.** Entry ids and the meta entry are server-side catalogue data; the client
   only supplies a coin guid. The reward is paid only from the saved ledger's completion, and the
   once-only guard is the ledger itself.
10. **Wire format matches the client reader exactly.** 38/10 unchanged; verified against
    `0x008d8570` and the case-10 insert/banner path at `0x00939e2f`. The 284 test asserts the
    exact 33-byte AddEntry for 2170 (entry 2170, icon 2239, name 419916, collection 309, index
    1, collected true) against reader-derived bytes.
11. **Unique ids.** No id is allocated; the captured entry ids are unique and the catalogue loader
    already refuses a duplicate entry id.
12. **Others see changes.** Collection state is personal (T450 `(R)` coin visibility); nothing is
    broadcast to other players.
13. **Content works end to end.** All eight Elite sets are completed through coins and the test
    asserts set rewards and the final 70349 grant, not an intermediate flag.
14. **Values live in data.** The map is derived from `collection_catalogue.json`; no set, entry,
    icon or item id is hardcoded in the source. The two-level bound is a structural policy.
15. **Canaries break production code.** The canary changed `meta_map` itself; the observed
    failures are recorded above and the code was reverted.
16. **Hands off session plumbing.** No session, teardown, transaction or save-ordering change.
17. **One player's error never stops the server.** The cascade runs inside one session's staged
    gameplay state and returns `Err`/a chat refusal for that player; it performs no work in a
    shared tick and no `unwrap` on client data.
18. **A type's rules live on the type.** The map, its one-to-one rule and its depth prune are
    documented on `CollectionCatalogueContent`/`meta_map`; the runtime one-level rule is
    documented on `record_collection_entry`.
19. **Hot paths stay cheap.** Load-time map only; no per-tick work and no clone unless a
    collection actually completes.
