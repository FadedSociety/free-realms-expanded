# T887: an owned stack is never shown as a Rental; the Inspect portrait finding

Two native fails from the 2026-10-29 two-client session.

## Rental on an owned item: fixed

The owner's Action Power Warrior Hightops showed as a Rental with 4099 days left, quantity 2, "cannot use this
right now". No code path creates a `RentalState` for a grant (`Inventory::grant` always stores `rental: None`, and
the saved stack for that item was `rental: null`), so the server state was right and the wire was wrong.

Cause: every stack update (`38/3`, built by `inventory::item_update` for a stacking grant, a consume or a reward)
ended with `last_cast_time`, which for an owned item is `0x7fffffff`. The client does not read those two dwords as a
last-cast value:

- 38/3 case of `HandleClientUpdate` (`009392c0`): the last two dwords go to `008d0d90` -> keyed setter `008c7090`.
- `008c7090` looks the item up (`008becc0`) and compares them with the item's block at `+0x28` or, when there is
  none, with the global null time `dword_1BE48B8/BC` (zero, no writer in the exe). A different value runs
  `0103e080`, which allocates the block (`0103df50`) and stores the value in it.
- That `+0x28` block is the rental block: `008fa4b0` (instance reader) allocates it only when the rental flag byte
  is set and fills it with `008cd5e0` (expiry, upsells, bundle id); `0103e030` turns it into "seconds remaining"
  (0 when there is no block or it holds the never-expires sentinel) and `0103dfe0` is the "expired" test. The last-cast
  time is `+0x20`, written by `008cb5a0` from the instance record only.
- `0x7fffffff` seconds is 2038-01-19; from 2026-10-29 that is exactly 4099 days. Every stack update turned the item into
  a Rental with that expiry, which is also why a second copy "overrode" the first.

Fix: `ItemUpdateV2.last_cast_time` is now `rental_expiration`; `item_update` sends the item's rental expiry, or 0 (the
null time, a no-op in the client) for an owned item. The earlier "V2 fix" had moved the field from the rental expiry to
the last-cast time on a wrong reading of `008d0d90` (the Items and Inventory guide's "(the last-cast field)", marked
R); the guide line should be corrected by the notes task (not edited here: other notes are not mine).

Merging was already right: `grant` stacks only into a same-definition, same-tint, non-rental stack.

## Inspect portrait: not settled, needs a native check or the upload ingress

What the 149/1 reply already carries is correct (checked against the client, no change made):

- Header guid: `008d6370` reads it and `00984960` finds the actor with it; the actor is the AddPc'd character.
- The `BaseClient.Inspect` data source (`00cc0760`) reads `PlayerGUID`/`PlayerName` from the proxy built by `00ad8880`
  out of the actor (not from our payload), and `ProfileID` (`+200`) from the payload's active profile, which
  `public_look` fills from the live profile. `PlayerInspect.gfx` binds those columns (`PLAYER_GUID`, `PROFILE_ID`).
- The face is not part of the inspect payload. The movie calls `AutoMovieClipEntry.LoadPlayerPortrait`, which loads
  `imgps://<guid>`; the client resolves that through the Fotomat portrait manager (`FotomatPortraitDataManager`,
  request sender `00bd3ff0`, reply `00bd4a50`). `00bd4a50` stores the image only when the 156/3 reply carries a
  non-empty image; our `fotomat::encode_reply` always sends an empty one (its comment: "until the lead's upload
  ingress stores one"). With no image the client falls back to the empty-portrait icon, which matches "slot blank".
  The client's own routes to an image are the HTTP upload of `portrait.png`/`headshot.png` (`ScreenshotManager::
  PostPortraitToHttp`, `00b4fd60`) and, for a present actor, a local headshot render (`ScreenshotManager::LoadHeadShot`,
  `00b4f870`, drained by `ScreenshotManager::Update` `00b50330`).

So a fix is image bytes, not another packet field: either the portrait upload ingress (HTTP endpoint plus the 115 CRC,
a security-owned change) or confirming the local render runs for a remote actor in a native test. Nothing was
changed for it; the 156/2 -> 156/3 route and the inspect pin tests are untouched.
