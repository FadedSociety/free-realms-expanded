# T405: AddPc carries the active job's equipped weapon wield type

## What changed

Other players used to receive every character's AddPc with `wield_type = 0`, so a late
joiner saw every armed player unarmed. The public presentation now carries the active
job's slot-7 weapon definition's `wield_type`, the same value the live 35/6 already sends.
No new packet field, module, persisted field, selector or dependency.

| File | Change |
|---|---|
| `src/inventory.rs` | `Inventory::equipped_wield_type(profile)`: the `(profile, slot 7)` equipment row → the item with that id and `count > 0` → `content.definitions` → `wield_type.max(0)`; 0 for every missing row. The same join as `abilities::equipped_weapon_matches`; never reads `EquippedItem.category`. |
| `src/gameplay/profile_outfit.rs` | `Gameplay::public_wield_type(profile)`: one-line seam over the private inventory (non-hub child). |
| `src/gateway.rs` | `player_presentation` sets `look.wield_type` beside `attachments_wire` when gameplay is loaded. The stale 2-line `(R)` comment ("speed and wield type keep the defaults") became 1 line, so the hub is **net 0** (2221 → 2221 lines). |
| `src/players.rs` | Doc comment on `PlayerPresentation.wield_type`; `validate` refuses a negative value (second safety net behind the accessor's clamp). |
| `tests/multiplayer.rs` | `AddPc` parser reads the wield dword at the reader offset; seven T405 tests (below). |
| `tests/players.rs` | `negative_wield` joins the rejected-presentation list. |

The refresh path is unchanged: `osfr-gateway.rs` already rebuilds the presentation with
`set_presentation` on every committed gameplay change (T027), and `join_player` builds it
at join, so the value reaches late joiners and relogs without new plumbing.

## Client evidence

| Fact | Address |
|---|---|
| AddPc reads an i32 into packet +0x1a4 after the mount lift | reader `0x0091aee4` (`0x0091aed1` bounds check, `0x0091aee6` store) |
| Spawn (35/1 handler) passes packet +0x1a4 to the actor wield setter | `0x009300ea`–`0x009300f6` → `0x009582c0` (same block stores speed to actor +0x3ec at `0x009300d0`, active profile via `0x0096a3e0`) |
| 35/6 EquipItemChange reads guid, item id, attachment (`0x008e86f0`), profile (+0x1e8), unused (+0x1c), wield (+0x1ec) | body reader `0x0090a1f0` (via `0x00919c20`); ctor `0x008dcb40` |
| 35/6 handler passes +0x1ec to the same setter, unconditionally | `0x0093159d`–`0x009315a9` → `0x009582c0` |
| 35/0x3d `PlayerUpdatePacketUpdateActiveWieldType` passes its dword to the same setter | `0x00930454`–`0x00930460`; dtor `0x008a06f0` at `0x00930420`/`0x00930474`, ctor `0x008b3e80` |
| The setter stores the value at actor index 0x13f (+0x4fc), unless `0x008c6420` overrides it | `0x009582c0` |

So AddPc's field and 35/6's trailing dword are the same actor property, named by the
0x3d packet: the active wield type. `notes/Research/AddPc Layout.md` row 175+Z agrees.
Legacy's AddPc builder (reference only) never sets it.

Cross-check: the fixture values match the recovered constants (`piece_054` Brawler 13,
`piece_037` Medic 14, `piece_035` Archer 11).

## (R) choices

- **Slot 7 is the weapon slot** whose definition decides the wield type, as
  `abilities::equipped_weapon_matches` already rules. The client gives one wield value per
  actor; which slot the original server read is not recovered.
- **0 without a weapon**, and for a missing item/definition or a negative content value.
- The value is derived on every presentation build, never persisted.

## Not changed (evidence for later slices)

- **35/7 trailing i32 is not a wield value.** The 35/7 handler (`0x0093047e`–`0x0093057d`)
  attaches each row through `0x0095d620` and never calls `0x009582c0`. So a job switch does
  not update current viewers' wield type: they keep the old job's value until a 35/6 or
  a re-meet. A follow-up could send 35/0x3d (`0x008b3e80`) after a switch.
- **35/6 for a non-weapon slot clears the viewer's wield type.** The handler calls the
  setter for every 35/6, and `inventory.rs` writes the equipped piece's own definition
  value (0 for clothes; the unequip packet in `gameplay.rs::item_change_packet` writes 0).
  Equipping a shirt therefore shows an armed player unarmed to current viewers until they
  re-meet. Out of scope here (the brief forbids changing 35/6); a follow-up should send the
  slot-7 value (`equipped_wield_type`) in every 35/6.
- `count == 0` cannot occur in a loaded state (`validate_state` refuses it); the accessor
  checks it anyway to mirror the abilities rule.
