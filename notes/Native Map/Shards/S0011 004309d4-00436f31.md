# Shard S0011 - 004309d4-00436f31 (85 functions)

All 85 targets are GFC client GUI framework code. No packet class, opcode constant or serialiser
appears anywhere in the range, so this shard has no wire links and no server-contract inference.
Everything below is client-side UI machinery. Method: `nmq` queries over
`lab/native-map/run/map.sqlite` plus a read-only structural parse of the preserved binary
`lab/working/OSFR.Client/OSFR Client/FreeRealms.exe` (PE sections, .rdata vtable tables, MSVC RTTI
complete-object-locators). The vtable/slot statements marked "observed" come from that binary parse,
not from the Ghidra export, and are written out here in prose only.

## What the range contains

**1. Control-tree notification machinery (004309d4-00434f8b, engine.gfc.core).**
A base control class whose children are enumerated with a stack `GObjectIterator` filled through the
container's slot +0x50 (`004309d4`, `00430a9b`, `00430bfd`), and whose change notifications are
32-byte parameter blocks dispatched down the tree by `00430d7b`
(`FUN_00430d7b(block, 0x33/0x133/0x211)` recursions). Sub-object references are obtained through the
get-or-create pairs `004128ee`/`0041aaf2` (create a 0x34-byte data object when missing, otherwise take
the interface of the existing one) and finished by the commit pair `004311c5`/`0043190a`
(attach the new object via slot +0x9c, or send the block through the manager from slot +8).
The associated wrappers `004312ed`-`00431708` and `00431a36`-`00431c54` each acquire a record via
FUN_004128ee / FUN_0041aaf2, invoke one fixed slot of the held object (+0x1c, +0x34, +0x38, +0x3c,
+0x40, +0x44, +0x48, +0x4c, +0x50, +0x58), and then run the commit pair. They are named after the
slot they call (`CallAccessSlotXX` / `CallObjectSlotXX`) because read-vs-write direction is not
anchored: the same slot ids are used as getter access in the base reader `00436f31`, and the acquire
helpers are accepted in the map as `InitEventCursor` / `InitListenerRefs`, so "typed property write"
would overclaim.

Observed: that whole wrapper set is installed at fixed slots +0xb8..+0x110 of roughly sixty named
.rdata vtables - GLabelCtrl, GButtonCtrl, GCheckBoxCtrl, GRadioButtonCtrl, GComboBoxCtrl,
GScrollPanelCtrl, GPanelCtrl, GFormCtrl, GWindowCtrl, GTabCtrl, GTableCtrl, GTreeCtrl and the
GuiButtonCtrl/GuiCheckBoxCtrl/GuiComboBoxCtrl/GuiEditCtrl/GuiFlashCtrl/GuiCustomCtrl/GuiPropEditCtrl/
GuiScrollPanelCtrl/GuiTableCtrl/GuiTabCtrl/GuiTreeCtrl/GuiTreePrivateCtrl/GuiImageCtrl/GuiLabelCtrl/
GuiPanelCtrl/GuiRadioButtonCtrl/GuiWebBrowserCtrl/GuiFreeLayout/GuiHLayout/GuiVLayout/GuiSurfaceCtrl/
GuiTradingCardCtrl/GuiApp family. The identical function pointers across all of those classes mean the
wrappers are base-class implementations inherited by every control, i.e. the GCtrl-level property
plumbing shared by the whole widget tree.

**2. Application-level handlers (engine.gfc.app).**
`00434a67` is the window/application event dispatcher (activation, resize, move, visibility and one
event that interns and resolves the class name `GApplication`); `00436eb1` (`GuiAppShutdownUI`) is
the shutdown override that purges control state via `00431f07` and then calls the already-labelled
`GApplication::ShutdownControlManager` (`00405ddc`). Observed: `00436eb1` occupies slot 86 (byte
+0x158) of the GuiApp vtable, so GuiApp owns the override and GApplication only names the callee's
class; `00434a67` sits at slot +0x29c of one of the large GFC driver tables.

**3. Data-access layer (engine.gfc.serialization).**
`00435394` installs `GStringAccess::vftable` at +0x18 (GStringAccess init), `004353e2`
(`DataAccessCreateDispatch`) is the five-way create/destroy dispatch whose 0x34-byte objects receive
the derived vtable set (0x175ecf8/0x175ecf4/0x175ec58/0x175ec10) after `GDataAccessImpl::vftable` is
written transiently at +0x1c, and `004354b2` is the shared destructor that detaches from the owner
through the owner's slot +0x5c and then resets `GInterface::vftable`. `00436de0`/`00436e5d`
construct/destroy the 0x34-byte access object whose vtable set (`PTR_FUN_0175f0e8`,
`PTR_LAB_0175c450`, `PTR_LAB_0175f0e4`, `PTR_LAB_0175f068`) is identical to the constructor at 00528f2f
used by `004128ee`/`0041aaf2`. The five 12-byte wrappers `00436c51`/`00436c5d`/`00436c75`/`00436c81`
are **not** vtable installers: byte-decoding shows they just call the tree/container-header
initialisers `FUN_0041bd1c` / `FUN_0041bd41` / `FUN_0041f75d` / `FUN_0041f787` on ECX and return the
receiver (`00436c69` wraps the unmapped `FUN_0041f717`); the data-access constructors call
`FUN_0041bd1c`/`FUN_0041bd41` directly.

**4. Item classes, box-layout base classes and data readers (engine.gfc.core).**
`00435577`-`00436f31` contains several small classes with the vtables
`PTR_FUN_0175ee28`, `PTR_FUN_0175ee80`, `PTR_FUN_0175eed8`, `PTR_FUN_0175ef60`, `PTR_FUN_0175efe8`;
they all chain into the shared `GInterface` destructor `004354b2` and detach through owner slot +0x5c.
Class corrections from review: `00436edc` is the default constructor of the 0x175eed8-vtable class at
the base of the box-layout chain (the accepted constructors 0043b734/0043b78d call it as their base),
`00435c70` is the box-layout base copy constructor (GVBoxLayout/GHBoxLayout run it and then overwrite
+0/+4), `004358c7` copy-constructs the class whose +0x44 field is a **child vector** (copied through
the vector copy constructor `00427f67`, not an interface), and `00436f22` is a five-byte `e9` jump
thunk to the destructor body `0043591d`. The data readers are the payload of this block:

- `0043598a` reads `FixedSize` and instantiates/links every entry of the `Items` property.
- `00436baa` reads `ItemIndex` and `StackType` (with a default block) after delegating to `0043598a`.
- `00436938` reads `UseSeparator`, `UseOuterMargin`, `OuterMarginId`, `SeparatorId`, `OuterMargin`,
  `Separator` and `Direction` (default block) - the box-layout property set. Observed: this function
  is the +0x44 slot of both the GVBoxLayout and GHBoxLayout vtables, and `00436350` is their +0x20
  layout-solve method.
- `00436f31` is the base-control reader: `CtrlFlags` (default `GFC_CF_NOTVISIBLE`), `Placement`,
  `ClientOrigin`, `StyleId`, `MinMaxInfo` (0x24-byte structure), `InheritedMap`, `NoninheritedMap`,
  `ToolTipInfo`, `TopLayerBlitFx`, `BottomLayerBlitFx`, `Layout`, `ActiveChildPath`. Observed: it is
  slot 62 (byte +0xF8) of the vtable of GuiFlashCtrl, GuiCustomCtrl, GuiWebBrowserCtrl, GuiFreeLayout,
  GuiVLayout, GuiHLayout and GuiTradingCardCtrl; its 21 callers in the 0x60xxxx range are the
  per-window readers that extend this schema.

`00436350` + `00435d1a` implement the box-layout arrange/measure pass (space distribution over
seven-dword item records, orientation nibbles 0x0f/0xf0 of the control flag word at +0x10);
`00435d1a` has both a scaled path and a weighted path (per-record weight with a zero preference byte
counting as 1, clamped by a limit/priority field).

## Cross-function conclusions

- The GFC widget layer is data-driven: a control is built from a data-access object by reading named
  properties (`FixedSize`, `Items`, `StackType`, `CtrlFlags`, `StyleId`, ...) and every property read
  runs through the same named-property plumbing (`004e889c` intern, `FUN_004eb55e`/`0054616f` typed
  read, `004dc61b` release), with per-class readers chaining to their base reader (`00436f31`).
- The control hierarchy maintains two kinds of managed sub-objects (kind 1 = field +0x18, kind 2 =
  field +0x14) plus a manager fetched from the container slot +8; changes are published as 32-byte
  parameter blocks (`00430ff9`, `004311c5`, `00431757`, `0043190a`, `00431ca2`).
- Class-level facts for the vault: `GFC` is the client GUI framework name; the class registry around
  0x53e8d6-0x53f63a registers `GCtrlContainer`, `GObjectIterator`, `GObjectBase`, `GStringObject`,
  `GObjectChildList`, `GObjectDesc`, `GObjectHandle`, `GObjectIOInfo` and the `G*Ctrl` widget classes
  in the same process. `GDataAccessImpl`/`GStringAccess`/`GDataAccessWrapper`/`GStringAccessWrapper`/
  `GTableAccess`/`GTreeAccess` are its property-access interfaces; the Gui* classes are the game's
  wrapper layer over the G* widget classes.

## Open questions

- Container slots +0x44 / +0x50 / +0x94 / +0xa4 / +0x110 / +0x114 are only characterised from their
  call sites (remove/enumerate/notify); no vtable-slot dump of the container class was recoverable
  because those vtables live in the unnamed .rdata tables at 0x175d8d0 / 0x175e380 / 0x175f20c, which
  have no MSVC RTTI locator.
- The 32-byte parameter-block tag/mask values (0xf, 0xe, 0x12, 0x33, 0x133, 0x211, 0x8800, 0x24924)
  are recorded but not decoded.
- The 0x175eed8 and 0x175ef60/0x175efe8 vtables are the box-layout base chain (their constructors are
  called by the accepted GVBoxLayout/GHBoxLayout constructors), while 0x175ee28/0x175ee80 are the two
  item-class vtables whose C++ names are still unknown; GCtrlLayoutItem is a plausible candidate from
  the RTTI class list but unproven.
- The direction of the accessor wrapper slots (CallAccessSlotXX / CallObjectSlotXX) is unanchored -
  the same ids read values in 00436f31 - and the object resolved by FUN_0041aaf2 is accepted in the
  map as InitListenerRefs, so set-vs-get and the object's type remain open.
- FUN_0041f717 (wrapped by 00436c69) is unmapped, so that helper's net effect is unknown.
- The two managed sub-object kinds (1/2) map to roles (layout vs data) only by the property names read
  into the fields they guard; an independent caller-side anchor was not found in this shard.
