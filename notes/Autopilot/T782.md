# T782 - Card start screen: the client's close retires the run, 39/6 and 39/7 answered, card service events (lead brief, native 2026-10-27)

Native run 2026-10-27: Play on Card Duelist got the 39/16 offer, the start screen opened, and the X sent 39/6 and 39/7,
which gameplay never answered ("unknown application message"); a second Play then got a fresh offer.

## Root cause

The 39/6 was ignored because the run was already gone. The client does not send 39/6 first. Its X runs
`MiniGame:LeaveMiniGame` (`009bd240`), which sends the generic 26/42 Close (`CommandPacketClosedMinigameEndScreen`,
constructor `008a2eb0`, called from `0092f300`; four bytes `1a 00 2a 00`), and then the cancel path: `00938fe0` sends
39/6 through `009be8e0` (`009bdc60(6, -1, -1)`, current instance) and `MiniGame:CancelMiniGame` (`009bef50`) sends 39/7
(`009bdc60(7, instance, -1)`). The saved server trace of the 02:56Z native run
(`lab/runs/client-baseline-20261027T025616Z/server-trace.jsonl`) shows, for each of the three plays, the 26/42 first
and then 39/6 + 39/7: instance 61,000,001 at 106933 -> 107914, 61,000,002 at 181756 -> 182739 and 61,000,003 at
477852 -> 478869 (ts_ms).

The server fed that 26/42 to the card run:

- `src/gameplay/card_launch.rs:29` (`handle_card_game`) routed every in-world packet to the card run while
  `Launches::is_active`;
- `src/card_game.rs:144` (`Launches::route`) handed it to `MinigameRuns::handle_client`;
- `src/minigame.rs:406-420`, the shared 26/42 branch, retires an *Offered* run as `Cancelled` with no reply (right for
  chess's start screen, wrong for a card run, whose end is the 39/6).

So the run was retired silently by the 26/42; the 39/6 and 39/7 then found `is_active() == false`, fell through every
handler and were traced as unknown. That is also why the second Play got a new offer (61,000,002): the first run had been
retired by the Close. `MinigameRuns::handle_client` itself was correct for 39/6 and 39/7.

## What changed

- `src/minigame.rs`: `MinigameRuns::names_run(packet)`, a family-39 packet naming the current or last run.
- `src/card_game.rs`: `Launches::owns(packet)` (delegates to it).
- `src/gameplay/card_launch.rs`: `handle_card_game` routes only packets the run owns (replaces the `is_active` gate).
  Nothing but the run's own 39/x reaches it, so the 26/42 falls through to the other handlers exactly as in a session
  with no card run, and the 39/7 ack of the just-ended run is still routed (accepted, no reply). `is_active` still
  feeds the busy rule (`Occupation::CardGame`). (F800: once the run is Won/Lost, `owns` also takes the 26/42 results
  close so that future results path retires the run; see `F800.md`.)
- `src/gateway.rs` (CRLF kept, net 0 lines): the existing `card_game` label also names 39/7, so the ack of a card
  cancel is "handled" instead of "unknown application message". (Chess's and the movies' 39/7 now also trace as
  `card_game` when gameplay sends no reply; for that packet the label's remaining effect is that
  `known_no_reply` accepts it instead of rejecting it as an unknown application message. The
  pre-world quiet list does not name it, so nothing else changes.)
- `src/bin/osfr_gateway/card_listener.rs`: one JSON event line per step, drained by `Server::poll_card`:
  `card_connected {peer}`, `card_gateway_request {peer, host, port}` (the 414 answered), `card_login {peer, ok,
  character}` (the character guid only on success), `card_command_unhandled`, `card_closed {peer, reason,
  character}` with the reason `eof`, `deadline`, `read_failed`, `bad_frame`, `bad_message` or `write_failed`.
  Unhandled commands and each answered kind (414, 411 and, since T808, ping) have their own 16-line per-connection cap
  (R); a capped frame is not even serialized. (F800: the cap was one shared `answered` counter before, so sixteen 414s
  could suppress the one `card_login` line.)

## Threat note

A hostile client can send any 39/x packet with any instance, group, game and length, and a 26/42 at any time. Only a
packet naming this session's own card instance reaches the run; a wrong group or game id is ignored, a wrong length
is a per-message `Err` (only that single request is dropped; in a combined `[0, 25]` datagram the whole bundle is
refused before anything commits, so only the sender's session ends and the game state is unchanged), and a 26/42 can
no longer end an offered or started run (it retires only a Won/Lost run, the client's results close). Nothing here
changes a save, an item or a coin. A client that never cancels keeps only itself busy (session-only run). Listener
events are built from typed values (peer address, class id, guid, a fixed reason word): no ticket, session id, user
name or client text, so nothing a client sends can forge a log line. Open (R): the connect/close lines are one pair
per accepted connection, bounded by the existing 16/4 connection caps but not by connection rate.
