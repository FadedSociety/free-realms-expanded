# T658 - Enemy drops from the item-pass evidence

Brief: wire the 142 `quest-lines/wiring/drop.json` rows into the field-kill and battle reward data.
Result: **one** row survives the match (Yeti yarn, battle 12310). The other 141 are skipped with a reason
below. This is far fewer than the brief expects, and the lead should read the skip table before planning more drop work.

## What changed

- New `src/encounter/battle_drops.rs`: a `drops` list per `field_battles.json` battle row
  (`item_id`, `quantity`, `chance` 0..=1, `source` tags; load-time bounds, <= 4 rows, `(R)` rule through
  `field_rewards::validate_source`), and one roll per win. A hit rides out as the new
  `EncounterReward::bonus_items`.
- `src/gameplay/encounter_rewards.rs`: `bonus_items` are granted only if `accepts_reward_bundle` says the
  bag takes them; otherwise the drop is lost and the win's coins, prize and XP are untouched (item 17: a full
  bag must not turn a win into a tick `Err`).
- `data/content/field_battles.json` battle 12310 (Petty Yetis): one drop, item 893 "Yeti yarn", chance 0.25 (R).
- `tests/battle_item_drops.rs` (5 tests) and 2 unit tests in `battle_drops.rs`.

Field kills: **no change.** The only field-kill rows that match a shipped field enemy (Hooligan, Bixie
Soldier) are Wild Eagle / Wild Hawk, which are pet pals, not catalogue items (see skips). So
`field_kill_rewards.json` stays coins and job XP only.

## Checklist

1. Refusal changes nothing: the only new refusal is a bonus item that does not fit; the bag is untouched and the
   win's other payouts are applied (`a_bag_with_no_slot_loses_only_the_drop`, canary: removing the guard fails it).
2. Rollback: no new state outside the bag; `grant_bundle` is already staged on a clone.
3. Deltas, not snapshots: `grant_reward` adds to the live bag.
4. Busy rules: no new activity.
5. Entry paths: the roll sits in the single battle-win site; `realm win` (dev `debug_win`) is a separate dev
   path that does not roll drops (dev-only, no player impact).
6. Production-reachable: tests run marker click, Go, melee kills, results through the gateway.
7. Reconnect: the item lands in the saved bag at win; nothing pending persists. Mid-win disconnect has no
   new state.
8. Exit paths: unchanged.
9. Economy: yarn is junk meant to be sold to a merchant; 25% per repeatable win is (R) and tunable. It is a
   farmable coin source if its sale price is high; the sale price is unknown (open item). The roll is
   server-side only; no client value is read.
10. Wire format: no new packet. The drop uses the existing inventory-add replies from `grant_bundle`.
11. Unique ids: no ids minted.
12. Others see changes: inventory is private; unchanged.
13. Content end to end: the drop is non-empty, granted, and asserted in the bag after a real win.
14. Values in data: `chance`, `quantity`, `item_id` in `field_battles.json`, bounds validated at load.
15. Canaries: (a) the roll call replaced by `Vec::new()` fails the forced-drop test; (b) the fit guard replaced by
    `true` fails the full-bag test. Both reverted.
16. Session plumbing: untouched.
17. A per-player failure never reaches the tick: a full bag is a silent skip, not an `Err`. Chance is bounded
    to 0..=1 and finite at load.
18. Type rules on the type: `BattleDrop` owns its bounds (`validate`); `EncounterReward::bonus_items` documents that
    it never refuses the rest.
19. Hot path: no per-tick cost.

Threat note (secure-code-guardian): a hostile client sends nothing that reaches the roll; only a server-observed
battle win does. The roll is server entropy; the item id and quantity come from content, bounded (<= 100, catalogue
checked at roll by the grant). A replayed win cannot pay twice (the existing results-close and replay tests still hold).
Content tampering is the lead's file set.
